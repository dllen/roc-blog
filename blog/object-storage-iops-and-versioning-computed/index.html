对象存储的两笔账：IOPS 峰值与版本放大

#系统设计#架构设计#读书笔记#存储系统

对象存储的两笔账？买多少盘、以及版本控制要留多少历史。讲义把对象存储的设计哲学讲得很清楚（不可变、键值、一次写多次读、元数据与内容分离），也给了容量估算，但容量账和 IOPS 账被合在了一起，而版本控制的存储代价更是没提。这篇把三笔账分开算。

这篇不复述译文，也不搬运中文译本的任何段落。它复述这一章的骨架（三类存储的对比、术语、范围与估算、高层设计、上传下载流程），然后补三个自写模型：容量盘数与峰值 IOPS 盘数是两笔账、LIST 的元数据代价、不可变 + 版本控制带来的存储放大。

口径说明

  • 源笔记是 Alex Xu《System Design Interview — An Insider’s Guide》第 24 章的社区中译。上游两仓库的 LICENSE 在 main/master 分支经 raw 通道取均返回 404，上游许可未能确认；原书是商业出版物。故本篇为导读式：只复述章节骨架与需求数字，不引用译文原文或原书段落，不使用译本配图，正文主体是自写模型与判断。
  • 三个脚本均为自写增量，只依赖 Python 标准库；输出为实跑结果，逐行可复现（三段计算都不含随机数）。
  • 与已发文章的重叠见「这一章不重复已发的内容」一节。

一、本章骨架：三类存储、四个特性、五个部件

三类存储的取舍（讲义给了一张对比表）：块存储（HDD/SSD，可挂载、可格式化，性能高、成本高、面向虚拟机与数据库）、文件存储（建在块存储之上，提供目录与文件抽象，性能中到高、面向通用文件系统访问）、对象存储（以性能换耐久性、规模与成本；没有层级目录，数据以扁平结构存放；面向冷数据、归档与备份；RESTful API 访问；海量可扩展；强一致性——S3 Standard-IA 的 SLA 是跨多可用区 11 个 9 的耐久性、设计可用性 99.9%）。

术语：存储桶（对象的逻辑容器，名称全局唯一）、对象（单个数据片段，含数据与元数据）、版本控制（同一桶内保留同一对象的多个变体）、URI（每个资源的唯一标识）、SLA。

范围（讲义用问答敲定）：功能是存储桶创建、对象上传/下载、版本控制、列出桶内对象；大小对象都要高效支持；一年存 100 PB；假设 6 个 9 耐久性、4 个 9 可用性；非功能需求还有存储效率——在保持可靠与性能的同时压低成本。

讲义的粗略估算：20% 小对象（<1MB）、60% 中等（1–64MB）、20% 大（>64MB），按中位数 0.5MB / 32MB / 200MB 取值；100 PB（10¹¹ MB）、存储使用率 40% ⇒ 6.8 亿个对象；元数据按 1 KB/对象 ⇒ 0.68 TB。并且指出瓶颈可能在磁盘容量或每秒 IO：SATA 7200rpm 每盘 100–150 次随机寻道。

四个设计特性：对象不可变（可删可替换，不能更新）；本质是键值存储（URI 即键，HTTP 取内容）；一次写多次读（引用 LinkedIn 研究：95% 的操作是读）；小对象与大对象都要支持。

UNIX 类比：保存文件时创建 inode（文件名 + 文件块指针列表），文件数据散落在磁盘各处；访问时先取元数据再取内容。对象存储同理——元数据存文件信息、内容存磁盘；把两者分离，就能独立扩展。

高层设计五个部件：负载均衡器、API 服务（无状态，编排对元数据存储、对象存储与 IAM 的调用）、IAM（鉴权授权访问控制的中心）、数据存储（按对象 ID/UUID 操作）、元数据存储。

二、增量一：容量盘数与 IOPS 盘数是两笔账

讲义说瓶颈可能在容量或 IOPS，然后只用容量算出了 6.8 亿对象。把两笔账分开算：

"""对象存储：容量要多少盘，峰值 IOPS 要多少盘——两者不是同一笔账。

用讲义给的量：100 PB、存储使用率 40%、6.8 亿对象、SATA 7200rpm 每盘 100-150 IOPS。
只依赖标准库；输出确定性。
"""
STORAGE_PB = 100
UTIL = 0.40                # 存储使用率（讲义）
DISK_TB = 10               # 单盘容量（估）
IOPS_PER_DISK = 125        # 讲义：100-150 取中值
IO_PER_OBJECT = 1.95       # 每对象平均 IO（1 次写 + 95% 操作是读）

effective_pb = STORAGE_PB / UTIL
disks_for_capacity = effective_pb * 1e3 / DISK_TB          # 1 PB = 1000 TB
print("容量账：%d PB 存储、使用率 %.0f%% -> 有效容量需求 %.0f PB" % (STORAGE_PB, UTIL * 100, effective_pb))
print("  按每盘 %d TB -> 需要 %s 块盘" % (DISK_TB, format(int(disks_for_capacity), ",")))
print()
print("IOPS 账：峰值才是约束（总对象数除以一年没意义，突发才是）")
for burst_objects, window_s, label in ((100_000_000, 3600, "1 小时内写入 1 亿对象"),
                                        (1_000_000_000, 3600, "1 小时内写入 10 亿对象"),
                                        (100_000_000, 60, "1 分钟内写入 1 亿对象")):
    obj_s = burst_objects / window_s
    iops = obj_s * IO_PER_OBJECT
    disks = iops / IOPS_PER_DISK
    print("  %-22s -> %9.0f 对象/s、%9.0f IO/s -> 需要 %6s 块盘（占容量盘的 %.2f%%）"
          % (label, obj_s, iops, format(int(disks), ","), 100.0 * disks / disks_for_capacity))
print()
print("  => 结论：容量是按 TB 采购的（%s 块盘），IOPS 峰值是按突发采购的；" % format(int(disks_for_capacity), ","))
print("     两者不必落在同一批盘上——这与讲义「元数据与内容分离、可独立扩展」是同一条原则。")
print("  => 判据：先问「一天的写入峰值是多少对象/秒」，再决定盘的采购与 IO 预算；")
print("     用容量除以盘大小算出的盘数，只是上限，不是 IO 预算的答案。")

输出：

容量账：100 PB 存储、使用率 40% -> 有效容量需求 250 PB
  按每盘 10 TB -> 需要 25,000 块盘

IOPS 账：峰值才是约束（总对象数除以一年没意义，突发才是）
  1 小时内写入 1 亿对象          ->     27778 对象/s、    54167 IO/s -> 需要    433 块盘（占容量盘的 1.73%）
  1 小时内写入 10 亿对象         ->    277778 对象/s、   541667 IO/s -> 需要  4,333 块盘（占容量盘的 17.33%）
  1 分钟内写入 1 亿对象          ->   1666667 对象/s、  3250000 IO/s -> 需要 26,000 块盘（占容量盘的 104.00%）

  => 结论：容量是按 TB 采购的（25,000 块盘），IOPS 峰值是按突发采购的；
     两者不必落在同一批盘上——这与讲义「元数据与内容分离、可独立扩展」是同一条原则。
  => 判据：先问「一天的写入峰值是多少对象/秒」，再决定盘的采购与 IO 预算；
     用容量除以盘大小算出的盘数，只是上限，不是 IO 预算的答案。

三处结论：

第一，容量账：250 PB 有效容量 ⇒ 25,000 块盘（每盘 10 TB 估）。 这是讲义 40% 使用率假设的直接结果。

第二，IOPS 账：真正要问的不是「一共多少对象」，而是「峰值写入多少对象/秒」。 1 小时内写入 1 亿对象 ⇒ 27,778 对象/秒、54,167 IO/秒 ⇒ 需要 433 块盘的 IO 能力——只占容量盘的 1.7%。这说明两件事：容量是按 TB 采购的，IO 峰值是按突发采购的，两者不必落在同一批盘上（与讲义「元数据与内容分离、可独立扩展」是同一条原则，只是这次分的是盘的角色）。

第三，但极端突发会把顺序反过来。 1 分钟内写入 1 亿对象 ⇒ 166 万对象/秒、325 万 IO/秒 ⇒ 需要 26,000 块盘，比容量本身需要的 25,000 块还多。这时 IOPS 才是真约束，而采购没法解决——只能靠架构：写缓冲合并、小对象打包、或者接受突发期间的排队与降级。判据：先问「一天的写入峰值是多少对象/秒」，再定 IO 预算；用容量除以盘大小算出的盘数只是上限，不是 IO 预算的答案。

三、增量二：LIST 的代价必须按「页」算

讲义把「列出存储桶中的对象」列为功能之一，也把元数据存储单列为部件。两者放在一起才有意思：

"""元数据与 LIST：0.68 TB 的元数据怎么被读。

用讲义给的量：6.8 亿对象、元数据 1 KB/对象。
只依赖标准库；输出确定性。
"""
OBJECTS = 680_000_000
META_KB = 1
PAGE = 1000

meta_tb = OBJECTS * META_KB * 1024 / 1e12
print("元数据存储：%s 个对象 x %d KB = %.2f TB（讲义给的是 0.68 TB）" % (format(OBJECTS, ","), META_KB, meta_tb))
print()
print("列出存储桶中的对象（LIST）怎么读：")
page_bytes = PAGE * META_KB * 1024
print("  分页读 %d 个对象/页 -> 每页读 %d KB = %.1f MB" % (PAGE, page_bytes, page_bytes / 1e6))
full_bytes = OBJECTS * META_KB * 1024
print("  若全表扫一遍 -> 读 %.1f GB = %.1f TB" % (full_bytes / 1e9, full_bytes / 1e12))
print("  差 %.0f 倍 -> 所以 LIST 必须走**有序索引 + 分页标记**，不能全表扫" % (full_bytes / page_bytes))
print()
print("按页扫描的代价（客户端一页一页往下翻）：")
for pages in (1, 10, 100, 1000):
    read_mb = pages * page_bytes / 1e6
    print("  翻 %4d 页 -> 读 %8.1f MB（对应 %s 个对象）" % (pages, read_mb, format(pages * PAGE, ",")))
print()
print("判据：")
print("  - LIST 的代价必须按「页」算，不按「桶」算：桶里有 6.8 亿对象，但一次 LIST 只读一页的元数据；")
print("  - 这要求元数据存储是**按 key 有序**的（LSM / 有序 KV），而不是 RDBMS 的哈希索引；")
print("    也是讲义把元数据与内容分开存储、并用独立服务扩展元数据层的原因。")
print("  - 顺着这条推：列举大桶本身就是危险操作——它把「一个请求」放大成「一个页的随机读」，")
print("    翻页越多、放大越多，所以真实实现会给 LIST 加前缀与最大页数限制。")

输出：

元数据存储：680,000,000 个对象 x 1 KB = 0.70 TB（讲义给的是 0.68 TB）

列出存储桶中的对象（LIST）怎么读：
  分页读 1000 个对象/页 -> 每页读 1024000 KB = 1.0 MB
  若全表扫一遍 -> 读 696.3 GB = 0.7 TB
  差 680000 倍 -> 所以 LIST 必须走**有序索引 + 分页标记**，不能全表扫

按页扫描的代价（客户端一页一页往下翻）：
  翻    1 页 -> 读      1.0 MB（对应 1,000 个对象）
  翻   10 页 -> 读     10.2 MB（对应 10,000 个对象）
  翻  100 页 -> 读    102.4 MB（对应 100,000 个对象）
  翻 1000 页 -> 读   1024.0 MB（对应 1,000,000 个对象）

判据：
  - LIST 的代价必须按「页」算，不按「桶」算：桶里有 6.8 亿对象，但一次 LIST 只读一页的元数据；
  - 这要求元数据存储是**按 key 有序**的（LSM / 有序 KV），而不是 RDBMS 的哈希索引；
    也是讲义把元数据与内容分开存储、并用独立服务扩展元数据层的原因。
  - 顺着这条推：列举大桶本身就是危险操作——它把「一个请求」放大成「一个页的随机读」，
    翻页越多、放大越多，所以真实实现会给 LIST 加前缀与最大页数限制。

三处结论：

第一，分页读与全表扫差 68 万倍。 桶里有 6.8 亿对象、0.7 TB 元数据；一次 LIST（1000 个对象/页）只读 1 MB，全表扫要读 696 GB。所以 LIST 必须走按 key 有序的索引 + 分页标记——这要求元数据层是 LSM / 有序 KV 那种结构，而不是 RDBMS 的哈希索引。

第二，这也解释了讲义为什么要把元数据与内容分离、还要给元数据存储单独一套服务。 元数据的读写模式（按 key 顺序翻页）与内容的读写模式（按 UUID 随机取块）完全不同，混在一起就是两种负载互相干扰。

第三，翻页本身就是危险操作。 翻 100 页要读 102 MB、翻 1000 页要读 1 GB——「一个请求」被放大成「一页的随机读」，翻得越多放大越多。所以真实实现会给 LIST 加前缀过滤与最大页数限制；讲义在「元数据数据模型」与「列出存储桶中的对象」两节里分别处理了这两件事，只是没把「代价按页算」这句话写出来。

四、增量三：不可变 + 版本控制 = 存储放大

讲义说对象不可变（覆盖写只能是新版本）、有版本控制一节、有垃圾回收一节。三件事连起来是个乘法：

"""不可变 + 版本控制的存储放大，以及 GC 要回收多少。

只依赖标准库；输出确定性。
"""
OBJECTS = 680_000_000
AVG_MB = 60.0              # 按讲义的中位数加权（20% x 0.5MB + 60% x 32MB + 20% x 200MB ≈ 76MB，取 60MB 估）
VERSION_WRITE_RATIO = 0.15  # 每天有多少比例的对象被覆盖写一个新版本（估）
DAYS = 365

base_tb = OBJECTS * AVG_MB * 1024 / 1e12
print("基线（每对象 1 个版本，平均 %.0f MB）-> %.0f TB" % (AVG_MB, base_tb))
print()
print("版本控制：对象不可变，覆盖写 = 新增一个版本")
for versions in (1, 3, 10):
    print("  平均保留 %2d 个版本 -> %.0f TB（放大 %.1fx）" % (versions, base_tb * versions, versions))
print()
print("每天的新版本（写入侧）：")
new_versions = OBJECTS * VERSION_WRITE_RATIO
new_tb = new_versions * AVG_MB * 1024 / 1e12
print("  %.0f%% 的对象每天被覆盖写 -> 每天新增 %s 个版本 = %.1f TB/天" % (VERSION_WRITE_RATIO * 100,
                                                                     format(int(new_versions), ","), new_tb))
print("  一年累计 %.0f TB 的新版本数据" % (new_tb * DAYS))
print()
print("GC 要做的是：把「已被新版本取代且超过保留期」的版本删掉。")
print("  若保留 T 天、多留 K 个版本，稳态存储 ≈ 基线 x (1 + 覆盖写比例 x K)")
for keep_versions in (2, 5, 20):
    steady = base_tb * (1 + VERSION_WRITE_RATIO * keep_versions)
    print("    多留 %2d 个版本 -> 稳态 %.0f TB（是基线的 %.2fx）" % (keep_versions, steady, 1 + VERSION_WRITE_RATIO * keep_versions))
print()
print("判据：")
print("  - 不可变 + 版本控制 = **写放大**（每次覆盖写都占新空间），所以回收只能靠 GC，不能靠「就地覆盖」；")
print("  - 稳态存储 ≈ 基线 x (1 + 覆盖写比例 x 保留版本数)：保留版本数每加 1，存储涨 %.0f%%；"
      % (VERSION_WRITE_RATIO * 100))
print("  - 因此「保留多少个历史版本」是一个**存储预算**决策，不是产品偏好；")
print("    讲义把垃圾回收单列一节正是因为它必须常驻运行，而且删掉的量与写入量同阶。")

输出：

基线（每对象 1 个版本，平均 60 MB）-> 42 TB

版本控制：对象不可变，覆盖写 = 新增一个版本
  平均保留  1 个版本 -> 42 TB（放大 1.0x）
  平均保留  3 个版本 -> 125 TB（放大 3.0x）
  平均保留 10 个版本 -> 418 TB（放大 10.0x）

每天的新版本（写入侧）：
  15% 的对象每天被覆盖写 -> 每天新增 102,000,000 个版本 = 6.3 TB/天
  一年累计 2287 TB 的新版本数据

GC 要做的是：把「已被新版本取代且超过保留期」的版本删掉。
  若保留 T 天、多留 K 个版本，稳态存储 ≈ 基线 x (1 + 覆盖写比例 x K)
    多留  2 个版本 -> 稳态 54 TB（是基线的 1.30x）
    多留  5 个版本 -> 稳态 73 TB（是基线的 1.75x）
    多留 20 个版本 -> 稳态 167 TB（是基线的 4.00x）

判据：
  - 不可变 + 版本控制 = **写放大**（每次覆盖写都占新空间），所以回收只能靠 GC，不能靠「就地覆盖」；
  - 稳态存储 ≈ 基线 x (1 + 覆盖写比例 x 保留版本数)：保留版本数每加 1，存储涨 15%；
  - 因此「保留多少个历史版本」是一个**存储预算**决策，不是产品偏好；
    讲义把垃圾回收单列一节正是因为它必须常驻运行，而且删掉的量与写入量同阶。

三处结论：

第一，「保留多少个历史版本」是存储预算决策，不是产品偏好。 平均保留 3 个版本 → 存储放大 3 倍；保留 10 个 → 10 倍（42 TB → 418 TB）。

第二，稳态存储 ≈ 基线 ×（1 + 覆盖写比例 × 保留版本数）。 按 15% 的对象每天被覆盖写算：多留 2 个版本 → 稳态 54 TB（1.30×）；多留 5 个 → 73 TB（1.75×）；多留 20 个 → 167 TB（4.00×）。保留版本数每加 1，存储涨 15%——而这 15% 就是「不可变」这个设计选择的年租金。

第三，GC 必须常驻运行，而且删除量与写入量同阶。 每天新增 1.02 亿个版本、6.3 TB/天，一年 2.3 PB 的新版本数据要靠 GC 回收——讲义把垃圾回收单列一节，理由就在这里：不可变让「回收空间」这件事从「覆盖时顺手做」变成了「独立的持续工作」，这正是对象存储与文件系统最本质的差别之一。

顺带一句与成本诉求的呼应：讲义把「存储效率」列为非功能需求，而这份账说明效率的主要杠杆不是压缩率，是「不保留没人要的版本」——版本策略比编码器更值钱。

五、把三个模型套回本章（判据清单）

  1. 容量与 IOPS 分开预算：容量 25,000 块盘（100 PB、使用率 40%）；峰值写入 1 亿对象/小时 → 433 块盘的 IO 就够，但 1 亿对象/分钟 → 26,000 块（超过容量）→ 极端突发要靠架构（写缓冲、小对象打包）而不是采购。
  2. 元数据层用有序结构：LIST 按页读 1 MB vs 全表扫 696 GB（差 68 万倍）→ 必须按 key 有序 + 分页标记；这是元数据与内容分离的真正理由。
  3. 大桶列举是危险操作：翻 1000 页读 1 GB → LIST 要加前缀与最大页数限制。
  4. 版本保留是存储预算：稳态 = 基线 ×（1 + 覆盖写比例 × 保留版本数）；每多留 1 个版本涨 15%。
  5. GC 是常驻工作：每天 6.3 TB 新版本要回收，删除量与写入量同阶——不可变的代价就在这里。
  6. durability 与 availability 要分开算：讲义给 6 个 9 耐久 + 4 个 9 可用，与 S3 Standard-IA 的 11 个 9 + 99.9% 是两套口径，落地时按自己的 SLA 组合算副本与跨可用区分布。

六、这一章不重复已发的内容

  • 副本、同步与一致性（跨可用区分布、ISR 之类的机制）：见《消息队列的三笔账》与《扩展的每一步都在换瓶颈》——本文只算对象存储自己的三笔账。
  • 一致性哈希（对象到节点的映射）：见《一致性哈希实测》。
  • 大文件分片上传（讲义「优化大文件上传」一节）：与本文的三个模型无关，未展开。

七、这三个模型判不了什么

  • 每盘 10 TB、每盘 125 IOPS、每对象 1.95 次 IO、覆盖写比例 15%、平均对象 60 MB 都是估的。真实 IOPS 取决于盘型（NVMe 是 SATA 的两个数量级）、对象大小分布、以及写入是否合并——小对象尤其吃 IO，4 KB 的随机写也要一次寻道。
  • 突发模型假设峰值是「一批对象在固定窗口内到达」。真实峰值有更长的尾（秒级突刺），而 IO 预算要按能扛住的尾来留，不是按小时均值。
  • 没算元数据存储的实现细节：有序 KV 的写放大、LSM compaction 的 IO 消耗、索引与数据的双写一致性——这些会让「元数据 0.7 TB」这个数字背后的 IO 与运维成本远高于表面。
  • 没算 LIST 与 GC 的相互影响：GC 在删版本时会改动元数据，若元数据是 LSM 索引，删除会触发 compaction，把「后台清理」变成「前台写放大」。
  • 三个模型都没碰 IAM 与访问控制，而讲义把它单列为一个部件——对象存储的真实成本大头之一是「谁能读什么」的策略复杂度。

FAQ（八、常见问题）

对象存储的瓶颈是容量还是 IOPS？ 分开算。容量：100 PB、使用率 40% ⇒ 25,000 块盘。IOPS 峰值看写入突发：1 亿对象/小时只要 433 块盘的 IO（占 1.7%），但 1 亿对象/分钟就要 26,000 块，比容量还多——极端突发下 IOPS 才是真约束，只能靠写缓冲/小对象打包，采购解决不了。

LIST 一次要读多少数据？ 按页算：1000 个对象/页 ≈ 1 MB 元数据；全表扫是 696 GB，差 68 万倍。所以元数据必须按 key 有序存储（LSM / 有序 KV），LIST 走前缀 + 分页标记；翻页越多放大越多，所以要给 LIST 加最大页数限制。

版本控制让存储涨多少？ 稳态 ≈ 基线 ×（1 + 覆盖写比例 × 保留版本数）。按 15% 覆盖写：多留 2 个版本涨到 1.30 倍、5 个 1.75 倍、20 个 4 倍。每多留 1 个版本涨 15%——保留多少版本是存储预算决策，不是产品偏好。

不可变带来的最大代价是什么？ 回收空间从「覆盖时顺手做」变成「独立的常驻工作」：每天新增 1.02 亿个版本、6.3 TB/天的垃圾要靠 GC 回收，删除量与写入量同阶。这是对象存储与文件系统最本质的差别之一。
