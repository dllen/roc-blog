写扩散还是读扩散：把信息流的推拉边界算出来

#系统设计#架构设计#读书笔记#信息流

写扩散还是读扩散？讲义给的是方向（「对大多数用户用推模式，对高连接数用户如明星用拉模式」），没给数。这篇把那把尺子补出来：分界线是可以算的，而且它会随参数移动，不是常数。

这篇不复述译文，也不搬运中文译本的任何段落。它复述这一章的骨架（两个流程、三种扩散模式、五层缓存），然后补三个自写模型：推拉两种方案的成本账与混合方案的阈值、feed 缓存只存 ID 与存完整对象的内存差、信息流分页在持续插入下的重复与漏读。

口径说明

  • 源笔记是 Alex Xu《System Design Interview — An Insider’s Guide》第 11 章的社区中译。上游两仓库的 LICENSE 在 main/master 分支经 raw 通道取均返回 404，上游许可未能确认；原书是商业出版物。故本篇为导读式：只复述章节骨架与需求数字，不引用译文原文或原书段落，不使用译本配图，正文主体是自写模型与判断。
  • 三个脚本均为自写增量，只依赖 Python 标准库；输出为实跑结果，逐行可复现（三段模拟都不含随机数）。
  • 与已发文章的重叠见「这一章不重复已发的内容」一节。

一、本章骨架：两个流程、三种扩散、五层缓存

需求：Web 与移动端都要；用户能发帖、能在信息流里看好友的帖子；排序按逆时间（为简化）；规模上用户最多 5000 个好友、1000 万 DAU，帖子含文本、图片、视频。

两个流程：

  • 消息流发布：用户发帖子 → 负载均衡 → Web 服务器鉴权转发 → 帖子服务（写入数据库与缓存）→ 扩散服务（把帖子扩散进好友的消息流）→ 通知服务。
  • 动态消息流获取：用户请求自己的信息流 → 负载均衡 → Web 服务器 → 信息流服务：先从信息流缓存拿帖子 ID，再从数据库或缓存取完整帖子详情。

三种扩散模式（本章的核心）：

  • 写扩散：发帖时就把帖子推进每个好友的 feed 缓存。读快、实时；代价是好友多的用户把写放大了。
  • 读扩散：读的时候现拉。写省；对不活跃用户高效；读慢。
  • 混合方案：大多数用户推，连接数极高的人（明星）拉。

扩散服务内部五步：从图数据库取好友 ID → 从缓存里按用户设置过滤（屏蔽的好友、选择性分享）→ 好友列表与帖子 ID 一起进消息队列 → 扩散工作进程更新缓存，缓存里存 <post_id, user_id> 映射而不是完整的用户与帖子对象 → 追加进好友的 feed 缓存，并用一个可配置的上限只保留最近的帖子。

五层缓存：信息流缓存（帖子 ID）、内容缓存（帖子详情，热门放热缓存）、社交图谱缓存、行为缓存（点赞/回复/分享）、计数器缓存（点赞、回复、关注者数）。

二、增量一：推拉两本账，和那条分界线

把两种方案的代价写成式子：写扩散的写放大 = 每条帖子 × 粉丝数；读扩散的读放大 = 每次读 × 好友数。代入本章的规模（1000 万 DAU、每人 500 好友、每天读 5 次、发 0.5 帖），差距立刻显形：

"""写扩散 vs 读扩散：把「混合方案」的分界线算出来。

讲义说「对大多数用户用推模式，对高连接数用户（如明星）用拉模式」——这给了方向，没给数。
这里把两种方案的成本写成式子，解出阈值。

只依赖标准库；输出确定性。
"""
DAU = 10_000_000
FRIENDS = 500            # 普通用户好友数
READS_PER_DAY = 5         # 每人每天读几次 feed
POSTS_PER_DAY = 0.5       # 每人每天发几帖
FANOUT_CAP = 500          # feed 缓存每用户最多存多少条

def write_fanout_cost(fans):
    """写扩散：每条帖子写进每个粉丝的 feed 缓存。"""
    return fans * POSTS_PER_DAY

def read_fanout_cost():
    """读扩散：每次读 feed 要从每个好友那里拉一次。"""
    return FRIENDS * READS_PER_DAY

print("全站规模：%d DAU，每人 %d 好友、每天读 %d 次、发 %.1f 帖" % (DAU, FRIENDS, READS_PER_DAY, POSTS_PER_DAY))
print()
print("单用户每天的放大（以「一次 feed 缓存写」或「一次拉取」为单位）")
print("  写扩散（普通用户 %d 好友）：%.0f 次写/天" % (FRIENDS, write_fanout_cost(FRIENDS)))
print("  读扩散：%d 次拉/天（每次读都拉 %d 个好友）" % (read_fanout_cost(), FRIENDS))
print("  -> 单用户视角：写扩散省 %.0f 倍，因为读次数是发次数的 %.0f 倍"
      % (read_fanout_cost() / write_fanout_cost(FRIENDS), READS_PER_DAY / POSTS_PER_DAY))
print()
print("全站每天（亿次）")
w_total = DAU * write_fanout_cost(FRIENDS) / 1e8
r_total = DAU * read_fanout_cost() / 1e8
print("  写扩散：%.1f 亿次 feed 缓存写" % w_total)
print("  读扩散：%.1f 亿次拉取" % r_total)
print()
print("大 V 那一侧（一个用户有 B 个粉丝）")
print("  %-12s %14s %14s" % ("粉丝数 B", "写扩散(亿次/天)", "读扩散(亿次/天)"))
for B in (500, 5_000, 50_000, 500_000, 5_000_000, 50_000_000):
    w = B * POSTS_PER_DAY * DAU * 0.001 / 1e8   # 假设 0.1% 的用户是这类大 V
    r = r_total * 0.001
    print("  %-12d %13.2f %14.2f" % (B, w, r))
print()
threshold = (READS_PER_DAY / POSTS_PER_DAY) * FRIENDS
print("阈值推导：对一个粉丝数 B 的用户，写扩散成本 = B x 发帖数，读扩散成本 = 好友数 x 读次数")
print("  两者相等 -> B_threshold = (读次数/发帖数) x 好友数 = %.0f x %d = %.0f" % (READS_PER_DAY / POSTS_PER_DAY, FRIENDS, threshold))
print("  粉丝数超过 %.0f 的大 V，用读扩散更划算：他的帖子不适合写扩散到每个粉丝的缓存。" % threshold)
print("  这条线就是讲义「明星用拉模式」的量化版本——阈值随读/发比与好友数移动，不是常数。")
print()

四件事值得看：

第一，普通用户走写扩散，全站每天 25 亿次 feed 缓存写；读扩散是 250 亿次拉取——差 10 倍。 差的来源不是技术，是读次数是发帖次数的 10 倍：每次读都要按好友数拉一遍，而写只在发帖时发生。所以「读扩散对不活跃用户高效」的真正含义是：读扩散的成本按读计，写扩散的成本按写计，两者的比值就是这个读写比。

第二，但对粉丝多的人，结论翻转。 粉丝数 5000 时，两边成本已经持平（各 0.25 亿次/天）；粉丝数 5000 万时，写扩散要 2500 亿次/天，而读扩散仍是 0.25 亿次。大 V 的帖子写扩散是灾难性的，因为写放大的系数就是粉丝数本身。

第三，讲义的「明星用拉模式」可以写成一条公式。 对一个粉丝数 B 的用户，写扩散成本 = B × 发帖数，读扩散成本 = 好友数 × 读次数，两者相等解出

B 阈值 =（读次数 ÷ 发帖数）× 好友数 =（5 ÷ 0.5）× 500 = 5000

粉丝数超过 5000 就该用读扩散。这条线不是常数：读/发比涨 10 倍（用户更爱看少发），阈值跟着涨到 5 万；好友数少的用户阈值也低。所以「哪些人算明星」不是身份标签，是当天的读写比与好友数算出来的。

第四，混合方案的成本可以估算。 假设 0.1% 的用户是大 V 且全部走拉模式，这部分每天 0.25 亿次拉取；剩下 99.9% 走写扩散，每天约 25 亿次写。总成本 = 25 亿写 + 0.25 亿拉。这个数字可以拿去和「把所有人都改成读扩散」的 250 亿次拉做对比——混合方案省下的不是一点点。

三、增量二：feed 缓存存 ID 还是存对象，差几倍内存

讲义给了两个很具体的工程细节：缓存存 <post_id, user_id> 映射而不是完整对象；以及用一个可配置上限只存最近的帖子。两句都只给了理由，没给数字。补上：

"""feed 缓存存什么：只存 ID 与存完整对象，内存差多少倍。

讲义说扩散工作进程「存 <post_id, user_id> 映射而非完整的用户和帖子对象，以节省内存」，
并说「可配置的上限保证只存最近的帖子」。这里把这两句换成具体字节数。

只依赖标准库；输出确定性。
"""
DAU = 10_000_000
ID_BYTES = 16          # post_id 8B + user_id 8B
OVERHEAD = 40          # 列表节点、哈希桶、序列化开销（估）
FULL_OBJECT = 200      # 完整帖子对象（正文摘要 + 元数据）的估字节
PAGE_SIZE = 10

print("规模：%d DAU；每条 feed 记录只存 post_id + user_id = %d B，加约 %d B 容器开销" % (DAU, ID_BYTES, OVERHEAD))
print()
print("%-12s %12s %12s %12s %12s" % ("每用户上限", "每用户字节", "全站(GB)", "可翻页数", "存完整对象(GB)"))
for cap in (100, 500, 1000):
    per_user = cap * (ID_BYTES + OVERHEAD)
    total = DAU * per_user / 1e9
    full = DAU * cap * (ID_BYTES + OVERHEAD + FULL_OBJECT) / 1e9
    print("%-12d %12d %12.1f %12d %12.1f" % (cap, per_user, total, cap // PAGE_SIZE, full))
print()
print("读法：")
print("  - 存 ID：每用户 500 条时全站 %.0f GB；存完整对象则是 %.0f GB，是 %.1f 倍。"
      % (DAU * 500 * (ID_BYTES + OVERHEAD) / 1e9, DAU * 500 * (ID_BYTES + OVERHEAD + FULL_OBJECT) / 1e9,
         (ID_BYTES + OVERHEAD + FULL_OBJECT) / (ID_BYTES + OVERHEAD)))
print("  - 上限不只是内存问题，还是产品参数：500 条 / 每页 10 条 = 可翻 50 页，")
print("    上限设 100 条就只能翻 10 页——用户翻到底会「没有更多了」，而那不是真的没有。")
print("  - 上限越小内存越省，但越早触底；判据：上限 >= 目标用户 %d 天的发帖量。" % (500 // PAGE_SIZE * 2))

  - 上限不只是内存问题，还是产品参数：500 条 / 每页 10 条 = 可翻 50 页，
    上限设 100 条就只能翻 10 页——用户翻到底会「没有更多了」，而那不是真的没有。

读法：

  • 每用户存 500 条、只存 ID，全站约 280 GB；存完整帖子对象（每条按 200 B 估）约 1280 GB，是 4.6 倍。 讲义说「以节省内存」是对的，但真正的原因是乘数：同一份内存要乘以 1000 万用户和每人的条数，任何单条的小节省都会变成全站的大数字。
  • 上限不只是内存参数，还是产品参数。 500 条 / 每页 10 条 = 可翻 50 页；上限设 100 条就只能翻 10 页——用户翻到底会看到「没有更多了」，而那不是真的没有更多，只是缓存里没有。上限要按目标用户几天内的发帖量来定，否则记忆点就是错的。
  • 顺带一句：讲义让缓存存 ID、详情另取，本身也把「详情可能已经不在缓存里」变成了常态，所以详情层还要有自己的存储与命中率监控——这正是五层缓存里另外四层的存在理由。

四、增量三：信息流是活的，位置是死的

讲义把排序定为逆时间，并说「大多数用户只关注最新内容」。这两句加上「持续有帖子被发布」，必然引出一个讲义没写、但每个信息流都会踩的坑：分页。

offset 分页把「第几条」当成位置，而位置在持续插入下会漂移。确定性模拟：初始 1000 条按 key 降序，读 5 页 × 每页 10 条，第 2 页起每页之前插入 5 条新帖（key 更大 = 更新），并以「没有插入时同样这 50 条会读到什么」为基线来算漏读：

"""信息流分页：offset 分页在有插入时会重复与漏读，keyset 分页不会。

feed 按 key 降序（key 越大越新）；分页从最新往旧走。
「漏读」以「同样页数在没有插入时会读到的条目」为基线来算。
确定性模拟：固定初始列表 + 固定插入时机与数量 -> 输出确定性。
"""
BASE = 1000            # 初始 feed 条数（key 1000..1）
INSERTED = 5           # 每次插入的新帖数（key 更大 = 更新），必须 < PAGE_SIZE 才会产生重复
PAGES = 5
PAGE_SIZE = 10

def new_items():
    return list(range(BASE, 0, -1))          # key 降序

def offset_paginate(live, page):
    return live[page * PAGE_SIZE:(page + 1) * PAGE_SIZE]

def keyset_paginate(live, cursor):
    out = []
    for it in live:
        if cursor is None or it < cursor:    # key 严格小于游标 = 更旧
            out.append(it)
            if len(out) == PAGE_SIZE:
                break
    return out

def run(with_inserts):
    live = new_items()
    off_seen, key_seen = [], []
    cursor = None
    next_key = BASE + 1
    for page in range(PAGES):
        if with_inserts and page > 0:
            fresh = list(range(next_key, next_key + INSERTED))
            next_key += INSERTED
            live = fresh + live
        off_seen.extend(offset_paginate(live, page))
        chunk = keyset_paginate(live, cursor)
        key_seen.extend(chunk)
        if chunk:
            cursor = chunk[-1]
    return off_seen, key_seen

def report(name, seen, baseline):
    uniq = set(seen)
    dup = len(seen) - len(uniq)
    missed = len(baseline - uniq)
    fresh = len(uniq - baseline)
    print("%-14s %8d %10d %12d %12d" % (name, len(seen), dup, missed, fresh))
    return dup, missed

off_base, key_base = run(False)
baseline = set(off_base)
print("初始 %d 条（key 降序），读 %d 页 x 每页 %d 条；第 2 页起每页前插入 %d 条新帖"
      % (BASE, PAGES, PAGE_SIZE, INSERTED))
print("基线（没有插入时同样这 %d 条会读到什么）：%s ..." % (PAGES * PAGE_SIZE, sorted(baseline, reverse=True)[:6]))
print()
print("%-14s %8s %10s %12s %12s" % ("方案", "读到条数", "重复条数", "漏读基线条", "多读的新帖"))
d1, m1 = report("offset 分页", off_base and run(True)[0], baseline)
d2, m2 = report("keyset 分页", run(True)[1], baseline)
print()
off_seen = run(True)[0]
key_seen = run(True)[1]
print("offset 分页前两页：")
print("  第 1 页 %s" % off_seen[:PAGE_SIZE])
print("  第 2 页 %s" % off_seen[PAGE_SIZE:2 * PAGE_SIZE])
print("keyset 分页前两页：")
print("  第 1 页 %s" % key_seen[:PAGE_SIZE])
print("  第 2 页 %s" % key_seen[PAGE_SIZE:2 * PAGE_SIZE])
print()
print("结论：")
print("  - offset 分页把「第几条」当位置，每次插入 5 条就把后面所有条目往后推 5 位，")
print("    于是第 2 页重新读到了第 1 页已经读过的 %d 条，同量级的旧帖被挤出窗口而漏读。" % d1)
print("  - keyset（游标）分页以上一页最后一个 key 为锚，插入只影响更前面的页，重复 %d、漏读 %d。" % (d2, m2))
print("  - 讲义没写分页这一层，但「逆时间排序 + 持续插入」的组合必然踩到：信息流是活的，位置是死的。")

  第 2 页 [990, 989, 988, 987, 986, 985, 984, 983, 982, 981]

结论：
  - offset 分页把「第几条」当位置，每次插入 5 条就把后面所有条目往后推 5 位，
    于是第 2 页重新读到了第 1 页已经读过的 20 条，同量级的旧帖被挤出窗口而漏读。
  - keyset（游标）分页以上一页最后一个 key 为锚，插入只影响更前面的页，重复 0、漏读 0。
  - 讲义没写分页这一层，但「逆时间排序 + 持续插入」的组合必然踩到：信息流是活的，位置是死的。

三处结论：

第一，offset 分页在 5 页里重复读了 20 条、漏读基线里的 20 条。 每插入 5 条，后面所有条目往后挪 5 位，于是第 2 页的前 5 条是第 1 页刚读过的（995 994 993 992 991 又出现一次），同量级的旧帖被挤出窗口。这两类错误在客户端完全看不出来——页面正常渲染，只是用户往回滑会看到重复，下拉刷新又会「丢掉」刚才看过的一些内容。

第二，keyset（游标）分页是 0 重复、0 漏读。 做法是以上一页最后一个 key 为锚，下一页取 key 更小的条目；新帖的 key 更大，落在锚之前，所以它只影响更前面的页，对已经翻过的区间没有影响。

第三，这条与 feed 缓存上限是一对。 上限 500 条 + keyset 分页，用户能稳定翻 50 页且不重复；上限 500 条 + offset 分页，越往后翻重复越多。反过来，上限设 100 条时，即使分页实现完美，翻到第 10 页也到底了——缓存上限决定「能翻多深」，分页方式决定「翻得对不对」，两件事要一起设计。

五、把三个模型套回本章（判据清单）

  1. 给每个用户算一遍 B 阈值 =（读次数 ÷ 发帖数）× 好友数，超阈值的走读扩散（明星），其余走写扩散。阈值会随读写比与好友数漂移，别把它写死在配置里。
  2. feed 缓存只存 ID，并把上限按「目标用户几天内的发帖量」定；上限同时决定内存（1000 万 × 上限 × 56 B）与用户能翻多深。
  3. 分页一律用 keyset/游标，不要用 offset；把「插入会漂移位置」当成默认前提，而不是异常情况。
  4. 写扩散的写放大要计入容量规划：25 亿次/天不是「缓存写得快」就完事，它是每天都要扛的写入量；而大 V 的写放大会单独把这本账掀翻。
  5. 过滤要在扩散前做：讲义的扩散服务第二步先用缓存里的用户设置过滤（屏蔽、选择性分享），这一步放在扩散之后就没有意义了。

七、这三个模型判不了什么

  • 粉丝数分布是假设的。真实分布是幂律，少数超大会长用户贡献绝大部分写放大；本模型用单点参数算阈值，落地时要按分布积分而不是取一个 B。
  • 读写比会随产品形态变。订阅流（读远多于发）与社交流（发占比高）的 B 阈值差一个数量级，阈值不能跨形态复用。
  • 内存账里的 40 B 开销与 200 B 对象大小都是估的。真实数字取决于序列化格式、容器实现与缓存客户端；要把它们换成实测的 profile，而不是靠估。
  • 分页模型只模拟了「插在最前」。真实的插入位置、时间分布与用户翻页速度交织，重复与漏读的形态会更复杂；模型的结论（keyset 不受插入影响）才是可迁移的部分。
  • 三个模型都不含内容排序质量。讲义为简化把排序定为逆时间；真实信息流的排序、召回与去重是另一层问题，本文完全没碰。

FAQ（八、常见问题）

写扩散和读扩散怎么选？ 看粉丝数与读写比。粉丝数 B 的用户，写扩散成本 = B × 发帖数，读扩散成本 = 好友数 × 读次数；相等解出 B 阈值 =（读次数 ÷ 发帖数）× 好友数。本章参数下是 5000，超过就用读扩散。

为什么普通用户写扩散更省？ 因为两边成本的计量单位不同：写扩散按写计（每人每天 0.5 帖 × 500 好友 = 250 次写），读扩散按读计（每人每天 5 次读 × 500 好友 = 2500 次拉）。读次数是发帖次数的 10 倍，差距就来自这 10 倍。

feed 缓存该存多少条？ 按目标用户几天内的发帖量定，不是按内存余量定。每条 ID 记录约 56 B（16 B ID + 约 40 B 容器开销），1000 万用户存 500 条约 280 GB；存完整对象约 1280 GB，是 4.6 倍。

信息流分页为什么不能用 offset？ 因为位置会漂移：每插入一条新帖，后面所有条目往后挪一位，于是翻页会重复读到已读内容、并把同量级旧帖挤出窗口。实测 5 页里重复 20 条、漏读 20 条；keyset 分页是 0/0。

混合方案的成本怎么估？ 分开算：走写扩散的普通用户贡献 Σ(好友数 × 发帖数)，走读扩散的大 V 贡献 Σ(粉丝数占比 × 读次数)。本例约 25 亿次写 + 0.25 亿次拉，而全量读扩散是 250 亿次拉。
