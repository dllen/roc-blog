短链 key 该取多长：把「7 位够用」算成碰撞概率

#系统设计#架构设计#读书笔记#短链接

短链 key 该取多长？几乎每份讲义都给出同一个答案：base62 编码，7 位，够装 3650 亿条。这个答案对了一半——它算的是容量，而短链真正会出事的地方是碰撞。这两个问题的答案差了 11 位。

这篇不复述译文，也不搬运中文译本的任何段落。它做三件事：用自己的话复述第 8 章的骨架（两条技术路线、数据模型、读写路径），然后补三个能跑的模型——把 key 容量与碰撞概率写成可计算的判据、把截断哈希的碰撞率与短 key 的可枚举性做成实测、把布隆过滤器的假阳性换算成读路径上多余的回源。

口径说明：这是导读，不是改写

  • 源笔记是 Alex Xu《System Design Interview — An Insider’s Guide》第 8 章的社区中译。上游两个仓库的 LICENSE 在 main/master 分支经 raw 通道取均返回 404，上游许可未能确认；原书是商业出版物。故本篇为导读式：只复述章节骨架与需求数字，不引用译文原文或原书段落，不使用译本配图，正文主体是自写模型与判断。
  • 三个脚本均为自写增量，只依赖 Python 标准库；文中输出为实跑结果，逐行可复现。
  • 与已发文章的重叠见「这篇不重复已发的内容」一节。

一、短链服务的骨架

需求（四个数字）

  • 缩短后的 URL 必须唯一，且在能接受的前提下尽量短；
  • 每天 1 亿次生成，要撑 10 年；
  • 读写比 10:1，读多写少；
  • 10 年累计 3650 亿条记录，对应约 365 TB 存储。

这四个数字后面每一个都会变成一道约束题：唯一性、长度、读放大、存储。其中最容易被跳过的就是唯一性——因为它是唯一的、纯逻辑的、看起来不需要“设计“的那一个。

两条技术路线

哈希截断 + 冲突解决自增/分布式 ID + base62
长度固定（截断到 N 位）随 ID 增长而增长
是否需要唯一 ID 生成器不需要需要
是否会碰撞会，靠冲突解决兜底不会（前提是 ID 唯一）
能否直接算出「下一个可用 key」不能，因为 key 不依赖 ID能，ID + 1 再编码即可

这张表的真正信息量不在“谁更长“，而在唯一性的责任落在谁头上：

  • 路线 1 把唯一性托付给哈希函数。哈希函数只是“把输入映射到一个固定大小的空间“，映射必然不单射，所以碰撞是这套方案的固有成本，不是意外事故。
  • 路线 2 把唯一性托付给 ID 生成器。只要 ID 全局唯一，base62 编码就是单射，碰撞概率恒等于 0，与 key 长度无关。

于是「7 位够不够」这句话的完整含义是：7 位够用来装下 3650 亿个互不相同的 ID——因为 ID 本身不重复。它从来没说过 7 位够用来装下 3650 亿个哈希值。

数据模型与读写路径

  • 存储：关系型数据库一张表，三列——主键 id、短链、长链。短链的唯一性靠数据库约束兜底，而不是靠应用层自觉。
  • 写路径：先查这个长链是否已有短链（有就复用，保证同一长链得到同一个短链），没有就生成新 key 并落库。
  • 读路径：先查缓存，未命中再查数据库，然后返回重定向。
  • 重定向语义：301 表示永久迁移，浏览器会缓存响应、对同一短链的后续请求不再回源；302 表示临时跳转，适合点击统计这类分析场景。
  • 其他：按 IP 限流防滥用，Web 层保持无状态以便横向扩展，数据库用复制加分片扛量，另有点击量/来源/时间戳的分析需求。

第 8 章还提到“用分布式 ID 生成器产出唯一 ID 再转 base62“。分布式 ID 的位分配与时钟回拨问题已单独成文（《雪花 ID 的 41 位怎么分配》），本文不复述，只在判据里引用它。

二、增量一：key 容量与碰撞概率，是一道题的两半

把“7 位够用“拆开，里面藏着一个偷换：容量约束用指数刻画，碰撞约束用平方刻画。

  • 容量：L 位、字符集大小 N，能区分 N 的 L 次方个 key。需求是 3650 亿条，所以要 N 的 L 次方 ≥ 3.65×10¹¹。
  • 碰撞：往同一个空间里塞 n 个 key，至少撞一次的概率由生日悖论给出——n 个 key 落进空间 S，至少一次碰撞的概率约为 1 − e^(−n²/2S)。注意分母里的 S 与 n 的平方相除：n 涨一倍，碰撞概率大约涨四倍。

于是同一个 7 位空间，两个判据给出完全不同的答案。下面这个脚本把两边都算出来（只依赖标准库，输出确定性）：

"""短链 key 的容量与碰撞概率：把「够不够长」变成可计算的判据。

只依赖标准库；输出为确定性结果。
"""

NEED = 365_000_000_000          # 3650 亿条（讲义给的需求：每天 1 亿条、存 10 年）
TARGET_P = 1e-9                  # 目标：碰撞概率 <= 1e-9
ALPHABETS = [
    ("base62  [0-9a-zA-Z]", 62),
    ("base64  标准表 (+/)", 64),
    ("base64url 安全表 (-_)", 64),
]

def capacity(alphabet, length):
    return alphabet ** length

def collision_prob(n, space):
    """生日悖论：n 个 key 落进 space 大小的空间，至少撞一次的概率。"""
    return 1.0 - pow(2.718281828459045, -(n * n) / (2.0 * space))

def min_length_for_capacity(alphabet, need):
    L = 1
    while capacity(alphabet, L) < need:
        L += 1
    return L

def min_length_for_collision(alphabet, n, p):
    L = 1
    while collision_prob(n, capacity(alphabet, L)) > p:
        L += 1
    return L

def enc_len(bits, alphabet):
    import math
    return int(math.ceil(bits / math.log2(alphabet)))

print("需求：%d 条 key（每天 1 亿条 x 3650 天）" % NEED)
print()
print("%-24s %-3s %-24s %-8s %-12s" % ("字符集", "L", "容量", "装得下", "碰撞概率"))
for name, size in ALPHABETS:
    for L in (6, 7, 8):
        cap = capacity(size, L)
        print("%-24s %-3d %-24d %-8s %.6f"
              % (name, L, cap, "是" if cap >= NEED else "否",
                 collision_prob(NEED, cap)))
print()
print("装下需求所需的最小长度：")
for name, size in ALPHABETS:
    L = min_length_for_capacity(size, NEED)
    print("  %-24s L=%-3d 容量 %-22d 余量 %.1f 倍"
          % (name, L, capacity(size, L), capacity(size, L) / NEED))
print()
print("碰撞概率 <= %g 所需的最小长度（n = %d）：" % (TARGET_P, NEED))
for name, size in ALPHABETS:
    L = min_length_for_collision(size, NEED, TARGET_P)
    print("  %-24s L=%-3d 容量 %.3e" % (name, L, capacity(size, L)))
print()
for L in (6, 7, 8):
    r = capacity(64, L) / capacity(62, L)
    d = min_length_for_collision(64, NEED, TARGET_P) - min_length_for_collision(62, NEED, TARGET_P)
    print("L=%d 同长度容量：base64 是 base62 的 %.3f 倍（多 %.1f%%）；同等碰撞余量下 base64 省 %d 位"
          % (L, r, (r - 1) * 100, -d))
print()
for bits in (32, 64, 128, 256):
    print("  %3d bit 摘要 -> base62 %2d 字符 / base64 %2d 字符"
          % (bits, enc_len(bits, 62), enc_len(bits, 64)))
print()
import base64, random
rng = random.Random(20261126)          # 固定种子，输出可复现
hit = 0
for i in range(2000):
    plain = base64.b64encode(bytes(rng.randrange(256) for _ in range(16))).decode()
    if "+" in plain or "/" in plain:
        hit += 1
print("2000 个固定种子生成的 16 字节里，标准 base64 含 '+' 或 '/' 的有 %d 个（这类字符在 URL 里要转义）" % hit)

三处值得停下来看：

第一，L=7 装得下需求，但碰撞概率打印出来是 1.000000。 不是“接近 1“，是四舍五入后的 1。3650 亿个 key 塞进 3.52 万亿的空间，n²/2S ≈ 1.9×10¹⁰——这个量级下“至少撞一次“是必然事件（概率与 1 的差在 10⁻¹⁰ 量级）。所以如果走哈希截断且只用 7 位，3650 亿条记录里必然存在大量重复 key，冲突解决机制会被持续触发。

第二，装得下与撞得少，差 11 位。 要把碰撞概率压到 1×10⁻⁹，base62 需要 L=18。18 位短链对用户来说基本没有意义——这正是“哈希截断 + 冲突解决“这套方案存在的理由：它不指望 7 位能扛碰撞，而是承认碰撞会发生，然后用冲突解决（追加盐、探测下一个候选）把它消化掉。

第三，字符集的影响比想象中小。 同长度下 base64 的容量比 base62 多 21%~29%（L=6/7/8），但在“同等碰撞余量“这个口径下，两者需要的位数都是 18——因为碰撞约束由 n² 主导，字符集差异在取整后被吃掉了。字符集决定的是容量余量，不是抗碰撞能力。 想抗碰撞，只有两条路：加长，或者别用哈希。

同一脚本还给出两条常被忽略的对照：

  • 编码长度上，base62 与 base64 几乎一样：32 位摘要两者都是 6 个字符，64 位 11 个，128 位 22 个，256 位 43 个（因为 log₂62 与 log₂64 只差约 3%）。
  • 而标准 base64 表里含 + 和 /，这两个字符放进 URL 必须转义。实测 2000 个随机 16 字节里，**有 1015 个（50.8%）**的标准 base64 串含 + 或 /。URL-safe 表（- _）能绕开，但既然长度优势不到 3%，短链里直接用 base62 省事——这也是很多实现选 base62 的真实理由：不是容量，是 URL 干净。

三、增量二：截断哈希实测会撞多少，短 key 有多容易被扫

上一节的碰撞概率是模型。这一节把它变成实测：生成 100 万个不同 URL，取 SHA-256 的 base62 表示的前 L 位当 key，数一数真撞了几次，和理论期望对比。

"""截断哈希到底会碰撞多少 + 短 key 有多容易被枚举。

实测 + 理论期望对照；时间随机器波动，碰撞数是确定性的。
"""
import hashlib, string, sys, time

ALPHABET = string.digits + string.ascii_lowercase + string.ascii_uppercase  # 62

def to_base62(num, width=None):
    if num == 0:
        s = ALPHABET[0]
    else:
        s = ""
        while num:
            num, r = divmod(num, 62)
            s = ALPHABET[r] + s
    if width:
        s = s.rjust(width, ALPHABET[0])
    return s

def key_of(url, length):
    h = int(hashlib.sha256(url.encode()).hexdigest(), 16)
    return to_base62(h)[:length]

N = 1_000_000
print("样本 %d 个不同 URL，取 SHA-256 的 base62 前 L 位作 key" % N)
print("%-3s %-12s %-10s %-10s %-8s" % ("L", "空间", "实测碰撞", "理论期望", "比值"))
for L in (5, 6, 7):
    seen = set()
    collisions = 0
    for i in range(N):
        k = key_of("https://example.com/p/%d" % i, L)
        if k in seen:
            collisions += 1
        else:
            seen.add(k)
    space = 62 ** L
    expect = N * (N - 1) / (2.0 * space)
    ratio = collisions / expect if expect else 0.0
    print("%-3d %-12.3e %-10d %-10.1f %-8.2f" % (L, space, collisions, expect, ratio))
print()
print("短 key 的可枚举性（攻击者全量遍历 key 空间）：")
print("  计时结果走 stderr，stdout 保持确定性，便于与文中期望输出逐行比对")
for L in (3, 4):
    space = 62 ** L
    t0 = time.time()
    table = set()
    for i in range(space):
        table.add(to_base62(i, L))
    dt = time.time() - t0
    rate = space / dt / 1e6
    print("  L=%d 空间 %-10d 全部枚举得到 %d 个互异 key（攻击者只需遍历这个空间）"
          % (L, space, len(table)))
    print("     实测枚举耗时 %.2f 秒，速度 %.1f 万 key/秒" % (dt, rate), file=sys.stderr)
    if L == 4:
        print("     外推：L=5（%d）按同速需 %.1f 小时，L=6（%d）需 %.1f 天（外推，非实测）"
              % (62 ** 5, (62 ** 5) / rate / 3600.0, 62 ** 6, (62 ** 6) / rate / 86400.0),
              file=sys.stderr)

  L=3 空间 238328     全部枚举得到 238328 个互异 key（攻击者只需遍历这个空间）

实测与理论吻合得很好。 L=5 实测 556 次、理论期望 545.8 次（比值 1.02）；L=6 实测 12 次、期望 8.8 次（1.36，比值偏大是样本量小所致，此时期望值只有个位数，方差大）；L=7 实测 0 次、期望 0.1 次。这说明：想把碰撞数压到“基本不发生“，需要 L=7；想把碰撞率压到可忽略，需要 L=9 往上（理论期望 n²/2S < 0.01）。而短链长度的用户体验红线通常在 7 位以内——这就是冲突解决机制必须存在的量化理由。

第二段输出是另一个方向的代价。攻击者不需要破解哈希，只需要穷举 key 空间：对每个候选 key 算一次哈希，比对已知的长链候选集。实测：

  • 3 位 key（空间 238,328）：全量枚举 0.06~0.13 秒（同一台机器多次运行的区间）；
  • 4 位 key（空间 1,478 万）：全量枚举 6.6~6.9 秒（约 2.1 万 key/秒，这是 Python 实现的实测速度；脚本把计时打到 stderr，stdout 保持确定性以便逐行比对）。

按这个速度线性外推，5 位（9.16 亿）需要 11~12 万小时——但这个外推会误导，因为换成 C/Go 的紧凑实现会快一到两个数量级（这是量级推算，不是实测），那么 5 位就是分钟级。真正的结论因此是：4 位及以内的短链，其 key 空间小到单机可以整体扫出来，不应被当作保密手段；5 位在编译语言实现下也构不成障碍。

短链 key 的“短“是产品属性，不是安全属性。它的保密性如果重要，就该来自别处（比如需要输入正确口令才跳转的服务端校验），而不是来自 key 只有 6 个字符。

四、增量三：布隆过滤器的假阳性，不是免费的

第 8 章提到用布隆过滤器做冲突判定：key 不在过滤器里，说明一定没被占用；key 在过滤器里，可能在（假阳性）。这听起来是单向安全的——不会漏掉冲突，只会多查一次。

但“多查一次“在读路径上是有价的：短链服务 10:1 的读写比意味着每次 404 判定都是一次无效回源。布隆过滤器的假阳性率是可直接算的：

"""布隆过滤器的假阳性，会怎样影响「找下一个可用 key」的循环。"""
import hashlib

class Bloom:
    def __init__(self, m_bits, k_hashes):
        self.m = m_bits
        self.k = k_hashes
        self.bits = bytearray((m_bits + 7) // 8)

    def _idx(self, item, i):
        h1 = int.from_bytes(hashlib.md5(item.encode()).digest()[:8], "big")
        h2 = int.from_bytes(hashlib.md5(item.encode()).digest()[8:16], "big")
        return ((h1 + i * h2) % (2 ** 31)) % self.m

    def add(self, item):
        for i in range(self.k):
            p = self._idx(item, i)
            self.bits[p >> 3] |= 1 << (p & 7)

    def __contains__(self, item):
        for i in range(self.k):
            p = self._idx(item, i)
            if not (self.bits[p >> 3] >> (p & 7)) & 1:
                return False
        return True

N = 100_000
for bits_per_item in (10, 16):
    m = N * bits_per_item
    b = Bloom(m, 4)
    for i in range(N):
        b.add("key-%d" % i)
    false_pos = sum(1 for i in range(N, N + 20_000) if ("miss-%d" % i) in b)
    fp_rate = false_pos / 20_000
    # 理论值：(1 - e^(-k*n/m))^k
    import math
    theory = (1 - math.exp(-4 * N / m)) ** 4
    print("m=%d bit（%d bit/项，k=4）  假阳性实测 %.4f  理论 %.4f"
          % (m, bits_per_item, fp_rate, theory))
print()
print("读路径上查 key 存在的次数（每查一次假阳性就浪费一次 DB 回源）：")
m = N * 10
b = Bloom(m, 4)
for i in range(N):
    b.add("key-%d" % i)
hits = 0
for i in range(N, N + 100_000):
    if ("miss-%d" % i) in b:
        hits += 1
print("  10 万次不存在的查询，%d 次被误判为存在（%.2f%%），这些都会穿透到数据库" % (hits, hits / 1000.0))

输出：

m=1000000 bit（10 bit/项，k=4）  假阳性实测 0.0118  理论 0.0118
m=1600000 bit（16 bit/项，k=4）  假阳性实测 0.0029  理论 0.0024

读路径上查 key 存在的次数（每查一次假阳性就浪费一次 DB 回源）：
  10 万次不存在的查询，1161 次被误判为存在（1.16%），这些都会穿透到数据库

读法：

  • 10 bit/项、k=4 时假阳性率 1.18%（理论 1.18%，实测与公式吻合到小数点后两位），16 bit/项时降到 0.29%（理论 0.24%，实测略高是因为样本只有 2 万次查询）。
  • 换算成读路径：10 万次“这个 key 不存在“的查询，有 1,161 次被误判为存在并穿透到数据库。假阳性率 1% 听起来无害，可它作用在每一次不存在的短链访问上——而短链服务里“访问了一个已被删除或从未存在的 key“是常态流量，不是异常。

还有一个容易被忽略的连带效应：布隆过滤器只在写路径上帮得上忙（判断候选 key 是否已被占用）。一旦某个 key 被误判为已占用，写路径就得换下一个候选——布隆过滤器的假阳性会直接变成冲突解决次数的增加。所以布隆过滤器的位数不该按“查得快“来定，该按回源预算来定：先定“我愿意为多少比例的假阳性多打一次 DB“，再反推 bit 数。

五、把三个模型套回设计：五条可执行的判据

  1. 走哈希截断，key 长度按碰撞概率算，不要按容量算。 容量 7 位够用是另一道题；抗碰撞要按 n²/2S 算，或干脆不截断。
  2. 走 ID + base62，7 位容量够用，但唯一性完全依赖 ID 生成器；分布式 ID 的位分配与时钟回拨见《雪花 ID 的 41 位怎么分配》。注意“ID 每涨 1 就换一个 key“会让短链可预测——自增 ID 直接 base62 等于把全站短链变成一个可枚举的序列。
  3. key 长度 ≤ 4 位时，视为公开。 单机秒级可枚举，不要在文档或设计评审里把它当保密措施。
  4. 字符集选 base62：与 base64 同长度容量差不大、编码长度几乎相同，而标准 base64 一半样本含 + /，URL 里要转义。若必须用 base64，用 URL-safe 表。
  5. 布隆过滤器按回源预算定位数，并预期它的假阳性会同时推高写路径的冲突重试次数。

六、什么时候不该用哈希截断

  • 要求短链稳定（同一长链永远同一个短链）：哈希天然满足，ID 方案需要额外存映射或保证 ID 由长链派生。
  • 要求短到能塞进短信/明信片：长度是硬约束时，宁可接受更长的字符集（base62 → 加前缀分桶）也不要靠截断哈希硬压。
  • 要求短链不可枚举：哈希截断 + 短 key 恰好是最差组合（可被全量扫描）；要么加长，要么换威胁模型。
  • 要求 key 本身有序或可分区：哈希不保序，ID 保序但会暴露规模。

八、这三个模型判不了什么

  • 哈希不是理想均匀的。 实测用的是 SHA-256 转 base62 的前缀，均匀性接近理想；真实哈希函数的首位/前缀可能有可利用的偏置。
  • 生日悖论假设 key 独立同分布。 攻击者若能观察你的 key 分布，可以刻意构造输入让哈希集中到已占用的前缀上——模型里的期望碰撞数会显著低估被定向攻击时的实际损失。
  • 枚举速度是 Python 实现的实测下限，换 C/Go 快一到两个数量级属于量级推算而非实测，本文用它支撑的只是“≤4 位必然被扫“这个弱结论。
  • 布隆过滤器只回答“存在与否“，不回答“这个 key 是不是我的长链的 key“；前者能挡住冲突，后者要靠数据库。
  • 三个模型都不含容量规划：3650 亿条、365 TB、分片与冷热分离属于另一条线。

FAQ（九、常见问题）

7 位到底够不够？ 看走哪条路线。ID + base62：够，因为 ID 唯一，碰撞概率恒为 0。哈希截断：远远不够，7 位空间的碰撞概率已接近 1，抗碰撞需要 18 位（1×10⁻⁹ 口径）。

为什么不用 base64？ 可以用。同长度容量多 21%~29%，编码长度几乎相同（32 位摘要两者都是 6 字符），但标准 base64 表含 + /，实测一半样本会触发 URL 转义；用 URL-safe 表可以规避。

key 取几位才“安全“？ 长度与安全性无关。≤4 位可被单机秒级全量枚举；5 位在编译语言下也只需分钟级。真要保密，靠服务端校验，不靠 key 短。

布隆过滤器能替代数据库吗？ 不能。它只把“一定不存在“的查询挡在数据库之前；假阳性会穿透（实测 1.18%），而假阳性率应当按可接受的回源预算来反推位数。

3650 亿条 / 365 TB 是怎么来的？ 需求段给出的量级估算：每天 1 亿条乘 3650 天约等于 3650 亿条，每条记录包含主键、短链与长链，长链占存储大头。
