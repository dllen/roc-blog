让结论可解释：事件溯源、CQRS 与需求变化的位置

#软件工程#架构设计#事件溯源#领域建模

要让结论可解释，第一步是承认它现在不可解释。软件能跑起来，数据却逐渐变成无法解释的黑洞——这是很多跑了多年的业务系统共同的命运。问题不在数据库，在于某个字段把太多东西压成了一个值。

本文整理自南京大学《生成式软件工程》2026 秋第 6 讲「需求和架构 (1)」（主讲：jyy），原始讲义。讲义用教务系统作为贯穿例子；文中事件溯源、CQRS、DDD 的模式定义参考了 Microsoft 的 Event Sourcing 与 CQRS 模式 说明，限界上下文部分参考 Eric Evans 的 DDD Reference。

一、代码便宜以后，什么变得更重要

传统软件工程面对几个朴素而顽固的事实：客户用自然语言描述工作，开发者必须翻译成精确行为；满足同一组要求的实现方法有很多；产品好不好用往往要做出来才知道；而代码生产和返工都很贵，一个前面的误解可能在后面变成整个团队数周的无效劳动。

于是有了各种方法论。但这里有一重张力：**需求、产品和架构又特别难做定量研究。**一个架构今天写起来顺手，三年后是否仍然合适？一种需求分析方法让产品成功了，究竟是方法有效，还是参与者本来就更有经验？这些问题很难像比较算法运行时间那样放进统一实验里得到答案。

于是有了本讲的核心因果链：**当生产目标明确的代码变得便宜，需求、产品设计和架构就成为撬动软件生产力的杠杆。**一个正确的抽象，可能让后续大量代码都变得容易生成和检查；一个含混的决定，也可能被 AI 迅速扩散到整个系统。

讲义给这个病态起了名字——AI Slop：

如果我们只追求生成速度，最后得到的就可能是 AI Slop：代码和功能不断堆积，却越来越难说明它们为什么正确、彼此怎样配合。

二、需求泥潭：表面是几张表，背后是许多参与者

教务系统是个好例子。学生要经历学籍登记、培养方案选择、选课、考试、成绩认定和毕业审核；教师开课、管理名单、登记成绩；教务员排课、处理学籍变化；教务处执行政策、汇总统计；财务和辅导员各有业务。表面上是几张表、几个页面，背后却连着许多不同的参与者。

为什么经典做法（逐一访谈需求方）在这里会失败？两条独立的理由：

  1. 成本：逐一访谈一遍，期末考试都结束了。
  2. 本质：客户常常说不清楚完整需求。一个人熟悉自己每天处理的普通情况，却未必能立刻列出所有例外；不同人即使都说清楚了，也未必能达成一致。

冲突是结构性的。讲义给的冲突三角很典型：学生希望选上课，教师希望控制班额，教务员希望学生按时毕业——这几个要求遇到同一门满员的必修课时，就需要有人作出业务决定。

真正困难的地方在于规则会相遇。假设一位 2024 级学生在 2026 年转入计算机专业，适用目标专业的 2024 版培养方案：毕业至少需要 160 学分，其中通识 40、专业必修 72、专业选修 28、实践 20，每一类都要分别达标；数学要求可以用 5 学分的高数 A 满足，也可以用 4 学分的高数 B 加 1 学分的桥接课满足；算法课要求先通过数据结构；缓考学生可以暂时选课，但开课前仍未通过就要撤销；两门交换课程经批准可合抵一门 4 学分的算法课，但不能重复计入专业选修。

每一条单独看都不难。难的是它们会相遇：转专业学生恰好参加过交换，交换课程还没有完成认定，先修课正在等待缓考成绩，此时选课窗口却马上关闭。

**总有某种经过线下批准的特殊情况，没有来得及变成系统里的规则。**最后只能有一个「视为满足」的兜底入口——大家调侃的「暗箱操作」。

但这个入口本身也有需求。系统必须能表达：谁有权批准、豁免哪一项要求、适用于哪个学生和哪一版方案、理由是什么。若系统不能表达这些内容，工程师就只能直接改数据库。

讲义记录了一次课堂实验：绕过前端校验，把一位同学的缺课次数改成 -1。结果是教务系统中所有能选出这位同学选课记录的部分都瘫痪了。讲义的解读很克制：

我们没有据此定位某一处具体代码错误，但可以看到，某个看似局部的数据假设，已经被许多功能共同依赖。一个特殊值进入系统，问题就沿着这些依赖扩散。

这句「沿着依赖扩散」是理解后续所有内容的钥匙——它引出的正是数据依赖图这个贯穿全讲的分析工具。

三、MVP 帮助发现需求，也会掩盖困难

AI 让最小可行产品变得非常容易。先实现最重要的功能，把一个可操作的产品交给用户，往往比继续讨论抽象需求更有用。用户马上就能指出：「这门课我在交换时已经修过了，为什么系统还要求我再修一次？」试用本身就在帮我们发现没有说出口的需求。

但 MVP 也有反面。

**第一次顺利运行容易让人产生「我已经驾驭了 AI」的错觉。**原型走通了正常路径，转专业、课程替代、规则追溯和人工批准这些角落，可能还没有露出獠牙。

更大的考验是：**需求变了以后怎么办。**把「一门交换课程替代一门本校课程」改为「允许两门交换课程合抵一门必修课」，受到影响的就不只是一个下拉框——课程对应关系、学分计算、毕业审核、成绩单显示、相关测试，全都要改。还有两个业务问题必须回答：已经认定过的学分是否重新计算？已经批准的特例是否继续有效？

讲义引回了上一讲的数据依赖图：一个结论以另一个结论为前提，需求变化就可能沿着依赖关系穿透整个系统。软件增长得越快，未管理的依赖也可能积累得越快。

所以结论不是「所以别用 MVP」，而是：快速生成原型很有价值，但需求冲突、历史包袱和持续变化仍然要有人处理。接下来的问题就是——怎样让这些复杂性有合适的位置？

四、几行代码也有架构

讲义对架构的定义性陈述：

软件架构决定我们怎样分解问题、安排职责和组织依赖。它让一些事情变得容易，也决定另一些事情将来需要付出多大的修改成本。

门槛比想象的低。不必等到有数据库、微服务和流式数据处理，才开始谈架构。一个小程序也可以先读取输入，再解析、处理，最后输出。这几个阶段一旦成为明确的边界，就有机会分别考虑三个问题：换一种输入格式，需要改到哪里？核心算法是否必须知道结果最终写到终端还是文件？错误应该由谁处理？

但讲义立刻给出反驳：**把代码切成四个函数，还不能保证边界真的存在。**判据是——如果它们随意修改同一批全局变量，每一步都依赖其他步骤的内部细节，变化仍然会四处传播。

架构的价值要落实到数据怎样流动、谁拥有状态、谁可以依赖谁。

由此可以得到一个学编程语言的新视角：

语言构件架构作用
函数表达边界
类型约束表示
作用域限制信息可见的范围
调用栈保存尚未完成的工作

五、十行汉诺塔：复杂性只是换了地方

讲义用「不允许递归写汉诺塔」这个题，展示同一问题的三种表示。

第一种看法（数学规律）：把盘子从小到大编号，最少步数解中第 step 步移动的盘号，就是 step 的二进制表示末尾连续零的个数加一。三层汉诺塔的步号 1 到 7，对应盘号恰好是 1, 2, 1, 3, 1, 2, 1。方向也是固定的，由总盘数和盘号的奇偶关系决定。

for (uint64_t step = 1; step <= total; step++) {
    int disk = 1;
    for (uint64_t x = step; (x & 1) == 0; x >>= 1) {
        disk++;
    }
    int direction = (n - disk) % 2 == 0 ? -1 : 1;
    int from = position[disk];
    int to = (from + direction + 3) % 3;
    printf("Move disk %d: %c -> %c\n", disk, pegs[from], pegs[to]);
    position[disk] = to;
}

讲义对这段代码的评价极其克制但深刻：

这段程序之所以短，是因为对问题的理解已经承担了原来需要代码处理的复杂性。代价则是必须解释并验证这些规律；若游戏规则变了，原来的数学结构未必还能使用。短代码也没有消除指数级的移动次数。

复杂度没有消失，只是从代码转移到了理解里。

第二种看法（显式保存任务）：把「还没做完的任务」存起来，一个任务记录盘数、起点、终点和辅助柱。讲义指出一个反直觉的细节：用栈保存任务时，因为后放入的先取出，必须按执行顺序的反方向压栈。

第三种看法（模拟调用栈）：每层调用用一个栈帧表示，保存 n、三根柱子的角色，以及程序计数器 pc——pc 表示「这层函数执行到了哪一步」。遇到调用压栈，遇到返回弹栈，重新轮到上一层时按保存的 pc 接着执行。讲义的评价升到了另一个层次：这时我们其实构造了一台很小的抽象机器，函数调用和返回都变成了状态转移。

三种写法的对照结论：**它们分别把复杂性放在数学规律、任务分解和执行机器里。**有价值的部分在这些表示方法本身——若只盯着眼前该写哪个 if，很容易陷入越来越多的分支；换一种表示，问题可能突然变得简单。

架构关乎的，正是我们对问题掌控到了什么程度。

六、两千行二维码程序：原来我们需要一个编译器

这一节从汉诺塔向外走，是本讲方法论上最完整的一段。

需求：在 Excel 中输入字符串，由工作表公式计算并显示二维码，修改输入后二维码随之变化。

直接做会失败，失败机理很具体：**直接让 Agent 写出所有公式，很快就会碰到长公式的脆弱性。**括号、引用、数组运算和算法步骤缠在一起，模型可能花大量时间与不配对的括号搏斗。

即使公式终于能运行，下一次需求变化仍然很痛苦：要兼容更老的 Excel、利用新版本的能力、把二维码移动到工作表另一个位置、换一种计算方法、再增加一个字符串输入单元格——原本看似局部的修改，都可能穿过整片公式。

跳出公式来看：二维码算法用普通编程语言并不难描述，困难在于怎样把这些计算映射到工作表。需求的重新表述是：

我们真正需要的，其实是一个小型编译器——用一种便于表达算法的形式描述计算，再把它翻译到目标环境。

可行设计是中间表示（IR, Intermediate Representation）：IR 保存输入、常量、异或、查表、条件选择等计算节点，节点之间的边记录数据依赖。高级语言负责构造这张计算图，后端再负责把它翻译成 Python 程序或 Excel 公式。

这里有一个必须分清的区分——生成时 vs 运行时：

  • Python 中的循环可以按选定容量，展开二维码计算所需的有限步骤（生成时）；
  • 用户将来输入的字符串则要保留为符号输入（运行时）；
  • 由字符串内容决定的分支，也必须变成图里的条件选择节点，留给 Excel 在重算时判断。

讲义给了一句警示性推论：否则生成器只是提前算出了一张固定二维码，并没有实现原来的需求。

有了 IR，几类变化就能找到各自的位置：

变化由谁负责
算法改变算法只知道名为 text 的输入
输入绑定改变输入绑定模块才知道它位于哪个单元格
布局改变（移动二维码位置）布局模块分配中间结果和最终图案的位置
兼容不同 Excel 版本由目标能力和公式生成部分处理
增加一个输入先明确它怎样参与拼接、编码和容量计算

IR 本身也需要自己的语义——讲义列出不能交给后端各自猜测的东西：**字节的取值范围、整数除法、字符串编码、数组形状。**此外构图时可以检查类型和容量，节点还可以保存来源，使错误能够追溯到某一步计算。括号和单元格引用由生成器统一处理，算法作者就不必在每个地方重新处理这些细节。

性能优化也有了明确的位置：常量折叠（与输入无关的内容生成时算好）、公共子表达式共享（重复的纯计算共享一个节点，避免把同一段长公式到处粘贴）、内联 vs 辅助单元格（真正生成工作表时再决定哪些内联、哪些放辅助单元格）。

讲义还给出一种交叉验证办法：给定相同输入，比较 Python 的结果与目标 Excel 实际重算后的结果。但它立刻指出了局限：两者可能共享同一个算法错误，因此还应通过独立实现或二维码解码器核验内容。

这一节的落点：

这套设计的价值在于，一次需求变化可以主要落到负责它的模块。我们仍然需要验证整个结果，但不必每次都重新与所有公式搏斗。

七、当前状态里藏着什么

讲义用「把系统看成当前状态的快照」这一种理解方式引出全讲的核心问题。

这就是常说的 CRUD（创建、读取、更新、删除）。数据库课程中的范式帮助减少冗余和更新异常。对于简单的数据维护，这种组织方式十分直接——只要为每个按钮找到对应的状态变化，一个功能似乎就完成了。

但讲义指出了一个被忽视的性质：教务系统里的许多字段，已经是推理和决策的结果。

例子极为典型：一个 can_graduate = true，可能依赖学生的课程成绩、课程替代审批、培养方案版本和人工豁免。它把历史事实、适用规则以及根据规则作出的决定，压缩成了一个当前值。

这又是一组数据依赖，于是引出核心困境：

  • 成绩更正以后，哪些学分认定需要重新计算？
  • 哪些毕业审核需要复核？
  • 某个决定如果已经正式发布，还能不能直接覆盖？

讲义的判断很直接：即使数据库表没有重复字段，如果没有保存这些依赖，我们仍然不知道一个结论从哪里来，也不知道前面的变化会破坏哪些后续结论。

**更麻烦的一层：软件只是现实过程在信息世界中的有损投影。**现实中政策已经更新、领导已经批准，系统却还没来得及表达它；眼看今天不处理，学生就不能毕业了，工程师只能先把数据库改成「满足毕业条件」。然后是那个真正致命的问题：

如果最后只留下一个布尔值，几个月以后就难以分辨：这是正常审核、正式特批，还是一次救火时的误操作？

收束于两句递进的诊断：

程序还能运行，数据却逐渐变成无法解释的黑洞。继续让 AI 修修补补，可以消除眼前的一些报错，却未必能补回已经丢失的业务含义。

身份、属性与时间

讲义用一个具体问题演示「保存结论」不够：计算机系变成计算机学院（真实事件），dept_id 该沿用还是新建？

方案 A（沿用旧 ID，直接覆盖名称）：关联都能继续工作，但查询历史成绩单或报表时，只要连接到现在的组织表，过去的「计算机系」也会被显示成「计算机学院」；如果层级、职责和管理范围一并改变，一个 ID 背后就混入了不同时间的含义。

方案 B（新建 ID，保留旧组织）：新学院可能变成一个没有学生、没有课程、没有权限关联的空壳；把所有旧关联迁过去，又会改写学生和课程过去的归属；跨年统计、权限继承、培养方案适用范围，仍然需要解释两个组织之间是什么关系。

讲义给出的核心解法是一个三分法：区分组织身份、组织属性，以及某个时刻的隶属关系。

业务判断处理方式
组织身份延续保留稳定的组织 ID，让名称、层级等属性按有效期保存版本
产生了新的组织建立新 ID，并记录带日期的承继关系，按业务决定转移相应关联，同时保留历史归属

查询也要说清口径：是查看当时的组织归属，还是按今天的组织结构重新汇总？讲义给了一条很实际的要求：培养方案应有自己的版本，不能因为组织换了名称，就让学生自动适用另一套毕业要求。

同样的三分法在别处重复出现：**业务发生或生效的时间，与系统得知这件事的时间，应该分别保存。**假设一项豁免在 6 月 1 日生效，6 月 3 日才录入系统，那么「6 月 2 日豁免是否有效」和「6 月 2 日系统为什么拒绝毕业」是两个问题——只保存一个时间，无法同时解释它们。

身份 / 属性 / 时间：当一个东西会随时间变化时，把「它是谁」「它现在是什么样」「它什么时候是这样」分开保存。

八、事件溯源：把历史保存下来

讲义这一节的提问方式本身就体现了思路风格：既然依赖和历史如此重要，为什么不把它们变成程序可以明确表示、保存和处理的对象？

数据结构有两种观察角度：

  • 只保存状态：「张三目前选了《生成式软件工程》」
  • 保存事件：「张三的选课申请已被接受」这件事，以及后来是否退选、是否再次选入

后者能回答前者回答不了的问题：把被系统接受的事件依次应用到初始状态上，可以得到当前状态；改变查询方式，还能回答过去发生了什么。

这就是事件溯源（Event Sourcing）：把状态变化保存在事件序列里，并让状态能够由这些记录重建。讲义给的类比是账本——余额告诉你现在有多少钱，逐笔收支还能解释钱为什么变成了这么多。

回到教务系统，可记录的事件包括：选课已接受、成绩已登记、课程替代已批准、毕业审核已完成；再从中构造学生课表、教师点名册或审核视图。两个术语在此定义：

  • 投影（projection）：把事件转换成某种状态或查询结果的过程；
  • 重放（replay）：重新应用已有事件的过程。

性能上的现实约束：记录历史也不要求每次查询都从学生入学开始重新计算。日常维护当前结果，新事件到来时增量更新；需要重建时再重放相应历史，或者从一个有明确位置的快照继续处理后续事件。

**但事件序列本身不够。**讲义指出了它的边界：

若要沿着依赖找到受影响的结论，还应记录一次学分认定或毕业审核具体使用了哪些输入、哪个规则版本、什么审批依据。把日志保存下来，是为可解释性准备材料；还需要设计这些材料之间的关系。

这句区分很重要：**事件溯源解决的是「状态从哪来」，不自动解决「这个结论依赖了什么」。**后者仍然是 traceability 问题。

九、恢复历史与按新规则重算

讲义先给出一个必须避开的误解：

保存事件，让我们在语义改变时有了更多余地，但不能把它理解成「以后规则随便改，历史自然都能正确恢复」。

至少要区分两个问题：

  1. **当时究竟发生了什么，为什么作出那个决定？**回答它需要当时记录的事实、适用规则和有关输入。
  2. **如果用今天的新方案重新审核，会得到什么结果？**这可以通过新的投影或计算得到，但它并不自动改写已经发生的事实。

讲义给的例子直击要害：**一位学生已经获得学位。今天换一套规则重算，结果不符合要求，不能因此让「当年已经授予学位」这件事从历史里消失。**若业务上需要复核或撤销，应经过相应流程，再记录新的决定。

事件格式和业务规则也会各自演化，需要分别管理版本。讲义给了事实录错时的正确做法：可以追加更正事件及其原因，保留原始记录与更正之间的关系。

重放必须隔离对外部世界的副作用，讲义列了两条：

  • 重建一次选课视图，不能再给所有学生发送一遍短信，更不能重复扣费；
  • 若历史决定依赖一个外部查询的结果，也需要保留当时的输入，不能拿今天查到的值冒充过去的依据。

收束句是一个成本判断：历史保存得越完整，我们就越有机会解释旧决定、比较新方案和修正错误；哪些信息值得保存，仍然是一项架构决定。

十、CQRS：怎样做决定，怎样看结果

CQRS = Command Query Responsibility Segregation（命令与查询职责分离），是大语言模型出现之前的软件工程实践。它把负责接受业务操作的写模型，与负责提供查询结果的读模型分别设计。

模型例子职责
命令「申请选课」表达一个业务意图。写模型检查先修资格、课程容量和时间冲突，再接受或拒绝申请
查询学生看课表 / 教师看点名册 / 教务员看开课统计服务于不同使用者，这些结果没有必要被迫使用同一种展示结构

讲义对架构边界做了重要澄清：CQRS 的重点在两类模型的职责，可以在同一个进程、同一个数据库里实现；是否再采用事件溯源，是另一个选择。

**异步化引入的代价：最终的间隙。**若读模型通过异步处理事件更新，就可能出现短暂的间隙——选课已经确认，课表还没刷新。两条设计要求：

  • 界面需要能解释这个状态，系统也要明确「选课成功」究竟由哪个环节确认；
  • 不能因为查询视图还没显示这条记录，就让用户误以为没有成功而不断重复提交。

**还有一个更硬的约束：并发。**只剩最后一个名额，两位学生同时申请，不能让两人都占位成功。解法是：检查容量与确认占位需要作为一个不可被其他申请穿插破坏的操作完成。

讲义随即纠正了一个常见的错误推论：使用事件存储时，也仍然需要并发控制——追加前检查所读取的事件流版本，发现已经变化就重新读取和判断。并发控制不会因为数据采用追加方式就自动消失。

本节的结论是一个可以被明确讨论的决定：系统中哪些部分必须立即保持一致，哪些查询结果允许稍后更新。

十一、DDD：让业务概念决定边界

DDD = Domain-Driven Design（领域驱动设计）。讲义给「领域」下了明确定义：这里的领域就是软件试图处理的业务世界。

核心机制：开发者与业务人员共同建立模型，让「选课」「学分认定」「毕业审批」这些概念进入软件的结构和语言，而不是只围绕数据库表名讨论系统。

两个关键概念：

  • 统一语言（Ubiquitous Language）：在一个明确边界内，同一个词应当具有一致的含义；
  • 限界上下文（Bounded Context）：明确模型适用的范围，再描述不同范围之间如何协作。

讲义对限界上下文的动机说得很清楚：一个庞大的系统不必强迫所有参与者共享一份无所不包的模型。

用限界上下文解释教务系统：

范围关心什么
选课业务学生有没有资格、课程还有没有名额
财务业务应收和到账
毕业审核认定学分与适用方案

它们都谈到「学生」，但需要维护的状态和规则并不相同。

边界之间传递信息时，也要明确含义。讲义给了一个反面案例，这正是「统一语言失效」的具体形态：

「课程成绩已经通过」可以成为学分认定的输入，但能否计入某个专业的毕业学分，应该由学分认定的规则决定。如果直接把两个概念压成同一个 passed 字段，以后就很难解释「通过了这门课，却仍然不满足这项毕业要求」的情况。

十二、让下一次需求变化有地方可去

第一步：从一个结论开始。一次毕业审核除了保存「通过」或「不通过」，还可以记录：输入记录的标识与版本（或当时的快照）、规则版本、结论、审批依据。收益很明确：成绩被更正时，系统能够沿着依赖找到受影响的审核；已经发布的正式决定，则进入复核流程。

**第二步：把时间明确表示。**业务发生或生效的时间，与系统得知这件事的时间，分别保存。

**第三步：模块边界应围绕可能变化的决定来安排。**讲义点名了三个各自有负责模块和明确接口的对象：培养方案、课程替代、组织身份映射。

关于微服务，讲义给了一个很清醒的顺序建议：

起初完全可以把这些模块放在一个程序里，先把数据归属和调用关系理清；需要独立发布或扩容时，再考虑拆成服务。把一个大文件拆成许多服务，并不会自动补上原来没有说清楚的业务边界。

**第四步：对于已经运行的系统，从一条业务链逐步改进。**讲义给了一条具体的渐进路线，这是本讲最具操作性的建议：

  1. 先整理毕业审核的事实来源、规则版本和审批流程；
  2. 让新旧审核并行计算；
  3. 重点解释转专业、补考、课程替代与人工豁免案例中的差异；
  4. 再逐步切换权威写入入口；
  5. 旧系统提供切换时的基线快照，明确其时间和来源。

底线原则：已经丢失的历史，不能伪装成我们亲眼记录过的事件。

成本判断：追溯与重算有成本，可以优先用于确实需要解释依据的业务；简单的信息维护仍然可以采用 CRUD。每增加一层结构，都应能说明它让哪一种变化更容易处理，以及带来了什么新的维护责任。

讲义的总结陈词：

从十行汉诺塔、两千行二维码程序，到几十万行的教务系统，规模不同，选择表示方式的影响始终存在。给 AI 增加「采用 CQRS」这样几个字，就可能让它生成一个完全不同的系统；这几个字背后需要我们理解的，是谁维护业务约束、哪些信息应当保留、变化沿什么关系传播。代码越容易生成，越值得在这些少量但影响深远的决定上花时间。

十三、它不解决什么

  • **事件溯源不是可解释性的替代品。**事件序列只说明发生了哪些变化。「这个结论依赖了哪些输入、哪一版规则、什么审批依据」仍然需要单独设计记录，事件日志本身不会自动回答。
  • **历史完整不等于语义正确。**重放能忠实复现当时的规则，但当时的规则本身可能就是错的。事件溯源给的是「按当时的规则算出了什么」，不是「当时的规则是对的」。
  • **CQRS 不等于分布式。**它可以在同一个进程、同一个数据库里实现。拆成分布式服务是另一个决策，而且带来读模型延迟这个新问题。
  • **限界上下文不消除重复。**选课和毕业审核都要看「学生」，边界内各自维护一套模型是刻意的代价，不是需要被消除的坏味道。真正要避免的是把两个上下文里的概念压成同一个字段。
  • **迁移的成本不会因为模式正确而消失。**渐进改造路线里的「新旧并行计算」本身就是双份成本，只有在需要解释依据的业务上才值得付。
