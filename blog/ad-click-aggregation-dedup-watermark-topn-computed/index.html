广告点击聚合的三笔账：去重、水位线与 top-N

#系统设计#架构设计#读书笔记#实时数据

广告点击聚合的三笔账？重复怎么去、水位线放多长、top-N 怎么查。这章讲义把实时聚合的骨架讲全了（事件时间 vs 处理时间、水位线、四种窗口函数、投递保证、去重、Lambda vs Kappa），但这三笔账它都留成定性判断。这篇把它们算出来。

这篇不复述译文，也不搬运中文译本的任何段落。它复述这一章的骨架（需求问答、估算、查询 API、数据模型、事件收集与去重、流式与批处理、时间与窗口、投递保证与去重、扩展与容错），然后补三个自写模型：重复事件与幂等键的代价、水位线的漏计率-延迟旋钮、聚合存储与 top-N 查询。

口径说明

  • 源笔记是 Alex Xu《System Design Interview — An Insider’s Guide》第 21 章的社区中译。上游两仓库的 LICENSE 在 main/master 分支经 raw 通道取均返回 404，上游许可未能确认；原书是商业出版物。故本篇为导读式：只复述章节骨架与需求数字，不引用译文原文或原书段落，不使用译本配图，正文主体是自写模型与判断。
  • 三个脚本均为自写增量，只依赖 Python 标准库；输出为实跑结果，逐行可复现（三段计算都不含随机数）。
  • 与已发文章的重叠见「这一章不重复已发的内容」一节。

一、本章骨架：10 亿点击/天、每分钟 top-100、水位线

需求问答：每天 10 亿次广告点击、200 万个广告，年增长 30%；核心查询是「广告 X 在过去 Y 分钟内的点击数」与「过去 1 分钟内点击量最高的 100 个广告」（聚合每分钟进行一次），都支持按 ip、user_id、country 过滤；边界情况包括比预期更晚到达的事件、重复事件、系统不同部分宕机；延迟上，广告点击聚合端到端几分钟可接受（用于计费与报表），而 RTB 要求小于 1 秒。

非功能需求：聚合结果正确性很重要（用于 RTB 与计费）、正确处理迟到与重复事件、健壮性（容忍部分故障）、延迟最多几分钟。

讲义的估算：10 亿 DAU、每人每天点 1 次 → 每天 10 亿次点击；QPS 10,000、峰值 5 倍 = 50,000；单次点击 0.1 KB → 每天 100 GB、每月 3 TB。

API：GET /v1/ads/{ad_id}/aggregated_count（参数 from/to/filter）与 GET /v1/ads/popular_ads（参数 count/window/filter）。

数据模型：原始事件形如 ad001, 2021-01-01 00:00:01, user 1, 207.148.22.22, USA，另有结构化表（ad_id、click_timestamp、user、ip、country）与聚合表（按维度汇总的计数）。

流式 vs 批处理：讲义给了三者的对比（在线服务 / 批处理 / 流处理），本设计是混合的——流处理做近实时聚合，批处理用于备份历史数据；这就是 Lambda 架构，缺点是两条处理路径与两套代码库；Kappa 架构则合并为一条流处理路径。

时间：聚合需要时间戳，可以在事件时间（点击发生的时间）或处理时间（服务器处理时间）两处生成。异步队列与网络延迟让两者可能显著不同：用处理时间则迟到事件会算错，用事件时间则要处理延迟事件（且客户端时间可能错、可能被恶意伪造）。讲义因为准确性最重要而选事件时间，用水位线（watermark）处理迟到：短水位线增加漏事件概率但降低延迟，长水位线反之；无论水位线多大总有漏掉的事件，所以每天结束时对账兜底。

窗口函数：翻滚（固定）、跳跃、滑动、会话四种；本设计对点击计数用翻滚窗口，对「过去 M 分钟点击最多的 N 个广告」用滑动窗口。

投递保证与去重：数据用于计费，所以准确性与不丢是第一位的；三种保证——最多一次、至少一次、精确一次。重复来源有客户端重发（含恶意）与聚合服务节点中途宕机导致上游没收到确认而重发。三种缓解：把最后看到的 offset 存到 HDFS/S3（可能结果永远到不了下游）、原子存 offset（需要分布式事务）、或让下游幂等处理（讲义个人备注：这样就不需要分布式事务了）。

二、增量一：去重的三种解法里，幂等下游最便宜

讲义把三条路都列了出来，但没说各自的价签。把账算出来：

"""重复事件：幂等下游 vs 精确一次投递，谁更便宜。

用讲义给的量：每天 10 亿次点击、每点击 0.1 KB、去重靠「下游幂等」或「原子存 offset（需分布式事务）」。
只依赖标准库；输出确定性。
"""
import math
CLICKS_DAY = 1_000_000_000
PRICE = 0.01              # 每次点击的计费单价（美元，估）
DUP_RATE = 0.001          # 重复率（客户端重发 + 宕机重试，估）
ID_BYTES = 16             # 事件 ID + 哈希的字节数

dup = CLICKS_DAY * DUP_RATE
print("重复事件：%s x %.2f%% = %s 次/天" % (format(CLICKS_DAY, ","), DUP_RATE * 100, format(int(dup), ",")))
print("  若下游不幂等，每次重复都计一次费 -> 每天多付 $%s，一年 $%s"
      % (format(int(dup * PRICE), ","), format(int(dup * PRICE * 365), ",")))
print()
print("幂等下游的代价：要记住所有已处理的 ID（不是只记重复的那些）")
for hours in (1, 6, 24):
    ids = CLICKS_DAY * hours / 24
    gb = ids * ID_BYTES / 1e9
    print("  保留 %2d 小时 -> %14s 个 ID = %6.1f GB（精确集合）" % (hours, format(int(ids), ","), gb))
print()
print("布隆过滤器（允许假阳性）：m/n = -ln(p) / (ln2)^2")
for fp in (0.01, 0.0001, 0.00001):
    bits = -math.log(fp) / (math.log(2) ** 2)
    gb = CLICKS_DAY * bits / 8 / 1e9
    wrongly_dropped = CLICKS_DAY * fp
    print("  假阳性 %.4f%% -> %5.1f bit/项 -> 24 小时窗口 %5.2f GB；代价：每天误丢 %s 个真实点击 = $%s"
          % (fp * 100, bits, gb, format(int(wrongly_dropped), ","), format(int(wrongly_dropped * PRICE), ",")))
print()
print("对比「原子存 offset」：需要分布式事务（讲义原话），而分布式事务的代价是")
print("  每次提交都要等所有参与者确认 -> 延迟随参与者数量线性增加；")
print("  而幂等下游只需下游自己多写一个 ID 集合。")
print()
print("判据：")
print("  - **去重的三种解法里，幂等下游最便宜**（讲义自己的备注）：存储换时间，且不需要分布式事务。")
print("  - 幂等键的存储是主要成本：24 小时精确集合 %s GB；用布隆过滤器可压到 %.2f GB，" % (
    format(int(CLICKS_DAY * ID_BYTES / 1e9), ","), CLICKS_DAY * (-math.log(0.0001) / (math.log(2) ** 2)) / 8 / 1e9))
print("    代价是假阳性会**误丢真实点击**（少计费）而不是多计费 —— 方向与重复相反，要单独监控。")
print("  - 幂等窗口必须覆盖事件的最长重试周期，否则同一事件在窗口外重发仍会被计两次。")

输出：

重复事件：1,000,000,000 x 0.10% = 1,000,000 次/天
  若下游不幂等，每次重复都计一次费 -> 每天多付 $10,000，一年 $3,650,000

幂等下游的代价：要记住所有已处理的 ID（不是只记重复的那些）
  保留  1 小时 ->     41,666,666 个 ID =    0.7 GB（精确集合）
  保留  6 小时 ->    250,000,000 个 ID =    4.0 GB（精确集合）
  保留 24 小时 ->  1,000,000,000 个 ID =   16.0 GB（精确集合）

布隆过滤器（允许假阳性）：m/n = -ln(p) / (ln2)^2
  假阳性 1.0000% ->   9.6 bit/项 -> 24 小时窗口  1.20 GB；代价：每天误丢 10,000,000 个真实点击 = $100,000
  假阳性 0.0100% ->  19.2 bit/项 -> 24 小时窗口  2.40 GB；代价：每天误丢 100,000 个真实点击 = $1,000
  假阳性 0.0010% ->  24.0 bit/项 -> 24 小时窗口  3.00 GB；代价：每天误丢 10,000 个真实点击 = $100

对比「原子存 offset」：需要分布式事务（讲义原话），而分布式事务的代价是
  每次提交都要等所有参与者确认 -> 延迟随参与者数量线性增加；
  而幂等下游只需下游自己多写一个 ID 集合。

判据：
  - **去重的三种解法里，幂等下游最便宜**（讲义自己的备注）：存储换时间，且不需要分布式事务。
  - 幂等键的存储是主要成本：24 小时精确集合 16 GB；用布隆过滤器可压到 2.40 GB，
    代价是假阳性会**误丢真实点击**（少计费）而不是多计费 —— 方向与重复相反，要单独监控。
  - 幂等窗口必须覆盖事件的最长重试周期，否则同一事件在窗口外重发仍会被计两次。

三处结论：

第一，重复事件的代价直接是钱。 每天 10 亿次点击、重复率 0.1%（客户端重发 + 宕机重试）= 100 万次重复/天；若下游不幂等、每次都计一次费（按 $0.01/点击估），每天多付 $10,000、一年 $365 万。更麻烦的是讲义强调的准确性：RTB 与广告主预算都依赖这些数，重复会直接变成「广告主多付钱」。

第二，去重的三条路里，幂等下游最便宜——这是讲义自己的备注。 「原子存 offset」需要分布式事务，而分布式事务的代价是每次提交都要等所有参与者确认、延迟随参与者数量上升；幂等下游只需要下游自己多维护一个 ID 集合。存储换时间，且不需要分布式事务。

第三，幂等键的存储才是主要成本，而它有便宜版。 精确集合在 24 小时窗口要 16 GB（10 亿个 ID × 16 B）；换成布隆过滤器：假阳性 1% 是 1.20 GB、0.01% 是 2.40 GB、0.001% 是 3.00 GB。但要注意方向：布隆过滤器的假阳性会把真实的新事件误判成重复——每天误丢 1,000 万（$10 万/天少计费）、10 万（$1,000/天）、1 万（$100/天）。少计费与多计费是两个方向的错误，要分开监控：前者是账单缺口，后者是广告主投诉。

第四，幂等窗口必须覆盖事件的最长重试周期，否则同一事件在窗口外重发仍会被计两次——窗口的选择不是「存得越久越安全」，而是「覆盖重试上界」。

三、增量二：水位线是旋钮，不是开关

讲义说「短水位线增加错过事件的可能性，长水位线反之」，并说「无论水位线多大，总有可能错过事件」。把这句话变成曲线：

"""水位线：漏计率与延迟的旋钮。

用讲义给的量：每天 10 亿点击、事件时间聚合、水位线（短 -> 漏事件多但延迟低，长 -> 反之）、每天对账。
只依赖标准库；输出确定性。
"""
import math
CLICKS_DAY = 1_000_000_000
TAU_MIN = 2.0             # 到达延迟的指数分布参数（估：平均延迟 2 分钟）
PIPELINE_MIN = 2          # 事件时间到聚合结果可见的固有延迟（估）

print("到达延迟服从指数分布（均值 %.0f 分钟）：P(delay > w) = exp(-w/tau)" % TAU_MIN)
print()
print("%-10s %14s %20s %20s" % ("水位线 w", "漏计率", "每天漏计事件", "端到端延迟"))
for w in (1, 2, 5, 10, 20, 30, 60):
    miss_rate = math.exp(-w / TAU_MIN)
    missed = CLICKS_DAY * miss_rate
    latency = w + PIPELINE_MIN
    print("%-10s %13.4f%% %20s %19.0f 分钟" % ("%d 分钟" % w, miss_rate * 100, format(int(missed), ","), latency))
print()
print("漏计率对水位线的敏感度：")
for a, b_ in ((2, 5), (5, 10), (10, 20)):
    ra, rb = math.exp(-a / TAU_MIN), math.exp(-b_ / TAU_MIN)
    print("  w %2d -> %2d 分钟：漏计率 %.4f%% -> %.4f%%（降 %.0f 倍），代价是多等 %d 分钟"
          % (a, b_, ra * 100, rb * 100, ra / rb, b_ - a))
print()
print("讲义说「无论水位线多大，总有漏掉的事件」，并用每天对账兜底：")
for w in (5, 10, 30):
    missed = CLICKS_DAY * math.exp(-w / TAU_MIN)
    print("  w=%2d 分钟 -> 每天漏计 %12s 次，对账要修正的就是这些" % (w, format(int(missed), ",")))
print()
print("判据：")
print("  - **水位线是「漏计率 vs 延迟」的旋钮，不是开关**：w 从 5 加到 10 分钟，")
print("    漏计率从 %.1f%% 降到 %.2f%%，延迟只多 5 分钟 —— 边际收益极大。" % (
    math.exp(-5 / TAU_MIN) * 100, math.exp(-10 / TAU_MIN) * 100))
print("  - 但漏计不是「少收钱」而是「账对不上」：所以必须有对账流程，否则错误会静默累积。")
print("  - 端到端延迟 = 水位线 + 管道固有延迟；讲义说几分钟可接受（RTB 要 <1 秒），")
print("    所以这两个场景不能用同一套水位线参数。")

输出：

判据：
  - **水位线是「漏计率 vs 延迟」的旋钮，不是开关**：w 从 5 加到 10 分钟，
    漏计率从 8.2% 降到 0.67%，延迟只多 5 分钟 —— 边际收益极大。

    所以这两个场景不能用同一套水位线参数。

三处结论：

第一，漏计率对水位线的敏感度是指数级的，所以水位线是个高杠杆旋钮。 到达延迟按均值 2 分钟的指数分布估：w=1 分钟 → 漏计 60.65%；w=5 分钟 → 8.21%；w=10 分钟 → 0.67%；w=20 分钟 → 0.0045%。w 从 5 加到 10 分钟，漏计率降 12 倍，代价是多等 5 分钟（端到端 7 → 12 分钟，仍在讲义「几分钟可接受」的范围内）。

第二，漏计不是「少收钱」，是「账对不上」。 每天漏计 8,200 万（w=5）还是 670 万（w=10），对下游是两种完全不同的修正工作量——这正是讲义说「每天结束时对账」的必要性所在：漏计无法被消除，只能被事后修正，所以对账流程必须按漏计量级设计容量。

第三，端到端延迟 = 水位线 + 管道固有延迟，而不同场景不能共用同一组参数。 讲义说计费场景几分钟可接受、RTB 要小于 1 秒——RTB 根本不能用事件时间 + 水位线这套（它的超时预算装不下一个水位线）。判据：先分场景定延迟预算，再反推水位线；把计费场景的水位线参数直接套到 RTB 上会直接违约。

四、增量三：聚合表的大小由 key 基数决定，top-N 用候选集而不是排序

讲义要求「过去 1 分钟点击量最高的 100 个广告」（滑动窗口）、每分钟聚合一次，原始数据 100 GB/天。把聚合侧的账算出来：

"""聚合的存储账与 top-N 查询代价。

用讲义给的量：200 万广告、10 亿点击/天、单次 0.1 KB、每分钟 top-100（滑动窗口）、峰值 5x、原始 3 TB/月。
只依赖标准库；输出确定性。
"""
import math
CLICKS_DAY = 1_000_000_000
ADS = 2_000_000
PEAK_QPS = 50_000
TOP_N = 100
SHARDS = 16
ACTIVE_SHARE = 0.10       # 当天有活动的广告比例（估）
ROW_BYTES = 50            # 一行分钟级聚合的字节数（估）
EVENT_BYTES = 100         # 单次点击 0.1 KB

print("原始事件：%s 次/天 x %d B = %.0f GB/天 = %.1f TB/月（讲义 100 GB/天、3 TB/月）"
      % (format(CLICKS_DAY, ","), EVENT_BYTES, CLICKS_DAY * EVENT_BYTES / 1e9,
         CLICKS_DAY * EVENT_BYTES * 30 / 1e12))
print()
print("分钟级聚合（滚动窗口）：行数 = 活跃广告 x 1440")
active = int(ADS * ACTIVE_SHARE)
rows = active * 1440
print("  活跃广告 %s 个（%.0f%% x %s）-> %s 行/天" % (format(active, ","), ACTIVE_SHARE * 100,
                                                  format(ADS, ","), format(rows, ",")))
print("  每行 %d B -> %.1f GB/天 = %.1f TB/年" % (ROW_BYTES, rows * ROW_BYTES / 1e9, rows * ROW_BYTES * 365 / 1e12))
print("  => 聚合比原始小 %.1f 倍（把同一广告的多次点击合并成一行）" % (CLICKS_DAY * EVENT_BYTES / (rows * ROW_BYTES)))
print()
print("top-%d 查询（滑动窗口）：" % TOP_N)
print("  每片维护一个 %d 大的候选集（每事件 O(log N)）：" % TOP_N)
print("    峰值 %s QPS x log2(%d) = %s 次堆操作/秒" % (format(PEAK_QPS, ","), TOP_N,
                                                  format(int(PEAK_QPS * math.log2(TOP_N)), ",")))
print("  跨片归并：%d 片 x %d 条 = %d 条/查询" % (SHARDS, TOP_N, SHARDS * TOP_N))
print("  若在窗口内全量排序：%s 行/天的窗口 -> 不可行" % format(rows, ","))
print()
print("热点：偏斜的粒度是「单个广告」，不是「热门广告集合」")
even = PEAK_QPS / SHARDS
print("  均匀分片：每片 %d QPS（片数 %d）" % (even, SHARDS))
for single_share in (0.001, 0.01, 0.10):
    one_qps = PEAK_QPS * single_share

      % (format(int(ADS * 0.01), ","), format(int(PEAK_QPS * 0.5), ",")))

print("    每片只多接 %.0f QPS），但一个占 1%% 点击的超级广告会让它那一片 +16%%、占 10%% 则 +160%%。" % (PEAK_QPS * 0.5 / SHARDS))

  - **聚合的收益来自「同一 key 的多次事件合并」，代价来自「key 基数 x 时间粒度」**：
    行数 = 活跃广告 x 1440，与点击量无关 —— 所以广告数比流量更能决定聚合表大小。
  - **top-N 用「每片维护候选集 + 归并」，不要在窗口内全量排序**：
    每事件 O(log 100)、每查询 1600 条，比扫 288,000,000 行小几个数量级。
  - **偏斜的粒度是「单个广告」**：按 ad_id 哈希时热门广告集合会被打散（1% 的广告占 50% 点击，

三处结论：

第一，聚合的收益来自「合并同一 key」，代价来自「key 基数 × 时间粒度」，与流量无关。 分钟级聚合的行数 = 活跃广告数 × 1440，不是事件数。按 10% 广告当天有活动（20 万个）估 → 2.88 亿行/天，每行 50 B → 14.4 GB/天、5.3 TB/年，比原始事件小 6.9 倍。判据：决定聚合表大小的是广告数与粒度，不是点击量——所以「我们有 200 万个广告」比「我们有 10 亿次点击」更该进容量评审。

第二，top-N 必须是「每片维护候选集 + 归并」，不能在窗口里全量排序。 每事件 O(log N) 更新一个 100 大的候选集：峰值 50,000 QPS × log₂100 ≈ 33 万次堆操作/秒，可接受；跨片归并是 16 片 × 100 条 = 1,600 条/查询。而「在窗口内全量排序」意味着扫 2.88 亿行——差好几个数量级。

第三，偏斜的粒度是「单个广告」，不是「热门广告集合」。 按 ad_id 哈希分片时：1% 的广告（2 万个）合计占 50% 点击，这 2.5 万 QPS 会被打散到 16 片，每片只多接 1,562 QPS，不构成偏斜；但一个占 1% 点击的超级广告 → 500 QPS 全在它那一片（+16%），占 10% → +160%。判据：只有单个广告的 QPS 超过分片均值 10% 时才需要特殊处理（单独分区或独立计数）。而且按 ad_id 分片对这两个查询都友好：同一广告的点击天然同片（点查是单片读），top-N 可以按片取 top-N 再归并。

五、把三个模型套回本章（判据清单）

  1. 去重优先选幂等下游：精确集合 24 小时 16 GB → 布隆过滤器 2.4 GB（假阳性 0.01%），代价是每天误丢 10 万个真实点击；「原子存 offset + 分布式事务」最贵。
  2. 幂等窗口覆盖重试上界，不是「存得越久越好」。
  3. 少计费与多计费分开监控：重复导致多付钱，布隆假阳性导致少收钱，方向相反。
  4. 水位线是高杠杆旋钮：w 5→10 分钟，漏计率 8.21%→0.67%（12 倍），只多等 5 分钟。
  5. 漏计只能靠对账兜底：对账容量按漏计量级设计（w=5 时每天 8,200 万条）。
  6. 延迟预算按场景分：计费几分钟可接受、RTB <1 秒——RTB 装不下事件时间 + 水位线这套。
  7. 聚合表大小 = 活跃 key 数 × 粒度：2.88 亿行/天（20 万活跃广告 × 1440），与点击量无关。
  8. top-N 用每片候选集 + 归并（每事件 O(log 100)、每查询 1,600 条），别扫 2.88 亿行。
  9. 偏斜看单个广告：热门广告集合会被哈希打散，单个超级广告才会让某片 +160%。

六、这一章不重复已发的内容

  • 消息队列的至少一次与去重表（去重的存储结构）：见《消息队列的三笔账》——那篇讲队列侧的去重窗口与存储乘数，本篇讲聚合侧的去重键与计费后果。
  • 短链的布隆过滤器与碰撞概率：见《短链的键要多长》——那篇算的是容量与碰撞，本篇用同一个布隆过滤器公式算的是假阳性导致的漏计。
  • 信息流的写扩散与读扩散：见《写扩散还是读扩散》——那是排序读的另一种形态。

七、这三个模型判不了什么

  • 重复率 0.1%、到达延迟均值 2 分钟（指数分布）、活跃广告占 10%、每点击 $0.01、行 50 B 都是估的。真实到达延迟往往是长尾（几个百分点的流量迟几小时甚至跨天），指数分布会低估极端迟到；而迟到超过一天的事件属于「对账也难修」的那一类。
  • 没算广告的竞价与实时出价流。RTB 的出价请求量与点击量是同一量级但方向相反（没点击就没收入），而它的延迟预算是 1 秒——本文的模型只覆盖聚合侧，不覆盖出价侧。
  • 没算去重键的跨窗口重放：同一个事件在窗口外重发（客户端离线重试跨天）需要跨窗口识别，精确集合做不到；讲义也没展开这个缺口。
  • 没算聚合表的保留与降采样。分钟级聚合按 5.3 TB/年增长，保留一年就 5.3 TB；保留策略（分钟级 7 天、小时级 1 年）能把成本砍一个数量级——聚合结果也可以降采样，和我在指标监控那篇算的是同一类杠杆。
  • 三个模型都没碰「过滤维度」的代价：讲义要求支持按 ip/user_id/country 过滤，而每加一个过滤维度，聚合表的行数就要乘一个维度——过滤维度是聚合表大小的乘数，这一项本文没算。

FAQ（八、常见问题）

重复事件有多贵？ 每天 10 亿点击、重复率 0.1% → 100 万次重复/天；下游不幂等就每次计一次费（$0.01/点击估）= 每天多付 $10,000、一年 $365 万。重复来源有两处：客户端重发（含恶意）与聚合节点宕机导致上游没收到确认而重发。

去重该用哪种方案？ 讲义列了三条，性价比是「下游幂等」最高：精确 ID 集合 24 小时要 16 GB，换布隆过滤器假阳性 0.01% 是 2.4 GB；「原子存 offset」最贵，因为要分布式事务（每次提交等所有参与者确认）。注意布隆假阳性会误丢真实点击（少计费），与重复导致的多计费方向相反，要分开监控。

水位线该放多长？ 它是「漏计率 vs 延迟」的旋钮。到达延迟按均值 2 分钟估：w=1 分钟漏计 60.65%、w=5 分钟 8.21%、w=10 分钟 0.67%、w=20 分钟 0.0045%——w 从 5 加到 10 分钟漏计率降 12 倍，只多等 5 分钟，端到端仍在「几分钟可接受」内。

漏掉的事件怎么补？ 补不了，只能对账——讲义说「无论水位线多大，总有漏掉的事件」。w=5 分钟时每天漏 8,200 万条、w=10 分钟时 670 万条，对账的容量要按这个量级设计，否则修正本身会成为瓶颈。

聚合表会有多大？ 行数 = 活跃广告数 × 1440，与点击量无关：20 万活跃广告 → 2.88 亿行/天、每行 50 B → 14.4 GB/天、5.3 TB/年（原始事件是 100 GB/天，小 6.9 倍）。所以容量评审里该问的是「有多少广告」和「粒度多细」，不是「有多少点击」。

top-100 怎么查才不扫全量？ 每片维护一个 100 大的候选集，每事件 O(log 100) 更新（峰值 50,000 QPS 下约 33 万次堆操作/秒），查询时跨 16 片归并 1,600 条；而在窗口内全量排序要扫 2.88 亿行，差好几个数量级。另外按 ad_id 哈希分片时热门广告集合会被打散（每片只多接 1,562 QPS），真正需要特殊处理的是单个超级广告（占 1% 点击 → 那片 +16%）。
