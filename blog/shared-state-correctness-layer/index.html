共享状态：并发修改、崩溃与查找

#系统设计#数据库#事务#存储引擎

共享状态要解决的是同一份数据被多方同时读写的问题，而这件事里其实混着三个完全不同的子问题：

  • 同时改，怎么不互相踩？
  • 崩了，怎么恢复？
  • 改完，怎么读得快？

这三件事的机制看起来毫不相干——锁、日志、索引树。但它们最后收敛到同一个点：你必须能证明系统状态永远满足某些性质。

这是《系统设计的三层》的第二层深挖。下一层是跨机器协作，上一层是执行与性能。

一、隔离级别是权衡，不是等级

事务的 ACID 里，最容易被误解的是 I（隔离性）：它不是一个「有或没有」的开关，而是一组可以分级放宽的保证。

级别脏读不可重复读幻读典型场景
Read Uncommitted可能可能可能几乎没有实现
Read Committed不会可能可能多数数据库默认
Repeatable Read不会不会可能MySQL InnoDB 默认
Serializable不会不会不会代价最高

方向很明确：隔离级别越高，并发度越低，吞吐越低。所以「选最高级别」不是正确答案，选「业务能接受的最低级别加明确的不变量保护」才是。

二、两阶段锁：用阻塞换可串行化

两阶段锁把事务分成增长阶段（只能加锁）和收缩阶段（只能解锁）。这个约束保证所有事务都在等锁时不可能形成环，从而避免死锁，也带来可串行化。

变体做法风险
严格两阶段锁一直持有写锁到提交最安全，也最常用
基本两阶段锁收缩阶段可提前解锁可能读到未提交结果
保守两阶段锁一开始锁全部要用的数据无死锁，但并发度极低

锁的粒度还有一层设计：共享锁与排他锁解决读写冲突，意向锁防止「别人锁了行而我要锁整表」的死锁，间隙锁在 RR 级别防幻读。

三、MVCC：读不阻塞写，但不等价于可串行化

MVCC 的核心是每个写创建新版本，读永远看到某个快照版本。它最大的价值是读不阻塞写、写不阻塞读，读操作几乎零锁开销。

代价也很实在：

陷阱说明
写写冲突两个事务改同一行，后者必须等待或失败
长事务撑爆版本链事务开得越久，旧版本越不能回收，空间膨胀且扫描变慢
快照隔离不等于可串行化允许写偏斜

写偏斜是最经典的坑，用医生值班表能说清楚：

不变量：任意时刻至少一名医生在岗

事务 T1: 读「A 在岗、B 在岗」→ 写「A 休息」
事务 T2: 读「A 在岗、B 在岗」→ 写「B 休息」
两个事务并发执行，都读到了旧快照
结果：A 和 B 都不在岗，不变量被破坏

这两个事务没有读写同一行，所以快照隔离下它们不冲突，都能提交——但合起来破坏了不变量。解决路径有三条：用真正的可串行化隔离（SSI 检测读写依赖环并中止其中一个）、加显式谓词锁、或者上乐观并发控制。

四、乐观并发控制：读-改-写窗口越长，冲突越高

核心假设是冲突很少，所以先做、冲突了再回滚。

  1. 读数据，记录版本号或时间戳；
  2. 业务计算（可能很长）；
  3. 提交前检查版本是否还是当初那个；
  4. 是则提交，否则冲突，重试或失败。
策略机制特点
版本号 CASUPDATE ... WHERE id=? AND version=?最简单，影响行数为 0 即冲突
时间戳排序每个事务带 ts，冲突时比较决定回滚谁天然可串行化，但要维护时钟
序列化检测维护读写依赖图，成环就中止SSI 的做法

关键权衡是窗口长度：读-改-写跨越的时间越长，冲突率越高。所以乐观控制适合短事务、高吞吐、低冲突（比如计数器自增），不适合长事务高冲突（那该用悲观锁或队列串行化）。

五、WAL：先写日志，再改数据

问题很朴素：数据库要改磁盘上的数据页，但一次写入可能写到一半机器就断电了。

答案是不要直接改数据，先写日志。规则只有一条：

在把任何数据页写回磁盘之前，对应的日志记录必须先落盘。

提交事务的标准顺序:

  1. 写 WAL: BEGIN, UPDATE row42 SET bal=100, COMMIT
  2. fsync(WAL)      ← 屏障点：到这里事务才算持久
  3. 返回客户端「提交成功」
  4. 异步刷脏页（可以延后）

崩溃在 1-2 之间 → WAL 不完整 → 事务视为未提交 → 客户端还没收到成功 ✅
崩溃在 3 之后   → WAL 完整 → 重做 → 数据在 ✅

WAL 之所以比直接改数据好，有三个原因：顺序写代替随机写、数据页可以延迟刷盘（写放大降低）、日志小而全。

一个高吞吐数据库几乎必然要用组提交：多个事务的 WAL 一起 fsync，一次刷盘提交多个事务。刷盘策略则是经典的三角权衡——每提交都 fsync 最安全但吞吐最低，定时刷盘吞吐高但崩溃会丢最近几秒，只写操作系统页缓存最快但最弱。

六、崩溃恢复：ARIES 为什么先 Redo 后 Undo

重启时要做两件事：重做已提交的记录，把数据页恢复到最新状态；撤销未提交的记录，避免它们污染状态。

为了避免重复执行搞坏数据，日志记录里带 LSN（日志序列号），每个数据页记录自己的 pageLSN。重放时如果日志 LSN 不大于 pageLSN 就跳过——这就让重做变成幂等操作。

ARIES 把恢复分成三步：

  1. 分析：从检查点开始扫描日志，重建事务表和脏页表；
  2. 重做：重复历史，把数据库恢复到崩溃瞬间的状态（不管事务有没有提交）；
  3. 撤销：回滚所有未提交的事务。

顺序不能反，而且重做是「幂等地重放全部」。这样恢复逻辑不必区分哪些已提交、哪些没有——这是 ARIES 的精髓。

检查点解决另一个问题：WAL 无限增长，重启要重放几 GB 日志。检查点把当前活跃事务列表和脏页列表写入日志，之前的日志在对应数据页都落盘后就可以截断，恢复从最后一个完整检查点开始。

间隔的权衡是：短则恢复快但检查点本身开销大，长则开销小但恢复慢、日志占空间大。所以现代数据库大多用模糊检查点——不在检查点强制刷完所有脏页，只记录进度，允许与写入并发。

七、B+ 树与 LSM 树：三种放大只能选两个

B+ 树LSM 树
写入随机 I/O，路径上的页都要改，可能分裂内存攒批后顺序写盘
读取树高约 3–4 层，点查 2–3 次 I/O要查多个 SSTable，靠 Bloom Filter 和索引压
典型系统InnoDB、PostgreSQLLevelDB、RocksDB、Cassandra

LSM 的本质是把随机写换成顺序写，代价是写放大：一次用户写入可能触发多级 compaction，同一个 key 被写入磁盘多次。

存储引擎里有三种放大，业界共识是最多同时优化两个：

放大含义优化手段
写放大实际写盘量除以用户写入量Leveling 每次合并少量文件
读放大一次读要查多个 SSTable更大的 Block Cache、更多级 Bloom Filter
空间放大旧版本没及时清理及时 compaction、分层 TTL

Leveling 写放大小、读放大和空间放大大；Tiering 反过来。这就是为什么同样叫 LSM，RocksDB 和 Cassandra 的性能曲线完全不同。

顺带一个时代的注脚：LSM 最初是为机械盘设计的，在 NVMe 上 B+ 树和 LSM 的差距正在缩小，选型时不该再只按「LSM 写快」这一条下结论。

八、收敛点：把不变量写下来

事务和 WAL 这两条完全不同的路径，最后都指向同一句话：你要能证明系统状态永远满足某些性质。

问题在于，隔离级别选错、代码里少加一个锁，这类 bug 在正常路径测试里几乎不会暴露，只在并发交错到特定时序时才触发——罕见、难复现、后果严重。

做法分三步：

  1. 写下不变量。比如「任意时刻账户总余额等于所有流水之和」「订单状态只能单向流转」「已确认的写在崩溃后必须还在」。
  2. 状态机建模。把合法的状态迁移画出来，非法迁移就是 bug。
  3. 故障注入。随机时点杀进程、注入延迟丢包、注入磁盘写失败，每次注入后自动校验所有不变量。

这一步的价值不是「更严谨」，而是把并发和崩溃 bug 从「靠运气发现的灵异事件」变成「可搜索、可复现、可回归」的工程问题。

事务、WAL 与存储引擎的系统性讨论，可以看 Martin Kleppmann 的 Designing Data-Intensive Applications 第 5 章和第 7 章；本文的分层框架也来自这条脉络。
