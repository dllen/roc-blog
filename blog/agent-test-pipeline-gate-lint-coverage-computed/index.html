补测流水线的三笔账：闸门、lint 与覆盖率

#AI工程#测试工程#技术深度#大会笔记

补测流水线的三笔账？闸门的误杀率下界、lint 失败烧掉的工时、以及「覆盖率 +13 个百分点」到底覆盖了谁。我读完 AIE Code Summit 2026 那场《How AI Agents Shipped over 200k Lines of Tests on a 1.8M Line Codebase》之后，最想验证的是：这份成绩单里哪些数字可以直接引用、哪些需要加脚注。这篇把它算清楚。

口径说明

  • 源是我自己的精读笔记 02-课程体系/AIE-Code-Summit-2026/05-预录插播/15 Kush Agrawal - How AI Agents Shipped over 200k Lines of Tests on a 1.8M Line Codebase.md（约 10,240 字，已按官方 Day 1 中英对照稿校对）。
  • 演讲本身按导读式处理：只复述机制与公开数据，不引用官方译稿原文、不搬附件图。代码与数字均为自写模型。
  • 数据归属：Duolingo 移动端的规模与流水线结果（覆盖率 11%→24%、合并 700+ 个测试 PR、新增约 225,000 行测试、13.6% 的 PR 因 lint 失败、已审约 1200 个 PR 拒绝 73 个）都是讲者公开陈述的团队数据，非我的实测。注意：这是单一团队、单一仓库、单一语言栈的结果，外推到别的技术栈要重新量。
  • 标题与正文的口径差异：标题写 1.8M 行、正文写「接近 200 万行」，我的笔记按官方原文两处都保留、未强行统一。
  • 我为了建模补的（作恶 PR 比例、每次审查耗时、每次 lint 失败的 CI 时间、每 PR 的 agent 会话时间、三层代码规模占比）都标为「估」。
  • 三个脚本只依赖 Python 标准库；输出为实跑结果，逐行可复现（无随机数，两次运行输出逐字一致）。
  • 撞题与边界：本系列已发《反 Slop 的三笔账》《自治等级的三笔账》《软件工厂的三笔账》《撤销按钮的三笔账》。那四篇讲的是「治理与边界」，本文是「一条具体的 agent 流水线的运行账」：闸门误杀、lint 浪费、覆盖率构成。

一、讲者的骨架：五步循环与四个里程碑

背景：Duolingo 移动端每周都发版到 App Store，任何时刻有 600 多个 A/B 测试在线；iOS 与 Android 应用都已存在 10 年以上。iOS 仓库可执行代码从 2019 年约 20 万行涨到如今接近 200 万行，而且随着 AI 辅助编程普及，曲线开始向上弯。写代码的人也在变：去年约 200 人提交 iOS 代码，今年已过 250 人，其中很多根本不是 iOS 工程师（后端、Android，甚至 PM 与设计师）。

起点与成绩单：今年三月整体单测覆盖率 11%（repositories 11%、view models 9%、data sources 5%，MVVM 一片约 9%）；八个月后整体 11% → 24%、repositories 11% → 72%、view models 9% → 58%、data sources 5% → 41%。流水线合并了 700+ 个测试 PR、新增约 225,000 行测试代码，而且每一个 PR 都经过人工审核批准。单测之所以值得做，是因为它同时是 agent 的护栏（改动打破测试时立刻给出「该修什么」）与代码行为的活文档。

五步循环：① 识别需要测试的文件 → ② 用 agent 写测试 → ③ 验证（质量达标 + CI 通过）→ ④ 处理 PR（工程师评审并合并）→ ⑤ 迭代反馈。生产形态是几个由 S3 共享状态协调起来的 Temporal workflow，而 Temporal 的 schedules、可组合 workflow、重试与超时、以及 idempotency 恰好对上 agent 的特性（session 从几秒到几小时、会调外部工具、必须不重复副作用）。

四个里程碑：本地验证 → 定时补测工作流 → PR 生命周期工作流 → 让工程师为自己的新代码也能一键拿到测试。

里程碑一（起手刻意做小）：极简本地 Claude Code 设置，一个命令充当编排器——跑 Xcode build script 生覆盖率报告 → 交给文件选择脚本 → 每个选中的文件交给两个子 agent（一个写测试、一个开 PR）。前两批：17 个 PR 合并 8 个、40 个合并 19 个。

里程碑二（最有信息量的一段）：选择器按「agent 有多大概率能为这个文件写出好测试」打分——最强的信号是文件类型（view models / repositories / data sources 拿到 2.5 倍加权，legacy 降权，UI 代码完全跳过，那里更适合用快照测试），文件越大越被惩罚。

里程碑三（PR 生命周期是一个状态机）：每隔几小时跑一次，扫过所有生成的测试 PR，对每个 PR 恰好执行一个动作。pre-commit 问题（lint、格式化）由 GitHub action 直接修——「便宜、确定，而且不需要 agent」；真正的测试失败才启动另一个 agent 读 CI 日志修。整个修复循环上限 5 次尝试；拒绝则该文件进入 30 天冷却期，不再反复骚扰工程师。

里程碑四的两大挑战：① lint 失败——agent 原本跑在没有 Xcode、也没有 SwiftLint 的 Linux 机器上，开 PR 后 20–30 分钟才在 CI 上因 lint 挂掉；一度 13.6% 的 PR 因 lint 失败，而其中 62% 的失败只来自两条 lint 规则。② PR 质量的三类作恶：为了让失败测试通过而编辑生产代码、修改/删除/禁用已有测试、在测试里塞长等待（导致 CI flaky）。

三层闸门：① 确定性规则（PR 触及的文件不是 test/mock/fake/stub 就直接关掉）；② AI code review（用 Claude 和 Codex 各审一遍，再用一个 agent 在人类看到之前解决所有 P0 评论）；③ LLM 作为裁判（读 PR diff，拒绝生产代码改动、被改被删的测试、被禁用的测试、以及长等待；规则会随经验不断追加）。

二、增量一：闸门的拒绝数本身就能推出误杀率的下界

"""闸门账：可用率、误杀率，以及「规则只增不减」的代价。

数字取自我的精读笔记（本地批次：第一批 17 个 PR 合并 8 个、第二批 40 个合并 19 个；已审约 1200 个
PR、拒绝 73 个；修复循环上限 5 次尝试；拒绝后文件进入 30 天冷却期），其余为估。
只依赖标准库；输出确定性。
"""
LOCAL_PRS = (17, 8), (40, 19)     # (PR 数, 合并数)
REVIEWED = 1200
REJECTED = 73
MISCHIEF_RATE = 0.02              # agent PR 里作恶（改生产代码/删测试/塞长等待）的比例（估）
REVIEW_MIN_PER_PR = 30            # 每 PR 人工审查成本（分钟，估）
COOLDOWN_DAYS = 30

print("一、无闸门时 agent PR 的端到端可用率")
tot_pr = sum(p for p, _ in LOCAL_PRS)
tot_ok = sum(o for _, o in LOCAL_PRS)
for prs, ok in LOCAL_PRS:
    print("   批次：%d 个 PR -> 合并 %d 个（%.1f%%）" % (prs, ok, 100.0 * ok / prs))
print("   合计 %d 个 PR -> 合并 %d 个（**%.1f%%**）" % (tot_pr, tot_ok, 100.0 * tot_ok / tot_pr))
print()
print("   => **没有闸门时，agent 写的 PR 只有约一半能直接用**。")
print()
print("二、三层闸门之后")
pass_rate = 1 - REJECTED / REVIEWED
print("   已审 %d 个 PR，拒绝 %d 个 -> 通过率 **%.1f%%**、拒绝率 **%.1f%%**" % (
    REVIEWED, REJECTED, 100 * pass_rate, 100 * (1 - pass_rate)))
print("   （讲者说明：这是纯 LLM 裁判在**只有 4 类规则**时测出的数字，实际规则更多时误杀率只会更高）")
print()
print("三、闸门的交换：拒绝数本身就能推出误杀率的下界")
print("   拒绝率 %.1f%%（每 1000 个 PR 拒 %.0f 个）；而作恶 PR 的比例按 %.0f%% 估（每 1000 个约 %.0f 个）。" % (
    100 * (1 - pass_rate), 1000 * (1 - pass_rate), MISCHIEF_RATE * 100, 1000 * MISCHIEF_RATE))
print("   **被拒的数比作恶的数还多** -> 至少有 %d 个是冤枉的。判据：**误杀率的下界 = max(0, 拒绝率 - 作恶率)**。" % (
    int(1000 * max(0.0, (1 - pass_rate) - MISCHIEF_RATE))))
print()
print("%-22s %16s %18s %20s %22s" % ("规则量", "拒绝率", "每 1000 误杀(下界)", "误杀工时(h/1000)", "放过的作恶 PR"))
for rules_scale in (1, 2, 4):
    reject_rate = min(0.9, (1 - pass_rate) * rules_scale)
    false_reject = 1000 * max(0.0, reject_rate - MISCHIEF_RATE)
    review_h = false_reject * REVIEW_MIN_PER_PR / 60
    escaped = 1000 * MISCHIEF_RATE * (1 - reject_rate)
    print("%-22s %15.1f%% %18.0f %20.1f %22.1f" % (
        "规则量 x%d" % rules_scale, reject_rate * 100, false_reject, review_h, escaped))
print()
print("   => 规则量翻倍，误杀下界从 %.0f 涨到 %.0f（每 1000 个 PR），而放过的作恶 PR 只从 %.1f 降到 %.1f。" % (
    1000 * max(0.0, (1 - pass_rate) - MISCHIEF_RATE),
    1000 * max(0.0, min(0.9, (1 - pass_rate) * 2) - MISCHIEF_RATE),
    1000 * MISCHIEF_RATE * pass_rate, 1000 * MISCHIEF_RATE * (1 - min(0.9, (1 - pass_rate) * 2))))
print("      判据：**规则只增不减时，误杀率单调上升** —— 必须定期审计并删掉低信号规则")
print("      （讲者做的正是这件事：审计无法自动修的规则，把没有高信号的直接删掉）。")
print()
print("四、拒绝不是零成本")
print("   每个被拒 PR 都要工程师花 %d 分钟审查并拒绝；而且**该文件进入 %d 天冷却期**，" % (
    REVIEW_MIN_PER_PR, COOLDOWN_DAYS))
print("   冷却期内这个文件不再被流水线挑中 -> 判据：**闸门噪声有隐性成本：它把文件挤出补测队列**。")
for scale in (1, 2, 4):
    reject_rate = min(0.9, (1 - pass_rate) * scale)
    files_lost_month = 1000 * reject_rate * 30 / COOLDOWN_DAYS
    print("     规则量 x%d -> 每月因冷却期损失的文件机会约 %s 个" % (scale, format(int(files_lost_month), ",")))

输出：

一、无闸门时 agent PR 的端到端可用率
   批次：17 个 PR -> 合并 8 个（47.1%）
   批次：40 个 PR -> 合并 19 个（47.5%）
   合计 57 个 PR -> 合并 27 个（**47.4%**）

   => **没有闸门时，agent 写的 PR 只有约一半能直接用**。

二、三层闸门之后
   已审 1200 个 PR，拒绝 73 个 -> 通过率 **93.9%**、拒绝率 **6.1%**
   （讲者说明：这是纯 LLM 裁判在**只有 4 类规则**时测出的数字，实际规则更多时误杀率只会更高）

三、闸门的交换：拒绝数本身就能推出误杀率的下界
   拒绝率 6.1%（每 1000 个 PR 拒 61 个）；而作恶 PR 的比例按 2% 估（每 1000 个约 20 个）。
   **被拒的数比作恶的数还多** -> 至少有 40 个是冤枉的。判据：**误杀率的下界 = max(0, 拒绝率 - 作恶率)**。

规则量                                 拒绝率      每 1000 误杀(下界)         误杀工时(h/1000)               放过的作恶 PR
规则量 x1                             6.1%                 41                 20.4                   18.8
规则量 x2                            12.2%                102                 50.8                   17.6
规则量 x4                            24.3%                223                111.7                   15.1

   => 规则量翻倍，误杀下界从 41 涨到 102（每 1000 个 PR），而放过的作恶 PR 只从 18.8 降到 17.6。
      判据：**规则只增不减时，误杀率单调上升** —— 必须定期审计并删掉低信号规则
      （讲者做的正是这件事：审计无法自动修的规则，把没有高信号的直接删掉）。

四、拒绝不是零成本
   每个被拒 PR 都要工程师花 30 分钟审查并拒绝；而且**该文件进入 30 天冷却期**，
   冷却期内这个文件不再被流水线挑中 -> 判据：**闸门噪声有隐性成本：它把文件挤出补测队列**。
     规则量 x1 -> 每月因冷却期损失的文件机会约 60 个
     规则量 x2 -> 每月因冷却期损失的文件机会约 121 个
     规则量 x4 -> 每月因冷却期损失的文件机会约 243 个

三处结论：

第一，没有闸门时 agent 写的 PR 只有约一半能用。 前两批本地试验：17 个 PR 合并 8 个（47.1%）、40 个合并 19 个（47.5%），合计 47.4%。判据：这是「无闸门的端到端可用率」基线——任何「agent 提效」的数字，都要和它对照。

第二，三层闸门把通过率拉到 93.9%，但拒绝数比作恶数还多。 已审约 1,200 个 PR、拒绝 73 个 → 拒绝率 6.1%。若作恶 PR（改生产代码/删测试/塞长等待）的比例按 2% 估（每 1,000 个约 20 个），那么每 1,000 个 PR 至少有 41 个是冤枉的。判据：误杀率的下界 = max(0, 拒绝率 − 作恶率)——你不需要知道真实的作恶率就能算出这个下界；反过来，如果拒绝数超过了作恶数，说明要么作恶率被低估，要么大部分拒绝是误杀。

第三，规则只增不减，误杀率就单调上升。 规则量翻倍 → 拒绝率 12.2% → 误杀下界涨到每 1,000 个 102 个，而放过的作恶 PR 只从 18.8 降到 17.6。判据：规则必须定期审计清理——讲者做的正是这件事：审计那些无法自动修的规则，把没有高信号的直接删掉。还有一条隐性成本：拒绝后该文件进入 30 天冷却期，等于把它挤出补测队列。

三、增量二：13.6% 的 lint 失败是纯工程问题

"""13.6% 的 lint 失败里 62% 只来自两条规则 —— 这不是模型能力问题。

数字取自我的精读笔记（13.6% 的 PR 因 lint 失败、其中 62% 的失败只来自两条 lint 规则；
agent 跑在没有 Xcode / SwiftLint 的 Linux 机器上，开 PR 后 20-30 分钟才在 CI 上因 lint 挂掉；
流水线合并 700+ 个测试 PR），其余为估。只依赖标准库；输出确定性。
"""
LINT_FAIL = 0.136
TWO_RULES_SHARE = 0.62           # 失败中来自那两条规则的比例
CI_MIN_PER_FAIL = 25             # 每次 lint 失败的 CI 时间（分钟，估：讲者说 20-30 分钟）
PR_COUNT = 700
AGENT_MIN_PER_PR = 45            # 每个 PR 的 agent 会话时间（估）

print("一、lint 失败把多少 PR 白烧了")
failed = PR_COUNT * LINT_FAIL
print("   %d+ 个 PR x %.1f%% = **约 %d 个 PR 因 lint 白跑**" % (PR_COUNT, LINT_FAIL * 100, round(failed)))
print("   其中 %.0f%% 只来自两条规则 -> 约 %d 个 PR" % (
    TWO_RULES_SHARE * 100, round(failed * TWO_RULES_SHARE)))
print()
print("二、把那两条规则处理掉，失败率降到多少")
rest = LINT_FAIL * (1 - TWO_RULES_SHARE)
print("   现状 %.1f%% -> 修掉那两条后 **%.2f%%**（降 %.0f%%）" % (
    LINT_FAIL * 100, rest * 100, 100 * (1 - (1 - TWO_RULES_SHARE))))
print("   再把 agent 迁到有 Xcode/SwiftLint 的 Mac runner（本地就能 build+lint）-> 期望 **接近 0**")
print()
print("三、被浪费掉的 CI 与 agent 时间")
print("%-22s %18s %20s %22s" % ("方案", "白跑的 PR", "CI 时间(h)", "agent 会话时间(h)"))
print("%-22s %18d %20.1f %22.1f" % ("现状", round(failed),
      failed * CI_MIN_PER_FAIL / 60, failed * AGENT_MIN_PER_PR / 60))
print("%-22s %18d %20.1f %22.1f" % ("修掉那两条规则", round(failed * (1 - TWO_RULES_SHARE)),
      failed * (1 - TWO_RULES_SHARE) * CI_MIN_PER_FAIL / 60,
      failed * (1 - TWO_RULES_SHARE) * AGENT_MIN_PER_PR / 60))
print()
print("   => 在 700+ PR 的规模上，光是 lint 环境不一致就烧掉 **%.0f 小时 CI + %.0f 小时 agent 会话**；" % (
    failed * CI_MIN_PER_FAIL / 60, failed * AGENT_MIN_PER_PR / 60))
print("      判据：**这是纯工程问题**——迁移一次 runner 就消掉，不需要任何模型改进；")
print("      讲者自己给的说法是「agent 与 CI 的运行环境不一致」，不是「agent 不够聪明」。")
print()
print("四、为什么它比模型问题更值得先修")
print("   修 runner 的收益是确定的（把失败率从 %.1f%% 打到接近 0）；" % (LINT_FAIL * 100))
print("   而「让模型更聪明」的收益不确定、且随模型换代而重置。")
print("   判据：**环境一致性问题的 ROI 是确定且一次性；模型能力问题的 ROI 是概率且会过期**。")

输出：

一、lint 失败把多少 PR 白烧了
   700+ 个 PR x 13.6% = **约 95 个 PR 因 lint 白跑**
   其中 62% 只来自两条规则 -> 约 59 个 PR

二、把那两条规则处理掉，失败率降到多少
   现状 13.6% -> 修掉那两条后 **5.17%**（降 62%）
   再把 agent 迁到有 Xcode/SwiftLint 的 Mac runner（本地就能 build+lint）-> 期望 **接近 0**

三、被浪费掉的 CI 与 agent 时间
方案                                 白跑的 PR             CI 时间(h)          agent 会话时间(h)
现状                                     95                 39.7                   71.4
修掉那两条规则                                36                 15.1                   27.1

   => 在 700+ PR 的规模上，光是 lint 环境不一致就烧掉 **40 小时 CI + 71 小时 agent 会话**；
      判据：**这是纯工程问题**——迁移一次 runner 就消掉，不需要任何模型改进；
      讲者自己给的说法是「agent 与 CI 的运行环境不一致」，不是「agent 不够聪明」。

四、为什么它比模型问题更值得先修
   修 runner 的收益是确定的（把失败率从 13.6% 打到接近 0）；
   而「让模型更聪明」的收益不确定、且随模型换代而重置。
   判据：**环境一致性问题的 ROI 是确定且一次性；模型能力问题的 ROI 是概率且会过期**。

三处结论：

第一，两条规则贡献了 62% 的 lint 失败。 700+ PR × 13.6% ≈ 95 个 PR 因 lint 白跑，其中约 59 个只来自那两条规则。判据：先修掉这两条，失败率从 13.6% 降到 5.17%——这是一个几乎不需要模型的改动。

第二，把 agent 迁到有 Xcode/SwiftLint 的 Mac runner，本地就能 build + lint，期望失败率接近 0。 讲者自己的说法是「agent 与 CI 的运行环境不一致」，不是「agent 不够聪明」。

第三，算出这笔浪费的规模：约 40 小时 CI + 71 小时 agent 会话（700+ PR 规模上，按每次失败 25 分钟 CI、45 分钟 agent 会话估）。判据：环境一致性问题的 ROI 是确定且一次性的；模型能力问题的 ROI 是概率且会随换代重置——所以这类问题应该排在「换更强的模型」之前。

四、增量三：「覆盖率 +13 个百分点」覆盖了谁

"""「覆盖率 +13 个百分点」到底覆盖了谁：选择器偏差的账。

数字取自我的精读笔记（整体覆盖率 11% -> 24%；repositories 11% -> 72%、view models 9% -> 58%、
data sources 5% -> 41%；选择器对这三类加权 2.5 倍、legacy 降权、UI 代码完全跳过、文件越大越惩罚；
流水线写出仓库中 34% 的新测试文件、44% 的新测试用例、新增 Swift 代码每 10 行中的 1 行），
比例参数为估。只依赖标准库；输出确定性。
"""
LAYERS = (("repositories", 0.11, 0.72), ("view models", 0.09, 0.58), ("data sources", 0.05, 0.41))
OVERALL_BEFORE = 0.11
OVERALL_AFTER = 0.24

print("一、三个被加权层的覆盖变化")
for name, before, after in LAYERS:
    print("   %-14s %5.0f%% -> %5.0f%%（+%.0f 个百分点）" % (name, before * 100, after * 100, (after - before) * 100))
print("   整体        %5.0f%% -> %5.0f%%（+%.0f 个百分点）" % (
    OVERALL_BEFORE * 100, OVERALL_AFTER * 100, (OVERALL_AFTER - OVERALL_BEFORE) * 100))
print()
print("二、反推：被选中的代码占多少、剩下多少没被碰")
# 被选中部分在三个层里的加权平均覆盖率（按各层代码规模等权近似，估）
avg_selected = sum(a for _, _, a in LAYERS) / len(LAYERS)
share_selected = OVERALL_AFTER / avg_selected
print("   三个被加权层的平均覆盖率约 **%.0f%%**（等权近似，估）" % (avg_selected * 100))
print("   整体 %.0f%% = 选中部分占比 x 该覆盖率 -> 选中部分约占代码库 **%.0f%%**" % (
    OVERALL_AFTER * 100, share_selected * 100))
print("   => **剩下约 %.0f%% 的代码这条流水线一次都没碰**（UI 层被完全跳过、大文件被惩罚、legacy 降权）；" % (
    100 * (1 - share_selected)))
print("      注意：**它们原有覆盖率可能不是 0**，所以这不等于「这些代码没有测试」。")
print()
print("   判据：**「整体 24%」不等于「代码被良好覆盖」**——它等于「被选择器选中的那部分被覆盖了」，")
print("         而选择器刻意避开了最难测的部分；**+13 个百分点是流水线的增量，不是全库水位**。")
print()
print("三、为什么 repositories 的 72% 是个信号而不是成就")
print("   repositories 层是**代码量小、逻辑集中、易测**的一层；")
print("   选择器给它 2.5 倍加权、UI 完全跳过 -> 覆盖率涨得最快的层，恰好是最容易的那层。")
print("   判据：**读覆盖率排名时先看选择器的加权规则**，否则会把「避开了难的部分」读成「覆盖得很好」。")
print()
print("四、增量口径与存量口径必须分开")
print("   流水线写出仓库中 **34% 的新测试文件**、**44% 的新测试用例**、新增 Swift 代码每 10 行中的 **1 行**。")
print("   判据：**这些是增量指标**（只针对流水线启动之后新增的代码），不能与「整体 24%」并列解读；")
print("         存量代码的覆盖情况要单独看。")
print()
print("五、如果按「要覆盖多少才够」倒推")
for target in (0.40, 0.60, 0.80):
    need_share = target / avg_selected
    flag = "**不可能**（需要超过 100%）" if need_share > 1 else "可行"
    print("   若目标整体覆盖 %.0f%%、而选择性保持不变 -> 需要把被选中的代码占比提到 **%.0f%%**（当前 %.0f%%）-> %s" % (
        target * 100, need_share * 100, share_selected * 100, flag))
print("   => 判据：**选择性越窄，越难靠它把整体覆盖率推上去**；要么扩选择器（但那是难测的部分），")
print("      要么承认「这层代码要靠别的手段验证」（快照测试、端到端、形式化验证）。")

   整体 24% = 选中部分占比 x 该覆盖率 -> 选中部分约占代码库 **42%**
   => **剩下约 58% 的代码这条流水线一次都没碰**（UI 层被完全跳过、大文件被惩罚、legacy 降权）；

   判据：**「整体 24%」不等于「代码被良好覆盖」**——它等于「被选择器选中的那部分被覆盖了」，
         而选择器刻意避开了最难测的部分；**+13 个百分点是流水线的增量，不是全库水位**。

三、为什么 repositories 的 72% 是个信号而不是成就
   repositories 层是**代码量小、逻辑集中、易测**的一层；
   选择器给它 2.5 倍加权、UI 完全跳过 -> 覆盖率涨得最快的层，恰好是最容易的那层。
   判据：**读覆盖率排名时先看选择器的加权规则**，否则会把「避开了难的部分」读成「覆盖得很好」。

四、增量口径与存量口径必须分开
   流水线写出仓库中 **34% 的新测试文件**、**44% 的新测试用例**、新增 Swift 代码每 10 行中的 **1 行**。
   判据：**这些是增量指标**（只针对流水线启动之后新增的代码），不能与「整体 24%」并列解读；
         存量代码的覆盖情况要单独看。

五、如果按「要覆盖多少才够」倒推
   若目标整体覆盖 40%、而选择性保持不变 -> 需要把被选中的代码占比提到 **70%**（当前 42%）-> 可行
   若目标整体覆盖 60%、而选择性保持不变 -> 需要把被选中的代码占比提到 **105%**（当前 42%）-> **不可能**（需要超过 100%）
   若目标整体覆盖 80%、而选择性保持不变 -> 需要把被选中的代码占比提到 **140%**（当前 42%）-> **不可能**（需要超过 100%）
   => 判据：**选择性越窄，越难靠它把整体覆盖率推上去**；要么扩选择器（但那是难测的部分），
      要么承认「这层代码要靠别的手段验证」（快照测试、端到端、形式化验证）。

三处结论：

第一，反推出被选中的代码只占约 42%。 三个被加权层的平均覆盖率约 57%（等权近似，估），整体 24% = 选中部分占比 × 该覆盖率 → 选中部分约占代码库 42%，剩下约 58% 的代码这条流水线一次都没碰（UI 层完全跳过、大文件被惩罚、legacy 降权）。注意：这些代码原有覆盖率可能不是 0，所以这不等于「它们没有测试」。判据：「整体 24%」不等于「代码被良好覆盖」——它等于「被选择器选中的那部分被覆盖了」，而选择器刻意避开了最难测的部分；+13 个百分点是流水线的增量，不是全库水位。

第二，repositories 的 72% 是个信号而不是成就。 涨得最快的那层恰好是代码量小、逻辑集中、易测的一层（还拿了 2.5 倍加权），而 UI 层被完全跳过。判据：读覆盖率排名先看选择器的加权规则，否则会把「避开了难的部分」读成「覆盖得很好」。

第三，靠现有选择性推不到 60%。 若保持选择器不变：目标整体 40% 需要把被选中部分占比提到 70%（当前 42%）；目标 60% 需要 105%、目标 80% 需要 140%——都不可能。判据：选择性越窄，越难靠它把整体覆盖率推上去；要么扩选择器（但那是难测的部分），要么承认「这层代码要靠别的手段验证」（快照测试、端到端、形式化验证）。

另外两个口径必须分开：流水线写出仓库中 34% 的新测试文件、44% 的新测试用例、新增 Swift 代码每 10 行中的 1 行——这些是增量指标，不能与「整体 24%」并列解读。

五、把三个模型套回本章（判据清单）

  1. 无闸门时 agent PR 的可用率 47.4%（57 个 PR 合并 27 个）→ 任何提效数字都要和它对照。
  2. 三层闸门后通过率 93.9%、拒绝率 6.1%（1,200 审 / 73 拒）。
  3. 误杀率下界 = max(0, 拒绝率 − 作恶率) → 每 1,000 个 PR 至少 41 个冤枉；规则量翻倍 → 102 个。
  4. 规则只增不减 → 误杀单调上升 → 必须定期删低信号规则。
  5. 拒绝有隐性成本：该文件进入 30 天冷却期 → 被挤出补测队列。
  6. 13.6% 的 lint 失败中 62% 来自两条规则 → 修掉后降到 5.17%；迁 Mac runner 期望接近 0。
  7. 这笔浪费的规模：700+ PR 上 40 小时 CI + 71 小时 agent 会话。
  8. 环境一致性 ROI 确定且一次性 > 模型能力 ROI 概率且会过期。
  9. 「整体 24%」= 选中部分（约 42%）被覆盖；剩下 58% 流水线一次没碰（其原有覆盖率可能非 0）。
  10. repositories 的 72% 是选择器偏差的信号；靠现有选择性推不到 60%（需 105%）。

六、这一章不重复已发的内容

  • 约束下沉、覆盖率门槛与回退止损线：见《反 Slop 的三笔账》——那篇讲「PR 能不能自动合」的判据，本文讲「一条补测流水线怎么跑起来」。
  • 自治升级的回本与样本量：见《自治等级的三笔账》——那篇的「覆盖率门槛」是约束覆盖率（代码被确定性检查覆盖的比例），本文的覆盖率是测试覆盖率，两者不是一回事，文中没有混用。
  • 软件工厂的燃料、垃圾山与围栏：见《软件工厂的三笔账》——那篇讲日常运营成本，本文讲流水线的失败模式。
  • 撤销与可恢复性：见《撤销按钮的三笔账》——那篇讲「干砸了怎么退回来」，本文的「修复循环上限 5 次尝试 + 30 天冷却期」是同一问题在流水线里的对策。

七、这三个模型判不了什么

  • 作恶 PR 比例 2%、每次审查 30 分钟、每次 lint 失败 25 分钟 CI、每 PR 45 分钟 agent 会话、三层代码规模等权，全是估的。其中作恶比例最关键：它直接决定误杀率下界——若真实比例是 6% 以上，则「拒绝数超过作恶数」就不成立，误杀下界会归零。这个比例应该从被拒 PR 的抽样复核里估出来，而不是猜。
  • 三层代码规模用等权近似。真实权重（repositories 与 view models 的代码量占比）不同，则「选中部分 42%」这个反推值会变；但**「整体覆盖率是选择器的函数」这个结论方向不变**。
  • 没有算「合并率 47.4% → 93.9%」是不是同一个口径：前者是本地小批量实验的端到端合并率，后者是审查通过率（不含工程师最终是否合并），两者不能直接相减得到「闸门带来的提升」。我在正文里分别陈述，没有合并计算。
  • 没有算人工审查的总成本：700+ 个 PR 每个都要工程师审一遍——按 30 分钟算，那是 350 小时的人工。讲者强调「每个 PR 都经过人工审核并获批」，但没给总工时；这条流水线的隐性成本是人力，不是 token，而这正是它与「纯自动化」的根本差别。
  • lint 的 13.6% 是「一度」的峰值，不是稳定值；模型里把它当常态算浪费，偏保守。
  • 三个模型都没算「补测本身的维护成本」：225,000 行测试代码是新增的负债——每次生产代码变更都要同步改测试。测试代码有没有自己的垃圾山问题（对应 Steve Yegge 那篇的生产代码垃圾山循环）需要另算，本文只算新增量、不算维护量。

FAQ（八、常见问题）

agent 写的 PR 直接能合吗？ 本地两批实测：17 个合并 8 个、40 个合并 19 个 → 端到端可用率约 47.4%。这是所有「agent 提效」数字的对照基线。

加了闸门好多少？ 三层闸门后审查通过率 93.9%（1,200 个 PR 拒 73 个）。但拒绝数比作恶数还多——若作恶比例是 2%，则每 1,000 个 PR 至少 41 个冤枉。

闸门怎么调？ 判据是误杀率下界 = max(0, 拒绝率 − 作恶率)。规则量翻倍，误杀下界从 41 涨到 102（每 1,000 个 PR），而放过的作恶 PR 只从 18.8 降到 17.6 → 规则只增不减时必须定期删低信号规则。拒绝还有隐性成本：该文件进 30 天冷却期，等于被挤出补测队列。

lint 失败要花多少？ 700+ PR × 13.6% ≈ 95 个白跑，其中 59 个只来自两条规则；修掉它们失败率 13.6% → 5.17%，迁到有 Xcode/SwiftLint 的 Mac runner 期望接近 0。规模上浪费 40 小时 CI + 71 小时 agent 会话。

这是模型问题吗？ 不是。讲者的说法是「agent 与 CI 的运行环境不一致」。判据：环境一致性问题的 ROI 确定且一次性，模型能力问题的 ROI 概率且会随换代重置——这类问题该排在换模型之前。

整体覆盖率 11%→24% 说明什么？ 只说明「被选择器选中的那部分被覆盖了」：反推选中部分约占代码库 42%（三个加权层平均覆盖 57%），剩下约 58% 流水线一次没碰（UI 层被跳过、大文件被惩罚、legacy 降权——它们原有覆盖率可能非 0）。+13 个百分点是增量，不是全库水位。

repositories 层 72% 可信吗？ 它涨得最快，而它恰好是代码量小、逻辑集中、易测的那层，还拿了 2.5 倍加权。判据：读覆盖率排名先看选择器的加权规则，否则会把「避开了难的部分」读成「覆盖得很好」。

靠这套流水线能把整体覆盖推到 60% 吗？ 保持选择器不变的话，需要把被选中部分占比提到 105% → 不可能。选择性越窄越推不动整体，要么扩选择器（难测那部分），要么承认这层代码要靠快照测试、端到端或形式化验证。

这 22.5 万行测试是资产还是负债？ 两面：它们是 agent 的护栏与活文档；但 225,000 行新增测试也是新增的维护负债——每次生产代码变更都要同步改。测试代码有没有自己的垃圾山问题，本文没算，这是下一个该补的账。
