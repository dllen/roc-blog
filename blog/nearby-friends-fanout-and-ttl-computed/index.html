附近的朋友怎么算：扇出量、TTL 与订阅状态

#系统设计#架构设计#读书笔记#实时位置

附近的朋友怎么算？三个数：扇出多少条消息、位置记录活多久、订阅关系占多少状态。讲义把架构与扩展手段讲得很细（WebSocket、Redis 位置缓存、pub/sub 通道、ZooKeeper 服务发现、一致性哈希、Erlang 替代方案），但这三个数是散在段落里的。这篇把它们算出来。

这篇不复述译文，也不搬运中文译本的任何段落。它复述这一章的骨架（两类服务、七步位置更新流程、深挖里的扩展性与替代方案），然后补三个自写模型：扇出量与 Redis 集群规模、TTL 与「离线判定」不能共用一个字段、40 亿条订阅关系对分片键的影响。

口径说明

  • 源笔记是 Alex Xu《System Design Interview — An Insider’s Guide》第 17 章的社区中译。上游两仓库的 LICENSE 在 main/master 分支经 raw 通道取均返回 404，上游许可未能确认；原书是商业出版物。故本篇为导读式：只复述章节骨架与需求数字，不引用译文原文或原书段落，不使用译本配图，正文主体是自写模型与判断。
  • 三个脚本均为自写增量，只依赖 Python 标准库；输出为实跑结果，逐行可复现（三段计算都不含随机数）。
  • 与第 16 章《邻近服务怎么算》是两章：那一章找的是静止的商家，这一章找的是不断移动的朋友，核心机制（动态位置、pub/sub 扇出、TTL、WebSocket 订阅）完全不同，只有「地理网格 + 距离阈值」这一处共通，见《邻近服务怎么算》。

一、本章骨架：两类服务、七步流程、三个状态量

范围（讲义用面试问答敲定）：多近算「附近」？5 英里，可配置。按直线距离算（不绕河）。10 亿用户，其中 10% 用这个功能。需要存位置历史（对机器学习有价值）。假设不活跃的朋友 10 分钟后从这个功能中消失。为简化不考虑 GDPR。

功能需求：手机上看到附近的朋友，每个朋友带距离和时间戳（标明位置更新时间）；列表每隔几秒更新一次。

非功能需求：低延迟（位置更新不能延迟太多）；可靠性（偶尔丢几个数据点可接受，系统整体可用）；最终一致性（位置数据不需要强一致，副本间几秒延迟可接受）。

粗略估算：附近朋友 = 5 英里半径内；位置刷新间隔 30 秒（理由：人类步行很慢，不必太频繁）；平均每天 1 亿用户用该功能，其中 10% 同时在线 = 1000 万；平均每人 400 个朋友（都用该功能）；每页展示 20 个。位置更新 QPS = 1000 万 / 30 ≈ 334k。

高层设计（七个部件）：负载均衡器、REST API 服务器（管理好友等辅助任务）、WebSocket 服务器（有状态，转发位置更新，并在客户端初始化时「播种」附近朋友的位置）、Redis 位置缓存（存每个活跃用户的最新位置，每条记录设 TTL，过期即视为用户不活跃并删除）、用户数据库（用户与好友关系）、位置历史数据库（Cassandra 适合写密集）、Redis pub/sub（轻量消息总线，每个用户一个通道）。

周期性位置更新的七步：客户端经负载均衡器把位置更新发到自己的 WebSocket 服务器 → 服务器写入位置历史库 → 更新 Redis 位置缓存（同时在内存里留一份用于距离计算）→ 通过 Redis pub/sub 发布到该用户的通道 → pub/sub 广播给订阅了该通道的服务器（即负责其朋友的那几台）→ 订阅到的服务器计算该把更新发给谁 → 发出。

深挖里的几个关键点：

  • 扇出量：平均每用户 400 好友、10% 在线 ⇒ 平均每次位置更新转发 40 条。
  • WebSocket 服务器下线要「排水中」：先在负载均衡器里标 draining、不再接新连接，再移出服务器池。
  • Redis 通道可以预分配：讲义指出「已初始化但未使用的通道不消耗内存」，所以可以为所有使用该功能的用户预建通道，免得上线时临时新建再通知活跃服务器。
  • 扩展性算账：维护所有通道约需 200 GB 内存（2 台 100 GB Redis）；但每秒要推送约 1400 万条位置更新，按单台每秒 10 万次推送算，至少需要 140 台 → 需要服务发现（ZooKeeper/etcd）记录哪些服务器活着，WebSocket 服务器缓存哈希环；扩缩容按历史流量做每日任务，或超配扛尖峰。
  • 扩容的坑：通道搬来搬去会引发大量重新订阅；操作期间客户端可能漏掉位置更新（本场景可接受，但应挑流量最低点做）；用一致性哈希最小化搬移量。
  • 大户：好友数可以设上限（Facebook 是 5000），这类用户的 WS 服务器负载更高。
  • 附近的陌生人：按 geohash 定义一组通道池，同一 geohash 内的人订阅对应通道即可收到随机用户的位置；相邻 geohash 要多订阅几个。
  • 替代方案：Erlang——用几百万个轻量进程同时处理 WebSocket 连接与 pub/sub 通道；难点是招人。

二、增量一：扇出量，以及「状态」与「吞吐」是两个扩展维度

讲义给了两个数：通道状态约 200 GB，Redis 至少 140 台。先把扇出算清楚，再看这两个数怎么凑在一起：

"""扇出账：位置更新 QPS x 好友扇出，以及 Redis 集群要多少台。

用讲义给的量：1000 万同时在线、每用户 400 好友、10% 好友在线、30 秒上报一次、
单台 Redis 每秒 10 万次推送、通道总内存 200 GB。
只依赖标准库；输出确定性。
"""
ONLINE = 10_000_000
FRIENDS = 400
FRIEND_ONLINE_RATE = 0.10
REPORT_INTERVAL = 30
PUSH_PER_SERVER = 100_000
CHANNEL_MEM_GB = 200
SERVER_MEM_GB = 100

update_qps = ONLINE / REPORT_INTERVAL
fanout = FRIENDS * FRIEND_ONLINE_RATE
delivery_qps = update_qps * fanout
servers = delivery_qps / PUSH_PER_SERVER

print("位置更新：%d 同时在线 / %d 秒 = %.0f QPS" % (ONLINE, REPORT_INTERVAL, update_qps))
print("每次更新的扇出：%d 好友 x %.0f%% 在线 = %.0f 条" % (FRIENDS, FRIEND_ONLINE_RATE * 100, fanout))
print("=> 位置消息投递：%.0f x %.0f = %.2f 百万条/秒（讲义写「约 1400 万」，一致）"
      % (update_qps, fanout, delivery_qps / 1e6))
print()
print("Redis 集群规模：%.2f 百万 / %d 每台 = %d 台" % (delivery_qps / 1e6, PUSH_PER_SERVER, int(servers)))
print()
print("但这里有一处容易混淆的地方——两个扩展维度不是一回事：")
print("  通道状态内存：讲义说所有通道约 %d GB，2 台 %d GB 的 Redis 就装得下" % (CHANNEL_MEM_GB, SERVER_MEM_GB))
print("  推送吞吐    ：需要 %d 台（每台 %d 次/秒）" % (int(servers), PUSH_PER_SERVER))
print("  若真按 %d 台 x %d GB 算，总内存 %.0f TB，而通道只占 %d GB（占 %.2f%%）"
      % (int(servers), SERVER_MEM_GB, servers * SERVER_MEM_GB / 1e3, CHANNEL_MEM_GB,
         100.0 * CHANNEL_MEM_GB / (servers * SERVER_MEM_GB)))
print("  => 通道状态不是瓶颈，**每台的推送能力（CPU/网卡）才是**；")
print("     所以「为所有用户预分配通道」这条优化的收益有限（省的是本来就便宜的那部分内存），")
print("     而集群规模要按吞吐算、按流量低点做日常扩缩容（讲义也是这么说的）。")
print()
print("位置缓存本身的内存（另一笔账）：")
REC_BYTES = 64            # user_id + lat/long + ts + 结构开销（估）
print("  %d 在线用户 x %d B = %.1f GB —— 比通道状态的 %d GB 小 %.0f 倍"
      % (ONLINE, REC_BYTES, ONLINE * REC_BYTES / 1e9, CHANNEL_MEM_GB,
         CHANNEL_MEM_GB / (ONLINE * REC_BYTES / 1e9)))

输出：

位置更新：10000000 同时在线 / 30 秒 = 333333 QPS
每次更新的扇出：400 好友 x 10% 在线 = 40 条
=> 位置消息投递：333333 x 40 = 13.33 百万条/秒（讲义写「约 1400 万」，一致）

Redis 集群规模：13.33 百万 / 100000 每台 = 133 台

但这里有一处容易混淆的地方——两个扩展维度不是一回事：
  通道状态内存：讲义说所有通道约 200 GB，2 台 100 GB 的 Redis 就装得下
  推送吞吐    ：需要 133 台（每台 100000 次/秒）
  若真按 133 台 x 100 GB 算，总内存 13 TB，而通道只占 200 GB（占 1.50%）
  => 通道状态不是瓶颈，**每台的推送能力（CPU/网卡）才是**；
     所以「为所有用户预分配通道」这条优化的收益有限（省的是本来就便宜的那部分内存），
     而集群规模要按吞吐算、按流量低点做日常扩缩容（讲义也是这么说的）。

位置缓存本身的内存（另一笔账）：
  10000000 在线用户 x 64 B = 0.6 GB —— 比通道状态的 200 GB 小 312 倍

三处结论：

第一，扇出量与讲义的「1400 万」互相印证。 位置更新 333k QPS × 每次扇出 40 条 = 1330 万条/秒——讲义深挖那节的「约 1400 万条」正是这个乘积，说明讲义自己的两个数字是自洽的。按单台 10 万次推送算，需要 133 台 Redis。

第二，也是这一节最值得停一下的地方：「通道占多少内存」和「每秒要推多少条」是两个不同的扩展维度，不能混。 通道状态 200 GB，2 台 100 GB 的机器就装得下；但 133 台 × 100 GB = 13 TB，通道只占其中的 1.5%。也就是说：这套设计的瓶颈是每台的推送吞吐（CPU 与网卡），不是内存。这个区分有两个直接后果：

  • 讲义那条「为所有用户预分配通道」的优化，收益有限——它省的是本来就便宜的那部分内存（通道状态），而真正稀缺的是推送能力。
  • 容量规划要用吞吐算机器数，用内存算每台装多少状态；讲义说「按历史流量每日扩缩容、必要时超配扛尖峰」是对的，但理由是吞吐，不是状态。

第三，位置数据本身是三者里最便宜的。 1000 万在线用户 × 64 B = 0.64 GB，比通道状态小 312 倍。这解释了为什么讲义说「Redis 是位置缓存的理想选择」——它便宜、且原生支持 TTL 淘汰，不需要为它单独做分片与服务发现。

三、增量二：TTL 与「离线判定」不该共用一个字段

讲义说：位置缓存里每条记录设 TTL，TTL 过期后，用户不再活跃，其数据会从缓存中删除；同时又假设「不活跃的朋友 10 分钟后消失」。这两句放在一起就有一个冲突：

"""位置缓存的 TTL：闪烁窗口怎么算，以及「离线判定」不该和它共用一个 TTL。

只依赖标准库；输出确定性。
"""
REPORT_INTERVAL = 30      # 讲义：位置刷新间隔 30 秒
OFFLINE_AFTER = 600       # 讲义：假设不活跃的朋友 10 分钟后消失
REC_BYTES = 64

print("位置每 %d 秒写一次；讲义说缓存记录设 TTL，过期即认为用户不活跃并删除" % REPORT_INTERVAL)
print()
print("%-8s %14s %18s %16s" % ("TTL", "两次写入间会过期?", "朋友列表空窗", "在线判定"))
for ttl in (30, 60, 90, 120, 300, 600):
    gap = ttl - REPORT_INTERVAL
    if gap < 0:
        verdict = "会（写入前就过期）"
        window = "整段 %.0f 秒" % REPORT_INTERVAL
    elif gap == 0:
        verdict = "竞态（与下次写入同时）"
        window = "随机 ~%.0f 秒" % REPORT_INTERVAL
    else:
        verdict = "不会"
        window = "无"
    offline = "%.0f 分钟后判定离线" % (OFFLINE_AFTER / 60) if ttl >= OFFLINE_AFTER else "%.0f 分钟后（偏早）" % (ttl / 60)
    print("%-8d %14s %18s %16s" % (ttl, verdict, window, offline))
print()
print("结论一：位置记录的 TTL 必须 >= 2 x 上报间隔（%d 秒），否则记录会在两次写入之间过期，" % (2 * REPORT_INTERVAL))
print("        朋友列表每 %d 秒闪一次（空窗最长 %d 秒）。" % (REPORT_INTERVAL, REPORT_INTERVAL))
print("结论二：讲义把两件事塞进了同一个 TTL ——")
print("        (a) 位置记录的过期：为了控制内存与新鲜度，需要 %d 秒量级；" % (2 * REPORT_INTERVAL))
print("        (b) 用户离线的判定：讲义假设 %d 分钟（%d 秒）后才算不活跃。" % (OFFLINE_AFTER // 60, OFFLINE_AFTER))
print("        两者差 %d 倍，共用一个字段就必然二选一：按 (a) 设，用户的在线状态会被误判为离线；"
      % (OFFLINE_AFTER // (2 * REPORT_INTERVAL)))
print("        按 (b) 设，位置记录要多留 %d 秒，内存按在线人数线性涨。" % (OFFLINE_AFTER - 2 * REPORT_INTERVAL))
print("        => 判据：**位置记录的 TTL 与「用户是否在线」是两个不同的量**，")
print("           后者应该由「最近一次上报时间距今多久」判定，而不是靠位置键过期。")
print()
mem = 10_000_000 * REC_BYTES
print("内存账：%d 在线用户 x %d B = %.2f GB（若 TTL 拉长到 %d 秒，在线人数不变则内存不变；" % (10_000_000, REC_BYTES, mem / 1e9, OFFLINE_AFTER))
print("      真正随 TTL 增长的是「已下线但记录未过期」的存量：下线速率 x TTL）。")

输出：

位置每 30 秒写一次；讲义说缓存记录设 TTL，过期即认为用户不活跃并删除

TTL           两次写入间会过期?             朋友列表空窗             在线判定
30          竞态（与下次写入同时）           随机 ~30 秒        0 分钟后（偏早）
60                   不会                  无        1 分钟后（偏早）
90                   不会                  无        2 分钟后（偏早）
120                  不会                  无        2 分钟后（偏早）
300                  不会                  无        5 分钟后（偏早）
600                  不会                  无       10 分钟后判定离线

结论一：位置记录的 TTL 必须 >= 2 x 上报间隔（60 秒），否则记录会在两次写入之间过期，
        朋友列表每 30 秒闪一次（空窗最长 30 秒）。
结论二：讲义把两件事塞进了同一个 TTL ——
        (a) 位置记录的过期：为了控制内存与新鲜度，需要 60 秒量级；
        (b) 用户离线的判定：讲义假设 10 分钟（600 秒）后才算不活跃。
        两者差 10 倍，共用一个字段就必然二选一：按 (a) 设，用户的在线状态会被误判为离线；
        按 (b) 设，位置记录要多留 540 秒，内存按在线人数线性涨。
        => 判据：**位置记录的 TTL 与「用户是否在线」是两个不同的量**，
           后者应该由「最近一次上报时间距今多久」判定，而不是靠位置键过期。

内存账：10000000 在线用户 x 64 B = 0.64 GB（若 TTL 拉长到 600 秒，在线人数不变则内存不变；
      真正随 TTL 增长的是「已下线但记录未过期」的存量：下线速率 x TTL）。

两处结论：

第一，位置记录的 TTL 必须 ≥ 2 × 上报间隔（60 秒）。 位置每 30 秒写一次，TTL 若正好等于 30 秒，记录会在下一次写入的同一瞬间过期——处于竞态边缘；TTL 小于 30 秒则必然出现空窗，表现为朋友列表每 30 秒闪一次（对方突然消失又出现）。这是这类系统里最常见、也最难被日志发现的 UX bug。

第二，讲义把两个不同的量塞进了同一个字段。 「位置记录该留多久」需要 60 秒量级（控制内存与新鲜度），而「用户算不算离线」需要 10 分钟（600 秒）——两者差 10 倍，共用一个 TTL 就必然二选一：按 60 秒设，用户的在线状态会被误判为离线（讲义正是用 TTL 过期来判定不活跃的）；按 600 秒设，位置记录要多留 540 秒，而真正随之增长的是「已下线但记录还没过期」的存量（约为下线速率 × TTL）。

判据：位置记录的 TTL 与「用户是否在线」是两个量。 后者应该由「最近一次上报时间距今多久」判定（一个独立的 last_seen 字段），而不是靠位置键过期。两者分开之后，TTL 纯粹变成内存与新鲜度的旋钮，扇出与在线判定都不再受它影响。

四、增量三：40 亿条订阅关系，以及分片键的选择

讲义说「客户端初始化时，WebSocket 服务器获取该用户的好友列表，订阅他们在 Redis pub/sub 上的通道」。这句话背后有一个大数：

"""订阅关系的总量：大户问题与分片键的选择。

只依赖标准库；输出确定性。
"""
USERS = 100_000_000
USING_FEATURE = 0.10      # 讲义：10% 使用附近朋友功能
FRIENDS = 400
ONLINE = 10_000_000
REPORT_INTERVAL = 30
FB_FRIEND_CAP = 5000
CHANNEL_NAME_BYTES = 24

active_users = USERS * USING_FEATURE
subs = active_users * FRIENDS
print("用该功能的用户 %d（%d x %.0f%%），每人 %d 好友" % (active_users, USERS, USING_FEATURE * 100, FRIENDS))
print("=> 订阅关系总量 %d 条" % subs)
print()
print("内存账（每条订阅至少要记通道名 + 元数据，按 %d B 估）：" % CHANNEL_NAME_BYTES)
print("  %.0f 亿条 x %d B = %.0f GB —— 这是这套设计里最大的隐含状态量" % (subs / 1e8, CHANNEL_NAME_BYTES, subs * CHANNEL_NAME_BYTES / 1e9))
print("  对比：位置缓存（%d 在线 x 64 B）只要 %.2f GB；通道状态（讲义）200 GB" % (ONLINE, ONLINE * 64 / 1e9))

读法：

  • 订阅关系总量是 40 亿条（1 亿用户 × 10% 用该功能 × 400 好友），按每条 24 B 估是 96 GB。三个状态量的排序是：通道状态 200 GB > 订阅关系 96 GB > 位置数据 0.64 GB。这与讲义的处理方式一致——通道状态要专门配服务发现与哈希环，位置数据随手放 Redis 就行。
  • 大户的扇出是平方级风险的入口：讲义提到可以给好友数设上限（Facebook 5000）。按平均 400 好友、10% 在线算，单次更新的扇出是 40 条；一个有 5000 好友的大户，扇出 500 条，是平均用户的 12 倍。这类用户不多，但每个都会给某台 WS 服务器制造尖峰——所以「按 user_id 分片」解决不了它，需要按扇出量做负载感知。
  • 分片键的选择由这条订阅关系决定：订阅是「被订阅者 → 订阅者」的有向边。若按订阅者（发更新的人）分片，一台 WS 服务器持有自己用户的好友通道订阅，但一次位置更新要投给分散在别的分片上的用户 → 必须经 pub/sub 跨节点转发（讲义的方案）；若按被订阅者分片，位置更新只写一个分片，订阅它的服务器去取 → 「谁在线」与「位置在哪」分离，正好对应讲义的两层结构（Redis 位置缓存 + pub/sub 通道）。
  • 搬移成本与状态量成正比：讲义用一致性哈希在增减服务器时最小化通道搬移量——按上面的排序，通道状态是最大的那个，所以一致性哈希的收益恰恰落在这里；而扩缩容时的「大量重新订阅」与「客户端可能漏掉位置更新」也是同一个权衡的另一面（本场景允许漏，所以选流量最低点做是合理的）。

五、把三个模型套回本章（判据清单）

  1. 扇出量是成本主项：位置更新 QPS × (好友数 × 好友在线率) = 投递消息 QPS；本例 333k × 40 = 1330 万/秒。容量按它算，不按用户数算。
  2. 区分状态维度与吞吐维度：通道状态 200 GB（2 台就够）vs 推送吞吐 133 台——瓶颈在每台的推送能力，扩缩容按吞吐、容量按状态。
  3. 位置 TTL ≥ 2 × 上报间隔（本例 60 秒），否则列表每 30 秒闪一次；离线判定另设 last_seen，不要靠位置键过期。
  4. 分片键跟着订阅关系走：按被订阅者分片可让位置更新只写一个分片；按订阅者分片则必须跨节点转发（讲义的 pub/sub 方案）。
  5. 大户要单独兜：好友上限（讲义举例 5000）之外，还要按扇出量做负载感知——单个大户的扇出是平均值的 12 倍。
  6. 预分配通道这类优化先看它省的是不是瓶颈：本例它省的是通道状态（占总内存 1.5%），收益有限。

七、这三个模型判不了什么

  • 每条订阅 24 B、每条位置 64 B 都是估的。真实占用取决于序列化格式与 Redis 的结构开销；数量级不会变，但「通道状态 vs 订阅关系 vs 位置数据」的排序在换实现后可能翻转——若通道名改短或订阅改用紧凑编码，排序就变。
  • 好友在线率 10%、人均 400 好友来自讲义假设。真实分布重尾，长尾用户的扇出分布比均值重要得多。
  • TTL 与离线的分析假设写入是严格周期性的。真实客户端会因为后台、省电、弱网而抖动上报间隔；此时「2 倍间隔」这条线要改成「2 倍间隔的 p99」。
  • 没算 WebSocket 服务器的连接数与内存：1000 万并发连接摊到 N 台，每台的连接数、每连接的内存在这里完全没算——而它与位置缓存是两份独立的账。
  • 三个模型都没碰讲义列出的那个开放问题（「附近的陌生人」的 geohash 通道池）：那个功能把「订阅一个用户通道」变成「订阅一个地理格子」，扇出量与隐私模型都完全不同，需要单独算。

FAQ（八、常见问题）

扇出量怎么算？ 位置更新 QPS × 每次更新的接收者数 = 投递消息 QPS。本例：1000 万在线 / 30 秒 = 333k 更新/秒，每次平均转发 400 好友 × 10% 在线 = 40 条 ⇒ 1330 万条/秒（讲义深挖里写的「约 1400 万」就是这个乘积）。

Redis 要多少台？ 按推送吞吐算：1330 万 ÷ 每台 10 万 = 133 台。注意别按内存算——通道状态 200 GB，2 台 100 GB 就装得下；133 台 × 100 GB 里通道只占 1.5%，瓶颈是每台的推送能力。

TTL 该设多少？ 位置记录 ≥ 2 × 上报间隔（本例 60 秒）；TTL 正好等于 30 秒会与下一次写入撞在同一瞬间，朋友列表每 30 秒闪一次。而「用户算不算离线」要 10 分钟——这两个是不同的量，离线判定该用独立的 last_seen，不要靠位置键过期。

订阅关系占多少？ 1 亿用户 × 10% × 400 好友 = 40 亿条，按 24 B 估 96 GB。它比位置数据（0.64 GB）大 150 倍，但小于讲义给的通道状态（200 GB）——所以一致性哈希与服务发现的重点理应放在通道上。

好友很多的用户怎么办？ 设上限（讲义举例 Facebook 5000）之外，注意单个大户的单次扇出是平均用户的 12 倍（500 条 vs 40 条）；按 user_id 分片解决不了这种尖峰，需要按扇出量做负载感知。
