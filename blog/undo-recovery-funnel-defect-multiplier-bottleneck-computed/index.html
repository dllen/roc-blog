撤销按钮的三笔账：恢复漏斗、缺陷乘数与瓶颈

#AI工程#Agent#技术深度#大会笔记

撤销按钮的三笔账？恢复成功率在真实规模下是多少、恢复缺陷吃掉了多少能力提升、以及为什么「只修一个瓶颈」几乎没有效果。我读完 AIE Code Summit 2026 那场《The Missing Undo Button for Coding Agents》之后，最想验证的是：讲者给的那组数字（84%、47%、54%、42%）在自己的实验设定之外还能不能这么读。这篇把它算清楚，顺便把「可恢复性」这笔账拆成三个可算的量。

口径说明

  • 源是我自己的精读笔记 02-课程体系/AIE-Code-Summit-2026/05-预录插播/14 Tanmay Sah and Dolly Sah - The Missing Undo Button for Coding Agents.md（约 8,270 字，已按官方 Day 1 中英对照演讲稿校对）。
  • 演讲本身按导读式处理：只复述机制与公开数据，不引用官方译稿原文、不搬附件图。代码与数字均为自写模型。
  • 必须保留的怀疑（我的笔记里已写）：UndoBench 的 2,880 次配对试验与 EvoUndo 的 600 个任务都属于作者自建 benchmark，实验设定（尤其是故障注入方式与任务分布）未在演讲中公开，因此 84%/47%/54%/42% 的外部可比性有限；「92% 恢复率」与「+30 个百分点」来自不同子组与不同实验，不宜简单相加。本文只做「把这组数字还原成绝对数与结构」的分析，不把它们当成通用基准。
  • 我为了建模补的（故障率、每天写操作数）都标为「估」；两个讲者给的分组数字（48/143/38/142/180）按笔记原样引用。
  • 三个脚本只依赖 Python 标准库；输出为实跑结果，逐行可复现（无随机数，两次运行输出逐字一致）。
  • 撞题与边界：本系列已发《反 Slop 的三笔账》（约束下沉、覆盖率门槛、回退止损线）、《自治等级的三笔账》（升级回本、样本量、scope 放大）、《软件工厂的三笔账》（燃料、垃圾山、围栏）。那三篇讲「怎么把活干好」，本文讲「干砸了怎么退回来」——衔接点：可恢复性是自治的前置条件，不是运维兜底。

一、讲者的骨架：从「失败的响应」到四种恢复

开场的问题：Git 能告诉我们仓库里发生了什么变化，但不在 Git 范围内的东西——外部 API 调用、运行时配置、通知——又该怎么处理？补充一句更狠的：简单地重新执行一个操作，并不一定能消除已经发生的事。

UndoBench 的那条裂缝：2,880 次配对试验，比较「正常执行」与「注入故障下的执行」——正常条件下成功率 84%；注入故障后，只有 47% 的（原本会成功的）试验能恢复成功。

关键机制：失败的响应 ≠ 失败的操作。agent 向外部系统发请求创建工单：请求已发出、agent 在等回复；服务器收到并成功创建了编号 781 的票；但确认信息在传给 agent 的途中丢了——从 agent 的视角看是超时，它并不知道票已经创建。朴素重试在 54% 的这类试验里制造了重复副作用。

为什么 git revert 不够：Git 只能恢复仓库内的变更，而 coding agent 还会修改自己的运行时状态（工具注册表、中间件、配置），还会触发外部副作用（部署、数据库权限）。更进一步：撤销也不总是「反向执行一条命令」就够——假设 agent 把超时从 30 改成 60，要撤销这次改动，它必须知道原值是 30。

EvoUndo 的做法：在施加变更之前先捕获一份 pre-state witness（修改前状态证据），用它提供恢复原始状态所需的信息，并在事后独立验证恢复是否真的成功。

那个令人不安的数字：EvoUndo 评估了 600 个自我进化任务，其中 478 个带来了能力提升，但这些改进里有 197 个存在恢复缺陷——约占能力正向案例的 42%。

提示词救不了：他们试了四种由验证器引导（verifier guided）的修复策略，在原始恢复语言下没有一种能修好这 197 个自然发生的失败。原因是两个瓶颈：状态接地（agent 缺少关于原始状态的准确信息）与恢复表达力（恢复语言无法表达逆转链条所需的操作）。分别补：给精确状态信息后，48 个案例里修好 38 个（从 0 提升）；引入更丰富的 undo 操作后，143 个案例里修好 142 个（从 0 提升）。两个都给（扩展恢复语言）后，197 个缺陷里修好 180 个（约 92%），可接受的改进从 600 个任务中的 281 个增加到 461 个——提升 30 个百分点。

Dolly 讲的落地流程：agent 拿到 effect contract（效果契约）与 recovery plan（恢复计划）；在施加变更之前捕获代表原始状态的 state witness；更早一步，在测试环境中先做测试；然后 agent 施加变更并执行恢复计划；最后由独立的验证者再验证一次——「仅仅因为执行了 undo 命令，恢复就不算成功」。

恢复不是统一动作，要分四种：什么都没变 → 安全重试；有原始状态可依 → 恢复；外部动作已提交 → 需要补偿机制；无法恢复、或无法验证恢复安全、或验证者拒绝 → 停下并升级求助。

三条收尾要点：UndoBench 表明任务执行成功并不保证恢复成功；EvoUndo 提供了「捕获原始状态 → 施加变更 → 恢复 → 独立验证」的结构化流程；只有当能力要求与可恢复性要求都得到满足时，才能承认自我进化带来的变更。

二、增量一：把百分比还原成绝对数

"""恢复漏斗：2,880 次配对试验里，绝对数比百分比更刺眼。

数字取自我的精读笔记（UndoBench：2,880 次配对试验；正常成功率 84%；注入故障后只有 47% 的
原本成功试验能恢复成功；朴素重试在 54% 的试验里制造重复副作用）。
只依赖标准库；输出确定性。
"""
TRIALS = 2880
P_NORMAL = 0.84            # 正常条件下的成功率
P_RECOVER = 0.47           # 注入故障后「原本会成功的试验」里能恢复成功的比例
P_DUP = 0.54               # 朴素重试产生重复副作用的试验比例

print("一、完整漏斗（把百分比还原成绝对数）")
normal_ok = TRIALS * P_NORMAL
recovered = normal_ok * P_RECOVER
lost = normal_ok - recovered
print("   总试验 %d 次" % TRIALS)
print("   正常条件下成功      : %s 次（%.0f%%）" % (format(int(normal_ok), ","), P_NORMAL * 100))
print("   注入故障后恢复成功  : %s 次（原本成功试验的 %.0f%%）" % (format(int(recovered), ","), P_RECOVER * 100))
print("   **恢复失败**        : %s 次" % format(int(lost), ","))
print()
print("   => 恢复成功率相对「正常执行」只有 %.0f%%（47%% / 84%%）——" % (100.0 * P_RECOVER / P_NORMAL))
print("      **每 100 次本来会成功的执行，故障会毁掉 %.0f 次**。" % (100.0 * (1 - P_RECOVER / P_NORMAL)))
print()
print("二、朴素重试 vs 恢复：失败率数字接近，性质不同")
dup_cases = TRIALS * P_DUP
print("%-28s %16s %22s %24s" % ("策略", "失败/副作用率", "折算次数(2,880 试验)", "副作用性质"))
print("%-28s %15.0f%% %22s %24s" % ("朴素重试", P_DUP * 100, format(int(dup_cases), ","), "**留下重复的外部副作用**"))
print("%-28s %15.0f%% %22s %24s" % ("恢复（restore）", (1 - P_RECOVER) * 100,
      format(int(lost), ","), "状态没回原样（可观测）"))
print()
print("   => 两者失败率接近（54%% vs %.0f%%），但**重试的失败会留下不可逆的脏数据**，" % ((1 - P_RECOVER) * 100))
print("      恢复失败只是「没恢复」。判据：**不能只看失败率，要看失败的副作用是否可逆**。")
print()
print("三、折算到真实系统：故障率才是乘数")
FAULT_RATE = 0.01            # 写操作遇到「响应丢失但操作已生效」这类故障的比例（估）
WRITES_PER_DAY = 100         # 每天的写操作数（估）
print("   注意：54%% 是**「遇到故障后选择朴素重试」时的副作用率**，不是所有写操作都会出重复副作用。")
print("   真正的乘数是故障率 f：")
print("%-14s %18s %20s %22s" % ("每天写操作", "故障率 f", "每天重复副作用", "每月重复副作用"))
for writes in (10, 100, 1000):
    for f in (0.001, 0.01, 0.05):
        dup_day = writes * f * P_DUP
        print("%-14d %17.1f%% %20.2f %21.0f" % (writes, f * 100, dup_day, dup_day * 30))
    print()
print("   => 每天 100 次写操作、故障率 1%% -> 每天 %.1f 次重复副作用、每月 %.0f 次。" % (
    WRITES_PER_DAY * FAULT_RATE * P_DUP, WRITES_PER_DAY * FAULT_RATE * P_DUP * 30))
print("      判据：**故障率是乘数、恢复能力是除数** —— 提高恢复率只能救回已经故障的那部分，")
print("      想少出重复副作用，要么把故障率降下来，要么让重试带上幂等键。")

输出：

一、完整漏斗（把百分比还原成绝对数）
   总试验 2880 次
   正常条件下成功      : 2,419 次（84%）
   注入故障后恢复成功  : 1,137 次（原本成功试验的 47%）
   **恢复失败**        : 1,282 次

   => 恢复成功率相对「正常执行」只有 56%（47% / 84%）——
      **每 100 次本来会成功的执行，故障会毁掉 44 次**。

二、朴素重试 vs 恢复：失败率数字接近，性质不同
策略                                    失败/副作用率         折算次数(2,880 试验)                    副作用性质
朴素重试                                      54%                  1,555           **留下重复的外部副作用**
恢复（restore）                               53%                  1,282              状态没回原样（可观测）

   => 两者失败率接近（54% vs 53%），但**重试的失败会留下不可逆的脏数据**，
      恢复失败只是「没恢复」。判据：**不能只看失败率，要看失败的副作用是否可逆**。

三、折算到真实系统：故障率才是乘数
   注意：54%% 是**「遇到故障后选择朴素重试」时的副作用率**，不是所有写操作都会出重复副作用。
   真正的乘数是故障率 f：
每天写操作                       故障率 f              每天重复副作用                每月重复副作用
10                           0.1%                 0.01                     0
10                           1.0%                 0.05                     2
10                           5.0%                 0.27                     8

100                          0.1%                 0.05                     2
100                          1.0%                 0.54                    16
100                          5.0%                 2.70                    81

1000                         0.1%                 0.54                    16
1000                         1.0%                 5.40                   162
1000                         5.0%                27.00                   810

   => 每天 100 次写操作、故障率 1% -> 每天 0.5 次重复副作用、每月 16 次。
      判据：**故障率是乘数、恢复能力是除数** —— 提高恢复率只能救回已经故障的那部分，
      想少出重复副作用，要么把故障率降下来，要么让重试带上幂等键。

三处结论：

第一，47% 这个数字的真实含义是 56%。 2,880 次试验里，正常条件下成功 2,419 次；注入故障后能恢复成功 1,137 次；恢复失败 1,282 次。恢复成功率相对正常执行只有 47% / 84% = 56%——每 100 次本来会成功的执行，故障会毁掉 44 次。判据：引用「47%」时要说清分母，它不是「47% 的操作会恢复」，而是「原本会成功的操作里只有 47% 能救回来」。

第二，朴素重试和恢复的失败率数字接近，但性质完全不同。 重试的副作用率 54%（2,880 次试验里约 1,555 次留下重复副作用）；恢复的失败率 53%（1,282 次）。判据：不能只看失败率，要看失败的副作用是否可逆——重试留下的是脏数据（重复工单、重复扣款、重复部署），恢复失败只是「没恢复」，前者往往不可回退。

第三，故障率才是乘数，恢复能力只是除数。 54% 是「遇到故障后选择朴素重试」时的副作用率，不是所有写操作都会出重复副作用：每天 100 次写操作、故障率 1% → 每天 0.5 次重复副作用、每月 16 次；故障率 5% → 每月 81 次。判据：提高恢复率只能救回已经故障的那部分；要减少重复副作用，要么把故障率降下来，要么让重试带上幂等键。

三、增量二：恢复缺陷是能力侧投入的乘数

"""42% 的恢复缺陷吃掉多少「能力提升」，以及它让能力侧投入放大多少。

数字取自我的精读笔记（EvoUndo 评估 600 个自我进化任务：478 个带来能力提升，其中 197 个存在
恢复缺陷，约占能力正向案例的 42%；扩展恢复语言后 197 个里修好 180 个；可接受改进从 281 增到 461）。
只依赖标准库；输出确定性。
"""
TASKS = 600
IMPROVED = 478             # 带来能力提升的任务
DEFECTIVE = 197            # 其中存在恢复缺陷的
STILL_BAD = 197 - 180      # 扩展恢复语言后仍未修好的
ADMISSIBLE_BEFORE = 281    # 扩展恢复语言前的可接受改进
ADMISSIBLE_AFTER = 461     # 之后

print("一、恢复缺陷吃掉了多少能力提升")
print("   自我进化任务 %d 个 -> 能力提升 %d 个 -> 其中带恢复缺陷 %d 个" % (TASKS, IMPROVED, DEFECTIVE))
print("   缺陷占能力正向案例的比例 = **%.1f%%**（讲者取整为 42%%）" % (100.0 * DEFECTIVE / IMPROVED))
print("   可接受改进（有能力提升且可恢复）= %d - %d = **%d**" % (IMPROVED, DEFECTIVE, ADMISSIBLE_BEFORE))
print()
print("二、补齐恢复表达力之后")
print("   扩展恢复语言 -> 197 个缺陷里修好 **180** 个（约 %.0f%%），仍未修好 %d 个" % (
    100.0 * 180 / 197, STILL_BAD))
print("   可接受改进 = %d - %d = **%d**（+30 个百分点：%d -> %d）" % (
    IMPROVED, STILL_BAD, ADMISSIBLE_AFTER, ADMISSIBLE_BEFORE, ADMISSIBLE_AFTER))
print()
print("   注：笔记提醒，**「92% 恢复率」与「+30 个百分点」来自不同子组与不同实验，不宜简单相加**；")
print("       本文只把它们并列呈现，不做合并推算。")
print()
print("三、恢复缺陷让能力侧的投入放大多少")
effective_before = ADMISSIBLE_BEFORE
effective_after = ADMISSIBLE_AFTER
print("   同样要拿到 %d 个「可接受改进」：" % effective_after)
print("     恢复能力不补（缺陷率 %.0f%%）：能力侧要做 %.2f 倍的提升才够" % (
    100.0 * DEFECTIVE / IMPROVED, effective_after / effective_before))
print("     恢复表达力补齐（残余缺陷 %d 个）：能力侧做 %.2f 倍即可" % (
    STILL_BAD, effective_after / (IMPROVED - STILL_BAD)))
print()
print("   => 判据：**恢复缺陷不是「效率问题」，是能力侧投入的乘数**——")
print("      %.1f%% 的缺陷率意味着同样的可接受改进数，能力侧要多做 **%.0f%%**。" % (
    100.0 * DEFECTIVE / IMPROVED, 100.0 * (effective_after / effective_before - 1)))
print("      所以「先补恢复能力」不是运维兜底，是**把能力投入的乘数降回 1**。")
print()
print("四、每 1% 的恢复率换回多少")
print("   按 600 个任务计：修复 %d 个缺陷 = 恢复率 +%.0f%%（197 的尺度）-> 可接受改进 +%d 个" % (
    180, 100.0 * 180 / 197, 180))
print("   即每 1 个修好的恢复缺陷 = 1 个可接受改进；每 1 个百分点的恢复率（197 的 1% ≈ 1.97 个缺陷）")
print("   ≈ **1.97 个可接受改进**。")

输出：

一、恢复缺陷吃掉了多少能力提升
   自我进化任务 600 个 -> 能力提升 478 个 -> 其中带恢复缺陷 197 个
   缺陷占能力正向案例的比例 = **41.2%**（讲者取整为 42%）
   可接受改进（有能力提升且可恢复）= 478 - 197 = **281**

二、补齐恢复表达力之后
   扩展恢复语言 -> 197 个缺陷里修好 **180** 个（约 91%），仍未修好 17 个
   可接受改进 = 478 - 17 = **461**（+30 个百分点：281 -> 461）

   注：笔记提醒，**「92% 恢复率」与「+30 个百分点」来自不同子组与不同实验，不宜简单相加**；
       本文只把它们并列呈现，不做合并推算。

三、恢复缺陷让能力侧的投入放大多少
   同样要拿到 461 个「可接受改进」：
     恢复能力不补（缺陷率 41%）：能力侧要做 1.64 倍的提升才够
     恢复表达力补齐（残余缺陷 17 个）：能力侧做 1.00 倍即可

   => 判据：**恢复缺陷不是「效率问题」，是能力侧投入的乘数**——
      41.2% 的缺陷率意味着同样的可接受改进数，能力侧要多做 **64%**。
      所以「先补恢复能力」不是运维兜底，是**把能力投入的乘数降回 1**。

四、每 1% 的恢复率换回多少
   按 600 个任务计：修复 180 个缺陷 = 恢复率 +91%（197 的尺度）-> 可接受改进 +180 个
   即每 1 个修好的恢复缺陷 = 1 个可接受改进；每 1 个百分点的恢复率（197 的 1% ≈ 1.97 个缺陷）
   ≈ **1.97 个可接受改进**。

三处结论：

第一，41.2% 的能力提升是「带伤」的。 600 个自我进化任务 → 478 个带来能力提升 → 其中 197 个存在恢复缺陷（41.2%，讲者取整为 42%）→ 可接受改进（有能力提升且可恢复）只剩 281 个。判据：谈「agent 自我改进带来了多少提升」时，如果不含恢复这一项，这个数字最多只对一半。

第二，能力侧的投入因此被放大 64%。 同样要拿到 461 个可接受改进：恢复能力不补，能力侧要做 1.64 倍的提升才够；补齐恢复表达力（残余缺陷 17 个）后，能力侧做 1.00 倍即可。判据：恢复缺陷不是「效率问题」，是能力侧投入的乘数——所以「先补恢复能力」不是运维兜底，而是把能力投入的乘数降回 1。

第三，每 1 个百分点的恢复率换回约 2 个可接受改进。 修好 180 个缺陷 = 恢复率 +91%（以 197 为分母）→ 可接受改进 +180 个；即每修好 1 个恢复缺陷 = 1 个可接受改进。判据：这条让「恢复投入」有了一个和「能力投入」可比的单位——你可以直接问「再修 10 个恢复缺陷，等于多训多少能力」。

四、增量三：两个瓶颈是互补的，必须一起补

"""两个瓶颈是互补的乘法关系：单独补一个，收益都接近零。

数字取自我的精读笔记（状态接地实验：48 个案例从 0 修到 38；恢复表达力实验：143 个案例从 0 修到
142；两种能力都给后 197 个缺陷里修好 180 个）。
只依赖标准库；输出确定性。
"""
GROUP_STATE = 48            # 缺「状态接地」信息的那批案例
GROUP_EXPR = 143            # 缺「恢复表达力」的那批案例
FIX_STATE_ONLY = 38         # 只补状态接地 -> 修好的个数
FIX_EXPR_ONLY = 142         # 只补恢复表达力 -> 修好的个数
TOTAL_DEFECTS = 197
FIX_BOTH = 180

print("一、两个批次各自的缺口")
print("   缺状态接地的批次     : %d 个案例" % GROUP_STATE)
print("   缺恢复表达力的批次   : %d 个案例" % GROUP_EXPR)
print("   合计 %d（笔记里的 197 个缺陷，差 %d 个在两个批次口径外）" % (
    GROUP_STATE + GROUP_EXPR, TOTAL_DEFECTS - GROUP_STATE - GROUP_EXPR))
print()
print("二、单独补一个瓶颈的收益")
print("%-24s %14s %18s %22s" % ("补什么", "修好个数", "占本批次", "占全部 197"))
for name, fixed, grp in (("只补状态接地", FIX_STATE_ONLY, GROUP_STATE),
                          ("只补恢复表达力", FIX_EXPR_ONLY, GROUP_EXPR)):
    print("%-24s %14d %17.0f%% %21.0f%%" % (name, fixed, 100.0 * fixed / grp,
          100.0 * fixed / TOTAL_DEFECTS))
print()
print("   => **单独补状态接地只修好 %d/%d（%.0f%%）**，因为另一批的缺口它补不上；" % (
    FIX_STATE_ONLY, TOTAL_DEFECTS, 100.0 * FIX_STATE_ONLY / TOTAL_DEFECTS))
print("      **单独补恢复表达力只修好 %d/%d（%.0f%%）**，同理。" % (
    FIX_EXPR_ONLY, TOTAL_DEFECTS, 100.0 * FIX_EXPR_ONLY / TOTAL_DEFECTS))
print()
print("三、两个都补")
print("   %d + %d = %d，与「两个都给后修好 %d 个」一致" % (FIX_STATE_ONLY, FIX_EXPR_ONLY,
      FIX_STATE_ONLY + FIX_EXPR_ONLY, FIX_BOTH))
print("   占全部 197 个的 **%.0f%%**" % (100.0 * FIX_BOTH / TOTAL_DEFECTS))
print()
print("   => 单独补状态接地 = %.0f%%、单独补恢复表达力 = %.0f%%、两个都补 = %.0f%%。" % (
    100.0 * FIX_STATE_ONLY / TOTAL_DEFECTS, 100.0 * FIX_EXPR_ONLY / TOTAL_DEFECTS,
    100.0 * FIX_BOTH / TOTAL_DEFECTS))
print("      关键不是「加」——而是**两个批次互补**：只补一项，最多拿到自己那批的份额；")
print("      两项都补才等于两批的并集（%d + %d = %d，与实测的 %d 一致）。" % (
    FIX_STATE_ONLY, FIX_EXPR_ONLY, FIX_STATE_ONLY + FIX_EXPR_ONLY, FIX_BOTH))
print("      判据：**互补的两个瓶颈必须一起补**——按「先修一个看看」的顺序做，会在一半的案例上")
print("      毫无进展（只补状态接地时，另外 %.0f%% 的案例根本没被覆盖）。" % (
    100.0 * GROUP_EXPR / (GROUP_STATE + GROUP_EXPR)))
print()
print("四、推广：任何一个「两处都要修」的工程问题")
print("   若两个独立批次各缺一项、每项的修复只能覆盖自己那批，")
print("   则「只修一项」的收益 ≈ 半数，「都修」才是 100%。")
for a_fixed, b_fixed, total in ((1, 1, 2), (9, 1, 10), (19, 1, 20)):
    print("     批次 %d+%d：只修第一项 -> %.0f%%；只修第二项 -> %.0f%%；都修 -> 100%%" % (
        a_fixed, b_fixed, 100.0 * a_fixed / total, 100.0 * b_fixed / total))

四、推广：任何一个「两处都要修」的工程问题
   若两个独立批次各缺一项、每项的修复只能覆盖自己那批，
   则「只修一项」的收益 ≈ 半数，「都修」才是 100%。
     批次 1+1：只修第一项 -> 50%；只修第二项 -> 50%；都修 -> 100%
     批次 9+1：只修第一项 -> 90%；只修第二项 -> 10%；都修 -> 100%
     批次 19+1：只修第一项 -> 95%；只修第二项 -> 5%；都修 -> 100%

三处结论：

第一，单独补一个瓶颈，收益远低于直觉。 只补状态接地 → 修好 38/197（19%）；只补恢复表达力 → 修好 142/197（72%）；两个都补 → 180/197（91%）。

第二，但这不是「加法」，是「并集」。 两个批次是互补的：48 个案例缺状态接地、143 个案例缺恢复表达力；补好第一个批次得到 38、修好第二个批次得到 142，38 + 142 = 180，与「两个都给后修好 180 个」完全一致。判据：互补的两个瓶颈必须一起补——按「先修一个看看」的顺序做，会在 75% 的案例上毫无进展（只补状态接地时，另外 143 个案例根本没被覆盖）。

第三，这个结构可以推广到任何「两处都要修」的问题。 若两个独立批次各缺一项、每项的修复只能覆盖自己那批，则「只修一项」的收益约等于自己那批的份额，「都修」才是 100%。判据：看到「修 A 能解决 79%、修 B 能解决 99%」这两个数字时，先问它们是不是在同一批案例上——如果不在，那两个 99% 加起来也只是一个 91%。

五、把三个模型套回本章（判据清单）

  1. 恢复漏斗：2,880 次试验 → 正常成功 2,419 → 恢复成功 1,137 → 恢复失败 1,282。
  2. 恢复成功率相对正常执行只有 56%（47% / 84%）→ 每 100 次本来会成功的执行，故障毁掉 44 次。
  3. 重试与恢复的失败率接近（54% vs 53%），性质不同：前者留下不可逆副作用（约 1,555 次），后者只是没恢复。
  4. 故障率是乘数、恢复能力是除数：每天 100 次写操作、故障率 1% → 每月 16 次重复副作用；5% → 81 次。
  5. 41.2% 的能力提升带恢复缺陷（讲者取整 42%）→ 可接受改进只剩 281（600 个任务中）。
  6. 恢复缺陷是能力侧投入的乘数：同样 461 个可接受改进，能力侧要多做 64%。
  7. 每 1 个百分点的恢复率 ≈ 2 个可接受改进 → 恢复投入与能力投入有了可比单位。
  8. 两个瓶颈互补：只补状态接地 19%、只补恢复表达力 72%、都补 91%（38 + 142 = 180）。
  9. 先修一个的顺序会在 75% 的案例上毫无进展 → 互补缺口必须一起补。

七、这三个模型判不了什么

  • 84%/47%/54%/41.2%/91%/30 个百分点全部来自作者自建 benchmark，故障注入方式与任务分布未公开。本文做的只是「把百分比还原成绝对数与结构」，不是验证这些数字本身；不同任务分布下它们会明显不同。任何把 47% 当成通用值的引用都是错的。
  • 「92% 恢复率」与「+30 个百分点」来自不同子组与不同实验，本文并列呈现、不做合并推算（笔记已提醒）。同理，48 + 143 = 191 ≠ 197，有 6 个案例落在两个分组口径之外——模型里如实标出。
  • 恢复漏斗假设「正常成功」与「注入故障」是可比的配对。若故障注入本身改变了任务难度（比如注入故障的样本恰好更复杂），那 47% 会低估恢复能力。
  • 没有算恢复机制自身的成本：捕获 pre-state witness 要读原值、写日志、还要独立验证器再跑一遍——这些都要 token 与时间。「恢复表达力扩展 +30 个百分点」的收益要减去这套机制的开销才净，本文没算（缺数据）。
  • 四分类恢复策略我只用了「重试 vs 恢复」两种做对比，而讲者给的是四类（安全重试 / 恢复 / 补偿 / 升级求助）。补偿那一类（外部动作已提交）恰恰是最贵也最难自动化的一类，本文没有它的数据，所以漏斗模型低估了真实世界的恢复难度。
  • 故障率 1%、每天 100 次写操作全是估的，而「重复副作用」的真实代价取决于业务（重复工单可能只是脏、重复扣款是真金白银）——同一个技术故障在不同业务里的成本差几个数量级，本文只算了次数。

FAQ（八、常见问题）

恢复成功率 47% 是什么意思？ 分母是「原本会成功的试验」：2,880 次试验里正常成功 2,419 次，注入故障后恢复成功 1,137 次 → 相对正常执行只有 56%，即每 100 次本来会成功的执行，故障毁掉 44 次。

那重试呢？不行吗？ 朴素重试在 54% 的这类试验里制造了重复副作用（2,880 次里约 1,555 次）。失败率数字和恢复接近（54% vs 53%），但重试留下的是不可逆的脏数据，恢复失败只是「没恢复」。

重复副作用怎么估？ 54% 是「遇到故障后用重试」的副作用率，真正的乘数是故障率：每天 100 次写操作、故障率 1% → 每月 16 次重复副作用；5% → 81 次。所以要么降故障率，要么给重试加幂等键——只提升恢复率救不了没发生的故障。

42% 的恢复缺陷意味着什么？ 600 个自我进化任务里 478 个提升了能力，其中 **197 个（41.2%，讲者取整 42%）**带恢复缺陷 → 可接受改进只剩 281 个。恢复缺陷是能力侧投入的乘数：同样要拿 461 个可接受改进，能力侧原本得多做 64%。

补齐恢复能力值多少？ 扩展恢复语言后 197 个缺陷修好 180 个（约 92%），可接受改进从 281 升到 461（+30 个百分点）。换算下来：每 1 个百分点的恢复率 ≈ 2 个可接受改进。

为什么「只修一个瓶颈」没用？ 两个批次是互补的：只补状态接地修好 38/197（19%）、只补恢复表达力 142/197（72%）、两个都补 180/197（91%）。因为 38 + 142 = 180 正好是并集——按「先修一个看看」的顺序做，75% 的案例毫无进展。

那恢复到底该怎么做？ 分四种：什么都没变 → 安全重试；有原始状态 → 恢复；外部动作已提交 → 补偿机制；无法恢复或验证不通过 → 停下升级求助。而且「仅仅因为执行了 undo 命令，恢复就不算成功」——必须有独立验证者。

这些数字能外推吗？ 不能。UndoBench 与 EvoUndo 都是作者自建 benchmark，故障注入方式与任务分布未公开；「92% 恢复率」与「+30 个百分点」还来自不同子组。把它们当结构参考，别当基准值引用。
