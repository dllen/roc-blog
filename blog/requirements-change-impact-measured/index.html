「需求改一处要跟几处」：把架构直觉变成能每轮自动跑的命令

#软件工程#需求工程#架构#度量

需求工程的第一件事是直面本质复杂性、收缩意图空间里的不确定性。南京大学《生成式软件工程》第 7 讲的原话是：

说「课程容量为 100 人」还不够：候补学生算不算？跨院预留名额能不能借用？特殊批准能不能突破上限？补充这些条件，会减少实现者自行猜测的空间。

这句话看上去是常识，落到工程上却很难验收：「收缩意图空间」做得好不好，通常要等到实现出来、各页面开始各说各话的时候才看得见。 本文用一份课程练习代码把这件事变成可测量的：同一组请求喂给三个页面，看它们给出几个答案；再把「改一处要跟几处」做成一条每轮都能跑的统计命令。

一、三个空白，三种答案

讲义的三连问针对的都是同一个数字。下面这张表把每个空白、练习项目给出的答案、以及「不回答会怎样」并排放在一起：

讲义的追问练习项目的回答不回答会怎样
候补学生算不算？算。候补进入队列就占用名额，被退掉才释放各页面自己决定：选课页算、导入页不算，名单人数与占位人数长期对不上
跨院预留名额能不能借用？不能自动借用。预留只对外院开放，本院要等名额释放或走审批三个页面给三个答案：选课页只给外院、管理员页连本院也能用、导入页只数总数
特殊批准能不能突破上限？能，但必须留下批准依据；突破的是「授权」而不是业务规则一个没有来由的通过只是在隐藏复杂性，下次重新审核时仍然不知道为什么放行

练习项目还补了第四个空白：转专业或交换的学生，之前在外院修过的课算不算先修。它的答案是「算，但走认定记录这条独立通道」——认定记录是事实，不是特判分支。先修条件一旦写成「转专业学生特判」，就会越堆越乱，而且判定依据无处可查。

这三行不是纸面设计。练习代码把同一个选课系统实现了两遍：一遍是「Slop 版」（规则被抄进三个页面），一遍是「建模版」（三个入口调用同一组规则）。下面是把同一组请求喂给 Slop 版三个页面的实测输出（摘录）：

    选课页    小明 选 CS2101 → 选课成功
    选课页    小红 选 CS2101 → 拒绝：先修课程 CS1001 未完成
    选课页    小刚 选 MA2003 → 选课成功
    选课页    小刚 选 CS2101 → 选课成功
    管理员页  小红 补选 CS2101（认定单 #A12）→ 补选成功（未检查先修条件）
    管理员页  小华 补选 CS2101（教学院长审批）→ 拒绝：CS2101 容量已满
    导入页    批量导入 2 条 → 导入 2 条：成功 1；小华/CS2101 容量已满

  问题已经发生了（都能从上面这几行结果里读出来）：
    · 小刚 在选课页同时拿到了 MA2003 和 CS2101 —— 该页没有时间冲突检查
    · 小红 在选课页被先修条件挡住，在管理员页却直接放行 —— 该页根本不查先修
    · 跨院预留名额的判法三个页面各不相同：选课页只给外院，
      管理员页连本院也能用，导入页只数总数、完全不区分预留
    · 导入页不看重复与冲突，把小刚已经选过的 MA2003 又导入了一遍

读上面那七行请求结果就能读出问题：选课页放行了同时选 MA2003 和 CS2101 的小刚（该页没有时间冲突检查）；选课页以先修条件挡住的小红，在管理员页却直接放行（该页根本不查先修）；管理员页把小华挡在容量门外，导入页却只看总数。同一门课，三种判法。

换成建模版，同样的请求：

    选课入口  小明 选 CS2101 → 选课成功
    选课入口  小红 选 CS2101 → 小红 缺少先修课程 CS1001
    选课入口  小刚 选 MA2003 → 选课成功
    选课入口  小刚 选 CS2101 → CS2101 与已选的 MA2003 时间冲突
    补选入口  小红 补选 CS2101（认定单 #A12）→ 选课成功
    补选入口  小华 补选 CS2101（教学院长审批）→ 选课成功
    补选入口  小红 补选 CS2101（无依据）→ 拒绝：管理员补选必须写明批准依据
    导入入口  批量导入 2 条 → 共 2 条：成功 0，失败 2；小刚/MA2003 小刚 已经选过 MA2003，小华/CS2101 小华 已经选过 CS2101

差别不在于建模版更「聪明」，而在于它把「为什么失败、怎样修复」和判定本身放在一处，跨入口复用。建模版还多出一条约束：管理员补选必须写明批准依据，没有依据直接拒绝——这正是第一条空白里「批准依据」的落点。

二、收缩不等于把需求写长

讲义紧接着说了一句容易被跳过的话：需求也不是越长越好，每写下一条承诺，就多了一条需要检查、维护并在需求变化时重新审视的约束。一条约束实际上同时产生三类成本：

成本说明谁承担
检查成本这条约束要有能判断真假的方式。写不出检查方式，Agent 只能靠猜每一轮开发循环
维护成本约束变化时，所有引用它的地方都要重新审视需求变更时
模型成本约束要进上下文，占 token；条目越多，模型在组合条件下出错的概率越高每一轮生成

练习项目按「三条业务规则（资格 / 容量 / 冲突）合起来 12 行实现代码」的密度做了一个粗略估算（这是估算，不是实测）：约束 10 条 → 约 40 行实现、10 个检查项；约束 30 条 → 约 120 行实现、30 个检查项，外加一张 30 项的回归测试；而每次需求变更都要重新审视 30 处，漏掉一处不会报错，只会让业务自相矛盾。

估算之外还有一个判据更实用：该追问还是该停，看这个空白是否改变可被观察到的事实。

  • 该追问：不同的人会做出不同的决定，而且事后无法从系统里判断当初选的是哪一种。例：预留名额借不借——放行之后，名单上根本看不出这人是走了预留还是走了正式名额。
  • 该停：这个空白不影响任何可以被观察到的事实。例：内部日志格式、失败时的堆栈层级。这些该由实现者决定并写进代码，而不是让客户逐条确认。

一句话的判据是：「这条需求需要被检查吗？」如果不需要，就不该写进需求文档。

三、把「改一处要跟几处」变成一条命令

讲义给出的架构判断标准是：需求改了一处，系统里需要跟着改多少处？ 练习代码把这句话做成了一个可运行的门禁——--impact 会扫描两份实现，统计四条真实需求变更分别要动几处：

  需求变更：容量 —— 候补学生进入队列即占用名额
    [Slop 版] 需要动 3 处
            已有实现：admin_add.py(2 行)，batch_import.py(2 行)，student_select.py(3 行)
    [建模版] 需要动 1 处
            已有实现：capacity.py(4 行)
            → Slop 版要动 3 处，建模版要动 1 处（3 倍）

  需求变更：跨院预留 —— 预留名额在无人认领时可释放给本院
    [Slop 版] 需要动 3 处
            已有实现：admin_add.py(1 行)，batch_import.py(1 行)，student_select.py(4 行)
    [建模版] 需要动 1 处
            已有实现：capacity.py(2 行)
            → Slop 版要动 3 处，建模版要动 1 处（3 倍）

  需求变更：资格/先修 —— 转专业认定记录可以替代先修课成绩参与判定
    [Slop 版] 需要动 3 处
            已有实现：admin_add.py(1 行)，student_select.py(2 行)
            尚未实现：batch_import.py（改完其余地方后，这些页面仍然行为不一致）
    [建模版] 需要动 1 处
            已有实现：eligibility.py(3 行)
            → Slop 版要动 3 处，建模版要动 1 处（3 倍）

  需求变更：时间冲突 —— 选课期间的临时调课必须即时参与冲突判定
    [Slop 版] 需要动 3 处
            已有实现：admin_add.py(2 行)
            尚未实现：student_select.py，batch_import.py（改完其余地方后，这些页面仍然行为不一致）
    [建模版] 需要动 1 处
            已有实现：conflict.py(3 行)
            → Slop 版要动 3 处，建模版要动 1 处（3 倍）

    统计口径：一个「副本位置」= 业务规则被抄写的地方。
    Slop 版把三条规则抄进三个页面，每条规则有三个副本，所以任何一次
    需求变更都要逐页核对——漏掉一处不会报错，只会让页面看起来都正常、
    业务开始自相矛盾。建模版每条规则只有一个位置，改完即全局一致。

四条需求变更，Slop 版每次要动 3 处，建模版每次动 1 处，稳定的 3 倍。更值得注意的是「尚未实现」那一栏：第三、四条需求变更里，有的页面根本没抄这条规则。改完其余地方后，这些页面仍然行为不一致——而 CI 全绿、页面看起来都正常。漏改的那一处不会抛异常，它只会安静地给出另一个答案。

这件事完全可以做成一条每轮自动跑的检查。下面这段是把它抽出来的最小实现：规则用一句可搜索的标记串表示，统计每个「页面」抄了几处、漏了几处，以及改一次要跟几处。

def scan(pages, marker):
    copies = []
    missing = []
    for name, source in pages:
        if marker in source:
            copies.append(name)
        else:
            missing.append(name)
    return copies, missing


def main():
    marker = "rule_capacity("
    slop_pages = [
        ("student_select.py", "def check(sid):\n    if rule_capacity(sid):\n        return 'ok'\n"),
        ("admin_add.py", "def add(sid):\n    if rule_capacity(sid):\n        return 'ok'\n"),
        ("batch_import.py", "def imp(rows):\n    return [r for r in rows if not dup(r)]\n"),
    ]
    modeled = [
        ("rules/capacity.py", "def rule_capacity(sid):\n    return True\n"),
    ]

    totals = {}
    for label, pages in (("Slop 版", slop_pages), ("建模版", modeled)):
        copies, missing = scan(pages, marker)
        totals[label] = len(copies) + len(missing)
        print("{}：规则抄写 {} 处{}；改一次要跟 {} 处".format(
            label, len(copies),
            "，另有 {} 处未实现（{}）".format(len(missing), "、".join(missing))
            if missing else "，无遗漏",
            totals[label]))

    print("改一次要跟 {} 处 vs {} 处（{} 倍）".format(
        totals["Slop 版"], totals["建模版"],
        totals["Slop 版"] // max(totals["建模版"], 1)))
    print()
    print("注意：未实现的那几处不会报错，只会让同一门课在不同页面给出不同答案。")


if __name__ == "__main__":
    main()
Slop 版：规则抄写 2 处，另有 1 处未实现（batch_import.py）；改一次要跟 3 处
建模版：规则抄写 1 处，无遗漏；改一次要跟 1 处
改一次要跟 3 处 vs 1 处（3 倍）

注意：未实现的那几处不会报错，只会让同一门课在不同页面给出不同答案。

把它接到 CI 上的方式很直接：每次改需求时先跑一遍，输出里「改一次要跟 N 处」的数字变大或「未实现」的列表非空，就说明这次改动要么碰到了新的规则副本，要么有页面没跟上。这条检查不需要理解业务，只需要能搜到规则在哪。

四、搬到自己的项目：四步

拿到一句含糊的需求时，练习项目总结的四步可以直接照做：

  1. 找出所有会改变结果的解释。 把需求里的每个数字、每个形容词列出来，逐个问「有没有第二种理解」。例：「容量 100 人」→ 100 是硬上限还是初始值？候补算不算？
  2. 对每个解释，问「事后能不能追溯」。 两种解释产生同样的结果，这处空白不重要（写下默认值即可）；产生的结果不同却无法区分，这处空白必须现在收缩。
  3. 给每条收缩后的约束配一个检查方式。 写不出检查方式的约束，说明它还没想清楚，回到第 1 步。
  4. 数一遍总账。 约束总数 ×（检查成本 + 维护成本 + 上下文成本）。如果新增一条约束需要改动的位置超过 1 个，先考虑是不是该把它建模成一条独立规则，而不是写成一句散落在多个页面里的说明。

第 4 步就是上面那条命令在做的事：把「改一处要跟几处」从架构直觉变成一个每轮都能跑的数。 这也正是第 7 讲（需求与架构）与第 8 讲（Agent Native 开发）的衔接点——架构质量的判据可以变成门禁，门禁就可以交给 Agent 跑。

五、哪些是实测，哪些不是

  • 实测（本次运行 course_select.py --demo 与 --impact 的输出，摘录于文中）：三个页面给出三种答案、三种日期格式、同一份学生信息存五份；四条需求变更的改动点统计（3 处 vs 1 处）；其中两条需求变更存在「尚未实现」的页面。输出是确定性的——同一份代码连跑两次输出逐字节相同。
  • 估算（不是实测）：「三条规则 12 行实现」推出的 10 条/30 条约束的实现规模与检查项数量；以及「模型在 30 条组合约束下的正确率明显低于 3 条」这一说法，属于讲义的定性判断，本文没有复现。
  • 练习代码不是生产系统：它是课程练习里的教学示例，用固定的学生与课程数据演示两种架构，规则本身简单到能一眼看完。它的价值在于把判据说成可运行的度量，而不是示范真实业务该有多复杂。
