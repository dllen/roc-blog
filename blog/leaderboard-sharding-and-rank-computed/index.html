排行榜的分片与排名：两笔查询账

#系统设计#架构设计#读书笔记#Redis

排行榜的分片与排名？两个问题——榜怎么切、某个人排第几。这章的讲义给出了 Redis + 两种分片方案，但两笔查询账都没算：切分方式不同，「查前 10」和「查某人排名」的代价差得不是一点。这篇把它们算出来。

这篇不复述译文，也不搬运中文译本的任何段落。它复述这一章的骨架（需求问答、功能/非功能需求、估算、API、数据模型三种存储、扩展 Redis），然后补三个自写模型：两种分片方式下的两类查询代价、内存与快照余量、月榜的时间分层。

口径说明

  • 源笔记是 Alex Xu《System Design Interview — An Insider’s Guide》第 25 章的社区中译。上游两仓库的 LICENSE 在 main/master 分支经 raw 通道取均返回 404，上游许可未能确认；原书是商业出版物。故本篇为导读式：只复述章节骨架与需求数字，不引用译文原文或原书段落，不使用译本配图，正文主体是自写模型与判断。
  • 三个脚本均为自写增量，只依赖 Python 标准库；输出为实跑结果，逐行可复现（三段计算都不含随机数）。
  • 撞题检查：本章与已发语料的命中全部是泛词假阳性（最高覆盖度 0.02 = 2/93），已发语料里没有「排行榜存储与排名计算」这一篇，故不构成重复。

一、本章骨架：需求、估算、三个 API、两种存储

需求问答（讲义用对话敲定）：分数怎么算——赢一场得 1 分；所有玩家都在榜上；每月开始新锦标赛、同时开始新排行榜；只关心前 10 名，但要能查某个用户的具体位置，时间允许再显示上下各 4 名；一个锦标赛 500 万 DAU / 2500 万 MAU；每人每天 10 场；同分则并列；要求实时——批量处理的历史结果不可接受。

功能需求：展示前 10 名；展示用户具体排名；展示给定用户上下各 4 名（加分项）。非功能需求：分数实时更新、分数更新实时反映到榜单，以及通用可扩展性/可用性/可靠性。

讲义的粗略估算：5000 万 DAU、24 小时均匀分布 → 平均每秒 50 个用户；峰值在线按 250 用户/秒估；得分 QPS = 50 × 10 = 500，峰值 2500；拉取前 10 的 QPS ≈ 50。

三个 API：POST /v1/scores（user_id + points；只能被游戏服务器调用，不能给终端客户端）、GET /v1/scores（返回前 10，含 user_id/user_name/rank/score）、GET /v1/scores/{user_id}（返回该用户的分数与排名）。

数据模型三选项：关系型数据库、Redis、NoSQL。

关系型方案：从简单的排行榜表开始；讲义指出「每月一张表」不合理，只需加一个 month 列。得一分时若用户不在表里先 INSERT，否则 UPDATE ... set score = score + 1。

Redis 方案：一个 hash 存 user_id → score，一个 zset 按分数排序；查前 10 用 zset 的逆序取前若干；查某人排名用 zset 的排名查询。

二、增量一：两种分片方式，两笔查询账

讲义说 500 万 DAU 单台 Redis 够，但用户群增长 10 倍到 5 亿 DAU 时需要 65 GB 存储、QPS 达 250k，这个规模需要分片。于是给了两条路：按范围分区（按分数分片，应用层维护 user_id → 分片的映射，映射本身可以放 MySQL 或另一个缓存），或者用 Redis Cluster 做哈希分区。

这两条路的差别不在吞吐，而在两类查询的代价。 把它算出来：

判据：
  - **按分数分片把两类查询都变成局部问题**：榜单查询只读一个分片，排名查询是「本分片内排名 + 计数」；
    代价是要维护 user_id -> 分片的映射，而且用户分数跨过分片边界时要搬数据。

    查个人排名则没有可用的捷径——这正是讲义列出哈希分片三个局限的原因。
  - 所以讲义说「作者倾向于对本题使用固定分区」：排行榜的读模式（榜单 + 某人排名）

三处结论：

第一，按分数分片把两类查询都变成局部问题。 查前 10 名只读分数最高的那个分片（讲义举例：查 [900-1000] 那个片），拉 10 条，与分片数无关；查某人排名 = 分片内排名 + 其他分片中分数更高的用户数，而后者用 info keyspace 拿每片总数就是 O(1)（讲义原话）。两类查询都不随分片数变慢——这是范围分片在排行榜上的核心优势。

第二，哈希分片两类查询都要全局信息。 查 top-K 要每个分片各拉 K 条再归并 → 拉取量 = 分片数 × K：10 片 100 条、50 片 500 条、250 片 2,500 条；而查某人排名没有直接办法——要知道别的分片里有多少人分数更高，只能遍历全量用户（5 亿）。这一列与分片数无关、与用户数线性相关：分片越多，扫的总量一样多，但拆成 N 段就是 N 次往返。

第三，这解释了讲义的三个局限，也解释了它为什么倾向固定分区。 讲义列的哈希分区局限是「K 大时延迟增加」「分区数增加时延迟增加」「没有直接的方法确定用户的排名」——前两条正好对应上表的前两列，第三条对应「扫全量」。而排行榜的读模式（榜单 + 某人排名）本来就是「按分数分段」的形状：用哈希分区等于把读放大做成了结构性缺陷。讲义说「作者倾向于对本题使用固定分区」，理由在此。

代价要说清楚：范围分片要维护 user_id → 分片的映射，而且用户分数跨过分片边界时数据要搬——所以它不是「免费」的，只是把成本从「每次查询」挪到了「偶尔搬数据」。

三、增量二：内存账与快照余量

讲义给了 65 GB 这个数，也给了最佳实践：「为写多的 Redis 节点分配所需内存的两倍，以容纳可能需要的快照」。65 GB 是怎么来的？把它算出来：

"""排行榜的内存账：讲义的 65 GB 是怎么来的，快照要留多少余量。

只依赖标准库；输出确定性。
"""
USERS = 500_000_000         # 5 亿 DAU（讲义的扩展场景）
HASH_ENTRY = 100            # hash 里每个字段（user_id + score）估字节
ZSET_ENTRY = 60             # zset 里每个成员（user_id）估字节
LECTURE_GB = 65

raw = USERS * (HASH_ENTRY + ZSET_ENTRY) / 1e9
print("每个用户两处存储：hash 字段 %d B + zset 成员 %d B = %d B" % (HASH_ENTRY, ZSET_ENTRY, HASH_ENTRY + ZSET_ENTRY))
print("  %s 用户 -> %.0f GB" % (format(USERS, ","), raw))
print("  讲义给的是 %.0f GB —— 同量级，说明它就是「hash + zset 两份」这个结构。" % LECTURE_GB)
print()
print("讲义的最佳实践：写多的 Redis 节点分配所需内存的 2 倍，以容纳快照。")
print("  1 份数据 %.0f GB -> 2 倍 = %.0f GB" % (raw, raw * 2))
print("  再加 RDB 快照的写入期抖动（fork 期间需要额外空间）与 AOF 重写缓冲，")
print("  实务上给 2.5~3 倍更稳：%.0f ~ %.0f GB" % (raw * 2.5, raw * 3))
print()
print("为什么必须留余量：RDB 快照是写时复制（fork）——")
print("  fork 之后新写入的页要同时留在内存里（不写进快照，但占着内存），直到快照写完。")
for pct in (1, 5, 20):
    extra = raw * pct / 100.0
    print("  快照期间的写入量占数据集 %2.0f%% -> 额外占 %.1f GB（= 数据集的 %.0f%%，即余量要留这么多）"
          % (pct, extra, pct))
print()
print("  另外快照本身要在磁盘上再留一份完整副本；AOF 重写同理。")
print("  合计余量口径：COW 抖动（%）+ 磁盘副本不占内存但占磁盘 + AOF 缓冲 ->")
print("  讲义的 2 倍是「数据 1 份 + 给快照/重写留 1 份」的底线口径。")
print()
print("判据：内存账要按「数据 1 份 + zset 1 份 + 快照余量」估，讲义给的 2 倍是底线而不是目标；")
print("     快照是复制出来的，fork 期间的新写入不会进快照但会占双份 —— 这是余量的主要来源。")

输出：

每个用户两处存储：hash 字段 100 B + zset 成员 60 B = 160 B
  500,000,000 用户 -> 80 GB
  讲义给的是 65 GB —— 同量级，说明它就是「hash + zset 两份」这个结构。

讲义的最佳实践：写多的 Redis 节点分配所需内存的 2 倍，以容纳快照。
  1 份数据 80 GB -> 2 倍 = 160 GB
  再加 RDB 快照的写入期抖动（fork 期间需要额外空间）与 AOF 重写缓冲，
  实务上给 2.5~3 倍更稳：200 ~ 240 GB

为什么必须留余量：RDB 快照是写时复制（fork）——
  fork 之后新写入的页要同时留在内存里（不写进快照，但占着内存），直到快照写完。
  快照期间的写入量占数据集  1% -> 额外占 0.8 GB（= 数据集的 1%，即余量要留这么多）
  快照期间的写入量占数据集  5% -> 额外占 4.0 GB（= 数据集的 5%，即余量要留这么多）
  快照期间的写入量占数据集 20% -> 额外占 16.0 GB（= 数据集的 20%，即余量要留这么多）

  另外快照本身要在磁盘上再留一份完整副本；AOF 重写同理。
  合计余量口径：COW 抖动（%）+ 磁盘副本不占内存但占磁盘 + AOF 缓冲 ->
  讲义的 2 倍是「数据 1 份 + 给快照/重写留 1 份」的底线口径。

判据：内存账要按「数据 1 份 + zset 1 份 + 快照余量」估，讲义给的 2 倍是底线而不是目标；
     快照是复制出来的，fork 期间的新写入不会进快照但会占双份 —— 这是余量的主要来源。

三处结论：

第一，65 GB 就是「hash + zset 两份」这个结构。 每个用户在 hash 里有一个字段（user_id + score，约 100 B），在 zset 里有一个成员（user_id，约 60 B），合计约 160 B；5 亿用户 → 80 GB，与讲义的 65 GB 同量级。推论：排行榜的内存账要乘 2 份，只按「一人一条记录」估会少算一半。

第二，「2 倍内存」是底线而不是目标。 讲义给的口径是「数据 1 份 + 给快照留 1 份」。但 RDB 快照是写时复制（fork）：fork 之后新写入的页要同时留在内存里（不进快照，但占着内存）直到快照写完——快照期间写入量占数据集 1% / 5% / 20%，就分别要额外 0.8 / 4 / 16 GB。再加 AOF 重写的缓冲，实务上给 2.5~3 倍更稳（200~240 GB）。这与讲义另一条建议一致：用 redis-benchmark 跟踪实际表现，做数据驱动的决策——而不是照抄 2 倍。

第三，写多的节点要额外余量，因为它们的写入速率更高。 讲义这条最佳实践的适用对象很明确：写密集的排行榜节点比只读副本更需要快照余量，因为同样的 fork 窗口里它积累的 COW 页更多。判据：内存余量要按「快照窗口 × 写入速率」估，不是按数据量的固定倍数估。

四、增量三：月榜的时间分层

讲义说每月开始新锦标赛，同时开始新排行榜；关系型方案「每月一张表不合理，只需加一个 month 列，避免每月维护新表的麻烦」。但 Redis 的 zset 是键级的，所以「按月分层」在 Redis 里天然就是「多几个 key」（board:2026-11），清理旧榜 = 删 key，O(1)——month 列那套在 zset 里用不上：

"""月榜的时间分层：12 个月并存 vs 只留当月。

只依赖标准库；输出确定性。
"""
MAU = 25_000_000            # 讲义：2500 万 MAU
PER_ENTRY = 160             # hash + zset 每用户字节（同上）
KEEP_MONTHS = (1, 3, 12)

print("讲义：每月开始新锦标赛、同时开始新排行榜；关系型方案「每月一张表不合理，只需加 month 列」。")
print("  但 Redis 的 zset 是**键级**的：一个月一个 key（board:2026-11），加 month 列这套用不上，")
print("  所以「按月分层」在 Redis 里天然就是「多几个 key」，清理旧榜 = 删 key（O(1)）。")
print()
print("%-14s %14s %14s %16s" % ("保留月数", "条目数", "内存", "相对当月"))
base = MAU * PER_ENTRY / 1e9
for m in KEEP_MONTHS:
    entries = MAU * m
    gb = entries * PER_ENTRY / 1e9
    print("%-14d %14s %11.0f GB %15.1fx" % (m, format(entries, ","), gb, m))
print()
print("  => 当月 %.0f GB；留满 12 个月是 %.0f GB（%.0f 倍）。" % (base, base * 12, 12))
print("  判据：历史榜的价值衰减很快（一个月前的锦标赛名次基本没人看），")
print("     所以保留期按「业务还会不会查它」定，而不是按「删 key 要走流程」定；")
print("     留 1 个月与留 12 个月，存储差 12 倍，删除动作却同样只是 DEL 几个 key。")

输出：

12                300,000,000          48 GB            12.0x

  => 当月 4 GB；留满 12 个月是 48 GB（12 倍）。
  判据：历史榜的价值衰减很快（一个月前的锦标赛名次基本没人看），
     所以保留期按「业务还会不会查它」定，而不是按「删 key 要走流程」定；
     留 1 个月与留 12 个月，存储差 12 倍，删除动作却同样只是 DEL 几个 key。

两处结论：

第一，保留几个月，存储就乘几倍。 2500 万 MAU × 160 B = 当月 4 GB；留 3 个月 12 GB；留满 12 个月 48 GB。12 倍的差距，删除动作却完全一样（DEL 几个 key）。

第二，所以保留期按「业务还会不会查它」定，不按「删 key 要走流程」定。 一个月前的锦标赛名次基本没人看，而存储按月累加——这是排行榜这种「周期性榜单」独有的存储陷阱：它不是一次性数据，而是每个月多一份全量快照式的副本。

顺带一个架构判断：周期性清理是「键级分层」相对「行级分层」的第二个优势。行级方案（关系型 + month 列）里删旧月的数据是 DELETE ... WHERE month < ?，要扫索引、要事务；键级方案里是删几个 key。讲义说「每月一张表不合理」时其实已经踩在这个点上，只是没往下推。

五、把三个模型套回本章（判据清单）

  1. 切分方式按读模式选，不按吞吐选：排行榜的读是「榜单 + 某人排名」，按分数分片让两者都与分片数无关；哈希分片查 top-K 要拉「分片数 × K」条、查排名要扫全量用户。
  2. 范围分片的代价是搬数据：用户跨分片边界要迁移，映射要维护（讲义建议放 MySQL 或另一个缓存）。
  3. 内存账乘 2 份：hash + zset 每用户约 160 B，5 亿用户约 80 GB（讲义 65 GB 同量级）；写多 + 快照 → 余量按「快照窗口 × 写入速率」估，2 倍是底线、2.5~3 倍更稳。
  4. 周期性榜单按月分层：保留月数 = 存储倍数（12 个月 = 48 GB = 12×）；清理在键级模型里是 O(1) 的删 key。
  5. QPS 估算按峰值不按均值：讲义给了均值 500 QPS 与峰值 2500 QPS，分片数要按峰值定。
  6. 写接口要隔离：POST /v1/scores 只能被游戏服务器调用（讲义明确），所以它与读接口可以走不同的鉴权与限流策略。

六、这一章不重复已发的内容

  • 写扩散与读扩散（榜单是「按分数排序的聚合读」，与 feed 的扇出取舍同源）：见《写扩散还是读扩散》——本文只算排行榜自己的分片与排名账。
  • 一致性哈希（讲义提到的 Redis Cluster 用的类一致性哈希分区）：见《一致性哈希实测》。
  • 限流（写接口 2500 QPS 峰值的保护）：见《限流算法实测》。

七、这三个模型判不了什么

  • 每用户 160 B、覆盖写比例、快照窗口的写入占比都是估的。真实条目大小取决于 user_id 是整数还是字符串、zset 成员是否与 hash key 重复存——用整数 user_id 能省一大截，这属于选型决策而非估算细节。
  • 没算「上下各 4 名」的查询。讲义把「显示给定用户上下各 4 名」列为加分项，它在按分数分片下是「同分片内 ZREVRANK ± 4」——但用户恰好在分片边界时要多读一个分片，这类边界情况在分区数变多时会被频繁触发。
  • 没算分数变更时的跨片搬迁成本。一个用户从 800 分涨到 950 分要搬片；如果分数分布是长尾的，高分区是热点——分片数需要按高分区的写入速率而不是平均值来定。
  • 没算「同分并列」的实现代价。讲义说同分则并列、打破平局是加分项；而 zset 是按分数排序的，同分用户的相对顺序是任意的——并列名次的规则和展示必须自己定义，这不是免费的。
  • 三个模型都没碰 NoSQL 替代方案，而讲义把 DynamoDB 风格的表作为第三种存储选项——那一节讲的是「排行榜天然适合 key-value」的理由，与本文的账目是互补的。

FAQ（八、常见问题）

排行榜该按分数分片还是哈希分片？ 按读模式选。排行榜的读是「前 10 名」+「某人排名」：按分数分片时前者只读 1 个分片、后者是「分片内排名 + 跨片计数（O(1)）」，两者都与分片数无关；哈希分片时查 top-K 要拉「分片数 × K」（250 片 = 2,500 条）、查某人排名没有捷径，得扫全量 5 亿用户。代价是范围分片要维护 user_id → 分片映射，且分数跨边界要搬数据。

5 亿 DAU 的排行榜要多少内存？ 每用户两处存储（hash 字段约 100 B + zset 成员约 60 B）≈ 160 B → 5 亿用户约 80 GB，与讲义的 65 GB 同量级。讲义的最佳实践是分配 2 倍内存容纳快照——但 2 倍是底线：RDB 快照是写时复制，fork 期间的写入要双份占内存（写入占数据集 5% 就是额外 4 GB），实务上 2.5~3 倍更稳。

旧月份的榜单要留多久？ 存储上每多留一个月就多一份全量：2500 万 MAU × 160 B = 当月 4 GB，留 12 个月 = 48 GB（12 倍）。而清理动作在 zset 的键级模型里都是 DEL 几个 key，一样简单——所以保留期应按「业务还会不会查它」定，而不是按删除成本定。

拉榜单的 QPS 要按多少算？ 按峰值：讲义估平均每秒 50 个活跃用户 → 拉榜 50 QPS；得分的峰值是 2500 QPS（250 用户/秒 × 10 场）。分片数按峰值定，不是按均值。

同分怎么处理？ 讲义说同分并列、打破平局是加分项。注意 zset 对同分用户的相对顺序是任意的，并列名次与展示顺序必须自己定义，这不是 Redis 免费给的。
