让 Skill 更强并落地团队：sidecar 扩展与「idea→ship 主线」

#AI#Agent Skills#Claude#SRE#系列教程

本文是 Agent Skills 系列教程第 5 篇，也是收官之作。前四篇铺完了一条完整的路：第 1 篇说 Agent 是「没有记忆的新人」，codebase 结构决定它的产出质量；第 2 篇说结构该怎么改——深模块把接口做窄，灰盒模块把「人定接口、AI 管实现、测试锁行为」固定下来；第 3 篇给了写 skill 的三条规则——分层架构、命名约定、「skill 不必长」的克制；第 4 篇拿这套规则写出了一个能跑的 incident-diagnosis skill。这一篇回答最后两个问题：一个 skill 写完之后，怎么让它更强、更经得起真实故障的检验？以及，当 skill 不止一个时，怎么把它们串成一条「idea→ship」的主线，真正落进团队？

答案分三步。第一步是扩展——给 incident-diagnosis 装上 sidecar（references/、scripts/、agents/），让它在不臃肿的前提下覆盖深水区；第二步是组合——用五个 skill 跑通一条从「盘问需求」到「ship 代码」的主线，演示第 3 篇那句「主线是脊椎，塑形/维护喂养它」在实战里长什么样；第三步是落地——把这一整套装进团队，附一张 adoption 清单，让你能照着打勾。

为什么要拆分：渐进式披露

第 4 篇写出来的 incident-diagnosis，正文只有三段、不到 40 行——一段原则、一段六步循环、一段三条铁律。它是刻意「克制」的产物，呼应第 3 篇那条硬规则：skill 不必长，每一句都要在干活时真的用得上。 但克制不是「不完整」。真实世界里的一次线上故障排查，会碰到大量具体到「只有背过手册才知道」的深水区知识：Kafka 消费积压怎么分层排查、JVM 各种 OOM 怎么区分取证、数据库慢查询先看什么后看什么。这些东西如果全塞进 SKILL.md 正文，那个不到 40 行的骨架就会被撑爆成几百行，Agent 每次触发都要把这几百行全部读进上下文——你的克制就白费了。

怎么解决这个「要完整、又不能臃肿」的矛盾？答案就是第 2 篇和第 3 篇反复出现的那个词：渐进式披露（progressive disclosure）。 它的核心思想是：正文只写「什么时候用、按什么骨架走」，深水区的细节放到 references/ 里按需加载。 Agent 触发 skill 时，先读到的只是 SKILL.md 那个骨架；只有当循环真的走到「取证」这一步、真的面对一个 Kafka 积压现象时，它才去翻 references/kafka-backlog.md。没遇到的问题，手册就安静地躺在磁盘上，一分 token 都不占。

这正好呼应第 2 篇的「灰盒模块」哲学。灰盒的本质是人定接口、AI 管实现——你定下「六步循环」这个接口，AI 负责每一步的「具体怎么查」。而 sidecar 就是把这个分工往前又推了一步：接口（骨架）留在正文，实现（具体排查清单）下沉到 references/。 骨架不变，手册可以随时增删改，这就是深模块说的「接口做窄、实现藏深」——调用方（Agent 的排查循环）只需要知道「有手册可查」，不需要把手册背下来。

除了 references/，这个 skill 还需要另外两类 sidecar。一类是 scripts/——把「聚合多个日志文件里的错误行」这种重复手工操作固化成脚本，让 Agent 直接调用而不是每次手写一串 grep；一类是 agents/——放一个「假设评审」子代理，在排查循环最危险的「建立假设」环节，给 Agent 自己的猜测上一道对抗式的挑错。三类 sidecar 各司其职：references 补知识，scripts 补操作，agents 补判断。

装上这三类 sidecar 之后，incident-diagnosis 的最终目录树长这样：

incident-diagnosis/
├── SKILL.md                      # 六步循环 + 三条铁律（第 4 篇）
├── references/
│   ├── kafka-backlog.md          # Kafka 积压排查手册
│   ├── jvm-oom.md                # JVM OOM 排查手册
│   └── db-slow-query.md          # 慢查询排查手册
├── scripts/
│   └── tail-errors.sh            # 多日志错误聚合
└── agents/
    └── hypothesis-reviewer.md    # 假设对抗式评审子代理

可以看到，SKILL.md 依然是那个短小的骨架，一切的「重」都被塞进了 sidecar。这就是渐进式披露想要的结果：skill 大而不臃肿，完整却不占上下文。 下面逐个展开这三类 sidecar 的内容，每一个都是完整文件，你可以直接复制进自己的 skill 目录。

references/：三本排查手册

references/ 是渐进式披露的主战场。它的文件有一个统一的形态：不是教程，是查表清单。 一篇好的排查手册，应该让你（或 Agent）在故障现场「对着现象翻条目」，而不是「从头读一篇科普」。所以三本手册用了同一个模板，每一本都分四段：先确认（把现象分类，判断方向）、按概率排查（按发生频率从高到低列出检查点）、止损（先止血的动作，按顺序）、回归（修复后怎么确认真的好了）。

这个模板不是随手定的，它和第 4 篇 SKILL.md 的六步循环严格咬合。循环里的「取证」一步，要求 Agent「用日志、指标、trace、dump 验证排第一的假设」——但验证一个 Kafka 积压假设、和验证一个 JVM OOM 假设，看的完全是两套东西。手册就是在这里被按需调起的：Agent 走到「取证」时，看手上是什么现象，就翻对应哪一本，按「按概率排查」的清单逐条取证。 换句话说，SKILL.md 给的是「该先确认再取证」的纪律，手册给的是「取证时具体看什么」的实现。

下面是第一本手册的全文。

# Kafka 消息积压排查手册

消费积压（consumer lag）飙升时的排查清单。

## 先确认
- 是生产突增还是消费变慢？看 `kafka-consumer-groups --describe` 的 LAG 变化斜率。
- 是单分区积压还是全部分区？单分区 = 分区热点，全分区 = 消费端整体问题。

## 按概率排查
1. **消费端慢了**：消费线程池打满 / 下游 DB 慢 / 每批处理时间变长。看消费端 CPU、GC、下游调用 P99。
2. **消费者 Rebalance**：频繁 rebalance 让消费暂停。看 `max.poll.interval.ms` 是否被长处理打穿。
3. **生产突增**：上游流量翻倍。看生产 QPS 曲线。
4. **分区热点**：某个 key 倾斜。看分区维度 LAG 分布。

## 止损动作（按顺序）
1. 扩分区 / 加消费者（先评估是否解决热点）。
2. 临时提高消费并发。
3. 若下游慢，先给下游降级或限流。

## 修复后的回归
- 观察 LAG 回落到正常水位并稳定 30 分钟以上。

注意两个细节。第一个是「先确认」里的两问——生产突增还是消费变慢、单分区还是全分区——它们不是排查步骤，而是分类：先给现象归了类，后面「按概率排查」的四条才有了先后顺序（消费端慢了排第一，因为最常见）。这正是第 4 篇「缩小范围」在手册里的具体化：先二分，再深挖。第二个是「止损动作」标了「按顺序」——先扩分区加消费者，再提高并发，最后才给下游降级。止损的顺序就是「先恢复、再追根」原则在 Kafka 场景下的落点。

剩下两本手册用的是同一个模板，只换内容。一本管 JVM，一本管数据库。

# JVM OOM 排查手册

OutOfMemoryError 的排查清单。

## 先拿现场
- 确认是堆 OOM 还是 Metaspace / 直接内存 OOM（看异常类型）。
- 若启用了 `-XX:+HeapDumpOnOutOfMemoryError`，先取 dump 再重启。

## 按概率排查
1. **堆 OOM**：看 `jmap -histo` 的 Top 大对象，是否某集合/缓存无界增长。
2. **Metaspace OOM**：是否动态生成类过多（反射/CGLib/热部署）。
3. **直接内存 OOM**：是否 Netty/堆外缓存未释放，`-XX:MaxDirectMemorySize` 是否过小。
4. **GC 频繁但回收不掉**：是否存在内存泄漏，对比 `jstat -gcutil` 多次采样的老年代占用。

## 止损
- 能重启先重启保命（但先留 dump/日志）。
- 定位到泄漏点后按最小改动修复。

## 回归
- 重启后观察老年代占用曲线是否稳定，不再线性上涨。

这本手册的第一段叫「先拿现场」而不是「先确认」，因为 OOM 的现场是会消失的——一旦重启，dump 和日志没了，根因就再也追不回来。「先取 dump 再重启」这一条，是把「止损」和「取证」的先后顺序钉死了：止损（重启保命）可以，但必须先把证据留下来。这是排查 JVM 故障最容易被跳过的动作，写进手册的第一段，就是为了让 Agent 不会在「赶紧重启」的冲动里丢掉唯一的证据。

# 数据库慢查询排查手册

接口变慢、DB 连接池打满时的排查清单。

## 先确认
- 是单条 SQL 慢还是整体 QPS 太高？看慢查询日志 vs 连接池活跃数。
- 是突然变慢还是持续慢？突然 = 数据量/索引/执行计划变化，持续 = 设计问题。

## 按概率排查
1. **缺索引 / 索引失效**：`EXPLAIN` 看是否全表扫描、是否隐式类型转换导致索引失效。
2. **锁等待**：看 `information_schema.innodb_trx` / 行锁，是否长事务阻塞。
3. **数据量陡增**：是否某张表突然写入放大。
4. **连接池打满**：看是否慢 SQL 占住连接、是否有连接泄漏。

## 止损
- 先 kill 阻塞的慢查询 / 长事务。
- 紧急加索引（评估写放大）或加缓存。

## 回归
- 复跑 `EXPLAIN` 确认走索引；观察慢查询日志该 SQL 消失。

三本手册摆在一起，能看出同一个原则的三次复现：先分类、再按概率排、先止血、后回归。 这也是为什么手册要「按概率排查」而不是「穷举所有可能」——排查的本质是「用最少的取证动作，最快收敛到根因」，而概率排序就是那个收敛的顺序。如果你愿意，可以照这个模板无限扩张：加一本 Redis 热 key、加一本消息积压、加一本内存泄漏——每一本都只占 references/ 里一个文件，不会让 SKILL.md 多一个字。

scripts/：日志聚合脚本

references/ 补的是「知识」，scripts/ 补的是「操作」。排查手册里反复出现同一类动作：从一堆日志文件里把错误行捞出来，看哪个错误出现得最多。 这个动作人肉做，就是一行 grep 加一堆 sort、uniq、head 的管道；让 Agent 做，它每次都要现场把这串命令重新想一遍、拼一遍，还可能拼错。把这种「稳定、可复用、容易拼错」的操作固化成脚本，是 scripts/ 存在的全部理由。

下面是 scripts/tail-errors.sh 的全文。

#!/usr/bin/env bash
# 聚合多日志文件中的错误行，去重后按出现次数排序，快速看清"主要错误是哪个"
# 用法: tail-errors.sh 'ERROR|Exception' /var/log/app/*.log
set -euo pipefail

pattern="${1:?用法: tail-errors.sh <pattern> <logfile...>}"
shift

grep -hE "$pattern" "$@" 2>/dev/null \
  | sort | uniq -c | sort -rn | head -50

这个脚本只有十几行，做的事情一句话就能说清：拿一个错误匹配模式、若干日志文件，输出「去重后按出现次数排序」的前 50 条错误行。 它落在排查循环的「取证」环节——当 Agent 面对「error 率飙升」时，与其一条条看日志，不如先跑 tail-errors.sh 'ERROR|Exception' /var/log/app/*.log，几秒内看到「哪个错误最密集」，取证的方向立刻就有了。「主要错误是哪个」这个问题的答案，往往就是下一步建立假设的第一候选。

几个细节值得点一下。set -euo pipefail 保证脚本在出错时不继续往下跑（-e）、引用未定义变量时报错（-u）、管道里任何一步失败都算失败（-o pipefail）——这是运维脚本的基操，也把「脚本不会静默地给你一个错的结果」这个保证固化了下来。pattern="${1:?...}" 则在调用者忘了传参数时直接报用法，而不是跑到一半才发现少了个变量。这些不是炫技，是让脚本在凌晨三点的生产环境里可以被信任。 至于 2>/dev/null，它把「某些日志文件读不到」这种噪声吞掉，让输出只剩真正有用的错误行。

把脚本放进 skill 而不是写进文档，还有一个容易被忽略的好处：文档里的一串命令，Agent 要「读懂再复现」，中间可能抄错；脚本是一个可执行的实体，Agent 直接调用，不存在「复现」这一步。 这和第 3 篇「把流程编码成路径」是同一件事的两种形态——skill 正文把「该做什么」编码成了步骤，scripts/ 把「怎么做的具体动作」编码成了可执行文件。

agents/：假设评审子代理

references/ 补知识、scripts/ 补操作，agents/ 补的是判断。在六步循环里，最危险的一步不是「取证」，而是「建立假设」——因为 Agent 一旦在这里认准了一个错误的方向，后面所有取证都会变成「为这个错误假设找证据」的自我强化。人也会有这个毛病，但人还有直觉和「以前踩过坑」的经验兜底；Agent 没有记忆，它更容易在第一个看似合理的假设上一条道走到黑。

怎么防？答案是引入对抗：不让 Agent 一个人既是「提出假设的」又是「评审假设的」，而是给它配一个专门挑毛病的子代理。这就是 agents/hypothesis-reviewer.md 的由来。

---
name: hypothesis-reviewer
description: 对故障排查中的根因假设做对抗式评审，找出最可能被证伪的漏洞
---

你是资深 SRE，负责挑战一个故障根因假设。

对给定的假设，逐一检查：
1. **可证伪性**：这个假设能被什么观察证明是错的？
2. **证据链**：现有证据（日志/指标/trace）是否真的支持它，还是只是"相关性"？
3. **遗漏**：有没有更简单的解释能覆盖同样的事实？

输出：该假设的置信度（高/中/低）+ 最致命的漏洞 + 建议的下一个取证动作。

这个子代理的全部工作，就是三问。第一问「可证伪性」——一个假设必须能说出「什么观察能证明它错」，否则它就不是假设，是信仰。「大概是网络问题」没法证伪，所以没价值；「如果是新版本引入的，回滚后 error 率应该下降」能证伪，才有资格往下走。第二问「证据链」——现有证据和假设之间，是「因果」还是「相关」？日志里同时出现了 A 和 B，不等于 A 导致了 B。第三问「遗漏」——有没有一个更简单的解释能覆盖同样的事实？这问专治「复杂假设」，因为排查里最常见的坑，就是把一个简单的「缓存过期」解释成一场复杂的「分布式事务雪崩」。

三问过后，子代理输出的不是一个「对不对」的结论，而是三个东西：置信度（高/中/低）+ 最致命的漏洞 + 下一个取证动作。 这个输出设计得很克制——它不替主 Agent 做决定，只给主 Agent 一个「你的假设哪里最可能翻车、下一步该取什么证」的提示。这就是「对抗」和「替你做主」的区别：评审者是顾问，不是上司。 主 Agent 依然掌控六步循环，只是在「建立假设」之后多了一道被质疑的关卡。

为什么把它做成 agents/ 子代理，而不是再写一段正文？因为评审需要换一个角色立场——正文里的 Agent 是「排查者」，天然偏向「我的假设是对的」；子代理是「挑战者」，天然偏向「找你的漏洞」。同一个模型，两个不同的角色设定，就能产生对抗。 这比在正文里加一句「记得质疑自己的假设」有效得多，因为那句自我提醒，恰好是 Agent 最容易在「顺着假设跑」的时候忘掉的。

「idea→ship 主线」：五个 skill 串成一条脊椎

到这里，incident-diagnosis 被扩展成了一个「大而不臃肿」的 skill。但一个 skill 再强，也只是「在一件事上可靠」。这一节回到第 3 篇埋下的那个问题：当 skill 不止一个时，怎么把它们串成一条「idea→ship」的主线？

第 3 篇的分层架构给过一个总纲：主线（Main Flow）是脊椎，Shaping/Upkeep 喂养它，Reference 是共享层。 这句话当时是抽象的，现在用一条真实的「从需求到代码」的流程把它走一遍，你就知道「脊椎」和「喂养」在实战里到底长什么样。

这条主线由五个 skill 依次组成，对应「把一个想法变成 shipped 的代码」的五个阶段：

第一步：/grill-me——盘问澄清需求。 你刚有一个 idea，脑子里还是模糊的，就想直接让 Agent 开写。这个 skill 拦在主线最前端，用一连串问题把「你到底想要什么」盘问清楚：要解决谁的什么问题、边界在哪、成功长什么样。它的价值在于把「模糊的需求」在进入编码前先逼成「清晰的约束」。 这是 Shaping 层的典型职责——探索开放问题，产出决策喂给主线。

第二步：/to-spec——沉淀成 spec/PRD。 盘问完的需求还散在对话里，这一步把它们收敛成一份规格文档：目标、范围、非目标、验收标准。从「对话」到「文档」这一步很关键，因为文档是主线后面所有环节共享的锚点——它把「我们到底要做什么」钉成了一份可以反复引用、可以 review 的资产，而不是躺在聊天记录里的一段话。

第三步：/to-tickets——拆成垂直切片 ticket + 阻塞关系。 有了 spec，接下来把它拆成一张张可以独立实现的 ticket。这里有两个要求：垂直切片（每张 ticket 切过所有层、能独立交付、能独立验证，而不是按「写 DAO 层」「写 Service 层」这种水平切法）；以及阻塞关系（哪些 ticket 必须先于哪些）。这一刀决定主线后面能不能并行、能不能持续交付。切法错了，后面的 TDD 再漂亮也是在错误的颗粒度上打转。

第四步：/tdd——red-green-refactor 逐个实现。 真正写代码了。这个 skill 是主线的「生产车间」：每张 ticket 都走「先写一个失败的测试（red）→ 用最小代码让它通过（green）→ 重构（refactor）」的循环，一张 ticket 一次循环。它和第 2 篇「测试锁行为」完全接上了——TDD 里的测试，就是在行为层面锁死「这段代码该做什么」。

第五步：/improve-codebase-architecture——每周跑一次维护。 这是 Upkeep 层。主线一直在「消耗工作」（吃掉一张张 ticket），而维护 skill 负责「制造工作」：定期审视 codebase 和 issue 列表，把积累的坏味道、该重构的地方、该拆的模块，整理成新的 ticket，再喂回主线。它不参与日常交付，却保证主线不是在一堆技术债上越跑越慢。

这五步串起来，就是一条完整的流水线：grill-me 澄清 → to-spec 定型 → to-tickets 切分 → tdd 实现 → improve-codebase-architecture 维护再生成新工作。 注意它是一条有方向的脊椎，不是五个可以随便堆叠的工具：每一步的输入是上一步的输出，输出是下一步的输入，顺序不能乱。你不可能跳过 grill-me 直接 to-spec——没有盘问过的需求，沉淀出来的 spec 就是一堆拍脑袋；你也不可能跳过 to-tickets 直接 tdd——没有切片的 spec，TDD 不知道「一张 ticket」该多大多小。

再回头看第 3 篇那句话，就具体了：「主线是脊椎」，指的就是 grill-me→to-spec→to-tickets→tdd 这条从 idea 到 ship 的主干；「塑形喂养它」，指 grill-me 和 to-spec 在主线前端把开放问题收敛成决策喂进来；「维护喂养它」，指 improve-codebase-architecture 在后端把整理好的新工作喂进来。 一条脊椎，两个供血器官，前面喂决策、后面喂工作——这就是一个 skill 系统「活着」的样子，而不是一堆 skill 文件死气沉沉地躺在目录里。

这一节同时也是对第 4 篇的收束。第 4 篇写了一个「在故障现场可靠」的 skill，但它属于 Reference 或 Upkeep 那一侧——它不在这条 idea→ship 的主干上，而是「当主线生产的代码在线上出问题时」跳出来兜底。一个完整的 skill 系统，既有把想法变成代码的脊椎，也有出了问题能把现场查清楚的 sidecar。 前者保证你「造得动」，后者保证你「撑得住」。

落地团队 + adoption 清单

写会了扩展、组合，最后一步是让它真正属于团队，而不是属于你一个人。这一节讲四件落地的事，最后收一张能照着打勾的 adoption 清单。

第一件事：安装与 setup。 这一整套 skill 的作者是 Matt Pocock（aihero.dev/skills），他的分发方式正是第 3 篇「工程控制权」里推荐的那种——可读、可改、装进你自己的项目。安装不是「下载一个插件」而是跑一个 setup-matt-pocock-skills skill，它会在安装时通过三个问题带你走完配置——选哪些 skill、装到哪个 agent（Claude Code、Cursor 等）、以什么方式接进当前项目。把「安装」本身也做成一个 skill，是同一个哲学的自我贯彻：连「怎么装这套东西」这种一次性的流程，也被编码成了一条可复用的路径，而不是一段要靠人去记的安装文档。

第二件事：CONTEXT.md 共享语言。 skill 只解决「流程」，不解决「这个团队说的『订单』『结算』『风控』到底指什么」。一个 codebase 要想让 Agent 高效协作，得有一份团队共同维护的 CONTEXT.md，记录领域术语、架构决策、那些「老员工知道、新人要踩坑才知道」的上下文。skill 给 Agent 一套「怎么干活」的流程，CONTEXT.md 给 Agent 一套「这个项目在说什么」的语言。 两者缺一不可：有语言没有流程，Agent 知道术语但乱干；有流程没有语言，Agent 每一步都按规矩走，却每一步都踩在错误的术语上。

第三件事：skill 存 git，随仓库走。 这一点在第 3 篇「工程控制权」已经埋过伏笔，这里把它落成动作：把 .agents/skills/（以及 CONTEXT.md）提交进项目仓库。这样 skill 就和代码一样走 review、走版本、走 CI——谁改了一个 skill，队友能在 review 里看到，出了问题的 skill 能被 git 回滚。 一套不进 git 的 skill，本质上是「只有你一个人拥有的私有配置」，团队协作无从谈起。

第四件事：按团队裁剪，别一次全上。 五步主线加一堆 sidecar，看起来诱人，但一次全装进团队，往往消化不良。务实的第一步是先上三个最贴身、收益最直观的：/tdd、/code-review、/diagnosing-bugs。 tdd 锁住「先写测试再写码」的行为，code-review 给每次改动上一道标准化的审视，diagnosing-bugs 把「查 bug」从瞎猜变成纪律。这三个覆盖了日常开发的「写、审、查」三件事，是投入产出比最高的第一批。等团队用顺了，再逐步补 to-spec、to-tickets 把主线拉长，补 improve-codebase-architecture 把维护做起来。

到这里，读者可能会问一个自然的问题：市面上「让 Agent 更好用」的东西这么多——mattpocock/skills、Anthropic 官方 Skills、GSD/BMAD/Spec-Kit、MCP——它们到底什么关系？该选哪个？ 它们不是一回事，甚至不在同一个维度上。下面这张对比表，从五个维度把它们摆在一起。

这张表最想传达的是：它们不是「四选一」的竞品，而是四个不同层面的东西。 mattpocock/skills 和 Anthropic 官方 Skills 是同一层面（skill 层）的两种来源——前者是「社区里一位作者做的一套、你拥有它」，后者是「厂商做的一套、你使用它」，区别在控制权；GSD/BMAD/Spec-Kit 是更高的「方法论」层，它们不给你单个 skill，而给你一整套「怎么组织 Agent 开发」的流程约定；MCP 则是最底层的「协议」层，它和 skill 根本不冲突——skill 里甚至可以用 MCP 去接外部工具。如果只想要「几个能让 Agent 更可靠的流程」，从 mattpocock/skills 这类可拥有、可改的 skill 集入手，是上手成本最低、控制权也最稳的一条路。 这也正是本系列一路推荐它的原因。

最后，把这一路的结论收成一张 adoption 清单。每一项做完就打一个勾，团队就算真正落了地：

  • 装好 setup-matt-pocock-skills，选好第一批 skill（建议从 /tdd、/code-review、/diagnosing-bugs 起步）
  • 把 .agents/skills/ 和 CONTEXT.md 提交进项目仓库，纳入 review 流程
  • 写完 CONTEXT.md：领域术语、架构决策、团队约定，别只写一句「这是我们的项目」
  • 给 incident-diagnosis 补上第一本 references/ 手册（从你团队最常遇到的那类故障开始）
  • 把最常做的重复操作，固化成一个 scripts/ 脚本，让 Agent 直接调用
  • 在「建立假设」环节接入 hypothesis-reviewer 子代理，给排查上对抗
  • 跑通一次完整主线：拿一个真实的小需求，走完 grill-me → to-spec → to-tickets → tdd，感受「脊椎」怎么把人逼到每个阶段都做对
  • 定一个维护节奏（每周一次 improve-codebase-architecture），让 Upkeep 持续给主线喂新工作
  • 用「好响应 vs 坏响应」的方式验证一次：喂给 Agent 一个真实任务，看它有没有按 skill 的路径走，而不是自由发挥

这张清单的价值不在「打勾」本身，而在它把「落地」从一句口号，变成了九个可以逐项确认的动作。 团队采纳一套 skill，最怕的是「装了但没人真用」——清单逼着你把「装」和「用」拆开，一项项落实。

系列总结：从「为什么」到「怎么落地」

五篇到这里全部写完。回过头看，这一系列走的是一条从抽象到具体的直线：第 1 篇立哲学（Agent 没有记忆，结构决定产出），第 2 篇给方向（深模块、灰盒模块怎么改造结构），第 3 篇给规则（分层架构、命名约定、克制），第 4 篇给实操（写一个能跑的 skill），第 5 篇给落地（扩展 sidecar、组合主线、进团队）。每一篇都在回答上一篇逼出的下一个问题，串起来就是一套完整的「Agent Skills」方法论。

但这套方法论的真正起点，其实是一个更诚实的姿态：承认 Agent 不是「更聪明的同事」，而是「没有记忆、但严格照章办事的新人」。 从这个姿态出发，一切都顺理成章——你不能指望它记得怎么做，所以你写 skill；你不能指望它自己权衡，所以你定铁律；你不能指望它自己质疑，所以你配子代理；你不能指望它自己知道「什么先做什么后做」，所以你把它们串成一条有方向的主线。skill 的全部力量，都在于「把你不放心交给 Agent 自由发挥的东西，提前写成它每次都会走的路径」。

系列的作者是 Matt Pocock，他的 skill 设计哲学（以及完整的 skill catalog）都在 aihero.dev/skills。下一步很明确：去那里把整套 catalog 读一遍，挑一个对你团队最痛的点，改造进自己的项目。 不要一次全上——先挑一个（比如先上 /tdd），把它用透，再用这篇的扩展方法给它加 sidecar，再慢慢把它串进你自己的「idea→ship 主线」。单个 skill 让你在「一件事」上可靠，一套 skill 系统让你在「一整条链路」上可靠。这条路，现在你可以自己走下去了。
