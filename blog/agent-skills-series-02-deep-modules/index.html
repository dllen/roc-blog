深模块与灰盒模块：让 AI 在你划定的边界内干活

#AI#Agent Skills#Claude#软件设计#系列教程

本文是 Agent Skills 系列教程第 2 篇。第 1 篇回答了一个前置问题：Agent 是「没有记忆的新人」，决定它产出好坏的首先是 codebase 结构，而不是 prompt。这一篇把问题往前推一步——结构具体该怎么改。答案落在两条设计原则：深模块和灰盒模块。本文仍然不写任何 skill 文件，先把这两条哲学讲透；第 3 篇再谈 skill 这个工具如何把它们固化下来。

回顾：从「没有记忆的新人」到「给新人划边界」

第 1 篇的结论可以浓缩成一句话：Agent 每次开工都是一个失忆的新人，它对项目的全部认知都来自文件系统。文件系统里没有的——模块之间的分组、边界、约定——它就感知不到，于是它在黑暗中摸索，在错误的地方打补丁。

那么接下来的问题自然就是：既然它只能在文件系统里重建心智地图，我们能对文件系统做什么，好让这张地图第一次就能被它拼出来？ 注意，到这里，问题的性质已经变了。

一开始你问的是「要不要让 AI 帮忙」——这是个判断题，答案是“要“或“不要“。现在你问的是「怎么让 AI 在你划定的边界内发挥」——这是个设计题，答案不是一个开关，而是一套关于“边界“的取舍：哪些东西暴露给它、哪些东西藏起来、哪些东西由你说了算、哪些东西可以放心交给它折腾。

「边界」这个词，就是这一篇的核心。深模块告诉你边界该画成什么样，灰盒模块告诉你边界两侧各自归谁管。先把这两条讲清楚，后面所有 skill 的写法才有落脚点。

深模块：大量实现，藏在简单接口后面

「深模块」这个概念来自 John Ousterhout 的《A Philosophy of Software Design》。他给出的定义非常朴素：好的模块应该是“深“的——大量的实现被控制在一个简单的接口之后。 接口很窄，调用方需要知道的很少；实现很深，模块背后真正做的事很多。复杂度不是消失了，而是被“藏“在了接口后面，没有摊给调用方。

举一个后端工程师都熟的例子：一个封装的好的数据库访问层。调用方只需要看到一个 getUserById(id) 这样的签名，它背后可能藏着连接池管理、SQL 拼接、结果映射、缓存失效、超时重试——但这一切对调用方来说都不可见。你用一个窄接口，买到了背后一大块能力。这就是深模块。

和它相对的是浅模块：接口复杂、实现却单薄。Ousterhout 的原话描述是，一个模块的接口相对于它提供的功能来说“过于复杂“。最典型的例子，恰恰是那种「只为了可测试性而抽出来的纯函数」——把一个本来内聚的逻辑拆成一堆零散的小函数，每个函数的签名都得声明一堆参数来传递上下文，可每个函数自己又做不了几件事。结果是接口的总面积膨胀了，功能却没有变多。

为什么浅模块对 Agent 是致命的？回到“没有记忆的新人“这个前提：Agent 理解一个模块，是从接口开始的。深模块意味着它读一个签名就能拿到一大块能力，理解成本极低；浅模块意味着它必须读懂十几个零散的小接口、自己把它们在脑子里拼回原状，才能理解“这段代码到底在干什么“。接口表面积越大，Agent 要重建的心智地图就越碎。 浅模块不是让 AI 干不了活，而是逼着 AI 在一堆碎片里走迷宫。

这也是为什么这套做法对人和对 AI 同时成立。Ousterhout 反复强调的一点是：这本来就是过去 20 年里好代码库一直以来的组织方式——它对人有效，对 AI 同样有效。 换句话说，你不需要为 AI 发明一套全新的、别扭的代码组织法；你只需要把那些“让人读起来舒服“的老原则执行得更彻底。深模块不是 AI 时代的时髦，而是被时间验证过的常识，只是现在多了一个必须吃透它的读者——你的 Agent。

灰盒模块：人定接口，AI 管实现，测试锁行为

深模块解决了「边界该画成什么样」，但没回答一个更实际的合作问题：画好边界之后，边界两侧的活分别归谁干？ 这就是灰盒模块要回答的。它是这一节的核心。

灰盒模块有三要素，缺一不可：

第一，人定接口。 一个模块的公共契约——它对外暴露哪些函数、每个函数接受什么、返回什么、有什么副作用——由人来设计。这部分的判断权不交给 AI，因为接口是模块的“脸面“，它决定了所有调用方（包括 AI）理解这个模块的成本。接口一旦画得又宽又碎，后面的一切都跟着乱。

第二，AI 管实现。 接口定了之后，内部怎么实现，交给 AI 去折腾。它想用循环还是递归、想把逻辑拆成三个私有函数还是一个、想加不加一层内部缓存——这些细节你不过问。因为在接口锁死的前提下，实现细节已经不会影响调用方了，交给谁写都一样。

第三，测试锁行为。 这是三要素里最关键、也最反直觉的一条：只要测试过了，你就不需要再检查它的内部实现。 你不需要一行行 review AI 写出来的内部代码，不需要确认它有没有用上你偏爱的写法，甚至不需要理解它具体怎么做到的——你只需要确认它对外承诺的行为，被测试锁住了。

把这三条拼起来，就是灰盒模块的全部：一个对调用方半透明、对实现细节半遮住的盒子。 外部看得到接口（所以不黑），内部不必逐行审查（所以不白）。这也是它被称为「信任机制」的原因——信任不是靠“盯着 AI 干活“建立的，而是靠“锁住行为、放开实现“建立的：你给了 AI 最大的内部自由，同时也用接口和测试划死了它不能越过的边界。

这种分工恰好和人的天性格格不入。人写代码时天然地想看实现，看到 AI 写了个「不那么漂亮」的内部结构就想上手改。灰盒模块要求你克制这种冲动：内部不漂亮不影响任何人，因为没有人需要看它；真正需要保证的是外部契约，而那是接口和测试的事。管住接口，放开实现，用测试换信任——这就是灰盒模块的纪律。

渐进式披露：按需而不是一次性倾倒

深模块和灰盒模块背后，还站着一条更底层的原则：渐进式披露。它的意思是，接口只解释「做什么」，实现只在真正必要时才被翻开；复杂度的披露是按需的，而不是一次性全部倒给你。

还是拿那个数据库访问层说事。调用 getUserById(id) 的人，只需要知道「你给我一个 id，我返回一个用户或 null」——这是“做什么“。至于内部怎么连库、怎么缓存、怎么重试，那是“怎么做“，99% 的场景下你根本不需要知道。只有当你在排查一个连接池泄漏、或者要改缓存策略时，你才需要钻进实现，而且那时你是带着明确问题去的，看得懂多少算多少。

渐进式披露的反面，是“一次性倾倒“——把所有复杂度摊平在调用方面前：每个内部实现细节都暴露成公共接口的一部分，想用一个功能得先读懂它的全部机理。这正是第 1 篇讲的「认知过载」的来源之一：当 AI 被迫一次吞下远超当前任务所需的细节时，它要么被细节淹没、抓不住重点，要么在错误的地方过度联想。

所以渐进式披露其实就是第 1 篇「认知过载」的反面教材。认知过载说“别把复杂度全倒给 AI“；渐进式披露说“那就按需披露——它当下只需要接口，就只给它接口“。深模块负责把接口做窄，让“当下需要的部分“足够小；灰盒模块负责把实现藏好，让“暂时不需要的部分“真的可以不去看。三条原则其实是同一件事的三个切面。

落地动作：五条清单

哲学讲得再多，最后要落到能执行的清单上。这一节给你五条可以直接照着做的动作：

一、每个模块一个文件夹，配一个清晰的公共接口。 让模块的物理边界和逻辑边界对齐——一个目录就是一个模块，目录里有一个能被一眼看懂的公共入口，其余都是私有实现。别让一个功能散落在十几个文件里，那会让 Agent 根本找不到模块的边界在哪。

二、让 AI 从文件系统就能读到 service 的类型与签名，无需翻实现。 接口要被写进文件系统，而不是只活在你脑子里。类型定义、函数签名、导出的入口文件——这些东西要让 Agent 读文件就能拿到，而不是逼它去翻每个实现的源码才能拼出“这个模块能干嘛“。

三、在委托内部实现之前，先写测试锁行为。 顺序很重要：不是“AI 写完代码、你再补测试“，而是“你先把行为测试写好、再让 AI 去填实现“。测试先于实现，行为就有了唯一的验收标准，AI 的内部自由度才真正成立。

四、从需求到实现，全程保持「模块边界」思维。 每当你（或 AI）要新增一个功能，先问一句：它属于哪个模块？该加在接口的哪一侧？是现有模块的扩展，还是一个需要单独成模块的新边界？边界思维不能是事后补救，得是贯穿始终的习惯。

五、保证快速可靠的反馈闭环。 这一条直接呼应第 1 篇的「弱反馈闭环」失败模式：AI 改完实现，必须能立刻跑测试验证行为有没有被锁住。测试这条闭环越短，灰盒模块的信任机制就越能自运转。

五条动作里，没有一条是“给 prompt 加更多约束“。它们全都作用在 codebase 结构上——因为这才是决定 AI 能不能干好活的那个变量。

语言层面的现实：边界在 TypeScript 里很难守

讲到这里，一个诚实的读者会问：这些原则听着都对，但在自己用的语言里守得住吗？这个系列的作者 Matt Pocock（aihero.dev/skills）自己也给了诚实的答案：在 TypeScript 里，模块边界非常难守住。

原因在于，TypeScript 的类型系统是“结构性“的，它擅长描述“这个对象长得像不像“，却不擅长强制“这块代码只能这样被使用“。一个“模块“的边界在 TS 里没有运行时实体，纯靠约定和自觉：你可以 import 任何没有导出的东西吗？不能，但你可以通过相对路径绕进任何目录、碰任何被导出的内部文件。类型能拦住一些错误，却拦不住“越界“这件事本身。

正因为边界难守，作者本人也在实践中转向了 Effect 这类工具——它们的卖点之一，恰恰是在类型层面把“副作用““依赖”“边界“这些概念变成一等公民，让编译器帮你守住那些在原生 TS 里只能靠自觉守的线。边界这件事重要到，有人愿意为了它换掉整个编程范式。

但我们也要诚实：这不是放之四海而皆准的方案，也不是唯一答案。 不同语言、不同团队、不同项目规模，能承受的改造成本完全不同。换 Effect 的代价对一个五个人的小团队可能太高；对一个 Java 团队，“模块“的边界天然有包和访问修饰符帮着守。真正通用的不是“你必须用哪个工具”，而是那个方向本身：把边界显式化、让接口窄而清晰、用测试锁住行为——这个方向在哪门语言里都成立。 语言决定了你实现它的难易，但改变不了它对 AI 协作的价值。

小结：哲学讲完，接下来是工具

这两篇把设计哲学的部分讲完了。第 1 篇说清了“为什么“：Agent 是没有记忆的新人，codebase 结构决定它的输出质量。这一篇说清了“怎么办“的方向：用深模块把接口做窄、把实现做深，用灰盒模块把「人定接口、AI 管实现、测试锁行为」的分工固定下来，用渐进式披露控制复杂度的释放节奏。

但哲学毕竟只是方向，方向要靠工具落地。你不可能指望每一次开工，都重新向 Agent 口头交代一遍“记得用深模块、记得先写测试、记得别碰实现细节“——Agent 没有记忆，这些交代转瞬即逝。你需要一个东西，把这些原则编码成 Agent 每一次开工都必须严格走一遍的流程，让它不靠记忆、不靠自觉，每次都被同一个结构牵引着走上同一条可靠的路。

这个东西，就是 skill。下一篇开始，我们进入实操：讲清楚 skill 这个工具到底是什么、它如何把这两篇的哲学变成一条条 Agent 每次都绕不开的纪律。
