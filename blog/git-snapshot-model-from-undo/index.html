从「我想撤销」推导出 Git 的快照模型

#版本管理#Git#软件工程

Git 教程都在教命令：记住 git add、git commit、git merge 各是什么。这门课换了个起点——从「我想撤销」推出 Git 的快照模型：从“我想撤销“这个最朴素的个人经验出发，推导出「Git 管理项目的快照」这个核心概念，再向下展开到对象模型、暂存区的语义、原子变更与协作规则。

推导出概念之后，命令就不再是需要背下来的字符串：操作之前可以预测工作区会不会变、下一次提交包含什么、哪个引用会移动、历史里会增加什么关系。

本文整理自南京大学《生成式软件工程》2026 秋第 3 讲「版本管理 (1)」（主讲：jyy），原始讲义。文中所有 Git 行为均在本地 git 仓库实跑验证。

一、从「我想撤销」到「快照」

起点是一个人人都有的需求：我想撤销刚才那次修改。

要满足它，系统至少得保存旧版本。但只保存旧版本还不够——真实的项目里，你可能想撤销的是“三小时前那一组改动“，而这期间你自己又做了别的事。撤销的对象必须能被指认，于是需求变成：要保存的不只是文件当前的样子，还要保存它经过哪些状态，以及这些状态之间的关系。

这个推导直接决定了 Git 的基本对象不是“文件“也不是“行级 diff“，而是快照（snapshot）：一个包含文件内容与目录位置的整体状态。历史则是快照之间的关系网——父提交的连接把它组织成一张有向无环图。

“以项目为单位“也来自同一个推导。源代码、接口文档和配置文件经常一起变化；只恢复旧代码却留下新配置，会拼出一个从未正常运行过的版本。所以 Git 管的是项目整体的状态，而不是单个文件。

存过盘 vs 提交过。 编辑器保存的是工作区状态，Git 提交才记录快照。这个区分有实际后果：把文件删掉再提交，旧快照里它仍然存在——历史不会因为当前状态的变化而改写。

二、三个区域：add 之后又改，提交的是哪个版本

讲义提出一个值得亲手试的问题：执行 git add hello.c，然后又修改它，最后 git commit——提交的是哪个版本？

答案：add 时暂存的版本。 后续修改仍在工作区，要再次 add 才会进入这次提交。实测：

--- git show 提交内容:
v1
--- 工作区当前内容:
v2
--- git status --short:
 M hello.c
--- git diff --cached (暂存区相对当前提交):
--- git diff (工作区相对暂存区):
diff --git a/hello.c b/hello.c
index 626799f..8c1384d 100644
--- a/hello.c
+++ b/hello.c
@@ -1 +1 @@
-v1
+v2

这里的关键是讲义区分的三个区域：

  • 工作区 —— 你正在编辑的文件；
  • 暂存区（Staging Area，也叫 Index）—— 保存下一次提交准备采用的内容；
  • 提交历史 —— 已经记录下来的快照。

git diff 看你相对于暂存区改了什么，git diff --cached 看暂存区相对于当前提交改了什么。两个 diff 都空，恰恰说明暂存区和提交历史一致、工作区另有改动。

暂存区的价值在这里显形：它让你能够组织一次提交的内容，而不是被迫把此刻所有编辑一并记录下来。改了三处、只有两处相关，就只 add 那两处。

这些区域背后不是一个大 opaque 的包。Git 把快照拆成三类对象，用内容哈希寻址：

  • blob 保存文件内容；
  • tree 把文件名与对象组织成目录结构；
  • commit 关联根目录树和父提交。

用 git cat-file 可以直接看：

blob oid = 626799f0f85326a8c1fc522db584e86cdfccd51f
--- blob 内容:
v1
--- tree:
100644 blob 626799f0f85326a8c1fc522db584e86cdfccd51f	hello.c
--- commit:
tree fe91be2b138ae0ccc96e29d9c0d12632d9d981df
author t <t@t> 1794415044 +0800
committer t <t@t> 1794415044 +0800

first

对象按内容寻址带来一个直接后果：内容相同的文件在仓库里只存一份。内容变了，哈希变了，就是新对象；路径没变但内容变了，git ls-files -s 里的 blob id 就会换。

三、分支是可移动引用，合并有两种形态

分支名不是一个独立的容器，而是指向某个提交的可移动引用。HEAD 表示当前所在的分支。你在分支上创建新提交，分支引用就向前移动；另一个分支仍然停在原处。

--- refs/heads 内容:
98611617734e1ddd0ca2e6a3a72ae6a4238413b9 refs/heads/feature
98611617734e1ddd0ca2e6a3a72ae6a4238413b9 refs/heads/main

两边从同一个提交出发后分道扬镳：

--- feature 现在指向:
307797479212d72a8676ce3bf57cd9e260678084
--- main 仍指向:
98611617734e1ddd0ca2e6a3a72ae6a4238413b9

合并有两种形态。如果一方只是另一方的后续，Git 只把引用向前移动，不创建新提交——这就是 fast-forward。双方都前进过，则创建一个有两个父提交的合并提交。

冲突时，Git 会把标记直接写进工作区文件：

<<<<<<< HEAD
mine
||||||| 09f3b44
base
=======
theirs
>>>>>>> other

工具能发现文本上的分歧，但究竟要哪一种行为，得回到需求去决定。二进制文件和“删除 vs 修改“这类冲突不一定呈现同样的文本标记，所以关键是同时检查状态和文件。

git rebase 则把一串提交代表的改动依次重放到新起点上。重放得到的提交通常有新标识，过程中也可能冲突。如果别人已经依赖原来的提交，你再改写它们就会增加协作成本——这条约束决定了 rebase 适合在约定允许的范围内整理工作。

四、“我的目录里有什么” vs “项目需要共同保存什么”

教程教完命令似乎就可以开工了，但软件里还有大量约定俗成的 best practices。讲义用一个极小的例子切入：目录里同时有 hello.c 和编译得到的 hello，要不要一起提交？

两者都保存，下一次只改了源码却忘记重新编译，仓库里就有两份不一致的状态，别人该相信哪份？只保存源码，也还要说明怎样构建。“我的目录里有什么“和“项目需要共同保存什么”，是两个问题。

几条常被提醒的：

  • 构建产物和运行日志通常不提交（dist/、调试日志等）——它们既不表达项目意图，也不参与项目构建；
  • 依赖锁文件虽然由工具生成，却常常用于固定依赖版本；有些项目也有意保存生成的头文件或静态发布产物；
  • 个人配置通常不提交，尤其是含自己机器绝对路径、私人偏好的设置；
  • 密钥不能提交——源码需要共享，不意味着访问服务的凭据也该一起共享。

这些不是按文件名机械执行的禁令。真正要解释的是：这个文件为何构成共同维护的项目状态，以及怎样保证它与其他文件一致。

.gitignore 不会让已跟踪文件退出版本管理

.gitignore 是落实这些约定的工具，但它有两个容易误解的边界。实测：先跟踪 secret.key 并提交，之后再把它写进 .gitignore——

--- git ls-files（仍在跟踪列表里）:
.gitignore
secret.key
--- 修改这个被 ignore 的文件，git 会把它当已跟踪文件报出来:
 M secret.key

已经被跟踪的文件，后来写进 .gitignore 也不会自动退出版本管理。 忽略规则只影响未跟踪文件的添加过程。

误提交密钥后，仅仅删除当前文件不够

--- 当前 HEAD 树:
100644 blob a0c34ad378ffc99656d542c0855631b651acabac	.gitignore
--- 但旧提交里仍能取回密钥:
SECRET-VALUE
--- 历史仍然存在这条路径:
4721f43 remove from index
65425d4 commit the key (mistake)

把文件从 index 里删掉并提交，当前 HEAD 树里确实没有了——但旧提交里还能原样取回，别人也可能已经拿到副本。要真正从历史里抹掉，需要重写历史（git filter-repo 或 BFG；git filter-branch 内置但已废弃）。

讲义对此的措辞很克制：版本管理帮助我们记住过去；不该公开的东西一旦进入过去，就不能假装它从未发生。

提交信息：diff 展示怎样改，说明补为什么改

update 当然能当提交说明，但几个月后翻历史，它几乎不能帮助任何人。讲义给了一个 Conventional Commits 风格的例子：

fix(parser): accept repeated spaces between arguments

fix 表示修复，parser 标示范围，后面说明行为变化。固定结构既方便人浏览，也方便工具分类和生成更新记录。

标题之后还可以解释：旧解析器把连续空格当成空参数，导致复制来的命令失败；现在忽略参数之间的多余空格，但保留引号内部的空格。代码 diff 展示怎样改，提交说明补上为什么改、想保留什么。 将来有人想删掉这段逻辑，就能找到判断依据，而不必重新猜一遍。

判断一份提交说明是否合格，落点仍然在恢复、理解和协调的成本上——一段说明符合格式，不等于它解释清楚了行为。

五、原子变更：让历史成为可用的调试工具

讲义把这一讲的核心概括成一句：项目是由原子变更推进的快照，可以分支，可以合并。

原子变更（atomic change） 指围绕一个明确意图组织的完整修改，它应当能够被解释、验证，并在需要时单独撤销。它不一定只改一个文件，也不一定只有几行。

为什么强调这个？因为人很难处理“一团混沌“。一次改了接口、重写了实现、更新了依赖、调整了格式，最后测试失败，应该从哪里找起？如果这些变化有清楚的边界，就可以分别理解、审查和处理冲突。

历史因此能成为调试工具，而这个能力取决于历史本身的质量：

  • git bisect 在已知好版本与坏版本之间不断测试中间提交，缩小引入问题的范围；
  • git revert 记录一次撤销——注意它是新提交，历史不被改写。

实测 git bisect 用一段脚本做自动判断（git bisect run 会逐个 checkout 中间提交执行脚本，直到锁定第一个坏提交）：

    step 5

 h.txt | 2 +-
 1 file changed, 1 insertion(+), 1 deletion(-)
bisect found first bad commit

有些项目要求线性历史，把集成后的提交组织成较直接的一条主线，便于阅读和追踪，也方便用 cherry-pick 把指定提交的变化应用到其他分支，或结合 blame 追查代码行的来历。但讲义强调：线性只是组织形式。 每一步都意义不明、不能运行，排成一条直线也不会自动变成好历史。

六、代码产能提高一千倍之后

讲义最后做一个思想实验：假设 Agent 生产代码的速度提高一千倍，会发生什么？这里“一千倍“是用来放大矛盾，不是测量结果。

生成一分钟，人工理解和验收一小时，积压的就会是等待判断的变更。Git 本身还能保存它们，但围绕人工提交、审查和协调组织起来的工作方式，可能成为瓶颈。

从零为 Agent 设计版本控制系统，也许应该把快照、变更以及变更如何组合放到中心。所谓 change algebra，可以理解为描述变更组合规则的一套运算：两项变化能否独立应用？能否交换顺序？是否依赖某个前置变化？冲突以后应当重做哪一部分？

这与数据库的 MVCC（多版本并发控制） 有相通之处，但讲义严谨地限定了类比范围：MVCC 关心多个版本下的并发访问，变更的组合规则还要表达修改如何衔接；即使两项修改可以交换应用顺序，结果也未必符合项目要求。

write skew：文本合并没有冲突，约束却破了

讲义给了一个值班员的例子。项目要求至少有一名值班员在岗，初始状态是甲、乙都在岗：

  • Agent A 看到乙在岗，就把甲改为离岗；
  • Agent B 看到甲在岗，就把乙改为离岗。

两项修改写在不同文件里，文本合并没有任何冲突，结果却是无人值班。这类似数据库里的 write skew：各自依据旧快照作出的决定，组合后破坏了共同约束。

这说明快照和局部检查之外，还需要检查组合结果，或者采用更强的并发控制。

一种可能的设计是让 Agent 在独立快照上生成变更，系统把变更与当前主线组合，验证候选结果，再原子地发布这个确切版本。发布时需要确认主线还是验证所依据的版本；如果其他 Agent 已经推进了它，就重新组合并验证。锁只保护短暂的版本读取或发布过程，耗时的生成和测试在锁外完成——否则把整个开发过程锁住，只是把并发工作重新排成了长队。

讲义还挑了一个更根本的挑战：反正没有哪个 Agent 能被开除，我们能不能再也不要 blame，只让它把事情推进、把问题修好？ 如果生成和修复都足够便宜，工程流程是否可以把更多精力放在正确性保障和恢复能力上？

这个问题的答案取决于错误能否及时发现、后果是否可恢复，以及验收标准能覆盖多少真实要求。测试全绿只说明已有检查通过了；如果“至少一人值班“从未写进要求或检查，就不能指望文件合并替我们保证它。

一个人的工作方式：单线程收敛 + 有限并发

在进入并发之前，讲义先讲人的部分。课程实践是：架构阶段先“单线程“——与能力强的模型反复讨论，直到接口、约束和总体设计逐渐收敛，再把结果写成文档、规则和示例，包括测试要做到什么程度。

这个阶段仍然需要人的知识。为什么还要学习操作系统、编译原理和数据库？因为这些领域积累了大量好设计：怎样划分职责，怎样表达不变量，怎样隔离变化，怎样协调并发。知道这些，才能在讨论中提出有效问题，判断模型给出的方案是否值得继续。

进入实现阶段后，可以打开少量终端并行工作。讲义给出的实践范围是不超过三个终端，通过 AGENTS.md 说明协作规则（例如历史如何整理、任务怎样集成），再由人脑承担一部分并发控制：尽量安排相互不冲突的任务。讲义特意限定——这个数量是个人工作方式，不是并发 Agent 的普遍上限。

每一轮产出都应尽快检查；有界面的项目立即打开看看，给出视觉验收反馈。无论觉得模型这一次质量高不高，都不要让未确认的设计选择积累太久。

三件事需要配合：架构讨论收敛共同前提，有限并发推进独立工作，快速反馈纠正理解偏差。

七、这套模型不解决什么

上面推导出的概念模型，解释的是 Git 为什么这样设计，不是怎么用好它。

具体说，它不替你判断该不该重构、该不该写测试、该怎么拆模块——那些是工程判断，不在版本管理这一层。它也不保证协作顺畅：git 管版本，但 issue、审查讨论和 CI 运行状态属于平台协作对象，需要 gh、glab 这类命令行工具把版本操作与平台上的协作过程连接起来。

还有一个边界值得单独说：这套概念来自 2026 年的课堂，不是一份完备的 Git 手册。 它讲的是快照模型和三区域语义，实践中还有 rebase 的代价、签名与子模块、.gitattributes 等大量细节需要另行查文档。把它当作“理解 Git 的骨架“，剩下的细节再按需补齐，比一开始背命令更省力。

如果对 Git 的命令行操作本身感兴趣，Git Worktree 实践指南讲的是多工作目录的完整用法与避坑；如果想看把版本管理重新设计成 Agent 可用的形态——change ID、first-class conflicts、锁与 MVCC 的取舍——那在 版本管理该把什么当作基本对象里，是本讲的下一讲。
