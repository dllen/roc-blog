Skill 设计最佳实践：分层架构、命名约定与「三句话的力量」

#AI#Agent Skills#Claude#工程效率#系列教程

本文是 Agent Skills 系列教程第 3 篇。前两篇把「为什么」和「往哪改」讲完了：第 1 篇说 Agent 是没有记忆的新人，codebase 结构决定它的输出质量；第 2 篇说结构该怎么改——深模块把接口做窄，灰盒模块把「人定接口、AI 管实现、测试锁行为」固定下来。这一篇进入实操，回答一个更直接的问题：skill 这个工具，到底该怎么写才是一个好 skill？ 答案落在三条规则上——分层架构、命名约定，以及「skill 不必长」的克制。

从哲学到工具：把「严格路径」编码给 Agent

第 1 篇的结论是：Agent 每次开工都是一个失忆的新人，它只能靠文件系统重建心智地图，所以你无法指望它「自己记得怎么做」。这句话逼出一个必然的推论：你只能把「正确的过程」写成一份每次都必须严格遵循的路径，让 Agent 不靠记忆、不靠自觉，每次都被同一个结构牵引着走上同一条可靠的路。 这个东西，就是 skill。

这个系列的作者 Matt Pocock（aihero.dev/skills 的设计哲学系列）给 skill 下的定位，正是这句话：skill 是把「严格路径」编码给 Agent 的载体。原文里反复出现的一个说法是 “extremely strict and well-defined processes”——极其严格、定义清晰的流程。为什么必须「严格」？还是回到没有记忆这个前提：模糊的流程对人是有弹性的（人会自己补全），对 Agent 却是灾难（它会在每一处模糊里自由发挥，而它的「发挥」没有历史经验兜底）。只有把路径定义到「每一步都明确」的程度，Agent 才不会被自己的不确定性带偏。

到这里，前两篇的哲学和这一篇的工具就接上了。第 1 篇说「结构先于 prompt」，第 2 篇说「用深模块和灰盒模块改造结构」——但它们都没回答最后一个问题：那些「每次都要做对」的事，比如先写测试、先读 CONTEXT.md、先把边界想清楚再动手，怎么保证 Agent 每次都不落下？ 口头交代没用，Agent 记不住；写进 AGENTS.md 也没用，那只是背景信息，不是「步骤」。你需要的是一个能在正确时机被触发、并把正确步骤递到 Agent 面前的东西。这就是 skill 的用武之地。

所以这一篇不再谈「要不要」，直接谈「怎么写」。一个写得好的 skill，靠三条规则立起来：分层架构决定它的内部怎么组织，命名约定决定它怎么被 Agent 和队友一眼认出来，**「skill 不必长」**则是一条贯穿始终的克制——它提醒你，skill 的力量不在篇幅，而在「在对的时机说对的话」。

SKILL.md 最小结构：description 比正文重要

skill 的物理形态极其简单：一个文件夹，里面一个 SKILL.md。但「简单」不等于「随便」，一个最小可用的 skill 由这几部分组成：

name：小写字母 + 连字符（kebab-case），比如 tdd、grill-me。它是 skill 的身份标识，也是后面命名约定那一节要展开的起点。

description：触发条件——什么时候用这个 skill，以及几个能命中它的关键词。

正文：真正的纪律。它告诉 Agent 该按什么步骤、遵守什么规则、产出什么结果。

可选部分：references/（按需加载的详细文档）、scripts/（skill 附带的脚本）、agents/（子代理配置）。这些是可选的，复杂 skill 才需要，简单 skill 一行都用不上。

这里要重点强调的是 description，而不是正文。description 是 skill 的触发开关，写好它比写好正文重要得多。 原因在渐进式披露：会话开始时，Agent 只读所有 skill 的 name 和 description，靠它们判断「这个任务该不该加载这个 skill」。description 写砸了，正文写得再精彩也没机会被读到——开关没合上，整条路径都不会启动。

一个能触发的 description 长什么样？作者 tdd 这个 skill 的 description 是逐字这样的：

description: Test-driven development. Use when the user wants to build features or fix bugs test-first, mentions "red-green-refactor", or wants integration tests.

拆开看，它做了两件事：先用一句 “Test-driven development” 点明这是干什么的，再用 “Use when…” 列出触发场景（build features / fix bugs test-first）和命中关键词（red-green-refactor、integration tests）。有了这后半句，当用户说「帮我按 TDD 的方式改这个 bug」、或提到 “red-green-refactor” 时，Agent 就能把这条 description 对上号，加载对应的 skill。「什么时候用 + 关键词」，这两个要素缺一不可——只有关键词没有场景，会误触发；只有场景没有关键词，会漏触发。

这一节只是把格式精炼地过一遍，帮你在进入分层架构前先铺一张地图。skill 格式的完整细节与渐进式披露机制，可参见本站专文《彻底搞懂 Agent Skills：从原理到实践》，这里不展开。

分层架构：六层，一条脊椎

写单个 skill 有格式，管一堆 skill 就得有架构。当你手上的 skill 从一两个涨到十几个，最需要回答的问题不再是「每个怎么写」，而是：它们之间怎么组织、怎么分工、怎么互相配合？ 作者给出的答案是六层分层。

Getting Started（一次性配置）：装环境、设工具、跑初始化。它们不需要每天被触发，只在第一次、或环境变了的时候跑一次。把这类 skill 单独拎出来，是因为它们和「日常干活」的主线无关——不该混进主线里稀释注意力。

Main Flow（主线）：「idea→ship」主线，按顺序走。从拿到一个 idea，到把它 ship 出去，这是一条有明确先后顺序的路径。主线层就是这条路径上的每一步——它们是整个 skill 系统的「脊椎」。

Shaping（塑形）：探索开放问题 → 产出决策喂给主线。当主线走到一个岔路口、面对一个没有现成答案的开放问题时，Shaping 层的 skill 跳出来，帮你把问题收敛成一个可以执行的决策，再把它喂回主线继续走。

Upkeep（维护）：维护 codebase 与 issue 列表，为主线生成工作。主线会消耗工作，Upkeep 则负责制造工作——它盯着代码库和 issue 列表，把需要做的事整理成一条条可执行的任务，喂给主线。

Productivity（人面向）：人面向的工作流，非代码。这一层不是给代码干活用的，而是给人自己用的——那些提升个人效率、但不直接产出代码的工作流。

Reference（可复用底层）：其他 skill 调用/引用的可复用底层。它不是一条独立的流程，而是被别的 skill 引用的一块「公共积木」——比如「怎么读 CONTEXT.md」「怎么写一条好测试」这类底层知识。

这六层不是并列的六堆文件，它们之间有明确的主从关系。一句话概括：主线是脊椎，Shaping/Upkeep 喂养它，Reference 是共享层。

展开说：Main Flow 是脊椎——整个 skill 系统围绕「idea→ship」这条主线搭建，其他层要么为它服务，要么从它这里领取任务。Shaping 和 Upkeep 是这条脊椎的两个「供血器官」：Shaping 在主线遇到开放问题时，把探索出的决策喂进来；Upkeep 在主线需要工作时，把整理好的任务喂进来。一个供决策，一个供工作，方向不同、功能互补。Reference 则垫在所有层下面——它不参与主流程，但主线、Shaping、Upkeep 随时可以引用它，是大家共享的底层。至于 Getting Started，它只在系统刚搭起来时出现一次，之后安静退场；Productivity 则偏向人的一侧，与代码主线平行但不纠缠。

理解了这层关系，你写 skill 时就知道该把它放哪、该不该让它去碰主线。一个常见的错误是：把本该属于 Shaping 的「探索」塞进主线，让主线在岔路口停下来发散；或者把本该属于 Upkeep 的「维护」写进主线，让主线背着它越走越重。分层的第一要义，就是别让脊椎背上不属于它的重量。

命名约定：名字即自文档

分层解决「内部怎么组织」，命名解决「外部怎么识别」。skill 的命名有两条硬规则，和一条决定语义的规则。

两条硬规则：slash + kebab-case。 skill 以斜杠命令的形式出现（比如 /grill-me），名字本身用 kebab-case——全小写、单词之间用连字符连接。没有大写、没有空格、没有下划线。这条规则没得商量，因为它决定了 skill 能不能被一致地输入和匹配。

语义规则，决定名字的第一眼含义。作者用两种命名方式，把 skill 分成了两类：

verb-first（动词开头）：/grill-me、/wait-what。名字以动词开头，表示「这是一个动作 / 一条命令」——你调用它，是让它去干一件事。动词开头读起来像一句祈使句，Agent 和人都能立刻明白「这是在发起一个动作」。

noun-phrase（名词短语）：/domain-model。名字是个名词短语，表示「这是一块知识 / 一个参考」——它不是让你「做」什么，而是提供一个可以查阅、可以引用的东西。名词开头读起来像一本书的标题，暗示「这是资料，不是动作」。

这两种命名不是随意的，它们和分层架构是对应的：verb-first 的 skill 往往属于 Main Flow、Shaping、Upkeep 这些「做事」的层；noun-phrase 的 skill 往往属于 Reference 这一「共享底层」。名字本身就在告诉你它属于哪一类。

还有第三类，转换型——/to-X 模式：/to-prd、/to-issues、/to-spec、/to-tickets。这个模式专门表达「把 A 变成 B」：把一堆想法变成 PRD，把 backlog 变成 issues，把讨论变成 spec，把需求变成 tickets。/to-X 的名字本身就是一张流程图：你一眼就能看出「这是从某物到某物的转换」。

为什么命名这么重要？因为命名即自文档。 Agent 没有记忆，它认识一个 skill 的第一眼、也是很多时候唯一的一眼，就是名字。一个好名字让 Agent 不需要读正文就能大致猜到「这是什么、该不该用」；一个坏名字（比如 util、helper、stuff）则什么都没说，等于把「理解成本」转嫁到了每一次触发上。命名是 skill 设计里成本最低、收益最高的一步。

editable vs read-only：工程控制权

写好 skill 之后，还有一个更根本的问题：它归谁管？ 这决定了 skill 是「你的资产」，还是「厂商的黑盒」。

作者区分了两种分发方式。第一种是 npx 安装器：它把可编辑的文件直接拷进你的项目——skill 的每一个文件都落在你自己的目录里，你能读、能改、能 review。第二种是 Claude Code 插件：skill 由插件托管，你只能「用」，不能「改」，文件是只读的，藏在插件内部。

这两种方式的区别，表面上是「文件在哪」，本质上是「控制权在谁」。npx 安装器给你的是一份你能拥有的源码；插件给你的是一套你只能调用的黑盒。对大多数工程团队来说，这个区别是决定性的。

作者的立场很明确：skill 应该被团队拥有、审查、修改，而不是当黑盒来用。 理由回到第 1 篇：Agent 的行为由它读到的文件决定。如果 skill 是只读黑盒，团队就无法审查「我们的 Agent 到底会怎么做」；如果 skill 是团队仓库里的一份可改文件，那它就是 codebase 的一部分，和代码一样走 review、走版本、走测试。「工程控制权」这五个字，是这一节的全部——你愿意把「引导 Agent 干活的那套流程」，交到一个你不能改的黑盒手里吗？

这其实和灰盒模块的哲学一脉相承：第 2 篇说「人定接口、AI 管实现、测试锁行为」，前提是你得能定接口、能锁行为。一个只读的 skill，等于把你「定接口、锁行为」的权力没收了。所以选 skill 时，优先选那些能拷进项目、能被 review、能被改的——哪怕这意味着你要自己维护它。

「skill 不必长」：三句话的 grill-me

有了架构和命名，最后一条规则反而是最反直觉的：skill 不必长。 而且很多时候，越短越好。

作者最常举的例子是 grill-me。这个 skill 的全文只有三句话，做的事情却一点也不轻：它会引导一场 30 到 50 个问题、长达半小时的深入追问，把你想做的一件事、一个决定，从各个角度盘问清楚。三句话，换一场半小时的深度对话——这就是 skill 的力量，而它完全不是靠篇幅实现的。

背后的道理，作者用一句话点破：你只需在对的时机说对的话。 skill 的价值不在「说了多少」，而在「该说的时候，说到了点子上」。grill-me 的三句话，每一句都踩在一个精确的时机上，把 Agent 引向下一个问题、下下个问题——它不需要把 50 个问题都写出来，因为那 50 个问题是 Agent 在对话中自己生成出来的。skill 要做的是「起个头、把住方向」，而不是「把整个过程都写死」。

这条克制还有一个硬理由：token 优化是内建考量，不是偶然。 每个 skill 在被触发时都会被读进上下文，而上下文是要花钱、要占窗口的。作者在迭代这套 skill 时，光 v1.0 一个版本就砍掉了 63% 的 token——不是事后补救，而是从一开始就把 token 当作设计约束：每一个字都要占上下文窗口，所以多写一句，就多一分不该付的成本。篇幅不是美德，精确才是。

所以「skill 不必长」不是一句安慰话，而是一条硬规则：写 skill 时，每多写一句，就问自己一句「这一句，Agent 在真正干活时用得着吗？」用得着就留，用不着就删。skill 的终极形态，是「把话说得最少、把路指得最准」。

小结：规则讲完，第 4 篇动手写

这一篇把写 skill 的三条规则讲完了。分层架构告诉你 skill 之间怎么组织——主线是脊椎，Shaping/Upkeep 喂养它，Reference 是共享层；命名约定告诉你 skill 怎么被一眼认出来——slash + kebab-case，verb-first 与 noun-phrase 各归其位，/to-X 表达转换；「skill 不必长」告诉你克制的边界——在对的时机说对的话，篇幅是成本不是美德。再加上 editable vs read-only 这条「控制权」红线，你已经有了一套完整的、可以照着做的设计规则。

但规则终究要在动手里验证。下一篇，我们就拿这套规则亲手写一个 skill：从分层架构出发，起一个符合约定的名字，写一个克制而精确的 SKILL.md，再看它如何在 Agent 的每一次开工里被真正触发、真正起作用。
