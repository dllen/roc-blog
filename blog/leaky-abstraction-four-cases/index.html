抽象泄漏：四个案例说明架构为什么会变成阻力

#软件工程#架构#Agent Harness

「在某个架构下开发」意味着接受它的表达方式、接口和边界：你不能随意做所有事情，但也因此获得一批不必自己重写的能力。 这是南京大学《生成式软件工程》第 9 讲对架构的定义。讲义接着用一串例子说明「接受限制换来便利」这件事在不同层次上的形态，最后给出这一讲的诊断句：

边界与需求吻合时，我们得到解耦、复用、可测试性，以及团队共同理解的接口；假设改变时，被隐藏的细节重新影响上层，这就是抽象泄漏。

架构开始成为阻力，往往不是因为它突然「变坏」，而是它替我们固定下来的选择不再合适。

本文把讲义这四个例子拆成一张可对照的表，并补上这一讲的后半段（Agent Harness 的世界模型与插件协同）。讲义原文与本文的归类会分开标注——下面第三节的「时间尺度」是本文自己加的读法，不是讲义的说法。

一、四个案例：限制换来了什么，隐藏了什么

抽象换来的便利隐藏的假设假设被打破时谁先痛
进程与地址空间编辑器、编译器、播放器同时运行；一个程序的非法访存不会直接改坏另一个程序的数据每个进程「像是拥有自己的机器」活跃数据放不进物理内存时频繁换页；多进程竞争 CPU 与磁盘
Java / HotSpot GC写论坛时不必逐个判断对象何时释放，集中处理帖子与评论垃圾回收的成本由运行时承担论坛加入低延迟互动后，GC 暂停与 CPU 开销进入用户体验
LAMP + PHP-FPM成熟的 Web 服务、事务与备份设施可直接复用，按请求 / 业务 / 数据划分职责每个请求结束就释放资源出现「所有人一直在线的课堂讨论」，工作进程一直等消息，持续占用处理名额
事件溯源同一份事实既能回答「现在是多少」，也能回答「为什么是这个数」重放是安全的、历史输入与规则不会变重算余额时不能再扣一次钱；重现历史外币消费不能偷偷换成今天的汇率

案例一：独立地址空间隐藏了映射，没有消灭容量

普通进程在自己的地址空间里运行，通过系统调用申请资源，不能任意修改别的进程的内存——接受这些限制，操作系统才替我们组织起隔离、调度与资源访问。

但讲义随即加上转折：

独立地址空间隐藏了地址映射，却没有消灭物理资源的容量和竞争。想解释性能问题时，我们仍要走到抽象背后。

这句话的分量在于它不是抱怨：抽象没有承诺消除物理约束，它只承诺把约束藏起来。 于是「进程互相独立」这个假设，在解释性能问题时必须被重新打开。

案例二：GC 的三个目标只能保两个

以 Java 这样的托管语言为例：程序员接受对象、类型与引用的规则，把对象布局和垃圾回收交给运行时。讲义点出核心——降低暂停、提高吞吐、减少内存占用之间有取舍，运行时隐藏的成本又回到了开发者面前。

低延迟互动一旦进入产品范围，GC 暂停就从一个「别人负责」的问题变成「我的问题」。这不是 GC 做得不好，而是抽象把取舍藏起来之后，需求换了一个维度，被藏起来的东西就得出来。

案例三：PHP-FPM 的容量约束可以推出来

讲义给了一个可以照着推的容量推演：LAMP 让大量 Web 应用有了直接的组织方式；但新增「所有人一直在线的课堂讨论」之后，请求结束、释放资源的惯常节奏就变了。假设让 PHP-FPM 的工作进程一直等消息，它就持续占用处理名额，而进程池限制了同时服务的请求数。

紧接着还有更狠的一条：

进一步接入外部支付时，MySQL 回滚也不会替你撤销已经完成的外部扣款。

前者是容量约束（同一抽象内部可以推得出来），后者是跨越抽象边界的泄漏——事务的原子性只在它覆盖的边界内成立。这一条对写 Agent 工具的人尤其刺眼：工具调用「成功/失败」的语义边界，与外部世界真正发生的事之间，往往隔着一个回滚不到的地方。

案例四：事件溯源买到的能力与付出的代价

事件溯源要求把发生过的事实记录下来，再从这些事实计算状态。讲义的例子是校园卡：先充值 100 元，消费 12 元，再退款 12 元，最终余额与只充值 100 元相同，历史却不同。 接受事件记录的约束，就能同时回答「现在是多少」和「为什么是这个数」。

它的边界同样明确：回放消费记录以重算余额，不能再扣一次钱；要重现历史外币消费的计算，不能偷偷换成今天的汇率。讲义把结论落在一句话上：保存事件给了我们重建的依据，怎样解释事件仍是设计责任。

二、这四个案例的共同形状

把四个案例并排放，抽象泄漏的形状就清楚了：每一次交换都同时写下一份契约和一个假设，而假设总有失效的一天。

失效的时间尺度并不一样，这是本文自己加的归类（讲义把五个例子并排列出，但没给这个分层）：

案例泄漏发生在什么时刻
进程地址空间同一次运行内：物理内存装不下活跃数据
PHP-FPM 进程池需求一换：请求结束即释放的节奏不再成立
MapReduce（讲义的第五例）需求迭代一轮：中间结果反复交换成为负担
事件溯源跨版本重算：规则变了、外部副作用已经发生

这四种尺度对应四种不同的应对：前两种要回到抽象背后看容量，第三种要换计算形式（讲义给的演进链是 MapReduce → Spark → Flink），第四种要显式处理外部副作用与历史输入。

讲义给的诊断句值得单独记住：架构开始成为阻力，往往不是因为它突然「变坏」，而是它替我们固定下来的选择不再合适。 所以真正该做的事不是「把抽象做得更好」，而是知道自己把哪些选择固定住了——第 7 讲讲 UNIX 时那条「哪些决定现在固定、哪些留给未来」的线索，在这里又出现了一次。

三、另一半：Agent Harness 需要自己的世界模型

讲义把架构的定义从软件扩展到「一个很小的 Agent 循环，怎样容纳不断增加、甚至突然改变的需求」，答案落在插件体系上。

底层是 Cordis，负责四项职责：服务解析（「这个插件需要的能力由谁提供」）、依赖激活（「所需能力何时可用」）、作用域（注册项在哪些上下文里生效）、卸载（撤销相应的注册与监听）。讲义给了一个恰当的类比与一个恰当的否定类比：可以类比操作系统管理进程生命周期和资源访问，但插件框架的作用域并不等于操作系统级的安全隔离。

真正困难的不是「把文件分成很多包」——讲义说得很直接，把文件分成很多包，并不会自动得到解耦。困难在协同：工具、界面、记忆和执行循环如果各不往来就是一堆孤岛，随便往来又变成无法管理的混乱。正确方向是让插件共同理解少量稳定的概念。

这些稳定概念就是「世界模型」：

操作系统为程序提供进程、文件和网络这些基本对象。Agent Harness 也需要自己的「世界模型」，也就是软件对领域对象的组织方式。在本讲的抽象层次上，dsh 的几个核心概念是 Session、Agent，以及装配界面的 slots。

Session 记录发生过什么；Agent 接收输入并推动执行；slot 是界面预留的插入位置，让插件贡献按钮、面板或其他组件。

讲义对 Session 的核心表示是 Session = list[Event]，而它的实践要点在记录事实与解释事实的分工：追加业务事件、监听已提交事实（session.append / session/event）是一组；生成模型消息历史、注册与读取业务投影（session.deriveMessages() / ctx.sessionProjections）是另一组。讲义给的理解方法很对——关键不是记住函数名，而是区分「记录一件事」和「计算这件事意味着什么」。

这里还藏着一个容易混淆的区分，讲义称它为两种时间方向：session/event 面向已经发生的事实，只能追加新记录；agent/pre-step 面向尚未进入的步骤，可以参与决定下一步怎么走。混在一起的直接后果是：「插件想改变行为」很容易变成「插件悄悄改写历史」。

另外一条与可靠性直接相关的断言值得单独记：

没有收到成功消息，不等于操作没有执行。

文件已经移动、工具结果还没记录、进程就崩溃了——恢复时直接重放，可能再次移动、覆盖文件，或者误把「原文件不存在」当成另一个错误。这就是幂等性问题的来源，也是讲义要求「稳定操作标识 + 记录已执行结果 + 让重复请求得到相应回复」的原因。

四、局部合理不等于整体合理：把思想实验写成能跑的检查

讲义用一个刻意夸张的思想实验量化组合风险：安装十个自动上下文压缩插件，每个都把前一个的输出压缩到一半。如果它们确实依次作用于同一份上下文，剩余长度就是 (1/2)^10 = 1/1024。讲义立刻为这个算式加了限定——它不是对真实压缩算法的实验结论。

这个限定很重要，但这个算式可以变成一条每轮都能跑的检查。下面这段代码只做一件事：把「每个插件各省一半」这件事在链式作用下算到底：

def chain(n, factor=0.5):
    remaining = 1.0
    for _ in range(n):
        remaining *= factor
    return remaining


def main():
    for n in (1, 2, 5, 10):
        r = chain(n)
        print("插件数 {:2d} → 剩余上下文 {:.4f}（保留 {:.3f}%）".format(n, r, r * 100))
    print()
    print("每个插件单独看：100% → 50%，各省 50%；合起来看，第 10 个之后什么都不剩。")
    print("注意：这里算的是组合效应，不是任何真实压缩算法的效果。")


if __name__ == "__main__":
    main()
插件数  1 → 剩余上下文 0.5000（保留 50.000%）
插件数  2 → 剩余上下文 0.2500（保留 25.000%）
插件数  5 → 剩余上下文 0.0312（保留 3.125%）
插件数 10 → 剩余上下文 0.0010（保留 0.098%）

每个插件单独看：100% → 50%，各省 50%；合起来看，第 10 个之后什么都不剩。
注意：这里算的是组合效应，不是任何真实压缩算法的效果。

它把讲义的判断落成可检查的形式：每个插件单独看都在省一半，合起来看是指数衰减。 讲义的那句总结可以直接当规则用——每个插件单独都觉得自己在节省上下文，合起来可能把有用信息压没了；即使不存在顺序争议，局部合理也不保证整体合理。

同一节的另外两种冲突更值得警惕，因为它们不是「数量级」问题而是「谁说了算」问题：顺序冲突（A 改写输入、B 检查输入，先改后查就查的不是同一份东西）与决策冲突（两个 Hook 各自合理，却一个要求继续执行、另一个要求停止）。讲义给的结论是：「彻底解耦合」并不意味着不需要共同规则——哪些事件由谁负责、哪些行为可以同时存在、冲突时如何决定、卸载后有哪些状态需要处理，都需要明确；接口把协作集中到了可讨论的位置，也把原来藏在实现里的语义冲突暴露了出来。

五、给自己的系统做一次假设体检

讲义把落点收回到工程师的日常动作上，这句话适合原样抄下来：

对工程师来说，眼前可以做的，是不断检查：自己的系统和组织还在依赖哪些已经松动的前提？

按上面这张表，体检可以具体成四个问题：

  1. 我的抽象隐藏了什么物理约束？ 内存、连接数、进程名额、磁盘——「像是拥有自己的机器」的那些地方，出问题时你打算走到哪一层去看？
  2. 哪些选择是我替需求固定下来的？ 每一处提前设计的扩展点都暗含一个预测；写下这个预测，就是写下它的失效条件。
  3. 外部副作用落在谁的边界里？ 事务、支付、发信、写文件——回滚能覆盖到哪一步？
  4. 我的插件链里有没有指数项？ 单个插件省一半很美，串起来就什么都没剩——这条可以像上面那段脚本一样，每轮跑一次。

第 1、3 条是第 9 讲的直接结论，第 2 条来自第 7 讲（哪些意图必须固定下来），第 4 条是本讲插件部分给出的组合风险。

六、边界

  • 四个案例的措辞与引文均取自讲义原文（2026-11-20 抓取核对）；第二节的「时间尺度」表格是本文自己的归类，讲义未给这个分层。
  • 第四节那段脚本是思想实验的机械版，它只演示组合效应，不评价任何真实压缩算法；讲义原话也明确说这个算式不是实验结论。
  • 讲义第五例（MapReduce → Spark → Flink）本文只在下表中提了一句位置，展开它是另一个题目——「需求带着整个技术栈一起重组」这条线索已由 Agent Native 开发 与 DeepSeek Harness 两篇分担。
  • 事件溯源的机制细节（重算、投影、外部副作用）另有专文：让结论可解释：事件溯源、CQRS 与需求变化的位置、「需求改一处要跟几处」。
