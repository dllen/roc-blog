EvoOntology 详解：给数据 Agent 配一个会进化的语义字典

#EvoOntology#数据 Agent#本体#Text-to-SQL#MCP

一句话总结

EvoOntology 相当于给数据 Agent 配备了一个活的语义字典——不再靠提示词里塞死板的字段说明，而是让 Agent 在运行时动态查询一个会自动学习、纠错、进化的语义层，把 Agent 和数据库之间的“语言鸿沟“彻底打通。

1. 背景：Agent 和数据之间的“鸡同鸭讲“

想象你派一个实习生去管理公司的数据库，他从来没学过你们公司的业务。第一天你把他扔进去，说“随便用，有问题问我“。他连“用户等级“是什么、“订单状态“字段有哪些值都不知道，只能乱猜——效率可想而知。

这就是当前数据 Agent 面临的困境：

传统方案问题
直接探索原始数据Agent 看到一堆字段名（usr_lv_cd、ord_sts_cd），不知道啥意思
手动写死语义到提示词换个数据库/表格，所有提示词全部重写；而且无法适应 Agent 行为差异
通用工具调用Agent 知道“能查“，但不知道“查什么语义上有意义“

类比一下：

  • 直接探索原始数据 = 给你一本乱码字典让你查单词
  • 手动写语义提示词 = 雇一个翻译员，但这个翻译员只会背固定的单词表
  • EvoOntology = 给你一个活的语言助手，能实时翻译、还能根据你用过的词自动学习新词

2. 核心架构：三层语义 + MCP 协议

EvoOntology 把语义层设计成了一个自管理的知识库，通过 MCP 协议暴露给 Agent 查询。整个系统分三层：

┌─────────────────────────────────────┐
│          EvoOntology                 │
│     (动态演化的语义层)                │
└────────────────┬────────────────────┘
                 │
        ┌────────┴────────┐
        ▼                 ▼
 ┌─────────────┐   ┌─────────────┐
 │  Schema 层  │   │  Content 层  │
 │  (骨架)     │   │  (血肉)      │
 └─────────────┘   └─────────────┘
        │                 │
        └────────┬────────┘
                 ▼
         ┌─────────────┐
         │   Tool 层    │
         │  (暴露接口)  │
         └─────────────┘

2.1 Schema 层, “字典的偏旁部首规则”

定义四类节点的字段规范、允许的语义关系类型、以及引用模式的约束。相当于字典的“使用说明“：告诉你这本字典里有哪些类型的词条，它们之间可以怎么互相关联。

四类节点：

  • Term（术语）：业务概念，如“活跃用户“、“订单总额”
  • Mapping（映射）：从原始字段到语义的对应关系，如 usr_lv_cd → “用户等级”
  • Constraint（约束）：业务规则，如“订单状态只允许 5 种值：pending/paid/shipped/delivered/cancelled“
  • Evidence（证据）：这个语义是怎么来的、历史交互记录

2.2 Content 层, “活的内容本身”

一个带类型的语义图，存储具体的业务知识：

  • Term（术语）节点：包含业务术语的定义、别名、同义词
  • Mapping（映射）节点：原始字段名 ↔ 业务语义 的对应关系
  • Constraint（约束）节点：字段取值范围、业务规则
  • Evidence（证据）节点：这条知识的来源和验证记录

语义关系（Semantic Relations）把 Terms 连接起来，比如：

"活跃用户" --is_a--> "用户"
"活跃用户" --has_state--> "活跃/不活跃"
"订单" --contains--> "订单明细"

2.3 Tool 层, “查询接口”

暴露三个 MCP 工具：

  • browse_semantics：浏览/搜索语义（类似字典查词）
  • resolve_semantics：解析具体字段的语义（给定字段名，返回业务含义）
  • Session Manifest：当前会话的语义上下文摘要

2.4 为什么用 MCP？

MCP（Model Context Protocol）就像一个标准插座——不管你用的是 Claude、GPT-5 还是 Codex，只要插上 MCP 就能用。论文做了 Claude Code 和 Codex 两个插件。

3. Builder Agent：从零自动构建本体

传统方案需要业务专家手工填写语义层，工作量巨大且容易出错。EvoOntology 的 Builder Agent 自动从原始数据和真实查询日志中学习。

构建流程：

原始数据（表结构、字段、样本行）
        │
        ▼
[第一步] 从查询日志中提取候选概念
        │  "用户问了过去30天的活跃用户"
        │  → 提取出候选术语："活跃用户"、"时间范围"
        ▼
[第二步] 验证候选概念
        │  对比原始数据源，确认概念有对应字段支撑
        │  "活跃用户" 对应 `last_login_date` 字段
        ▼
[第三步] 发布 ontology_v0
        │  打包成一整套 Schema + Content + Tool 定义
        ▼
        ✓ 初始本体构建完成

关键思想：本体是“可训练的 Agent 状态“，而不是模型权重。就像微调模型能适应新任务一样，这个本体能适应新的数据源和查询模式。

4. 自我演化机制：配对评估，只进不退

这是 EvoOntology 最核心的创新点。本体不是建好就完事了，而是持续根据实际使用效果进化。

演化循环四步：

  ┌──────────┐     Agent 查询本体      ┌──────────┐
  │  Use     │ ◄───────────────────── │ Data     │
  │  Phase   │                        │ Agent    │
  └────┬─────┘                        └──────────┘
       │ 记录交互轨迹
       ▼
  ┌──────────┐     分析历史行为       ┌──────────┐
  │ Diagnose  │ ─────────────────────► │ Evolve   │
  │ 诊断      │                        │ Agent    │
  └────┬─────┘                        └────┬─────┘

类型化编辑 + 配对评估

配对评估是核心创新。给定一个本体的“修改提案“（比如新增一个术语），系统会：

  1. 同时运行两个版本：用旧本体跑 N 个查询，用新本体跑同样的 N 个查询
  2. 对比结果：哪个版本生成的结果更好？
  3. 只接受改进：只有当新本体在多数查询上不输于旧本体时，才接受这次修改

这就是“只进不退“的保证：如果新版本没有改进，就保留旧版本；如果有改进，才更新。

这种“配对评估 + 严格接受“的机制，让本体在不断适配新场景的同时，不会因为错误修改而退化。

5. 实验效果

论文在多个 Text-to-SQL 和数据分析基准上验证了 EvoOntology 的效果：

  • Text-to-SQL：Agent 理解字段语义，写出正确 SQL
  • 数据分析：理解“活跃用户“、“留存“等业务概念
  • 多数据库/多表格：统一语义层，跨源查询
  • RAG 增强：本体可以作为知识图的补充，提供结构化语义

6. 总结

EvoOntology 的核心贡献：

  1. 架构创新：提出 Schema / Content / Tool 三层本体架构，通过 MCP 协议动态暴露给 Agent
  2. 自动构建：Builder Agent 从原始数据和查询日志自动构建初始本体，无需人工标注
  3. 自我演化：类型化编辑 + 配对评估机制，确保本体只进不退、持续优化
  4. 通用插件：Claude Code / Codex 插件生态，一键接入现有 Agent

一句话本质：把语义层从“提示词里的静态文字“变成“运行时可查询、可学习、可进化的动态知识服务“。
