WFM 详解：Wiki 记忆的专用检索模型

#WFM#Wiki 记忆#RAG#LLM#腾讯优图

一句话总结

WFM 是一个专门为“互相链接的 Markdown 文件夹“这种记忆格式训练的检索模型，它把整个 Wiki 图谱当作一个整体来检索，而不是像传统 RAG 那样孤立地搜索每个文档。腾讯优图实验室与 Monash 大学联合提出，分布式训练速度比传统方案快 10.5 倍。

背景：为什么普通 RAG 不适合 Wiki 格式的记忆？

Agent 的记忆正在“升级“

现代 AI Agent 需要长期记忆——比如记住用户上个月提过的需求、之前讨论过的技术方案、阅读过的文档要点。

早期方案：把所有对话记录往向量数据库里一存，靠相似度搜索（普通 RAG）来找内容。

问题来了——当 Agent 把记忆组织成 LLM Wiki 时，情况变了：

  • 每一篇笔记是一个 Markdown 文件
  • 文件之间通过 [[双向链接]] 互相引用
  • 有的页面是概念定义，有的页面是具体案例，有的页面是人物关系图谱
  • 整个文件夹形成了一张语义网络

这种情况下，普通 RAG 遇到了瓶颈：

普通 RAG 的做法Wiki 记忆的真实情况
把每个文档单独向量化Wiki 页面之间有丰富的链接关系，这些关系在孤立 embedding 中丢失了
靠关键词或语义相似度找 Top-K 文档多跳问题需要“A 链接到 B，B 链接到 C，所以 A 和 C 有什么关系“
没有结构概念Wiki 有页面类型（概念、人物、事件）、链接类型（属于、导致、相关）

类比一下：普通 RAG 像是在图书馆里凭感觉找书（哪本书标题相似就拿哪本），而 Wiki 记忆实际上是一张布满交叉引用的参考书网络——你必须理解引用关系，才能回答“A 书第 3 章引用了 B 书，而 B 书的作者同时写了 C 书，那他们三个之间有什么关系“这种多跳问题。

核心方法：三板斧

第一板斧：统一图表示

WFM 的做法是把文本和链接融为一张图，叫 Wiki Graph Schema：

  • 节点 = 页面内容 + 元信息：每个 Wiki 页面是一个节点，节点里存着完整的 Markdown 文本内容
  • 边 = 链接关系：页面之间的 [[双向链接]] 变成图上有方向的边
  • 统一表示：文本语义和图结构同时编码，不拆开

这样设计的好处是：检索时不仅能找到语义相关的页面，还能顺着链接结构“走动“，探索关联内容。

第二板斧：查询条件化检索——“带着问题在图上走”

传统 RAG 是：问题 → 直接找最相似的文档

WFM 是：问题 → 在 Wiki 图上通过消息传递逐步扩散 → 注意力聚合收拢

给定一个查询（用户的问题），模型会：

  1. 在图上做消息传递（Message Passing）：从查询相关的节点出发，沿着链接向外扩散信息，每一步都结合边的方向和目标节点的文本内容
  2. 条件化处理：扩散的方式由查询内容决定——问技术概念就多往定义页面走，问人物关系就多往人物页面走
  3. 注意力聚合：最后把所有扩散结果汇总，不同节点的重要性由注意力分数决定，同时加入一个“注意力方差正则项“来防止注意力过度集中（否则就退化成普通 RAG 了）

简单类比：传统 RAG 像是让 100 个人各自独立投票选答案，WFM 则像是开一场议事会——每个人（节点）先和邻居讨论（消息传递），然后汇总讨论结果（注意力聚合）。

第三板斧：专为 Wiki 格式设计的训练目标

WFM 不是简单拿现成的检索模型套用，而是针对 Wiki 的结构特点设计训练目标：

  • 让模型同时学习：文本语义 + 链接拓扑结构
  • 通过注意力方差正则项，确保模型不会只盯着少数几个节点不放
  • 训练信号来自 Wiki 本身的结构——链接本身就是监督信号

分布式训练：GPU 到 GPU 直接通信，快 10.5 倍

大模型训练最怕什么？数据在 GPU 之间传来传去的时候卡住。

当 Wiki 图非常大时（比如有数百万个节点），一张 GPU 装不下，需要把图分布到多张 GPU 上。

传统方案：

GPU1 → 把数据发给 CPU 内存 → CPU 整理 → 发给 GPU2

这中间有两次内存拷贝，CPU 成了瓶颈。

WFM 的方案：直接用 NCCL（NVIDIA Collective Communications Library） 实现 GPU 到 GPU 直接交换，不经过 CPU。

结果：训练速度提升 10.5 倍。

打个比方：传统方案像是寄快递要先送到市级分拣中心再转发，WFM 的 NCCL 方案像是城市之间的光纤直连——数据直接从发送方 GPU 到达接收方 GPU，中间的网络设备支持 RDMA（远程直接内存访问），不需要 CPU 介入。

实验效果：五个基准测试，表现优异

论文在五个长期 Agent 记忆和多跳推理基准上进行了评估：

基准类型评估内容
长期 Agent 记忆Agent 能否从 Wiki 记忆中准确回忆多个月前的细节
多跳推理能否回答“A 和 B 有关，B 和 C 有关，所以 A 和 C 有什么关系“这类问题
跨文档聚合能否把多个相关页面的信息综合起来形成完整答案

结果显示 WFM 在所有基准上均达到了“remarkable performance“（显著优异的表现），说明专门为 Wiki 图格式设计的检索模型确实比通用 RAG 更适合这类场景。

为什么这是为“Markdown 文件夹“专门设计的？

这是理解 WFM 最重要的点。

普通 RAG 的设计假设

  • 知识库 = 一堆独立文档的集合
  • 文档之间没有关系，或者关系可以忽略
  • 检索 = 在一堆文档里找最相关的那几个

WFM 的设计假设

  • 知识库 = 一个 Wiki（由双向链接组织起来的页面网络）
  • 页面之间有丰富的拓扑关系，这些关系本身就是语义的一部分
  • 检索 = 在一张图上做多跳探索和聚合

如果你正在用 Obsidian、Notion 或者任何支持双向链接的工具管理笔记，你的知识库本质上就是一个 LLM Wiki。 这种场景下：

  • 用普通 RAG = 用图书馆的索引系统管理一张地铁图（不是不行，但很别扭）
  • 用 WFM = 用地铁图本身的换乘逻辑来管理地铁图（原生匹配）

WFM 特别适合的场景

  1. 个人知识管理：Obsidian vault、Notion 页面网络
  2. Agent 长期记忆系统：多轮对话中 Agent 自己构建的 Wiki 记忆
  3. 企业内部知识库：文档之间有大量交叉引用的场景（如技术文档体系）
  4. 研究笔记网络：论文、概念、实验记录相互链接的学术笔记体系

总结：WFM 解决的是什么问题？

痛点：Agent 的记忆是 Wiki 格式（互相链接的 Markdown），但普通 RAG 读不懂链接关系

WFM 的答案：
1. 把 Wiki 建模为一张统一的图（文本 + 链接不拆分）
2. 查询时在图上做消息传递（条件化扩散）+ 注意力聚合
3. 专门训练模型理解 Wiki 结构
4. 分布式训练用 NCCL 直连 GPU，极速

结果：专门为"Markdown 文件夹"这种格式打造的检索模型，
      在多跳推理和长期记忆任务上显著优于通用 RAG 方案。
