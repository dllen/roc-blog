Eval 设计与自动爬坡：为什么你的评测在骗你

#AI#Evaluation#Agent#LLM

先说结论：Eval 设计与自动爬坡这两件事，真正的产出不是分数，而是归因。看到涨，你要能说清是哪个改动涨的、涨的是不是生产里也在发生的事。做不到这两点，评测就只是给了你一个说服自己的理由。

Anthropic 的 Lance Martin 在 Automating eval design and hillclimbing with Claude 里给出了完整做法：评测设计四要素、自动爬坡（hillclimbing）三条选面原则，以及把这两件事包进 Claude Code 的 /claude-api build-eval 和 /claude-api hillclimb 两个命令。

他的团队在一个 44 条工单的客服 benchmark 上跑出了很干净的结果：Opus 4.8 高 effort 起步 74.4%、每张工单 4.6 美分；换成 Opus 5.5 低 effort 到 87.8%、1.9 美分；再试 Sonnet 5 低 effort，88.9%、约 1 美分；最后补上路由规则和退款上限的交叉引用，98.9%。在 14 条从没被测过的留出工单上，最终配置 90.5%，原始配置 78.6%，成本约为原来的五分之一。

这条路是真的走得通。但原文把留出集当成过拟合的主要解药，我读下来觉得需要补一刀：留出集防的是「背例子」，防不住「评测本身采错了」。下面第 5 节我自己写了个模拟把这件事量化了，虚报幅度差 5 倍多。

一、好评测的四个要素

原文的四条，我按可操作性重排：

任务分布要对齐生产。 样本要来自你真正在意的场景，而不是「好生成」或「好判分」的题。这条最难做到，也最容易自欺——因为不对齐的时候，评测照样能跑、照样出分、照样让你觉得在进步。

更强的模型、更高的思考预算，得分应该更高。 如果新一代模型高预算还打不过上一代低预算，先别庆祝，去怀疑题目有歧义或者判分器坏了。这是全流程里最便宜的一次校准。

前沿要留出可提升空间。 最强模型 + 最高预算应该明显低于 100%，否则改动带来的差异全被天花板吃掉。这里的坑是「靠不可能完成的题凑出来的低分」：一道题反复跑都失败，或者两个领域专家会给出不同判定，都是坏题的特征。

跑与跑之间的方差要低。 方差经常不是模型的锅：题目歧义、判分器对相同输出给出不同结论、effort 参数没真正生效、上一轮残留的文件或 git 历史把答案递给了 agent。

我想补第五条，它贯穿全文但原文没单列：先算噪音预算，再谈改进。44 条样本、80% 准确率时，二项分布的一个标准差约 6 分。也就是说 6 分以内的「提升」在统计上和扔硬币没区别。原文的 hillclimb 会在开跑前检查「eval 噪音是否小于你能接受的最小改进」，不满足就建议加样本——这一步应该提前到写题的时候，而不是等爬坡跑空了两轮才发现。

二、采样：模型能力是锯齿状的

如果专挑「今天模型做错的」当评测题，你采到的是这个模型能力地形的谷底。最后测出来的不是「这个任务本身难」，而是「这个模型的失败指纹」——换一代模型，这套题就失效了。

替代做法三条：

  • 因为人类判定它难才收进来，而且你要能说出为什么难；
  • 收自己应用里的具体失败：生产流量、bug 报告、工单；
  • 别盲信用户流量——用户往往只试他们觉得会成功的东西，纯按流量采会偏简单。

三、评分器：先验判官，再信分数

选择原则是最便宜的够用方案：输出可判定（分类标签、JSON schema、测试是否通过）就用程序化校验；开放、多解但有明确质量标准才上 LLM-as-judge；有基线可比就做成对比较——随机顺序、不告诉判官哪个是基线。

两条纪律比选型更重要：

rubric 写成可核查的断言，不要 1–5 分。 1–5 分的问题不是不精确，是它把「为什么」藏起来了，你没法复核。

judge 不能是被测模型自己。 同源模型打分有自我偏好，这是 auto-eval 系统里最常见的系统性偏差。

再加一条原文说得最直白的：判分前必须读一批被判过的 transcript。评分配置错误是评测失效最常见的原因，而它只在你看过原始判分过程时才暴露。实现侧的判官细节——指标怎么选、哪些老教程已经过时——可以对照 DeepEval v4 的三层判官架构 一起看。

四、自动爬坡：一次只动一个面

爬坡适合调 prompt、skill、tool 描述、模型与 effort、harness 代码这类成本低、可回滚的面。选面看三条：

迭代要便宜。 文本改动最小、回滚最容易；开放式的 harness 改造涉及大量代码，爬坡会卡住。

效果要可归因。 改 skill 描述，指标就该是 skill 触发率——两者直接挂钩。一次改五个地方再看总分，等于什么都没测。

目标要收口。 开放式的「把它变好」是最常见的失败模式。原文提到一个几乎总能用的目标：保性能降成本。即使评测已经饱和，成本还有空间——这条线上的账我们之前单独算过：每个 Agent 任务的 token 成本。

原文的爬坡器每轮只做一件事：读上一轮 train 的失败 transcript，提一个补丁，跑评测；train 涨、test 也涨就留，train 涨、test 走平就判过拟合回滚，出现回退就回滚。分数卡住两三轮，就停下来把所有剩余失败按根因归类，而不是继续瞎试——这一步经常抓出的是坏题和 harness 错误，而不是模型问题。

五、过拟合有两层，留出集只防第一层

原文列了三条对策：切分 train/test、不把看到的失败内容贴进 prompt、让答案在结构上不可达。问题在于它们各自管什么，原文没拆开。

第一层：背例子。 爬坡器读到 train 里某几条失败，加一条特判把它们修好。eval 涨，生产不动甚至变差。留出集能抓——train 涨、test 走平就是信号。

第二层：eval 采样偏移。 eval 里混着生产里已经不存在的 Case：旧格式、已下线的接口、当年才会出现的话术。爬坡器为它们加工具、加规则，train 和 test 一起涨——因为两者来自同一份有偏的 eval。留出集在这里彻底失效：它只保证 test 没被爬坡器看过，不保证 test 代表生产。

第二层的唯一解药是回到第一步：把 eval 采成生产的分布。原文其实写了（「eval tasks mirror production」），但放在设计原则里，读起来像可选的最佳实践；在真实流水线里它是前置条件——不满足的话，后面所有自动化都在优化一个错误的函数，而且优化得很高效。

六、我按它的规则跑了一遍

我把原文的三条判定规则抽出来写成模拟：合成一个 4000 条的「生产分布」、一个 120 条的 eval（其中 20 条是生产已淘汰的旧格式，模拟从旧工单采样的偏移），三个候选补丁——背 8 条难例的特判、只对旧格式有用的 handler、对所有请求有效的路由规则。核心判定逻辑就是这几行：

for name in PATCHES:
    d_tr = score(train, adopted + [name]) - score(train, adopted)
    d_te = score(test,  adopted + [name]) - score(test,  adopted)
    if use_holdout:
        keep = d_tr > sigma(len(train)) and d_te > sigma(len(test)) * 0.5
    else:
        keep = d_tr > 0          # 只看 train
    if keep:
        adopted.append(name)

跑三次，换不同策略：

== 只看 train（不设留出集） ==
  special-case-memo        train  +5.0  test  +0.0  → 采纳（train 涨就收）
  add-old-format-handler   train  +1.2  test  +5.0  → 采纳（train 涨就收）
  add-routing-rules        train +12.5  test  +5.0  → 采纳（train 涨就收）
  采纳 3 项；eval +19.8 → 生产 +10.2

== train/test 分流（原文做法） ==
  special-case-memo        train  +5.0  test  +0.0  → 回滚（test 走平）
  add-old-format-handler   train  +2.5  test  +5.0  → 回滚（train 没过噪音）
  add-routing-rules        train +12.5  test +12.5  → 采纳（过噪音且 test 同向上涨）
  采纳 1 项；eval +14.3 → 生产 +12.0

  add-old-format-handler   train  +0.0  test  +0.0  → 回滚（train 没过噪音）
  add-routing-rules        train +12.5  test +15.0  → 采纳（过噪音且 test 同向上涨）

三个能直接拿去用的观察。

不设留出集时，eval 会奖励「背例子」。 那条特判让 train 涨 5 分、test 涨 0 分、生产反而退 1.8 分，但它被采纳了——因为只看 train 的规则里没有「涨得对不对」这一项。注意它的 train 涨幅（+5.0）还略微超过了噪音门槛（4.5），也就是说只加噪音门槛也不够，必须看第二个分布。

分流把虚报砍掉四分之三，但没归零。 剩下 2.3 分来自三处：小样本随机波动（test 只有 40 条，1σ 就有 6.3 分）、旧格式 handler 的无效增益、以及「test 涨过半个 σ」这个阈值本身是我拍的。

旧格式 handler 在分流下依然通过（train +2.5、test +5.0，同向）。这不是 bug，是留出集的边界：train 和 test 来自同一份有偏的 eval，删掉旧格式后它的增益立刻归零。能挡住分布偏移的只有重新采样，没有别的机制。

还有一条阈值纪律值得单独记：test 只有 40 条时，一个 3 分的真实回退在统计上是隐形的。所以「train 涨、test 走平就回滚」实际只能挡住「test 完全不动」这种明显情况，小回归会漏过去。要么把 test 做大，要么接受「被采纳的改动里有一部分是噪音」这个事实，在合并前用人工复核兜底。

七、落地到中文环境

原文的流程绑在 Claude Code 的 claude-api skill 上，搬到国内要处理四件事：

工具链要自己搭。 这两个命令本质是「一段写死的流程 + 一把脚本」，规则在上面五节里已经写全了，任何能读写文件、能跑命令的 agent 都能复刻。难的不是命令，是忍住不去改判定规则。

judge 与被测模型同源的问题更严重。 国内可选模型少，很容易变成「用 A 家模型测 A 家模型」。能拆就拆，拆不开就把 rubric 写得更机械（断言式），并在报告里注明 judge 是谁。

成本结构不同，轮数可以放宽。 原文精算到「每张工单 4.6 美分 → 1 美分」是因为要对外报成本；国内单价低一个量级，同样的预算可以多跑几轮、多切几次 test。但样本量买不来分布正确——这是唯一不能靠多花钱解决的问题。

生产 transcript 的采集要过合规。 原文要求先问 retention 与敏感数据政策；在国内这步不是可选项，要么在采集侧脱敏，要么评测集只留结构不留原文。

如果明天就要在真实项目里落地，顺序我会这么排：

  1. 写 5–10 条手写题，每条写一句「为什么它难」；说不出来的删掉。
  2. 定评分方式：能程序化就别用 judge；用 judge 就把 rubric 写成断言，judge 换一家模型。
  3. 算噪音：1σ ≈ sqrt(p(1-p)/n)。样本不够先扩样本，别急着爬坡。
  4. 拿一批生产 transcript 做分布对照，对不齐就先修 eval——这步不做，后面全是白干。
  5. 切 train/test，爬坡开始前把改动面限定成一个。
  6. 每轮只改一处，记录 train Δ / test Δ；test 走平就回滚，别解释。
  7. 收尾看两件事：test 增益是否超过噪音、这个改动能不能一句话说清为什么有效。说不清的别合。
