规格的三笔账：采样、损失与组合

#AI工程#技术深度#大会笔记

规格的三笔账？验证 spec 的那几步到底该怎么定参数、歧义造成的损失能不能在下游补回来、以及「逐句检查」漏掉了什么。我读完 AIE Code Summit 2026 那场《Specs Have Bugs Too》之后，最想验证的是它那句**「LLM 翻译，求解器验证，人类决定」**——这三个环节的参数能不能算出来。这篇把它算出来。

口径说明

  • 源是我自己的精读笔记 02-课程体系/AIE-Code-Summit-2026/05-预录插播/07 Rajath Kotyal - Specs Have Bugs Too.md（约 12,600 字）。官方稿是录屏自动转写，本文按导读式处理：不引用译文原文、不搬附件图，只复述机制与讲者给出的数字。
  • 官方稿的转写限制：专名（团队成员姓名、工具名 Kero specification analyzer）以官方稿为准，未经外部核实；笔记里对 “AT bench / hugging face” 一类术语转写存疑，只在有把握处保留原文。
  • 动机数字必须带限定：讲者说这些来自「近期的公开研究」，官方稿并未给出出处——本文一律写成「讲者引用的研究数据」，不当成已核实结论。
  • 我为了建模补的（单次翻译的主流概率 p、下游验证器假阴性率、等价类数 K、每句的读法数）都标为「估」。
  • 三个脚本只依赖 Python 标准库；输出为实跑结果，逐行可复现（无随机数，两次运行输出一致）。
  • 撞题与边界：本系列已发《评测与测试的三笔账》——那篇讲评测集怎么造、回归阈值怎么定、怎么防污染；本文讲的是更靠上游的一环：规格本身有没有 bug，以及怎么验它。两者不共用数字。

一、讲者的骨架：让验证不依赖「人作为第一审阅者」

Rajath Kotyal 属于 AWS 自动化推理（automated reasoning）团队，讲的项目是 Kero specification analyzer：用形式化方法 + 自动化推理去验证那些「在 coding agent 写代码之前就会提交给它」的规格。

触发案例是一份电商规格里的两条规则：

  • 规则二：当订单被提交、且库存不可用时，把该订单列为 backorder（延期订单）——单独读完全合理。
  • 同一份规格里还有另一条规则：不允许把任何订单列为 backorder。

单独读每条都成立，但一个 LLM 同时读到两条时，两者不可能同时被满足（讲者原话：“individually read, these two lines make sense… but both cannot hold through at the same time”）。这就是需要解决的核心歧义。

动机数字（讲者引用的近期公开研究）：提示不明确时，LLM 生成的准确性与代码准确性下降 20%–40%；60%–90% 的有效代码在写完之后仍然是错的；在这种情况下，代码部署后出现的回归问题多两倍。于是问题变成：这类错误藏在哪里？ 他的答案是：藏在 spec 里。目标是在它们进入代码库之前就发现。

一个很精确的目标设定：验证的是「没有人类（或任何人）作为第一个审阅者读过这些文件」的情况。

两个尺度的问题：句内——歧义（ambiguity）、措辞不当（wording）、细节层次不足；跨句——规则之间的冲突（conflicts）与空白（gaps）。因此需要三种检查能力：审查单句、在句之间搜索、发现歧义。

三步流程：

  1. LLM 先自己优化措辞。 如果成功当然好——但这只处理了句内的 wording 问题。
  2. 优化不成，把英文形式化为 SMT 公式。 SMT（SMT-LIB）是一类函数表达式，交给 SAT 求解器 / 可满足性检查器，求解器返回一个布尔值：这个表达式是否有效（valid）、为真还是为假。
  3. 拿到结果后分流：表达式有效 → 什么都不做（silent pass）；求解器检测到两句之间或一句之内存在歧义（一句话有两种含义）→ 把这个句子交回 LLM 重新检查，LLM 重新表述后再次验证。

深挖：多次采样 + 逻辑等价聚类。 发现可疑句子后，他们再做一轮三步流程，重点是反复测试翻译结果：让 LLM 翻译 7 次或 10 次，以判断「这个 LLM 是真的就是这样表现的，还是有什么外部因素把它推到了这个状态」。然后按逻辑等价性对这 7–10 组解释做聚类，看清「这些解释分别落在 LLM 自己做过的哪一组假设下」。聚类之后有三个出口：接受当前状况；要求用户消除歧义；放弃——不在代码库里实现这条规则。

三类缺陷的可操作样例：歧义——「删除记录」这句话非常模糊，LLM 可以随意解释但不能允许；工具的做法是给出两个选项让人选：要么按现状删除记录，要么保留记录但对用户隐藏。冲突——前面那条规则一与规则三冲突。空白——当 LLM 检测到某条实际存在的流程或管道时，发现没有对应规则覆盖它，也就是你缺了东西。

边界与分工：对这三类问题，他讲得很坦白——「归根结底，除了用户之外，我们无法保证有任何其他机制来确保规范的准确性。」 用户必须在把片段发给 LLM 之前，逐条检查规则手册里的每一部分；用户更重要，因为规范里包含隐含的领域知识（implicit domain knowledge），LLM 不了解多少领域知识，也没有任何保证。他同时承认当前对「形式化方法及其在 agent 中的应用」的证据还很薄（thin evidence），这项技术仍在探索阶段。

带走的结论（他自述）：① 把 spec 交给 agent 之前，务必先检查它。 ② 对翻译结果做聚类——按逻辑等价项聚类，以确定 LLM 的不同解释以及真正出错的地方。职责分工一句话：LLM 翻译，求解器验证，人类决定。 如果选项里没有合适答案，就用 LLM judge 裁决，或者干脆不实现这一段。

二、增量一：N=7 还是 N=10，应该反解出来

"""采样 7 次还是 10 次？N 应该由「检出第二种解释的目标置信度」反解出来。

数字取自我的精读笔记：让 LLM 翻译 7 次或 10 次，再按逻辑等价性聚类，以判断「这个 LLM 是真的
就是这样表现的，还是有什么外部因素把它推到了这个状态」。
只依赖标准库；输出确定性。全部用 f-string，避免 %-格式化与中文标点冲突。
"""
import math

TARGETS = (0.90, 0.95)
P_MAIN = (0.70, 0.85, 0.95)      # 单次翻译给出主流解释的概率（估）


def detect_prob(p, n):
    """采样 n 次都没出现非主流解释的概率是 p^n -> 至少检出一个非主流的概率"""
    return 1.0 - p ** n


def n_needed(p, target):
    """反解：1 - p^n >= target  =>  n >= ln(1-target)/ln(p)"""
    return math.ceil(math.log(1 - target) / math.log(p))


print("一、检出「第二种解释」的概率 = 1 - p^N")
print(f"{'主流概率 p':<16}" + "".join(f"{'N=' + str(n):>12}" for n in (3, 7, 10, 15)))
for p in P_MAIN:
    print(f"{format(p, '.2f') + ' (估)':<16}" + "".join(
        f"{detect_prob(p, n) * 100:>11.1f}%" for n in (3, 7, 10, 15)))
print()
print("二、反解：达到目标置信度需要几次")
print(f"{'主流概率 p':<16}{'90% 所需 N':>14}{'95% 所需 N':>14}   讲者给的 7 / 10 够不够")
for p in P_MAIN:
    n90, n95 = n_needed(p, 0.90), n_needed(p, 0.95)
    note = f"90% 需 {n90} 次（讲者取 7，够）" if n90 <= 7 else f"90% 需 {n90} 次，讲者的 7 次不够"
    print(f"{format(p, '.2f') + ' (估)':<16}{n90:>14}{n95:>14}   {note}")
print()
print(f"   => 判据：**N=7 只在「单次翻译的主流概率 <= 0.72」时才够 90% 检出**")
print(f"      （1 - 0.72^7 = {detect_prob(0.72, 7) * 100:.1f}%；而 p=0.85 时 N=7 只有 "
      f"{detect_prob(0.85, 7) * 100:.1f}%，要 N={n_needed(0.85, 0.90)} 才到 90%）")
print("      所以「翻译 7 次或 10 次」不是随手取的数，**它隐含了一个关于模型歧义度的假设**；")
print("      换个模型或换个 spec 域，这个数就得重算。")
print()
print("三、采样的成本：翻译 N 次 + 求解 K 次")
for n, k in ((7, 3), (10, 5), (15, 8)):
    print(f"   N={n:2d} 次翻译、聚成 {k} 个等价类 -> 翻译成本 {n:2d} 个单位、SMT 求解 {k} 个单位"
          f" -> 合计 {n + k:2d} 个单位")
print("   => 判据：**深挖不是免费的**：每多采一次就多一次翻译，每多一个等价类就多一次 SMT 求解。")
print("      N 从 7 提到 15，翻译成本翻倍还多；所以 N 应该由置信度反解，而不是「保险起见多采几次」。")

输出：

一、检出「第二种解释」的概率 = 1 - p^N
主流概率 p                   N=3         N=7        N=10        N=15
0.70 (估)               65.7%       91.8%       97.2%       99.5%
0.85 (估)               38.6%       67.9%       80.3%       91.3%
0.95 (估)               14.3%       30.2%       40.1%       53.7%

二、反解：达到目标置信度需要几次
主流概率 p                90% 所需 N      95% 所需 N   讲者给的 7 / 10 够不够
0.70 (估)                     7             9   90% 需 7 次（讲者取 7，够）
0.85 (估)                    15            19   90% 需 15 次，讲者的 7 次不够
0.95 (估)                    45            59   90% 需 45 次，讲者的 7 次不够

   => 判据：**N=7 只在「单次翻译的主流概率 <= 0.72」时才够 90% 检出**
      （1 - 0.72^7 = 90.0%；而 p=0.85 时 N=7 只有 67.9%，要 N=15 才到 90%）
      所以「翻译 7 次或 10 次」不是随手取的数，**它隐含了一个关于模型歧义度的假设**；
      换个模型或换个 spec 域，这个数就得重算。

三、采样的成本：翻译 N 次 + 求解 K 次
   N= 7 次翻译、聚成 3 个等价类 -> 翻译成本  7 个单位、SMT 求解 3 个单位 -> 合计 10 个单位
   N=10 次翻译、聚成 5 个等价类 -> 翻译成本 10 个单位、SMT 求解 5 个单位 -> 合计 15 个单位
   N=15 次翻译、聚成 8 个等价类 -> 翻译成本 15 个单位、SMT 求解 8 个单位 -> 合计 23 个单位
   => 判据：**深挖不是免费的**：每多采一次就多一次翻译，每多一个等价类就多一次 SMT 求解。
      N 从 7 提到 15，翻译成本翻倍还多；所以 N 应该由置信度反解，而不是「保险起见多采几次」。

三处结论：

第一，「翻译 7 次或 10 次」不是随手取的数，它隐含了一个关于模型歧义度的假设。 检出「第二种解释」的概率是 1 − p^N（p = 单次翻译给出主流解释的概率，估）。p=0.70 时 N=7 的检出率是 91.8%；p=0.85 时只有 67.9%；p=0.95 时只有 30.2%。判据：N=7 只在「单次翻译的主流概率 ≤ 0.72」时才够 90% 检出。

第二，N 应该由目标置信度反解，而不是拍脑袋。 N ≥ ln(1−C)/ln(p)：p=0.70 时 90% 需 7 次、95% 需 9 次；p=0.85 时 90% 需 15 次、95% 需 19 次；p=0.95 时 90% 需 45 次。判据：换个模型或换个 spec 域，主流概率一变，这个数就得重算——而「7 或 10」把假设藏在了流程里。

第三，深挖不是免费的。 N=7、K=3 时是 7 次翻译 + 3 次 SMT 求解；N=15、K=8 时是 15 + 8。判据：每多采一次就多一次翻译，每多一个等价类就多一次求解，所以 N 应该由置信度反解，而不是「保险起见多采几次」。

三、增量二：歧义造成的损失，无法在下游修复

"""歧义的损失无法在下游修复：验证器能把 200~400 缩到 10~20，剩下的必须靠人。

数字取自我的精读笔记（讲者引用的近期公开研究，官方稿未给出处）：
提示不明确时 LLM 生成的准确性与代码准确性下降 20%-40%；60%-90% 的有效代码在写完之后仍然是错的；
在这种情况下部署后出现的回归问题多两倍。
只依赖标准库；输出确定性。
"""
TASKS = 1000
LOSS_LOW, LOSS_HIGH = 0.20, 0.40     # 提示不明确带来的准确率下降（讲者引用的研究区间）
FALSE_NEG = 0.05                       # 下游验证器的假阴性率（估）

lo = TASKS * LOSS_LOW
hi = TASKS * LOSS_HIGH
print("一、每 1000 个任务里，歧义造成多少个错误理解")
print(f"   准确率下降 {LOSS_LOW:.0%}-{LOSS_HIGH:.0%} -> 每 {TASKS} 个任务里有 "
      f"**{int(lo)}~{int(hi)} 个**因 spec 歧义而理解错")
print()
print("二、下游验证器能把它们缩到多少")
for f in (0.01, 0.05, 0.20):
    print(f"   验证器假阴性率 {f:>4.0%} -> 抓到 {int((1 - f) * lo)}~{int((1 - f) * hi)} 个，"
          f"**漏 {int(f * lo)}~{int(f * hi)} 个**进入交付")
print()
print("   => 判据：**歧义造成的损失无法在下游修复**——")
print(f"      验证器（假阴性率 {FALSE_NEG:.0%}）能把每千个任务里的 {int(lo)}~{int(hi)} 个缩到 "
      f"{int(FALSE_NEG * lo)}~{int(FALSE_NEG * hi)} 个，")
print(f"      但**剩下的这 {int(FALSE_NEG * lo)}~{int(FALSE_NEG * hi)} 个不是验证器能修的**："
      "它继承的是同一个错误理解。")
print("      所以验证的价值在于「**发现歧义**」，不在于「在歧义存在时给出正确答案」。")
print()
print("三、这一讲给的流程正好对应这个分工")
print("   LLM 翻译 -> SMT 求解器判定 -> **人决定**（接受 / 要求用户消除歧义 / 放弃不实现）")
print("   判据：**不要让 LLM 同时扮演规格的作者、译者和裁决者**——")
print("      求解器的作用不是「更聪明的模型」，而是一个**与 LLM 无关的确定性裁判**。")
print()
print("四、一个必须避开的坑：不要把三个数字相乘")
wrong = (1 - 0.60) * (1 - 0.40)
print("   若把「60%-90% 有效代码写完仍错」与「歧义导致 20%-40% 下降」相乘，")
print(f"   会得到「正确率只有 {wrong * 100:.1f}%」这种结论——**这是双重计数**："
      "前者是总体缺陷率，后者是其中的一个成因，")
print("   官方稿也没给这两组数字的出处（讲者只说「基于近期的公开研究」），")
print("   引用时必须保留「讲者引用的研究数据」这个限定，不能当成已核实结论。")
print()
print("五、回归「多两倍」的含义")
base = 100
print(f"   若清晰 spec 部署后每版出 {base} 个回归问题，歧义 spec 下是 {base * 2} 个（**多两倍**）")
print("   判据：**spec 阶段的收益是「避免错误被自动写进代码库并扩散」**——")
print("      错误进库之后的修复成本远高于在 spec 阶段拦住。")

输出：

一、每 1000 个任务里，歧义造成多少个错误理解
   准确率下降 20%-40% -> 每 1000 个任务里有 **200~400 个**因 spec 歧义而理解错

二、下游验证器能把它们缩到多少
   验证器假阴性率   1% -> 抓到 198~396 个，**漏 2~4 个**进入交付
   验证器假阴性率   5% -> 抓到 190~380 个，**漏 10~20 个**进入交付
   验证器假阴性率  20% -> 抓到 160~320 个，**漏 40~80 个**进入交付

   => 判据：**歧义造成的损失无法在下游修复**——
      验证器（假阴性率 5%）能把每千个任务里的 200~400 个缩到 10~20 个，
      但**剩下的这 10~20 个不是验证器能修的**：它继承的是同一个错误理解。
      所以验证的价值在于「**发现歧义**」，不在于「在歧义存在时给出正确答案」。

三、这一讲给的流程正好对应这个分工
   LLM 翻译 -> SMT 求解器判定 -> **人决定**（接受 / 要求用户消除歧义 / 放弃不实现）
   判据：**不要让 LLM 同时扮演规格的作者、译者和裁决者**——
      求解器的作用不是「更聪明的模型」，而是一个**与 LLM 无关的确定性裁判**。

四、一个必须避开的坑：不要把三个数字相乘
   若把「60%-90% 有效代码写完仍错」与「歧义导致 20%-40% 下降」相乘，
   会得到「正确率只有 24.0%」这种结论——**这是双重计数**：前者是总体缺陷率，后者是其中的一个成因，
   官方稿也没给这两组数字的出处（讲者只说「基于近期的公开研究」），
   引用时必须保留「讲者引用的研究数据」这个限定，不能当成已核实结论。

五、回归「多两倍」的含义
   若清晰 spec 部署后每版出 100 个回归问题，歧义 spec 下是 200 个（**多两倍**）
   判据：**spec 阶段的收益是「避免错误被自动写进代码库并扩散」**——
      错误进库之后的修复成本远高于在 spec 阶段拦住。

三处结论：

第一，每千个任务里有 200~400 个因 spec 歧义而理解错（讲者引用的研究：提示不明确导致准确率下降 20%–40%）。判据：歧义是「上线前」的问题，不是「上线后」的问题。

第二，下游验证器能把 200~400 缩到 10~20，但剩下的修不了。 假阴性率 1% → 漏 2~4 个；5% → 漏 10~20 个；20% → 漏 40~80 个。判据：那剩下的 10~20 个不是验证器能修的——它继承的是同一个错误理解。所以验证的价值在于「发现歧义」，不在于「在歧义存在时给出正确答案」。这也正好对应讲者的三段分工：LLM 翻译 → SMT 求解器判定 → 人决定；不要让 LLM 同时扮演规格的作者、译者和裁决者——求解器的作用不是「更聪明的模型」，而是一个与 LLM 无关的确定性裁判。

第三，一个必须避开的坑：不要把几个数字相乘。 把「60%–90% 有效代码写完仍错」与「歧义导致 20%–40% 下降」相乘，会得出「正确率只有 24.0%」这种结论——这是双重计数：前者是总体缺陷率，后者是其中的一个成因。官方稿也没给这两组数字的出处。判据：引用时必须保留「讲者引用的研究数据」这个限定。

第四，「回归多两倍」是这条流程真正的收益来源。 若清晰 spec 部署后每版出 100 个回归问题，歧义 spec 下就是 200 个。判据：spec 阶段的收益是「避免错误被自动写进代码库并扩散」——错误进库之后的修复成本远高于在 spec 阶段拦住。

P_MAIN = 0.85            # 单次翻译给出主流解释的概率（估，与采样模型同一个假设）


def expected_classes(n, p):
    """现实期望：主流解释占 p，其余每次采到彼此不同的读法 -> 期望等价类数"""
    return 1 + (1 - p) * (n - 1)

三处结论：

第一，联合读法是乘性的。 m 条约束句、每句两种读法 → 2^m 种联合读法：m=3 → 8 种、m=5 → 32 种、m=10 → 1,024 种、m=15 → 32,768 种。判据：逐句检查漏掉了组合歧义——每句单独都清楚，合起来仍有 2^m 种读法。

第二，采样次数与组合空间不是一个量级。 最坏情况（每次都采到全新读法）下要覆盖 90% 的组合空间，m=5 需 29 次、m=8 需 231 次、m=12 需 3,687 次；现实里主流解释占 85%（估），10 次采样期望只看到 2.35 个等价类，m=12 时覆盖率 0.057%。判据：N 次采样最多只能看到 N 个等价类，而组合空间是 2^m——聚类压缩的是重复解释，不是组合空间。所以真正能收敛组合爆炸的不是「多采几次」，而是把约束写成 SMT 交给求解器逐条判冲突：求解器面对的是公式之间的可满足性，不是采样出来的句子集合。

第三，聚类的工程价值在于把不确定性变成选项。 原始翻译数 N → 逻辑等价类数 K → 三个出口（接受 / 要求用户消除歧义 / 放弃不实现），对用户展示的选项数是 K（估 3），不是 N。判据：把「模型有多种合理解释」从隐藏的随机性变成可枚举、可展示给人选择的选项——这正是讲者那句「按逻辑等价性聚类」的价值所在。

第四，五类缺陷各自的检查者不同。 句内 ambiguity → 多次采样 + 逻辑等价聚类；句内 wording → LLM 先自己优化措辞；句内细节层次不足 → 需要人（隐含领域知识）；跨句 conflict → SMT/SAT 求解器判定；跨句 gap → 对照实际流程/管道人工核对。判据：形式化方法只能发现「形式化之后仍然可见」的冲突与空白——一旦关键判断依赖领域知识（「延期订单」业务上到底允不允许），形式化无法替你做，只能把选项摆出来让人选。

五、把三个模型套回本章（判据清单）

  1. 检出第二种解释的概率 = 1 − p^N；N=7 只在 p ≤ 0.72 时才够 90% 检出。
  2. N 由目标置信度反解：N ≥ ln(1−C)/ln(p)；p=0.85 → 90% 需 15 次、95% 需 19 次；p=0.95 → 90% 需 45 次。

  4. 歧义造成的损失无法在下游修复：每千任务 200~400 个错误理解，验证器假阴性率 5% 也只缩到 10~20 个。

七、这三个模型判不了什么

  • 单次翻译的主流概率 p、下游验证器假阴性率、每句的读法数（我取 2）、等价类数 K 全是估的。其中p 直接决定 N 该取多少——p=0.70 与 p=0.85 之间，90% 检出所需的 N 从 7 变成 15，这是整个第一节最敏感的参数。
  • 「每句两种读法」是最简假设。真实 spec 里有的句子只有一种读法（那类句子不贡献组合），有的有三四种（贡献更多）。组合爆炸的斜率取决于「多义句的比例」，我只用了一个平均化的 2。
  • 最坏情况上界假设读法在组合空间里均匀分布，这显然不成立——现实里歧义高度相关（一条规则歧义常常带出整族歧义）。所以「覆盖 90% 需 3,687 次」是上界，不是典型值。
  • 2^m 是联合读法数，不是缺陷数。很多种读法并不产生冲突，只是「读法不同」；真正的缺陷是那些不可同时满足或缺覆盖的那些。我没有用 SMT 求解器真去判可满足性——这一讲的核心工具恰恰是我没有实现的。
  • 讲者引用的三个数字（20%–40%、60%–90%、回归多两倍）官方稿没给出处，我只把它们当作「讲者引用的研究数据」使用，没有独立核实。
  • 「验证器假阴性率 5%」是我设的。如果真实是 20%，那 200~400 会缩到 40~80，第三节的「缩到 10~20」就不成立——但结论方向不变：剩下的那些仍然继承同一个错误理解。
  • 成本表里的「单位」是相对权重，不是真实 token 或时间——翻译与 SMT 求解的实际单价我没测。
  • 没有测「人决定」这一环的成本。讲者强调用户必须逐条检查规则手册，但这一环的人力账缺失；而按第二节的算术，这一环恰恰是唯一能消除歧义的地方。
  • 工具名与团队成员姓名沿用官方自动转写稿，未经外部核实（我的笔记里也明确标了这点）。

FAQ（八、常见问题）

spec 有 bug 是什么意思？ 单看每条都成立，合起来不可能同时满足。讲者的例子：一条规则说「库存不可用时把订单列为 backorder」，另一条说「不允许把任何订单列为 backorder」——单独读两条都合理，但两者不可能同时成立。

这套方法的核心是什么？ 三步：LLM 先自己优化措辞 → 不成则把英文形式化为 SMT 公式交给 SAT 求解器判定 → 检测到歧义就把那句交回 LLM 重新表述再验。分工是LLM 翻译，求解器验证，人类决定。

为什么要翻译 7 次或 10 次？ 为了判断「这个 LLM 是真的就是这样表现的，还是有什么外部因素把它推到了这个状态」；然后按逻辑等价性聚类，把 7–10 组解释收敛成若干个假设组，对用户展示的选项数是等价类数，不是采样数。判据：N=7 只在「单次翻译的主流概率 ≤ 0.72」时才够 90% 检出——这个数应该反解，不该照抄。

歧义能在下游修好吗？ 不能。每千个任务里 200~400 个因歧义理解错，验证器假阴性率 5% 也只能缩到 10~20 个，剩下的继承同一个错误理解。所以验证的价值是「发现歧义」，不是在歧义存在时给出正确答案。

三类缺陷分别怎么查？ 句内 ambiguity → 多次采样 + 逻辑等价聚类；句内 wording → LLM 自己先优化措辞；跨句 conflict → SMT/SAT 求解器判可满足性；跨句 gap → 对照实际存在的流程/管道人工核对；句内「细节层次不足」→ 靠人。

为什么必须有人参与？ 讲者的原话是「归根结底，除了用户之外，我们无法保证有任何其他机制来确保规范的准确性」——因为规格里包含隐含的领域知识，LLM 不了解、也没有任何保证。他也承认形式化方法在 agent 中的证据还很薄。

逐句检查够不够？ 不够。m 条约束句每句两种读法 → 2^m 种联合读法（m=10 是 1,024 种）；采样 10 次最坏只覆盖 0.98%、现实期望只看到 2.35 个等价类。判据：逐句检查漏掉了组合歧义，聚类压缩的是重复解释而不是组合空间——收敛组合爆炸要靠求解器。
