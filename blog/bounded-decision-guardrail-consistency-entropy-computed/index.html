有界决策的三笔账：召回、可复现与信息量

#AI工程#技术深度#大会笔记

有界决策的三笔账？哪些步骤其实不需要一个生成式模型、护栏的召回提升到底省了多少、以及「可复现」为什么比「更准」更值钱。我读完 AIE Code Summit 2026 那场《Beyond Generation》之后，想验证它最可执行的那条规则——输出能否被提前列举出来——是不是真的能算成账。这篇把它算出来。

口径说明

  • 源是我自己的精读笔记 02-课程体系/AIE-Code-Summit-2026/02-System-One-模型/Chinmay Goyal - Beyond Generation - Fast, Structured AI Decisions with Jev at Glean.md（约 9,590 字，已按官方 Day 1 中英对照演讲稿校对）。官方稿是中英对照全文，本文按导读式处理：不引用译文原文、不搬附件图，只复述机制与公开数据。
  • 官方稿的转写偏差按上下文校正（我的笔记已逐条记录，这里一并写明）：
    • 官方英文是 “It nearly the output quality of a base Laia model, and is able to perform at 90% quality in comparison to a fine-tuned Laia model”，官方中译作「接近基座 Llama 的两倍」——「两倍」是错的，正确是与基座 Llama 几乎同等质量、达到微调 Llama 的 90%。
    • 官方把模型名转写成 “Laia”，据上下文（开源基座 + 微调版本）应为 Llama。
    • “virtue classifiers” / “a virtual classifier using T4 GPUs” 应为 virtual classifier——它本来就是安全护栏第一阶段那层分类器，词本身不是 “virtue”。
    • 官方英文 “more than 50%”（中译「超过 50%」），既有笔记写「远超 50%」属加码，已改。
    • 工程师人数官方本身就不确定：原句 “across like 500 engineers or 300 engineers at clean”，是一个 “500 or 300” 的口误式表述；这里按区间标注。
    • 一致性对比的对象不是 Llama：原句 “how consistent and reproducible Jev results were in comparison to something like say Luna”，官方未点明具体模型（官方中译「与 Luna 等工具相比」）。
  • 我为了建模补的（护栏检查 QPS、每套分类器的维护工时、通用 LLM judge 的不一致率、改 prompt 的单次成本、微调的人时成本）都标为「估」。
  • 三个脚本只依赖 Python 标准库；输出为实跑结果，逐行可复现（无随机数，两次运行输出一致）。
  • 撞题与边界：本系列已发《裁判的三笔账》（单个 judge 的漏放率、级联灰区与影子模式）、《评测与测试的三笔账》（回归阈值、污染与评测集）、《AI 安全的三笔账》（差分隐私、护栏与投毒）。那三篇分别讲判得准不准、评测集怎么造、攻击面怎么防；本文讲判定的可复现性、决策模型的选型账与护栏召回的绝对数——是三个不同的切面。

一、讲者的骨架：大多数步骤不是生成问题

问题重定义：Glean 产品工程侧的 Chinmay Goyal 开场就把问题换掉了——AI 产品里大多数步骤是有界决策（bounded decisions），不是生成问题：用户 query 的意图分类、从 n 个候选里挑一个建议的 ranker、判断一条引用是否成立、把请求路由到正确的模型或专家。而此前的做法是为这些有界问题付完整 LLM 的成本与延迟。

jev 的定位：填在通用 LLM 与微调分类器之间的空档——通用 LLM 太贵太慢；jev 根本不做文本生成，只输出决策（含各选项概率）；更关键的是，决策空间的分类体系（taxonomy）变化时，改一下 prompt 就能开箱即用，不必反复微调。

上线前的评估闸门：Glean 有数百万用户，任何改动都不能让产品回归，所以走多阶段 rollout：凡是涉及生成式 AI 的环节几乎都有一个 golden eval set；改动先在内部 Glean 实例（全公司约 1500 人）里 soak 数周，靠内部用户的高频反馈迭代；最后才和客户做 A/B。

三条路的对比（开源 Llama 基座 / 直接上 jev / 用自己的算力微调 Llama）：结论是 jev 是团队眼中最好的「不训练」选项——输出质量几乎与基座 Llama 模型相当，而能达到微调 Llama 模型 90% 的水平。省掉的是一整条流水线：数据采集、数据清洗、训练算力、taxonomy 一变就得重训，以及模型托管与推理成本。

用例一 · query classification：最好的「零训练」选项。

用例二 · expert routing：Glean 收到 query 后要决定交给哪个「专家」回答，此前用通用 LLM 路由。搭了 n 个专家的测试床后，jev 在精度显著更高的同时把延迟降了约 8 倍。代价是为这一阶段显著改造了实现与基础设施——Goyal 特意强调，Glean 的原则是把系统做得尽量简单，「这是我们少数认为复杂度值得的地方」。

用例三 · follow-up 建议 ranker（内部叫 Q）：架构是 10–15 个互相独立的来源各自用自然语言 LLM 生成建议，再交给一个 ranker（输入建议集合 + 原始 query + Glean 的输出，选出最好的一个）。硬约束是「snappy」：不能先给用户正文、再让他等 5 秒才看到建议，所以这一步有 1.5–2 秒的时间上限。两个数字：jev 在时限内给出建议的比例 99.2%，通用 LLM 约 90%；以及护栏命中率——通用 LLM 约 10% 的产出不合法（语言不对、不满足程序化条件），jev 是零个非法样本（他承认两边 prompt 有差异，但已尽量对齐以排除干扰）。还有一个只有决策模型才有的好处：jev 返回的是各选项的概率分布，而不是二值 yes/no，于是阈值可以按部署调；他们还做了自学习系统，按客户用量自动调阈值，让每个客户的体验贴着自身使用模式。

用例四 · 评测流水线里的 LLM judge：Glean 的答案带 citation，引用是信任的根基，所以评测流水线里有一道高门槛检查：被引文档是否真的支持答案里的论断——本质是一道 yes/no 题。jev 的延迟和成本更好，但真正让他意外的是可复现性：在 28 或 30 个用例里，多次运行只有一次结果不同。这直接改变了工程经济：LLM-as-judge 通常要重复跑多次来抵消方差，现在不必了；单个工程师跑评测快 5–6 倍，乘以 Glean 的数百名工程师，产品改进的杠杆就从线性变成指数。

用例五 · 安全护栏分类器：安全是客户对 Glean 的硬要求，工具与 LLM 的输入输出都要过检查。他们的做法是两阶段（第一阶段 “recall heavy phase”，第二阶段 “the final heavy loaded LLM”），且这些检查与真实工具调用并行执行。旧方案是在每个客户单租户环境里、用 T4 GPU 托管一个 virtual classifier：Glean 是单租户架构，约 1000 个客户就要维护约 1000 套分类器，本身就是一个难题，还要占用 2–3 名工程师全职维护。换成 jev 后，第一阶段召回从 31.5% 提升到 90.2%，同时资源成本明显下降；把工程师人力算进去，总节省「超过 50%」。

一条可以贴在工位上的选型规则：输出能否被提前列举出来？（Can the output be listed in advance?）不能 → 这是自由文本生成问题，回去用生成式模型；能 → 用 jev（或标签分类）——若标签稳定且量大，可以微调（「如今这种情况已经很少」）；若标签经常变，还是 jev；需要动态文本 → 考虑混合方案：jev 做决策 + 自由文本 LLM 做表达。

二、增量一：护栏召回提升 7.0 倍，但乘上流量才是成本

"""护栏召回 31.5% -> 90.2%：把召回率乘上流量，才是真正的成本。

数字取自我的精读笔记（安全护栏两阶段：第一阶段 recall heavy、第二阶段 final heavy loaded LLM；
第一阶段召回从 31.5% 提升到 90.2%；约 1000 个客户各托管一套 T4 GPU 的 virtual classifier，
另有 2-3 名工程师全职维护；总节省「超过 50%」）。
只依赖标准库；输出确定性。
"""
RECALL_OLD = 0.315
RECALL_NEW = 0.902
CHECKS_PER_SEC = 100       # 护栏检查的 QPS（估）
PHASE2_CATCH = (0.0, 0.5, 0.9)   # 第二阶段（重 LLM）能抓住第一阶段漏放的比例（估）

print("一、召回率提升了多少，漏放降了多少")
print("%-22s %14s %16s %20s" % ("方案", "第一阶段召回", "第一阶段漏放", "漏放下降倍数"))
print("%-22s %13.1f%% %15.1f%% %20s" % ("旧方案（T4 虚拟分类器）", RECALL_OLD * 100,
      (1 - RECALL_OLD) * 100, "-"))
print("%-22s %13.1f%% %15.1f%% %19.1fx" % ("换成决策模型", RECALL_NEW * 100,
      (1 - RECALL_NEW) * 100, (1 - RECALL_OLD) / (1 - RECALL_NEW)))
print()
print("二、两阶段串联：总体漏放是乘积")
print("%-20s %22s %22s %20s" % ("第二阶段捕获率", "旧方案总体漏放", "新方案总体漏放", "下降倍数"))
for c2 in PHASE2_CATCH:
    old_total = (1 - RECALL_OLD) * (1 - c2)
    new_total = (1 - RECALL_NEW) * (1 - c2)
    print("%-20s %21.2f%% %21.2f%% %19.2fx" % ("%.0f%%" % (c2 * 100),
          old_total * 100, new_total * 100, old_total / new_total))
print()
print("   => 判据：**两阶段串联的总体漏放是乘积**，但注意表里的下降倍数**恒为 6.99 倍**：")
print("      第二阶段对旧新方案同等作用，只是把总体漏放整体压低，**不改变新旧之间的差距**。")
print("      所以「第一阶段召回从 31.5% 提到 90.2%」这个改进，收益是**等比缩放**的，")
print("      不会被第二阶段摊薄 —— 反过来说，第二阶段再强，也不能替第一阶段补上召回。")
print()
print("三、乘上流量才是成本")
for qps in (10, 100, 1000):
    per_day = qps * 86400
    old_leak = per_day * (1 - RECALL_OLD)
    new_leak = per_day * (1 - RECALL_NEW)
    print("   %5d QPS -> 每天 %s 次检查 | 旧方案漏放 %s 次/天 | 新方案 %s 次/天（少 %s 次）" % (
        qps, format(int(per_day), ","), format(int(old_leak), ","), format(int(new_leak), ","),
        format(int(old_leak - new_leak), ",")))
print()
print("   => 判据：**召回率本身不是成本，漏放的绝对数才是**。")
print("      100 QPS 的护栏检查下，旧方案每天漏放 %s 次、新方案 %s 次。" % (
    format(int(100 * 86400 * (1 - RECALL_OLD)), ","), format(int(100 * 86400 * (1 - RECALL_NEW)), ",")))
print()
print("四、还有一笔账：每客户一套分类器")
CUSTOMERS = 1000
ENGINEERS = 2.5            # 讲者给的全职维护工程师（2-3 名，取中值）
HOURS_PER_MONTH = 160     # 每人每月工时
HOUR_COST = 100            # 工程师时薪（美元，估）
total_hours = ENGINEERS * HOURS_PER_MONTH
per_classifier_h = total_hours / CUSTOMERS
monthly = total_hours * HOUR_COST
print("   %d 个单租户客户 = %d 套 virtual classifier，由 %.1f 名全职工程师维护" % (
    CUSTOMERS, CUSTOMERS, ENGINEERS))
print("   总工时 %.0f 小时/月 -> **摊到每套分类器只有 %.2f 小时/月**" % (
    total_hours, per_classifier_h))
print("   人力成本：%.1f 人 x %d 小时 x $%d = **$%s/月** = $%s/年" % (
    ENGINEERS, HOURS_PER_MONTH, HOUR_COST,
    format(int(monthly), ","), format(int(monthly * 12), ",")))
print("   判据：**单租户护栏的成本是「每客户一套」的运维乘数，不是 GPU**——")
print("      讲者说总节省「超过 50%」，而这里的大头是人力结构：")
print("      1000 套分类器带来的维护工作量随客户数线性增长，集中式决策模型则不增长。")

输出：

四、还有一笔账：每客户一套分类器
   1000 个单租户客户 = 1000 套 virtual classifier，由 2.5 名全职工程师维护

      讲者说总节省「超过 50%」，而这里的大头是人力结构：
      1000 套分类器带来的维护工作量随客户数线性增长，集中式决策模型则不增长。

三处结论：

第一，召回 31.5% → 90.2% 对应漏放降 7.0 倍。 第一阶段漏放从 68.5% 降到 9.8%。判据：看护栏改造时要说「漏放降了几倍」，而不是只说「召回到了 90.2%」——后者听起来像 90% 的漏放被拦住，实际漏放仍近 10%。

第二，两阶段串联的下降倍数恒为 6.99 倍，与第二阶段强弱无关。 第二阶段捕获率 0% / 50% / 90% 三档下，旧新方案的总体漏放分别是 68.50% → 9.80%、34.25% → 4.90%、6.85% → 0.98%，倍数都是 6.99×。判据：第一阶段召回的提升是等比缩放——第二阶段对旧新方案同等作用，只把总体漏放整体压低，不改变新旧差距；反过来也成立：第二阶段再强，也不能替第一阶段补上召回。

第三，召回率本身不是成本，漏放的绝对数才是。 100 QPS 的护栏检查下，旧方案每天漏放 5,918,400 次、新方案 846,719 次，少 507 万次。判据：护栏方案要按「每天漏掉多少次」评估，不是按召回率。

第四，还有一笔没算完的账：每客户一套分类器。 讲者给的是 2–3 名全职工程师维护约 1000 套分类器 → 总工时约 400 小时/月，摊到每套只有 0.4 小时/月；按 $100/小时估，人力成本约 $40,000/月、$48 万/年。判据：单租户护栏的成本是「每客户一套」的运维乘数，不是 GPU——讲者说总节省「超过 50%」，而这笔账的大头是人力结构：1000 套分类器的维护量随客户数线性增长，集中式决策模型则不增长。

三、增量二：一致性的价值不是「更准」，是「跑一次就够」

"""一致性值多少钱：它决定「评测要跑几次」。

数字取自我的精读笔记（引用校验的 judge：在 28 或 30 个用例里，多次运行只有一次结果不同；
单个工程师跑评测快 5-6 倍；LLM-as-judge 通常要重复跑多次来抵消方差）。
只依赖标准库；输出确定性。
"""
JEV_DISAGREE = 1           # jev：约 29 个用例的多轮运行里只有 1 次不同
CASES = 29
Q_GENERIC = 0.15           # 通用 LLM judge 的逐次判定不一致率（估；讲者未给具体数）

print("一、逐次判定的不一致率（上界）")
print("   jev：%d 个用例的多轮运行里只有 %d 次不同" % (CASES, JEV_DISAGREE))
for runs in (2, 3, 5):
    q = JEV_DISAGREE / (CASES * (runs - 1))
    print("     若每例跑 %d 次 -> 判定共 %d 次，其中 1 次不同 -> 逐次不一致率 <= **%.2f%%**" % (
        runs, CASES * (runs - 1), 100 * q))
print("   注：讲者没说每例跑了几次，所以只能给上界；通用 LLM 的对应数字他也没给（估 15%）。")
print()
print("二、一致性决定「跑几次」：重测差异率 = 1-(1-q)^N")
print("%-12s %18s %18s %20s" % ("跑 N 次", "jev (q=3.4% 上界)", "通用 LLM (q=15% 估)", "两者的重测差异率比"))
for n in (1, 3, 5, 10):
    q_jev = 0.034
    d_jev = 1 - (1 - q_jev) ** n
    d_gen = 1 - (1 - Q_GENERIC) ** n
    print("%-12d %17.2f%% %17.2f%% %19.1fx" % (n, d_jev * 100, d_gen * 100, d_gen / d_jev))
print()
print("   => 判据：**不一致率 q 决定同一用例重测 N 次会不会变**；q 越大，越要多跑才能稳住，")
print("      而多跑就是多花钱。通用 LLM judge 跑 10 次，重测差异率已到 %.0f%%。" % (
    (1 - (1 - Q_GENERIC) ** 10) * 100))
print()
print("三、把「跑几次」折成评测吞吐")
for n_gen in (3, 5):
    gen_cost = n_gen * 1.0

  • 通用 LLM judge 的不一致率 15% 是我估的，讲者只给了 jev 的「29 个用例里 1 次不同」。如果通用 LLM 实际是 5% 而不是 15%，第三节的差距会缩到 1.5 倍左右，「跑 5 次」的必要性也就没那么强。
  • 讲者没说每例跑了几次，所以 jev 的不一致率只能给上界区间（1.7%~3.45%），不是一个点估计。

  • 信息量账用了 ~4 bits/token 的经验折算，真实分词器对「选项名 + 概率」这类文本的有效熵远低于 4 bits/token，所以真实的信息量差会比我算的更大，成本差也会被压得更小。
  • 「成本主导项是输入与推理」是从「信息量差 267× vs 成本差 8×」反推的，我没有直接测量 jev 的输入/推理 token 占比；也可能存在别的解释（比如定价策略本身不同）。

  • 两阶段护栏的第二阶段捕获率完全是我设的（0/50/90% 估），讲者只说第二阶段是「final heavy loaded LLM」，没给捕获率。

FAQ（八、常见问题）

什么时候该用决策模型，什么时候该用生成式模型？ 判据是输出能否被提前列举出来。不能（自由文本）→ 生成式模型；能 → 决策模型或标签分类；标签稳定且量大可以微调（但这种已少见）；标签经常变就用决策模型；需要动态文本 → 决策模型做决策 + 生成式模型做表达。

决策模型比微调差多少？ 讲者的口径是：输出质量几乎与基座 Llama 相当，而能达到微调 Llama 的 90%（官方中译「接近基座 Llama 的两倍」是错的）。省掉的是数据采集、清洗、训练算力、taxonomy 一变就重训、模型托管与推理成本这一整条流水线。

护栏召回从 31.5% 提到 90.2%，到底省了多少？ 漏放率从 68.5% 降到 9.8%，降 7.0 倍；100 QPS 下每天少漏 507 万次。另外还有运维结构那笔账：约 1000 个客户各一套 T4 虚拟分类器 + 2–3 名全职工程师，换成集中式决策模型后总节省「超过 50%」。

两阶段护栏的第二阶段能补多少？ 它能把总体漏放整体压低（第二阶段捕获 90% 时，新方案总体漏放从 9.80% 降到 0.98%），但新旧方案的差距恒为 6.99 倍——第二阶段再强，也不能替第一阶段补上召回。

LLM judge 的「一致性」为什么值钱？ 因为它决定跑几次：不一致率 q 决定同一用例重测 N 次会不会变（重测差异率 = 1−(1−q)^N）。通用 LLM（q=15% 估）跑 10 次，重测差异率已到 80.3%——在 CI 里就是 flaky。jev 的 q ≤ 3.45%，跑一次就够，于是单个工程师评测快 5–6 倍，乘以数百名工程师，杠杆从线性变指数。

决策模型能便宜多少？ 讲者给的 expert routing 场景是延迟降约 8 倍；加上评测侧 5~6 倍与护栏侧「超过 50%」的节省。判据：省下的不只是钱，还有「不必反复微调」这条流水线。

K 变多会不会变贵？ 几乎不会：K 从 2 到 1000，输出信息量只涨 9.97×，而输出信息量只占成本的一小部分。判据：可枚举的任务要一次把选项列全，分批枚举要多付几份指令开销。

什么时候该微调？ 只在改 prompt 反复失败时：失败率 10% 时改 prompt 期望 0.56 人时 vs 微调 24 人时；失败率 50% 时才接近。判据：taxonomy 变更越频繁，微调越不划算——这正是讲者说「若标签经常变，还是 jev」。
