AI 系统设计的三笔账：权限、延迟与降级

#AI 工程#系统设计#技术深度#面试笔记

AI 系统设计的三笔账？权限过滤把检索逼到什么形状、延迟预算是加法还是根号、模型挂了怎么降级。我的面试答案笔记《07 AI 系统设计》里有 20 道工程设计题，答案都写得很完整，但三笔「各是多少」是定性的。这篇把它们算出来。

口径说明

  • 源是我自己的面试答案笔记 06-面试/答案/07-AI系统设计-答案.md（43 KB，20 题：实时语音 Agent、RAG、企业级权限 RAG、个人助理记忆、多 Agent 客服、LLM 推理平台、评测平台、Coding Agent、代码生成与评审、内容审核、实时推荐、跨会话记忆、延迟与质量、缓存、限流与成本、故障转移、高可用、优雅降级、多区域部署、容量规划）。可以自由引用；本文正文主体是自写可复现模型。
  • 三个脚本只依赖 Python 标准库；输出为实跑结果，逐行可复现（无随机数，两次运行输出逐字一致）。
  • 笔记里给出的数字（1000 万文档、粗排去掉 80%、ANN Top-500 → 过滤 Top-50 → rerank Top-10、延迟预算表、五级降级链）直接标注来源；我为了建模补的（可见比例、向量维度、召回衰减系数、各阶段 σ、降级质量分与单价、请求量）都标为「估」。
  • 撞题检查：自动判 HIGH_RISK，命中的是 inference-engineering 系列（vLLM / PagedAttention / KV Cache 等泛词，最高覆盖度 0.03 = 1/39）——那些是推理引擎主题；本文取的三题（权限过滤、延迟预算、降级链）与之机制不同，故不重复。另外笔记的 Q6「LLM 推理平台」与该系列同题，本文刻意避开不写。

一、笔记的骨架：20 题里的三道

Q3 企业级 RAG（1000 万文档 + 每用户权限）给了一个「必须知道的坑」：HNSW 索引基于向量相似度，不能直接在 ANN 搜索时做精细 ACL 过滤。两种做法的代价——Pre-filter（先过滤再 ANN，过滤后数据集变小、召回率下降，HNSW 图结构被打断）、Post-filter（ANN 取 Top-N 再按 ACL 过滤，若过滤掉很多，尾部可能全是低相似度结果）；实战解法是四步漏斗（BM25/元数据粗排去掉 80% 无权限文档 → ANN Top-500 → ACL 过滤后 Top-50 → rerank 到 Top-10），更工程的方案是为权限建单独的 Bitmap 索引（每用户一个 allowed_doc_ids BitSet），与 HNSW 并行查询做两阶段 join。

Q1 实时语音 Agent 的延迟预算给了逐阶段目标：AEC+NS 10–20 ms、VAD 20–50、ASR（首个 partial）100–200 /（final）200–400、LLM TTFT 150–300、TPOT 30–80 ms/token、TTS TTFA 150–300、网络 50–150，端到端 < 1.5 s (P95)；外加 barge-in 打断与失败模式。

Q18 优雅降级给了五级链：L1 正常（GPT-4o + RAG）→ L2 主模型延迟（小模型）→ L3 同能力备用（另一家厂商，30% 概率）→ L4 语义缓存 → L5 模板兜底 + UI 提示「当前为简化版」；配套组件是 health check + 实时熔断、多模型路由、quality-aware judge、模板引擎、缓存兜底、UI 提示。

二、增量一：权限过滤把 ANN 的前提吃掉了

笔记说 pre-filter 会让召回率下降、post-filter 会让尾部质量变差。到底差多少、什么时候该换结构，可以算：

"""权限过滤 + ANN：过滤把 ANN 的前提破坏后，精确搜索反而更好。

用笔记的量：1000 万文档、BM25 粗排去掉 80% 无权限文档、ANN Top-500 -> ACL 过滤后 Top-50 -> rerank Top-10、
每用户 allowed_doc_ids BitSet 与 HNSW 并行做两阶段 join。
只依赖标准库；输出确定性。
"""
import math

N_DOCS = 10_000_000
DIM = 768
BYTES_PER_DIM = 4         # float32
TOP_K = 10
ANN_N = 500
ANN_RECALL_FULL = 0.95    # 全量 ANN 的召回率（估）
RECALL_PER_DECADE = 0.03  # 候选集每缩小 10 倍，召回率下降的百分点（估）

print("文档总量 %s、向量 %d 维（%d B/维）" % (format(N_DOCS, ","), DIM, BYTES_PER_DIM))
print()
print("一、Post-filter：先 ANN 取 %d 条，再按 ACL 过滤" % ANN_N)
print("%-14s %18s %22s" % ("可见比例", "期望剩余条数", "够不够 Top-%d" % TOP_K))
for vis in (0.5, 0.1, 0.01, 0.001, 0.0001):
    left = ANN_N * vis
    print("%-14s %18.1f %22s" % ("%.2f%%" % (vis * 100), left, "够" if left >= TOP_K else "不够（要再放大 ANN_N）"))
print()
print("  -> post-filter 要凑够 %d 条，ANN_N 必须放大到 %d / 可见比例：" % (TOP_K, TOP_K))
for vis in (0.01, 0.001):
    print("     可见 %.2f%% -> ANN_N >= %s（而 ANN 的取数越多延迟越高）" % (vis * 100, format(int(TOP_K / vis), ",")))
print()
print("二、Pre-filter：先过滤再建图/搜索，召回率随候选集缩小而掉")
print("%-22s %14s %14s %22s" % ("阶段", "候选集", "召回率", "相对全量"))
stages = [
    ("全量 ANN", N_DOCS),
    ("ACL 过滤后", int(N_DOCS * 0.01)),
    ("+ BM25 粗排 80%", int(N_DOCS * 0.01 * 0.2)),
]
for name, n in stages:
    decades = math.log10(N_DOCS / n) if n < N_DOCS else 0.0
    recall = ANN_RECALL_FULL - RECALL_PER_DECADE * decades
    print("%-22s %14s %13.1f%% %21.1f%%" % (name, format(n, ","), recall * 100, (recall / ANN_RECALL_FULL) * 100))
print()
print("三、关键：权限过滤后，ANN 的前提（千万级）可能不成立")
print("%-16s %14s %16s %22s" % ("可见候选数", "扫描字节", "估算耗时", "与 ANN 比"))
for n in (1_000, 10_000, 100_000, 1_000_000):
    byts = n * DIM * BYTES_PER_DIM
    # 估算：10 GB/s 内存带宽
    ms = byts / 10e9 * 1000
    verdict = "精确搜索更快" if ms < 20 else "ANN 更划算"
    print("%-16s %14s %15.2f ms %22s" % (format(n, ","), "%.1f MB" % (byts / 1e6), ms, verdict))
print()
print("  => **当权限把候选集压到万级，暴力打分（精确）在毫秒级完成，比 ANN 的近似更快也更准**；")
print("     ANN 的价值前提是「候选集大到无法暴力」，权限过滤把这个前提吃掉了。")
print()
print("四、每用户权限位图的存储账")
for users in (1_000, 10_000, 100_000):
    bits = users * N_DOCS / 8
    print("  %7s 用户 x %s 文档的 BitSet = %7.1f GB" % (format(users, ","), format(N_DOCS, ","), bits / 1e9))
print("  -> 每用户 1 个 BitSet = %s B（1.25 MB）；10 万用户 = %s GB（可接受，但要按用户维度分片）"
      % (format(N_DOCS // 8, ","), format(100_000 * N_DOCS // 8 / 1e9, ".1f")))
print()
print("判据：")
print("  - **先看可见比例再选检索结构**：可见比例低于 0.1% 时 post-filter 必然不够用；")
print("  - **可见候选 <= 万级时用精确搜索**，别硬上 ANN；")
print("  - pre-filter 的代价是召回率：候选集每缩 10 倍掉 %d 个百分点（估），粗排 80%% + ACL 0.01%% 之后" % (RECALL_PER_DECADE * 100))
print("    召回率从 %.0f%% 掉到 %.0f%%（相对全量 %.0f%%）；" % (
    ANN_RECALL_FULL * 100,
    (ANN_RECALL_FULL - RECALL_PER_DECADE * math.log10(N_DOCS / (int(N_DOCS * 0.01 * 0.2)))) * 100,
    100 * (ANN_RECALL_FULL - RECALL_PER_DECADE * math.log10(N_DOCS / (int(N_DOCS * 0.01 * 0.2)))) / ANN_RECALL_FULL))
print("  - 所以笔记给的「粗排 -> ANN Top-500 -> 过滤 Top-50 -> rerank Top-10」是折中，不是最优解；")
print("    真正的最优解取决于可见比例与候选规模，要分别算。")

三处结论：

第一，post-filter 在低可见比例下根本不够用。 ANN 取 Top-500 后按 ACL 过滤：可见比例 1% → 期望只剩 5 条（目标 Top-10 不够）；0.1% → 0.5 条；0.01% → 0.1 条。要凑够 10 条，可见 1% 需要 ANN_N ≥ 1,000、可见 0.1% 需要 ≥ 10,000——而 ANN 取数越多延迟越高。判据：先算可见比例，再决定检索结构；企业级权限 RAG 的难点不在向量检索，在于「用户能看到的那部分有多小」。

第二，pre-filter 的代价是召回率，而且能被算出来。 候选集每缩小 10 倍召回率掉约 3 个百分点（估）：全量 1000 万 → 95%；ACL 过滤到 10 万 → 89%；再加 BM25 粗排去掉 80% → 2 万 → 87%（相对全量 91%）。笔记给的四步漏斗把召回率压在这个量级——它是折中，不是最优解，最优解取决于可见比例与候选规模。

第三，也是本篇最有用的一条：当权限把候选集压到万级，精确搜索比 ANN 更快也更准。 768 维 float32 向量，扫描 1,000 条是 3.1 MB（0.31 ms）、10,000 条是 30.7 MB（3.07 ms）——按 10 GB/s 内存带宽估算，毫秒级就能扫完；而 ANN 的价值前提是「候选集大到无法暴力」。权限过滤恰恰把这个前提吃掉了：用户只可见 1% 文档时，暴力打分既精确（召回 100%）又快（3 ms）。判据：可见候选 ≤ 万级用精确搜索，超过十万级才值得上 ANN。

顺带一句权限位图的账：每用户一个 BitSet = 1000 万位 = 1.25 MB；10 万用户 = 125 GB（可接受，但要按用户维度分片）——这正是笔记说的「两阶段 join」在存储上的价码。

三、增量二：延迟预算是算术和还是均方根

笔记给的是逐阶段目标表与端到端 < 1.5 s (P95)。中间那一步——各阶段怎么加——最容易被搞错：

"""延迟预算：串联系统的预算是算术和还是均方根？P95 怎么来。

用笔记的量：AEC+NS 10-20ms、VAD 20-50、ASR final 200-400、LLM TTFT 150-300、TTS TTFA 150-300、
网络 50-150，端到端 < 1.5s (P95)；TPOT 30-80ms/token。
只依赖标准库；输出确定性。
"""
import math

STAGES = (
    ("AEC + NS", 15, 5),
    ("VAD", 35, 10),
    ("ASR final", 300, 60),
    ("LLM TTFT", 225, 45),
    ("TTS TTFA", 225, 45),
    ("网络", 100, 30),
)
Z95 = 1.645

print("%-12s %10s %10s %14s %16s" % ("阶段", "目标中值", "波动σ", "P95(单阶段)", "含P95的累加"))
sum_p95 = 0.0
for name, mu, sd in STAGES:
    p95 = mu + Z95 * sd
    sum_p95 += p95
    print("%-12s %8d ms %8d ms %12.0f ms %14.0f ms" % (name, mu, sd, p95, sum_p95))
print()
print("算术和口径：各阶段都按自己的 P95 累加 = %.0f ms" % sum_p95)
rms_sigma = math.sqrt(sum(sd * sd for _, _, sd in STAGES))
mu_sum = sum(mu for _, mu, _ in STAGES)
p95_rms = mu_sum + Z95 * rms_sigma
print("均方根口径：波动互相独立时，端到端 P95 = Σμ + 1.645×√Σσ² = %.0f + %.0f = **%.0f ms**"
      % (mu_sum, Z95 * rms_sigma, p95_rms))
print("  -> 两种口径差 %.0f ms（%.0f%%）：**串联系统的延迟预算是「算术和」还是「均方根」，" % (sum_p95 - p95_rms, 100 * (sum_p95 - p95_rms) / p95_rms))
print("     取决于各阶段波动是否相关**（同一条链路上通常正相关 -> 取算术和这一侧）。")
print()
print("对照笔记的端到端目标 < 1500 ms (P95)：")
for name, total in (("算术和口径", sum_p95), ("均方根口径（波动独立）", p95_rms)):
    print("  %-22s %6.0f ms -> %s（余量 %.0f ms）" % (name, total, "达标" if total < 1500 else "超标", 1500 - total))
print()
print("流式输出改变的是「首个有效输出」的延迟，不是总时长：")
for tpot in (30, 50, 80):
    ttf = 225
    first_chunk = sum(mu for _, mu, _ in STAGES[:4]) + tpot   # 到首个音频 chunk
    print("  TPOT %2d ms/token -> 首个音频 chunk 约 %4d ms；完整 20 token 回复约 %4d ms"
          % (tpot, first_chunk, first_chunk + 19 * tpot))
print()
print("判据：")
print("  - **延迟预算是串联系统的算术和**（同链路的波动正相关时），别用 √Σσ² 自我安慰；")
print("    两个口径在本模型里差 %.0f ms（%.0f%%）。" % (sum_p95 - p95_rms, 100 * (sum_p95 - p95_rms) / p95_rms))
print("  - **流式只改善「首个有效输出」，不改善总时长**；但用户感知的是前者 —— 所以 ASR final 与")
print("    TTFT 是压缩重点，TTS 与网络各占 225/100 ms。")
print("  - **P95 不是各阶段 P95 的和**：它是最坏路径的组合，实际更接近「各阶段取 P95 且同时发生」；")
print("    所以端到端 SLO 要按这个更悲观的数定，%.0f ms。" % sum_p95)

输出：

AEC + NS           15 ms        5 ms           23 ms             23 ms
VAD                35 ms       10 ms           51 ms             75 ms
ASR final         300 ms       60 ms          399 ms            473 ms
LLM TTFT          225 ms       45 ms          299 ms            772 ms
TTS TTFA          225 ms       45 ms          299 ms           1071 ms
网络                100 ms       30 ms          149 ms           1221 ms

均方根口径：波动互相独立时，端到端 P95 = Σμ + 1.645×√Σσ² = 900 + 153 = **1053 ms**
  -> 两种口径差 168 ms（16%）：**串联系统的延迟预算是「算术和」还是「均方根」，
     取决于各阶段波动是否相关**（同一条链路上通常正相关 -> 取算术和这一侧）。

对照笔记的端到端目标 < 1500 ms (P95)：
  算术和口径                    1221 ms -> 达标（余量 279 ms）
  均方根口径（波动独立）              1053 ms -> 达标（余量 447 ms）

流式输出改变的是「首个有效输出」的延迟，不是总时长：
  TPOT 30 ms/token -> 首个音频 chunk 约  605 ms；完整 20 token 回复约 1175 ms
  TPOT 50 ms/token -> 首个音频 chunk 约  625 ms；完整 20 token 回复约 1575 ms
  TPOT 80 ms/token -> 首个音频 chunk 约  655 ms；完整 20 token 回复约 2175 ms

判据：
  - **延迟预算是串联系统的算术和**（同链路的波动正相关时），别用 √Σσ² 自我安慰；
    两个口径在本模型里差 168 ms（16%）。
  - **流式只改善「首个有效输出」，不改善总时长**；但用户感知的是前者 —— 所以 ASR final 与
    TTFT 是压缩重点，TTS 与网络各占 225/100 ms。
  - **P95 不是各阶段 P95 的和**：它是最坏路径的组合，实际更接近「各阶段取 P95 且同时发生」；
    所以端到端 SLO 要按这个更悲观的数定，1221 ms。

三处结论：

第一，两种口径差 16%，而该取哪一侧取决于波动是否相关。 各阶段按自己的 P95 累加 = 1,221 ms；若各阶段波动互相独立，端到端 P95 = Σμ + 1.645×√Σσ² = 1,053 ms。同一条语音链路上，各阶段往往同时受网络抖动影响（正相关）→ 该取算术和这一侧。判据：别用 √Σσ² 给自己省 168 ms 余量。

第二，端到端 P95 不是各阶段 P95 的和，而是「最坏路径的组合」。 真正要定 SLO 的那个数是 1,221 ms——它离笔记的 1.5 s 只剩 279 ms 余量，而这 279 ms 要留给 GC、突发排队与网络抖动。

第三，流式只改善「首个有效输出」，不改善总时长。 TPOT 30 / 50 / 80 ms/token 时，首个音频 chunk 分别在 605 / 625 / 655 ms，而完整 20 token 回复要 1,175 / 1,575 / 2,175 ms。用户感知的是前者，所以压缩重点是 ASR final（300 ms）与 TTFT（225 ms），TTS 与网络各占 225 / 100 ms；但 TPOT 决定的是「用户等多久才听完」，两者要分开定目标。

四、增量三：降级链的质量-成本账与熔断误伤

笔记的五级降级链写清了顺序，但每级「值多少」和「熔断误伤多少人」没算：

"""降级链的质量-成本账：五级降级各值多少，熔断误伤多少人。

用笔记的量：L1 正常（GPT-4o + RAG）、L2 延迟（mini）、L3 同能力备用（Claude，30% 概率）、
L4 语义缓存、L5 模板兜底。
只依赖标准库；输出确定性。
"""
LEVELS = (
    ("L1 主模型 + RAG", 1.00, 1.00, 1000),
    ("L2 小模型", 0.88, 0.15, 300),
    ("L3 备用厂商", 0.95, 0.70, 950),
    ("L4 语义缓存", 0.70, 0.02, 20),
    ("L5 模板兜底", 0.30, 0.00, 1),
)
CACHE_HIT = 0.25          # L4 的缓存命中率（估）
BACKUP_PROB = 0.30        # 笔记说 L3 同等答案、30% 概率
REQ_DAY = 10_000_000       # 日请求量（估，千万级）

print("%-18s %10s %12s %12s %20s" % ("降级级别", "质量分", "相对成本", "单次成本", "日成本(10万请求)"))
for name, q, c, unit in LEVELS:
    print("%-18s %9.2f %11.2f %11.2f %19.0f" % (name, q, c, unit, unit * REQ_DAY))
print()
print("一、熔断器打开时，各级的流量怎么分")
print("  L3 备用厂商只有 %.0f%% 概率可用 -> 其余落到 L4/L5：" % (BACKUP_PROB * 100))
for l3_share in (0.0, 0.30, 1.0):
    l4 = (1 - l3_share) * CACHE_HIT
    l5 = (1 - l3_share) * (1 - CACHE_HIT)
    q = 0.95 * l3_share + 0.70 * l4 + 0.30 * l5
    cost = 950 * l3_share + 20 * l4 + 1 * l5
    print("    L3 占比 %.0f%% -> L4 %.0f%%、L5 %.0f%% -> 平均质量 %.3f、平均单次成本 %.1f"
          % (l3_share * 100, l4 * 100, l5 * 100, q, cost))
print()
print("二、熔断误伤的账：打开期间到达的请求全部降级")
for window_s, rps in ((30, REQ_DAY / 86400 * 5), (60, REQ_DAY / 86400 * 5)):
    hits = window_s * rps
    for level, q in (("L2", 0.88), ("L4", 0.70), ("L5", 0.30)):
        loss = hits * (1.00 - q)
        print("  熔断打开 %d 秒（%d 请求）-> 落到 %s：质量损失合计 %.0f 个「请求 x 质量分」"
              % (window_s, int(hits), level, loss))
print()
print("三、什么时候不该熔断：主模型只是慢，不是挂")
for slow_share, timeout_ms in ((0.02, 2000), (0.05, 2000)):
    # 慢请求里有一部分其实还能出结果，只是超时
    rescued = slow_share * 0.5
    print("  %.0f%% 的请求偏慢（超时 %d ms），其中一半能救回来 -> 误熔断掉的质量 %.3f"
          % (slow_share * 100, timeout_ms, slow_share * 0.5 * (1 - 0.88)))
print()
print("判据：")
print("  - **降级链的顺序要按「质量损失 / 成本节省」排**：L3 备用厂商质量 0.95 成本 950，")
print("    L4 缓存质量 0.70 成本 20，L5 模板 0.30 成本 1 —— 便宜的那些质量损失很大，")
print("    所以能走 L3 就别急着掉到 L4/L5。")
peak_rps = REQ_DAY / 86400 * 5
print("  - **熔断窗口越长，误伤面越大**：60 秒窗口在峰值 %s 请求/秒下就是 %s 个请求被降级，" % (
    format(int(peak_rps), ","), format(int(60 * peak_rps), ",")))
print("    质量损失随降级级别线性放大 —— 所以熔断要快开快关，而不是固定 30 秒。")
print("  - **慢 ≠ 挂**：本模型里 2% 的「超时」里有一半其实能出结果，误熔断等于白丢质量；")
print("    慢请求占比越高，熔断越不该只靠「超时」判定。")
print("  - **L5 模板不是失败，是产品决策**：质量 0.30 但成本 0；关键是 UI 要标明「简化版」，")
print("    否则用户会把模板答案当成系统故障 —— 这是笔记里「UI 提示」那一条的算术依据。")

判据：
  - **降级链的顺序要按「质量损失 / 成本节省」排**：L3 备用厂商质量 0.95 成本 950，
    L4 缓存质量 0.70 成本 20，L5 模板 0.30 成本 1 —— 便宜的那些质量损失很大，
    所以能走 L3 就别急着掉到 L4/L5。
  - **熔断窗口越长，误伤面越大**：60 秒窗口在峰值 578 请求/秒下就是 34,722 个请求被降级，
    质量损失随降级级别线性放大 —— 所以熔断要快开快关，而不是固定 30 秒。
  - **慢 ≠ 挂**：本模型里 2% 的「超时」里有一半其实能出结果，误熔断等于白丢质量；
    慢请求占比越高，熔断越不该只靠「超时」判定。

    否则用户会把模板答案当成系统故障 —— 这是笔记里「UI 提示」那一条的算术依据。

三处结论：

第一，降级链的顺序要按「质量损失 / 成本节省」排，而不是按「越便宜越后面」。 L3 备用厂商质量 0.95、成本 950；L4 语义缓存质量 0.70、成本 20；L5 模板质量 0.30、成本 1。熔断打开时若 L3 完全不可用（笔记说它只有 30% 概率可用），平均质量掉到 0.565、平均单次成本 289；L3 全可用时是 0.950 / 950。判据：能走 L3 就别急着掉到 L4/L5——每掉一级，质量损失是非线性的。

第二，熔断窗口是误伤面。 按千万级日请求、峰值 5 倍算，峰值 578 请求/秒：熔断打开 30 秒 → 17,361 个请求被降级，60 秒 → 34,722 个；掉到 L2 的质量损失是 4,167，掉到 L4 是 10,417，掉到 L5 是 24,306（是 L2 的 6 倍）。判据：熔断要快开快关，而不是固定 30 秒——窗口长度直接乘在质量损失上。

第三，慢 ≠ 挂。 本模型里 2% 的「超时」请求中有一半其实能出结果——只靠超时判定熔断会把可用流量误伤掉。而 L5 模板兜底不是失败而是产品决策（质量 0.30、成本 0），关键是 UI 必须标明「简化版」，否则用户会把模板答案当成系统故障——这就是笔记里「UI 提示」那条的算术依据。

五、把三个模型套回本章（判据清单）

  1. 先算可见比例再选检索结构：可见 1% 时 post-filter 的 Top-500 只剩 5 条，不够 Top-10。
  2. 可见候选 ≤ 万级用精确搜索：扫描 10,000 条 768 维向量只要 3.07 ms，比 ANN 的近似更快也更准——ANN 的前提被权限吃掉了。
  3. pre-filter 的召回代价可算：候选集每缩 10 倍掉约 3 个百分点；粗排 + ACL 后 95% → 87%。
  4. 权限位图按用户维度分片：每用户 1.25 MB，10 万用户 125 GB。
  5. 延迟预算取算术和：各阶段 P95 累加 1,221 ms vs 均方根 1,053 ms（差 16%）；同链路波动正相关时按前者定 SLO。
  6. 流式只改善首个有效输出：TPOT 30→80 ms/token 时首个 chunk 605→655 ms，总时长 1,175→2,175 ms。
  7. 压缩重点是 ASR final 与 TTFT（300 / 225 ms），TTS 与网络各占 225 / 100 ms。
  8. 降级链按「质量损失/成本节省」排：L3(0.95/950) → L4(0.70/20) → L5(0.30/1)，能走 L3 别掉 L4。
  9. 熔断窗口直接乘在质量损失上：60 秒 = 峰值下 34,722 个请求被降级，掉 L5 的损失是 L2 的 6 倍。
  10. 慢 ≠ 挂：只靠超时判定熔断会误伤可救回的请求。

七、这三个模型判不了什么

  • 可见比例 1%/0.1%、768 维、召回每十倍掉 3 个点、各阶段 σ、单请求成本、请求量、降级质量分都是估的。真实企业里「用户可见比例」是长尾分布（大部分用户可见很少，少数用户可见很多）——一个全局比例会同时对两种用户都不准。
  • 没算多租户下的隔离粒度。笔记给的是「每用户 allowed_doc_ids BitSet + 两阶段 join」，但多租户若按组织授权，位图可以按组织共享，成本降一个量级；反过来，跨组织共享文档会让位图爆炸。授权模型决定位图怎么存，本文没展开。
  • 没算召回率下降对下游的影响。召回 95% → 87% 意味着 rerank 与 LLM 看到的候选变少，最终答案质量掉多少——这一环取决于 rerank 的能力，本文只算到检索层。
  • 延迟模型假设各阶段延迟独立可加，但没算排队与背压：TTFT 超时往往不是模型慢，而是队列排队（GPU batch 等待），此时「各阶段 σ」并不适用。判据：延迟模型要分清「计算慢」与「排队慢」，两者的优化手段完全不同。
  • 降级模型没有把「用户可感知」量化：L5 模板的质量 0.30 是我的赋值，实际影响取决于用户对该场景的容忍度——有的场景模板答案完全够用（查余额），有的场景一字都不能错（转账）。

FAQ（八、常见问题）

权限过滤下还能用 ANN 吗？ 看可见候选规模。可见 1% 时 post-filter 的 Top-500 只剩 5 条，不够 Top-10；而候选压到万级时，暴力打分扫 10,000 条 768 维向量只要 3.07 ms（按 10 GB/s 带宽），既精确（召回 100%）又快——ANN 的价值前提「候选大到无法暴力」被权限吃掉了。可见候选超过十万级才值得上 ANN。

pre-filter 的代价是多少？ 召回率随候选集缩小而掉（估每缩 10 倍掉 3 个点）：1000 万全量 95% → ACL 过滤到 10 万 89% → 再粗排去掉 80% 到 2 万 87%。笔记的四步漏斗（粗排 → Top-500 → 过滤 Top-50 → rerank Top-10）是折中，不是最优解。

端到端 P95 怎么加？ 各阶段按自己的 P95 算术和 = 1,221 ms；若波动独立则是均方根口径 1,053 ms（差 16%）。同一条链路的波动通常正相关，该取算术和这一侧——离 1.5 s 只剩 279 ms 余量。

流式输出能改善多少延迟？ 只改善首个有效输出：TPOT 30→80 ms/token 时首个音频 chunk 从 605→655 ms，而完整 20 token 回复从 1,175→2,175 ms。所以压缩重点是 ASR final（300 ms）与 TTFT（225 ms），TPOT 决定的是「听完要等多久」。

降级链怎么排？ 按「质量损失 / 成本节省」：L3 备用厂商 0.95 质量 / 950 成本，L4 缓存 0.70 / 20，L5 模板 0.30 / 1。能走 L3 就别掉 L4/L5——每掉一级质量损失是非线性的。熔断打开时若 L3 只有 30% 可用，平均质量掉到 0.565。

熔断开多久合适？ 窗口直接乘在误伤面上：千万级日请求、峰值 578 请求/秒下，30 秒 = 17,361 个请求、60 秒 = 34,722 个请求被降级，掉到 L5 的质量损失是掉到 L2 的 6 倍。所以要快开快关；另外慢 ≠ 挂——2% 的超时里有一半其实能出结果，只靠超时判定会误伤。
