聊天系统的三个可计算处：ID 撞号、存储差百倍与在线扩散

#系统设计#架构设计#读书笔记#即时通讯

聊天系统的三个可计算处？ID 怎么发、消息存几份、在线状态怎么扩散。讲义这三处都给了方向，其中两处还给了「更好的做法」——但把讲义的数据模型和同步模型放在一起看，群聊的消息同步会漏消息，而且漏得很厉害。这篇先验这件事。

这篇不复述译文，也不搬运中文译本的任何段落。它复述这一章的骨架（协议三选、组件两分、数据模型的两个决定、消息流程），然后补三个自写模型：本地序列号与单一水位线的冲突、群聊消息存一份还是每人一份、在线状态扩散与心跳阈值的成本账。

口径说明

  • 源笔记是 Alex Xu《System Design Interview — An Insider’s Guide》第 12 章的社区中译。上游两仓库的 LICENSE 在 main/master 分支经 raw 通道取均返回 404，上游许可未能确认；原书是商业出版物。故本篇为导读式：只复述章节骨架与需求数字，不引用译文原文或原书段落，不使用译本配图，正文主体是自写模型与判断。
  • 三个脚本均为自写增量，只依赖 Python 标准库；输出为实跑结果，逐行可复现（三段模拟都不含随机数）。
  • 与已发文章的重叠见「这一章不重复已发的内容」一节。

一、本章骨架：协议三选、组件两分、数据模型两个决定

需求：一对一聊天 + 群聊（最多 100 人）；文本消息最多 100,000 字符；在线/离线状态；多设备；推送通知。规模按 5000 万 DAU 设计，聊天记录永久保存。

通信协议三选：轮询（冗余请求多，低效）、长轮询（挂住连接直到有消息；对不活跃用户低效）、WebSocket（双向持久连接，收发都用它）。发送方用 HTTP + 持久连接提高效率。

组件两分：无状态服务（注册、登录、资料，并做服务发现给客户端推荐聊天服务器）；有状态的聊天服务器（维持持久 WebSocket 连接，负责投递与同步）。第三方推送服务负责离线提醒——那部分见《通知系统的投递率怎么算》。服务发现用 Zookeeper，按地理位置与服务器容量分配聊天服务器。

数据模型的两个决定：

  1. 聊天记录存键值存储。理由讲义给了四条：易水平扩展、访问延迟低、关系型数据库不擅长长尾数据（索引变大后随机访问开销大）、以及 Facebook Messenger 与 Discord 也这么做。
  2. 主键是消息 ID（用来确定消息顺序）；群聊用复合主键 (channel_id, message_id)。ID 可以用 Snowflake 这类全局 64 位序列号生成器，但更好的做法是用本地序列号——ID 只在群内唯一就够，因为在一个频道内维护消息顺序已经足够。

消息流程：1:1 聊天是「A 发 → 聊天服务器 1 分配消息 ID 并写入键值存储 → B 在线则转发到 B 所在的聊天服务器 2 → B 离线则发推送」。群聊则是「消息被复制到群内每个接收者的个人收件箱」，讲义明确说这简化了同步但对大群开销很大；每个接收者有一个收件箱，里面装着来自不同发送者的消息。

消息同步：多设备场景下，每台设备维护一个 cur_max_message_id（该设备上最新的消息 ID）；满足「接收者 ID = 当前登录用户」且「键值存储中的消息 ID > cur_max_message_id」的消息被视为新消息。

在线状态：客户端定期发心跳，超过阈值（讲义举例 x = 30）没收到就标记离线；状态更新用发布-订阅推给好友，每对好友之间维护一个频道——A 的状态变化发布到 A-B、A-C、A-D 三个频道。

二、增量一：本地序列号与单一水位线合起来有个洞

讲义把两件事分开写：数据模型那节说群聊可以用本地序列号（只在群内唯一）；同步那节说设备维护一个 cur_max_message_id，比它大的消息才算新。这两节各自看都成立，放在一起对群聊就不成立。

原因一句话：本地序列号只在同一个发送者内单调，跨发送者不可比。而单一水位线假定的是「全局单调」。

"""群聊的本地序列号：讲义说「ID 只在群内唯一就够」，但客户端用单一水位线同步。

这里把两件事放在一起跑：
  1) 本地序列号在同一个群里，不同发送者之间会撞号；
  2) 客户端只维护一个 cur_max_message_id，于是新消息判定「id > 水位线」会漏消息。

只依赖标准库；输出确定性。
"""

# 一个 100 人群里的 3 个发送者，各自维护自己的计数器（本地序列号）
SENDERS = ["alice", "bob", "carol"]
seq = {s: 0 for s in SENDERS}

def send(sender):
    seq[sender] += 1
    return {"sender": sender, "seq": seq[sender], "message_id": seq[sender]}

# 交错发送（确定性顺序）
timeline = [send(s) for s in ["alice", "bob", "alice", "carol", "bob", "alice",
                              "bob", "carol", "alice", "bob", "carol", "alice"]]

print("群内消息时间线（本地序列号 -> message_id）")
print("%-8s %-6s %-10s" % ("发送者", "seq", "message_id"))
for m in timeline:
    print("%-8s %-6d %-10d" % (m["sender"], m["seq"], m["message_id"]))

ids = [m["message_id"] for m in timeline]
dup_ids = sorted(set(i for i in ids if ids.count(i) > 1))
print()
print("message_id 重复出现的值：%s" % dup_ids)
print("  -> 同一个群内，不同发送者的 message_id 会撞号：复合主键必须是 (channel_id, message_id)，")
print("     单靠 message_id 定位消息在群内就已经不唯一。")
print()
print("客户端同步：只维护一个 cur_max_message_id，新消息判定 = message_id > cur_max")
cur_max = 0
delivered, missed = [], []
for m in timeline:
    if m["message_id"] > cur_max:
        delivered.append(m)
        cur_max = m["message_id"]
    else:
        missed.append(m)
print("  收到的 %d 条，被判为「不是新消息」而漏掉 %d 条：" % (len(delivered), len(missed)))
for m in missed:
    print("    漏掉: %s 的第 %d 条（message_id=%d，不大于当前水位线 %d）"
          % (m["sender"], m["seq"], m["message_id"], cur_max))
print()
print("结论：")
print("  - 本地序列号在「同一发送者内」单调，跨发送者不可比；")
print("  - 因此「单一水位线 + id 比较」这种同步模型在群聊里不成立；")
print("  - 修法二选一：(a) 水位线按发送者分开维护（每个发送者一个 cur_max_id）；")
print("                 (b) 排序键用 (send_time, seq) 复合键，而不是裸 message_id；")
print("  - 讲义把这两件事分开写（数据模型讲本地 ID、同步讲 cur_max），合起来看才有这个洞。")

输出：

    漏掉: bob 的第 3 条（message_id=3，不大于当前水位线 5）

结论：
  - 本地序列号在「同一发送者内」单调，跨发送者不可比；
  - 因此「单一水位线 + id 比较」这种同步模型在群聊里不成立；
  - 修法二选一：(a) 水位线按发送者分开维护（每个发送者一个 cur_max_id）；
                 (b) 排序键用 (send_time, seq) 复合键，而不是裸 message_id；
  - 讲义把这两件事分开写（数据模型讲本地 ID、同步讲 cur_max），合起来看才有这个洞。

这个洞值得说清楚：

  • 群里三个发送者各发了几条，message_id 撞号了：alice 的第 1 条和 bob 的第 1 条都是 1，carol 的第 1 条也是 1。讲义说复合主键要用 (channel_id, message_id)——注意在群里，channel_id 对所有成员是同一个，所以这个复合主键在群内仍然不唯一，真正唯一的其实是 (channel_id, sender_id, seq)。这不是说讲义错了（它说本地 ID 只在群内唯一，意思是不与别的群冲突），而是「群内唯一定序」这件事需要复合键才成立。
  • 客户端漏消息：12 条消息里只收到 5 条，漏掉 7 条（58%）。因为 bob 的第 1 条（id=1）在 alice 的第 5 条（id=5）之后到达，而 1 不大于当前水位线 5，于是被判为「不是新消息」。
  • 一对一聊天不受影响：一个频道只有一个对方，ID 序列天然单调，单一水位线是对的。这个洞只在群聊出现——而群聊恰恰是本地序列号这个选择的唯一理由。
  • 两种修法：(a) 水位线按发送者分开维护（每个发送者一个 cur_max_id，客户端存一张小表）；(b) 排序键用复合键 (send_time, sender_id, seq)，比较时不用裸 message_id。

这是本文最有价值的一处增量：它不是说讲义错了，而是说讲义的一个结论（可以用本地序列号）与另一个机制（单一水位线同步）不能同时用在群聊上——真实系统里两者常常被分别实现，然后在线上打出「有人说话但我看不到」。

三、增量二：群聊的消息存一份还是每人一份

讲义给了群聊的做法（每人一份收件箱）和它的代价（大群开销很大），但没给量级。把它算出来：

"""群聊存一份还是每人一份：存储量与读时组装的排序代价。

只依赖标准库；输出确定性。
"""
GROUPS = 1_000_000          # 全站群数
GROUP_SIZE = 100            # 群上限（讲义需求）
MSGS_PER_GROUP = 100_000    # 每群累计消息数
BYTES_PER_MSG = 200         # 单条消息估字节（正文 + 元数据）
SORT_KEYS = 40              # 排序键宽（复合键：时间 8B + 发送者 8B + seq 8B + 余量）

print("规模：%d 个群 x 每群 %d 人 x 每群 %d 条消息，单条按 %d B 估" % (GROUPS, GROUP_SIZE, MSGS_PER_GROUP, BYTES_PER_MSG))
print()
copies = GROUPS * GROUP_SIZE * MSGS_PER_GROUP
shared = GROUPS * MSGS_PER_GROUP
print("%-28s %18s %12s" % ("方案", "消息条数", "存储(TB)"))
print("%-28s %18d %12.1f" % ("讲义方案：每人一份收件箱", copies, copies * BYTES_PER_MSG / 1e12))
print("%-28s %18d %12.1f" % ("共享存储：每群一份", shared, shared * BYTES_PER_MSG / 1e12))
print("  -> 差 %.0f 倍；讲义说「对大群开销很大」，量级就是这个。" % (copies / shared))
print()
print("读时组装的代价：拉一个用户的收件箱，要合并所有发送者的消息流")
per_sender = MSGS_PER_GROUP // GROUP_SIZE
print("  每个发送者在本群的本地 seq 上限约 %d 条；拉一个收件箱要合并 %d 个流" % (per_sender, GROUP_SIZE))
print("  合并后必须按 (send_time, sender_id, seq) 排序，单条排序键 %d B" % SORT_KEYS)
print("  存排序键的成本：每群 %d 条 x %d B = %.1f GB（全站 %.1f TB）"
      % (MSGS_PER_GROUP, SORT_KEYS, GROUPS * MSGS_PER_GROUP * SORT_KEYS / 1e9,
         GROUPS * MSGS_PER_GROUP * SORT_KEYS / 1e12))
print()
print("为什么不能用裸 message_id 排序：本地序列号跨发送者会撞号")
sample = []
for sender, sid in (("alice", 1), ("bob", 1), ("alice", 2), ("bob", 2), ("carol", 1), ("alice", 3)):
    sample.append({"sender": sender, "seq": sid, "message_id": sid, "t": len(sample) + 1})
by_id = sorted(sample, key=lambda m: m["message_id"])
by_true = sorted(sample, key=lambda m: (m["t"], m["sender"], m["seq"]))
print("  按 message_id 排序 : %s" % " ".join("%s#%d" % (m["sender"][0], m["seq"]) for m in by_id))
print("  按 (时间,发送者,seq) : %s" % " ".join("%s#%d" % (m["sender"][0], m["seq"]) for m in by_true))
print("  -> 两者顺序不同：裸 message_id 排序会把 alice 的第 2 条排到 bob 的第 2 条之前，")
print("     时间线被打乱。群聊的排序键必须是复合键，这是「本地序列号」这个选择的连带成本。")

输出：

规模：1000000 个群 x 每群 100 人 x 每群 100000 条消息，单条按 200 B 估

方案                                         消息条数       存储(TB)
讲义方案：每人一份收件箱                     10000000000000       2000.0
共享存储：每群一份                          100000000000         20.0
  -> 差 100 倍；讲义说「对大群开销很大」，量级就是这个。

读时组装的代价：拉一个用户的收件箱，要合并所有发送者的消息流
  每个发送者在本群的本地 seq 上限约 1000 条；拉一个收件箱要合并 100 个流
  合并后必须按 (send_time, sender_id, seq) 排序，单条排序键 40 B
  存排序键的成本：每群 100000 条 x 40 B = 4000.0 GB（全站 4.0 TB）

为什么不能用裸 message_id 排序：本地序列号跨发送者会撞号
  按 message_id 排序 : a#1 b#1 c#1 a#2 b#2 a#3
  按 (时间,发送者,seq) : a#1 b#1 a#2 b#2 c#1 a#3
  -> 两者顺序不同：裸 message_id 排序会把 alice 的第 2 条排到 bob 的第 2 条之前，
     时间线被打乱。群聊的排序键必须是复合键，这是「本地序列号」这个选择的连带成本。

读法：

  • 讲义的「每人一份收件箱」在 100 人群里是 10¹³ 条消息副本、约 2000 TB；共享存储（每群一份）是 10¹¹ 条、约 20 TB——差 100 倍。 讲义说「对大群开销很大」，量级就是这个：群规模 100 时成本线性放大，群规模 1000 时就是 10 倍于此。
  • 代价的另一半在读时组装：拉一个收件箱要把 100 个发送者的消息流合并起来排好序，所以每条消息还得带一个 40 字节左右的复合排序键，全站 4 TB。这是「共享存储 + 读时组装」换来的省下来的 1980 TB 里必须付的部分。
  • 排序键不能是裸 message_id：脚本里两种排序结果不同——按 message_id 排出来是 a#1 b#1 c#1 a#2 b#2 a#3，按 (时间, 发送者, seq) 排是 a#1 b#1 a#2 b#2 c#1 a#3。前者把 alice 的第 2 条排到了 bob 的第 2 条前面，群里的时间线被打乱。这正是第二节那个洞在存储层的投影：本地序列号的选择，把「排序键必须是复合键」这件事一并带了出来。

所以这一节的判据是两条一起看：每群一份 + 复合排序键 + 读时组装是一个自洽的组合；「每人一份」在 100 人群就贵 100 倍，而它换来的好处（同步简单）可以用「按发送者维护水位线」以极小的代价拿到。

四、增量三：在线状态扩散与心跳阈值的两本账

讲义给在线状态设计的做法是：每对好友之间维护一个频道，A 的状态变化发布到 A-B、A-C、A-D 等频道。这套设计在小规模好友关系下有效——但它有个线性系数：好友数。

"""在线状态扩散：讲义用「每对好友一个频道」，成本是好友数的一次方。

只依赖标准库；输出确定性。
"""
DAU = 50_000_000
FRIENDS = 200             # 平均好友数
CHANGES_PER_DAY = 20      # 每人每天在线状态变化次数（上线/下线/移动端切换）

print("规模：%d DAU，平均 %d 好友，每人每天状态变化 %d 次" % (DAU, FRIENDS, CHANGES_PER_DAY))
print()
edges = DAU * FRIENDS / 2              # 无向好友边数
pub_pair = DAU * CHANGES_PER_DAY * FRIENDS
pub_user = DAU * CHANGES_PER_DAY
print("%-34s %14s %14s" % ("方案", "发布次数/天", "相对"))
print("%-34s %14d %13.0fx" % ("每对好友一个频道（讲义方案）", pub_pair, pub_pair / pub_user))
print("%-34s %14d %13.0fx" % ("每用户一个频道 + 客户端聚合", pub_user, 1))
print()
print("读法：")
print("  - 讲义方案：用户 A 状态变化要发布到 A-B、A-C、A-D 等 %d 个频道，每次变化 %d 次发布；" % (FRIENDS, FRIENDS))
print("    全站每天 %.0f 亿次发布，量级随好友数线性增长，好友越多越贵。" % (pub_pair / 1e8))
print("  - 替代：每个用户一个频道，状态变化只发布 1 次，好友关系在客户端侧（或服务端本地）聚合；")
print("    全站每天 %.0f 亿次发布，降 %.0f 倍。" % (pub_user / 1e8, pub_pair / pub_user))
print("  - 代价：客户端要多维护一份好友关系来聚合，状态到达有额外延迟（先到频道、再聚合过滤）。")
print()
print("判据：在线状态扩散的成本 = 状态变化频率 x 好友数（讲义方案）；")
print("      只要这个乘积进入亿级/天，就该换成「按用户发布 + 关系侧聚合」。")
print()

输出：

规模：50000000 DAU，平均 200 好友，每人每天状态变化 20 次

方案                                         发布次数/天             相对
每对好友一个频道（讲义方案）                       200000000000           200x
每用户一个频道 + 客户端聚合                        1000000000             1x

读法：
  - 讲义方案：用户 A 状态变化要发布到 A-B、A-C、A-D 等 200 个频道，每次变化 200 次发布；
    全站每天 2000 亿次发布，量级随好友数线性增长，好友越多越贵。
  - 替代：每个用户一个频道，状态变化只发布 1 次，好友关系在客户端侧（或服务端本地）聚合；
    全站每天 10 亿次发布，降 200 倍。
  - 代价：客户端要多维护一份好友关系来聚合，状态到达有额外延迟（先到频道、再聚合过滤）。

判据：在线状态扩散的成本 = 状态变化频率 x 好友数（讲义方案）；
      只要这个乘积进入亿级/天，就该换成「按用户发布 + 关系侧聚合」。

心跳阈值的影响：阈值 x 越大，误判离线越少但发现下线越慢（要等 x 秒）
  x= 10 秒 -> 误判下线最多滞后  10 秒；每秒心跳成本 = 50000000 DAU / 10 = 500 万 QPS
  x= 30 秒 -> 误判下线最多滞后  30 秒；每秒心跳成本 = 50000000 DAU / 30 = 167 万 QPS
  x=120 秒 -> 误判下线最多滞后 120 秒；每秒心跳成本 = 50000000 DAU / 120 = 42 万 QPS

读法：

  • 成本 = 状态变化频率 × 好友数。 按 5000 万 DAU、平均 200 好友、每人每天状态变化 20 次算，讲义的方案是每天 2000 亿次发布；换成「每用户一个频道 + 关系侧聚合」是每天 10 亿次，降 200 倍。代价是客户端要自己维护好友关系来做过滤，以及状态到达多一跳延迟。
  • 心跳阈值 x 是另一笔账：x 越大，误判离线的窗口越长，但发现下线也越慢。x=10 秒时心跳本身是 500 万 QPS，x=30 秒是 167 万 QPS，x=120 秒是 42 万 QPS。讲义举例 x=30 是个平衡点：把 30 秒改成 10 秒，心跳带宽涨 3 倍；改成 120 秒，误判下线的时间窗涨 4 倍。 心跳 QPS 与在线状态存储的读压力直接相关，这也是为什么这类系统通常把「最后一次活跃时间」写成写时更新而不是读时计算。
  • 两条账合起来给出判据：在线状态扩散走「每对好友一个频道」，前提是「变化频率 × 好友数」不进亿级/天；一旦进了，就该把发布粒度从「好友对」提到「用户」。

五、把三个模型套回本章（判据清单）

  1. 群聊的消息 ID 要复合：(channel_id, sender_id, seq)；客户端同步水位线按发送者分开维护，不要用单一 cur_max_message_id。1:1 聊天不受影响，但同一套客户端代码要能同时处理两者。
  2. 群聊消息共享存储 + 读时组装，别按人复制；排序键用 (send_time, sender_id, seq) 复合键，并单独算它的存储（全站 4 TB 量级）。
  3. 在线状态发布粒度按成本选：发布次数 = 变化频率 × 好友数；进亿级/天就改成「每用户一个频道 + 关系侧聚合」。
  4. 心跳阈值当成带宽参数算：x=10 秒 → 500 万 QPS，x=30 秒 → 167 万 QPS，x=120 秒 → 42 万 QPS；阈值直接影响误判窗口。
  5. 长轮询与 WebSocket 的取舍看在线率与消息密度（讲义只说长轮询对不活跃用户低效）：在线率高但消息稀疏时，长轮询的连接数远小于 WebSocket 的常驻连接；反之 WebSocket 更划算。
  6. 离线提醒复用通知系统的降级链路，见《通知系统的投递率怎么算》。

  • 消息队列与解耦：《扩展的每一步都在换瓶颈》。
  • 一致性哈希（把请求均匀分布到各服务器）：《一致性哈希实测》。

  • 信息流的推拉与缓存：已单独成文《写扩散还是读扩散》——那篇讲的是「推还是拉」，这篇讲的是「ID 怎么发、消息存几份」，机制不同，只在 fan-out 这个词上重叠。

七、这三个模型判不了什么

  • 本地序列号方案假设「群内排序只需要组内有序」。真实需求里常要「消息在全局可比较」（比如跨群搜索、审计、跨设备去重），那时本地序列号就不够用了，得回到全局 ID 或带逻辑时钟的混合 ID。
  • 存储账里的每条 200 B 与排序键 40 B 都是估的。真实字节数取决于正文长度分布、压缩率与序列化格式；且讲义说消息最长 100,000 字符——长消息会让「每条 200 B」的假设严重低估，长消息通常单独存对象、消息体只放引用。
  • 在线状态模型假设好友数均匀。真实好友分布是重尾的，少数超大会长用户贡献绝大部分发布量，单点参数会低估尾部成本。
  • 心跳模型假设心跳均匀到达。真实网络抖动会让「30 秒没心跳」既可能误判离线、也可能延迟判定，两者会同时变差。
  • 三个模型都不含端到端加密（讲义列为未来扩展）。加上 E2EE 后，服务端不再能看到消息正文，按发送者维护水位线的可行性、以及「服务端排序」的可行性都要重新评估。

FAQ（八、常见问题）

群聊能用本地序列号吗？ 能在「同一个发送者内」用，跨发送者不可比。必须配复合键 (channel_id, sender_id, seq)，客户端水位线按发送者分开维护；单一 cur_max_message_id 在群聊里会漏消息（实测 12 条漏 7 条）。

群聊的消息要复制给每个成员吗？ 不要。100 人群复制给每人就是 10 倍存储（讲义方案 2000 TB vs 共享存储 20 TB），代价换来的是「同步简单」——而这份简单可以用「按发送者维护水位线」以很小代价拿到。

在线状态要怎么广播？ 讲义的「每对好友一个频道」成本是变化频率 × 好友数（5000 万 DAU 下每天 2000 亿次发布）。改成「每用户一个频道 + 关系侧聚合」降到每天 10 亿次，代价是客户端多维护一份好友关系。

心跳间隔怎么定？ 当带宽参数算：x=10 秒是 500 万 QPS，x=30 秒是 167 万 QPS，x=120 秒是 42 万 QPS；同时 x 决定误判离线的窗口。讲义举例的 30 秒是「带宽 ×3 与误判窗口 ×4」之间的折中。

长轮询还是 WebSocket？ 看在线率与消息密度。在线用户多但消息稀疏时，长轮询的连接数远小于 WebSocket 的常驻连接；消息密集时 WebSocket 的复用优势才显现。讲义只说长轮询「对不活跃用户低效」，量化要结合本章 5000 万 DAU 的规模自己算。
