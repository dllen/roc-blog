消息队列的三笔账：分区数、至少一次的重复与存储乘数

#系统设计#架构设计#读书笔记#消息队列

消息队列的三笔账？分区数怎么定、重复消息从哪来、历史数据要占多少盘。讲义把消息队列的设计要素讲全了（模型、分区、消费者组、复制、再均衡、投递语义），但这三个「定」的动作它都留成定性判断。这篇把它们算出来。

这篇不复述译文，也不搬运中文译本的任何段落。它复述这一章的骨架（四个额外需求、两套消息模型、三种投递语义、扩展手段），然后补三个自写模型：分区数同时是三个天花板、至少一次投递的重复来源与去重表该存什么、保留期 × 副本 × 消费组的存储账。

口径说明

  • 源笔记是 Alex Xu《System Design Interview — An Insider’s Guide》第 19 章的社区中译。上游两仓库的 LICENSE 在 main/master 分支经 raw 通道取均返回 404，上游许可未能确认；原书是商业出版物。故本篇为导读式：只复述章节骨架与需求数字，不引用译文原文或原书段落，不使用译本配图，正文主体是自写模型与判断。
  • 三个脚本均为自写增量，只依赖 Python 标准库；输出为实跑结果，逐行可复现（三段计算都不含随机数；分区映射用固定 md5 哈希，避免字符串哈希随机化）。
  • 与已发文章的重叠见「这一章不重复已发的内容」一节。

一、本章骨架：四个额外需求、两套模型、三种投递语义

消息队列的四个好处：解耦（组件可独立更新）、更好的可扩展性（生产者与消费者按流量独立扩缩容）、更高的可用性（一部分挂了其余仍能与队列交互）、更好的性能（生产者发消息时不用等消费者确认）。

本章的范围（讲义用问答敲定）：消息只有文本、通常几 KB；消息可以被不同消费者重复消费（传统消息队列不支持）；顺序要保留（传统队列不支持）；消息保留两周（传统队列不支持）；生产者与消费者「越多越好」；投递语义至少支持 at-least-once，理想是三种全支持、做成可配置；性能上要能按用例在「高吞吐」与「低延迟」之间切换。

两套消息模型：点对点（一条消息被恰好一个消费者消费，确认后即从队列删除、没有数据保留）与发布订阅（消息关联到主题，消费者订阅主题）。讲义也指出 Kafka 与 Pulsar 严格说是事件流平台而不是消息队列，功能趋同、界限越来越模糊。

主题、分区与 broker：主题数据量大就拆成分区；消息在分区内 FIFO，分区内顺序保留；消息在分区中的位置叫偏移量；每条消息由分区键决定落到哪个分区（例如用 user_id 保证同一用户的消息有序）。托管分区的服务器叫 broker。

消费者组：同一批消息在消费者组之间是复制的（不是按消费者复制）；每组维护自己的偏移量；组内并行读能提吞吐但破坏顺序保证，缓解办法是「一个组内只允许一个消费者订阅一个分区」——于是组内消费者数量不能超过分区数。

可扩展性：生产者最容易扩；消费者组之间隔离、可随意增减，靠再均衡处理组内变化；broker 故障时由副本兜底、协调器重新分配分区、副本先作为从副本追上领导者再进入 ISR；最小 ISR 数量在延迟与安全之间权衡；副本应跨 broker 分散、跨数据中心更安全但延迟更高（可用数据镜像做变通）。加分区时通知生产者并触发消费者再均衡，且只把新消息写进新分区、不拷旧消息；减分区更复杂：分区下线后新消息只发往剩余分区、下线分区不立即删除（里面还有消息要消费）、保留期过后才截断释放空间、过渡期生产者只写活跃分区而消费者读所有分区、保留期后再均衡。

数据投递语义：最多一次——生产异步发送、失败不重试，消费者拉到就提交 offset（崩溃则这条丢失）；至少一次——生产用 ack=1/ack=all 并持续重试，消费者处理完才提交 offset，因此可能重复投递（处理完但提交前崩溃），适合「重复可接受或可去重」的用例；恰好一次——讲义说实现成本极高、对用户最友好。

高级特性：消息过滤（朴素做法在消费者侧过滤会引入无谓流量；也可打标签让消费者按标签订阅；按载荷过滤对加密消息难且不安全；让 broker 跑脚本/解析器对 MQ 太重）、延迟与定时消息（先发到临时存储，到期再移进分区；可用专用延迟队列或层级时间轮）。

二、增量一：分区数同时是三个天花板

讲义把「分区数」讲成一个扩展手段（主题太大就拆分区），但没有说它同时绑住了三件事。把它列出来：

"""分区数同时绑住三件事：吞吐上限、消费并行度上限、以及扩分区对顺序保证的破坏。

只依赖标准库；输出确定性。
"""
import hashlib

TARGET_QPS = 100_000        # 目标吞吐（msg/s）
PER_PARTITION_QPS = 10_000  # 单分区吞吐（估）
KEYS = 1_000_000            # 分区键基数（如 user_id）

def partition_of(key, partitions):
    """与真实实现一致的哈希取模（用 md5 模拟，避免 PYTHONHASHSEED 随机化）。"""
    h = int(hashlib.md5(key.encode()).hexdigest(), 16)
    return h % partitions

PARTS = 12                 # 选定分区数
print("目标吞吐 %d msg/s，单分区吞吐 %d msg/s -> 最少需要 %d 个分区，这里选 %d 个"
      % (TARGET_QPS, PER_PARTITION_QPS, -(-TARGET_QPS // PER_PARTITION_QPS), PARTS))
print()
print("同一个分区数绑住三件事：")
print("  1) 吞吐上限     = 分区数 x 单分区吞吐 = %d x %d = %d msg/s"
      % (PARTS, PER_PARTITION_QPS, PARTS * PER_PARTITION_QPS))
print("  2) 消费并行度   = 分区数（组内一个分区只能一个消费者）-> %d" % PARTS)
print("  3) 单 key 吞吐  = 单分区吞吐（同一 key 必须同分区）= %d msg/s" % PER_PARTITION_QPS)
print("  => 分区数必须**一次定对**：它同时是吞吐天花板、消费者数天花板和单 key 吞吐天花板。")
print()
print("热点检查：若某个 key 的流量占比 p 超过单分区吞吐 / 总吞吐，就会压垮它所在分区：")
total = PARTS * PER_PARTITION_QPS
for p in (0.01, 0.05, 0.10, 0.20):
    key_qps = total * p
    verdict = "超" if key_qps > PER_PARTITION_QPS else "安全"
    print("  单 key 占比 %5.1f%% -> %7.0f msg/s（单分区上限 %d）%s"
          % (p * 100, key_qps, PER_PARTITION_QPS, verdict))
print("  => 判据：单 key 占比 <= 单分区吞吐 / 总吞吐（本例 <= %.0f%%）；" % (100.0 * PER_PARTITION_QPS / total))
print("     超了就只能加分区或换分区键（比如把 user_id 换成 user_id + 业务维度）。")
print()
print("扩分区对顺序保证的影响（哈希取模变了）：")
keys = ["user-%d" % i for i in range(1000)]
before = {k: partition_of(k, 4) for k in keys}
after = {k: partition_of(k, 8) for k in keys}
moved = [k for k in keys if before[k] != after[k]]
print("  分区数 4 -> 8：%d/%d 个 key 的分区号变了（%.0f%%）" % (len(moved), len(keys), 100.0 * len(moved) / len(keys)))
sample = moved[0]
print("  例如 key %s：扩分区前在分区 %d，扩分区后在分区 %d -> **跨分区没有顺序保证**"
      % (sample, before[sample], after[sample]))
print("  => 判据：扩分区对「同一 key 有序」是**破坏性操作**：")
print("     要么接受边界处乱序，要么给分区键加 epoch 前缀（新分区用新前缀），")
print("     要么把顺序保证的边界明确画在分区内部（如同一会话、同一订单）。")

输出：

目标吞吐 100000 msg/s，单分区吞吐 10000 msg/s -> 最少需要 10 个分区，这里选 12 个

同一个分区数绑住三件事：
  1) 吞吐上限     = 分区数 x 单分区吞吐 = 12 x 10000 = 120000 msg/s
  2) 消费并行度   = 分区数（组内一个分区只能一个消费者）-> 12
  3) 单 key 吞吐  = 单分区吞吐（同一 key 必须同分区）= 10000 msg/s
  => 分区数必须**一次定对**：它同时是吞吐天花板、消费者数天花板和单 key 吞吐天花板。

热点检查：若某个 key 的流量占比 p 超过单分区吞吐 / 总吞吐，就会压垮它所在分区：
  单 key 占比   1.0% ->    1200 msg/s（单分区上限 10000）安全
  单 key 占比   5.0% ->    6000 msg/s（单分区上限 10000）安全
  单 key 占比  10.0% ->   12000 msg/s（单分区上限 10000）超
  单 key 占比  20.0% ->   24000 msg/s（单分区上限 10000）超
  => 判据：单 key 占比 <= 单分区吞吐 / 总吞吐（本例 <= 8%）；
     超了就只能加分区或换分区键（比如把 user_id 换成 user_id + 业务维度）。

扩分区对顺序保证的影响（哈希取模变了）：
  分区数 4 -> 8：491/1000 个 key 的分区号变了（49%）
  例如 key user-1：扩分区前在分区 0，扩分区后在分区 4 -> **跨分区没有顺序保证**
  => 判据：扩分区对「同一 key 有序」是**破坏性操作**：
     要么接受边界处乱序，要么给分区键加 epoch 前缀（新分区用新前缀），
     要么把顺序保证的边界明确画在分区内部（如同一会话、同一订单）。

三处结论：

第一，分区数是三个天花板里的同一个数。 目标 100k msg/s、单分区 10k msg/s ⇒ 至少 10 个分区，选 12 个。但同一个数同时是：吞吐天花板（12 × 10k = 120k）、消费并行度天花板（组内一个分区只能一个消费者 ⇒ 最多 12 个消费者）、以及单 key 吞吐天花板（同一 key 必须同分区 ⇒ 一个 key 最多 10k msg/s）。所以它必须一次定对：定小了吞吐上不去，定大了白白浪费 broker 资源，而事后调整的代价见下一条。

第二，热点判据是「单 key 占比 ≤ 单分区吞吐 / 总吞吐」（本例 8%）。 超过这个比例，承载该 key 的分区就会成为整条链路的最慢点——注意此时加分区也救不了，因为热点 key 永远落在某一个分区里。能救的只有换分区键（比如把 user_id 换成 user_id + 业务维度）或做 key 内部拆分。

第三，也是最容易被忽略的一条：扩分区是「同一 key 有序」的破坏性操作。 哈希取模的基数变了，key 到分区的映射就变了——模拟里分区数 4→8 时，1000 个 key 里 491 个（49%）的分区号变了，比如 user-1 从分区 0 挪到分区 4。旧消息在老分区、新消息在新分区，跨分区没有顺序保证。讲义只说「加分区时通知生产者并触发消费者再均衡」，把这层顺序影响留白了。落地有三条路：接受边界处乱序、给分区键加 epoch 前缀（新分区用新前缀）、或者把顺序保证的边界明确画在分区内部（同一会话、同一订单）——第三种最省事，也最该在设计期就定下来。

三、增量二：至少一次的重复从哪来，去重表该存什么

讲义说 at-least-once 下「消息可能被投递多次，例如消费者处理完消息但在提交偏移量前崩溃」，并说「这适合数据重复可接受或可去重的用例」。把「重复」量化，再看去重表要多大：

"""至少一次投递：重复从哪来、去重表要多大。

只依赖标准库；输出确定性。
"""
RATE = 100_000             # 消息速率 msg/s
MSG_KB = 4
CRASH_PER_HOUR = 0.5      # 消费者每小时崩溃次数（估）
ACK_LATENCY_S = 0.02      # 提交 offset 的耗时（估）
BATCH = 500                # 拉取批大小
PROCESS_THROUGHPUT = 20_000   # 单消费者每秒处理条数（估）

batch_seconds = BATCH / PROCESS_THROUGHPUT
window = batch_seconds + ACK_LATENCY_S
print("消费者每批拉 %d 条、每秒处理 %d 条 -> 一批处理 %.3f 秒；提交 offset %.3f 秒"
      % (BATCH, PROCESS_THROUGHPUT, batch_seconds, ACK_LATENCY_S))
print("崩溃窗口 = 处理 + 提交 = %.3f 秒" % window)
print()
dups_per_hour = CRASH_PER_HOUR * window * RATE
dups_per_day = dups_per_hour * 24
print("每小时崩溃 %.1f 次 -> 每小时可能重复投递 %.0f 条；每天 %.0f 条（占总量 %.3f%%）"
      % (CRASH_PER_HOUR, dups_per_hour, dups_per_day, 100.0 * dups_per_day / (RATE * 86400)))
print()
print("去重表要存多久？窗口必须 >= 消息可能被重投的最长时间。存什么，决定了它是 GB 还是 TB：")
DEDUP_ROW = 32             # 只存幂等键 + 载荷摘要
FULL_ROW = MSG_KB * 1024   # 直接把整条 payload 存进去
for dedup_window_s in (60, 300, 3600, 86400):
    entries = RATE * dedup_window_s
    print("  窗口 %6d 秒 -> %12d 条：存摘要 %8.1f GB；存整条 payload %8.1f GB"
          % (dedup_window_s, entries, entries * DEDUP_ROW / 1e9, entries * FULL_ROW / 1e9))
print()
print("  => 同样一小时窗口，存摘要与存整条 payload 差 %.0f 倍 —— 去重表存什么，"
      % (FULL_ROW / DEDUP_ROW))
print("     决定了它是几十 GB 还是上 TB；只有必要时才存完整 payload。")
print()
print("判据：")
print("  - 去重窗口 >= 消息可能被重投的最长时间（重试上限 x 退避 + 消费者重启时间）；")
print("  - 注意「至少一次 + 重试」会把重复放大：一次重试就多一份重复，")
print("    所以幂等键要按「业务唯一键」而不是「投递序号」来设计，否则重试会绕过去重。")
print("  - 另一种路线是「恰好一次」：讲义说它实现成本极高、对用户最友好——")
print("    代价通常落在事务协调或 broker 端的事务日志上，而不是消费者侧那点去重表。")

输出：

消费者每批拉 500 条、每秒处理 20000 条 -> 一批处理 0.025 秒；提交 offset 0.020 秒
崩溃窗口 = 处理 + 提交 = 0.045 秒

每小时崩溃 0.5 次 -> 每小时可能重复投递 2250 条；每天 54000 条（占总量 0.001%）

去重表要存多久？窗口必须 >= 消息可能被重投的最长时间。存什么，决定了它是 GB 还是 TB：
  窗口     60 秒 ->      6000000 条：存摘要      0.2 GB；存整条 payload     24.6 GB
  窗口    300 秒 ->     30000000 条：存摘要      1.0 GB；存整条 payload    122.9 GB
  窗口   3600 秒 ->    360000000 条：存摘要     11.5 GB；存整条 payload   1474.6 GB
  窗口  86400 秒 ->   8640000000 条：存摘要    276.5 GB；存整条 payload  35389.4 GB

  => 同样一小时窗口，存摘要与存整条 payload 差 128 倍 —— 去重表存什么，
     决定了它是几十 GB 还是上 TB；只有必要时才存完整 payload。

判据：
  - 去重窗口 >= 消息可能被重投的最长时间（重试上限 x 退避 + 消费者重启时间）；
  - 注意「至少一次 + 重试」会把重复放大：一次重试就多一份重复，
    所以幂等键要按「业务唯一键」而不是「投递序号」来设计，否则重试会绕过去重。
  - 另一种路线是「恰好一次」：讲义说它实现成本极高、对用户最友好——
    代价通常落在事务协调或 broker 端的事务日志上，而不是消费者侧那点去重表。

三处结论：

第一，重复来自一个可算的窗口。 消费者每批 500 条、每秒处理 2 万条 ⇒ 一批处理 0.025 秒，加上提交 offset 的 0.02 秒，崩溃窗口 = 0.045 秒。消费者每小时崩 0.5 次 ⇒ 每小时可能重复 2,250 条、每天 5.4 万条（占总量 0.001%）。重复率不大，但它是系统性的：只要消费者会崩，重复就必然存在，所以幂等不是「可选优化」而是「至少一次语义的必要配套」。

第二，去重表存什么，决定了它是几十 GB 还是上 TB。 同样一小时窗口：只存幂等键 + 载荷摘要（32 B/条）是 11.5 GB；把整条 payload 存进去（4 KB/条）是 1,474 GB——差 128 倍。判据是：窗口 ≥ 消息可能被重投的最长时间（重试上限 × 退避 + 消费者重启时间），而存摘要是默认选择，除非业务真的需要拿重复的那条原文。

第三，幂等键必须按「业务唯一键」设计，不能按「投递序号」。 讲义提了「至少一次 + 重试」，但重试会制造重复投递；如果幂等键是投递序号，每次重试都是一个新序号，去重就被绕过去了。业务唯一键（如订单号 + 操作类型）才是稳定的去重依据。至于讲义说的「恰好一次对用户最友好、实现成本极高」——它的代价通常落在事务协调或 broker 端的事务日志上，而不是消费者侧这张去重表；两者不能混为一谈。

四、增量三：保留期 × 副本 × 消费组，是三个乘数

讲义给了「保留两周」、副本（同步副本）、以及「消息按消费者组复制」。三个都是乘数，叠起来：

"""存储账：保留期 x 副本数 x 消费组数。

讲义说消息保留两周、可被不同消费者重复消费（按消费者组复制）、副本做持久化。

五、把三个模型套回本章（判据清单）

  1. 分区数一次定对：它同时是吞吐天花板、组内消费者数天花板、单 key 吞吐天花板（本例 12 个分区 = 120k msg/s = 12 个消费者 = 单 key 10k msg/s）。
  2. 热点判据：单 key 占比 ≤ 单分区吞吐/总吞吐（本例 8%）；超了加分区无效，要换分区键。
  3. 扩分区要先想清楚顺序：分区数变化会改掉 key→分区 的映射（4→8 时 49% 的 key 换区）；要么接受边界乱序、要么加 epoch 前缀、要么把顺序边界画在分区内部。
  4. 至少一次 ⇒ 幂等是必需品：重复窗口 = 处理 + 提交 offset 的耗时；幂等键用业务唯一键；去重窗口 ≥ 消息可能重投的最长时间；去重表存摘要不存 payload（11.5 GB vs 1.4 TB）。
  5. 存储按三个乘数算：保留期 × 副本 × 消费组；加消费组的成本是加一整份历史。
  6. 减分区比加分区贵（讲义给了四步过渡），所以它应该是最后手段，而不是「调整分区数」这个动作的默认选项。

七、这三个模型判不了什么

  • 单分区吞吐 10k msg/s、消费者每秒处理 2 万条、每小时崩 0.5 次都是估的。真实值随硬件、批大小、消息大小变化；重复率与去重表大小随这些参数线性变化，结论的形状不变。
  • 分区映射用 md5 取模模拟。真实实现可能用不同哈希或一致性哈希；「扩分区导致 key 迁移」这个结论对任何取模类映射都成立，但对一致性哈希类的迁移比例会小很多（只迁移部分 key）——这一点值得单独验。
  • 没算再均衡的代价。讲义说扩分区会触发消费者再均衡；再均衡期间要 stop-the-world 还是增量接管、暂停消费多久，直接决定扩分区能不能在业务高峰期做。这块讲义没展开。
  • 没算副本同步的写放大：3 副本 + 同步复制意味着每条消息写 3 份，leader 还要等 follower 确认——这会直接影响端到端延迟与吞吐上限，本文的模型里没体现。
  • 三个模型都不含 broker 自身的故障与恢复（讲义讲的 leader 选举、ISR 追赶、副本重新分配）。

FAQ（八、常见问题）

分区数应该定多少？ 至少满足吞吐目标（目标吞吐 ÷ 单分区吞吐），并把它当三个天花板看：吞吐上限、组内消费者数上限、单 key 吞吐上限。本例目标 100k msg/s、单分区 10k ⇒ 至少 10 个，选 12 个。定完还要查单 key 占比是否超过 8%（单分区吞吐/总吞吐）。

扩分区会破坏顺序吗？ 会。哈希取模的基数变了，key 到分区的映射就变了——模拟里 4→8 时 49% 的 key 换了分区，同一 key 的新旧消息落在不同分区，跨分区没有顺序保证。要么接受边界处乱序、要么给分区键加 epoch 前缀、要么把顺序边界限定在分区内部。

至少一次到底会重复多少？ 重复来自「处理完但还没提交 offset」的窗口：批处理 0.025 秒 + 提交 0.02 秒 = 0.045 秒，消费者每小时崩 0.5 次 ⇒ 每小时约 2,250 条、每天 5.4 万条重复。所以幂等消费者不是可选项。

去重表要存多久、存什么？ 窗口要 ≥ 消息可能被重投的最长时间（重试上限 × 退避 + 重启时间）。存幂等键 + 载荷摘要（32 B/条）：一小时 11.5 GB；存整条 payload（4 KB/条）：一小时 1.4 TB，差 128 倍——默认存摘要。

加一个消费者组要多花多少存储？ 一整份全量历史。本例 100k msg/s × 4 KB、保留两周、3 副本：单组 1.4 TB，两组 2.8 TB，五组 7.3 TB。副本可以按分区冷热差异化，消费组不行。
