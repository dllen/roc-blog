版本管理该把什么当作基本对象

#版本管理#Git#软件工程#Agent 协作

版本管理的教程都在教命令。真正值得讨论的是它的设计前提：如果今天重新设计一套版本管理系统，你会把什么当作基本对象？如果主要使用者变成了能快速工作、还能并行复制的 Agent，原来的设计有哪些前提需要重想？ 「版本管理该把什么当作基本对象」这个问题背后还有一层：当执行者从人变成可以并行复制的 Agent，哪些原本靠人顺手协调的细节会变成显著成本。

本文整理自南京大学《生成式软件工程》2026 秋第 4 讲「版本管理 (2)」（主讲：jyy），原始讲义。

一、文件是接口，项目不是目录树

传统看法把软件项目看成各种文件的集合：Intent（意图）记录想做什么，Spec（规约）说明具体应当满足什么要求，Code 给出实现，再加上测试、配置、文档和生成的产物。这些开发过程中形成的对象统称 artifact。

讲义随即给出一个清醒的判断：文件是一个非常成功的接口，但它首先是现有文件系统和工具生态提供的方便，项目本身并不天然就是一棵目录树。

人可以用编辑器阅读修改，程序可以搜索比较编译打包，版本管理工具也能接手——这些都是既得利益。但「放在文件里」是历史条件，不是本质。把所有内容存进数据库，同样能组织一个项目，只是围绕文本文件积累的大量工具和习惯不再能直接可用。

目录树尤其不擅长直接表达制品之间的关系。举一个个人助手的例子：需求是「记住用户纠正过的偏好」。这条需求可能对应一条规格、一个更新记忆的函数、几组测试。现在用户又提出「有些偏好只在某段时间内有效」——想知道的不只是哪个文件变了，还包括哪些设计假设受到影响、哪些实现需要调整、哪些测试应该增加。

从需求走到设计、实现和验证，再从一段代码反查它服务的需求，这类关系构成 traceability（可追踪性）。

关键在于：把相关文件放进同一个目录，不会自动建立这些联系；保存每个文件的所有版本，也不会自动说明某项设计为什么存在。

二、快照、分叉与合并：冲突发生在意图层面

Git 管理文件内容、目录树，以及快照之间的历史关系。一次 commit 除了指向文件状态，还记录父提交、作者、说明等信息。父提交的连接把历史组织成一张有向无环图（DAG）。

如果两个人都从 A 出发，一人修改输入方式，另一人修改结果展示，就会得到两条开发路线。Merge 把两边成果整合起来，产生同时连接两边历史的新提交；Rebase 把一条路线上的改动重新应用到另一个起点上，让这些改动「好像是在新的基础上依次完成的」。

冲突来自两边对共同状态作出了不能直接兼容的修改。讲义给了一个配置项的例子：原来写着「立即保存」，一边改成「手动确认后保存」，另一边改成「每分钟自动保存」。工具可以发现文本上的分歧，究竟要哪一种行为，却需要回到需求。

更进一步：即使改动位于不同文件、能够自动合并，组合起来也可能违背双方原来的假设——这说明合并冲突只是症状，真正的冲突发生在意图层面。

三、change ID：把两个身份拆开

理解了快照之后，Git 的某些操作会让人感到一点「不和谐」。执行 cherry-pick 时，你通常想搬走的是某次提交引入的改动；执行 rebase 时，你也认为「我做的还是那件事，只是换了一个基础」。但我们传给工具的主要标识，是 commit。

问题出在身份的绑定方式上：commit 的身份与它的具体内容和元数据相联系。父提交一变，commit 的内容就变了；重写时会创建新的 commit 对象，得到不同的 ID。于是原来的 C 经过重写变成 C′：人知道这仍然是在修改同一个功能，单靠 commit ID 却无法表达这种身份的延续。

讲义在这里点出两个必须区分的问题：

  • 某个版本的准确状态是什么（由 commit ID 标识）
  • 某项改动随着反复修改经历了哪些版本（改动本身的身份）

把后一个问题直接纳入工具设计，就走到了 Jujutsu 的一个重要思路。它常简称为 jj，用 change ID 追踪一项持续演化的改动，同时保留 commit ID 标识具体版本。官方术语说明里的措辞很明确：

Rewriting a commit results in a new commit, and thus a new commit ID, but the change ID generally remains the same.

所以 C 和 C′ 可以拥有不同的 commit ID，却延续同一个 change ID。

这里要澄清一个容易误解的点：讲义特别强调，change 仍然是随时间演化的提交，它的底层依然保存快照，并不是把系统改成了补丁文件的集合。

这个抽象变化的价值在于把两个正交的身份显式分开。 commit ID 是「这个快照是什么」，change ID 是「这项演化的东西是谁」。同样的思路在别处也反复出现——区分组织身份与组织属性、区分「业务发生的时间」与「系统得知的时间」。真正可迁移的不是 jj 的命令，而是这个提问习惯：我手上这个标识，回答的是哪个问题？

四、冲突可以是一种被保存的状态

另一个值得单独拿出来的设计是把冲突作为可以保存的状态。

假设正在把一串改动移到新的基础上，其中一处发生冲突。在 jj 中，冲突可以直接记录在重写后的提交里，rebase 先完成，之后再处理冲突。系统保存的是冲突的逻辑表示，仍然能够对它继续进行重写和合并。

官方文档列出的好处不只是「少敲几个命令」：

  • 不再需要 git rebase --continue 这类命令，处理冲突走统一流程：检出那个提交、解决、amend；
  • 支持 auto-rebase，被重写的提交的后代自动跟着重写；
  • 合并提交里的 change 可以定义为「与两个父提交相比的差异」，因此合并提交能被正确 rebase（包括常见的 evil merge 问题）；
  • 可以把冲突解决推迟到你准备好了的时候，同时让工作中的提交始终保持 rebase 到上游最新状态；
  • criss-cross 合并和 octopus 合并这类复杂情形变得平凡。

讲义称之为课堂所说的 killer feature：冲突的存在不必把整个操作卡在半途中。

但真正值得留意的是抽象发生了什么变化——当一项过去被当作异常或临时过程的东西，可以被明确表示、保存和继续操作，许多流程就有机会统一起来。

五、工作区也进了模型

Git 的常见流程是先编辑，再通过暂存区挑选内容，最后提交。jj 把当前工作区对应到一个可以继续修订的提交，大多数命令执行时会先把文件变化保存为新的快照（Working Copy 文档）。

使用体验有点像不断 commit 和 amend 已有提交，因此不必把一个独立的 staging area 当作日常操作的中心。另一个差异是新增文件默认隐式跟踪——你往工作区放一个新文件，跑一次 jj st 它就被提交了。

这类差异看着是细节，实际影响的是操作顺序：Git 训练出来的肌肉记忆在这里全部要重练。讲义对此有一句挺实在的建议：先理解更自然的抽象，再回望历史，理解旧设计为什么会出现。工具的熟练程度会过时，对设计前提的理解却可以带到下一套工具里。

六、当开发者可以并行复制

前面的设计仍然很大程度上围绕人展开。课堂把人戏称为 single-threaded 的生物：我们只有一双手、一张嘴、一对眼睛。虽然能够同时惦记许多任务，实际与开发环境交互的带宽相当有限。对一个人来说，分支、stash 和工作区切换已经能支持不少场景。

Agent 改变了这个节奏：一次范围合适的修改，可能在分钟级就推进到可以提交的程度；多个 Agent 还可以同时工作。 一个负责界面，一个负责数据处理，另一个补充验证。但共享目录会立刻带来问题：某个 Agent 刚读过的文件可能被另一个改掉，测试正在运行时实现又发生了变化。讲义给出的提醒很尖锐：

给每个 Agent 起一个名字，并不会自动获得独立的开发环境。

一个自然的办法，是把每个 Agent 当成独立开发者，各有一份仓库，再把其他仓库配置为 remote 来同步成果。Git 还提供了可以在本地使用的 worktree：同一个仓库关联多个工作目录，各自拥有工作区、HEAD 和暂存区，同时共享仓库中的对象和大部分引用。

git worktree add -b agent-ui ../project-ui
git worktree add -b agent-memory ../project-memory

这样，两个 Agent 可以分别在界面分支和记忆分支上开发，各自运行测试，再把成果整合起来。新提交已经存在于共享的本地仓库中，无需互相 push、pull，修改仍然需要通过 merge 或 rebase 汇合。worktree 的完整用法在另一篇里有专门展开。

但 worktree 减少的是相互覆盖工作文件的问题，任务之间的依赖仍然要管理：界面等待什么数据格式，记忆模块什么时候能提供这个接口，双方是否采用了相同的错误处理约定。

这里有个很实际的推论：多个 Agent 并行时，最先该固化的不是代码结构，而是一份共享的接口约定——数据格式、错误约定、时序。否则 worktree 只是把冲突从文件层面推迟到了合并层面。并行执行的成本，会以依赖协调的形式重新出现。

七、先分开做再合并，还是先上锁

回到最初的问题：为什么需要版本控制？人的生产速度有限，人和人之间沟通困难，沟通过后还会误解和出错。目标是保存可靠的状态、分小步前进、让不同方向独立探索、让失败之后能够回查。

两种经典机制体现了这个目标。bisect 可以利用一组可重现的好坏判断，逐步缩小引入问题的提交范围；blame 可以把当前代码行关联到相应的历史修改，帮助找到当时的上下文。它们减少了对人的记忆的依赖。

讲义在此处做了一次价值重估：这些机制当然可以被用于找责任人，但在工程里，更有用的问题往往是「这个决定当时为什么合理，现在什么前提变了」。

课堂由此提出了一个有点挑衅的设想：反正没有哪个 Agent 能被开除，我们能不能再也不要 blame，只让它把事情推进、把问题修好？ 这里想重新考虑的是协作流程的目标——如果执行者主要是可复制的 Agent，能不能减少围绕个人交接和事后协调的步骤，直接围绕项目状态组织工作？

一种设计是锁。由主 Agent 负责规划，把任务拆成边界明确的部分；子 Agent 要修改某项共享资源时先取得互斥锁，读取最新状态，完成修改和必要检查，留下可恢复的快照，再释放锁。锁的定义是：同一时刻，只允许一个参与者修改约定范围内的状态。

具体例子：两个任务都要改个人助手的记忆格式。先取得锁的 Agent 完成一次一致的修改，后一个取得锁后重新读取最新状态，再继续工作。主 Agent 则可以把不依赖这项资源的工作继续分配出去——这正是锁相对于「全局大锁」的并行度收益。

讲义借数据库里的 MVCC（多版本并发控制） 帮助理解另一种路线：保留多个版本，让工作先推进，再处理版本之间的关系。讲义严谨地限定了类比范围：这是关于并发策略的类比；Git 的合并并不因此具有数据库事务的全部性质。（顺带一提，MVCC 本身在共享状态那一层有更完整的展开。）

上锁也有代价，讲义列了四类具体问题：

  • 粒度问题：锁住整个项目很简单，但可能把并行工作重新排成串行；只锁一个文件比较灵活，却未必覆盖跨文件的不变量——例如接口定义和调用方必须一起更新，只锁其中一个文件就不够；
  • 回收问题：Agent 意外停止时，锁如何回收？
  • 死锁问题：一个任务同时需要两项资源时，怎样避免互相等待？
  • 陈旧读问题：后一个任务拿到锁后，有没有继续使用等待之前读到的旧内容？

最终判断是：「Agent 先上锁再干活」是一条值得实验的设计路线。它让我们看到三种协作协调方式：工作之前通过调度和互斥协调（锁），工作之后通过版本和合并协调（分支/合并），以及两者的结合。

选择哪种机制，要看共享资源、冲突频率和返工代价，而不能只看参与者是不是 AI。

八、人多以后，困难转移到了协作

版本管理终究只是工具。真正困难的，是团队怎样持续朝着同一个目标前进。

若 n 个成员都可能需要两两沟通，潜在的沟通关系有 n(n−1)/2 条——3 人是 3 条，6 人就有 15 条。讲义严谨地限定：它数的是潜在关系，并不意味着每个团队的实际耗时都严格服从这个公式；清楚的接口和组织分工，正是在减少必须直接协调的关系。

两个典型失败场景：

  1. 语义分歧：每个人都觉得自己的部分很清楚。界面已经能展示模拟数据，后端已经通过自己的测试，但两边对字段含义和失败情况的理解不同。
  2. 完成度分歧：大家都说任务「基本完成」，有人指代码写完，有人指测试通过，有人则以为可以部署。还有人为了等待上游决定不断改计划，上游却不知道自己的延迟挡住了谁。

结果是：代码量增长了，项目离可用状态的距离却没有按同样速度缩短。

分歧也可能出现在目标和责任上：一个人要赶紧上线，另一个人要趁机重构，两个人都觉得自己在帮项目。界面、接口、测试分别有人负责，跨模块的问题却可能落在分工的缝隙里。讲义指出：再多几个提交也不能自动确定优先级，或者替团队找到愿意把整件事接起来的人。

这一节的结论是版本管理留给我们的启发——把项目看成一个持续演化的过程：保存当前状态，保留走到这里的历史和教训，允许多条探索路线存在，并设计它们重新汇合的办法。

九、从零开始：你就是包工头

讲义把视角转回课程实验（实验一：会成长的个人助手），给出一个角色隐喻——你就是包工头：决定先做哪一块，说明各部分怎样接起来，判断交付的东西能不能用。Agent 可以写很多代码，但目标、接口、验证和节奏仍然需要组织。

一个反直觉的事实：从零开始做产品，有时比参与一个成熟开源项目更难。 成熟项目已经固定了许多选择：用户是谁，代码怎样分层，什么叫兼容，测试怎样运行。做一个局部修改时，可以沿着这些约束前进。空项目里的约束少、自由度大，Intent、Spec、Impl 之间的缺口也就有更多机会被默认选择填满。

以「会成长的个人助手」为例，至少留下几个决定：成长指记住事实、修正偏好，还是学会执行新任务？助手什么时候应该主动行动？记错了以后怎样纠正？

反面推演：如果一开始就把所有记忆都设计成永久有效，后来才发现大量信息有时间和场景限制，早期那个看起来很确定的数据结构，就把一项需求误解固定进了实现。

早期 prompt 对项目走向的影响尤其大。 第一次描述里的「确定设计」，往往会成为以后代码和讨论的默认前提。接下来的 Agent 读到现有实现，又会顺着它继续生成。一个方便的临时选择，可能就这样逐渐变成 technical debt——未来修改系统时必须额外偿还的技术债。

技术债也可能来自认识的进步。第一版的设计在当时有充分理由，真正做出来、用起来之后，团队才知道哪些概念应当分开、哪些接口应当重新组织。Martin Fowler 在 Technical Debt Quadrant 里讨论过这种情况：即使团队认真设计，也可能在学习之后发现原来的结构已经落后于新的理解。讲义关注的不是债务本身，而是怎样记录这个发现，以及何时调整结构。

最后是 MVP（Minimum Viable Product，最小可行产品）：做出足够小、又真正投入使用的版本，检验最关键的假设。开工前先写下两个问题：这个版本要验证什么？出现什么结果，就说明我们想错了？

落到个人助手，第一版不必包揽邮件、日程、浏览器和所有长期记忆。讲义建议的范围非常小——先选择一个你每天都会遇到的场景：记录一项偏好，在下一次相关任务中使用它，并允许你纠正。 这个版本可以很粗糙，但你能亲自观察三件事：它有没有帮忙、记忆有没有被正确利用、纠正之后是否真的改变了行为。
