当代码不再值钱：从 Linus 到 LLM，一个行业信条的两次反转

#LLM#软件工程#技术思考#AI

2026 年，一个中国后端工程师的日常大概是这样的：上午用 Cursor 搭完一个部门内部工具的完整后台——CRUD 接口、权限校验、Dockerfile 打包、甚至 Github Actions 一键生成；下午参加需求评审，发现产品经理想做的功能去年其实做过一次，相关代码散落在三个微服务里，没人记得为什么这么设计，而负责那段代码的同事半年前转岗了。

代码从来没有这么好写过，也从来没有这么不值钱过。

本文尝试回答一个问题：当 LLM 能让任何人在几分钟内产出能跑的代码时，一个软件工程师的不可替代性到底在哪里？

沿着 Linus Torvalds 那句统治行业二十余年的信条——“Talk is cheap. Show me the code”——我追溯它在 2025 年的一次回响和 2026 年的一次反转，最终落到一个递进的论点：不是代码变廉价就说明写代码的人变廉价了，而是“能写出对的代码“的门槛，反而比任何时候都高了。

一、1991-2000，Linus 的锤子

2000 年 9 月，Linus Torvalds 在 Linux 内核邮件列表中回复一位讨论者时甩出了这句后来成为程序员圣谕的话：

“Talk is cheap. Show me the code.”

放在当时的语境下看，这句话锋利得有理有据。Linux 内核开发社区里永远不缺“架构师“——他们热衷于在新特性讨论帖里长篇大论，画出精美的框图，提供五六种方案，然后用几百封邮件论证其中一种最优雅。但他们不写代码。真正把功能落地的人，永远是另一小撮沉默的贡献者。

Linus 的愤怒指向的是一种不对称：talk 的成本几乎为零——你在邮件列表里花三十分钟写一段设计建议，消耗的只是你自己的时间；但你要让别人相信你的建议可行、值得投入精力去实现，你需要提供一个东西来抵消这种信任成本。在那个年代，这个东西就是代码。能跑的代码是唯一的硬通货。

这里面有一个隐含的前提，在 2000 到 2024 年间几乎从未被质疑：产出代码需要巨大的投入。一个人要写出能用的内核补丁、文件系统驱动或 TCP 栈，意味着他至少：

  • 熟练掌握了 C 语言和 POSIX 编程模型；
  • 理解内核内部的数据结构和同步机制；
  • 有能力在真实硬件上调试和验证；
  • 并且愿意付出几周甚至几个月的专注时间。

这些门槛合在一起，把“能写代码的人“筛选到极少数。代码本身在市场上是稀缺品。当代码稀缺时，talk 是 cheap 的——因为你靠嘴说出来的东西，远远不足以证明你愿意投入代码所需要的那份努力。

Linus 的逻辑不是“讨论不重要“，而是“如果你真想推动一件事，把你写的那部分代码拿出来“。这是一种以产出物稀缺性为基础的工作证明机制。在接下来四分之一个世纪里，这个机制运转得如此良好，以至于“Talk is cheap. Show me the code“从内核社区的内部准则溢出为整个行业的集体潜意识。面试看 GitHub，晋升看交付量，说服同事靠 POC 原型——代码即议价权。

二、2025，Parra 的回响

2025 年 7 月，软件工程师 Andres Parra 写了一篇短文，标题就是这句话本身——“Talk is cheap. Show me the code.” 他把这句内核社区的箴言延伸到了更广泛的个人成长和创业哲学中：

“Torvalds 认识到了人类的一个基本真相：我们倾向于迷失在抽象和无穷无尽的计划中而不采取行动。”

Parra 的立场是彻底的行动主义。他说自己在业余项目上反复验证过：前进的最好方式，是先做出点什么——什么都行，哪怕它不完美。 他把这个原则对标到创业方法论：成功的创业公司总是先做一个 MVP，验证它能工作，然后再进入更深层的规划。

这篇文章写得很真诚，也很有道理。事实上，它很大程度上是对的——在很多场景下仍然是。一个在 2025 年还在为要不要做某个项目而纠结了两个月的工程师，确实需要听一听这句话。

但有一个值得注意的细节：Parra 发表这篇文章的时间是 2025 年 7 月。在这个时间点，Claude Code 已经发布两个月，Gemini CLI 正在内测，GPT-5 尚未问世但已经被广泛预期。LLM coding 的浪潮即将吞噬整个行业，但那种吞噬的深度和速度，在 2025 年夏天仍然超出大部分人的想象。

Parra 的“talk is cheap, show me the code“，说的是用行动对抗完美主义。它的核心价值是心理层面的：不要因为害怕写出来的东西不够好而什么都不写。这个价值没有过时，但它在 LLM 的世界里悄然褪色——因为**“写出来“这件事的成本已经急剧下降到了几乎人人都能承担的水平。** 当 copilot 在 0.5 秒内补全一行代码，当 cursor 在 30 秒内生成一个完整函数，当 claude CLI 在 5 分钟内搭出一套项目骨架，“show me the code” 的重量就不可逆地减轻了。

三、2026，Nadh 的反转

2026 年 1 月，Kailash Nadh——zerodha 的技术负责人、一个在开源社区深耕多年的工程师——发表了一篇题为 “Code is cheap. Show me the talk.” 的文章，将 Linus 的信条完全颠倒过来。

这是一个精心设计的反转。Nadh 不是 LLM 的狂热信徒，也不是“编码已死“的布道者。他是一位有深厚技术根基、在真实业务中使用了 LLM 的工程师。正因为如此，他的结论比任何一周前还在 push vibe-coding 的推特大 V 都更有分量。

3.1 代码为什么变廉价了？

Nadh 的论证从四个维度展开：

第一个维度：努力成本的塌缩。 过去需要几周甚至几个月才能完成的开发工作，现在能在几天甚至几小时内完成。他没有用“零成本“这种夸张说法，而是精确地指出：产出功能性软件的“生理、认知和情绪成本“已经至少减少了几个数量级。

这几个认知维度拆解得非常诚实：

  • 生理成本：从昼夜对着显示器打字，到用自然语言描述需求——体力损耗本身下降了；
  • 认知成本：从需要把脑子里的抽象设计精确翻译成特定语言的语法和 API 调用，到用自然语言表达意图——翻译损耗大幅下降；
  • 情绪成本：从一个 bug 卡一整天带来的沮丧，到把栈跟踪扔给 LLM 秒出修复——挫败感显著降低。

这三个成本合在一起，解释了我们最近一年来一个普遍的感受：写代码这件事，从“有门槛的技能“变成了“只要会说话就能做“的事情。 就像数码摄影把拍照的成本降到了零（胶卷、冲印、暗房全部消失），LLM 把写代码的成本降到了前所未有的低。

第二维度：稀缺性蒸发。 Nadh 点出了一个关键变化：一直以来，一个高质量的大型代码库本身就是其作者投入了巨大心血的信号。一万行整洁、有组织的代码背后，往往意味着作者对这门语言、这个框架、这个领域的深度积累。但现在，LLM 可以“一秒生成同样的东西“。任何可以无限量、零努力生成且缺少可验证出处的东西，都很难被赋予价值。

这个逻辑很像经济学上的“资源诅咒“：当一个资源变得太丰富、太唾手可得，它的交换价值就会崩溃。代码曾经是稀缺资源，现在它在 LLM 的图灵管道里像水龙头一样流出来。过剩的代码不再是资产，而是负债——需要被审查、被维护、被理解的负债。

第三维度：质量信号的失灵。 这是 Nadh 最精彩的一层洞察：我们过去用来识别好代码的那些信号——统一的代码组织、完善的文件结构、详细的文档、整洁的 README——现在全部失效了，因为它们也可能是 LLM 在几秒内生成的。

“一个东西看起来越惊艳、越完美，反而越可疑。”

这在一个层面上是对整个软件美学的摧毁：如果一个 GitHub 仓库看起来“太漂亮“，你反而不知道它是一个资深工程师精心打磨的作品，还是一个实习生用一行 prompt 生成的。漂亮曾经是认真工作的副产品，现在变成了一声“不确定这是谁做出来的“的警告铃。

第四维度：溯源的崩塌。 Nadh 提出了一个严肃的哲学担忧：当我们无法知道代码背后的“人类投入“时，所有代码在 LLM 的无限产能面前都变成了“slop“——堆砌的、不可分辨的、没有意义的文本。他用博尔赫斯的巴别图书馆作隐喻：一个包含所有可能排列组合的文本的图书馆，在理论上“包含“一切知识，但因为你永远不知道哪些是人类写的、哪些是随机排列组合的巧合，整个图书馆变得毫无意义。

3.2 那什么变得值钱了？

Nadh 的答案很直接：talk——不是空谈，而是“想象问题、清晰表达、定义问题陈述、进行架构和工程决策“的能力。语言知识、语法知识、框架经验这些过去构成程序员核心竞争力的东西，不再是瓶颈。

这也是人类软件发展史上第一次出现的一种状态：好的 talk 比好的 code 指数级地更有价值。

但这个结论有一个非常重要的注脚，也是 Nadh 全文中我最认同的部分：他同时拒绝了两端的极端——既反对“vibe coding“式的狂欢（对着 AI 一顿狂写，从不审查生成的代码），也反对彻底的 LLM 拒绝主义。他给了一条中间路径：对掌握基础功的工程师来说，LLM 是力量倍增器；对新手来说，LLM 是“不可靠的危险精灵“。

为什么新手危险？因为 LLM 生成的代码“看起来对“但可能“完全错“——而你只有在亲自踩过坑、调试过各种诡异的边界条件之后，才有能力分辨这两种状态的差异。没有基础功的人用 LLM 写代码，就像一个不会画画的人用 Midjourney 生成了一幅插画——你可以发朋友圈展示“我也能画“，但你不能改任何一笔，因为你根本不懂构图、色彩和透视。

四、两种哲学的纠缠

把 Parra 和 Nadh 放在一起看，事情变得很有意思。

表面上，他们在说完全相反的话。Parra 说 talk 是 cheap 的，Nadh 说 code 是 cheap 的。有人会想：时代变了，旧信条过时了，新信条取代了旧信条。

但如果你看得更深一层，他们的“talk“和“code“指向的其实是不同的东西：

  • Parra 的 code 是行动的象征。他反对的 talk 是犹豫、恐惧、拖延——是那种让一个人三年没做出一个业余项目的内耗。他的 code 是 solution to paralysis。
  • Nadh 的 talk 是判断力的象征。他反对的 code 是被无差别批量生成的文本——是那种没有人类投入背书、缺少出处链条、不知道是精雕细琢还是随机排列的 slop。他的 talk 是 solution to mindlessness。

所以这两句话不是在同一根轴上做相反方向的位移，而是在不同层面上描述同一个东西的核心需求：把思想转化为可运行系统的人类能力。 这个能力从来不是“纯代码产出“或“纯口头表达“，而是二者之间的那道翻译桥梁。

LLM 做的事情，是在这个翻译链条的最末端——从设计到代码的那一段——放了一台高效机器。这台机器的存在，使得这个链条的瓶颈发生了位移：瓶颈从“写出代码“移到了“写出代码之前的一切“。

写出代码之前需要什么？ 需要理解业务到底是解决什么问题，需要判断这个功能的正确性标准是什么，需要想象这个代码放进现有系统之后会影响哪些上下游，需要预见到当请求量比现在大十倍的时候它会在哪里断掉，需要在三个技术方案之间做权衡——每个方案在不同维度（性能、可维护性、团队学习成本、运维复杂度）上有不同的代价曲线。

这些能力有一个共同的名字：判断力。而判断力，恰恰是 LLM 目前最不擅长、未来大概率也最难以替代的东西——因为它不是“知识“或“技能“，而是在不确定性下做取舍的经验积累。你不可能靠 API 调用别人的经验来获得你自己的经验。

这就是我为什么不认同“Parra 过时了、Nadh 取代了他“这种解读。更准确的描述是：

Linus → Parra → Nadh 这个演化链条，不是“旧哲学被新哲学推翻“，而是同一块硬币在不同时代条件下暴露了不同的面。

在开发门槛高到只有少数人能跨越的时代，硬币的正面是“别光说，写出来证明自己“（Linus）。在开发门槛正在坍塌的过渡期，硬币的反面开始显现：“当大家都写得出来时，写出来就不够了——你说的是什么、你判断该写什么，才是区分值”（Nadh）。

这才是递进论证的核心：不是代码变廉价就说明写代码的人变廉价了，而是“能写出对的代码“的门槛不降反升。 LLM 拉平的是“写出任何代码“的底线，但它没有拉平——在某些方面甚至拉高了——“写出对的代码“的上限。

五、中国工程现场

把上述分析搬到中国互联网行业，很多问题会呈现出更复杂的纹理。

5.1 历史债务：LLM 写过但没有

国内后端工程师的日常里，只有很小一部分时间花在 “从零开始写一个新功能” 上。更多的时间花在：

  • 理解一段三年前写的、没有注释的方法到底在做什么；
  • 排查为什么某个定时任务在特定条件下会产生重复数据；
  • 在不破坏八个下游消费者的前提下，修改一个公共 RPC 接口的返回值；
  • 上线前发现性能回归了 20%，逐行比对 diff 定位到罪魁祸首。

这些场景有一个共同特点：问题域和解决方案域是不对称的。 问题域是“这个系统为什么这么跑“，解决方案域才是“我需要写什么代码来改它“。LLM 擅长后者，对前者几乎帮不上忙——因为它需要参与的上下文不是“这一行代码“甚至不是“这个文件“，而是这个组织过去数年的技术决策、踩过的坑、走过的弯路，这些知识不在任何代码仓库里。

5.2 业务复杂度：你的系统不是 GitHub 上的开源项目

国内互联网业务往往具备几个 GitHub 上找不到对应物的复杂度：

  • 合规与监管需求：支付结算中的分账逻辑、用户数据的本地化存储策略、金融级的审计追踪——这些不是从 Stack Overflow 上搜到 pattern 就能套用的；
  • 大促驱动的架构变形：双 11 秒杀、直播带货瞬时峰值的应对策略——“正常日“和“峰值日“是两套完全不同的系统行为，LLM 无法在没有亲身运维过这些系统的前提下做出正确的取舍；
  • 组织边界内的互联互通：一个中型互联网公司可能有 200+ 个微服务，互相之间的调用链路像一张没有文档的蜘蛛网。LLM 可以帮你写一个新服务，但它不知道这个新服务应该接在哪里、用什么协议、超时设多少、熔断配多大——这些决策依赖的不是代码知识，而是组织内部的隐性基础设施知识。

5.3 35 岁焦虑 × LLM

一个在中国互联网行业特有的变量：35 岁焦虑和 LLM 时代的叠加。

对 35 岁+ 的工程师来说，LLM 的出现是一把双刃剑。一方面，如果“写代码快“是你和年轻人之间唯一的核心差异，那你确实应该焦虑——因为速度差距正在被 LLM 抹平。但另一方面，如果你积累的是**“怎么写才对“的判断力**——那种见过十个分布式事务方案都失败过之后，能在需求评审阶段就识别出“这个方案在超时重试场景下会丢数据“的直觉——那么 LLM 是在放大你的价值，而不是削减它。因为你通过 prompt 引导 LLM 产出的代码，质量远高于一个新手用同样的 LLM 产出。

所以对 35 岁+ 工程师来说，LLM 时代的核心问题是：你的经验能不能翻译成更好的 prompt、更准的判断、和更少的踩坑？如果能，你就是受益者。如果你的经验停留在“我能比年轻人更快地打出这个框架的配置文件“，那 LLM 确实不公平地偏袒了年轻人——因为它抹平了打字速度，但没有抹平判断力。

六、分层生存指南

基于以上分析，我尝试给不同经验阶段的工程师一个模糊的方向感。注：这不是教学指南，只是思考框架。

6.1 新人（0-3 年）：先关掉 AI，学完基础再用

这可能是最反直觉但最重要的一条建议。在你还不具备判断 LLM 输出质量的“基准线“时，LLM 不是在加速你的学习，而是在破坏它。

具体来说：

  • 先手动写完至少一个完整项目——从前端到数据库到部署，理解每一层是怎么串起来的。不要用 copilot，不要用 cursor，用你会的任何东西自己敲出来。可以是 Todo App，可以是个人博客，可以是一个记账工具。关键是全链路走一遍——自己手写 SQL、自己配 Nginx、自己 debug 一个 500 错误到凌晨三点。比你用 AI 快速产出十端的印象深10倍。
  • 学完基础后，把 LLM 当“高级搜索引擎“而非“代码代写“：问“为什么用 B+ 树索引而不是红黑树“，而不是“帮我写一个数据库索引“。
  • 阅读 LLM 生成的代码时，要求自己能解释每一行：为什么这里需要 nil 检查？为什么这个锁加在这里而不是外面？如果解释不了，就应该写一段注释——或者承认自己还没理解。

一句话概括这一阶段的核心原则：先建立自己的“认知锚点“，再用 LLM 加速。 没有锚点的人，在 LLM 的洪流里是永远漂浮的——看起来代码一直能跑，实际上什么都不会独立做。

6.2 中级（3-8 年）：把 LLM 当生产力杠杆，建立你自己在一个领域里的唯一判断力

这个阶段的工程师已经具备了基本的代码质量判断能力。LLM 对你来说是真正的生产力倍增器——前提是你知道放什么在 AI 流水线上，什么必须亲手做。

具体来说：

  • 让 LLM 做“实施“，你保留“设计“和“审查“：你可以把接口定义告诉它，让它生成实现代码和单元测试。你自己写接口定义——因为这个决定会影响未来三年的系统形态。代码实现可以改，一个坏的接口设计改起来会扩散到五个服务。
  • 建立“修 bug 分为三步“的习惯：第一步，自己分析根因，形成假设（30 分钟）；第二步，让 LLM 根据你的假设提出修复方案（5 分钟）；第三步，你自己评审和验证（60 分钟）。时间分配的重点偏移到了两端——分析和验证，而不是写代码本身。
  • 选定一个领域深耕到“LLM 不如你“的深度。今天 LLM 的弱项不是知识广度，是深度。一个花了两年时间做 Kafka 调优、踩过六个线上故障的工程师，对 Kafka 的理解仍然远深于任何 LLM。泛用型 AI 压缩不了“被真实故障逼出来的经验“。

6.3 资深/管理者（8 年+）：从写代码的人变成“放大写代码的人“的人

到了这个阶段，你的价值早就不仅限于你能写多少代码。LLM 时代，你的角色需要完成一个清晰的转化：

  • 从解决技术问题到定义技术问题：你的核心交付物不再是 pull request，而是设计文档、技术方案、架构图、和权衡分析——即 Nadh 定义的“talk“。确保团队在做对的事情，比把事情做对更重要。
  • 建立团队级的“判断力基础设施“：建设内部的 coding guidelines、设计 review 流程、post-mortem 文化，让团队的决策质量不依赖某个人的直觉。
  • 培养新人时的自觉：你可能有二十年经验，可能看过 LLM 的每一处坑。但团队里的新人没有。你需要有一套机制性的培养方式——不只是 code review 时指出 bug，还要解释“为什么那种写法会导致 bug“和“你是怎么在一个小时内就定位到这个 bug 的“——把你的判断力可复制地传递给新人。
  • 保持 Hands-on：即使你不再写每日的 feature 代码，也要保持“能读懂代码“的能力。因为你的技术决策质量建立在“能对 LLM 输出做最终判断“之上——你不需要会写，但必须能看懂，而且要看得比写的人更准。如果你连 LLM 输出的代码正确与否都无法判断，你的决策权就是空中楼阁。

结语：Code is abundant. Judgment is scarce.

回到开头那个场景：一个中国后端工程师的日常。他的价值不在于他能在 Cursor 里多快地 protype 一个管理后台——LLM 在这方面正在迅速逼近所有人。他的价值在于：他看到产品文档时，能立刻识别出那个看起来简单的需求在事务一致性上的坑；他在三个实现方案中，知道哪个会在三个月后产生可维护性地狱；他能在凌晨三点的故障中，凭经验和直觉在五分钟内锁定根因，而不是在十几个服务日志里漫无目的地 grep。

这些能力不会出现在任何 GitHub 的 contribution graph 上，也不是“show me the code“能够验证的。但它们构成了一个软件工程师之所以是工程师——而不是一个“写代码的“——的不可替代部分。

不是代码变便宜了，就说明写代码的人变便宜了。是代码变得更充裕了，所以判断力变得更稀缺了。 在一个 code is abundant 的世界里，稀缺品不是能写代码的人，而是能写出对的代码的人——以及那个更难回答的问题：在 LLM 能给出一百种写法的时候，你到底应该写什么？

这个问题的答案，不在任何 API 的另一端。它在你过去几年积累的认知地图里。
