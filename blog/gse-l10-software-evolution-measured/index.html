架构要经得起时间：把「软件的演化」写成可测量的轨迹

#软件工程#架构设计#课程笔记#生成式 AI

架构要经得起时间，而不是提前猜中一切——这是 GSE 第 10 讲最该被带走的一句话，也是最难被验证的一句话。这篇把它变成三个能跑的模型。

这篇不复述讲义。它做三件事：用自己的话复述这一讲的骨架（讲义讲了三件事：结构怎样演化、演化怎样被学习、人在演化中的位置），然后给每件事配一个可执行的判据——架构决策的可逆性代价曲线、提交历史里的原子性指标、taste-bench 的成对比较与胜负反转。

口径说明

  • 讲义原文：GSE 2026 · 第 10 讲：软件的演化（南京大学《生成式软件工程》2026 秋季学期公开讲义）。本文只复述骨架与要点、引用以链接指回原文，未大段搬运讲义段落。
  • vault 精读笔记：02-课程体系/jyywiki/生成式软件工程-GSE/2026-逐讲/L10-软件的演化.md。
  • 讲义开篇用一条「模型给出否定指数时间假说结果」的研究新闻起手，把「工具失效」的焦虑从软件推到人；本文不复述这条新闻，也不核实它——它在这里的作用只是说明讲义的起手式。
  • 三个脚本均为自写增量，只依赖 Python 标准库；文中输出为实跑结果，逐行可复现。

一、本讲的纲领：三个问题

讲义开篇抛出两个问题：今天看到的架构、规则和测试，是怎样一步一步形成的？当 AI 能完成越来越多的修改，人又应该怎样决定软件往哪里走？

这两个问题被拆成三段：

  1. 结构怎样演化——航母不是一天长成的；架构要经得起时间，而不是提前猜中一切。
  2. 演化怎样被学习——从 dsh 的提交历史里读工程实践；理解一个版本，也要理解版本之间的迁移。
  3. 人在演化中的位置——AI 能做越来越多修改时，人负责把「不好」挡在项目之外；而讲义诚实地承认，排除了坏答案，还没有学会什么是好，并用「蒸馏我自己」这个失败实验收尾。

这三段都是叙述性的判断。而叙述性判断的弱点是：它无法被证伪，也就无法被执行。下面三节各把其中一段换成可测的东西。

二、航母不是一天长成的

讲义把 dsh 比作航母：平台已经开始搭建，飞机还在试验，围绕它的完整协作方式也在探索——并且明确说，最终成功的平台未必就是今天的 dsh。这个比方里最锋利的不是「航母很大」，而是两个细节：

  • 升降机的接口问题：装上升降机之后，它降到底的位置与原有甲板之间仍可能有高度差，还需要滑道与人员配合才能完成转运。「有这个部件」与「整个流程能工作」之间，总会冒出新的接口问题。
  • Midway 级别的协同：到这样的规模，飞行甲板、机库、动力、防护和保障空间已经需要在整舰设计中共同安排，而不是各管一段再拼接。

讲义强调这比较的是能力与组织方式的变化，而不是船型谱系。这两句都可以直接搬到软件上：模块都到位了（接口、构建、部署都有），但流程仍然跑不通；等到要动的时候才发现部件之间的接口是后来才长出来的。

但「航母」这个比喻本身推不出任何工程决策。要用它，得先把「经得起时间」变成一个能算的量。

三、增量一：把「经得起时间」算成代价曲线

「架构要经得起时间，而不是提前猜中一切」这句话隐含一个前提：有些决策该早定，有些不该。讲义没有给出分界线，于是常见的做法是用「重要程度」当代理——重要的早定，不重要的晚定。这个代理是错的。

一个决策被推翻时的代价，取决于决策周围会长出多少新代码：代码是围着决策长的，决策的触达面会随时间膨胀；而迁移成本还额外跟着数据量涨。所以代价随时间近似线性增长，而增长斜率由耦合程度决定，与这个决策「重不重要」无关。

"""架构决策的可逆性代价：把「经得起时间，而不是提前猜中一切」算成一条曲线。

模型：推翻一个决策的代价 ≈ 触达文件数 × (决策周围长出的新代码) + 迁移成本。
系数是设出来的，可迁移的是「形状」：代价随时间近似线性增长，增长率由耦合决定。

只依赖标准库；输出确定性。
"""

# (决策名, 初始触达文件数, 周围代码年增长率, 数据迁移成本基数)
DECISIONS = [
    ("命名与目录结构", 3, 0.05, 0),
    ("模块边界划分", 20, 1.50, 0),
    ("存储引擎与对外协议", 60, 12.00, 40),
]
DAYS = (1, 30, 365)

def cost(touch, growth, migration, day):
    touched = touch * (1.0 + growth * (day / 365.0))
    data = migration * (1.0 + day / 365.0) ** 2
    return touched + data

def verdict(multiple):
    if multiple < 2.0:
        return "可逆：晚做也不迟，先做反而锁定心智"
    if multiple < 6.0:
        return "中等：尽早定，改起来会明显变贵"
    return "不可逆：先想清楚再动，改不动"

print("相对代价（以第 1 天为 1.00 归一）")
print("%-22s %s  %s" % ("决策类型", "  ".join("day %-3d" % d for d in DAYS), "365 天倍数"))
for name, touch, growth, migration in DECISIONS:
    base = cost(touch, growth, migration, 1)
    vals = [cost(touch, growth, migration, d) / base for d in DAYS]
    print("%-22s %s  %5.1fx  -> %s"
          % (name, "  ".join("%5.2f" % v for v in vals), vals[-1], verdict(vals[-1])))
print()
print("规律：代价随时间近似线性增长，增长率由「决策周围会长出多少新代码」决定，")
print("      而不是由决策本身有多重要决定。所以「重要就早定」是错的判据；")
print("      正确问法是「推翻它时，代价会放大多少倍」。")
print()
name, touch, growth, migration = DECISIONS[2]
early = cost(touch, growth, migration, 30) / cost(touch, growth, migration, 1)
late = cost(touch, growth, migration, 365) / cost(touch, growth, migration, 1)
print("反例检验：把不可逆决策也当可逆决策（拖到很晚再定）")
print("  存储引擎决策：第 30 天定 -> 之后推翻代价 %.1fx；第 365 天定 -> %.1fx；晚定的额外代价 %.1fx"
      % (early, late, late / early))

输出：

相对代价（以第 1 天为 1.00 归一）
决策类型                   day 1    day 30   day 365  365 天倍数
命名与目录结构                 1.00   1.00   1.05    1.0x  -> 可逆：晚做也不迟，先做反而锁定心智
模块边界划分                  1.00   1.12   2.49    2.5x  -> 中等：尽早定，改起来会明显变贵
存储引擎与对外协议               1.00   1.62   9.20    9.2x  -> 不可逆：先想清楚再动，改不动

规律：代价随时间近似线性增长，增长率由「决策周围会长出多少新代码」决定，
      而不是由决策本身有多重要决定。所以「重要就早定」是错的判据；
      正确问法是「推翻它时，代价会放大多少倍」。

反例检验：把不可逆决策也当可逆决策（拖到很晚再定）
  存储引擎决策：第 30 天定 -> 之后推翻代价 1.6x；第 365 天定 -> 9.2x；晚定的额外代价 5.7x

三处值得停一下：

第一，三个决策落在了三个不同的档位。 命名与目录结构 365 天只有 1.0 倍——推翻它几乎不要钱，所以它根本不需要提前定，甚至早定反而锁死了心智；模块边界 2.5 倍，属于“尽早定“；存储引擎与对外协议 9.2 倍，属于“先想清楚再动“。用「重要程度」排序会得出同样的结论，但那是巧合：一旦某次重构让命名决策的触达面从 3 个文件涨到 30 个，它的档位就会跳档。

第二，“晚定“的额外代价是可数的。 存储引擎决策在第 30 天定，之后推翻是 1.6 倍；拖到第 365 天再定，是 9.2 倍——晚定的额外代价 5.7 倍。这给「重要就早定」一个更准确的替身：不是按重要性早定，是按代价放大倍率早定。

第三，模型给不出精确数字，但能给出形状。 系数（增长率 0.05 / 1.5 / 12）是设出来的，换一组数字三档的位置会变，但「代价随时间近似线性、超线性部分来自数据迁移」这个形状是可迁移的结论。真正的用法是：对任何一个候选决策，先估它的触达面会怎么长，再问「推翻时放大多少倍」。

四、增量二：把「原子提交」变成可测指标

讲义说「从 dsh 的提交历史里学习工程」，并给出两条实践：原子提交让一个逻辑变化能够单独理解和检查；一个 PR 对应一个 worktree，让不同任务各自修改、安装和测试；有依赖的工作可以组织成堆叠 PR。

讲义还讲了这个做法的边界，而且举了一个非常具体的坑：dsh 曾遇到在一个 worktree 安装 Git 钩子管理工具 Lefthook，却影响了其他 worktree 的 hooks。讲义的结论是一句话——「目录分开了，不代表所有底层状态都分开了。工程规则也要通过实际故障检验。」

这句话可以直接变成检查项：hooks、依赖缓存、构建产物、数据库连接池、环境变量文件——哪些是 per-worktree 的，哪些是全局的？隔离的边界画在哪里，通常要靠一次真实故障才知道。

至于「原子提交」，它是可测的。写一个分析器：统计每个提交触碰了几个文件、改了多少行、消息前缀是什么类型，然后看分布：

"""从提交历史里学工程：把「原子提交」「工作怎样划分」变成可测的指标。

用法:
    python3 l10_b_history.py            # 造一个确定性的演示仓库并分析
    python3 l10_b_history.py <仓库路径>  # 分析真实仓库

只依赖标准库；演示模式输出完全确定。
"""
import os, subprocess, sys, tempfile, shutil

def run(args, cwd, env=None):
    return subprocess.run(args, cwd=cwd, capture_output=True, text=True, env=env).stdout

def build_demo_repo(path):
    """一个有组织有故意的演示仓库：混合原子提交、大提交、破坏性变更与纯文档提交。"""
    env = dict(os.environ)
    env.update({"GIT_AUTHOR_NAME": "demo", "GIT_AUTHOR_EMAIL": "demo@example.com",
                "GIT_COMMITTER_NAME": "demo", "GIT_COMMITTER_EMAIL": "demo@example.com"})
    run(["git", "init", "-q", "-b", "main"], path, env)
    def commit(msg, files, day):
        for name, content in files.items():
            full = os.path.join(path, name)
            os.makedirs(os.path.dirname(full), exist_ok=True)
            with open(full, "w") as f:
                f.write(content)
        stamp = "2026-01-%02dT12:00:00" % day
        env["GIT_AUTHOR_DATE"] = stamp
        env["GIT_COMMITTER_DATE"] = stamp
        run(["git", "add", "-A"], path, env)
        run(["git", "commit", "-q", "-m", msg], path, env)
    commit("init: 骨架", {"README.md": "# demo\n"}, 1)
    commit("feat: 加上重试逻辑", {"src/client.py": "def call():\n    return 1\n"}, 2)
    commit("fix: 修空指针", {"src/client.py": "def call():\n    return 2\n"}, 3)
    commit("feat: 加上日志", {"src/log.py": "log = 1\n"}, 4)
    commit("feat: 加上指标", {"src/metrics.py": "m = 1\n"}, 5)
    commit("docs: 写 README 段落", {"README.md": "# demo\n\n用法。\n"}, 6)
    commit("fix: 修空指针", {"src/client.py": "def call():\n    return 3\n"}, 7)
    commit("refactor: 重命名内部函数", {"src/client.py": "def call():\n    return 4\n",
                                        "src/internal.py": "x = 1\n"}, 8)
    commit("feat: 一次加完整个搜索功能",
           {"src/search.py": "\n".join("line %d" % i for i in range(60)),
            "src/search_test.py": "\n".join("t %d" % i for i in range(40)),
            "src/index.py": "idx = 1\n",
            "src/parser.py": "p = 1\n"}, 9)
    commit("feat!: 改掉对外字段名", {"src/client.py": "def call():\n    return 5\n"}, 10)
    commit("chore: 升级依赖", {"requirements.txt": "requests==2.0\n"}, 11)
    return path

def analyze(path):
    raw = run(["git", "log", "--numstat", "--date=short", "--pretty=format:%H%x01%s%x01%ad%x01"], path)
    commits = []
    cur = None
    for line in raw.splitlines():
        if "\x01" in line:
            sha, subject, date = line.split("\x01")[0:3]
            cur = dict(sha=sha[:7], subject=subject, date=date, files=0, churn=0)
            commits.append(cur)
        elif cur is not None and line.strip():
            cols = line.split("\t")
            if len(cols) >= 3:
                cur["files"] += 1
                if cols[0].isdigit():
                    cur["churn"] += int(cols[0])
                if cols[1].isdigit():
                    cur["churn"] += int(cols[1])
    return commits

def summarize(commits):
    n = len(commits)
    if n == 0:
        print("没有提交")
        return
    atomic = [c for c in commits if c["files"] <= 2 and c["churn"] <= 20]
    docs = [c for c in commits if c["subject"].lower().startswith(("docs", "chore"))]
    breaking = [c for c in commits if "!" in c["subject"] or "breaking" in c["subject"].lower()]
    mixed = [c for c in commits if c["files"] >= 3]
    biggest = max(commits, key=lambda c: c["churn"])
    churns = sorted(c["churn"] for c in commits)
    print("提交总数                        : %d" % n)
    print("单提交改动行数中位数             : %d" % churns[len(churns) // 2])
    print("最大单提交                      : %s  %s (%d 文件 / %d 行)"
          % (biggest["sha"], biggest["subject"][:26], biggest["files"], biggest["churn"]))
    print("原子提交占比(<=2 文件且 <=20 行) : %d/%d = %.0f%%" % (len(atomic), n, 100.0 * len(atomic) / n))
    print("跨 3 个及以上文件的提交          : %d/%d = %.0f%%" % (len(mixed), n, 100.0 * len(mixed) / n))
    print("纯文档/杂务提交                  : %d/%d = %.0f%%" % (len(docs), n, 100.0 * len(docs) / n))
    print("破坏性变更提交(带 !)             : %d" % len(breaking))

if len(sys.argv) > 1:
    print("真实仓库：", os.path.abspath(sys.argv[1]))
    print()
    summarize(analyze(sys.argv[1]))
else:
    tmp = tempfile.mkdtemp(prefix="hist-demo-")
    try:
        build_demo_repo(tmp)
        print("演示仓库（临时目录，路径不打印以保证输出确定）")
        print()
        summarize(analyze(tmp))
    finally:
        shutil.rmtree(tmp, ignore_errors=True)

输出（演示仓库，故意混合了原子提交、一个大提交、一次破坏性变更和纯文档提交）：

演示仓库（临时目录，路径不打印以保证输出确定）

提交总数                        : 11
单提交改动行数中位数             : 2
最大单提交                      : 2bfe1a3  feat: 一次加完整个搜索功能 (4 文件 / 102 行)
原子提交占比(<=2 文件且 <=20 行) : 10/11 = 91%
跨 3 个及以上文件的提交          : 1/11 = 9%
纯文档/杂务提交                  : 2/11 = 18%
破坏性变更提交(带 !)             : 1

这份输出把「原子」变成了三个可看的数：单提交改动行数的中位数（演示仓库是 2 行）、跨 3 个以上文件的提交占比（9%，就是那个一次性加完搜索功能的大提交）、破坏性变更是否被单独标记（消息里带 ! 的有 1 个）。

同一个分析器可以直接跑在真实仓库上。本文的博客仓库（roc-blog，2026-11-26 实跑）：

真实仓库： /Users/shichaopeng/Work/self-dir/roc-blog

提交总数                        : 438
单提交改动行数中位数             : 104
最大单提交                      : 5f25027  fix: resolve merge conflic (753 文件 / 28073 行)
原子提交占比(<=2 文件且 <=20 行) : 119/438 = 27%
跨 3 个及以上文件的提交          : 168/438 = 38%
纯文档/杂务提交                  : 86/438 = 20%
破坏性变更提交(带 !)             : 0

真实仓库有两个数字值得单独说。最大的那个提交是一次解决合并冲突——753 个文件、28073 行：这种提交在演化上几乎没有信息量，却会主导所有「改动规模」的分位数，用中位数看才不至于被它带偏。而带破坏性变更标记的提交是 0 个，说明这套约定在这个仓库里根本没有留下痕迹——正是上一段那句话的实证：规则要能在历史里被找到痕迹，否则它只是口号。

另一个提醒：本文仓库的提交天然是大块（整篇文章就是一个文件），所以原子提交占比只有 27%。这个指标必须按仓库类型解读，不能跨仓库横向比——给讲义、给文章仓库、给应用代码仓库，用的是三把不同的尺子。

看真实历史和演示仓库的差别，比看讲义那句话更有用——这也是讲义那句「工程规则也要通过实际故障检验」在数据上的对应物：规则要能在历史里被找到痕迹，否则它只是口号。

至于「一个 PR 对应一个 worktree」，在提交历史里只能看到间接痕迹（分支寿命、短期分支的数量、同一时间并行的分支数）。这不是缺陷，是提醒：有些实践只能从过程数据看，不能从最终历史反推。

五、增量三：taste-bench 的最小可行形态

讲义说：也许需要一个 taste-bench，评价做软件的品味。两份实现都能通过测试，哪份更贴合问题、更容易理解、给下一次修改留下的负担更少？

讲义接着说得很克制：这不容易压成一个 Yes/No 或总分。可以先在同一需求下做多维度的相对比较，再加入后续需求，看看原来的优劣是否反转。讲义最后给出全讲的落点：软件的「好」，本来就包含它将来怎样继续变化。

这段可以照着写成一个最小可用的比较器：

"""taste-bench 的最小可行形态：成对相对比较，并检查加入后续需求后优劣是否反转。

只依赖标准库；输出确定性。
"""

DIMS = ["贴合问题", "可读性", "下次修改负担", "扩展性"]

# 同一需求的两份实现，在两个场景下的分维度打分
SCENARIOS = {
    "场景一：只做当前需求": {
        "A 直白重复":   {"贴合问题": 5, "可读性": 5, "下次修改负担": 4, "扩展性": 2},
        "B 抽象统一":   {"贴合问题": 3, "可读性": 3, "下次修改负担": 3, "扩展性": 5},
    },
    "场景二：加入后续需求（第三种分支）": {
        "A 直白重复":   {"贴合问题": 2, "可读性": 3, "下次修改负担": 1, "扩展性": 2},
        "B 抽象统一":   {"贴合问题": 4, "可读性": 3, "下次修改负担": 4, "扩展性": 5},
    },
}

A, B = "A 直白重复", "B 抽象统一"

def compare(scene):
    sa, sb = SCENARIOS[scene][A], SCENARIOS[scene][B]
    wins = {A: 0, B: 0}
    flips = []
    for d in DIMS:
        if sa[d] > sb[d]:
            wins[A] += 1
            flips.append((d, A))
        elif sb[d] > sa[d]:
            wins[B] += 1
            flips.append((d, B))
        else:
            flips.append((d, "平"))
    return wins, flips

for scene in SCENARIOS:
    wins, flips = compare(scene)
    print(scene)
    for d, who in flips:
        print("  %-8s : %s" % (d, who))
    print("  => 成对比较：%s %d : %d %s" % (A, wins[A], wins[B], B))
    print()

w1, f1 = compare("场景一：只做当前需求")
w2, f2 = compare("场景二：加入后续需求（第三种分支）")
d1 = dict((d, who) for d, who in f1)
d2 = dict((d, who) for d, who in f2)
flipped = [d for d in DIMS if d1[d] != d2[d] and "平" not in (d1[d], d2[d])]
print("胜负翻转的维度：%s" % ("、".join(flipped) if flipped else "无"))
def side(wins):
    if wins[A] > wins[B]:
        return "%s 胜" % A
    if wins[B] > wins[A]:
        return "%s 胜" % B
    return "平局"
s1, s2 = side(w1), side(w2)
if s1 != "平局" and s2 != "平局" and s1 != s2:
    verdict = "总胜负发生反转"
elif s1 == "平局":
    verdict = "从平局变成一边倒"
else:
    verdict = "总胜负未反转"
print("  场景一 %s（%d:%d），场景二 %s（%d:%d）—— %s"
      % (s1, w1[A], w1[B], s2, w2[A], w2[B], verdict))
print()
print("可执行判据（三条）：")
print("  1. 不要先压成一个总分或 Yes/No；先在同一需求下做多维度的成对比较。")
print("  2. 把「后续需求」当成第二个场景重跑一次，并显式看哪一维翻转了。")
print("  3. 若两个场景才分出胜负（平局变一边倒、或胜负反转），说明当前选择其实是不可逆决策，别急着定。")

输出：

场景一：只做当前需求
  贴合问题     : A 直白重复
  可读性      : A 直白重复
  下次修改负担   : A 直白重复
  扩展性      : B 抽象统一
  => 成对比较：A 直白重复 3 : 1 B 抽象统一

场景二：加入后续需求（第三种分支）
  贴合问题     : B 抽象统一
  可读性      : 平
  下次修改负担   : B 抽象统一
  扩展性      : B 抽象统一
  => 成对比较：A 直白重复 0 : 3 B 抽象统一

胜负翻转的维度：贴合问题、下次修改负担
  场景一 A 直白重复 胜（3:1），场景二 B 抽象统一 胜（0:3）—— 总胜负发生反转

可执行判据（三条）：
  1. 不要先压成一个总分或 Yes/No；先在同一需求下做多维度的成对比较。
  2. 把「后续需求」当成第二个场景重跑一次，并显式看哪一维翻转了。
  3. 若两个场景才分出胜负（平局变一边倒、或胜负反转），说明当前选择其实是不可逆决策，别急着定。

这个玩具例子把讲义的三句话都落到了可执行的形式上：

  • 不给总分。四个维度各自的胜负被分开保留，而不是压成一个数字——压成数字会丢掉「在哪个维度赢」，而那正是决策信息。
  • 加入后续需求后重跑。场景一（只做当前需求）A 直白实现 3:1 胜；场景二（加入第三种分支）B 抽象实现 0:3 胜，总胜负反转，翻转发生在「贴合问题」和「下次修改负担」两维。注意 A 在场景一之所以「负担低」，是因为当前需求下它根本没那么多地方要改；一旦分支变多，复制粘贴的负担才显形。任何只测当前需求的评分，都会系统性地高估“看起来简单“的实现。
  • 什么时候才该下结论。若两个场景才分出胜负（平局变一边倒、或胜负反转），说明这个选择其实是不可逆决策，别急着定——这正好接回第三节的代价曲线：不可逆决策要慢，代价曲线告诉你多慢。

六、把「不好」挡在项目之外：规则本身也在演化

讲义讲人怎么留在演化里：当 AI 能完成越来越多的修改时，人负责把「不好」挡在项目之外。讲义还给出了经验怎样进入下一轮工作的链路：

  • 一次事故可以留下复盘、修复提交和回归测试；
  • 被采纳的评审意见可以整理为候选规则，再由维护者审阅并更新 Skill；
  • 下一位开发者或 Agent 不必完全依赖记忆；
  • 但规则也会积累负担，所以 Agent Notes 要归档、重复要求要清理、检查要考虑运行时间；
  • 结论：流程本身也是软件演化的一部分。

最后两条最容易被略过，而它们恰好是这一讲的自我一致性证明：规则集也是一份软件，所以它同样要面对可逆性、负担与退化问题。「候选规则 → 维护者审阅 → 更新 Skill」是一条带人工闸门的演化路径，「重复要求要清理」是它的重构，「检查要考虑运行时间」是它的性能预算。

这给出一条能落地的判据：任何写进 Skill 或 Agent Notes 的规则，都应该带一个可检查的退场条件——比如「当 X 出现三次以上就合并」「当检查超过 N 秒就降级为抽查」。没有退场条件的规则集，只会单调增长。

八、这三个模型判不了什么

  • 代价模型的系数是设出来的。它给出形状与档位顺序，不给出你项目里的真实倍率；真实数字要靠你自己估触达面的增长速度。
  • 提交历史指标只描述已发生的演化。它能告诉你历史是否原子、是否标记了破坏性变更，但看不出被放弃的分支、被打回的 PR、没写进提交的临时决策——过程数据在最终历史里是丢失的。
  • taste 的两个实现是玩具。真实实现的多维打分需要人（或 Agent）判断，脚本只能承载打分结果，不能替代打分；而且四个维度本身也可能有偏（比如「可读性」对熟人和生人不是一回事）。
  • 三个模型都不涉及 AI 参与度。讲义把「AI 能做越来越多修改」作为前提，但本文所有模型都是关于软件本身的演化，不涉及人机分工的度量。

FAQ（九、常见问题）

什么样的架构决策该早定？ 用代价放大倍率判断：推翻时成本放大 6 倍以上（存储、协议、数据模型一类）先想清楚再动；2~6 倍（模块边界一类）尽早定；低于 2 倍（命名、目录结构一类）不用提前定，早定只会锁定心智。

「不要提前猜中一切」是不是等于「别做设计」？ 不是。它反对的是按重要性排序的提前定，支持的是按代价倍率排序的提前定。不可逆决策照样要早想清楚，可逆决策照样可以晚做。

怎么判断一个提交是不是原子的？ 用可测的代理指标：单提交触碰的文件数、改动行数、是否同时改了实现与测试、消息前缀是否表明它是一个完整逻辑变化。演示仓库里「原子提交」表现为 10/11 的提交落在 2 文件 20 行以内，那个一次改 4 个文件 102 行的大提交就是反例。

taste-bench 到底怎么做？ 三步：同一需求下两份实现 → 分维度成对比较（不给总分）→ 加入后续需求重跑，看总胜负是否反转、哪一维翻转。两场景才分出胜负时，别急着定，那说明这是不可逆决策。

讲义里的「目录分开了，不代表所有底层状态都分开了」怎么落地？ 列出工作区隔离清单：hooks、依赖缓存、构建产物、凭据文件、端口。每项标注 per-worktree 还是全局；全局的那些要么挪进工作区，要么明确承认它们是共享的并在文档里写清影响。
