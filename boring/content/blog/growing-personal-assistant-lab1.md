GSE 2026 的第一个实验叫「会成长的个人助手」，要求做出一个持续为你工作、并且能在被你纠正之后下次做对的个人助手。原文（[实验一原文](https://jyywiki.cn/GSE/2026/lab1.md)，2026-11-24 抓取）列了五项能力约束：个人数据库、持续关联邮箱、办理 ehall 事务、手机端联动、能力组合，另加一条元要求——把成功流程和你的纠正保存成可读的脚本、技能或记忆，用 Git 管起来。

我读的时候第一反应是「五个功能需求」，读第二遍才反应过来：**这五条里每一条都藏着一条机制，缺了机制，功能只是能演示的东西。** 已发的[课程地图](/blog/generative-software-engineering-course-map/)里 Lab1 只占一行表格加一段元要求说明，正好留出这块缺口。

## 一、约束表背后的机制表

| 原文约束 | 隐含机制 | 机制坏掉时的症状 |
|---|---|---|
| 个人数据库：能索引检索、能定位到原文 | 记忆可检查 + 回答带出处 | 只给结论、给不出是哪份资料的哪一段 → 无法验证，等于黑盒 |
| 邮箱：持续获取、关联历史、拟草稿、你确认后发 | 草稿-确认-发送 + 幂等去重 | Agent 直发不可逆；重复轮询重复发送 |
| ehall：查 + 至少一种事务，提交前展示、明确确认 | 动作按可逆性分级 + 人工确认闸门 | 把「退课」也当成普通提交 → 不可逆损害 |
| 手机端：发起、看进度、改草稿、确认 | 控制平面外置，不绑定某台机器的某个 session | 一离开电脑就失联，任务断在半路 |
| 能力组合：共享上下文，至少一条反复用的流程 | 唯一可写归档 + 可重复执行的编排 | 各工具各记一份状态，跨工具对不上账 |
| 元要求：纠正落盘、Git 管理、跨会话生效 | 成长 = 状态被记住 + 纠正被加载 + 失败可诊断 + 动作可回滚 | 每次都要重新教一遍；纠错变成二次事故 |

注意最后两行的关系：**「会成长」不是第六个功能，而是前五项都做对之后才可能出现的性质。**

## 二、逐条拆：每条约束要落到哪个工程动作

### 2.1 个人数据库：硬指标是「能指回原文」

原文推荐 Markdown + 目录结构，给的理由是「你可以直接阅读、修改文件，也更容易观察 Agent 读了什么、写了什么」。这个理由比「Markdown 好用」重要得多：**记忆如果是人可读可改的纯文本，它才能进 git，才能 diff，才能被审计。** 塞进向量库的记忆，你没法回答「它为什么这么说」——而这恰恰是第一个约束想要的答案。

「能定位到原文」应该落成硬指标而不是口号：每次回答必须附（文件, 行号或段落标题）引用，给不出引用的结论视为未回答。召回上，混合检索（关键词/BM25 + 向量）比纯向量更合适——你要找的往往是一段具体的表述（报名时间、截止日期），而不是一个语义邻居。返回给模型的是**带行号的段落**，这样引用是顺手的事，不用事后编。

### 2.2 邮箱：两个机制，一个是发送闸门，一个是幂等

「发送的应当是你确认的最终版本」是一条单向阀：Agent 可以起草，不能拍板。而「重复检查邮箱不应重复处理或发送同一封邮件」是幂等要求，工程上就是维护一个「已处理集」。

键怎么选是个坑：只用 `Message-ID` 不够——邮件被转发或抄送时会带同一个 `Message-ID`，去重就会误伤；只用 IMAP `UID` 也不够——UID 只在同一个邮箱文件夹内单调，换文件夹或账号重建就不可比。稳妥做法是 `(Message-ID, UID)` 组合键，再加发件人与日期兜底。

还有一个更要紧的点：**幂等标记的写入必须和副作用同事务**。如果你先发信再标记已处理，中间崩溃一次，这封信会再发一遍；反过来先标记再发，崩溃一次这封信就永远发不出去了。真实实现里这两件事要么放进同一个可恢复流程，要么用「发信前写 pending 意图、发信后写完成」的二阶段状态。

### 2.3 ehall：把动作按可逆性分级

原文的态度非常明确：提交前要展示关键字段与后果、由你确认，退课与撤销申请「尤其不能自行决定」。翻译成工程语言就是**按可逆性给动作分级**：

- 查询、检索、填表草拟 → 自动执行；
- 提交（会改变记录）→ 展示 diff 后等你一句确认；
- 退课、撤销这类不可逆或影响重大的 → 二次确认，且要求显式输入目标（如课程号）而不是点一下。

提交前给人看的应该是**将要填进去的字段和后果**，而不是一个「确定吗」。让人核对 diff 的人，做出的确认才是有内容的确认。

### 2.4 手机端：控制平面不能绑在某台机器的某个窗口上

原文那句「任务不能依赖桌面端某个始终开着的对话窗口」，点破的是 Agent 系统里一个常见隐含假设：状态活在那个会话里。会话一关，任务就断。

所以手机端这一条的真实要求是**任务生命周期与设备解耦**：任务状态存在服务端或共享文件里，任何设备上的任何 agent 都能接管；发起、查进度、改草稿、确认这四件事都要能在手机上完成。用 Telegram bot 推送草稿加回调按钮、用移动端网页、或者 iOS 快捷指令，都只是表面，底下那套「状态不在会话里」才是关键。

### 2.5 能力组合：一条唯一可写的归档

「共享必要的上下文」落地后的形态是：各工具读写**同一个**可写位置（你的个人数据库），而不是各自维护一份记忆。工具之间要交换的东西都从这里过。这样做的好处是能对账——一次办事流程结束后，结果归档到哪、哪一步的状态是什么，都能查。

## 三、可运行的最小实现：幂等 + 规则落盘

上面两条最容易做错、又最能体现「成长」的机制，我写了个自写示例跑通（代码为自写演示，与课程无关）：邮箱去重用一个内存 SQLite 记已处理集，规则落盘用 `rules/*.md` 承载，跨会话靠「下次加载同一个目录」实现。

```python
import sqlite3
import tempfile
from pathlib import Path

# ---------- 1. 幂等：已处理集靠 Message-ID + UID 双键 ----------
STATE = sqlite3.connect(":memory:")
STATE.execute("""create table if not exists handled(
    msg_id text primary key, uid integer, subject text, reply_draft text)""")

def process_mailbox(mailbox):
    acted = []
    for m in mailbox:
        row = STATE.execute(
            "select msg_id from handled where msg_id=?", (m["message_id"],)).fetchone()
        if row:
            acted.append((m["subject"], "SKIP 已处理过"))
            continue
        # 只有首次见到才拟草稿并落「已处理」标记
        draft = "您好，关于「%s」，我已备齐材料，正文见附件。" % m["subject"]
        STATE.execute("insert into handled values(?,?,?,?)",
                      (m["message_id"], m["uid"], m["subject"], draft))
        acted.append((m["subject"], "DRAFT 已拟稿"))
    return acted

# ---------- 2. 成长：纠正写成规则文件，下次运行加载并命中 ----------
# 真实实现里这个目录在 vault 里（跟着 git 走，跨会话不变）；
# 示例用临时目录，避免验证时在仓库里留垃圾，且输出保持确定性。
RULES_DIR = Path(tempfile.mkdtemp(prefix="growth_rules_"))

def load_rules():
    rules = []
    for f in sorted(RULES_DIR.glob("*.md")):
        for line in f.read_text(encoding="utf-8").splitlines():
            if line.startswith("- "):
                rules.append((f.name, line[2:].strip()))
    return rules

def classify_notice(notice, rules):
    """规则命中就改写判断；命中不了就按原样返回。"""
    hits = []
    for src, rule in rules:
        # 规则形如：deadline != start_time
        if "!=" in rule:
            wrong, right = [x.strip() for x in rule.split("!=", 1)]
            if wrong and right and wrong in notice:
                hits.append((src, rule))
                notice = notice.replace(wrong, right)
    return notice, hits

if __name__ == "__main__":
    RULES_DIR.mkdir(exist_ok=True)
    # 第一次运行：纠正还没落盘
    mailbox = [
        {"message_id": "<m1@ehall>", "uid": 101,
         "subject": "报名通知", "body": "报名截止时间 2026-12-01"},
    ]
    print("== 第 1 次检查邮箱 ==")
    for subject, action in process_mailbox(mailbox):
        print("  %-10s %s" % (action, subject))
    print("== 第 2 次检查同一封 ==")
    for subject, action in process_mailbox(mailbox):
        print("  %-10s %s" % (action, subject))

    notice = "报名截止时间 2026-12-01"
    fixed, hits = classify_notice(notice, load_rules())
    print("== 规则命中（纠正未落盘时）==")
    print("  改写后:", fixed, "| 命中:", hits)

    # 人纠正一次：规则落盘
    (RULES_DIR / "notifications.md").write_text(
        "# 通知类规则\n- 报名截止时间 != 活动开始时间\n", encoding="utf-8")
    fixed2, hits2 = classify_notice(notice, load_rules())
    print("== 规则命中（纠正落盘后，新会话加载同一份规则）==")
    print("  改写后:", fixed2, "| 命中:", hits2)
    print("  规则条数:", len(load_rules()))
```

```text
== 第 1 次检查邮箱 ==
  DRAFT 已拟稿  报名通知
== 第 2 次检查同一封 ==
  SKIP 已处理过  报名通知
== 规则命中（纠正未落盘时）==
  改写后: 报名截止时间 2026-12-01 | 命中: []
== 规则命中（纠正落盘后，新会话加载同一份规则）==
  改写后: 活动开始时间 2026-12-01 | 命中: [('notifications.md', '报名截止时间 != 活动开始时间')]
  规则条数: 1
```

输出里有三处值得停下来看：

第一，**第二遍检查是 SKIP 而不是「又拟了一次稿」**。这不是优化，是正确性——在没有幂等的状态上叠加「会成长」，长出来的是重复劳动，不是能力。

第二，**规则命中从空变非空，发生在「人纠正一次」之后，而不是「模型想通了」之后**。这就是原文元要求那句话的工程含义：纠正要落在下次会被加载的地方。没落盘的纠正等于没纠正。

第三，示例里规则写成了 `报名截止时间 != 活动开始时间` 这种可执行形式，而原文里人说的是「不要把报名截止时间当成活动开始时间」。**从人话到可执行规则的翻译，是每次纠正都要付的工**——这才是「成长」的代价，也是为什么原文要求规则以可读脚本/技能/记忆的形式落盘：翻译的结果要能被下一个人（包括下一个会话的 agent）读懂和改。

顺带一提：示例里「发信」被换成了「拟稿」。因为发信涉及真实副作用，把它留在人确认之后，比在示例里演示自动发送更接近这套约束的本意。

## 四、「会成长」是自指约束

把上面几条连起来看，可以得到一个比逐条实现更有用的结论。**要实现「下次能做对」，至少需要四个前提同时成立：**

1. **状态被记住** —— 否则上次做到哪一步都说不清，幂等都无从谈起；
2. **纠正被加载** —— 否则新会话根本不知道这条规则存在；
3. **失败可诊断** —— 否则出了问题只能重读整个项目猜哪里错了；
4. **动作可回滚** —— 否则「纠正」本身会变成第二次事故（把课退了发现退错了，还得再退一次）。

这四条对应的正是原文那些看起来零散的约束细节：幂等、定位到原文、Git 管规则、提交前展示。它们不是五条并列的功能，而是**「会成长」这一条自指要求的四个支点**。所以原文把元要求跟功能清单并列写，并不是把它当成第五条功能，而是说：前五条决定这套东西有没有用，元要求决定它会不会随时间变好。

这个视角还有一个副作用：它解释了为什么原文说「组合方式本身就是你的设计」是个发散任务。组合方式不收敛，是因为每种组合背后都是这四个支点的不同摆法——共享哪份状态、幂等键选什么、规则放哪里、确认放在哪一步。没有唯一正确答案，但每个组合都要对这四条给出答案。

## 五、把实验当规格来用

原文第 3 节讲布置这个实验的理由，值得整段读：不加澄清就把这些需求丢给 Agent，大概率得到一团 AI slop——它也许确实能工作，但每次修改都消耗大量 token，Agent 在泥潭里反复读代码试错，像极了《人月神话》的软件焦油坑。

但原文紧接着说了另一半：这是好事，因为 AI 重构能力极强，找到更好的架构瞬间就能改进。**两句话合起来的操作建议是：先把规格写死，再让 Agent 生成实现。** 原文给的工具是「配合一个 Grill Me 之类的技能，让它追问你的需求」——把模糊需求追问成可验收条目。

我的补充是给每条约束配一个**可执行的验收动作**，否则「可验收」还是软的：

| 约束 | 验收动作 |
|---|---|
| 个人数据库 | 随机挑一个回答，要求给出来源文件与行号；给不出即判不通过 |
| 邮箱幂等 | 同一封邮件连续处理两遍，断言第二遍不产生新草稿 |
| ehall 保守 | 构造一次「退课」请求，断言在确认前没有任何写操作发生 |
| 手机端 | 在手机上接管一条进行中的任务，断言不需要桌面窗口在线 |
| 规则跨会话 | 关掉当前会话重开，问一条只有规则里才有的问题，看它是否按规则作答 |

这几条断言都不难写，难的是**先承认它们存在**。约束清单的价值不在于约束，而在于它给出了可以写成测试的东西。
