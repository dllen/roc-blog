酒店预订的三笔账？超售敢定多少、漏斗把写放大多少、库存行能扛多少并发。讲义把酒店预订的设计讲得很细（需求问答、四张表、房型而非房间、幂等键、乐观锁/悲观锁/约束三种解法、按 hotel_id 分片、Redis 缓存 + CDC），但这三笔账它都留成定性判断。这篇把它们算出来。

这篇不复述译文，也不搬运中文译本的任何段落。它复述这一章的骨架（需求与估算、API、数据模型、并发问题、可扩展性、服务间一致性），然后补三个自写模型：**超售比例与取消率的关系**、**转化口径决定的写峰值**、**检查-写入窗口与热点行锁**。

## 一、本章骨架：规模、10% 超售、四张表、两种并发问题

**需求问答（讲义用对话敲定）**：5000 家酒店、100 万间客房；**预订时全额付款**；只支持网站或 App；**可以取消**；**允许 10% 超售**——「酒店会出售比实际更多的房间，因为预计客户会取消」；**房价每天变化**（价格取决于当天满房程度）；范围聚焦展示酒店页、客房详情页、预订、管理后台、支持超售。

**非功能需求**：**支持高并发**（旺季很多人同时订同一家酒店）、**中等延迟**（几秒可接受）。

**讲义的估算**：70% 占用、平均入住 3 天 → 每日预订约 240k（按公式算是 233,333，讲义取整）→ **平均约 3 TPS**；漏斗按「到达预订页三步、每步转化 10%」推算：3 个预订 ⇒ 30 次预订页浏览 ⇒ 300 次详情页浏览。

**API**：酒店/客房的增删改查（仅运维）、预订的创建/查询/取消。预订请求体带 `reservationID`——讲义明确它是**幂等键**，用来避免重复预订。

**数据模型**：讲义先选关系型数据库，理由是读多写少、**需要 ACID**（防止负余额、重复扣款）、结构清晰。第一版 schema 以「具体房间」为中心，讲义自己指出这适用于 Airbnb 而不适用于酒店——**用户订的是房型不是房间，房号在预订时确定**。改进版引入 `room_type_rate`（价格）与 **`room_type_inventory`**（库存），键是 `(hotel_id, room_type_id, date)`，两列关键值：**`total_inventory`（总房间数减去暂时下架的）** 与 **`total_reserved`（已订总数）**。

**并发问题有两个**：同一用户点两次「预订」（客户端禁用按钮不可靠，因为用户可以禁用 JS → 用幂等键 + `reservation_id` 唯一约束）；多人同时订同一间房（讲义给出悲观锁、乐观锁、数据库约束三种解法，并指出隔离级别不够可串行化时会双卖）。

**可扩展性与一致性**：全部服务无状态可复制，**数据库按 `hotel_id` 分片**（QPS 大 1000 倍时 16 片 → 1875 QPS/片）；**Redis 缓存库存**（key = `hotelID_roomTypeID_{date}`，值 = 可用房数，TTL 过期），通过 **CDC（Debezium）** 把数据库变更流到缓存，**缓存与数据库可能短暂不一致，但没关系——因为数据库会阻止无效预订**，UI 上表现为用户要刷新才看到「没房了」；跨服务一致性的备选是两阶段提交（阻塞）与 Saga（补偿），讲义的务实选择是把互相依赖的**预订与库存放在同一个关系型数据库**里。

## 二、增量一：超售 10% 的成立条件是取消率

讲义给了一句理由：「酒店会出售比实际更多的房间，因为预计客户会取消」。这句话可以变成一个不等式：

```python
"""超售 10% 的成立条件：超售比例必须小于取消率。

用讲义给的量：5000 家酒店、100 万间客房、70% 占用、240k 预订/天、允许 10% 超售。
只依赖标准库；输出确定性。
"""
ROOMS = 1_000_000
OCCUPANCY = 0.70
AVG_STAY_DAYS = 3
OVERBOOK = 0.10
DAILY_RES = ROOMS * OCCUPANCY / AVG_STAY_DAYS

print("规模：%s 间房、占用率 %.0f%%、平均入住 %d 天 -> 每日预订 %s 次（讲义的 240k）"
      % (format(ROOMS, ","), OCCUPANCY * 100, AVG_STAY_DAYS, format(int(DAILY_RES), ",")))
print()
print("超售 10%% = 名义库存 %s 间之外再卖 %s 间" % (format(ROOMS, ","), format(int(ROOMS * OVERBOOK), ",")))
print()
print("%-12s %16s %18s %22s" % ("取消率", "实际卖出", "物理占用", "相对 100 万上限"))
for cancel in (0.0, 0.05, 0.091, 0.10, 0.20):
    sold = ROOMS * (1 + OVERBOOK) * (1 - cancel)
    print("%-12.1f%% %16s %18s %22s"
          % (cancel * 100, format(int(sold), ","), format(int(sold), ","),
             ("超卖 %s 间" % format(int(sold - ROOMS), ",")) if sold > ROOMS else "安全"))
print()
need = OVERBOOK / (1 + OVERBOOK)
print("临界取消率：超售 10%% 时，取消率必须 >= %.2f%%（= 10%% / 1.1）" % (need * 100))
print("  => 超售 10%% 只有 0.91 个百分点的缓冲：取消率预测偏 1 个点，就是 %s 间/天的超卖。"
      % format(int(DAILY_RES * OVERBOOK * 0.01)))
print()
print("入住 3 天 -> 取消窗口的影响：")
for window in (0, 1, 3, 7):
    print("  入住前 %d 天就要定超售 -> 预测期 %d 天，取消率预测的误差要累积这么久" % (window, max(window, 1)))
print()
print("判据：")
print("  - **超售比例是取消率预测的下限约束，不是营销参数**：超售 %.0f%% 要求取消率 >= %.2f%%。" % (OVERBOOK * 100, need * 100))
print("  - 每日 %s 次预订、10%% 超售 = 每天 %s 间暴露在超卖风险里；" % (format(int(DAILY_RES), ","), format(int(DAILY_RES * OVERBOOK), ",")))
print("    取消率预测每差 1 个百分点，就是 %s 间/天的账面亏损（要在入住前发现并转售出去）。" % format(int(DAILY_RES * OVERBOOK * 0.01)))
print("  - 所以超售必须配一条「发现超卖怎么办」的流程（转售/升级/取消并赔付），否则超卖不是收益，是负债。")
```

输出：

```text

超售 10% = 名义库存 1,000,000 间之外再卖 100,000 间

  => 超售 10% 只有 0.91 个百分点的缓冲：取消率预测偏 1 个点，就是 233 间/天的超卖。

入住 3 天 -> 取消窗口的影响：
  入住前 0 天就要定超售 -> 预测期 1 天，取消率预测的误差要累积这么久
  入住前 1 天就要定超售 -> 预测期 1 天，取消率预测的误差要累积这么久
  入住前 3 天就要定超售 -> 预测期 3 天，取消率预测的误差要累积这么久

判据：
  - **超售比例是取消率预测的下限约束，不是营销参数**：超售 10% 要求取消率 >= 9.09%。
  - 每日 233,333 次预订、10% 超售 = 每天 23,333 间暴露在超卖风险里；
    取消率预测每差 1 个百分点，就是 233 间/天的账面亏损（要在入住前发现并转售出去）。

```

三处结论：

**第一，超售 10% 要求取消率至少 9.09%。** 名义库存 100 万间，超售后再卖 10 万间；若一个都不取消，物理占用 110 万间，直接超卖 10 万间。临界条件是 `110 万 × (1 − 取消率) ≤ 100 万`，即**取消率 ≥ 10% / 1.1 = 9.09%**。取消率 5% 时超卖 4.5 万间，取消率 20% 时安全。

**第二，缓冲只有 0.91 个百分点，所以超售本质上是取消率预测问题。** 每天 233,333 次预订、10% 超售 = **每天 23,333 间**暴露在超卖风险里；**取消率预测每差 1 个百分点，就是 233 间/天的账面亏损**（而且必须在入住前发现并转售出去，否则是赔付）。所以超售比例不能当营销参数拍脑袋定，它有下限：**超过取消率预测就是负债**。

**第三，超售必须配套「发现超卖怎么办」的流程。** 转售、升级房型、还是取消并赔付——这是运营与客服的活，不是代码能自动消掉的。判据：**没有兜底流程的超售，等于把一个统计误差直接转成赔款。**

## 三、增量二：漏斗系数定读放大，转化位置定写峰值

讲义说平均 TPS 只有 3，这掩盖了真正的问题——**读放大和写峰值是两回事**：

```python
"""转化率口径决定写放大：同一份流量，预订写的峰值能差 10 倍。

用讲义给的量：每天 24 万预订、漏斗三步每步 10%、每步浏览量 10 倍。
只依赖标准库；输出确定性。
"""
DAILY_RES = 240_000
FACTOR = 10                # 每一步的浏览量是上一步的 10 倍（讲义的漏斗假设）

views = DAILY_RES * FACTOR ** 2
print("日访问量：%s 次详情页浏览（讲义：300 次浏览 -> 3 个预订）" % format(views, ","))
print()
print("两种转化口径，同样的访问量：")
print("%-26s %14s %14s %18s" % ("口径", "详情页 QPS", "预订页 QPS", "预订写 QPS"))
for peak_share, burst in ((0.20, 1), (0.20, 10), (0.50, 10)):
    vps = views * peak_share / 3600 * burst
    booking_qps_stepwise = vps * 0.01 / 2      # 10% 分布在两步上
    booking_qps_direct = vps * 0.01            # 全部集中在最后一步
    print("%-26s %14s %14s %18s"
          % ("峰时占 %.0f%%、集中 %dx" % (peak_share * 100, burst), format(int(vps), ","),
             format(int(vps * 0.1), ","),
             "%.0f -> %.0f" % (booking_qps_stepwise, booking_qps_direct)))
print()
print("  => 同样 1% 的总转化率，**写在哪一步决定了写的峰值**：")
print("     逐步转化（详情->预订页->下单）-> 预订写峰值是最后一步的 1/2；")
print("     直接转化（看完详情页就下单）-> 全部压在最后一步，峰值翻倍。")
print()
print("读放大则是固定的：每 1 个预订带来 %d 次页面浏览" % (FACTOR ** 2))
print()
print("判据：")
print("  - **漏斗系数决定读放大（固定 %d 倍），转化位置决定写峰值（2 倍差）**；" % (FACTOR ** 2))
print("    写峰值直接决定库存行的事务 TPS 与锁竞争（下一节的热点行账）。")
print("  - 讲义说「平均预订 TPS 只有 3」——那是日均；峰值要看流量怎么分布，")
print("    而「旺季很多人同时订同一家酒店」意味着流量在**单个酒店上**叠加，")
print("    全站 TPS 3 和单店 TPS 是两回事。")
```

输出：

```text
日访问量：24,000,000 次详情页浏览（讲义：300 次浏览 -> 3 个预订）

两种转化口径，同样的访问量：
口径                                详情页 QPS        预订页 QPS            预订写 QPS
峰时占 20%、集中 1x                       1,333            133            7 -> 13
峰时占 20%、集中 10x                     13,333          1,333          67 -> 133
峰时占 50%、集中 10x                     33,333          3,333         167 -> 333

  => 同样 1% 的总转化率，**写在哪一步决定了写的峰值**：
     逐步转化（详情->预订页->下单）-> 预订写峰值是最后一步的 1/2；
     直接转化（看完详情页就下单）-> 全部压在最后一步，峰值翻倍。

读放大则是固定的：每 1 个预订带来 100 次页面浏览

判据：
  - **漏斗系数决定读放大（固定 100 倍），转化位置决定写峰值（2 倍差）**；
    写峰值直接决定库存行的事务 TPS 与锁竞争（下一节的热点行账）。
  - 讲义说「平均预订 TPS 只有 3」——那是日均；峰值要看流量怎么分布，
    而「旺季很多人同时订同一家酒店」意味着流量在**单个酒店上**叠加，
    全站 TPS 3 和单店 TPS 是两回事。
```

三处结论：

**第一，读放大是固定的 100 倍。** 每个预订带来 300 次详情页浏览（讲义的漏斗假设），日访问量 = 240k × 100 = **2400 万次/天**。这部分压力落在读路径（缓存、酒店服务），**与库存并发无关**。

**第二，写峰值取决于转化发生在哪一步，差 2 倍。** 逐步转化（详情页 → 预订页 → 下单，10% 分布在两步上）时，峰时 20% 流量 + 10 倍集中下预订写是 67 QPS；直接转化（看完详情页就下单）时全部压在最后一步 → **133 QPS**。同样的 1% 总转化率、同样的访问量，**写峰值差一倍**。

**第三，「平均 3 TPS」和「旺季同一家酒店」是两个量纲。** 全站日均 3 TPS 听起来毫无压力，但需求里的高并发指的是**单店集中**：流量在单家酒店上叠加，而库存行的热点恰好也在单家酒店的某个房型的某一天。**下一节的账就发生在这个格子上**——所以容量规划必须做「单店单房型单日」这一格的推演，而不是全站平均值。

## 四、增量三：超卖窗口与热点行锁的正面冲突

讲义把并发问题讲得很清楚：先 `SELECT` 库存检查、再更新库存，两个事务在非可串行化隔离下会双双看到「还剩 1 间」→ 双卖。**把这个窗口量化**：

```python
"""超卖窗口与热点行锁：同一行上的两个指标直接冲突。

用讲义给的量：room_type_inventory 的 (hotel_id, room_type_id, date) 行、16 分片按 hotel_id。
只依赖标准库；输出确定性。
"""
INV = 100                 # total_inventory
RESERVED = 99             # 已订，只剩 1 间
ARRIVAL = 100             # 热点房型同一天的到达率（请求/秒，估）
WINDOWS_MS = (0.5, 1, 5, 10, 50)
TX_MS = 5                 # 单次事务耗时（估）

print("热点场景：某房型某天 total_inventory=%d、total_reserved=%d（只剩 1 间），" % (INV, RESERVED))
print("同时到达率 %d 请求/秒。检查与写入之间的窗口 w 决定超卖期望：" % ARRIVAL)
print()
print("%-14s %18s %20s" % ("窗口 w", "期望超卖间数", "判定"))
for w in WINDOWS_MS:
    exp_oversell = ARRIVAL * (w / 1000.0)
    verdict = "必然超卖" if exp_oversell >= 1 else ("%.0f%% 概率超卖" % (exp_oversell * 100))
    print("%-14s %18.2f %20s" % ("%.1f ms" % w, exp_oversell, verdict))
print()
print("改成原子条件更新（UPDATE ... WHERE total_reserved + n <= total_inventory）：")
print("  超卖期望 = 0，代价是同一行上的写被串行化：")
print("  单行预订 TPS 上限 = 1 / 事务耗时 = 1 / %d ms = %d TPS" % (TX_MS, int(1000 / TX_MS)))
print()
print("讲义的分片键是 hotel_id（16 片、30000 QPS -> 1875 QPS/片）：")
print("  但热点行是 (hotel_id, room_type_id, date) —— 同一酒店、同一房型、同一天 = 同一行，")
print("  **按 hotel_id 分片并不能把这一行打散**（它只会把整家酒店的行分到同一片）。")
print()
print("能打散热点的三个方向（各自代价）：")
for name, effect, cost in (
    ("按 (hotel_id, room_type_id, date) 再分片", "把同一天的行拆成 N 份，N 倍并行", "需要额外的行合并/协调逻辑，跨行事务"),
```

三处结论：

**第一，检查-写入的窗口直接决定超卖概率。** 热点房型某天只剩 1 间、到达率 100 请求/秒时：窗口 0.5 ms → 超卖期望 0.05 间（5% 概率）；1 ms → 0.1 间（10% 概率）；**5 ms → 50% 概率；10 ms → 必然超卖**。所以「超卖率」不是玄学，它 ≈ 到达率 × 窗口。

**第二，堵住超卖的代价是同一行串行化。** 改成原子条件更新（`UPDATE ... WHERE total_reserved + n <= total_inventory`）后超卖期望为 0，但**同一行的写被串行**：事务 5 ms → 单行预订 TPS 上限只有 **200**。**「绝不超卖」与「高并发」在同一行上直接冲突**——这是讲义「支持高并发」与「关系型数据库 + ACID」两个选择撞在一起的地方。

**第三，讲义的分片键打不散这个热点。** 讲义按 `hotel_id` 分片（16 片、30000 QPS → 1875 QPS/片），但热点行是 `(hotel_id, room_type_id, date)`——**同一酒店、同一房型、同一天 = 同一行**，按 hotel_id 分片只会把整家酒店的行放到同一片，**行热点原封不动**。能真正打散它的只有三条路：把库存拆成多行（需要跨行协调）、按日期分库（不同日期天然不争）、或读写分离（读走 Redis，写仍走 DB——**讲义自己也承认 DB 才是阻止无效预订的权威**）。

**第四，所以正确的解法不是「把事务做快」，而是承认这是业务决策。** 热点日排队/限流、允许有限超卖、或拆库存行让并发真正并行——**都要先定策略再改代码**。

## 五、把三个模型套回本章（判据清单）

1. **超售比例有下限：超售 ≤ 取消率 − 1% 左右**。10% 超售要求取消率 ≥ 9.09%，缓冲 0.91 个百分点；取消率预测每差 1 个点 = 233 间/天。
2. **超售必须配兜底流程**（转售/升级/赔付），否则超卖是负债而不是收益。
3. **读放大固定 100 倍、写峰值差 2 倍**：漏斗系数决定读，转化位置决定写；容量规划要做「单店单房型单日」这一格，不看全站均值。
4. **超卖率 ≈ 到达率 × 检查写入窗口**：1 ms → 10% 概率，10 ms → 必然超卖。
5. **原子更新的代价是单行 TPS 上限**（事务 5 ms → 200 TPS）；要「绝不超卖 + 高并发」，必须承认要拆行或排队。
6. **分片键 hotel_id 打不散库存行热点**：热点是 `(hotel_id, room_type_id, date)`，要按它再分或按日期分库。
7. **缓存只解决读，不解决写的一致性**：讲义用 Redis + CDC 缓存库存，并明说 DB 才是阻止无效预订的权威——UI 上「刷新才看到没房了」是这个取舍的可见代价。

## 七、这三个模型判不了什么

- **取消率、到达率 100 请求/秒、事务 5 ms、漏斗系数 10 都是估的**。真实取消率随提前预订天数、季节、房价波动剧烈；**它是这三个模型里最不确定、也最要命的一个输入**。
- **没算价格与超售的联动**。讲义说「价格取决于当天满房程度」——这意味着动态定价会把订满的时间点提前，**超售窗口与价格曲线的耦合会同时改变取消率和到达率**（越贵 → 取消越多、越多人提前订），这三者不能分开估。
- **没算房型内部的替换**。改进后的模型里用户订的是房型、房号到店才定——所以「库存」是房型级的，而「超卖」最终要落到具体房间上；**同房型不同房价、房间不可互换**（大床 vs 双床）会让这层映射带来额外的拒绝率。
- **没算管理后台与客服的负载**。讲义把管理后台（退款、取消付款）也划进范围，它的时间分布与用户侧完全不同（退款集中在入住失败与投诉时段），是一类独立的峰值。
- **三个模型都没碰跨服务一致性**（2PC 与 Saga 的取舍）：讲义选了「同库同事务」的务实路线，本篇没有展开它的长期代价——**每多一个服务，就多一次跨服务原子性的谈判**。

## FAQ（八、常见问题）

**超售 10% 安全吗？** 它的成立条件是**取消率 ≥ 9.09%**（临界式 `110 万 × (1 − 取消率) ≤ 100 万`）。缓冲只有 0.91 个百分点：取消率预测偏 1 个点，就是每天 **233 间**的账面亏损（每天 23,333 间暴露在风险里）。所以超售比例不是营销参数，而是取消率预测的下限约束。

**为什么讲义说平均只有 3 TPS，却要担心高并发？** 因为 3 是全站日均，需求里的高并发指的是**单店集中**：流量叠加在同一家酒店的同一个房型的同一天上，而库存行的热点恰好就在这一格。容量规划必须推演「单店单房型单日」的并发，不能看全站平均。

**转化率 10% 会带来多少写压力？** 读放大固定是 **100 倍**（每单 300 次详情页浏览，日访问 2400 万），写峰值则取决于转化发生在哪一步：逐步转化下是 67 QPS（峰时 20% + 10 倍集中），直接转化下是 **133 QPS**——同一份流量、同样 1% 转化，写峰值差 2 倍。

**怎么防止超卖？** 窗口决定超卖率：**超卖率 ≈ 到达率 × 检查写入窗口**（100 请求/秒时，1 ms → 10% 概率、5 ms → 50%、10 ms → 必然）。改成原子条件更新后超卖为 0，但同一行的写被串行，事务 5 ms 时**单行预订 TPS 上限只有 200**。所以「绝不超卖」与「高并发」在同一行上直接冲突，要靠拆行、按日期分库或排队限流来解。

**按 hotel_id 分片能解决热点吗？** 不能。热点行是 `(hotel_id, room_type_id, date)`——**同一酒店同一房型同一天就是同一行**，按 hotel_id 分片只会把整家酒店的行放进同一片，行热点原封不动。能打散它的只有：把库存拆成多行（需跨行协调）、按日期分库、或读写分离（但讲义明确 DB 才是阻止无效预订的权威）。
