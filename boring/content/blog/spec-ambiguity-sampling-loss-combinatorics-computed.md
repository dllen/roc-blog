## 一、讲者的骨架：让验证不依赖「人作为第一审阅者」

Rajath Kotyal 属于 **AWS 自动化推理（automated reasoning）团队**，讲的项目是 **Kero specification analyzer**：用**形式化方法 + 自动化推理**去验证那些「在 coding agent 写代码之前就会提交给它」的规格。

**触发案例**是一份电商规格里的两条规则：

- 规则二：当订单被提交、且**库存不可用**时，把该订单**列为 backorder（延期订单）**——单独读完全合理。
- 同一份规格里还有另一条规则：**不允许把任何订单列为 backorder**。

**单独读每条都成立，但一个 LLM 同时读到两条时，两者不可能同时被满足**（讲者原话："individually read, these two lines make sense... but both cannot hold through at the same time"）。这就是需要解决的核心歧义。

**动机数字**（讲者引用的近期公开研究）：提示不明确时，LLM 生成的准确性与代码准确性**下降 20%–40%**；**60%–90% 的有效代码在写完之后仍然是错的**；在这种情况下，代码部署后出现的**回归问题多两倍**。于是问题变成：**这类错误藏在哪里？** 他的答案是：藏在 spec 里。目标是在它们**进入代码库之前**就发现。

**一个很精确的目标设定**：**验证的是「没有人类（或任何人）作为第一个审阅者读过这些文件」的情况**。

**两个尺度的问题**：**句内**——歧义（ambiguity）、措辞不当（wording）、细节层次不足；**跨句**——规则之间的**冲突（conflicts）**与**空白（gaps）**。因此需要三种检查能力：审查单句、在句之间搜索、发现歧义。

**三步流程**：

1. **LLM 先自己优化措辞。** 如果成功当然好——但这只处理了句内的 wording 问题。
2. **优化不成，把英文形式化为 SMT 公式。** SMT（**SMT-LIB**）是一类函数表达式，交给 **SAT 求解器 / 可满足性检查器**，求解器返回一个布尔值：这个表达式是否有效（valid）、为真还是为假。
3. **拿到结果后分流**：表达式**有效** → 什么都不做（silent pass）；求解器检测到**两句之间或一句之内存在歧义**（一句话有两种含义）→ **把这个句子交回 LLM 重新检查**，LLM 重新表述后再次验证。

**深挖：多次采样 + 逻辑等价聚类。** 发现可疑句子后，他们**再做一轮三步流程**，重点是**反复测试翻译结果**：让 LLM **翻译 7 次或 10 次**，以判断「这个 LLM 是真的就是这样表现的，还是有什么外部因素把它推到了这个状态」。然后按**逻辑等价性**对这 7–10 组解释做**聚类**，看清「这些解释分别落在 LLM 自己做过的哪一组假设下」。聚类之后有**三个出口**：**接受**当前状况；**要求用户消除歧义**；**放弃**——不在代码库里实现这条规则。

**三类缺陷的可操作样例**：**歧义**——「删除记录」这句话非常模糊，LLM 可以随意解释但不能允许；工具的做法是给出两个选项让人选：**要么按现状删除记录，要么保留记录但对用户隐藏**。**冲突**——前面那条规则一与规则三冲突。**空白**——当 LLM 检测到某条**实际存在的流程或管道**时，发现**没有对应规则覆盖它**，也就是**你缺了东西**。

**边界与分工**：对这三类问题，他讲得很坦白——**「归根结底，除了用户之外，我们无法保证有任何其他机制来确保规范的准确性。」** **用户必须在把片段发给 LLM 之前，逐条检查规则手册里的每一部分**；**用户更重要，因为规范里包含隐含的领域知识（implicit domain knowledge）**，LLM 不了解多少领域知识，也没有任何保证。他同时承认**当前对「形式化方法及其在 agent 中的应用」的证据还很薄**（thin evidence），这项技术仍在探索阶段。

**带走的结论**（他自述）：① **把 spec 交给 agent 之前，务必先检查它。** ② **对翻译结果做聚类**——按逻辑等价项聚类，以确定 LLM 的不同解释以及真正出错的地方。**职责分工一句话：LLM 翻译，求解器验证，人类决定。** 如果选项里没有合适答案，就用 **LLM judge** 裁决，或者干脆**不实现这一段**。

## 二、增量一：N=7 还是 N=10，应该反解出来

```python
"""采样 7 次还是 10 次？N 应该由「检出第二种解释的目标置信度」反解出来。

数字取自我的精读笔记：让 LLM 翻译 7 次或 10 次，再按逻辑等价性聚类，以判断「这个 LLM 是真的
就是这样表现的，还是有什么外部因素把它推到了这个状态」。
只依赖标准库；输出确定性。全部用 f-string，避免 %-格式化与中文标点冲突。
"""
import math

TARGETS = (0.90, 0.95)
P_MAIN = (0.70, 0.85, 0.95)      # 单次翻译给出主流解释的概率（估）


def detect_prob(p, n):
    """采样 n 次都没出现非主流解释的概率是 p^n -> 至少检出一个非主流的概率"""
    return 1.0 - p ** n


def n_needed(p, target):
    """反解：1 - p^n >= target  =>  n >= ln(1-target)/ln(p)"""
    return math.ceil(math.log(1 - target) / math.log(p))


print("一、检出「第二种解释」的概率 = 1 - p^N")
print(f"{'主流概率 p':<16}" + "".join(f"{'N=' + str(n):>12}" for n in (3, 7, 10, 15)))
for p in P_MAIN:
    print(f"{format(p, '.2f') + ' (估)':<16}" + "".join(
        f"{detect_prob(p, n) * 100:>11.1f}%" for n in (3, 7, 10, 15)))
print()
print("二、反解：达到目标置信度需要几次")
print(f"{'主流概率 p':<16}{'90% 所需 N':>14}{'95% 所需 N':>14}   讲者给的 7 / 10 够不够")
for p in P_MAIN:
    n90, n95 = n_needed(p, 0.90), n_needed(p, 0.95)
    note = f"90% 需 {n90} 次（讲者取 7，够）" if n90 <= 7 else f"90% 需 {n90} 次，讲者的 7 次不够"
    print(f"{format(p, '.2f') + ' (估)':<16}{n90:>14}{n95:>14}   {note}")
print()
print(f"   => 判据：**N=7 只在「单次翻译的主流概率 <= 0.72」时才够 90% 检出**")
print(f"      （1 - 0.72^7 = {detect_prob(0.72, 7) * 100:.1f}%；而 p=0.85 时 N=7 只有 "
      f"{detect_prob(0.85, 7) * 100:.1f}%，要 N={n_needed(0.85, 0.90)} 才到 90%）")
print("      所以「翻译 7 次或 10 次」不是随手取的数，**它隐含了一个关于模型歧义度的假设**；")
print("      换个模型或换个 spec 域，这个数就得重算。")
print()
print("三、采样的成本：翻译 N 次 + 求解 K 次")
for n, k in ((7, 3), (10, 5), (15, 8)):
    print(f"   N={n:2d} 次翻译、聚成 {k} 个等价类 -> 翻译成本 {n:2d} 个单位、SMT 求解 {k} 个单位"
          f" -> 合计 {n + k:2d} 个单位")
print("   => 判据：**深挖不是免费的**：每多采一次就多一次翻译，每多一个等价类就多一次 SMT 求解。")
print("      N 从 7 提到 15，翻译成本翻倍还多；所以 N 应该由置信度反解，而不是「保险起见多采几次」。")
```

输出：

```text

```

三处结论：

**第一，「翻译 7 次或 10 次」不是随手取的数，它隐含了一个关于模型歧义度的假设。** 检出「第二种解释」的概率是 **1 − p^N**（p = 单次翻译给出主流解释的概率，估）。p=0.70 时 N=7 的检出率是 **91.8%**；p=0.85 时只有 **67.9%**；p=0.95 时只有 **30.2%**。**判据：N=7 只在「单次翻译的主流概率 ≤ 0.72」时才够 90% 检出**。

**第二，N 应该由目标置信度反解，而不是拍脑袋。** N ≥ ln(1−C)/ln(p)：p=0.70 时 90% 需 **7** 次、95% 需 9 次；p=0.85 时 90% 需 **15** 次、95% 需 19 次；p=0.95 时 90% 需 **45** 次。**判据：换个模型或换个 spec 域，主流概率一变，这个数就得重算**——而「7 或 10」把假设藏在了流程里。

**第三，深挖不是免费的。** N=7、K=3 时是 7 次翻译 + 3 次 SMT 求解；N=15、K=8 时是 15 + 8。**判据：每多采一次就多一次翻译，每多一个等价类就多一次求解**，所以 N 应该由置信度反解，而不是「保险起见多采几次」。

## 三、增量二：歧义造成的损失，无法在下游修复

```text
   判据：**spec 阶段的收益是「避免错误被自动写进代码库并扩散」**——
```

三处结论：

**第一，每千个任务里有 200~400 个因 spec 歧义而理解错**（讲者引用的研究：提示不明确导致准确率下降 20%–40%）。**判据：歧义是「上线前」的问题，不是「上线后」的问题**。

**第二，下游验证器能把 200~400 缩到 10~20，但剩下的修不了。** 假阴性率 1% → 漏 2~4 个；5% → 漏 10~20 个；20% → 漏 40~80 个。**判据：那剩下的 10~20 个不是验证器能修的——它继承的是同一个错误理解**。所以验证的价值在于「**发现歧义**」，不在于「在歧义存在时给出正确答案」。这也正好对应讲者的三段分工：**LLM 翻译 → SMT 求解器判定 → 人决定**；**不要让 LLM 同时扮演规格的作者、译者和裁决者**——求解器的作用不是「更聪明的模型」，而是**一个与 LLM 无关的确定性裁判**。

**第三，一个必须避开的坑：不要把几个数字相乘。** 把「60%–90% 有效代码写完仍错」与「歧义导致 20%–40% 下降」相乘，会得出「正确率只有 24.0%」这种结论——**这是双重计数**：前者是总体缺陷率，后者是其中的一个成因。官方稿也没给这两组数字的出处。**判据：引用时必须保留「讲者引用的研究数据」这个限定**。

**第四，「回归多两倍」是这条流程真正的收益来源。** 若清晰 spec 部署后每版出 100 个回归问题，歧义 spec 下就是 200 个。**判据：spec 阶段的收益是「避免错误被自动写进代码库并扩散」**——错误进库之后的修复成本远高于在 spec 阶段拦住。

## 四、增量三：歧义是乘性的，「逐句检查」漏掉了组合

```python
"""歧义是乘性的：m 条约束句 -> 2^m 种联合读法，采样 N 次最多看见 N 类。

数字取自我的精读笔记：规格问题分两个尺度（句内：歧义/措辞/细节层次；跨句：冲突/空白）；
按逻辑等价性对 7-10 组解释聚类；缺口是「存在流程或管道但没有对应规则覆盖」。
只依赖标准库；输出确定性。
"""
import math

P_MAIN = 0.85            # 单次翻译给出主流解释的概率（估，与采样模型同一个假设）


def expected_classes(n, p):
    """现实期望：主流解释占 p，其余每次采到彼此不同的读法 -> 期望等价类数"""
    return 1 + (1 - p) * (n - 1)


print("一、联合读法是乘性的")
print(f"{'约束句数 m':<14}{'每句 2 种读法':>16}{'联合读法数 2^m':>22}{'采样 10 次覆盖率':>20}")
for m in (3, 5, 8, 10, 12, 15):
    total = 2 ** m
    print(f"{m:<14}{2:>16}{format(total, ','):>22}{100.0 * min(10, total) / total:>19.2f}%")
print()
print("   => 判据：**逐句检查漏掉了组合歧义**——每句单独都清楚，合起来仍有 2^m 种读法；")
print(f"      m=10 时联合读法有 {format(2 ** 10, ',')} 种，采样 10 次只覆盖 "
      f"{100.0 * 10 / 1024:.2f}%。")
print()
print("二、采样次数与组合空间：最坏情况上界 vs 现实期望")
print(f"{'m':<8}{'联合读法 2^m':>14}{'覆盖 90% 需采样':>18}{'最坏情况 7-10 次':>18}"
      f"{'现实期望类数 p=0.85':>20}{'现实覆盖率':>14}")
for m in (3, 5, 8, 10, 12, 15):
    total = 2 ** m
    p90 = math.ceil(total * 0.9)
    worst = min(10, total) / total
    exp_cls = expected_classes(10, P_MAIN)
    print(f"{m:<8}{format(total, ','):>14}{format(p90, ','):>18}{worst * 100:>17.2f}%"
          f"{exp_cls:>20.2f}{100.0 * exp_cls / total:>13.3f}%")
print()
print("   读法：**「覆盖 90% 需采样」是最坏情况上界**（每次都采到全新读法，且读法在组合空间里均匀分布）；")
print(f"   现实里主流解释占 85%（估），10 次采样期望只看到 {expected_classes(10, P_MAIN):.2f} 个等价类。")
print("   => 判据：**N 次采样最多只能看到 N 个等价类，而组合空间是 2^m**——")
print(f"      m=12 时组合空间 {format(2 ** 12, ',')} 种，10 次采样现实期望只看到 "
      f"{expected_classes(10, P_MAIN):.2f} 类（覆盖率 "
      f"{100.0 * expected_classes(10, P_MAIN) / 2 ** 12:.3f}%）。")
print("      换个说法：**聚类压缩的是重复解释，不是组合空间**；")
print("      所以真正能收敛组合爆炸的不是「多采几次」，而是**把约束写成 SMT 交给求解器逐条判冲突**——")
print("      求解器面对的是公式之间的可满足性，不是采样出来的句子集合。")
print()
print("三、逻辑等价聚类在做什么")
print("   原始翻译数 N -> 逻辑等价类数 K -> 三个出口：接受 / 要求用户消除歧义 / 放弃不实现")
print(f"{'采样 N':<16}{'若全不同 K=N':>18}{'若含重复 K=3':>18}{'对用户展示的选项数':>22}")
for n in (7, 10):
    print(f"{n:<16}{n:>18}{3:>18}{3:>22}")
print()
print("   判据：**聚类把「模型有多种合理解释」从隐藏的随机性变成可枚举、可展示给人选择的选项**——")
print("      这就是讲者那句「按逻辑等价性聚类」的工程价值。")
print()
print("四、三类缺陷与它们的检查能力")
print(f"{'尺度':<12}{'缺陷类型':<26}{'谁能查出来':>30}")
for scale, kind, who in (("句内", "ambiguity 歧义", "多次采样 + 逻辑等价聚类"),
                          ("句内", "wording 措辞不当", "LLM 先自己优化措辞"),
                          ("句内", "细节层次不足", "需要人（隐含领域知识）"),
                          ("跨句", "conflict 冲突", "SMT/SAT 求解器判定"),

    print(f"{scale:<12}{kind:<26}{who:>30}")
print()
print("   => 判据：**形式化方法只能发现「形式化之后仍然可见」的冲突与空白**；")
print("      一旦关键判断依赖领域知识（「延期订单」业务上到底允不允许），形式化无法替你做，")
```

## 七、这三个模型判不了什么

- **单次翻译的主流概率 p、下游验证器假阴性率、每句的读法数（我取 2）、等价类数 K 全是估的**。其中**p 直接决定 N 该取多少**——p=0.70 与 p=0.85 之间，90% 检出所需的 N 从 7 变成 15，这是整个第一节最敏感的参数。
- **「每句两种读法」是最简假设**。真实 spec 里有的句子只有一种读法（那类句子不贡献组合），有的有三四种（贡献更多）。**组合爆炸的斜率取决于「多义句的比例」，我只用了一个平均化的 2**。
- **最坏情况上界假设读法在组合空间里均匀分布**，这显然不成立——现实里歧义高度相关（一条规则歧义常常带出整族歧义）。所以「覆盖 90% 需 3,687 次」是**上界，不是典型值**。
- **2^m 是联合读法数，不是缺陷数**。很多种读法并不产生冲突，只是「读法不同」；真正的缺陷是那些**不可同时满足**或**缺覆盖**的那些。**我没有用 SMT 求解器真去判可满足性**——这一讲的核心工具恰恰是我没有实现的。
- **讲者引用的三个数字（20%–40%、60%–90%、回归多两倍）官方稿没给出处**，我只把它们当作「讲者引用的研究数据」使用，没有独立核实。
- **「验证器假阴性率 5%」是我设的**。如果真实是 20%，那 200~400 会缩到 40~80，第三节的「缩到 10~20」就不成立——但**结论方向不变**：剩下的那些仍然继承同一个错误理解。
- **成本表里的「单位」是相对权重**，不是真实 token 或时间——翻译与 SMT 求解的实际单价我没测。
- **没有测「人决定」这一环的成本**。讲者强调用户必须逐条检查规则手册，但这一环的人力账缺失；而按第二节的算术，这一环恰恰是唯一能消除歧义的地方。

## FAQ（八、常见问题）

**spec 有 bug 是什么意思？** 单看每条都成立，合起来不可能同时满足。讲者的例子：一条规则说「库存不可用时把订单列为 backorder」，另一条说「不允许把任何订单列为 backorder」——**单独读两条都合理，但两者不可能同时成立**。

**这套方法的核心是什么？** 三步：LLM 先自己优化措辞 → 不成则把英文形式化为 SMT 公式交给 SAT 求解器判定 → 检测到歧义就把那句交回 LLM 重新表述再验。分工是**LLM 翻译，求解器验证，人类决定**。

**为什么要翻译 7 次或 10 次？** 为了判断「这个 LLM 是真的就是这样表现的，还是有什么外部因素把它推到了这个状态」；然后按**逻辑等价性聚类**，把 7–10 组解释收敛成若干个假设组，**对用户展示的选项数是等价类数，不是采样数**。判据：**N=7 只在「单次翻译的主流概率 ≤ 0.72」时才够 90% 检出**——这个数应该反解，不该照抄。

**歧义能在下游修好吗？** 不能。每千个任务里 200~400 个因歧义理解错，验证器假阴性率 5% 也只能缩到 10~20 个，**剩下的继承同一个错误理解**。所以验证的价值是「**发现歧义**」，不是在歧义存在时给出正确答案。

**三类缺陷分别怎么查？** 句内 ambiguity → 多次采样 + 逻辑等价聚类；句内 wording → LLM 自己先优化措辞；跨句 conflict → SMT/SAT 求解器判可满足性；跨句 gap → 对照实际存在的流程/管道人工核对；句内「细节层次不足」→ 靠人。

**为什么必须有人参与？** 讲者的原话是「**归根结底，除了用户之外，我们无法保证有任何其他机制来确保规范的准确性**」——因为规格里包含**隐含的领域知识**，LLM 不了解、也没有任何保证。他也承认**形式化方法在 agent 中的证据还很薄**。

**逐句检查够不够？** 不够。m 条约束句每句两种读法 → **2^m 种联合读法**（m=10 是 1,024 种）；采样 10 次最坏只覆盖 0.98%、现实期望只看到 2.35 个等价类。**判据：逐句检查漏掉了组合歧义，聚类压缩的是重复解释而不是组合空间**——收敛组合爆炸要靠求解器。

**聚类之后怎么办？** 三个出口：**接受**当前状况、**要求用户消除歧义**、**放弃**（不在代码库里实现这条规则）。如果选项里没有合适答案，就用 LLM judge 裁决，或者干脆不实现这一段。
