## 一、笔记的骨架：20 题里的三道

**Q3 企业级 RAG（1000 万文档 + 每用户权限）**给了一个「必须知道的坑」：HNSW 索引基于向量相似度，**不能直接在 ANN 搜索时做精细 ACL 过滤**。两种做法的代价——**Pre-filter**（先过滤再 ANN，过滤后数据集变小、召回率下降，HNSW 图结构被打断）、**Post-filter**（ANN 取 Top-N 再按 ACL 过滤，若过滤掉很多，尾部可能全是低相似度结果）；实战解法是四步漏斗（BM25/元数据粗排去掉 80% 无权限文档 → ANN Top-500 → ACL 过滤后 Top-50 → rerank 到 Top-10），更工程的方案是**为权限建单独的 Bitmap 索引**（每用户一个 allowed_doc_ids BitSet），与 HNSW 并行查询做**两阶段 join**。

**Q1 实时语音 Agent 的延迟预算**给了逐阶段目标：AEC+NS 10–20 ms、VAD 20–50、ASR（首个 partial）100–200 /（final）200–400、LLM TTFT 150–300、TPOT 30–80 ms/token、TTS TTFA 150–300、网络 50–150，**端到端 < 1.5 s (P95)**；外加 barge-in 打断与失败模式。

**Q18 优雅降级**给了五级链：L1 正常（GPT-4o + RAG）→ L2 主模型延迟（小模型）→ L3 同能力备用（另一家厂商，**30% 概率**）→ L4 语义缓存 → L5 模板兜底 + UI 提示「当前为简化版」；配套组件是 health check + 实时熔断、多模型路由、quality-aware judge、模板引擎、缓存兜底、UI 提示。

## 二、增量一：权限过滤把 ANN 的前提吃掉了

笔记说 pre-filter 会让召回率下降、post-filter 会让尾部质量变差。到底差多少、什么时候该换结构，可以算：

```python
"""权限过滤 + ANN：过滤把 ANN 的前提破坏后，精确搜索反而更好。

用笔记的量：1000 万文档、BM25 粗排去掉 80% 无权限文档、ANN Top-500 -> ACL 过滤后 Top-50 -> rerank Top-10、
每用户 allowed_doc_ids BitSet 与 HNSW 并行做两阶段 join。
只依赖标准库；输出确定性。
"""
import math

N_DOCS = 10_000_000
DIM = 768
BYTES_PER_DIM = 4         # float32
TOP_K = 10
ANN_N = 500
ANN_RECALL_FULL = 0.95    # 全量 ANN 的召回率（估）
RECALL_PER_DECADE = 0.03  # 候选集每缩小 10 倍，召回率下降的百分点（估）

print("文档总量 %s、向量 %d 维（%d B/维）" % (format(N_DOCS, ","), DIM, BYTES_PER_DIM))
print()
print("一、Post-filter：先 ANN 取 %d 条，再按 ACL 过滤" % ANN_N)
print("%-14s %18s %22s" % ("可见比例", "期望剩余条数", "够不够 Top-%d" % TOP_K))
for vis in (0.5, 0.1, 0.01, 0.001, 0.0001):
    left = ANN_N * vis
    print("%-14s %18.1f %22s" % ("%.2f%%" % (vis * 100), left, "够" if left >= TOP_K else "不够（要再放大 ANN_N）"))
print()
print("  -> post-filter 要凑够 %d 条，ANN_N 必须放大到 %d / 可见比例：" % (TOP_K, TOP_K))
for vis in (0.01, 0.001):
    print("     可见 %.2f%% -> ANN_N >= %s（而 ANN 的取数越多延迟越高）" % (vis * 100, format(int(TOP_K / vis), ",")))
print()
print("二、Pre-filter：先过滤再建图/搜索，召回率随候选集缩小而掉")
print("%-22s %14s %14s %22s" % ("阶段", "候选集", "召回率", "相对全量"))
stages = [
    ("全量 ANN", N_DOCS),
    ("ACL 过滤后", int(N_DOCS * 0.01)),
    ("+ BM25 粗排 80%", int(N_DOCS * 0.01 * 0.2)),
]
for name, n in stages:
    decades = math.log10(N_DOCS / n) if n < N_DOCS else 0.0
    recall = ANN_RECALL_FULL - RECALL_PER_DECADE * decades
    print("%-22s %14s %13.1f%% %21.1f%%" % (name, format(n, ","), recall * 100, (recall / ANN_RECALL_FULL) * 100))
print()
print("三、关键：权限过滤后，ANN 的前提（千万级）可能不成立")
print("%-16s %14s %16s %22s" % ("可见候选数", "扫描字节", "估算耗时", "与 ANN 比"))
for n in (1_000, 10_000, 100_000, 1_000_000):
    byts = n * DIM * BYTES_PER_DIM
    # 估算：10 GB/s 内存带宽
    ms = byts / 10e9 * 1000
    verdict = "精确搜索更快" if ms < 20 else "ANN 更划算"
    print("%-16s %14s %15.2f ms %22s" % (format(n, ","), "%.1f MB" % (byts / 1e6), ms, verdict))
print()
print("  => **当权限把候选集压到万级，暴力打分（精确）在毫秒级完成，比 ANN 的近似更快也更准**；")
print("     ANN 的价值前提是「候选集大到无法暴力」，权限过滤把这个前提吃掉了。")
print()
print("四、每用户权限位图的存储账")
for users in (1_000, 10_000, 100_000):
    bits = users * N_DOCS / 8
    print("  %7s 用户 x %s 文档的 BitSet = %7.1f GB" % (format(users, ","), format(N_DOCS, ","), bits / 1e9))
print("  -> 每用户 1 个 BitSet = %s B（1.25 MB）；10 万用户 = %s GB（可接受，但要按用户维度分片）"
      % (format(N_DOCS // 8, ","), format(100_000 * N_DOCS // 8 / 1e9, ".1f")))
print()
print("判据：")
print("  - **先看可见比例再选检索结构**：可见比例低于 0.1% 时 post-filter 必然不够用；")
print("  - **可见候选 <= 万级时用精确搜索**，别硬上 ANN；")
print("  - pre-filter 的代价是召回率：候选集每缩 10 倍掉 %d 个百分点（估），粗排 80%% + ACL 0.01%% 之后" % (RECALL_PER_DECADE * 100))
print("    召回率从 %.0f%% 掉到 %.0f%%（相对全量 %.0f%%）；" % (
    ANN_RECALL_FULL * 100,
    (ANN_RECALL_FULL - RECALL_PER_DECADE * math.log10(N_DOCS / (int(N_DOCS * 0.01 * 0.2)))) * 100,
    100 * (ANN_RECALL_FULL - RECALL_PER_DECADE * math.log10(N_DOCS / (int(N_DOCS * 0.01 * 0.2)))) / ANN_RECALL_FULL))
print("  - 所以笔记给的「粗排 -> ANN Top-500 -> 过滤 Top-50 -> rerank Top-10」是折中，不是最优解；")
print("    真正的最优解取决于可见比例与候选规模，要分别算。")
```

三处结论：

**第一，post-filter 在低可见比例下根本不够用。** ANN 取 Top-500 后按 ACL 过滤：可见比例 1% → 期望只剩 **5 条**（目标 Top-10 不够）；0.1% → 0.5 条；0.01% → 0.1 条。要凑够 10 条，可见 1% 需要 **ANN_N ≥ 1,000**、可见 0.1% 需要 **≥ 10,000**——而 ANN 取数越多延迟越高。**判据：先算可见比例，再决定检索结构**；企业级权限 RAG 的难点不在向量检索，在于「用户能看到的那部分有多小」。

**第二，pre-filter 的代价是召回率，而且能被算出来。** 候选集每缩小 10 倍召回率掉约 3 个百分点（估）：全量 1000 万 → **95%**；ACL 过滤到 10 万 → **89%**；再加 BM25 粗排去掉 80% → 2 万 → **87%**（相对全量 91%）。笔记给的四步漏斗把召回率压在这个量级——**它是折中，不是最优解**，最优解取决于可见比例与候选规模。

**第三，也是本篇最有用的一条：当权限把候选集压到万级，精确搜索比 ANN 更快也更准。** 768 维 float32 向量，扫描 1,000 条是 3.1 MB（**0.31 ms**）、10,000 条是 30.7 MB（**3.07 ms**）——按 10 GB/s 内存带宽估算，**毫秒级就能扫完**；而 ANN 的价值前提是「候选集大到无法暴力」。**权限过滤恰恰把这个前提吃掉了**：用户只可见 1% 文档时，暴力打分既精确（召回 100%）又快（3 ms）。判据：**可见候选 ≤ 万级用精确搜索，超过十万级才值得上 ANN**。

顺带一句权限位图的账：每用户一个 BitSet = 1000 万位 = **1.25 MB**；10 万用户 = **125 GB**（可接受，但要按用户维度分片）——这正是笔记说的「两阶段 join」在存储上的价码。

## 三、增量二：延迟预算是算术和还是均方根

笔记给的是逐阶段目标表与端到端 < 1.5 s (P95)。中间那一步——各阶段怎么加——最容易被搞错：

```python
"""延迟预算：串联系统的预算是算术和还是均方根？P95 怎么来。

用笔记的量：AEC+NS 10-20ms、VAD 20-50、ASR final 200-400、LLM TTFT 150-300、TTS TTFA 150-300、
网络 50-150，端到端 < 1.5s (P95)；TPOT 30-80ms/token。
只依赖标准库；输出确定性。
"""
import math

STAGES = (
    ("AEC + NS", 15, 5),
    ("VAD", 35, 10),
    ("ASR final", 300, 60),
    ("LLM TTFT", 225, 45),
    ("TTS TTFA", 225, 45),
    ("网络", 100, 30),
)
Z95 = 1.645

print("%-12s %10s %10s %14s %16s" % ("阶段", "目标中值", "波动σ", "P95(单阶段)", "含P95的累加"))
sum_p95 = 0.0
for name, mu, sd in STAGES:
    p95 = mu + Z95 * sd
    sum_p95 += p95
    print("%-12s %8d ms %8d ms %12.0f ms %14.0f ms" % (name, mu, sd, p95, sum_p95))
print()
print("算术和口径：各阶段都按自己的 P95 累加 = %.0f ms" % sum_p95)
rms_sigma = math.sqrt(sum(sd * sd for _, _, sd in STAGES))
mu_sum = sum(mu for _, mu, _ in STAGES)
p95_rms = mu_sum + Z95 * rms_sigma
print("均方根口径：波动互相独立时，端到端 P95 = Σμ + 1.645×√Σσ² = %.0f + %.0f = **%.0f ms**"
      % (mu_sum, Z95 * rms_sigma, p95_rms))
print("  -> 两种口径差 %.0f ms（%.0f%%）：**串联系统的延迟预算是「算术和」还是「均方根」，" % (sum_p95 - p95_rms, 100 * (sum_p95 - p95_rms) / p95_rms))
print("     取决于各阶段波动是否相关**（同一条链路上通常正相关 -> 取算术和这一侧）。")
print()
print("对照笔记的端到端目标 < 1500 ms (P95)：")
for name, total in (("算术和口径", sum_p95), ("均方根口径（波动独立）", p95_rms)):
    print("  %-22s %6.0f ms -> %s（余量 %.0f ms）" % (name, total, "达标" if total < 1500 else "超标", 1500 - total))
print()
print("流式输出改变的是「首个有效输出」的延迟，不是总时长：")
for tpot in (30, 50, 80):
    ttf = 225
    first_chunk = sum(mu for _, mu, _ in STAGES[:4]) + tpot   # 到首个音频 chunk
    print("  TPOT %2d ms/token -> 首个音频 chunk 约 %4d ms；完整 20 token 回复约 %4d ms"
          % (tpot, first_chunk, first_chunk + 19 * tpot))
print()
print("判据：")
print("  - **延迟预算是串联系统的算术和**（同链路的波动正相关时），别用 √Σσ² 自我安慰；")
print("    两个口径在本模型里差 %.0f ms（%.0f%%）。" % (sum_p95 - p95_rms, 100 * (sum_p95 - p95_rms) / p95_rms))
print("  - **流式只改善「首个有效输出」，不改善总时长**；但用户感知的是前者 —— 所以 ASR final 与")
print("    TTFT 是压缩重点，TTS 与网络各占 225/100 ms。")
print("  - **P95 不是各阶段 P95 的和**：它是最坏路径的组合，实际更接近「各阶段取 P95 且同时发生」；")
print("    所以端到端 SLO 要按这个更悲观的数定，%.0f ms。" % sum_p95)
```

输出：

```text

VAD                35 ms       10 ms           51 ms             75 ms
ASR final         300 ms       60 ms          399 ms            473 ms
LLM TTFT          225 ms       45 ms          299 ms            772 ms

    两个口径在本模型里差 168 ms（16%）。
  - **流式只改善「首个有效输出」，不改善总时长**；但用户感知的是前者 —— 所以 ASR final 与
    TTFT 是压缩重点，TTS 与网络各占 225/100 ms。
  - **P95 不是各阶段 P95 的和**：它是最坏路径的组合，实际更接近「各阶段取 P95 且同时发生」；
    所以端到端 SLO 要按这个更悲观的数定，1221 ms。
```

三处结论：

**第一，两种口径差 16%，而该取哪一侧取决于波动是否相关。** 各阶段按自己的 P95 累加 = **1,221 ms**；若各阶段波动互相独立，端到端 P95 = Σμ + 1.645×√Σσ² = **1,053 ms**。同一条语音链路上，各阶段往往**同时**受网络抖动影响（正相关）→ **该取算术和这一侧**。判据：**别用 √Σσ² 给自己省 168 ms 余量**。

**第二，端到端 P95 不是各阶段 P95 的和，而是「最坏路径的组合」。** 真正要定 SLO 的那个数是 1,221 ms——它离笔记的 1.5 s 只剩 **279 ms 余量**，而这 279 ms 要留给 GC、突发排队与网络抖动。

**第三，流式只改善「首个有效输出」，不改善总时长。** TPOT 30 / 50 / 80 ms/token 时，首个音频 chunk 分别在 **605 / 625 / 655 ms**，而完整 20 token 回复要 1,175 / 1,575 / **2,175 ms**。用户感知的是前者，所以**压缩重点是 ASR final（300 ms）与 TTFT（225 ms）**，TTS 与网络各占 225 / 100 ms；但 TPOT 决定的是「用户等多久才听完」，两者要分开定目标。

## 七、这三个模型判不了什么

- **可见比例 1%/0.1%、768 维、召回每十倍掉 3 个点、各阶段 σ、单请求成本、请求量、降级质量分都是估的**。真实企业里「用户可见比例」是**长尾分布**（大部分用户可见很少，少数用户可见很多）——**一个全局比例会同时对两种用户都不准**。
- **没算多租户下的隔离粒度**。笔记给的是「每用户 allowed_doc_ids BitSet + 两阶段 join」，但多租户若按**组织**授权，位图可以按组织共享，成本降一个量级；反过来，跨组织共享文档会让位图爆炸。**授权模型决定位图怎么存**，本文没展开。
- **没算召回率下降对下游的影响**。召回 95% → 87% 意味着 rerank 与 LLM 看到的候选变少，最终答案质量掉多少——**这一环取决于 rerank 的能力**，本文只算到检索层。
- **延迟模型假设各阶段延迟独立可加**，但没算**排队与背压**：TTFT 超时往往不是模型慢，而是队列排队（GPU batch 等待），此时「各阶段 σ」并不适用。**判据：延迟模型要分清「计算慢」与「排队慢」，两者的优化手段完全不同。**
- **降级模型没有把「用户可感知」量化**：L5 模板的质量 0.30 是我的赋值，实际影响取决于用户对该场景的容忍度——有的场景模板答案完全够用（查余额），有的场景一字都不能错（转账）。

## FAQ（八、常见问题）

**权限过滤下还能用 ANN 吗？** 看可见候选规模。可见 1% 时 post-filter 的 Top-500 只剩 **5 条**，不够 Top-10；而**候选压到万级时，暴力打分扫 10,000 条 768 维向量只要 3.07 ms**（按 10 GB/s 带宽），既精确（召回 100%）又快——**ANN 的价值前提「候选大到无法暴力」被权限吃掉了**。可见候选超过十万级才值得上 ANN。

**pre-filter 的代价是多少？** 召回率随候选集缩小而掉（估每缩 10 倍掉 3 个点）：1000 万全量 95% → ACL 过滤到 10 万 89% → 再粗排去掉 80% 到 2 万 **87%**。笔记的四步漏斗（粗排 → Top-500 → 过滤 Top-50 → rerank Top-10）是折中，不是最优解。

**端到端 P95 怎么加？** 各阶段按自己的 P95 **算术和** = 1,221 ms；若波动独立则是均方根口径 1,053 ms（差 16%）。同一条链路的波动通常正相关，**该取算术和这一侧**——离 1.5 s 只剩 279 ms 余量。

**流式输出能改善多少延迟？** 只改善首个有效输出：TPOT 30→80 ms/token 时首个音频 chunk 从 605→655 ms，而完整 20 token 回复从 1,175→**2,175 ms**。所以压缩重点是 ASR final（300 ms）与 TTFT（225 ms），TPOT 决定的是「听完要等多久」。

**降级链怎么排？** 按「质量损失 / 成本节省」：L3 备用厂商 0.95 质量 / 950 成本，L4 缓存 0.70 / 20，L5 模板 0.30 / 1。**能走 L3 就别掉 L4/L5**——每掉一级质量损失是非线性的。熔断打开时若 L3 只有 30% 可用，平均质量掉到 0.565。

**熔断开多久合适？** 窗口直接乘在误伤面上：千万级日请求、峰值 578 请求/秒下，**30 秒 = 17,361 个请求、60 秒 = 34,722 个请求**被降级，掉到 L5 的质量损失是掉到 L2 的 6 倍。所以要快开快关；另外**慢 ≠ 挂**——2% 的超时里有一半其实能出结果，只靠超时判定会误伤。
