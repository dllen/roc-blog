邻近服务怎么算？「找附近的店」这个需求背后有三个数：会扫多少家店、会扫多少格子、以及**刚改完的店多久能搜到**。讲义给了五种地理空间索引方案，但没给这三个数。这篇把它们算出来。

这篇不复述译文，也不搬运中文译本的任何段落。它复述这一章的骨架（两类服务、五种方案、粗略估算），然后补三个自写模型：**均匀网格下候选量与边长的真实关系**、**geohash 前缀长度对应的格子边长与扫描量**、**主从复制延迟如何变成一个用户可见的时间窗口**。

## 一、本章骨架：两类服务、五种方案、一条估算

**功能需求**：按用户位置（纬度经度）与搜索半径搜索商家；商家可新增/更新/删除（非实时）；请求时返回商家详情。

**非功能需求**：低延迟；遵守 GDPR / CCPA 的数据隐私要求；繁忙地点用餐高峰能扛住流量尖峰。

**粗略估算**：1 亿 DAU；系统里 2 亿商家；每人每天搜 5 次 → 搜索 QPS = (1 亿 × 5) / 86,400 ≈ **5,000**。

**API**：`GET /v1/search/nearby?latitude&longitude&radius`（默认半径 5000m）；商家详情 `GET /v1/businesses/{id}`；以及商家的新增、更新、删除。

**数据模型**：商家表 + 地理空间索引表；因为「搜附近」和「看详情」读量极大，用关系型数据库合适。

**两层服务**：**LBS**（处理位置搜索，读多写少、无写入请求、无状态，人口密集区用餐高峰 QPS 很高）与**商家服务**（处理商家增删改 + 顾客看详情）；负载均衡器把流量路由到两者；数据库用**主从架构**，讲义明确说 LBS 读到的数据可能与主库不一致，**「但这不是问题，因为商家信息不是实时更新的」**——这句话是本文第四节要量化的对象。

**五种方案**：

1. *朴素二维搜索*：用 SQL 的纬度/经度 BETWEEN 画一个矩形，扫全库；只能吃到一维索引的加速，很慢。
2. *更好的方法*：**地理空间索引**，把二维数据表示成一维。分两族——**哈希类**（均匀网格、Geohash）与**树类**（四叉树、Google S2、RTree）。
3. *均匀网格*：把世界切成固定大小的网格。问题是**商家分布不均匀**（城市密集、农村稀疏）。
4. *Geohash*：沿本初子午线和赤道把地球分四象限，再把每格四分，递归下去，用 base32 字符串编码。
5. *四叉树*与 *Google S2*：树类方案。

第 4 步讲数据库扩容与缓存策略，与地理索引是两条线，本文不碰。

## 二、增量一：均匀网格的候选量，与边长其实无关

讲义说均匀网格的毛病是「商家分布不均匀」。这可以算得更准一点：**在密度均匀的假设下，候选商家数与网格边长无关**。

```python
"""均匀网格方案：候选商家数与网格边长到底有没有关系。

讲义说均匀网格的缺点是「商家分布不均匀」。这里把候选量算出来。
只依赖标准库；输出确定性。
"""
RADIUS = 5000              # 讲义：默认搜索半径 5000m
BUSINESSES = 200_000_000   # 讲义：2 亿商家
EARTH_AREA = 5.1e14        # 地球表面积 m^2（估）

uniform_density = BUSINESSES / EARTH_AREA
print("讲义给的量：2 亿商家、平均搜索半径 %d m" % RADIUS)
print("地球表面积按 %.1e m^2 估 -> 全球平均密度 %.2e 家/m^2" % (EARTH_AREA, uniform_density))
print()
print("均匀网格下的候选量：")
print("  覆盖格数 = (2R/s)^2，每格商家数 = 密度 x s^2")
print("  => 候选 = (2R/s)^2 x 密度 x s^2 = 4R^2 x 密度  —— 与网格边长 s 无关")
for s in (250, 500, 1000, 2000):
    cells = (2 * RADIUS / s) ** 2
    per_cell = uniform_density * s * s
    cand = cells * per_cell
    print("  s=%5d m -> 覆盖 %8.0f 格，每格 %8.2f 家，候选 %8.1f 家" % (s, cells, per_cell, cand))
print()
print("  => 结论一：均匀网格下，**候选商家数只由半径与密度决定，缩小网格并不减少候选**；")
print("     网格边长的作用是「扫多少格」和「索引多大」，不是「看多少家店」。")
print()
print("但密度是不均匀的（讲义指出的正是这一点）：")
for factor, label in ((1, "全球平均"), (100, "市中心热点"), (1000, "超热点商场")):
    d = uniform_density * factor
    cand = 4 * RADIUS * RADIUS * d
    print("  %-12s（密度 x%4d）-> 5 km 内候选 %8.0f 家" % (label, factor, cand))
print()
print("  => 结论二：网格方案的真实成本由**局部密度上界**决定，不是平均值；")
print("     超热点区域候选量能到平均值的 1000 倍，这正是均匀网格在市中心的失效方式。")
print("     所以生产上要用密度自适应网格（quadtree / S2），而不是固定边长。")
```

两处结论：

**第一，缩小网格并不减少要比较的商家数。** 覆盖格数 =(2R/s)²，每格商家数 = 密度 × s²，两者相乘就是 **4R² × 密度**——s 被约掉了。脚本里 s=250 m 与 s=2000 m 的候选数都是 39.2 家，一模一样。所以网格边长的作用只有两个：**扫多少格**（(2R/s)²，随 s 变小而平方级增长）与**索引多大**（格子总数随 s 变小而平方级增长）。**「网格越细越准」在候选量上是错的**——细网格只是把同样的候选换了个地方找。

**第二，真正决定成本的是局部密度上界，而平均值会骗人。** 全球平均密度下 5 km 内只有 39 家店，看起来毫无压力；但市中心密度是平均的 100 倍 → **3,922 家**；超热点区域是 1000 倍 → **39,216 家**。这正是讲义说均匀网格「在市中心失效」的具体形态：不是格子边界算不准，而是**同一批格子里的商家数暴涨**。结论因此很直接：生产上要**密度自适应**的索引（四叉树、S2 这类树方案的意义就在这里），固定边长的网格只适合密度均匀的场景（比如仓库点位）。

## 三、增量二：geohash 前缀长度对应多大格子，要扫多少格

Geohash 之所以能当索引用，靠的是前缀性质：共享前缀 = 同一祖先区域，于是「查某前缀下的所有商家」就是一次等值范围扫描，在 B+ 树上就是普通范围查。那前缀要多长才够用？把位数分配算清楚：

```python
"""geohash：前缀长度与格子边长、搜索半径的关系。

geohash 是 base32 字符串，每加 1 位，区域面积缩小 32 倍。
只依赖标准库；输出确定性。
"""
RADIUS = 5000
B32 = "0123456789bcdefghjkmnpqrstuvwxyz"     # geohash 字符表

def lon_span(chars):
    """geohash 前 n 位对应的经度跨度（度）。

    每字符 5 bit，经纬度交替切分且从经度开始：n 个字符共 5n bit，
    经度拿 ceil(5n/2) 位、纬度拿 floor(5n/2) 位。
    """
    bits = 5 * chars
    lon_bits = (bits + 1) // 2
    return 360.0 / (2 ** lon_bits)

print("geohash 是 base32：每多 1 位，区域面积缩小 32 倍（经纬度各分一半 bit）")
print()
print("%-8s %14s %14s %16s %14s" % ("前缀长度", "经度跨度(度)", "纬度跨度(度)", "近似边长(m)", "查 5km 扫几格"))
for chars in (3, 4, 5, 6, 7, 8):
    lon = lon_span(chars)
    lat = lon * 0.87          # 高纬度附近经度跨度换算到地面距离的系数（估）
    edge_m = lon * 111320
    lat_edge = lat * 111320
    n = max(1, int((2 * RADIUS) // max(edge_m, 1)) + 1)
    print("%-8d %14.5f %14.5f %16.0f %14d" % (chars, lon, lat, edge_m, n * n))
print()
print("读法：")
print("  - 5 位 geohash 的格子约 %.1f km 见方，6 位约 %.1f km，7 位约 %.0f m；"
      % (lon_span(5) * 111320 / 1000, lon_span(6) * 111320 / 1000, lon_span(7) * 111320))
print("  - 查 5 km 半径时，格子必须比半径小很多，否则「一圈格子」会远大于目标圆；")
print("    而格子越小，需要扫的格子数按 1/s^2 涨 —— 这就是 geohash 精度与扫描量的权衡。")
print("  - geohash 的前缀性质（共享前缀 = 同一祖先区域）是它能当索引用的根本原因：")
print("    查询「以某前缀开头的所有商家」= 一个等值范围扫描，在 B+ 树索引上就是一次范围查。")
print()
print("讲义提到的两个坑，这里给它们算个数：")
print("  1. 边界问题：目标圆跨到相邻格子时，必须连查上下左右（甚至对角）的兄弟前缀；")
print("     格子边长越小，需要额外查的邻居格子占比越高。")
print("  2. 经纬度边界：geohash 用经纬度的二分网格，靠近极点时格子在地面上的实际面积会畸变，")
print("     同一前缀在赤道与在极地的覆盖面积差很多。")
```

读法：

- **标准表出来了**：5 位 geohash 的格子约 **4.9 km** 见方、6 位约 **1.2 km**、7 位约 **153 m**、8 位约 38 m。每多 1 位，区域面积缩小 32 倍（经纬度各拿一半 bit，交替切分且从经度开始，所以经度总是多拿一位）。
- **查 5 km 半径要扫多少格，由「格子边长 vs 半径」决定**：用 5 位格子（4.9 km）几乎覆盖了整个圆（9 格），但格子比半径还大，**扫到的候选会远多于目标圆内的真实商家**；用 6 位（1.2 km）要扫 81 格；用 7 位（153 m）要扫 4,356 格——**格子越准，扫的格数按 1/s² 涨**。这就是精度与扫描量的那条曲线，选定前缀长度就是在这条曲线上取点。
- **两个坑也有数**：目标圆跨格子时必须连查上下左右（甚至对角）的兄弟前缀，格子越小，这部分"额外扫的格子"占比越高；另外 geohash 是经纬度的二分网格，靠近极点时同一个前缀在地面上的实际面积会畸变——**同一个前缀在赤道和极地覆盖的地面范围差很多**。

## 四、增量三：「不一致没关系」这句话的量化形式

讲义说 LBS 读主从可能不一致，「但这不是问题，因为商家信息不是实时更新的」。这句话在工程上对应一个具体的数字：复制延迟。

```python
"""峰值 QPS、主从副本数，以及「读到旧数据」的容忍窗口。

只依赖标准库；输出确定性。
"""
DAU = 100_000_000
SEARCHES_PER_USER = 5
SECONDS_PER_DAY = 86_400
AVG_QPS = DAU * SEARCHES_PER_USER / SECONDS_PER_DAY
REPLICA_QPS = 5_000        # 单个只读副本承载的 QPS（假设）
LAG_P99_MS = 500           # 主从复制延迟 p99（假设）

print("讲义给的量：%d DAU、每人每天 %d 次搜索" % (DAU, SEARCHES_PER_USER))
print("  平均 QPS = (%d x %d) / %d = %.0f" % (DAU, SEARCHES_PER_USER, SECONDS_PER_DAY, AVG_QPS))
print()
print("峰值（用餐高峰按 10x 估）：%.0f QPS" % (AVG_QPS * 10))
print("  只读副本承载 %.0f QPS 的话，高峰需要 %d 个副本（低峰 %d 个）"
      % (REPLICA_QPS, int(AVG_QPS * 10 / REPLICA_QPS) + 1, int(AVG_QPS / REPLICA_QPS) + 1))
print()
print("一致性窗口：讲义说「LBS 读到的数据可能与主库不一致，但这不是问题，因为商家信息不是实时更新的」")
print("  这句话的量化形式：主从复制延迟 p99 = %d ms" % LAG_P99_MS)
print("  => 一个商家在 T 时刻更新，最坏情况下 T + %d ms 之前搜不到它" % LAG_P99_MS)
print("  => 高峰期 %.0f QPS 之下，这 %d ms 里最多有 %.0f 次搜索可能命中旧数据"
      % (AVG_QPS * 10, LAG_P99_MS, AVG_QPS * 10 * LAG_P99_MS / 1000.0))
print()
print("判据：")
print("  - 「不一致没关系」成立的前提是**业务能容忍这个窗口**（商家信息非实时更新，容忍度以分钟计）；")
print("  - 如果业务需要 read-after-write（刚改完地址立刻能搜到），就必须读主库或做会话亲和，")
print("    这时的成本是主库要扛住 %.0f QPS 的读 —— 于是「先写后搜」就成了一条独立的架构约束。" % (AVG_QPS * 10))
print("  - 隐私（非功能需求里的 GDPR/CCPA）与本节无关但常被忽略：搜索半径与位置上报都属于个人数据，")
print("    讲义没展开，落地时要单独设计脱敏与保留期。")
```

输出：

```text
  平均 QPS = (100000000 x 5) / 86400 = 5787

  这句话的量化形式：主从复制延迟 p99 = 500 ms
  => 一个商家在 T 时刻更新，最坏情况下 T + 500 ms 之前搜不到它
  => 高峰期 57870 QPS 之下，这 500 ms 里最多有 28935 次搜索可能命中旧数据

判据：
  - 「不一致没关系」成立的前提是**业务能容忍这个窗口**（商家信息非实时更新，容忍度以分钟计）；
  - 如果业务需要 read-after-write（刚改完地址立刻能搜到），就必须读主库或做会话亲和，
    这时的成本是主库要扛住 57870 QPS 的读 —— 于是「先写后搜」就成了一条独立的架构约束。
  - 隐私（非功能需求里的 GDPR/CCPA）与本节无关但常被忽略：搜索半径与位置上报都属于个人数据，
    讲义没展开，落地时要单独设计脱敏与保留期。
```

读法：

- **规模先算清楚**：平均 5,787 QPS，用餐高峰按 10 倍算 **57,870 QPS**；按单副本 5,000 QPS 估，高峰需要 12 个只读副本（低峰 2 个）。
- **一致性窗口 = 复制延迟**：主从延迟 p99 = 500 ms，意味着**一个商家在 T 时刻更新，最坏情况下 T+500 ms 之前搜不到它**；在高峰期 57,870 QPS 之下，这 500 ms 里最多有 **28,935 次搜索**可能命中旧数据。这就是「不一致没关系」的真正含义——**不是没有不一致，而是不一致窗口短到业务察觉不到**。
- **判据**：这句话成立的前提是业务能容忍这个窗口（商家信息非实时更新，容忍度以分钟计，500 ms 完全够）。**如果业务需要 read-after-write**（刚改完地址立刻要能搜到），就必须读主库或做会话亲和——那时主库要扛住 57,870 QPS 的读，「先写后搜」就变成一条独立的架构约束，而不是实现细节。
- 顺带：非功能需求里那条 GDPR/CCPA 与本节无关但常被忽略——**搜索半径与位置上报都属于个人数据**，讲义没展开，落地时要单独设计脱敏与保留期。

## 五、把三个模型套回本章（判据清单）

1. **别指望调网格边长来降候选量**：均匀网格的候选 = 4R² × 密度，与边长无关；密度不均才是真问题 → 用四叉树/S2 这类密度自适应结构。
2. **容量规划用局部密度上界，不用平均值**：热点区域候选量能到平均值的 1000 倍。
3. **geohash 前缀长度按「半径 ÷ 格子边长」推**：5 位格子 4.9 km 对 5 km 半径太粗，6 位 1.2 km 扫 81 格，7 位 153 m 扫 4356 格——按你要的精度和能接受的扫描量取点，并记得连查兄弟前缀。
4. **把「不一致没关系」翻译成时间窗口**：窗口 = 复制延迟 p99；业务容忍度（分钟级）> 窗口（毫秒级）才成立；要 read-after-write 就得换读路径。
5. **副本数按峰值算**：5,787 平均 QPS、57,870 峰值 QPS，单副本 5,000 QPS → 12 个副本起步。
6. **隐私单独立项**：位置与搜索半径都是个人数据，脱敏与保留期要单独设计。

## 七、这三个模型判不了什么

- **地球表面积、平均密度、热点倍数全是估的**。真实分布是幂律且高度相关（商场、景区、机场），「平均密度 × 1000」只是量级示意；要给容量，得用自己商圈的真实商家密度。
- **格子的形状与真实圆的关系被简化了**：脚本按正方形格子算覆盖格数，忽略了目标圆与格子相交的形状问题（真实实现里边界格子只取部分），所以「扫几格」是上界。
- **geohash 的经纬度跨度按赤道换算**，高纬度的地面距离与经度跨度的换算不同，表格里的米数在极地会偏小。
- **复制延迟、每副本 QPS 都是假设**。真实值随数据库实现、复制方式与负载变化；而且 p99 之外的尾部（网络抖动、主库切换）才是真正会咬人的部分。
- **三个模型都没算距离过滤的成本**。候选 39,216 家时要算 39,216 次 haversine（或用更便宜的近似），这本身是需要优化的热路径——讲义在方案一里提到要过滤，但没给过滤成本。

## FAQ（八、常见问题）

**网格切得越细，查得越准吗？** 候选量不降。均匀网格下候选 = 4R² × 密度，与边长无关（脚本里 s=250 m 与 s=2000 m 都是 39.2 家）。细网格只是把同样的候选换个地方找，同时让要扫的格子数按 1/s² 涨。真正的问题是密度不均——热点区域候选能到平均值的 1000 倍。

**geohash 用几位？** 按半径和格子边长推：5 位格子 4.9 km、6 位 1.2 km、7 位 153 m。查 5 km 半径时，6 位要扫 81 格、7 位要扫 4,356 格；格子比半径还粗时，扫到的候选会远多于圆内真实商家。另外别忘了跨格子时要连查兄弟前缀。

**为什么用四叉树/S2 不用均匀网格？** 因为它们按密度自适应：稀疏区格子大、密集区格子小。固定边长的网格在市中心会出现「同一批格子里塞了几万家店」的情况——这是讲义说均匀网格缺点时没展开的量级。

**主从不一致真的没关系吗？** 取决于业务容忍度。复制延迟 p99 = 500 ms 时，「刚更新的商家 500 ms 内搜不到」，而这 500 ms 里高峰可能有 28,935 次搜索命中旧数据——商家信息非实时更新时完全可接受；需要 read-after-write 时就得读主库，而主库要扛 57,870 QPS。

**这套系统要几个副本？** 峰值 57,870 QPS（平均 5,787 的 10 倍），单副本按 5,000 QPS 算 → 12 个只读副本，低峰 2 个。
