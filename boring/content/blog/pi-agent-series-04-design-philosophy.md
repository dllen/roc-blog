## Part 1：概念——Pi 的设计哲学全景

### 24% 这个数字

Pi 的完整代码库里，内核（`pi-ai` + `pi-agent-core`）只占 24%。剩下 76% 是产品层和外壳层——会话管理、130+ 工具、Prompt 组装、Extension 系统、三种 UI、Slack 适配、GPU 部署工具。

更精确地说，"真正的核心抽象"——StreamFunction、Context、Model 类型、agentLoop、Agent 类——总共不到 **3000 行**。

这个数字不是碰巧。它是"极简核心、能力外置"哲学的可量化证据。内核只做三件事：

1. **统一模型调用**——20+ 厂商，一个接口
2. **跑循环**——无状态双层循环 + 三阶段工具执行管线
3. **管状态**——有状态 Agent 外壳 + 事件订阅 + 消息队列

其余一切都在外面。

### 协议 vs 框架

Pi 的设计可以用一句话概括：

> **"Agent 系统的核心应该是一个协议（事件流 + 回调），而不是一个框架（内建的功能集）。"**

这个区别不是口头上讲的——它在每一行代码里：

| 你想做的事 | 框架方式 | Pi 的协议方式 | 区别在哪 |
|----------|---------|------------|---------|
| 加一个工具 | 继承基类 + `@Tool()` 装饰器 | 传一个符合 `AgentTool` 接口的对象 | 框架管理生命周期；协议把工具当数据结构 |
| 换压缩策略 | `setCompactionStrategy("summarize")` | 实现 `transformContext` 回调 | 框架预判你的需求；协议不预判任何东西 |
| 加权限控制 | 勾选"需要确认"配置项 | 实现 `beforeToolCall` 回调 | 框架假设一种交互模式；协议不假设 |

从代码分布看，`pi-ai` 有 ~27,000 行主要是 20+ 厂商各自的流式适配代码（每个厂商约 200-500 行）。**这才是内核真正大的东西——不是抽象多，而是真实世界的厂商差异多。**

### 四个反主流选择背后的统一原则

回顾第 3 篇的四件"不做的事"，现在可以给出每件的深层理由：

**1. 不做内建子 Agent。** 因为 `AgentLoop` 是一个无全局状态的可组合纯函数——在工具执行的内部启动另一个循环是完全安全的。子 Agent 作为一个普通工具，拿到了自己的消息列表、自己的回调、自己的停止条件。不需要新的抽象层。

**2. 不做内建 MCP。** 因为 Extension + Skill 的组合覆盖了 MCP 的场景但以不同的方式：不需要跨进程通信、不需要额外配置、不需要进程管理。Skill 是最轻的方式——纯 Markdown 注入 System Prompt，零运行时开销。

**3. 不做内建权限弹窗。** 因为安全策略与产品形态强耦合。CLI 需要同步终端确认、Slack 需要异步消息、CI/CD 需要零交互。内建弹窗假设一种交互模式——这个假设在产品形态多样化时立即失效。

**4. 不做内建 Plan Mode。** 因为 Plan Mode 只是在不同阶段注入不同指令——planning 阶段注入"只做计划"、executing 阶段注入"按计划执行"、reviewing 阶段注入"检查结果"。`transformContext` 已经能完成这个模式切换。内建 Plan Mode 会绑死确认方式——CLI 弹窗、Slack 消息、Web 弹窗——每种形式都需要不同的 UI。

### 内核的"不做"标准

Pi 有一个明确的判断标准——一个功能是否该进内核，要过三道关：

**1. 功能是否依赖产品形态？** 权限确认的方式因 CLI/Slack/Web 而不同 → 外置。工具执行的位置因本地/Docker 而不同 → 外置。输出渲染因 TUI/Markdown/HTML 而不同 → 外置。事件类型定义必须统一 → 内置。

**2. 是否有多种等价的实现方式？** 压缩策略各异（LLM 摘要 / 时间截断 / token 预算）→ 外置为 `transformContext` 回调。上下文变换有多种有效方法 → 外置为回调。消息的 LLM 格式因厂商而异 → 内置，在 Provider 层统一。

**3. 不一致是否产生不可预测的行为？** 事件类型定义必须统一 → 内置。工具执行的三阶段管线必须一致 → 内置。工具参数因场景而异 → 外置。

## Part 2：类比——乐高底板 vs 乐高套装

### 两种卖乐高的方式

想象两种卖乐高的策略：

- **乐高套装**：一个盒子，里面有 500 块积木和一本说明书。你照着搭，得到一辆完美的消防车。
- **乐高底板**：一块绿色底板，上面有均匀排列的凸起。没有任何说明书。你可以搭任何东西——消防车、城堡、飞船。

Pi 是一块乐高底板。LangChain 是一个乐高套装。

买乐高套装的人打开盒子就能开始。说明书是清楚的，结果是可预知的。代价是：如果你想搭的不是套装里的东西，你要么拆掉重来，要么买另一个套装。

买乐高底板的人面临一个完全不同的挑战：没有任何说明书。但他们可以搭任何东西，而且中途改主意不需要拆掉已有的一切——积木的组合方式是无限的。

| 乐高套装（框架） | 乐高底板（Pi 的协议式设计） |
|:--|:--|
| 开箱即用 | 需要自己组合 |
| 结果可预知 | 结果取决于你怎么组合 |
| 改了需求可能要拆掉重来 | 需求变了只需要调整组合方式 |
| 维护费在产品侧（买新套装） | 维护费在理解侧（搞懂怎么组合） |
| 适合：需求固定的单产品 | 适合：多变的多产品生态 |

### 什么时候不该用乐高底板

Pi 明确列出了自己的不适用场景：

- **只需要一个 LLM 调用的简单场景**——不需要完整运行时，用 Vercel AI SDK 或直接调 API
- **需要与现有企业基础设施深度集成的场景**——商业产品（如 Cursor）提供更完整的解决方案
- **多 Agent 协作是核心需求的场景**——CrewAI、AutoGen 和 OpenAI Agents SDK 是更好的起点
- **团队只有 1-2 人且不需要支持多种产品形态**——框架的开发效率远高于自己组合
- **需要开箱即用的 Agent 产品**——Claude Code 或 Cursor 是更直接的选择

## Part 3：全系列回顾 + 实践路线图

### 从零到一：搭建你的第一个 Pi-Style Agent

如果你想把 Pi 的设计理念应用到自己的 Agent 项目中，按这个顺序动手：

**第 1 步：从 Agent Loop 开始（~80 行）**
```typescript
// 一个最小循环，验证"发动机"能转
async function agentLoop(messages, tools, signal) {
  while (true) {
    const resp = await callLLM(messages, tools, signal);
    if (!resp.toolCalls) return resp.content;
    messages.push(resp);
    for (const tc of resp.toolCalls) {
      const result = await executeTool(tc);
      messages.push({ role: "tool", content: result });
    }
  }
}
```

**第 2 步：拆出 Provider 层（~50 行）**

把 `callLLM` 替换为一个可插拔的 Provider 接口。至少支持两家厂商（如 Anthropic + OpenAI），验证"换厂商不影响循环"。

**第 3 步：加入 `beforeToolCall` 钩子（~30 行）**

在工具执行前插入：检查工具名和参数 → block 或 allow。实现一个最简单的"危险命令检测"——匹配 `rm -rf /` 返回 block。

**第 4 步：加入 `transformContext` 钩子（~40 行）**

在调 LLM 前插入：控制 LLM 看到什么。先实现最简单的"Token 预算控制"——当消息历史超过 10000 token 时，将最早的消息替换为 "[早期对话已压缩]"。

**第 5 步：实现会话树（~100 行）**

用 JSONL + parentId 替代线性消息列表。实现分支和回退——在一个分支上做修改 C，退回到修改前的节点，另起一个分支做修改 D。

**第 6 步：搭产品外壳**

基于前 5 步的内核，选择你的产品形态：
- 终端应用 → 用 React Ink 或 Blessed 做 TUI
- Slack Bot → 用 Bolt SDK
- Web 界面 → 用 Express + WebSocket
- API 服务 → 用 Fastify

每走一步，你都在"选择要不要把一个功能变成内建"。"不做"始终是一个有效选项。

### 全系列四篇回顾

| 篇 | 主题 | 核心收获 |
|---|------|---------|
| 1 | Pi 是什么 | Agent 运行时处理的是"调完 LLM 之后发生什么"。四层洋葱 + 无状态 Loop = 多产品复用。 |
| 2 | 工具设计 | 给 LLM 设计工具就像给盲人设计菜单——结构化参数 + 精确约束 + 对 LLM 友好的错误信息。 |
| 3 | 能力外置 | 三个回调（execute / beforeToolCall / transformContext）组合出所有功能。不内建不是缺失，是更强的设计。 |
| 4 | 设计哲学 | 24% 代码驱动 100% 产品形态。协议胜于框架。知道什么时候不该用这种设计同样重要。 |

如果只记一句话，记住这个：

> **内核是协议（事件流 + 回调），不是框架（内建功能集）。极简核心的强大不在它做了什么，而在它允许产品层做什么。**

## 附录：Pi 与同类工具的定位差异

| 工具 | 核心定位 | 最适合 |
|------|---------|--------|
| **Pi** | 多产品 Agent 运行时 | 你需要同一份引擎驱动 CLI/Slack/Web 三种产品形态 |
| **Claude Code** | 单产品优化 | 你需要一个开箱即用的最强编程助手 |
| **Cursor / Windsurf** | IDE Agent | 你已经在 IDE 里工作，上下文天然丰富 |
| **Aider** | 垂直整合编辑 | 你只关心代码编辑效率和 diff 精度 |
| **LangChain** | LLM 调用编排 | 你需要快速串联 prompt + chain + agent 的完整工作流 |
| **CrewAI / AutoGen** | 多 Agent 编排 | 多 Agent 协作是你核心需求 |
