视频系统的三笔账？存多少、怎么转、怎么发。讲义给了架构与四条成本优化，但「存多少」「转多快」「发多贵」这三个最贵的乘数都停在定性。这篇把它们算成三个可跑的模型。

这篇不复述译文，也不搬运中文译本的任何段落。它复述这一章的骨架（七个组件、两条主流程、转码的 DAG 架构、三类优化），然后补三个自写模型：**转码的存储放大与按需转码**、**GOP 切分如何同时决定任务数与首帧延迟**、**分发成本对热度与码率的敏感度**。

## 一、本章骨架：七个组件、两条流程、一个 DAG

**关键统计（讲义标注 2020 年）**：20 亿月活、每天播放 50 亿个视频、37% 的移动互联网流量、支持 80 种语言、2019 年广告收入 151 亿美元。

**本章假设**：500 万 DAU；平均视频 300 MB；单视频上传上限 1 GB；每日存储需求 150 TB；CDN 成本按 `500 万 × 5 个视频 × 0.3 GB × $0.02 = $150,000/天` 估。

**七个组件**：客户端、CDN、API 服务器（处理除视频流外的所有交互）、元数据库、源存储（上传的原始 blob）、转码服务器、转码后存储。

**两条主流程**：

- *上传*：视频上传到 blob 存储 → 转码服务器转成多种格式 → 转码完成后**两件事并行**：转码后视频送去转码后存储 + 视频分发到 CDN；转码完成事件进完成队列 → 完成处理器更新元数据并通知用户。客户端并行发送元数据更新请求。
- *播放*：视频直接从 CDN 经边缘服务器流式传输，把延迟压到最小；流媒体协议有 MPEG-DASH、Apple HLS、Adobe HDS，**不同协议支持的编码与播放器各不相同**。

**转码为什么重要**（讲义三条）：原始视频占大量存储，转码能减少存储占用；保证各种设备与浏览器的兼容性；按网络状况自适应调整清晰度。

**DAG 模型**：转码计算开销大、耗时长，所以用有向无环图来编排——编码、缩略图生成、水印添加等任务并行展开。原始视频被拆成视频、音频、元数据三路。

**转码架构六个部件**：预处理器（按 GOP 对齐切片、把 GOP 与元数据存进临时存储以便失败重试）、DAG 调度器（把图拆成阶段任务）、资源管理器（三个队列：任务队列、工作节点队列、运行队列；外加一个挑最优任务/工作节点组合的调度器）、任务工作节点、临时存储、以及最终输出。

**三类优化**：速度（并行切块上传、用 CDN 当上传枢纽、消息队列解耦各模块）、安全（预签名 URL 限制上传者、DRM、AES 加密、水印）、成本（热门走 CDN、长尾从高容量服务器分发、很少被访问的视频按需编码、按热度做区域化分发、自建 CDN 配合 ISP）。

**错误处理**：可恢复错误重试（上传、转码、资源分配）；不可恢复错误（格式错误的视频）停止处理并返回错误码。

## 二、增量一：转码的存储放大，和按需转码能省多少

讲义说转码能「减少存储空间占用」，但同时又要求「转成多种分辨率和格式」——这两句在存储上是相反的方向。把它算出来：

```python
"""转码的存储放大：每个上传视频存几份，以及「按需转码」能省多少。

用讲义给的量：平均视频 300 MB、每日存储需求 150 TB。
只依赖标准库；输出确定性。
"""
AVG_MB = 300                # 讲义：平均视频大小
DAILY_TB = 150              # 讲义：每日存储需求
MINUTES = 10                # 估算用时长（讲义未给，取典型值）

# 码率阶梯（Mbps，估）
LADDER = [("360p", 0.8), ("480p", 1.4), ("720p", 3.0), ("1080p", 6.0), ("4K", 20.0)]
ORIGINAL_MBPS = 6.0         # 上传的原始视频按 1080p 码率估

def size_mb(mbps, minutes=MINUTES):
    return mbps * 60 * minutes / 8

uploads_per_day = DAILY_TB * 1e6 / AVG_MB
orig_mb = size_mb(ORIGINAL_MBPS)
ladder = [(name, size_mb(mbps)) for name, mbps in LADDER]
all_copies = sum(s for _, s in ladder)
print("讲义给的量：平均视频 %d MB、每日存储 %d TB -> 每天上传 %.0f 万个视频" % (AVG_MB, DAILY_TB, uploads_per_day / 1e4))
print("估算用时长 %d 分钟；原始视频按 %.1f Mbps 估 = %.0f MB" % (MINUTES, ORIGINAL_MBPS, orig_mb))
print()
print("%-8s %10s %14s" % ("清晰度", "体积(MB)", "占原始"))
for name, s in ladder:
    print("%-8s %10.0f %13.2fx" % (name, s, s / orig_mb))
print()
print("全档位存储放大：原始 %.0f MB + 各档 %.0f MB = %.0f MB，是原始的 %.1f 倍"
      % (orig_mb, all_copies, orig_mb + all_copies, (orig_mb + all_copies) / orig_mb))
daily_all = uploads_per_day * (orig_mb + all_copies)
daily_orig = uploads_per_day * orig_mb
print("每天 %d 万个视频全档位转码 -> %.0f TB/天；只存原始则 %.0f TB/天"
      % (uploads_per_day / 1e4, daily_all / 1e6, daily_orig / 1e6))
print()
HOT_SHARE = 0.05           # 热门视频占比（估）
HOT_VIEWS = 0.95           # 热门视频占播放量（估）
print("热度分层（热门 %d%% 的视频占 %d%% 播放，估）：" % (HOT_SHARE * 100, HOT_VIEWS * 100))
hot_mb = orig_mb + all_copies
cold_mb = orig_mb + dict(ladder)["720p"]
daily_mix = (uploads_per_day * HOT_SHARE * hot_mb +
             uploads_per_day * (1 - HOT_SHARE) * cold_mb)
print("  热门全档位 + 长尾只留 720p：%.0f TB/天（全档位是 %.0f TB/天，省 %.0f%%）"
      % (daily_mix / 1e6, daily_all / 1e6, 100.0 * (1 - daily_mix / daily_all)))
print("  完全不转码（只存原始，播放时再转）：%.0f TB/天" % (daily_orig / 1e6))
print()
print("判据：")
print("  - 存储放大是「清晰度档位数」的直接函数：档位越多，播放端体验越好，存储线性涨；")
print("  - 所以成本优化那节「对很少被访问的视频按需编码」不是省钱小技巧，而是主线策略——")
print("    把长尾视频的转码推迟到第一次被请求时；")
print("  - 转码服务器的成本同理：转码量与「被转码的视频数」成正比，按需转码让这部分接近播放量级别。")
```

输出：

```text
讲义给的量：平均视频 300 MB、每日存储 150 TB -> 每天上传 50 万个视频
估算用时长 10 分钟；原始视频按 6.0 Mbps 估 = 450 MB

清晰度          体积(MB)            占原始
360p             60          0.13x
480p            105          0.23x
720p            225          0.50x
1080p           450          1.00x
4K             1500          3.33x

全档位存储放大：原始 450 MB + 各档 2340 MB = 2790 MB，是原始的 6.2 倍
每天 50 万个视频全档位转码 -> 1395 TB/天；只存原始则 225 TB/天

热度分层（热门 5% 的视频占 95% 播放，估）：
  热门全档位 + 长尾只留 720p：390 TB/天（全档位是 1395 TB/天，省 72%）
  完全不转码（只存原始，播放时再转）：225 TB/天

判据：
  - 存储放大是「清晰度档位数」的直接函数：档位越多，播放端体验越好，存储线性涨；
  - 所以成本优化那节「对很少被访问的视频按需编码」不是省钱小技巧，而是主线策略——
    把长尾视频的转码推迟到第一次被请求时；
  - 转码服务器的成本同理：转码量与「被转码的视频数」成正比，按需转码让这部分接近播放量级别。
```

读法：

- **全档位转码的存储放大是 6.2 倍**：原始 450 MB，加上 360p/480p/720p/1080p/4K 五档共 2340 MB，合计 2790 MB。注意**低清晰度档位其实很小**（360p 只有原始的 0.13 倍），真正撑大存储的是 **4K 那一档（3.33 倍）**——如果产品不需要 4K，砍掉它立刻把放大倍数拉回 2.9。
- **按讲义的量，每天上传约 50 万个视频**（150 TB ÷ 300 MB）；全档位转码意味着**每天新增 1395 TB** 的转码后存储，只存原始是 225 TB。
- **热度分层把这件事变成主线策略**：热门 5% 的视频占 95% 播放，热门全档位 + 长尾只留 720p，存储从 1395 TB/天降到 **390 TB/天（省 72%）**；完全不预转码（只存原始、第一次被请求时再转）是 225 TB/天。讲义成本优化那节的「对很少被访问的视频按需编码」不是省钱小技巧，而是**把长尾视频的转码推迟到第一次被请求时**——顺带把转码服务器的计算量也压到接近播放量级别。
- **判据**：存储放大是「清晰度档位数」的直接函数。档位越多，播放端体验越好（弱网下也能降档），存储与转码成本线性涨。所以档位表是一次**产品 × 成本**的联合决策，不是技术选择：**先看你的观众有多少在弱网/小屏上，再决定要不要留低档**；反过来，4K 这类高档位通常是存储账单里最贵的一行。

## 三、增量二：GOP 切分如何同时决定任务数与首帧延迟

讲义说预处理器按 GOP 对齐切片、DAG 调度器分阶段、资源管理器管三个队列。这三件事连在一起的效果，可以写成两个式子：

```python
"""GOP 切分：任务数与首帧延迟怎么算。

讲义说预处理器按 GOP 对齐切片、DAG 调度器分阶段；这里把两件事变成可算的式子。
只依赖标准库；输出确定性。
"""
MINUTES = 10
SECONDS = MINUTES * 60
DURATIONS = 3.0             # 720p 目标码率 Mbps（估）
SPEEDUP = 30                # 转码速度 = 30x 实时（估，常见量级）
RENDITIONS = 5              # 清晰度档位数

print("估算：%d 分钟视频，720p %.1f Mbps，转码速度 %dx 实时，清晰度 %d 档"
      % (MINUTES, DURATIONS, SPEEDUP, RENDITIONS))
full_seconds = SECONDS / SPEEDUP
print("整片转码耗时 = %d 秒 / %d = %.1f 秒（不切 GOP 的话，用户要等这么久才能播）"
      % (SECONDS, SPEEDUP, full_seconds))
print()
print("%-8s %12s %14s %14s %12s" % ("GOP 长度", "GOP 数", "任务数(全档位)", "首帧延迟(秒)", "相对整片"))
for g in (0.5, 1, 2, 4, 8):
    gops = SECONDS / g
    tasks = gops * RENDITIONS
    first_frame = g / SPEEDUP
    print("%-8s %12.0f %14.0f %14.3f %11.1fx" % (g, gops, tasks, first_frame, full_seconds / first_frame))
print()
print("读法：")
print("  - 任务数 = (视频秒数 / GOP 长度) x 清晰度档位数：10 分钟视频、2 秒 GOP、5 档 = %.0f 个任务；"
      % (SECONDS / 2 * RENDITIONS))
print("    所以 GOP 越短、档位越多，调度器与资源管理器的队列压力越大（讲义那三个队列就是为此）。")
print("  - 首帧延迟 ≈ GOP 时长 / 转码倍数：GOP 2 秒、30x 实时 -> %.3f 秒，相对「等整片」快 %.0f 倍。"
      % (2 / SPEEDUP, full_seconds / (2 / SPEEDUP)))
print("  - GOP 长 -> 任务少、首帧慢；GOP 短 -> 首帧快、任务多。这是一条要自己权衡的曲线，不是免费加速。")
print("  - 注意 GOP 长度受编码器约束（H.264 常用 2 秒），不是纯工程参数；")
print("    真正的可调项是「档位数」与「转码倍数」，前者影响存储与任务数，后者影响首帧延迟。")
```

输出：

```text
估算：10 分钟视频，720p 3.0 Mbps，转码速度 30x 实时，清晰度 5 档
整片转码耗时 = 600 秒 / 30 = 20.0 秒（不切 GOP 的话，用户要等这么久才能播）

GOP 长度          GOP 数       任务数(全档位)        首帧延迟(秒)         相对整片
0.5              1200           6000          0.017      1200.0x
1                 600           3000          0.033       600.0x
2                 300           1500          0.067       300.0x
4                 150            750          0.133       150.0x
8                  75            375          0.267        75.0x

读法：
  - 任务数 = (视频秒数 / GOP 长度) x 清晰度档位数：10 分钟视频、2 秒 GOP、5 档 = 1500 个任务；
    所以 GOP 越短、档位越多，调度器与资源管理器的队列压力越大（讲义那三个队列就是为此）。
  - 首帧延迟 ≈ GOP 时长 / 转码倍数：GOP 2 秒、30x 实时 -> 0.067 秒，相对「等整片」快 300 倍。
  - GOP 长 -> 任务少、首帧慢；GOP 短 -> 首帧快、任务多。这是一条要自己权衡的曲线，不是免费加速。
  - 注意 GOP 长度受编码器约束（H.264 常用 2 秒），不是纯工程参数；
    真正的可调项是「档位数」与「转码倍数」，前者影响存储与任务数，后者影响首帧延迟。
```

读法：

- **任务数 = (视频秒数 ÷ GOP 长度) × 清晰度档位数。** 10 分钟视频、2 秒 GOP、5 档 = **1500 个任务**。这就是讲义为什么要「资源管理器 + 三个队列 + 一个挑最优任务/工作节点组合的调度器」——因为每个上传视频会产生上千个任务，队列压力按视频数 × 档位数 × (时长/GOP) 放大。
- **首帧延迟 ≈ GOP 时长 ÷ 转码倍数。** 2 秒 GOP、30 倍速转码 → **0.067 秒**；相比「等整片转完」的 20 秒，快 300 倍。这就是 GOP 切片存在的全部理由：**让第一个片段先转完就能播**。
- **但这是一条要权衡的曲线，不是免费加速**：GOP 0.5 秒 → 首帧 0.017 秒，但任务数翻到 6000；GOP 8 秒 → 任务数降到 375，首帧却要 0.267 秒。**GOP 短换来首帧快、代价是队列压力；GOP 长反过来。**
- **而且 GOP 长度不是纯工程参数**：它受编码器约束（H.264 常用 2 秒），所以真正可调的是**档位数**与**转码倍数**——前者同时影响存储、任务数与首帧延迟，后者只影响延迟。要提速先看这两个，而不是去动 GOP。

## 四、增量三：分发成本，以及一个口径提醒

讲义给的 CDN 成本算式是 `500 万 × 5 个视频 × 0.3 GB × $0.02 = $150,000/天`。先核对它，再看它对热度与码率的敏感度：

```python
"""分发成本：核对讲义的算式，看它对热度与码率的敏感度。

只依赖标准库；输出确定性。
"""
DAU = 5_000_000
VIDEOS_PER_USER_PER_DAY = 5
AVG_GB = 0.3
CDN_PRICE = 0.02            # $/GB（讲义给）
ORIGIN_PRICE = 0.005        # 源站出网 $/GB（假设：规模议价后低于 CDN 单价）
DAILY_VIEWS_REAL = 5_000_000_000   # 讲义「关键统计」：每天播放 50 亿次（2020 年真实规模）

views = DAU * VIDEOS_PER_USER_PER_DAY
traffic_pb = views * AVG_GB / 1e6              # GB -> PB
cost = views * AVG_GB * CDN_PRICE

print("讲义的算式：%d DAU x %d 个视频 x %.1f GB x $%.3f = $%.0f/天"
      % (DAU, VIDEOS_PER_USER_PER_DAY, AVG_GB, CDN_PRICE, cost))
print("倒推：每天 %.0f 万次播放 -> 出网 %.2f PB/天；%.2f PB x $%.3f/GB = $%.0f/天（算式自洽）"
      % (views / 1e4, traffic_pb, traffic_pb, CDN_PRICE, traffic_pb * 1e6 * CDN_PRICE))
print()
ratio = DAILY_VIEWS_REAL / views
print("口径提醒：讲义「关键统计」写的是 2020 年真实 YouTube 每天播放 %d 亿次，本章假设只有 %.0f 万次 —— 差 %.0f 倍。"
      % (DAILY_VIEWS_REAL / 1e8, views / 1e4, ratio))
print("  所以本章的 $%.0f/天 不是真实平台的成本；同一算式套到真实规模是 $%.0f/天。" % (cost, DAILY_VIEWS_REAL * AVG_GB * CDN_PRICE))
print("  用自己的规模重算，别把章节里的成本数字当行业数字。")
print()
print("码率档位对成本的影响（同样 10 分钟播放一次）：")
for name, mbps in (("360p", 0.8), ("720p", 3.0), ("1080p", 6.0), ("4K", 20.0)):
    gb = mbps * 600 / 8 / 1024
    print("  %-6s %5.1f Mbps -> %5.2f GB/次，CDN 成本 $%.4f/次" % (name, mbps, gb, gb * CDN_PRICE))
gb_360 = 0.8 * 600 / 8 / 1024
gb_4k = 20.0 * 600 / 8 / 1024
```

## 五、把三个模型套回本章（判据清单）

1. **档位表当成本决策做**：存储放大 = 原始 + Σ 各档（4K 一档就能撑到 3.3 倍）；先看有没有人真的看 4K，再决定留不留。
2. **长尾按需转码**：热门全档位 + 长尾只留一档（720p 够用），存储实测省 72%，转码计算量同步下降。
3. **GOP 是权衡不是优化**：任务数 = 时长 ÷ GOP × 档位数；首帧延迟 ≈ GOP ÷ 转码倍数。提速优先调档位数与转码倍数，GOP 受编码器约束。
4. **成本公式三个乘数逐个盯**：播放量（产品）、单次体积（清晰度策略）、单价（分发方式）；任何一条成本优化都要落到其中一个乘数上才说得清。
5. **区分「本章假设」与「行业现实」**：讲义关键统计与本章假设差 200 倍，所有成本数字按自己的规模重算。
6. **热门走 CDN 的前提是源站更便宜**，不是源站更近；议价拿不到就都走 CDN。

## 七、这三个模型判不了什么

- **码率阶梯、时长、转码倍数都是估的**。真实码率随内容类型变化（静态录屏 vs 高速运动），真实转码倍数取决于机型与编码器；把这些换成实测值，结论的量级不变但数字会动。
- **节点模型假设「热门 5% 占 95% 播放」**。真实观看分布是幂律，头部集中度更高时，热门分层的收益更大；反过来，若内容分布均匀，分层就没什么用。
- **GOP 与首帧延迟的关系忽略了排队**。首帧延迟 = GOP ÷ 转码倍数 **+ 队列等待**；上传高峰期排队可能远大于 GOP 本身，这时加机器比调 GOP 有效。
- **没算「转码后的分发存储」**。转码后存储 + CDN 缓存里的副本，是存储账的另一半，而这部分与「档位数 × 分段数」相乘，量级可以超过转码后存储本身。
- **成本模型假设单价固定**。真实 CDN 有阶梯折扣、跨区流量费与回源费；$0.02/GB 只是量级锚点。

## FAQ（八、常见问题）

**转码到底要不要全档位？** 看清晰度策略的成本：全档位把每个视频的存储放大到 6.2 倍（4K 一档就占 3.3 倍）。热门全档位 + 长尾只留一档，存储实测省 72%——所以全档位应该只给热门，按需转码给长尾。

**GOP 切多细合适？** 它是权衡：任务数 = 时长 ÷ GOP × 档位数，首帧延迟 ≈ GOP ÷ 转码倍数。2 秒 GOP、5 档时每个视频 1500 个任务、首帧 0.067 秒。但 GOP 受编码器约束（H.264 常用 2 秒），真正该调的是档位数与转码倍数。

**首帧延迟怎么压？** 先看两件事：转码倍数（机器与编码器）和队列等待。GOP 带来的部分只是 GOP ÷ 转码倍数；上传高峰期排队往往更大，那要靠加 worker。

**CDN 成本怎么算？** 播放量 × 单次平均体积 × 单价。讲义的算式（500 万 DAU × 5 × 0.3 GB × $0.02 = $150,000/天）自洽，但它对应的假设规模比讲义自己列的 2020 年真实统计小 200 倍——真实规模套同一算式是 $30,000,000/天。

**热门走 CDN、长尾走源站省不省？** 取决于源站单价是否低于 CDN。本例假设源站 $0.005/GB vs CDN $0.02，长尾走源站省 $5,625/天；议价拿不到这个价时，长尾也该走 CDN。真正的理由不是「源站更近」（长尾观众本来就分散），是单价。
