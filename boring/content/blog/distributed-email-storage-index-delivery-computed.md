## 一、本章骨架：10 亿用户、10 万封/秒、七个组件

**需求问答**：10 亿用户；功能是鉴权、发送/接收邮件、获取邮件、过滤、搜索、反垃圾保护；**本题用 HTTP 而非 SMTP/POP/IMAP**（讲义说这是为了灵活与可扩展）；**支持附件**。

**非功能需求**：可靠性（不能丢数据）、可用性（用副本防单点故障，容忍部分故障）、可扩展性、灵活性与可扩展性。

**讲义的估算**：**10 亿用户，每人每天发 10 封 → 每秒 10 万封**；每人每天收 40 封、每封元数据 50 KB → **每年 730 PB 存储**；**20% 的邮件有附件、平均 500 KB → 每年 1,460 PB**。

**邮件知识 101**：SMTP 是服务器间发送协议，POP 取回后从服务器删除，IMAP 保留在服务器端，HTTPS 用于 Web 客户端；**MX 记录**用于把域名指向邮件服务器；**附件以 base64 编码传输，通常有 25 MB 上限**。

**传统邮件服务器**：邮件存在本地文件系统、每封一个文件，规模上去后**磁盘 I/O 成瓶颈**，也不满足高可用要求（磁盘会坏、服务器会宕）。

**分布式邮件服务器（讲义的高层设计）**：Webmail、**Web 服务器**、**实时服务器**（WebSocket 推新邮件，老浏览器回退长轮询）、**元数据数据库**（主题、正文、发件人、收件人）、**附件存储**（对象存储如 S3）、**分布式缓存**（Redis 缓存最近邮件）、**搜索存储**（分布式文档存储做全文搜索）。

**发送流程**：负载均衡器限流并路由 → Web 服务器做基本校验与垃圾检查 → 进消息队列（附件以引用形式指向对象存储）→ **SMTP 外发 worker** 从外发队列拉取、做垃圾/病毒检查并路由到目标服务器 → 存进「已发送邮件」文件夹。**队列过大有两种原因**：收件服务器不可用（用指数退避重试）或消费者不足（扩消费者）——所以**外发队列大小必须监控**。

**接收流程**：SMTP 负载均衡器 → SMTP 服务器执行接收策略（无效邮件直接丢弃）→ **附件过大就放对象存储** → 处理 worker 做初步检查 → 转发到存储、缓存、对象存储和实时服务器；离线用户上线后通过 HTTP API 拉取。

**送达率**：讲义说「搭建发送服务器容易，让邮件到达收件箱很难」，措施包括**专用 IP**、**营销邮件与交易邮件分开**、**IP 预热 2–6 周**、**快速封禁垃圾邮件发送者**、**反馈循环**、**SPF/DKIM 认证**。

**搜索**：邮件搜索**局限于用户自己的邮箱**，且**写多于读**（每次操作都要重新索引，用户很少用搜索标签页）；对比 Google 搜索——范围是整个互联网、按相关性排序、索引需要时间，邮件搜索是按时间等属性排序、索引要快且准。方案两条：**Elasticsearch**（用 `user_id` 做分区键，变更经 Kafka 异步做以解耦服务与重建索引）或**自建**（用 LSM 组织磁盘上的索引，写路径只做顺序写；核心思想是数据先留在内存，达到阈值再合并到下一层）。

## 二、增量一：存储构成、保留期与 base64 的 33%

讲义给了两个存储数字（730 PB 元数据、1,460 PB 附件）和一条 25 MB 附件上限。把它们放一起算：

```python
"""邮件存储账：元数据 730 PB、附件 1,460 PB，留存期与 base64 是唯二杠杆。

用讲义给的量：10 亿用户、每天收 40 封、元数据 50 KB、20% 有附件、附件 500 KB、附件上限 25 MB。
只依赖标准库；输出确定性。
"""
USERS = 1_000_000_000
RECV_PER_DAY = 40
META_KB = 50
ATTACH_SHARE = 0.20
ATTACH_KB = 500
ATTACH_LIMIT_MB = 25
BASE64_BLOWUP = 4 / 3.0

recv_day = USERS * RECV_PER_DAY
meta_pb_day = recv_day * META_KB * 1024 / 1e15
att_pb_day = recv_day * ATTACH_SHARE * ATTACH_KB * 1024 / 1e15
print("收信：%s 封/天 = %s 封/秒（讲义：发信 10 万封/秒）"
      % (format(recv_day, ","), format(int(recv_day / 86400), ",")))
print("  元数据 %d KB/封 -> %.2f PB/天 = %.0f PB/年（讲义 730 PB）" % (META_KB, meta_pb_day, meta_pb_day * 365))
print("  附件 %d%% x %d KB -> %.2f PB/天 = %.0f PB/年（讲义 1,460 PB）" % (ATTACH_SHARE * 100, ATTACH_KB, att_pb_day, att_pb_day * 365))
print()
total = (meta_pb_day + att_pb_day) * 365
print("两者合计 %.0f PB/年；附件占 %.0f%%" % (total, 100 * att_pb_day / (meta_pb_day + att_pb_day)))
print("  -> 如果把附件也放进元数据库，数据库要 %.0f PB/年；讲义把附件放对象存储是对的。" % total)
print()
print("保留期是最大的杠杆（到达率不可控：用户收多少封不由你定）：")
for days in (30, 90, 180, 365):
    pb = (meta_pb_day + att_pb_day) * days
    print("  保留 %3d 天 -> %6.0f PB（全年口径的 %.0f%%）" % (days, pb, 100 * days / 365))
print()
print("base64 膨胀 %.0f%%：附件 base64 编码后再传输/存储" % ((BASE64_BLOWUP - 1) * 100))
print("  %d KB 附件 -> %.0f KB（+%.0f KB）" % (ATTACH_KB, ATTACH_KB * BASE64_BLOWUP, ATTACH_KB * (BASE64_BLOWUP - 1)))
limit_raw = ATTACH_LIMIT_MB / BASE64_BLOWUP
print("  上限 %d MB：若按**编码后**尺寸卡，原始附件只能到 %.2f MB；若按原始尺寸卡，编码后是 %.1f MB（超限）"
      % (ATTACH_LIMIT_MB, limit_raw, ATTACH_LIMIT_MB * BASE64_BLOWUP))
print()
print("判据：")
print("  - 存储预算 = 到达率 x 保留期 x 单封大小；到达率不可控、保留期可控 -> **先定保留期**；")
print("    保留 90 天比 365 天省掉 %.0f PB。" % ((meta_pb_day + att_pb_day) * 275))
print("  - 大字段（附件、正文）不进关系库：附件占 %.0f%% 的量。" % (100 * att_pb_day / (meta_pb_day + att_pb_day)))
print("  - base64 的 %.0f%% 膨胀必须体现在**尺寸限制**上：讲义说附件上限 25 MB，" % ((BASE64_BLOWUP - 1) * 100))
print("    那要问清是编码前还是编码后 —— 两者的可用原始容量差 %.1f MB。" % (ATTACH_LIMIT_MB - limit_raw))
```

输出：

```text
收信：40,000,000,000 封/天 = 462,962 封/秒（讲义：发信 10 万封/秒）
  元数据 50 KB/封 -> 2.05 PB/天 = 748 PB/年（讲义 730 PB）
  附件 20% x 500 KB -> 4.10 PB/天 = 1495 PB/年（讲义 1,460 PB）

两者合计 2243 PB/年；附件占 67%
  -> 如果把附件也放进元数据库，数据库要 2243 PB/年；讲义把附件放对象存储是对的。

保留期是最大的杠杆（到达率不可控：用户收多少封不由你定）：
  保留  30 天 ->    184 PB（全年口径的 8%）
  保留  90 天 ->    553 PB（全年口径的 25%）
  保留 180 天 ->   1106 PB（全年口径的 49%）
  保留 365 天 ->   2243 PB（全年口径的 100%）

base64 膨胀 33%：附件 base64 编码后再传输/存储
  500 KB 附件 -> 667 KB（+167 KB）
  上限 25 MB：若按**编码后**尺寸卡，原始附件只能到 18.75 MB；若按原始尺寸卡，编码后是 33.3 MB（超限）

判据：
  - 存储预算 = 到达率 x 保留期 x 单封大小；到达率不可控、保留期可控 -> **先定保留期**；
    保留 90 天比 365 天省掉 1690 PB。
  - 大字段（附件、正文）不进关系库：附件占 67% 的量。
  - base64 的 33% 膨胀必须体现在**尺寸限制**上：讲义说附件上限 25 MB，
    那要问清是编码前还是编码后 —— 两者的可用原始容量差 6.2 MB。
```

三处结论：

**第一，附件占 2/3 的量，所以「附件不能进元数据库」不是洁癖而是算术。** 按讲义参数复算：元数据 **748 PB/年**、附件 **1,495 PB/年**，合计 2,243 PB——**附件占 67%**。讲义把附件放对象存储、元数据库只存引用，省下的不是「一点空间」，而是三分之二的量级。

**第二，保留期是最大的杠杆，因为到达率不可控。** 用户一天收 40 封还是 80 封不由系统决定；但**保留多久由你决定**：保留 30 天 = 184 PB、90 天 = 553 PB、180 天 = 1,106 PB、365 天 = 2,243 PB。**保留 90 天比保留一年省下 1,690 PB**。判据：**存储预算 = 到达率 × 保留期 × 单封大小，其中只有保留期在你手里**——所以保留期是最先要定的参数，而不是最后优化的对象。

**第三，base64 的 33% 膨胀必须体现在尺寸限制上。** 500 KB 附件编码后是 667 KB。讲义说附件上限 25 MB——**但要问清是编码前还是编码后**：按编码后卡，原始附件只能到 **18.75 MB**；按原始尺寸卡，编码后是 33.3 MB，会超限。两个口径差了 **6.25 MB**，而这个差最后会变成用户侧「为什么我的 20 MB 附件传不上去」。

## 三、增量二：索引的写读比 40,000:1

讲义说邮件搜索「写多于读，用户很少用搜索标签页」，并给出 ES 与自建 LSM 两条路。把这个「多」量化：

```python
"""邮件搜索的写读比：写比读高几个数量级。

用讲义给的量：10 亿用户、每天收 40 封、搜索「写多于读，用户很少用搜索标签页」、ES + Kafka 异步索引或自建 LSM。
只依赖标准库；输出确定性。
"""
USERS = 1_000_000_000
RECV_PER_DAY = 40
SEARCH_USERS_SHARE = 0.001    # 每天真正搜一次的用户比例（估）
INDEX_RATIO = 0.20            # 索引大小 / 元数据大小（估）
LSM_WRITE_AMP = 10            # LSM 写放大（估）

recv_day = USERS * RECV_PER_DAY
index_writes = recv_day
search_qps = USERS * SEARCH_USERS_SHARE / 86400
print("索引写：每封邮件都要进一次索引 -> %s 次/天 = %s 次/秒" % (format(index_writes, ","), format(int(index_writes / 86400), ",")))
print("搜索读：%.1f%% 用户每天搜一次 -> %.0f 次/天 = %.1f 次/秒" % (SEARCH_USERS_SHARE * 100, USERS * SEARCH_USERS_SHARE, search_qps))
print("  => 写:读 = %d : 1" % int(index_writes / (USERS * SEARCH_USERS_SHARE)))
print()
print("这正是讲义说「要针对写多的工作负载优化」的原因：")
print("  - ES 路线：用 Kafka 把变更与索引解耦（异步、可回放）")
print("  - 自建路线：LSM 把磁盘上的索引组织成分层结构，写路径只做顺序写")
print()
meta_pb_day = recv_day * 50 * 1024 / 1e15
index_pb_day = meta_pb_day * INDEX_RATIO
print("索引量：元数据 %.2f PB/天 x %.0f%% -> %.2f PB/天 = %.0f PB/年"
      % (meta_pb_day, INDEX_RATIO * 100, index_pb_day, index_pb_day * 365))
print()
print("LSM 的代价在 compaction（写放大）：")
for amp in (5, 10, 20):
    write_pb_day = index_pb_day * amp
    gb_s = write_pb_day * 1e15 / 86400 / 1e9
    disks = gb_s / 0.2 * 1.2
    print("  写放大 %2d x -> 实际落盘 %.2f PB/天 = %.0f GB/s 顺序写 -> 按 200 MB/s/盘（+20%% 余量）算需要 %s 块盘"
          % (amp, write_pb_day, gb_s, format(int(disks), ",")))
print()
print("判据：")
print("  - **写:读 %d:1 意味着索引不能按「查询快」来优化，要按「写入吞吐」来优化**；" % int(index_writes / (USERS * SEARCH_USERS_SHARE)))
print("    讲义给的三个方向（ES+Kafka / 自建 LSM / 数据存储本身兼做搜索）正是这条约束下的选择题。")
print("  - LSM 让写变顺序，但把成本搬到 compaction：写放大 %d x 时每天落盘 %.2f PB，" % (LSM_WRITE_AMP, index_pb_day * LSM_WRITE_AMP))
print("    相当于每秒 %.0f GB 的顺序写 —— 这是自建方案的真实门槛，不是「用 LSM 就快了」。" % (index_pb_day * LSM_WRITE_AMP * 1e15 / 86400 / 1e9))
```

输出：

```text
索引写：每封邮件都要进一次索引 -> 40,000,000,000 次/天 = 462,962 次/秒
搜索读：0.1% 用户每天搜一次 -> 1000000 次/天 = 11.6 次/秒
  => 写:读 = 40000 : 1

这正是讲义说「要针对写多的工作负载优化」的原因：
  - ES 路线：用 Kafka 把变更与索引解耦（异步、可回放）
  - 自建路线：LSM 把磁盘上的索引组织成分层结构，写路径只做顺序写

索引量：元数据 2.05 PB/天 x 20% -> 0.41 PB/天 = 150 PB/年

LSM 的代价在 compaction（写放大）：
  写放大  5 x -> 实际落盘 2.05 PB/天 = 24 GB/s 顺序写 -> 按 200 MB/s/盘（+20% 余量）算需要 142 块盘
  写放大 10 x -> 实际落盘 4.10 PB/天 = 47 GB/s 顺序写 -> 按 200 MB/s/盘（+20% 余量）算需要 284 块盘
  写放大 20 x -> 实际落盘 8.19 PB/天 = 95 GB/s 顺序写 -> 按 200 MB/s/盘（+20% 余量）算需要 568 块盘

判据：
  - **写:读 40000:1 意味着索引不能按「查询快」来优化，要按「写入吞吐」来优化**；
    讲义给的三个方向（ES+Kafka / 自建 LSM / 数据存储本身兼做搜索）正是这条约束下的选择题。
  - LSM 让写变顺序，但把成本搬到 compaction：写放大 10 x 时每天落盘 4.10 PB，
    相当于每秒 47 GB 的顺序写 —— 这是自建方案的真实门槛，不是「用 LSM 就快了」。
```

三处结论：

**第一，写:读 = 40,000:1。** 每封邮件都要进一次索引 → 每天 400 亿次索引写（**46.3 万次/秒**）；而按 0.1% 的用户每天搜一次算，搜索读只有 **11.6 次/秒**。**这是四个数量级的差**，所以讲义说「要针对写多的工作负载优化」不是修辞，是被这个比值逼出来的：索引不能按「查询快」设计，要按「写入吞吐」设计。

**第二，所以讲义给的三个方向是这个约束下的选择题**：ES（现成，但要作为独立服务与元数据存储一起维护）+ Kafka 解耦（变更异步、可回放）；自建 LSM（写路径只做顺序写，但数据存储本身就要兼做搜索）；或者用数据存储本身当索引。

**第三，LSM 把写变顺序，但把成本搬到 compaction。** 索引量约 150 PB/年（按元数据的 20% 估），写放大 5× / 10× / 20× 时每天实际落盘 2.05 / 4.10 / 8.19 PB，也就是 **24 / 47 / 95 GB/s 的顺序写**（按每盘 200 MB/s 加 20% 余量算是 142 / 284 / 568 块盘）。**判据：自建方案的门槛不是「用 LSM 就快了」，而是这每秒几十 GB 的顺序写能不能持续**——它比索引本身大一个数量级。

## 四、增量三：重试把送达率换成队列吞吐，IP 是周级冷启动

讲义说「让邮件到达收件箱很难」，给了预热、专用 IP、反馈循环等措施，并说队列过大要指数退避重试。把代价算出来：

```python
"""发送侧：重试放大、队列积压与 IP 预热的冷启动成本。

用讲义给的量：10 亿用户、每人每天发 10 封（10 万封/秒）、指数退避重试、专用 IP、预热 2-6 周、投诉封禁。
只依赖标准库；输出确定性。
"""
import math
SEND_QPS = 100_000
Q_SINGLE = 0.95             # 单次尝试的送达概率（估：对方临时不可达/限流/进垃圾箱）
HARD_BOUNCE_SHARE = 0.5    # 失败里硬退信（永久失败，不该重试）的比例（估）
MAX_BACKOFF_H = 1          # 指数退避上限（估）
IP_PER_DAY = 500_000       # 单个 IP 每天可发多少封（保守估）
WARMUP_WEEKS = (2, 6)

daily = SEND_QPS * 86400
print("发送量：%s 封/秒 = %s 封/天" % (format(SEND_QPS, ","), format(daily, ",")))
print()
print("重试放大：单次尝试送达概率 %.0f%%，要达到目标送达率 p 需要 k = ln(1-p) / ln(1-q) 次尝试" % (Q_SINGLE * 100))
print("%-12s %12s %20s %18s" % ("目标送达率", "尝试次数", "队列吞吐(封/秒)", "相对放大"))
for p in (0.90, 0.99, 0.999, 0.9999):
    k = math.ceil(math.log(1 - p) / math.log(1 - Q_SINGLE))
    print("%-12s %12d %20s %17.2fx"
          % ("%.2f%%" % (p * 100), k, format(int(SEND_QPS * k), ","), k))
print()
print("硬退信不该重试：")
fail = 1 - Q_SINGLE
soft = fail * (1 - HARD_BOUNCE_SHARE)
print("  单次失败率 %.0f%%，其中约一半是硬退信（永久失败）-> 真正值得重试的只有 %.1f%%" % (fail * 100, soft * 100))
print("  若不区分而全部重试：%.0f%% 的失败进入指数退避队列，其中一半是注定失败的" % (fail * 100))
print()
print("队列积压：退避上限 %d 小时时最坏堆多少" % MAX_BACKOFF_H)
for label, retry_rate in (("正常（单次失败中值得重试的 1%）", 0.01),
                           ("对方服务器大面积拒收（失败 100%）", 1.0)):
    pending = SEND_QPS * retry_rate * 3600 * MAX_BACKOFF_H
    print("  %-28s -> 最坏积压 %13s 封 = %6.0f 秒的发送量"
          % (label, format(int(pending), ","), pending / SEND_QPS))
print()
print("IP 预热的冷启动成本：")
ips = daily / IP_PER_DAY
print("  每 IP 每天 %s 封 -> 支撑 %s 封/天需要 %s 个 IP" % (format(IP_PER_DAY, ","), format(daily, ","), format(int(ips), ",")))
for w in WARMUP_WEEKS:
    print("  预热 %d 周：新 IP 在这 %d 周内不能承接生产流量 -> 这段时间完全依赖已预热的池子" % (w, w))
print("  讲义还要求营销邮件用**独立 IP** -> 池子要再分一次，且两套池子都要各自预热")
print()
print("判据：")
k99 = math.ceil(math.log(0.01) / math.log(1 - Q_SINGLE))
k999 = math.ceil(math.log(0.001) / math.log(1 - Q_SINGLE))
print("  - **重试是把送达率换成队列吞吐**：单次成功率 %.0f%% 时，送达率从 99%% 提到 99.9%%，" % (Q_SINGLE * 100))
print("    尝试次数从 %d 次涨到 %d 次（+%.0f%%），队列吞吐同比例上涨 —— 送达率不是免费的。" % (k99, k999, 100 * (k999 / k99 - 1)))
print("  - **发信能力 = IP 数 x 每 IP 速率，而 IP 是用信誉换来的**：预热 2-6 周意味着")
print("    新 IP 的冷启动成本是**周级**，「加机器」解决不了信誉问题。")
print("  - **硬退信与软退信必须分开**：重试硬退信纯浪费队列与 IP 配额。")
print("  - 退避上限决定最坏积压 -> 讲义说「必须监控外发队列大小」，")
```

三处结论：

**第一，送达率不是免费的，它是拿队列吞吐换的。** 单次尝试送达概率 95% 时，要达到 99% 的目标送达率需要 **2 次**尝试（队列吞吐 20 万封/秒），要到 99.9% 需要 **3 次**（30 万封/秒）——**送达率每提高一个数量级，队列吞吐涨 50%**。这就是「外发队列过大」的第一类成因（收件服务器不可用）的量化：**你要求多高的送达率，就等于要求队列扛得住多少倍的写入**。

**第二，硬退信与软退信必须分开处理。** 单次失败 5%，其中约一半是硬退信（地址不存在，永久失败）——**重试硬退信纯浪费队列容量和 IP 配额**。真正值得重试的只有 2.5%。

**第三，IP 是用信誉换来的，冷启动成本是周级。** 支撑 86.4 亿封/天、按每个 IP 每天 50 万封（保守）算，需要 **17,280 个 IP**；而讲义说预热一个新 IP 要 **2–6 周**——**这 2–6 周里新 IP 完全不能承接生产流量**，容量只能靠已预热的池子。营销邮件还要独立 IP，池子要再分一次、两套各自预热。判据：**发信能力 = IP 数 × 每 IP 速率，而 IP 数是「养」出来的，不是「买」出来的**；这正是讲义「搭建发送服务器容易，让邮件进收件箱很难」这句话的算术。

**第四，队列积压的量级决定了监控阈值。** 正常情况下退避队列只有约 360 万封（36 秒的发送量），但对方服务器大面积拒收时最坏会堆 **3.6 亿封（1 小时的发送量）**。讲义说「必须监控外发队列大小」，因为**队列是可靠性问题的先行指标**：它同时暴露「对方挂了」和「消费者不够」两种完全不同的故障，而两者的处置方式相反（等 vs 扩容）。

## 五、把三个模型套回本章（判据清单）

1. **大字段不进关系库**：附件占 67% 的量（1,495 PB vs 748 PB），元数据库只存引用。
2. **先定保留期再谈架构**：到达率不可控，保留期可控——90 天 vs 365 天差 1,690 PB。
3. **尺寸限制要写清口径**：base64 膨胀 33%，25 MB 上限若按编码后算，原始容量只剩 18.75 MB。
4. **索引按写入吞吐设计**：写:读 = 40,000:1，所以选 ES+Kafka 还是自建 LSM 是被这个比值决定的；自建还要扛住 LSM 的 compaction 写放大（10× 时 47 GB/s 顺序写）。
5. **送达率换队列吞吐**：99% → 99.9% 需要 2 → 3 次尝试，队列吞吐 +50%；硬退信不进重试队列。
6. **IP 容量是周级问题**：17,280 个 IP 的池子 + 2–6 周预热 + 营销邮件独立池 → 扩容量前先看池子。
7. **队列是先行指标**：正常退避队列 360 万封 vs 大面积拒收时 3.6 亿封，监控阈值要按后者定。

## 七、这三个模型判不了什么

- **单次尝试送达率 95%、每 IP 每天 50 万封、索引占元数据 20%、搜索用户占比 0.1%、硬退信占失败一半都是估的**。真实送达率受收件方策略、时区、信誉积累影响，波动范围极大；**每 IP 限额更是服务商与租户信誉共同决定的变量**。
- **没算 25 MB 上限与 base64 的协议细节**。附件实际上常常是单独走对象存储 + 引用（讲义正是这么设计的），此时 base64 膨胀发生在**上传接口**而不是邮件正文流里——两处的限制口径不同。
- **没算垃圾邮件过滤的误伤成本**。讲义讲送达率时反复强调垃圾防护算法会让新服务器的信进垃圾箱——**误伤是双向的**：拦掉坏信的同时也拦掉好信，而「好信进垃圾箱」对业务方（交易确认）的伤害比延迟更大，这个不对称没有量化。
- **没算搜索的分区与再平衡**：讲义说用 `user_id` 做分区键把同一用户的数据放到同一节点，但**超大用户的邮箱会形成热点**，且重建索引（讲义用 Kafka 解耦的那条路）需要重放全量变更——这时的 IO 与 compaction 叠加，本文没算。
- **三个模型都没碰多数据中心与主从切换**（讲义在可扩展性一节提到），也没碰实时服务器（WebSocket / 长轮询回退）的连接成本——那一项与我在云盘那篇算的长轮询重连同源。

## FAQ（八、常见问题）

**730 PB 元数据和 1,460 PB 附件是怎么来的？** 10 亿用户 × 每天 40 封 = 400 亿封/天；元数据 50 KB/封 → 748 PB/年，附件 20% × 500 KB → 1,495 PB/年（讲义取整为 730 / 1,460）。**附件占 67%**，所以「附件放对象存储、元数据库只存引用」是算术要求而不是风格选择。

**保留多久历史邮件？** 存储预算 = 到达率 × 保留期 × 单封大小，**只有保留期在你手里**（用户收多少封不由你定）。保留 30 天 = 184 PB、90 天 = 553 PB、365 天 = 2,243 PB——**90 天比一年省 1,690 PB**。

**25 MB 附件上限是按编码前还是编码后算？** 必须问清：base64 膨胀 33%，按编码后卡则原始附件只能到 **18.75 MB**，按原始卡则编码后 33.3 MB 会超限。两个口径差 **6.25 MB**——这会变成用户侧「20 MB 传不上去」的具体原因。

**送达率要多少重试才够？** 单次成功率 95% 时，达到 99% 目标送达率要 **2 次**尝试（队列吞吐 20 万封/秒），99.9% 要 **3 次**（30 万封/秒）——**送达率每提一个数量级，队列吞吐涨 50%**。而且硬退信（地址不存在）不该重试，单次失败 5% 里约一半是硬退信。

**为什么发信容量是周级问题？** 支撑 86.4 亿封/天、按每 IP 每天 50 万封算需要 **17,280 个 IP**，而讲义说预热一个新 IP 要 **2–6 周**——这段时间新 IP 完全不能承接生产流量，营销邮件还要独立池。**IP 是养出来的，不是买出来的。**

**邮件搜索该怎么建？** 先看比值：索引写 46.3 万次/秒，搜索读只有 11.6 次/秒（写:读 = 40,000:1），所以要按写入吞吐优化。ES + Kafka 解耦，或自建 LSM；但自建的真实门槛是 compaction——写放大 10× 时每天落盘 4.1 PB，即 **每秒 47 GB 顺序写、约 284 块盘**。
