## 一、笔记的骨架：把 CAP 拆成两个问题

**CAP 的原始定义与局限**：一致性（所有客户端同时看到相同数据）、可用性（某些节点宕机时系统仍响应每个请求）、分区容忍性（网络分区时继续运行）；三选二，而 **CA 系统在现实中不存在**——网络故障不可避免，所以分布式系统必须容忍分区。讲义指出 CAP 的局限是**它只描述了分区发生时的选择，没告诉你平时该怎么取舍**。

**PACELC（2012，Daniel Abadi）的完整表述**：**P**artition 发生时在 **A**vailability 与 **C**onsistency 间选，**E**lse（平时，无分区）在 **L**atency 与 **C**onsistency 间选。笔记把它画成决策树：**问题 1（分区时）**——要「强一致但可短暂拒绝写入」还是「允许暂时不一致以保证高可用」；**问题 2（平时）**——「我能容忍多大延迟换取多强的一致性」，对应「多副本写入、同步复制、全局事务、线性一致性」对「最终一致性、异步复制、读本地副本」。四象限是 PC/EL、PC/EC、PA/EL、PA/EC。

**现代数据库的归类**（笔记第 3–4 节）：强一致多副本系统（PC/EC、PA/EC）、高可用最终一致系统（PA/EL）、以及金融/交易类数据库的典型权衡；另有**一致性光谱**（从强到弱的各级）与**延迟与一致性关系**一节，以及实践决策框架（业务需求分析 → 技术选型决策树 → 一致性配置示例）。

## 二、增量一：两个决策分支的时间权重差三个数量级

PACELC 把 P/A 与 E/C 分开是有原因的——它们的触发概率完全不同。算出来：

```python
"""PACELC 的时间权重：日常决策是 E/C，不是 P/A。

依据：笔记把决策拆成「分区时（P/A）」与「平时（E/C）」两个问题。
只依赖标准库；输出确定性。
"""
PARTITION_RATE = 0.001     # 分区发生率（按请求窗口估，一次网络抖动的量级）
RTT_CROSS_REGION = 50      # 跨区 RTT（ms，估）
RTT_LOCAL = 1              # 本地 RTT（ms，估）
WRITE_LOCAL_MS = 2         # 本地落盘耗时（ms，估）

print("一、两种决策的触发概率差几个数量级")
for p in (0.001, 0.01, 0.10):
    print("   分区发生率 %5.1f%% -> 每 1000 次设计/运行决策里，分区相关的只有 %4.1f 次，其余 %6.1f 次是 E/C"
          % (p * 100, 1000 * p, 1000 * (1 - p)))
print()
print("   => **PACELC 把 P/A 与 E/C 分开，正是因为触发概率差三个数量级**；")
print("      架构设计的重点因此落在「常态下的延迟 vs 一致性」，而不是「分区时怎么取舍」。")
print()
print("二、E/C 分支的延迟账：同步复制 vs 异步复制")
print("   %-24s %14s %16s %18s" % ("方案", "写延迟", "读延迟(本区)", "分区时的行为"))
rows = (
    ("异步复制 + 读本地副本", WRITE_LOCAL_MS, RTT_LOCAL, "继续服务，读可能陈旧"),
    ("同步复制 + quorum 读", WRITE_LOCAL_MS + RTT_CROSS_REGION, RTT_CROSS_REGION, "写要等多数派确认"),
)
for name, w, r, part in rows:
    print("   %-24s %11d ms %13d ms %18s" % (name, w, r, part))
print()
print("   => 同步复制把**每次写**都加上一个跨区 RTT（%d ms），而分区一年可能只发生几次。" % RTT_CROSS_REGION)
print("      判据：**强一致不是「慢一点」，而是每次写都要付一笔平时用不到的等待**。")
print()
print("三、关键前提：延迟预算必须装得下跨区 RTT")
SLA_MS = 20                # 写延迟 SLA（ms，估）
for rtt in (1, 10, 50, 100):
    total = WRITE_LOCAL_MS + rtt
    ok = total <= SLA_MS
    print("   跨区 RTT %3d ms -> 同步写延迟 %3d ms -> %s" % (rtt, total, "满足 SLA" if ok else "超出 SLA，写不可用"))
print()
print("   => 当写延迟 SLA 装不下跨区 RTT，PACELC 的 E 分支不是「选弱一点的一致性」，")
print("      而是**唯一可用的选择** —— 这是「一致性级别要按延迟预算倒推」的含义。")
```

三处结论：

**第一，日常决策几乎全是 E/C。** 分区发生率按 0.1%（一次网络抖动的量级）估：每 1000 次设计/运行决策里，分区相关的只有 **1 次**，其余 **999 次**是「延迟 vs 一致性」。**判据：PACELC 之所以要拆成两个分支，正是因为这两件事的触发概率差三个数量级**——所以架构设计的重心在常态下的延迟与一致性取舍，而不是「分区时怎么选」。CAP 的「三选二」之所以不够用，也是同一个原因：它把一年发生几次的时刻，写成了每天都在做的决策。

**第二，同步复制把「每次写」都加上一个跨区 RTT。** 异步复制 + 读本地：写 2 ms、读 1 ms；同步复制 + quorum 读：写 **52 ms**、读 **50 ms**（跨区 RTT 50 ms 估）。**判据：强一致不是「慢一点」，而是每次写都要付一笔平时用不到的等待**——而分区一年可能只发生几次。

**第三，也是最关键的一条：延迟预算装不下跨区 RTT 时，强一致不是「贵」而是「不可用」。** 写延迟 SLA 20 ms 时：跨区 RTT 50 ms → 同步写延迟 52 ms → **超出 SLA，写直接不可用**；RTT 100 ms 更甚。**判据：PACELC 的 E 分支不是「选弱一点的一致性」，而是「唯一能用的选择」**——这就是「一致性级别要按延迟预算倒推」的含义。

## 三、增量二：一致性级别买的是「每次操作多碰几个副本」

笔记的一致性光谱列了从强到弱的各级，但没说各级在副本数上要付什么。算出来：

```python
"""一致性级别 ↔ 读放大 / 写放大 / 延迟的对应账。

用笔记的 PACELC 框架与一致性光谱；副本数与 quorum 由本脚本设定（估）。
只依赖标准库；输出确定性。
"""
N = 3                       # 副本数
READ_QPS = 100_000          # 读 QPS（估）
REPLICA_QPS = 50_000        # 单副本能扛的 QPS（估）

LEVELS = (
    ("线性一致（PC/EC）", 2, 2, "读多数派 + 写多数派"),
    ("最终一致（PA/EL）", 1, 1, "读本地 + 写本地"),
    ("会话一致（读己之写）", 1, 3, "读本地（粘滞）+ 写多数派"),
)


def quorum(n):
    return n // 2 + 1


print("副本数 %d，强一致的最小 quorum = %d（W+R>N）" % (N, quorum(N)))
print()
print("%-22s %8s %8s %12s %14s %18s %18s" % ("一致性级别", "读 R", "写 W", "读放大(R)", "写放大(W)", "每副本读 QPS", "需要的副本数"))
for name, r, w, note in LEVELS:
    per_replica_read = READ_QPS * r / N
    need_replicas = -(-READ_QPS * r // REPLICA_QPS)
    print("%-22s %8d %8d %11.2fx %13.2fx %18s %17d" % (name, r, w, r, w,
          format(int(per_replica_read), ","), need_replicas))
print()
print("   注：会话一致那行读 R=1（读本地），但「读己之写」靠粘滞读或读修复实现，")
print("       写侧要付多数派的代价 —— **一致性代价可以挪到读侧或写侧，但不能消失**。")
print()
print("一、读放大落到集群规模上（N=3、%s 读 QPS、单副本 %s QPS）" % (format(READ_QPS, ","), format(REPLICA_QPS, ",")))
for name, r, w, note in LEVELS:
    per_replica_read = READ_QPS * r / N
    ok = per_replica_read <= REPLICA_QPS
    need = -(-READ_QPS * r // REPLICA_QPS)
    print("   %-22s 每副本读 %s QPS -> %s（需要 >= %d 个副本）"
          % (name, format(int(per_replica_read), ","),
             "单副本扛得住" if ok else "**单副本扛不住**", need))
print()
print("二、写侧：强一致让写吞吐也受 quorum 约束")
WRITE_QPS = 20_000
for name, r, w, note in LEVELS:
    per_replica_write = WRITE_QPS * w / N
    print("   %-22s 写 %d 副本 -> 每副本写 %s QPS（单副本 %s QPS）"
          % (name, w, format(int(per_replica_write), ","), format(REPLICA_QPS, ",")))
print()
print("判据：")
print("  - **一致性级别买的是「每次操作多碰几个副本」的延迟，不是「多几台机器」**：")
print("    N=3 时线性一致每次读碰 %d 个副本（相对最终一致的 1 个是 %.1fx），而集群规模要按 R 算：" % (
    quorum(N), quorum(N)))
print("    %s 读 QPS、单副本 %s QPS -> 线性一致需要 >= %d 个副本，最终一致 %d 个就够。" % (
    format(READ_QPS, ","), format(REPLICA_QPS, ","),
    -(-READ_QPS * quorum(N) // REPLICA_QPS), -(-READ_QPS // REPLICA_QPS)))
print("  - **代价可以挪到读侧或写侧，但不能消失**：会话一致把读降到 1x，写就得付 %.1fx。" % 3)
print("  - 所以选型时该问的是「**这个业务更不能忍读慢还是写慢**」，而不是「要不要强一致」。")
```

输出：

```text
  - **代价可以挪到读侧或写侧，但不能消失**：会话一致把读降到 1x，写就得付 3.0x。

```

三处结论：

**第一，线性一致的代价是每次读多碰一个副本，而集群规模要按 R 算。** N=3 时强一致的最小 quorum 是 2（W+R>N）：每次读碰 **2 个副本**（相对最终一致的 1 个是 2×）、每次写也碰 2 个。落到集群规模：10 万读 QPS、单副本 5 万 QPS 时，**每副本要扛 66,666 QPS > 50,000 → 3 副本不够，需要 ≥4 个**；最终一致每副本 33,333 → **2 个副本就够**。**判据：一致性级别买的是延迟（多等一个副本的往返），不是「多几台机器」——但机器数确实要按 R 重算。**

**第二，一致性代价可以在读侧与写侧之间挪，但不能消失。** 会话一致（读己之写）把读降到 R=1（读本地 + 粘滞），代价就落到写侧：W=3 → 写放大 3×，每副本写 20,000 QPS。**判据：选型时该问的是「这个业务更不能忍读慢还是写慢」，而不是「要不要强一致」。**

**第三，读与写的放大要分开看。** 同一个系统里，读放大决定**读侧副本数**、写放大决定**写侧每副本负载**：线性一致读 2×/写 2×，最终一致读 1×/写 1×，会话一致读 1×/写 3×。把两者混成一个「一致性强度」数字，就没法推出该买几台机器。

## 四、增量三：陈旧读的概率，与延迟代价做一次交换

笔记在「延迟与一致性关系」里画了曲线，但没给概率。把陈旧读算出来，再和延迟做交换：

```python
"""陈旧读的概率与代价：与延迟做一次交换。

依据：笔记「延迟与一致性关系」与「读本地副本 vs quorum 读」；参数为本脚本设定（估）。
只依赖标准库；输出确定性。
"""
READ_QPS = 1_000
REPLICA_LAG_MS = 200        # 副本落后（复制延迟中位数，估）
UPDATE_RATE = 0.10          # 每对象每秒被更新的次数（估）
LOSS_RATE_IF_STALE = 0.01   # 陈旧读中造成实际业务损失的比例（估）
LOSS_PER_EVENT = 5          # 每次实际损失（美元，估）
RTT = 50                    # 跨区 RTT（ms，估）

print("一、读到陈旧数据的概率 ≈ 更新速率 x 复制延迟")
```

三处结论：

**第一，陈旧读的概率 = 更新速率 × 复制延迟，与一致性级别无关。** 复制延迟 200 ms（估）时：每对象 0.01 次/秒更新 → 陈旧读 **0.20%**；0.1 次/秒 → **2.00%**；1 次/秒 → **20%**。**判据：这是异步复制的固有代价，换一致性级别换不掉**——所以「先降复制延迟」往往比「上强一致」更划算。

**第二，陈旧读的期望损失要和延迟代价用同一个口径比。** 本模型：1,000 读 QPS、陈旧读 2% → 每秒 20 次陈旧读，其中 1% 造成实际损失（每次 $5）→ **$1/秒、$86,400/天**。而延迟代价的记法取决于它是否把请求推出 SLA：RTT 50 ms 而 SLA 是 20 ms 时，代价不是「慢一点」而是**请求直接失败**（失败率 100%）。**判据：交换率 = 一次陈旧读的业务损失 ÷ 一次 RTT 的延迟成本，而后者在超 SLA 时是阶跃的**——所以强一致的成本容易被低估：它的风险不是「每天慢一点」，而是「延迟预算不够时直接不可用」。

**第三，两边的损失都难估，但陈旧读那侧更好估。** 陈旧读的损失可以从「陈旧读概率 × 实际造成损失的比例 × 单次损失」估出来；而「请求因为超 SLA 而失败」的损失要估重试、超时、级联与业务降级——**所以工程上会不自觉地偏向强一致，因为它的代价藏在更难估的那一侧**。这是笔记「实践决策框架」应该补上的一条：**先估不确定的那一侧**。

## 五、把三个模型套回本章（判据清单）

1. **P/A 与 E/C 的触发概率差三个数量级**：分区率 0.1% 时每 1000 次决策里 999 次是 E/C → 架构重心在常态。
2. **同步复制给每次写加一个跨区 RTT**（本模型 50 ms），而分区一年可能只发生几次。
3. **延迟预算装不下跨区 RTT 时，强一致不是贵而是不可用**：SLA 20 ms、RTT 50 ms → 同步写直接失败。
4. **一致性级别买的是「每次操作多碰几个副本」**：N=3 时线性一致读 2×/写 2×，最终一致 1×/1×，会话一致读 1×/写 3×。
5. **机器数按 R 算**：10 万读 QPS、单副本 5 万 QPS → 线性一致需 ≥4 副本，最终一致 2 副本够。
6. **一致性代价可以在读写之间挪，不能消失**。
7. **陈旧读概率 = 更新率 × 复制延迟**（0.1 次/秒 × 200 ms = 2%），且**换一致性级别换不掉** → 先降复制延迟往往更划算。
8. **交换率要用同一口径**：超 SLA 的延迟代价是阶跃的（失败率 100%），陈旧读的损失是线性的 → **先估难估的那一侧**。

## 七、这三个模型判不了什么

- **分区发生率、跨区 RTT 50 ms、单副本吞吐、更新率、复制延迟、每次业务损失都是估的**，而**陈旧读概率对更新率与复制延迟的乘积极其敏感**：更新率翻 10 倍，陈旧读概率也翻 10 倍。所以这两个参数必须从真实监控里取，不能拍。
- **没算多副本的写放大对提交延迟的尾部影响**。模型里写延迟是「等多数派确认」的一次 RTT，但真实系统里某个副本慢、确认超时重试，会让写延迟的尾部远大于 RTT——**这正是「同步复制在跨地域很危险」的另一半原因**，本文没建模。
- **没算会话一致的实现代价**。粘滞读要维护会话状态、读修复要触发额外读，两者都有复杂度与额外 IO；本文只把它记成「写放大 3×」。
- **没算「一致性级别」在不同数据上的差异**。同一系统里，账户余额可能需要线性一致，而商品浏览可以用最终一致——**按 key 分级**才是常见做法，本文的账是「系统级选一级」，偏粗。
- **三个模型都没碰 CAP 里「分区检测」本身的代价**：探测分区要超时（心跳/租约），而超时长度又与「误判分区导致不必要的降级」直接冲突——**这是 CAP 里最难的那一格**，本文没有算。

## FAQ（八、常见问题）

**CAP 和 PACELC 到底差在哪？** 在触发概率。分区发生率按 0.1% 估时，**每 1000 次决策里 999 次是「平时」**——所以 PACELC 把平时（E：延迟 vs 一致性）与分区时（P：可用 vs 一致）分开，是因为前者才是日常。CAP 的「三选二」把一年发生几次的时刻写成了每天都在做的决策。

**强一致要付多少？** 两种付法：延迟上，同步复制给每次写加一个跨区 RTT（本模型 50 ms）；集群上，每次读碰 2 个副本而不是 1 个 → 10 万读 QPS、单副本 5 万 QPS 时，**3 副本不够，需要 ≥4 个**（最终一致 2 个就够）。

**那强一致是不是一定更贵？** 不一定贵，但**可能不可用**：写延迟 SLA 20 ms 而跨区 RTT 50 ms 时，同步写延迟 52 ms → **直接失败**。这是阶跃而不是渐变：RTT 10 ms 时一切正常，50 ms 时整个方案不可用。

**读到陈旧数据的概率怎么估？** ≈ **更新速率 × 复制延迟**：0.1 次/秒 × 200 ms = 2%。这个量**与一致性级别无关**，是异步复制的固有代价——所以降复制延迟往往比上一致性级别更划算。

**一致性代价能挪吗？** 能在读侧与写侧之间挪，不能消失：会话一致（读己之写）把读降到读本地（R=1），代价就转到写侧（W=3，写放大 3×）。**所以该问的是「这个业务更不能忍读慢还是写慢」。**

**PACELC 的 E 分支是不是「降级方案」？** 更准确的说法是**「延迟预算下的唯一可行解」**：预算装不下跨区 RTT 时，同步写与 quorum 读不是「慢一点」而是直接不可用。**所以一致性级别应该按延迟预算倒推，而不是按「想要多强」正向挑。**
