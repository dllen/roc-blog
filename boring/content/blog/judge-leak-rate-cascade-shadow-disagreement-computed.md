裁判的三笔账？judge 到底漏放了多少、级联分流省下多少、以及影子模式怎么用最便宜的方式拿到最贵的证据。我读完 AIE Code Summit 2026 那场《Your Judge Is Hallucinating Too》之后，最想验证的是：一个每步都在把关的 judge，**实测有多准**，以及它的数字能怎么用。这篇把它算清楚。

## 一、讲者的骨架：故事 vs 收据

**开场案例**：agent 声称某封销售邮件**已经排程**，第二模型（judge）读了这个说法，**通过了**。但那封邮件从未发出——agent 甚至**没有能发邮件的工具**，它捏造了一次 send，judge 又给这个从未被核查过的声明盖了章。「所以那是两次失败：agent 捏造了发送，judge 给一个从未被检查的声明批了准。」

**结构性缺陷**：judge 每步只有三个动作——继续、重做、终止。问题在于**一个通用 judge 能判断「工作看起来完成了吗」，却无法判断「工作做对了吗」**——「对」的定义随任务而变，而他们问所有任务的都是同一个大问题：「这好吗？」

**第一次量化（500 步离线评测）**：从生产流量取 **500 个真实步骤**（每步都带原 judge 的判定），用更大的 frontier model 重新判 accept / send back，再**人工复核分歧样本、以人工判断为准**，得到 500 条参考标签。结果：原 judge 只有 **65%** 正确，接近抛硬币；它接受了 **118 个本应打回**的步骤，**占其全部 accept 的四分之一以上**。

**根因：故事 vs 收据**。回看那封邮件——judge 同时拿到了左边的「agent 自述」（自信、文笔好、说邮件已排期）和右边的「receipts」（明确的失败错误）。**judge 两样都拿到了，却选择了故事**，因为表面上看起来没问题。

**换问题，而不是调 prompt**：显而易见的修法是给 judge 写更好的 prompt，但那等于给每个用例做专用 judge——销售邮件、CRM 更新、调研……每类都要定制并持续维护，是**一个永不结束的 prompt tuning 项目**。他们改成执行者 **jev**——「一个 typed decision model，而不是生成模型」，一次调用回答**全部七个 yes/no 问题**、每个答案都带概率，而且**只看 tool call receipts 判案**。同一封邮件：LLM judge 用约 2.5 秒给出 accept；jev 用约五分之一秒给出 accept 0% / redo 97% / stop 3%。**决策规则**：accept 概率 **≥30% 通过、≤5% 重做或终止、中间灰区交给 LLM judge**；阈值由那 500 条标签调出。七个问题的作用是给出「why」，并写进 agent 真正需要重做时收到的反馈里。

**两组对照实验**：① **离线复测**（同样 500 步）：jev 对约 **7/10** 有把握；原 judge 误放行的 **82** 步中，jev 抓回 **74** 步。② **Shadow mode**：两个 judge 都看每一步，但**只有 LLM judge 的决策生效**，jev 的结果只记录不干预——累计 **37,000** 次决策，其中 **728** 步存在明显工具失败：LLM judge 只抓到 **294**，jev 抓到 **623**。开场那封假邮件也不是孤例：**同一步骤在生产跑了 1,081 次**，agent 几乎每次都声称已排期，LLM judge 只抓到 **1 次**，jev 抓到 **876 次**。性能上 jev **快 10 倍、便宜 40 倍**——而「只要链路里有 judge，每一步都得等它」，这个差距会被步数放大。

**下一步与可复制的行动清单**：他们正在加 **post-condition checks**——根据步骤内实际调用的工具动态追加问题（调了 send 工具就问「消息是否送达」，写了记录就问「记录是否存在」），与原有七个问题**同一次调用**送入 jev。给听众的三步：① 在系统里挑一个 LLM 判断点，改写成几个**能靠证据回答的 yes/no**；② 用 jev 实现（他们只用了七个问题）；③ **先以 shadow mode 与现有 judge 并行上线，只记录不决策，再读分歧案例**。核心告诫：「我们此前一直信任自己的 judge，直到真正测量它——**Measure yours.**」

## 二、增量一：从两个已知量把混淆矩阵定住

```python
"""judge 的漏放率：从 500 步评测还原混淆矩阵，看清「四分之一」是什么量级。

数字取自我的精读笔记（500 条真实生产步骤 + 人工复核分歧得到 500 条参考标签；原 judge 正确率 65%；
接受了 118 个本应打回的步骤，占其全部 accept 的四分之一以上）。
只依赖标准库；输出确定性。
"""
STEPS = 500
ACCURACY = 0.65             # 原 judge 的正确率
FALSE_ACCEPT = 118          # 接受了本应打回的步骤数

print("一、还原混淆矩阵（用两个已知量定住未知量）")
correct = round(STEPS * ACCURACY)      # 判对 = 325
false_accept = FALSE_ACCEPT            # 漏放 = 118
false_reject = STEPS - correct - false_accept   # 错杀 = 500 - 325 - 118 = 57（恒定）
# accept 总数 A：真接受 = A - 118；真打回 = (500 - A) - 57 = 443 - A >= 0  -> A <= 443
accept_max = 500 - false_reject        # = 443
accept_min = false_accept
print("   判对 %d + 漏放 %d + 错杀 %d = %d（对上了 500）" % (
    correct, false_accept, false_reject, correct + false_accept + false_reject))
print("   => **错杀恒为 %d 个**（由 500 - 判对 - 漏放 直接定住，与 accept 总数无关）" % false_reject)
print("   => accept 总数 A 只能落在 [%d, %d]：真打回 = 443 - A 必须非负。" % (accept_min, accept_max))
print()
print("%-16s %12s %12s %12s %18s" % ("accept 总数 A", "真接受", "漏放", "真打回", "漏放占 accept"))
for A in (accept_min, 300, 400, accept_max):
    tp = A - false_accept
    tn = 500 - A - false_reject
    print("%-16d %12d %12d %12d %17.1f%%" % (A, tp, false_accept, tn, 100.0 * false_accept / A))
print()
print("   => 漏放占 accept 的比例**下界 = 118 / %d = %.1f%%**（讲者说「四分之一以上」，与此一致）；" % (
    accept_max, 100.0 * false_accept / accept_max))
print("      判据：**漏放至少占它自己接受的 %.1f%%** —— 也就是每 4 个放行里就有 1 个以上是错的。" % (
    100.0 * false_accept / accept_max))
print("二、漏放与错杀的代价不对称")
print("   漏放：捏造的操作进了生产（可能不可逆、对外可见）；")
print("   错杀：好工作被退回重做（有成本，但可逆）。")
print("%-20s %18s %22s %20s" % ("漏放的外部后果占比", "每 1000 步漏放", "对外可见后果", "相当于错杀的倍数"))
for ratio in (0.02, 0.10, 0.30):
    per_1000 = 1000 * FALSE_ACCEPT / STEPS
    visible = per_1000 * ratio
    print("%-20s %18.0f %22.1f %20s" % ("%.0f%%" % (ratio * 100), per_1000, visible,
          "不可逆" if ratio >= 0.1 else "可事后修"))
print()
print("   => 判据：**judge 的阈值应该偏向高敏感度**（宁可错杀），因为漏放与错杀的代价不对称；")
print("      而这正是「先测量」的价值——没测就不知道自己在哪个方向上偏。")
print()
print("三、换成真实分布会怎样")
print("   500 步是**生产流量抽样**，不是全量；而且人工只复核了分歧样本。")
print("   若真实分布里「坏步骤」占比更高，漏放绝对数会同比放大。")
print("%-18s %18s %20s %20s" % ("真实坏步骤占比", "每 1000 步的坏步骤", "按 25%% 漏放率", "按 10%% 漏放率"))
for bad_rate in (0.05, 0.10, 0.25):
    bad = 1000 * bad_rate
    print("%-18s %18.0f %20.0f %20.0f" % ("%.0f%%" % (bad_rate * 100), bad,
          bad * 0.25, bad * 0.10))
print()
print("   => 判据：**「judge 有 65% 准确」这个数字必须配上「坏步骤占比」才有意义**；")
print("      坏步骤越多，同样的准确率漏放的绝对数越大。")
```

三处结论：

**第一，错杀数是确定的：57 个。** 判对 325 + 漏放 118 + 错杀 57 = 500——**错杀由「500 − 判对 − 漏放」直接定住，与 accept 总数无关**。**判据：引用「65% 准确」时最好同时给出漏放与错杀两个绝对数**，因为它们对业务的含义完全不同。

**第二，accept 总数只能落在 118~443，漏放占比的下界是 26.6%。** 真打回数 = 443 − A 必须非负 → A ≤ 443；而 A ≥ 118 → **漏放占 accept 的比例 ≥ 118/443 = 26.6%**（讲者说「四分之一以上」，与此一致）。**判据：每 4 个放行里就有 1 个以上是错的**——这个比例是「下界」，也就是说真实值只会更差。

**第三，漏放与错杀的代价不对称，所以阈值该偏向高敏感度。** 漏放 = 捏造的操作进了生产（可能不可逆、对外可见）；错杀 = 好工作被退回重做（有成本，但可逆）。按每 1,000 步漏放 236 个算：若 10% 的漏放造成对外可见后果，就是每千步 24 个不可逆事故。**判据：这就是「先测量」的价值——没测过，你不知道自己偏在哪一边。** 另外，「65% 准确」这个数字必须配上「坏步骤占比」才有意义：坏步骤占 5% 时每千步漏放 12 个，占 25% 时就是 62 个。

## 三、增量二：级联把每步成本压到 32%，延迟压到 0.89 秒

```python
"""级联：便宜模型分流 + 贵模型兜底，成本与延迟各省多少。

数字取自我的精读笔记（LLM judge 约 2.5 秒、jev 约五分之一秒即 0.2 秒；jev 快 10 倍、便宜 40 倍；
jev 对 7/10 有把握；accept >= 30% 通过、<= 5% 重做或终止、灰区交 LLM judge）。
只依赖标准库；输出确定性。
"""
LLM_SEC = 2.5
JEV_SEC = 0.2
PRICE_RATIO = 40.0          # jev 单价 = LLM 的 1/40（讲者：便宜 40 倍）
CONFIDENT = 0.70            # jev 有把握的比例（7/10）

print("一、每步的成本与延迟（灰区里的步骤走 LLM，其余走 jev）")
GRAY = 0.30                   # 讲者的配置：约三成步骤落在灰区
cost = (1 - GRAY) / PRICE_RATIO + GRAY
lat = (1 - GRAY) * JEV_SEC + GRAY * LLM_SEC
print("   灰区 %.0f%% -> 走 jev %.0f%%、走 LLM %.0f%%" % (GRAY * 100, (1 - GRAY) * 100, GRAY * 100))
print("   每步成本 **%.3f**（LLM 全量 = 1.000，即 %.0f%%）| 每步延迟 **%.2f 秒**（全量 %.1f 秒）" % (
    cost, 100 * cost, lat, LLM_SEC))
print()
print("二、为什么这个差距在有 judge 的链路里被放大")
print("   讲者原话方向：「只要链路里有 judge，每一步都得等它」。")
for steps in (1, 5, 20):
    print("     %2d 步的链路：全量 LLM 等 %.1f 秒；级联等 %.1f 秒（省 %.1f 秒）" % (
        steps, steps * LLM_SEC, steps * (0.70 * JEV_SEC + 0.30 * LLM_SEC),
        steps * (LLM_SEC - (0.70 * JEV_SEC + 0.30 * LLM_SEC))))
print()
print("   => 判据：**judge 在关键路径上时，它的延迟被步数乘一遍**——所以「先分流再兜底」")
print("      同时优化了延迟与成本，而不只是账单。")
print()
print("三、阈值的交换：灰区越宽越便宜，但漏放侧要靠另一条路补")
print("%-16s %18s %16s %22s" % ("灰区", "走 LLM 的比例", "每步成本", "漏放侧的保护"))
for gray in (0.10, 0.20, 0.30, 0.50):
    cost = (1 - gray) / PRICE_RATIO + gray
    prot = "更严（更多步骤走 jev 定案）" if gray < 0.30 else "更松（更多步骤交 LLM 兜底）"
    print("%-16s %17.0f%% %15.3f %22s" % ("%.0f%%" % (gray * 100), gray * 100, cost, prot))
print()
print("   注：**灰区放宽的漏放代价不能在这里量化**——讲者没有报留出集，")
print("   30%/5% 是在同一批 500 条标签上调出来的（我的笔记已记下这条怀疑）。")
print("   判据：**阈值是在「成本」与「未测量的漏放」之间做交换**，所以换阈值必须换一批新标签。")
```

```text
   30%/5% 是在同一批 500 条标签上调出来的（我的笔记已记下这条怀疑）。
   判据：**阈值是在「成本」与「未测量的漏放」之间做交换**，所以换阈值必须换一批新标签。
```

三处结论：

**第一，按讲者的配置，每步成本只要 32%、延迟 0.89 秒。** 约三成步骤落在灰区：其余七成走 jev（0.2 秒、单价 1/40），灰区走 LLM（2.5 秒）→ 每步成本 **0.318**（全量 LLM = 1.000）、延迟 **0.89 秒 vs 2.5 秒**。**判据：「便宜模型分流 + 贵模型兜底」同时优化了账单和关键路径**，不是二选一。

**第二，这个差距在多步链路里被放大。** 20 步的链路：全量 LLM 要等 **50.0 秒**，级联等 **17.8 秒**（省 32.2 秒）。**判据：judge 在关键路径上时，它的延迟被步数乘一遍**——所以「每步都等裁判」的系统，级联改造的收益是线性的。

**第三，阈值是在「成本」与「未测量的漏放」之间做交换。** 灰区 10% → 每步成本 0.122；30% → 0.318；50% → 0.512。**但灰区放宽的漏放代价不能在这里量化**——讲者没报留出集，30%/5% 是在同一批 500 条标签上调出来的。**判据：换阈值必须换一批新标签**，否则你只是在拟合旧标签。

## 四、增量三：影子模式里，分歧数就是产出的下界

## 七、这三个模型判不了什么

- **500 步是生产流量抽样，且人工只复核了分歧样本**——这是「相对人工标签」的口径，不是「相对真实结果」的口径；而且 65%、118、82、74 都来自**单一产品、单一 judge 配置**，外部效度有限。**模型的混淆矩阵还原还额外假设了「四分之一以上」是唯一约束**，若真实 accept 总数更小，漏放占比的下界会更高。
- **级联模型假设灰区比例固定在 30%**，而这取决于 jev 的置信度分布——讲者只说「约 7/10 有把握」，没给分布形状。**成本侧的比例是可以照抄的，漏放侧不能**（没有留出集）。
- **影子模式那 37,000 次决策的分歧总量未知**，我只用两个检出数给出了下界（329）。真实分歧数可能大得多（两个裁判一致通过的部分不产生分歧，但不产生分歧不等于安全）。
- **没有算 jev 的维护成本**：七个 yes/no 问题 + post-condition checks 的动态追加规则，本身就是一套要维护的东西——它比「一个大问题」复杂，只是**可复用**。
- **1,081 次那一步的 0.09% 不能推广**：那是一个特定的失败模式（假邮件），换成别的失败模式，通用 judge 的检出率可能完全不同。
- **三个模型都没碰「judge 该不该存在」**：判据是**漏放与错杀的代价不对称**，但如果你的场景里漏放的代价接近零（内部工具、可回滚），那么 65% 准确也许够用——**先量代价，再量准确率**。

## FAQ（八、常见问题）

**judge 实测有多准？** 500 步的参考标签下，原 judge **65%** 正确。拆开看：**漏放 118 个、错杀 57 个**（错杀数由 500 − 325 − 118 直接定住），accept 总数只能落在 118~443 → **漏放至少占它自己接受的 26.6%**。

**这意味着什么？** 每 4 个放行里就有 1 个以上是错的。**判据：没测过 judge，你不知道自己偏在哪一边**——漏放（捏造的操作进生产，不可逆）和错杀（退回重做，可逆）的代价完全不同。

**怎么改？** 不是调 prompt，而是**换问题**：把「这好吗」拆成几个**能靠工具回执回答的 yes/no**，用 typed decision model（jev）一次调用全答、每答带概率。同一封邮件：LLM judge 2.5 秒给 accept，jev 0.2 秒给 accept 0% / redo 97% / stop 3%。

**分级阈值怎么定？** accept ≥30% 通过、≤5% 重做或终止、灰区交 LLM。级联让**每步成本只要 32%、延迟 0.89 秒 vs 2.5 秒**；20 步链路省 32.2 秒。**但换阈值必须换一批新标签**——讲者的 30%/5% 是在同一批 500 条上调的，没报留出集。

**shadow mode 有什么用？** 两个 judge 同时看、只有一个生效，jev 的结果只记录。37,000 次决策里 728 步有明确工具失败，LLM 抓到 294、jev 抓到 623 → **不用知道交集，就能算出 jev 至少独抓了 329 个**。**判据：分歧数就是产出的下界**；人工只读分歧样本（成本下界约 16.5 小时）而不是全部 37,000 条（1,850 小时）。

**为什么同一个失败跑 1,081 次，LLM judge 只抓到 1 次？** 因为通用 judge 每次都在「看情况」，而结构化检查是**每次都命中**。**判据：重复出现的失败应该升级成确定性规则，而不是继续交给通用 judge**。

**这些数字能外推吗？** **不能直接外推**：单一产品、单一 judge 配置；728 是事后筛出的失败子集，jev 的 623 不是全量准确率；阈值有过拟合风险。**把它当结构参考，别当基准值。**

**那第一步该做什么？** 讲者给的三步：① 挑一个 LLM 判断点，改写成能靠证据回答的 yes/no；② 用 decision model 实现（他们只用了七个问题）；③ **先以 shadow mode 并行上线，只记录不决策，再读分歧案例**。核心是那句：**Measure yours.**
