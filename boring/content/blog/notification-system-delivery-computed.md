通知系统的投递率怎么算？讲义里每一环看起来都很稳——消息队列有持久化、工作进程有重试、第三方推送有 SLA——但端到端一算，1600 万条/天要丢 379 万条。这篇把「可靠性」从「每一环都有保障」翻译成「全链路乘出来的一个数」，再给三个能跑的模型。

这篇不复述译文，也不搬运中文译本的任何段落。它复述这一章的骨架（三条渠道、组件清单、从初始设计到加消息队列的改进），然后补三个自写模型：**端到端投递率的级联与重试该用在哪**、**幂等去重窗口的判据**、**设备 token 清理周期的公式**。

## 一、本章骨架：三条渠道与一次改进

**需求**：推送通知（iOS 走 APNs、Android 走 FCM）、短信（Twilio/Nexmo）、邮件（SendGrid/Mailchimp）三条渠道；软实时、延迟尽量小；触发可以是客户端事件或服务端定时任务；规模 1000 万推送 + 100 万短信 + 500 万邮件每天；用户要能退订。

**初始设计**：一个通知服务器提供发送 API、校验邮箱/手机号、查库取数据，然后直接调第三方服务。

**初始设计的挑战**：单点故障（一台通知服务器挂了就全挂）、扩展性差（数据库/缓存/处理揉在一台机器里）、性能瓶颈（发送本身资源消耗大）。

**改进设计**：把数据库和缓存移出通知服务器；水平扩展多台通知服务器；引入消息队列解耦——触发服务只管往队列里丢事件，工作进程从队列里拉事件、再调第三方投递。消息队列还顺手当了流量缓冲。

这一步改进的结论可以用一句话概括：**解耦买的是「各部分可以独立扩缩容」，不是「可靠」**。可靠这件事，讲义单独给了一节，而可靠性的真正问题是**乘出来的**。

## 二、增量一：端到端投递率是乘出来的，重试要用在低成功率环节

讲义给「可靠性」配了两个机制：防止数据丢失（通知数据持久化到数据库 + 通知日志库）和去重（按事件 ID 判重）。这两个机制解决的是「别丢」和「别重」，但**「最后能不能到」取决于每一环的成功率乘起来**。

下面这个脚本把六环成功率乘起来，再算重试对每一环的提升：

```python
"""通知的端到端投递率是各环节成功率的乘积；重试只对低成功率环节值得做。

只依赖标准库；输出确定性。
"""

STAGES = [
    ("通知服务器校验", 0.999),
    ("消息队列", 0.999),
    ("工作进程投递", 0.995),
    ("第三方推送服务", 0.980),
    ("APNs/FCM 送达", 0.980),
    ("设备在线", 0.800),
]

DAILY = 16_000_000   # 1000 万推送 + 100 万短信 + 500 万邮件

print("环节级联（端到端投递率 = 各环节乘积）")
print("%-22s %9s %12s" % ("环节", "成功率", "累计投递率"))
acc = 1.0
for name, p in STAGES:
    acc *= p
    print("%-22s %8.3f %11.4f" % (name, p, acc))
lost = int(DAILY * (1 - acc))
print()
print("每天 %d 条，按此链路预期丢失 %d 条（%.1f%%）" % (DAILY, lost, 100.0 * (1 - acc)))
print()
print("重试对单一环节的提升：1 - (1 - p)^k")
print("%-22s %s" % ("环节成功率", "   k=1      k=2      k=3"))
for p in (0.999, 0.98, 0.80):
    row = "  p=%.3f    " % p
    for k in (1, 2, 3):
        row += "  %.6f" % (1.0 - (1.0 - p) ** k)
    print(row)
print()
print("结论：对 p=0.999 的环节，三次重试只提升 1e-9 量级；")
print("      对 p=0.80 的环节，两次重试就补上 16 个百分点 —— 重试要用在低成功率环节上，")
print("      也就是「推送不到就降级走邮件/短信」这一类，而不是消息队列这种高成功率环节。")
```

```text
消息队列                      0.999      0.9980

设备在线                      0.800      0.7630

      对 p=0.80 的环节，两次重试就补上 16 个百分点 —— 重试要用在低成功率环节上，
      也就是「推送不到就降级走邮件/短信」这一类，而不是消息队列这种高成功率环节。
```

三处值得停下来：

**第一，每一环都很稳，乘起来仍然掉。** 校验 0.999、队列 0.999、工作进程 0.995、第三方 0.98、APNs/FCM 0.98、设备在线 0.80——端到端 **0.763**。1600 万条/天，按这条链路预期丢失 **379 万条（23.7%）**。这里的大头不是「系统不稳」，而是**设备在线率 0.80**——近四分之一的设备此刻拿不到推送。这就是为什么「推送送达率」和「用户收到率」是两个数。

**第二，重试在高成功率环节上几乎没用，在低成功率环节上是数量级提升。** 对 p=0.999 的环节，三次重试只提升 10⁻⁹ 量级；对 p=0.80 的环节，**两次重试就补上 16 个百分点**（0.80 → 0.96），三次 0.992。所以重试的正确用法是「推送不到就降级走邮件/短信」——把低成功率环节换成另一条链，而不是在消息队列这种高成功率环节上反复重试。

**第三，「可靠性」要拆成三个问题问：** 别丢（持久化与日志）、别重（幂等，下一节）、最后到（端到端投递率与降级链路）。讲义把前两个给了机制，第三个没给判据——判据就是「乘出来一个数，然后只对贡献最大的那个低成功率环节做重试或降级」。

## 三、增量二：幂等窗口盖得住最大重试延迟就够

讲义的去重是这么写的：通知事件首次到达时检查事件 ID，已见过就丢弃，否则发送。这句话藏着一个参数——**「见过」要存多久**。存太短，重试晚来一步就判成新事件，重复投递；存太长，内存/存储吃紧。

判据其实一行就能写出来：**窗口 = 最大重试延迟 + 1**。重试的延迟上限由重试策略决定，所以窗口大小是重试策略的函数，不是拍出来的。下面这个确定性模拟把这句话跑成一张表（顺序事件 ID、5% 事件在 3 步之后重试一次）：

```python
"""幂等去重的窗口判据：窗口要盖得住最大重试延迟，再大只浪费内存。

确定性事件流：顺序 ID，5% 事件在 3 步之后重试一次。
窗口存最近 W 步见过的事件 ID；在窗口内 -> 视为重复并丢弃。
只依赖标准库；输出确定性。
"""
TOTAL = 5000
RETRY_RATIO = 0.05
RETRY_DELAY = 3

def simulate(window):
    """返回(漏判重复数, 窗口内存上限, 重试事件总数)"""
    seen = []
    retries = [int(TOTAL * RETRY_RATIO * (i % 10 == 0)) for i in range(TOTAL)]
    dup_sent = 0
    retry_events = 0
    for i in range(TOTAL):
        # 新事件：顺序 ID，必然未见过
        if i in seen:
            seen.remove(i)
        seen.append(i)
        if len(seen) > window:
            seen.pop(0)
        # 固定比例的事件在 RETRY_DELAY 步后重试一次
        if i % int(1.0 / RETRY_RATIO) == 0 and i >= RETRY_DELAY:
            retry_id = i - RETRY_DELAY
            retry_events += 1
            if retry_id in seen:
                pass
            else:
                dup_sent += 1
                if retry_id in seen:
                    seen.remove(retry_id)
                seen.append(retry_id)
                if len(seen) > window:
                    seen.pop(0)
    return dup_sent, window, retry_events

print("事件流：%d 个新事件，%.0f%% 在 %d 步后重试一次" % (TOTAL, RETRY_RATIO * 100, RETRY_DELAY))
print("%-4s %10s %10s %10s" % ("窗口", "漏判重复", "内存上限", "漏判率"))
for W in (1, 2, 3, 4, 5, 10):
    dup, mem, retry = simulate(W)
    print("%-4d %10d %10d %9.2f%%" % (W, dup, mem, 100.0 * dup / max(1, retry)))
print()
print("结论：窗口 >= 最大重试延迟 + 1 时漏判归零，再大只浪费内存。")
print("      窗口大小 = max(重试延迟) + 1，是重试策略的函数，不是拍出来的。")
print("      换个延迟：把重试延迟从 3 改成 6，窗口就要开到 7。")
```

输出：

```text
事件流：5000 个新事件，5% 在 3 步后重试一次
窗口         漏判重复       内存上限        漏判率
1           249          1    100.00%
2           249          2    100.00%
3           249          3    100.00%
4             0          4      0.00%
5             0          5      0.00%
10            0         10      0.00%

结论：窗口 >= 最大重试延迟 + 1 时漏判归零，再大只浪费内存。
      窗口大小 = max(重试延迟) + 1，是重试策略的函数，不是拍出来的。
      换个延迟：把重试延迟从 3 改成 6，窗口就要开到 7。
```

读法：

- 重试延迟 3 步时，窗口 1~3 漏判 **全部 249 个重试事件**（漏判率 100%），窗口 4 漏判 0——正好卡住 `重试延迟 + 1`。
- 窗口从 4 加大到 10，漏判数不再下降，内存上限却从 4 涨到 10。**窗口的有效信息只有「最大重试延迟 + 1」这么大，再大是纯粹的开销。**
- 重试延迟从 3 改成 6，窗口就要开到 7。**改重试策略必须同步改窗口**，否则就是静默的重复投递——这类 bug 和「丢 query 的 URL 规范化」一样，日志里完全正常，只是用户重复收到同一通知。

真实系统里「事件 ID」常带时间戳或版本，窗口实现往往是一个带 TTL 的集合（比如 Redis 的 `SETEX` 或布隆过滤器）。TTL 的判断标准同上：**TTL = 最大重试延迟 × 安全系数**，而不是「经验上设 1 小时」。

## 四、增量三：死 token 的清理周期是可算的

推送 token 会失效：卸载 app、换机、重装、系统侧过期。死 token 留在表里不会报错，但会向第三方推送服务发无效投递——浪费带宽，还会被当成低质量发件方限流。讲义的「联系信息收集」只说「把 token 存进设备令牌表」，没说它什么时候该删。

假设每月失效 5%（卸载/换机/过期），模拟 12 个月，看不同清理周期下「清理前的峰值死占比」：

```python
"""设备 token 的失效与清理：不清理，无效投递率会单调上升。

固定月失效率，固定模拟步长，无随机数 -> 输出确定性。
"""
N = 10_000_000
MONTHS = 12
DIE_RATE = 0.05          # 每月失效 5%（卸载/换机/系统过期）

def simulate(clean_every):
    dead = 0.0
    records = []
    peak = 0.0
    for m in range(1, MONTHS + 1):
        live = N - dead
        newly_dead = live * DIE_RATE
        dead += newly_dead
        if m % clean_every == 0:
            peak = max(peak, dead / N)     # 清理前的峰值
            dead = 0.0
        records.append(dead / N)           # 清理后的月末值
    avg = sum(records) / MONTHS
    return peak, avg, int(MONTHS / clean_every)

print("初始 %d 万 token，每月失效 %.0f%%，模拟 %d 个月" % (N // 10000, DIE_RATE * 100, MONTHS))
print("%-10s %16s %16s %12s" % ("清理周期", "清理前峰值死占比", "平均月末死占比", "年清理次数"))
for clean in (1, 2, 3, 6, 12):
    peak, avg, cleans = simulate(clean)
    exact = 1.0 - (1.0 - DIE_RATE) ** clean
    print("%-10d %14.1f%% %15.1f%% %12d   (峰值公式 1-(1-q)^C = %.1f%%)" % (clean, peak * 100, avg * 100, cleans, exact * 100))
print()
print("读法：")
print("  - 清理周期从 12 个月缩到 3 个月，清理前的峰值死占比从 46% 降到 14%；")
print("  - 峰值公式是 1-(1-q)^C，周期 C 越短峰值越低，但清理次数按 12/C 线性上涨；")
print("  - 死 token 不是「留着没事」：向死 token 投递既浪费带宽，")
print("    还会被第三方推送服务当成低质量发件方而限流；")
print("  - 选周期就是在这两条曲线（峰值死占比 vs 清理次数）之间取可接受的交点，")
print("    判据可直接写成：峰值死占比 <= 你能容忍的无效投递率。")
```

输出：

```text
初始 1000 万 token，每月失效 5%，模拟 12 个月
清理周期               清理前峰值死占比          平均月末死占比        年清理次数
1                     5.0%             0.0%           12   (峰值公式 1-(1-q)^C = 5.0%)
2                     9.8%             2.5%            6   (峰值公式 1-(1-q)^C = 9.8%)
3                    14.3%             4.9%            4   (峰值公式 1-(1-q)^C = 14.3%)
6                    26.5%            11.7%            2   (峰值公式 1-(1-q)^C = 26.5%)
12                   46.0%            23.4%            1   (峰值公式 1-(1-q)^C = 46.0%)

读法：
  - 清理周期从 12 个月缩到 3 个月，清理前的峰值死占比从 46% 降到 14%；
  - 峰值公式是 1-(1-q)^C，周期 C 越短峰值越低，但清理次数按 12/C 线性上涨；
  - 死 token 不是「留着没事」：向死 token 投递既浪费带宽，
    还会被第三方推送服务当成低质量发件方而限流；
  - 选周期就是在这两条曲线（峰值死占比 vs 清理次数）之间取可接受的交点，
    判据可直接写成：峰值死占比 <= 你能容忍的无效投递率。
```

读法：

- **峰值死占比由公式 1 − (1 − q)ᴄ 给出**（C 是清理周期、q 是月失效率）：每月清 → 峰值 5%；3 个月清 → 14.3%；6 个月 → 26.5%；一年才清一次 → **46%**——将近一半的设备令牌是死的，意味着每次全量推送有近一半请求是发往无效地址的。
- 清理次数按 12/C 线性上涨：每月清要 12 次、3 个月要 4 次、一年只要 1 次。**选周期就是在「峰值死占比」和「清理次数」两条曲线之间取交点**，判据可直接写成：峰值死占比 ≤ 你能容忍的无效投递率。
- 真实系统里这往往不是定时任务，而是**用第三方推送服务的回执来删**（APNs/FCM 会返回无效 token 列表）——回执驱动的清理把「定时删」变成「被告诉删」，成本从扫描全表变成处理回调，峰值死占比则仍然由回执到达的延迟决定，公式还是这条。

## 五、把三个模型套回本章（判据清单）

1. **投递率按端到端算**：把每环成功率乘起来，然后只对贡献最大的低成功率环节做重试或降级。对高成功率环节做重试是浪费资源。
2. **幂等窗口 = 最大重试延迟 × 安全系数**：改重试策略必须同步改窗口（或 TTL），窗口加大不再降低漏判，只浪费内存。
3. **死 token 清理周期用 1 − (1 − q)ᴄ 定**：先定你能容忍的峰值死占比，反推 C；或者用第三方回执驱动清理，成本从扫描变回调。
4. **消息队列是解耦不是可靠**：可靠 = 持久化（别丢）+ 幂等（别重）+ 降级链路（最后到）。
5. **限流是单独的事**：讲义把「限制发给用户的通知频率」列为独立组件——见《[限流算法实测](/blog/rate-limiter-algorithms-measured/)》，本文不复述。

- **一致性哈希**（队列分片时可能用到）：见《[一致性哈希实测](/blog/consistent-hashing-measured/)》。
- **事件溯源与可解释结论**（通知日志库的作用之一）：见《[让结论可解释](/blog/event-sourcing-and-explainable-conclusions/)》。

## 七、这三个模型判不了什么

- **各环节成功率是拍出来的**。真实的成功率要靠埋点测，且随渠道、地域、时段波动；模型给的是「乘出来一个数」的形状，不是「你系统的那个数」。
- **设备在线率是个随机变量**，不是常数 0.80；真实系统里它和推送时段强相关（夜间在线率低）。
- **重试模型假设重试独立同分布**。真实失败往往成批发生（第三方服务整体故障），幂次提升公式在相关故障下会显著高估。
- **死 token 模型的失效率是固定 5%/月**。真实的失效率随 app 生命周期（新版本发布、大版本升级）跳变，且卸载与换机的失效表现不同（前者立即，后者延迟）。
- **三个模型都不含安全**：讲义给的 AppKey/AppSecret 鉴权只是门面，推送服务的限流、封禁策略才是真实约束。

## FAQ（八、常见问题）

**端到端投递率怎么算？** 把每一环的成功率乘起来，得到的是「用户最终收到」的概率。六环各 0.999~0.80，乘出来 0.763；每天 1600 万条要丢 379 万条。大头是设备在线率，不是系统稳定性。

**重试该用在哪里？** 低成功率环节。对 p=0.80 的环节两次重试补 16 个百分点；对 p=0.999 的环节三次重试只提升 10⁻⁹ 量级。正确的做法是「推送不到就降级走另一条渠道」，不是在高成功率环节上反复重试。

**幂等窗口开多大？** 最大重试延迟 + 1（或 × 安全系数）。窗口再加大漏判不再下降，只浪费内存；改重试策略必须同步改窗口，否则会静默重复投递。

**设备 token 多久清一次？** 用公式 1 − (1 − q)ᴄ 反推：先定你能容忍的峰值死占比（比如 15%），q=5%/月时 C=3 个月。更省的做法是用第三方推送服务的无效 token 回执驱动清理。

**消息队列是不是等于可靠？** 不是。消息队列买解耦和流量缓冲；可靠 = 持久化（别丢）+ 幂等（别重）+ 降级链路（最后到），三件事是分开的。
