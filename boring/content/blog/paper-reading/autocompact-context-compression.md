## 一句话总结

AutoCompact 训练编码智能体自主学习**何时压缩上下文、保留哪些工作状态、以及如何从压缩点继续执行**，通过裁判审查 + SFT + RL 的两阶段训练，显著提升了长程软件工程任务的表现。

---

## 背景：上下文越来越长，压缩却成了瓶颈

### 长程编码任务的挑战

现代 AI 编码智能体（如 GitHub Copilot、Claude Agent）被广泛用于处理**仓库级软件工程任务**——这类任务要求智能体进行大量的代码阅读、搜索、编辑和测试操作。随着任务推进，智能体积累的上下文信息越来越多，涵盖了：

- 之前浏览过的文件和代码片段
- 已尝试但失败的修复方案
- 测试结果和错误日志
- 对代码库结构和依赖关系的理解

### 传统压缩方案的问题

面对不断膨胀的上下文，现有的压缩方案主要面临以下问题：

**1. 被动触发，无法判断时机**

传统方法通常是当上下文即将超出模型的处理窗口（context window）时，被迫进行压缩。这种"溺水救援"式的方式无法区分：

- 哪些信息是真正冗余、需要丢弃的
- 哪些信息虽然旧，但仍是解决当前问题的关键

**2. 压缩内容靠规则，不够智能**

---

## 核心方法：让 AI 自己决定压缩策略

AutoCompact 的核心思想是：**将压缩决策本身视为智能体行为的一部分**，让智能体通过学习来掌握何时该压缩上下文、压缩时保留哪些关键信息、以及压缩后如何无缝衔接继续工作。

### 三步走：决策 + 执行 + 训练

#### 第一步：裁判审查数据收集

AutoCompact 首先让**基座编码智能体**（未经过压缩策略训练的版本）执行大量真实软件工程任务。在执行过程中：

- 智能体每执行若干步后，会面临"是否压缩上下文"的决策点
- 一个独立的**裁判（Judge）** 对以下三个维度进行评估：
  1. **决策时机**：此时压缩是否合理？
  2. **生成摘要**：压缩后生成的摘要保留了关键信息吗？
  3. **后续行动**：压缩后的行为是否仍然有效？

如果裁判判定某次压缩决策有缺陷（例如：不该压缩时压缩了、或者压缩时丢失了关键信息），则用**修正后的版本替换**原轨迹，确保训练数据质量。

#### 第二步：监督微调（SFT）

用修正后的高质量轨迹对基座模型进行**监督微调（Supervised Fine-Tuning）**。这一阶段让模型学习：

- 在特定情境下应该做出什么压缩决策
- 如何生成有效的上下文摘要
- 如何在压缩后正确地继续工作

#### 第三步：强化学习（RL）联合优化

在 SFT 的基础上，进一步使用**强化学习**进行优化：

- **奖励信号**：以任务最终是否成功完成为主要奖励
- **联合优化**：同时优化编码能力和压缩决策能力，确保两者相辅相成——压缩不仅是为了节省 token，更是为了更好地完成编码任务

---

## 裁判审查机制详解

裁判（Judge）是 AutoCompact 训练 pipeline 中的关键组件，可以将其理解为一位**经验丰富的"审核员"**。

### 裁判的职责

对于每一次压缩决策，裁判需要回答三个问题：

| 维度 | 问题 |
|------|------|
| **时机判断** | 现在是压缩的好时机吗？过早或过晚压缩会不会影响任务？ |
| **内容保留** | 压缩后的摘要是否包含了继续工作所必需的关键信息？ |
| **衔接正确性** | 压缩后的智能体行为是否与压缩前保持一致性和连贯性？ |

### 为什么需要裁判？

**因为压缩决策的对错，最终要体现在任务能否成功完成上。** 仅靠人工设计规则无法覆盖真实软件工程任务中的千变万化，而裁判通过在真实轨迹上的审查，能够识别出：

- 哪些压缩决策最终导致了任务失败
- 哪些压缩虽然看似合理，但丢失了隐含的关键依赖

通过替换（revise）这些有缺陷的轨迹，AutoCompact 确保只有高质量的决策模式被用于训练。

### 两阶段训练的意义

```
基座智能体 ──→ 裁判审查轨迹 ──→ SFT ──→ RL ──→ AutoCompact 智能体
  (未训练)        (数据构建)     (模仿学习)  (策略优化)
```

**SFT 阶段**：让模型模仿修正后的好决策，打下基础

**RL 阶段**：在任务成功的驱动下，让压缩策略和编码能力联合进化——压缩不再是机械的 token 节省，而是服务于任务成功的智能决策

## 实验效果

AutoCompact 在两个主流软件工程基准上进行了评估：

### SWE-bench Verified

SWE-bench 是目前最具影响力的软件工程智能体基准，测试智能体解决真实 GitHub Issue 的能力。

| 配置 | 提升幅度 |
|------|----------|
| **AutoCompact（完整方案）** | **+9.2%**（绝对提升） |

### SWE-PolyBench Verified

SWE-PolyBench 提供了更加多样化的软件工程任务类型，覆盖了更多场景。

| 配置 | 提升幅度 |
|------|----------|
| **AutoCompact（完整方案）** | **+5.0%**（绝对提升） |

### 关键发现：预算鲁棒性（Budget Robustness）

AutoCompact 的效果在不同上下文预算下都成立：

**256K 上下文窗口设置**（几乎不会溢出）

- 即便上下文空间充裕，智能体学到的压缩策略仍然有价值
- 说明压缩的真正意义在于**识别和保留关键工作状态**，而不仅仅是防止溢出

## 为什么重要

### 1. 突破长程任务的上下文瓶颈

随着 AI 智能体承接越来越复杂的长期任务（如跨月项目维护、多仓库协作），上下文管理将成为瓶颈。AutoCompact 提供了一种可扩展的思路：让智能体自己学会管理自己的"记忆"，而不需要无限扩展上下文窗口。

### 2. 自动判断压缩时机的核心能力

传统方案要么"溺水救援"（被动触发），要么"定时压缩"（机械规则）。AutoCompact 让智能体学会了**根据任务状态判断何时压缩**——这是一种通用能力。

### 3. 压缩与编码能力的联合优化

RL 阶段不是单独优化压缩指标，而是把压缩决策作为"服务于最终任务成功"的一部分。这种联合优化让压缩策略始终围绕"帮助完成任务"展开，而不是追求某个局部最优。

## 附：核心概念速查

| 概念 | 解释 |
|------|------|
| **上下文压缩（Context Compaction）** | 将长上下文中的冗余信息提炼为紧凑摘要的过程 |
| **裁判审查（Judge Review）** | 由独立裁判评估压缩决策质量，替换缺陷轨迹的数据构建方法 |
| **SFT** | 监督微调（Supervised Fine-Tuning），用标注数据训练模型 |
| **RL** | 强化学习（Reinforcement Learning），通过奖励信号优化策略 |
| **SWE-bench** | 软件工程智能体基准，测试解决真实 GitHub Issue 的能力 |
| **工作状态（Working State）** | 智能体在解决问题过程中积累的代码理解、尝试记录等关键信息 |
