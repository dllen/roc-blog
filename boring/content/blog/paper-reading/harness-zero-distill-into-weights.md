## 一句话总结

**把专用 harness（外部辅助系统）的能力，"蒸馏"进模型的权重里。** 训练时让 Agent 当 harness 来修正学生回答，生成微调示范，从而让模型在去掉 harness 之后，依然能达到甚至超越原来挂着 harness 时的表现。

---

## 背景：harness 很好，但维护成本高

### 什么是 harness？

打个比方：

> 你要让一个实习生完成一项专业任务，比如审阅法律合同。
> - **没有 harness**：你把他一个人扔进档案室，给他一份合同让他审。他大概率漏掉关键条款。
> - **有 harness**：你派一个资深律师（harness）坐在旁边，全程盯着，随时纠正他的错误，告诉他"这条要查法条"、"这个表述有歧义"。
> - **结果**：有资深律师盯着，实习生的表现会好很多。但问题是——每换一个领域（法律、医学、金融），你就得配一个不同的资深律师。

这就是 harness 的意义：**它不直接完成任务，而是作为"环境与模型之间的中介层"，帮模型更好地理解任务、给出更正确的行动**。

### 为什么不能每个领域都配专用 harness？

- 每个领域需要不同的 harness（工具、逻辑、评判标准）
- 部署时要维护多套系统，路由逻辑复杂
- 成本随领域数量线性增长
- 推理时多一跳延迟

Google 的研究者就想：**能不能把"资深律师"的经验，直接教给实习生，让实习生以后不需要律师陪同也能干活？**

---

## 核心方法：Agent-as-Harness

```
第一步：学生模型回答任务
       ↓
第二步：生成的学生回答往往有错误
       ↓
第三步：Agent-as-Harness（由专用 harness 指导）修正学生的回答
       ↓
第四步：用"学生原始错误答案 → Agent 修正后答案"这个对比
       作为微调示范，训练学生模型
       ↓
结果：学生模型学会了在目标 harness 下的正确行为模式，
     不再需要专用 harness 在旁边
```

### 关键设计：Agent-as-Harness vs Code-as-Harness

|  | Code-as-Harness | Agent-as-Harness |
|---|---|---|
| 本质 | 一套写死的规则/代码 | 一个能自主推理的 Agent |
| 适用场景 | 规则明确的简单任务 | 需要复杂判断的前沿任务 |
| 局限性 | 只能按固定逻辑走 | 能理解上下文灵活应对 |

研究发现：**对于前沿 LLM，Agent-as-Harness 优于 Code-as-Harness**。原因很直观——修正"学生错误"本身就是一项需要推理的工作，用 Agent 来做比用固定代码更灵活。

### 训练流程图解

```
专用优化 Harness（目标领域）
    ＋
学生模型（待蒸馏对象）
    ＋
Agent-as-Harness（居中协调）
    ↓
生成修正对（学生错误 → 正确）
    ↓
微调学生模型
    ↓
部署时：只保留学生模型，去掉所有 harness
```

## 效果数据

实验覆盖知识工作、工具调用、科学等领域：

| 配置 | 宏平均成功率 |
|---|---|
| 基座模型（无 harness） | 23.3% |
| 基座模型 + 专用 harness | 41.7% |
| **Harness-Zero 训练后（去掉 harness）** | **44.3%** |

关键发现：

- **去掉 harness 之后，反而比挂着 harness 更好**（44.3% vs 41.7%）
- 行为恢复率（28 种模式）：平均 **82.3%**
- 在知识工作、工具使用、科学等多个领域均有效

为什么去掉 harness 反而更好？可能的解释：harness 在推理时提供的是"即时反馈"，但模型的注意力会被分散；蒸馏后模型直接"内化"了正确的决策模式，减少了推理时的认知负担。

## 对多领域 harness 维护团队的实用价值

如果你的团队正在维护多套专用 harness，Harness-Zero 提供了两条路径：

### 路径一：逐步蒸馏

```
第一阶段：每个领域单独跑 Agent-as-Harness，生成蒸馏数据
第二阶段：合并所有蒸馏数据，统一微调一个通用模型
第三阶段：部署通用模型，按需裁撤各领域 harness
```

### 路径二：选择性保留

对于某些高风险领域（如医疗、法律），可以：

- 蒸馏后的模型作为"兜底"
- 保留专用 harness 处理极端 case
- 平时推理走蒸馏模型，降低成本

### 维护成本的实质变化

| 项目 | 原来 | 引入 Harness-Zero 后 |
|---|---|---|
| 推理时 harness 调用 | 每请求必调 | 按需（极端 case） |
| 新增领域 | 需新增 harness | 只需蒸馏数据 |
| 系统复杂度 | O(领域数) | O(1) |
| 推理延迟 | 多跳 | 单跳 |

---

## 总结

Harness-Zero 解决了一个很实际的问题：**专用 harness 带来的能力，能不能从"外挂"变成"内功"？**

答案是能。核心方法是用 Agent-as-Harness 生成"纠错示范"，让学生模型通过微调学会正确行为。实验结果超过了原来挂着 harness 的基座水平，说明这种蒸馏是有效的。

对于需要维护多领域 harness 的团队，这是一个降低系统复杂度、提升推理效率的有力候选方案。
