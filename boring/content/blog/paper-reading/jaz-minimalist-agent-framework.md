## 一句话总结

MIT 研究员提出了一个极简智能体框架 JAZ，整个框架只有一个核心操作叫 `invoke`，所有复杂能力（记忆管理、自我反思、工具调用）都由大模型在运行时自己"现场发挥"出来——就像把一支画笔交给毕加索，只说"画吧"，剩下的他全包了。

---

## 背景：传统智能体框架有多复杂？

在说 JAZ 之前，先看看以前的智能体框架是怎么工作的。

打个比方：想象你要指挥一个机器人完成复杂任务，传统框架就像给机器人配备了一个**全身上下装满专用工具的工装裤**——

- 一个口袋专门存记忆（MemGPT 的记忆分层）
- 一个口袋专门做规划（ACE 的策略模块）
- 一个口袋专门调用工具（ReAct 的工具调度）
- 还有一个口袋专门做反思（自我改进模块）

**问题来了：**

1. **每个组件都要单独设计、调试、迭代**——口袋越多，坏了越难修
2. **组件之间接口复杂**——记忆层和规划层怎么通信？格式不匹配怎么办？
3. **大模型被框死在固定流程里**——模型像被塞进了一个流水线，只能按预设步骤走
4. **扩展新能力就得加新口袋**——越来越臃肿

代表性的复杂框架有 **MemGPT**（记忆分层）和 **ACE**（策略强化），它们确实强大，但工程复杂度也相当高。

---

## 核心方法：为什么一个 `invoke` 原语就够了？

### 什么是 `invoke`？

`invoke` 的本质是一个**通用的大模型调用接口**。每次调用时，大模型自己决定要做什么——它可以：

- 访问变量（读取历史记录）
- 调用工具（搜索、计算等）
- 修改上下文（更新记忆）
- 触发自我反思（检查自己做得怎么样）

**关键洞察**：与其预先定义"智能体需要哪些能力"，不如只定义一个**最小调用接口**，然后让大模型在每次调用中**自己写出具体实现**。

### 类比：就像问一个全能的助理

传统的框架 = 给助理一本厚厚的《工作手册》，规定第 1 步做什么、第 2 步做什么……

JAZ = 只给助理一个笔记本，说"你把这件任务记下来，然后自己决定下一步怎么做"

```python
# JAZ 的核心使用方式（伪代码）
result = invoke(
    task="帮我分析这篇用户反馈，找出三个最重要的问题",
    context={
        # 所有历史交互都变成变量，大模型自由读取
        "messages": [...],
        "user_profile": {...},
        "past_reflections": [...]
    },
    hooks={
        # 程序员可以在这里加约束钩子
        "before_invoke": check_safety,
        "after_invoke": log_result
    }
)
```

### 程序员的两大武器：变量 + 钩子

| 武器 | 作用 |
|------|------|
| **一切皆变量** | 所有输入、输出、交互历史都是变量，LLM 可以自由读取、组合、写入 |
| **钩子（Hooks）** | 程序员在关键节点插入约束或监控，不干预 LLM 的"发挥空间"，只保底 |

---

## 一切皆变量是什么意思？

这是 JAZ 最核心的设计哲学。

### 传统做法 vs JAZ 做法

**传统框架的记忆管理：**

- 系统：我要管理一个 RAG 检索
- 系统：我要维护一个短期记忆栈
- 系统：我要触发长期记忆归档

每个能力都是独立的"子系统"，各自为政。

**JAZ 的做法：**

```
所有数据 = 变量
所有变量 = 可被 LLM 自由读写
```

就像一个 **全局工作台**，LLM 可以在上面随意摆放、取用、组合信息。它不需要知道"这是记忆"、"那是工具"——它只知道"这里有变量，变量里有信息"。

### 好处

1. **无需预先分类**：信息不需要被标记为"短期记忆"或"长期记忆"，LLM 自己判断重要性
2. **打破数据孤岛**：不同来源的信息天然可以混合使用
3. **简化接口**：不需要为每种数据类型设计专用 API

## 实验效果

| 指标 | JAZ | MemGPT（Letta） | ACE |
|------|-----|-----------------|-----|
| **召回率** | 最高 | 基准（-8%） | 基准（-4%） |
| **成本** | 最低 | 2x | 未披露 |
| **框架复杂度** | 单一原语 | 多组件协同 | 多模块集成 |

**核心结论：**

- 比 MemGPT 召回率高 **8%**，成本降低 **50%**
- 比 ACE 召回率高 **4%**
- 工程复杂度却大幅降低

---

## 为什么重要？

### 1. 从"预设主义"到"涌现主义"

传统框架假设：智能体的能力可以被预先拆解和定义。

JAZ 的假设反过来了：**能力应该从大模型的通用智能中涌现**，框架只提供最小舞台。

### 2. 大幅降低工程复杂度

当只有一个原语时：

- 调试变得简单（问题一定出在 invoke 的使用方式）
- 扩展新能力不需要加新组件
- 减少模块间通信的各种坑

### 3. 重新定义"框架"的边界

JAZ 提出了一个根本性问题：**框架应该管什么？**

- 不应该管"LLM 内部怎么推理"
- 不应该管"具体能力如何实现"
- **应该管**：输入输出的编排、安全约束、运行时监控
