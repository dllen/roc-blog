> **核心洞察**：记忆的"存什么、取什么"本来不需要大模型操心——一个轻量控制器就能搞定，只有真正的推理才需要调用 LLM。

## 一句话总结

Jev-Mem 用一个叫"系统一"的轻量控制器专职管记忆，让大模型（系统二）只在复杂推理时介入——记忆操作速度提升 6.6 倍，回答质量还高了 11%。

---

## 背景：记忆系统为什么要让大模型做决策？

在 Jev-Mem 之前，主流的 AI Agent 记忆系统（比如 MemGPT）是这样工作的：

- **存储记忆时**：让 LLM 决定这条信息该归类为什么类型、建立什么关系
- **读取记忆时**：让 LLM 决定该查哪块、查多深、怎么组合

**问题在哪？**

| 痛点 | 说明 |
|---|---|
| **贵** | LLM 在记忆操作的每一步都被调用，Token 消耗极大 |
| **慢** | LLM 生成需要完整的前向计算，延迟高 |
| **大材小用** | "这条信息该存在哪个表里"这种简单决策，不需要 GPT-4 来拍板 |
| **积累效应严重** | 长程 Agent 每一步都在做记忆决策，十步就是十次 LLM 调用 |

本质上：**记忆管理是高频、细粒度的操作，而 LLM 调用是重量级操作——两者天然不匹配。**

## 核心方法：System-One / System-Two 三平面架构

### 2.1 灵感来源：认知科学的双系统理论

System-One（系统一）和 System-Two（系统二）是认知科学中的经典概念：

- **System-One**：快速、自动、无意识的决策——比如凭经验找到路、识别熟人表情
- **System-Two**：缓慢、刻意、需要思考的推理——比如做数学题、写文章

Jev-Mem 把这个分工搬到了 AI Agent 的记忆架构里。

### 2.2 三个平面的分工

```text
┌─────────────────────────────────────────────────┐
│              System-One 控制平面                  │
│   （轻量控制器 · 快速决策 · 不调用 LLM）            │
└─────────────────────────────────────────────────┘
                         ↕ 指令
┌─────────────────────────────────────────────────┐
│           结构化多关系记忆平面                     │
│   （存储语义、时序、因果、实体关系）                 │
└─────────────────────────────────────────────────┘
                         ↕ 上下文
┌─────────────────────────────────────────────────┐
│              System-Two 推理平面                  │
│   （LLM · 复杂推理 · 最终答案生成）                │
└─────────────────────────────────────────────────┘
```

#### 平面一：System-One 控制平面（Controller）

这是 Jev-Mem 的核心创新——一个**不需要 LLM 的轻量控制器**，专门负责记忆相关的一切决策。

#### 平面二：结构化多关系记忆平面（Memory）

存储记忆本身，并维护多种关系：

- **语义关系**：两条信息在主题/概念上的关联
- **时序关系**：事件发生的先后顺序
- **因果关系**：一个事件导致另一个事件
- **实体关系**：涉及哪些具体的人事物

#### 平面三：System-Two 推理平面（Reasoning）

只在**真正需要复杂推理时才调用 LLM**，比如：

- 整合多条记忆进行深层推理
- 生成最终答案或建议
- 解决需要世界知识的复杂问题

## 控制器掌管记忆：具体管哪些事？

这是理解 Jev-Mem 最关键的部分。控制器在两个阶段发挥作用：

### 3.1 存储阶段（Write Path）

LLM 处理完用户输入后，不是直接把结果扔进记忆库，而是交给 Controller：

| 控制器职责 | 具体动作 |
|---|---|
| **分配记忆类型** | 判断这是"事实记录""用户偏好"还是"任务目标" |
| **建立关系连接** | 把新记忆和已有记忆做关联（时序、因果、语义） |
| **决定存储结构** | 用图结构还是向量检索，还是两者结合 |

### 3.2 读取阶段（Read Path）

这是 Controller 最繁忙的阶段，也是节省成本最关键的地方：

| 控制器职责 | 具体动作 |
|---|---|
| **查询路由** | 理解用户问题，决定该查哪些记忆分区 |
| **分配检索预算** | 决定这次查询允许消耗多少计算资源 |
| **图遍历** | 在记忆图上沿着关系边逐步扩展 |
| **候选打分** | 对找到的记忆片段做相关性排序 |
| **自适应停止** | 达到足够好的结果就停，不盲目多查 |

> **关键**：以上所有步骤都是 Controller 用小模型/规则执行的，**全程没有调用 LLM**。

## 实验效果

论文在 LoCoMo 基准（长程 Agent 记忆基准）上测试：

| 指标 | 结果 | 说明 |
|---|---|---|
| **LLM-as-Judge 得分** | 0.777 | 比最强基线高 **11%** |
| **记忆构建速度** | 158 秒 | 是最快竞品的 **6.6 倍** |
| **查询延迟** | 0.93 秒 | 降低 **36.7%** |

### 消融实验关键发现

- **去掉 Controller 改用纯 LLM**：速度骤降，Token 消耗翻倍
- **只保留 Controller 不做图结构**：召回率下降明显——多关系记忆图本身很重要
- **三者齐备（完整 Jev-Mem）**：质量和速度同时最优

---

## 为什么重要：不仅仅是记忆系统

Jev-Mem 的思路可以推广到 Agent 的其他决策环节：

```text
当前大多数 Agent 框架                    Jev-Mem 思路
┌─────────────────────────┐              ┌─────────────────────────┐
│  Tool Selection → LLM   │     →        │  Tool Selection → 轻量控制器│
│  Memory Ops → LLM       │     →        │  Memory Ops → 轻量控制器  │
│  Planning → LLM         │     →        │  Planning → 轻量控制器   │
│  Reasoning → LLM ✅      │     =        │  Reasoning → LLM ✅       │
└─────────────────────────┘              └─────────────────────────┘
```

**核心原则**：把"快、频、简"的决策和"慢、稀、难"的推理分开，让合适的组件做合适的事。
