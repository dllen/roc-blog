## 一、本章骨架：地图 101、三类服务、两个存储量

**背景事实**：Google Maps 2005 年上线；到 2021 年日活 10 亿，覆盖全球 99% 的区域，**每天有 2500 万次实时位置更新**。

**范围（讲义用面试问答敲定）**：10 亿 DAU；聚焦三个功能——**位置更新、导航（含 ETA）、地图渲染**；道路数据来自多个来源，TB 级原始数据；**需要路况**以准确估算时间；出行方式要支持步行/骑车/开车；多站点导航与商家地点照片不在本次范围内。

**非功能需求**：**准确性**（不能给用户指错路）；**流畅导航**；**数据与电量消耗**（客户端要尽量少耗流量与电量，这对移动设备很关键）；通用可用性与可扩展性。

**地图 101**（讲义特意补的基础概念）：

- *定位与投影*：经纬度定义位置；把 3D 映射到 2D 叫地图投影，几乎所有投影都会扭曲几何；Google 用的是墨卡托的改进版 **Web Mercator**。
- *地理编码 / 逆地理编码*：地址 ↔ 地理坐标；实现方式之一是**插值**——利用来自 GIS 等来源的数据把街道网络映射到坐标空间。
- *Geohashing*：把地理区域编码成字母数字串，递归四分地球。
- *地图渲染（瓦片）*：不渲染一张巨大的图，而是切成小瓦片，客户端只下载相关瓦片再拼接；**不同缩放级别有不同的瓦片**；整个世界缩到最小只需一张 256×256 的瓦片。
- *路网图*：路口是节点、道路是边；导航算法多用 **Dijkstra 或 A\* 的改进版**；**寻路性能对图的大小极敏感**，不能把整个世界做成一张图再跑算法。
- *路由瓦片*：像瓦片一样把世界细分成越来越小的图；路由瓦片持有对相邻瓦片的引用，遍历时可拼成更大的路网图——**显著降低内存带宽，只加载给定起点/终点对所需的瓦片**；但长路线拼小瓦片仍然耗时耗内存，所以**要用不同精细度的路由瓦片**，算法按目的地选合适精细度。

**粗略估算**：存储上——**世界地图瓦片约 70 PB**（基于所有瓦片，并考虑了大量相似瓦片如广袤沙漠的压缩），元数据可忽略，道路信息以路由瓦片形式存。导航请求——10 亿 DAU、每周用 35 分钟 ⇒ 每天 50 亿分钟；GPS 更新请求批量发送 ⇒ **QPS 约 20 万，峰值 100 万**。

## 二、增量一：70 PB 是怎么来的，以及为什么高层级不能预生成

讲义给了「世界地图瓦片约 70 PB」这个数，但没有说明它对应多少张瓦片。用 Web Mercator 的规则补上：**第 z 层的瓦片数是 4^z**（每放大一级，每一维变成两份）。

```python
"""地图瓦片的存储账：为什么高层级瓦片不能全部预渲染。

Web Mercator 下第 z 层的瓦片数是 4^z。讲义给的量：世界地图瓦片约 70 PB。
只依赖标准库；输出确定性。
"""
TILE_PX = 256
TILE_KB = 20               # 单瓦片平均字节（256x256 PNG 的量级，估）
LECTURE_PB = 70            # 讲义给的世界地图瓦片存储量

def tiles_at(z):
    return 4 ** z

total = 0
for z in range(0, 21):
    total += tiles_at(z)
print("Web Mercator：第 z 层瓦片数 = 4^z（每放大一级，每维变成 2 份）")
for z in (0, 5, 10, 14, 18, 20):
    print("  zoom %2d -> %13s 张瓦片" % (z, format(tiles_at(z), ",")))
print("  0..20 级累计 %s 张" % format(total, ","))
print()
print("若 0..20 级全部预渲染，按每瓦片 %d KB 估：" % TILE_KB)
storage_pb = total * TILE_KB * 1024 / 1e15
print("  %s 张 x %d KB = %.0f PB" % (format(total, ","), TILE_KB, storage_pb))
print("  讲义给的是 %.0f PB —— 同一量级。讲义补充这个数字「考虑了大量相似瓦片（例如广袤沙漠）的压缩」，" % LECTURE_PB)
print("  也就是真实系统靠**相同瓦片只存一份**（内容寻址去重）拿到这个数，而不是靠更好的压缩算法。")
print("  反过来看：讲义的 %.0f PB 相当于平均每瓦片 %.0f KB。" % (LECTURE_PB, LECTURE_PB * 1e15 / total / 1024))
print()
print("单看最高几层：")
for z in (16, 18, 20):
    n = tiles_at(z)

print("判据：")
print("  - 高层级瓦片的数量是指数级，而实际存在的瓦片远少于理论值（大量是海面/沙漠，可复用）；")
print("  - 所以高层级必须「按需渲染 + 缓存热点」，不能预生成——这就是瓦片服务存在的理由；")
print("  - 存储的真正杠杆是「相同瓦片只存一份」（内容寻址/去重），讲义的 70 PB 正是这个效果。")
```

三处结论：

**第一，瓦片数量是指数级的。** zoom 10 只有 104 万张，zoom 18 是 687 亿张，zoom 20 是 **1.1 万亿张**；0 到 20 级累计 **1.47×10¹² 张**。按每瓦片 20 KB 估，光「全部层级全部预渲染」就是 **30 PB**。讲义给的 70 PB 相当于平均每瓦片 **47 KB**——同一量级，这说明讲义的数字是自洽的。

**第二，讲义那句「考虑了大量相似瓦片（例如广袤沙漠）的压缩」说的不是压缩算法，是去重。** 真实系统里，海洋、沙漠、无人区的瓦片内容完全相同，**内容寻址只存一份**才是那个数量级的来源；压缩算法带来的收益远小于去重。所以存储的真正杠杆是「相同瓦片只存一份」+「按需生成」。

**第三，也是最实用的一条：高层级瓦片不可能预生成。** zoom 20 一层即使每张只占 1 KB，也要 **1.1 PB**；而现实中这些瓦片绝大多数根本没人看过。所以高层级必须是「**按需渲染 + 缓存热点**」——这就是瓦片服务存在的理由：它是一个「请求驱动 + 热点缓存」的渲染层，而不是一个离线批量生成器。

## 三、增量二：路由瓦片的精细度分级，代价是平方级

讲义说：长路线拼接小而精细的路由瓦片仍耗时耗内存，所以要用不同精细度的瓦片。把「加载多少」算出来：

```python
只依赖标准库；输出确定性。
```

## 四、增量三：A\* 的局部性，以及那个最容易写错的破平规则

讲义说导航算法多用「Dijkstra 或 A\* 的改进版」，而且强调「只加载给定起点/终点对所需的瓦片」。这两句话在算法层是同一件事：**搜索必须是局部的**。把局部性量化：

```python
"""Dijkstra 与 A* 的展开节点数：启发式在什么条件下才有效。

讲义说「大多数导航算法使用 Dijkstra 或 A* 的改进版」。这里在同一张网格上实测对比，
并扫三种障碍密度——障碍越密，直线启发式与真实距离的偏差越大，A* 的优势越小。
只依赖标准库；输出确定性。
"""
import heapq

W, H = 60, 60
START, GOAL = (0, 0), (W - 1, H - 1)

def make_blocks(density, seed):
    s = seed
    def rand(n):
        nonlocal s
        s = (s * 1103515245 + 12345) % (1 << 31)
        return s % n
    blocks = set()
    target = int(W * H * density)
    while len(blocks) < target:
        blocks.add((rand(W), rand(H)))
    return blocks

def neighbors(x, y, blocks):
    for dx, dy in ((1, 0), (-1, 0), (0, 1), (0, -1)):
        nx, ny = x + dx, y + dy
        if 0 <= nx < W and 0 <= ny < H and (nx, ny) not in blocks:
            yield nx, ny

def manhattan(x, y):
    return abs(x - GOAL[0]) + abs(y - GOAL[1])

def dijkstra(blocks):
    dist = {START: 0}
    pq = [(0, START)]
    visited = set()
    expanded = 0
    while pq:
        d, (x, y) = heapq.heappop(pq)
        if (x, y) in visited:
            continue
        visited.add((x, y))
        expanded += 1
        if (x, y) == GOAL:
            return d, expanded
        for nx, ny in neighbors(x, y, blocks):
            nd = d + 1
            if nd < dist.get((nx, ny), 1 << 30):
                dist[(nx, ny)] = nd
                heapq.heappush(pq, (nd, (nx, ny)))
    return None, expanded

def astar(blocks, tiebreak="goal"):
    """A*。

    破平规则：f 相同时优先取哪条。
      tiebreak="goal"  -> 取 g 更大的（更靠近目标），走廊式搜索；
      tiebreak="start" -> 取 g 更小的（更靠近起点），在开阔网格上会退化成广度扩展。
    """
    dist = {START: 0}
    pq = [(manhattan(START[0], START[1]), 0, START)]
    visited = set()
    expanded = 0
    while pq:
        _, tie, (x, y) = heapq.heappop(pq)
        d = -tie if tiebreak == "goal" else tie
        if (x, y) in visited:
            continue
        visited.add((x, y))
        expanded += 1
        if (x, y) == GOAL:
            return d, expanded
        for nx, ny in neighbors(x, y, blocks):
            nd = d + 1
            if nd < dist.get((nx, ny), 1 << 30):
                dist[(nx, ny)] = nd
                tie = -nd if tiebreak == "goal" else nd
                heapq.heappush(pq, (nd + manhattan(nx, ny), tie, (nx, ny)))
    return None, expanded

print("网格 %dx%d，起点 (0,0)，终点 (%d,%d)，障碍用固定种子伪随机散布" % (W, H, GOAL[0], GOAL[1]))
print()
print("%-10s %12s %14s %14s %12s %12s" % ("障碍密度", "可走格", "Dijkstra", "A*", "少展开", "路径步数"))
for density in (0.0, 0.02, 0.08):
    blocks = make_blocks(density, 20261126)
    walkable = W * H - len(blocks)
    dd, ed = dijkstra(blocks)

print()
```

三处结论：

**第一，同一张图、同一条最短路，A\* 展开 119 个节点，Dijkstra 展开全部 3,600 个——少 96.7%。** A\* 展开的节点数几乎就是路径长度（118），因为曼哈顿启发式在这个网格上足够准，搜索被压成一条通向目标的走廊。三种障碍密度（0% / 2% / 8%）下 A\* 的展开数几乎不变，障碍只让走廊绕一点。

**第二，也是这一节最值钱的一条：**f 相同时的破平规则决定 A\* 有没有用。** 开阔网格上所有节点的 f = g + h 都相同；若按「更靠近起点」破平，搜索退化成广度扩展，**展开数从 119 涨到 3,600——和 Dijkstra 一样**；按「更靠近目标」破平才是走廊式搜索。这是同一份代码里最容易写错的一处，而且**症状极隐蔽**：路径仍然最优、结果完全正确，只是慢了几十倍。

**第三，这解释了讲义为什么说真实系统用「改进版」。** 真实路网有主干道、有高速、有单行道与转向限制，启发式要按这些结构设计；纯欧氏/曼哈顿启发式在结构复杂的路网上会明显偏乐观，退化程度介于本例的两个极端之间。而只要搜索保持局部，「只加载起点/终点附近的瓦片」就成立——远处的瓦片真的不需要进内存。

## 五、把三个模型套回本章（判据清单）

1. **瓦片存储的杠杆是去重与按需生成，不是压缩算法**：0..20 级理论 1.47×10¹² 张；相同瓦片只存一份是 70 PB 的来源；高层级必须按需渲染 + 缓存热点。
2. **路由瓦片按路线长度分档**：瓦片数按 (距离/精细度)² 涨（100 km：1 km 档 1 万张/128 MB vs 25 km 档 17 张/0.2 MB）；策略是粗档全局规划 + 细档末段精化。
3. **A\* 的破平规则要按「更靠近目标」**：写反了会退化成 Dijkstra（119 → 3,600 展开），结果仍然正确、只是慢几十倍——这类 bug 只在压测里才看得见。
4. **ETA 与路况**：讲义把路况列为必需（为了准确估算时间），导航 QPS 20 万、峰值 100 万；ETA 侧的实时性预算与「非功能需求里的电量/流量」是同一笔账。
5. **客户端省流量/省电**是独立约束：瓦片缓存、位置上报频率、ETA 预取都在消耗电量，三者与准确性的取舍要一起看。

## 七、这三个模型判不了什么

- **每瓦片 20 KB、每条边 32 B、每张瓦片 400 条边都是估的**。真实数值随编码格式与瓦片内容变化；瓦片数量与层级的结论不依赖这些估值（它只依赖 4^z）。
- **A\* 的实验用的是规整网格 + 随机障碍**，不是真实路网。真实路网有结构（主干道、单行道、转向限制），启发式的有效性介于本例两个极端之间；本例能确定的是「破平规则」这条实现结论，与网格形态无关。
- **没算真实路网的规模**。讲义说道路数据是 TB 级原始数据，但没给图规模（多少节点、多少边）；「寻路性能对图大小极敏感」这句只能定性感受，无法从本章的数字推出具体延迟。
- **没算 ETA 的误差**。讲义把路况列为 ETA 准确性的前提，但没给「历史平均 vs 实时路况」的误差对比，也没有 ETA 的预测模型。
- **三个模型都没碰「每天 2500 万次实时位置更新」的写入侧**：位置更新本身是写密集负载，与瓦片渲染完全不同的两条流（讲义提到位置服务与地图渲染是分开的两套服务）。

## FAQ（八、常见问题）

**70 PB 的地图瓦片是怎么来的？** Web Mercator 下第 z 层 4^z 张，0..20 级累计 1.47×10¹² 张；按每瓦片 20 KB 估是 30 PB，讲义给 70 PB 相当于平均 47 KB/张。关键是讲义说的「大量相似瓦片的压缩」——真实做法是**内容寻址去重**（海洋、沙漠瓦片只存一份）+ 高层级按需生成，而不是靠更强的压缩算法。

**高层级瓦片能预生成吗？** 不能。zoom 20 一层就有 1.1 万亿张，即使每张 1 KB 也是 1.1 PB，而绝大多数没人访问过。必须按需渲染 + 缓存热点。

**路由瓦片的精细度怎么定？** 按路线长度分档。瓦片数按 (距离/精细度)² 涨：100 km 路线用 1 km 档要 1 万张瓦片、128 MB 路网，25 km 档只要 17 张、0.2 MB。但粗档给不出精确转向，所以要两级规划：粗档找方向，细档做末段精化。

**A\* 一定比 Dijkstra 快吗？** 取决于实现细节。同一张图上 A\* 展开 119 个节点、Dijkstra 展开 3,600 个（少 96.7%）；但如果 f 相同时的破平规则写成「偏向起点」，A\* 会退化成广度扩展，展开数变成 3,600——结果依然最优，只是慢了几十倍。

**这一章和「邻近服务」那篇重复吗？** 不重复。那两篇讲的是按位置找静止的商家、按位置找移动的人；这一篇讲的是把世界切成瓦片、按瓦片分精细度做路径搜索，共同的只有 geohash 这一个概念。
