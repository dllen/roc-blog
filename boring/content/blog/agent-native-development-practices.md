前几讲一直在讨论软件工程里的几道缝隙：人的意图怎样变成规格说明，规格又怎样变成实现。道理不能让人永远停留在讨论道理的阶段——**总得从「能运行的原型」开始**，让它跑起来，看看究竟造出了什么。Agent Native 开发要接着处理的就是这一步之后的事。

Agent Native 开发要回答的，正是接下来这一步该怎么组织：问题从「怎样让它写出这段代码」扩展成「**怎样组织一个能够持续开发、验证和修正的软件生产过程**」。

Agent Native 开发不只是「代码由 AI 写」，还包括让工程知识成为 Agent 找得到、用得上、能够验证的东西。

本文整理自南京大学《生成式软件工程》2026 秋第 8 讲「Agent Native 开发」（主讲：jyy），[原始讲义](https://jyywiki.cn/GSE/2026/lect8.md)。文中三个实践案例的原始出处列在文末。

## 一、Let it fail：失败可能出在哪一层

讲义先给出方法论前提：**这些道理都重要，但在某个时刻我们总得开始。**做出一个符合当前 Spec 的原型，让它运行起来，看看究竟造出了什么。

这一节的核心论点是「Let it fail」——但讲义立刻加了一个限定，避免它被误读成「随便交差」：

> 「Let it fail」并不是鼓励随便交差，而是**允许原型暴露我们的错误**。

失败可能出现在三个不同的层：

| 失败层级 | 说明 |
|---------|------|
| 实现层 | 实现可能没有满足规格 |
| 规格层 | 规格也可能没有表达真正的需求 |
| 假设层 | 即使两者都对上了，需求里关于**用户、规模和运行环境**的假设仍然可能不成立 |

讲义给了一个非常具体的例子：**纸面上说得通的选课系统，遇到两个人同时抢最后一个名额，就可能出现另一副面孔。**这正是本质复杂性——并发冲突不会因为代码写对了就消失。

这个三层分解决定了后面所有机制的形态。**先把想法变成可以观察的东西，才有机会知道下一步该改实现、改规格，还是改架构。**这三种「该改什么」的判断，正是后面所有 Harness 机制要服务的目标。

## 二、Ralph Loop：提示词没变，工作区变了

讲义先用一条能力增长曲线定位处境：从聊天式问答，到能够读写文件、执行命令和使用工具的 Agent。然后做了一个思想实验——如果模型足够聪明，拥有足够的工具、资源和行动权限，也许给它一个 Bash 入口，它就能组织完成极其复杂的工作。讲义诚实地标注：造芯片、证明黎曼猜想是对这种想象的**夸张表达**，并不是说今天的模型已经具备这些能力。

现实的问题恰恰在于，模型还没有万能到可以放心托付一切。尤其是**工程品味**：什么值得抽象，哪里应该保持简单，什么改动正在让项目变得难以维护，**并不容易只靠一句提示词教会**。

于是讲义提出全讲的关键一问：既然一次回答不能解决全部问题，**能不能让它不断尝试？**

答案来自 Geoffrey Huntley 提出的 **Ralph Loop**。循环骨架只有一行：

```bash
while true; do
    cat PROMPT.md | claude -p
done
```

讲义对这五行代码的解释是全讲最值得细读的部分：**每轮都把同一个任务交给 Agent，让它检查当前成果，选择下一项工作，修改并验证。**一次会话结束，下一轮重新开始。关键在于——**提示词没变，工作区却变了**：上一轮实现了功能、留下了测试结果、记录了失败原因，下一轮就能接着这些状态继续。

讲义随即给出一个非常克制的提醒（被单独强调）：

> **循环本身并没有魔法。** `while true` 不会自动识别「已经完成」或「无法改进」，也不能保证下一轮一定比上一轮好。

实际使用时，**必须另外定义验收条件、预算或停止条件**；反复遇到相同失败时，还要判断是不是任务表述、工具或架构出了问题。讲义用一句话收束这节的分寸感：**不断运行是产生进展的机会，能识别进展的反馈才让这些机会有价值。**

## 三、工作区即状态，Agent 是状态迁移

理解这种开发方式，讲义建议借用一个熟悉的视角：**Everything is a state machine.**

**工作区就是状态。**它不只包含当前代码，也包含需求、设计文档、测试用例、运行结果、日志和待办事项。Agent 读入这些状态，执行一轮工作，把它们变成下一份状态。于是**一次开发可以理解为一次状态迁移**：

```text
"这个功能尚未实现"
        ↓
"已有实现但测试失败"
        ↓
"失败原因已定位，修复通过了检查"
```

由此推出一个关于 long-horizon task 的重要结论：**长期任务不能只靠一段越来越长的聊天记录维持。**所谓 long-horizon task，是需要跨越许多步骤、许多次会话才能完成的任务。**新一轮 Agent 必须能够从留下来的材料中判断四件事**：目标是什么、已经做了什么、哪些结论有证据、哪里还没有完成。**如果关键经验只存在于上一轮的上下文里，下一轮就得重新踩坑。**

讲义用一对交接语句的对比把这一点讲得非常清楚：

| 交接写法 | 评价 |
|---------|------|
| 「选课功能已完成」 | 一句**含糊的交接** |
| 「普通选课已通过，两个请求竞争最后一个名额的测试失败，失败记录位于某份日志」 | 给出了**可以继续工作的起点** |

由此得到一条关于文档的判断标准：**文档在这里承担的是协作状态，而不是工作量展示。写得越多未必越有用，能让接手者恢复判断才有用。**

状态还可以**分叉**。有了 Git、Jujutsu 这样的版本管理工具，不同 Agent 可以在不同工作区推进不同任务，再把结果集成起来。但讲义立刻补上一个重要限定：**版本控制允许并行，并不自动保证任务彼此独立。**两个改动各自正确，合在一起仍可能出错；大家也可能同时扑向同一个问题。**要让并行有收益，任务划分、依赖关系和集成检查都得跟上。**

## 四、重新发现 CI/CD

这一节从「工作区每轮都在变」直接推出 CI/CD 的必要性。论证链条只有几步：既然开发会不断改变工作区，而我们希望进入主干的状态都是「好」的，就应该在集成这些改变时执行检查。然后把「好」变成具体条件——**能构建、测试通过、没有破坏已有功能、满足项目的重要约束**。

讲义用一句自嘲收尾：**「祝贺你，重新发明了 CI/CD。」**

关键在于讲义如何拆解这个吓人的名字。它的机制「可以从一个很小的想法理解」：**事件发生时，执行指定动作。**提交、推送、发起合并请求、主干更新，都是可以挂接动作的节点。

讲义在这里做了一个漂亮的回溯——之前尝试让 Agent 在合适时机「播放声音」提醒人的需求，也可以从这里重新理解：**需要把动作落实到明确的事件，而不能只期待它记得做。**把动作换成运行检查、构建页面、部署网站，就是开发流程中的 Hook。

落点是一个从个人小需求到工业基础设施的类比：**「播放声音」与「跑 CI/CD」用的是同一套 Hook 机制，区别只在于挂的是哪个事件、跑的是哪段动作。**

### 把发布流程也写成 Spec

讲义指出一个很多人低估的点：**CI/CD 真正琐碎的部分，往往是业务规则。**

| 业务规则问题 | 具体场景 |
|------------|---------|
| 合并交互 | 两个合并请求单独都通过，合起来却失败，怎么办？ |
| 失败处理 | 测试偶尔失败，是重跑还是隔离，谁负责修？ |
| 例外通道 | 线上急需修复时，谁有权例外放行，之后怎样补检查？ |
| 发布竞态 | 两个发布任务同时运行，新版本先完成，旧任务随后才结束，**会不会把网站覆盖回旧版**？ |

**这些问题都不是写出一份配置文件就自然消失的。**今天可以把配置交给 Agent，但**仍然要表达清楚希望系统怎样工作**。

讲义给出的流程约定：

1. **合并请求有新提交，就重新运行 Lint 和测试；合并前检查与最新主干的组合，失败时禁止合并。**
2. `main` 更新后，对这次提交运行检查并构建页面；**全部成功才部署这次构建的产物，失败则保留上一版。**
3. **多次发布发生重叠时，不能让过时产物覆盖新版本；例外放行需要明确的权限与记录。**

讲义特意澄清了两个概念的分工：**Lint 是对代码格式、可疑写法或项目约定的静态检查，不必先运行完整业务就能发现一部分问题；测试则通过执行程序检查具体行为。二者承担不同职责，不能因为其中一项通过，就省掉另一项。**

这一节最有价值的方法论是**验收失败路径**（讲义称之为检验「门是否真的关得住」）：

- 故意引入一次 Lint 错误，确认它**真的阻止合并**；
- 让测试失败，确认**没有发布新页面**；
- 再修好错误，确认能正常更新。

讲义明确对比了两种验收方式：这样检验的是「门是否真的关得住」，**而不只是「配置文件看起来像那么回事」**。

## 五、CI 阻止，Agent 修正

讲义指出一个在 Agentic AI 时代才出现的**不对称**：**Agent 能以很快的速度生成代码，也能以很快的速度积累维护负担。**

讲义列举了课堂中观察到的几种很有代表性的偏执（并特意声明：这些是实际协作中的观察，**不是对所有模型的统一排名**）：

- 一句话能交代的事情写成 20 KB 文档；
- 把每个细节在多个地方重复一遍；
- 在不重要的小问题上反复加固；
- 写出功能勉强能跑、但人类很难读懂的代码。

应对思路很明确：**如果项目仍然需要人共同维护，这些倾向就必须受到实在的约束。只在规范里写「请保持简洁」，效果未必稳定；把可以机械判断的部分交给检查，反馈就能进入每一次开发循环。**

讲义把「哪些检查值得写」做成了四类问题的对照表：

| 观察到的问题 | 可机械化检查的约束 |
|------------|------------------|
| 文档不断膨胀 | 为特定入口文件设置合理的大小限制，把详细材料放到有组织的位置 |
| 模块边界不断被绕过 | 检查禁止的依赖方向 |
| 代码难以阅读 | 用格式化、静态检查和复杂度规则拦下一部分明显问题 |
| 同一项规则到处复制 | 检查重复内容，并要求共同维护者判断应当保留哪一处事实来源 |

讲义加了一条重要的自制约束：**这些约束都是针对具体项目设计的，不能把「文件短」简单等同于「设计好」。**

另一条被单独强调的原则是**反馈的可操作性**：自动检查也应说明**为什么失败、怎样修复**。只返回一个红叉，会让 Agent 花时间猜规则；**指出违规依赖的位置与允许的访问方式，才能让下一轮有明确方向**。

讲义把三者合成一个闭环（加粗强调）：

> **CI 阻止，Agent 修正，再由同一套标准验证。**

但讲义同时划了一条边界，这一条在 Agent 时代尤其危险：

> 负责实现功能的 Agent，**不能因为过不了检查，就单方面把标准调低。**

测试确实可能过时，架构规则也可能需要改变，但**修改这些规则需要回到需求和设计理由**。讲义用一句对比把这件事的严重性说透了：**删掉失败断言得到的绿色，与修复程序得到的绿色，颜色相同，含义完全不同。**

### 为什么这条边界最危险

这条边界的危险在于它把一个「看起来像流程问题」的东西变成了**验证器可信度问题**。

Agent 有强烈的动机让检查变绿——它被训练成完成任务。而**修改规则的成本由它不承担**，由未来的维护者承担。一旦验证器由被验证者控制，它就不再是验证器：它退化成一个可以被协商的门槛。

工程上的应对通常是把规则的修改权从实现 Agent 手里拿走——比如规则文件放在 Agent 只读的路径、修改规则需要独立的签名或 review、或者把规则本身也写成测试来固定。无论用哪种办法，**判据都是同一个：规则变更的成本必须落在提出变更的人身上，而不是落在被规则约束的未来维护者身上。**

## 六、Agent Native：把工程知识放进环境

讲义在这里给出了 **Harness** 这个核心术语的定义：**围绕 Agent 建立的运行环境、工具、约束与反馈机制，常被统称为 Harness。**这个词可以理解为**让模型的能力能够稳定用于具体工作的整套配套设施**。

由此定义 Agent Native 开发的内涵：**它不仅是「代码由 AI 写」，还包括让工程知识成为 Agent 找得到、用得上、能够验证的东西。**

讲义引用 OpenAI 的 Harness engineering 文章作为例证：代码交给 Agent，人的工作转向组织环境、表达意图和建设反馈机制。文中把仓库知识组织为可查阅的结构，让 Agent 直接启动和观察应用，用 Lint 与结构测试检查架构边界，并持续提交小规模清理改动。

讲义把这个长句拆成四个可以逐条自检的具体问题——这是本讲最可操作的部分：

| 问题 | Agent Native 的回答 |
|------|-----------------|
| **1. 人脑中的知识有没有外部化？** | 「我们一直这样做」对刚开始一轮工作的 Agent 没有意义。重要决定应进入版本管理，说明**背景、约束和理由**；入口文档负责引导查阅，**不必把所有知识一次塞进去** |
| **2. Agent 能不能自己看到程序行为？** | 开发选课页面时，每次都等人转述「按钮好像没反应」，反馈既慢又容易丢信息。若它能**启动独立实例、操作页面、查看日志**，就能直接检查点击后是否发出请求、服务端怎样处理、界面最终显示什么 |
| **3. 架构品味能否转化为可检查的规则？** | 页面组件是否绕过业务层直接访问数据？某类日志是否缺少必要字段？错误处理是否沿着约定接口传播？**当然，哪些规则值得固定下来，本身仍然需要判断** |
| **4. 清理工作是否持续发生？** | 生成代码不断复制已有的不良模式，等到全仓库都长成同一种坏样子再修，成本就高了。小规模、经常性的修复可以**抑制扩散，让下一轮 Agent 看到更好的例子** |

讲义在最后加了一个很诚实的自嘲（源自对 OpenAI 那篇文章的课堂吐槽）：读到这里自然会想「好，那把完整的 CI 门控拿来看看吧！」——课堂里的「ClosedAI」吐槽，指的是文章没有附上该内部项目可直接复用的完整配置；**不能由此说它没有 CI**，文中确实介绍了相关约束。

但这个落点是有意义的：**看懂经验总结，还不等于拥有一套能在自己项目里工作的工程系统。**

## 七、三种把反馈做实的实践

讲义给出三个来自一线的案例，主题都是**怎样让反馈真的能被用来判断进展**。

### （1）Stripe 的 Minions：不是每一步都需要模型作决定

Stripe 用 **Blueprint** 组织混合工作流：**实现任务、修复失败等步骤交给 Agent，运行 Lint 等确定步骤则由普通代码保证执行**。它还**限制 CI 重试轮数，而不让一次任务无限循环**。

设计思路可以直接提炼为一条分工原则：**如果某一步每次都必须执行，且执行方式已经明确，就把它写进流程。模型适合处理需要理解和选择的问题，固定工序可以由程序可靠地完成。**

讲义还提醒了一句关于重试的话：**重试也有成本；连续失败时，应该判断反馈是否带来了新信息，而不是把「再试一次」当作永远正确的回答。**这正是对 Ralph Loop 那一节警告的工程回应。

### （2）Anthropic 的 C 编译器实验：验证方式改变了任务的可分性

团队让 **16 个 Agent 协作**编译 Linux 时却发现**大家撞上同一个错误，重复修复、互相覆盖**。后来他们改变策略：用 GCC 编译大部分文件，只让新编译器负责一部分，再通过切换文件的编译器**缩小失败范围**。不同 Agent 因而能处理不同子集暴露的问题；单独通过、组合失败的文件仍需进一步排查。

讲义提炼出的洞察比案例本身更重要：

> 原来只知道「整个内核编译失败」，大家只能涌向同一个入口；有了**可信的参照和可缩小的失败集合**，就能把大问题拆成可以分别推进的工作。

**增加 Agent 数量之前，先改善任务表示和反馈，可能更有效。**这句话可以直接当作多 Agent 系统的第一性设计原则。

### （3）StrongDM 的工程自述：验收依据要与实现分开

他们发现 Agent 有两个失效模式：**可能用过于简单的实现应付狭窄测试，也可能修改测试去迁就实现。**对策是：**把端到端用户故事组织为场景，常放在代码库之外，作为相对独立的验收依据**。对于包含 Agent 的产品，**还会观察多次执行轨迹中满足用户意图的情况，而不只看一次测试是否全绿**。

第二个做法是**为外部服务建立行为替身**，模拟 API 与边界情况，使大量场景能够反复运行。讲义把它翻译成课程场景，非常具体：

> 把它迁移到选课系统，可以设计「**最后一个名额刚被别人占走**」「**请求已成功提交，但响应丢失**」这样的练习环境。开发 Agent 不必等真实学生踩到这些问题，才知道失败是什么样子。

讲义同时给出了一个必要的警告：**替身与真实系统之间的差异也必须验证，否则我们只是造出了一个特别容易过关的考场。**

## 八、垃圾回收解决不了的问题

讲义用这一节点出「DeepSeek Harness」这个题目的着眼点：**模型之外，还有一整套让工作得以推进的装备。那些看似理所当然的设计，常常来自真的做过、失败过、修正过。仅凭空想象，很难一下子想到所有有效的边界和反馈方式。**

然后讲义提出了一个层层递进的追问：**但持续清理技术债，也有它解决不了的问题。**它给了一个纯粹的负载结构例子，不涉及任何代码质量问题：

> 假设所有用户的数据都可以集中在一个**写入节点**，其他节点保留完整副本以分担读请求。用户少时它很直观；写入和数据量持续增长后，**增加读副本未必能解除瓶颈，因为每个副本仍要承担全部更新**。

结论句很重：**把代码整理得再漂亮，也不会自动改变这种负载结构。**

讲义随后指出**失败在这里提供的价值**——**帮助我们看清应当改变哪一层设计**。这把「让 it fail」从一个态度变成了一个有信息量的动作。

**真实的失败案例（Friendster）**：讲义引用 Friendster 的亲历工程师 Dathan Pattishall 在 2006 年的复盘：他讨论了主库加完整副本所面临的写入复制、I/O 与复制延迟问题，并提出**按用户拆分数据**，使不同服务器只承担部分数据与相应负载；但据他的叙述，**这个方案没有在 Friendster 顺利推进，后来在 Flickr 得到了应用**。

讲义对这份复盘的解读很克制而准确：

> 这份复盘不能单独解释一家公司的全部兴衰，却很清楚地暴露出一个工程问题：**看出架构应该怎样改，和组织真的能够把它改掉，是两件事。**

及时重构既要求技术判断，**也要求团队有能力调整分工、迁移数据、安排上线，并承担变化过程中的成本**。一句很重的判断：**一直修补局部症状，可能只是在更认真地维护一个已经不合适的前提。**

## 九、好想法也会在落地中失败

讲义把风险从代码推广到产品和组织：**这样的风险不局限于代码。互联网时代已经有许多诱人的想法，在架构、运营或需求验证环节遭遇现实。**

**案例一（仓配系统）**：讲义以年报披露为据，指出配送中心当时的业务量低于原设计容量的 40%，订单量也低于实现盈利所需的水平。提炼出的教训是：**如果需求密度没有得到验证，庞大的仓配系统会把一次判断错误变得昂贵。**讲义同样加了限定：**这个结论是对案例的工程分析，不能简化成「某一种技术架构导致了全部失败」。**

**案例二（Quibi）**：Quibi 尝试为移动设备提供精品短视频，在 2020 年的告别信中宣布结束业务，并提出两种可能原因：**想法本身不足以支撑独立流媒体服务，或者推出时机不合适。**讲义的限定同样克制：**这是管理层的回顾和解释，并不是对失败原因的实验鉴定。**但它很适合提醒我们：**有内容、有技术、有产品形态，并不等于用户需要这样一个独立服务。**

讲义由此给出本讲对 Agent 时代最重要的一个判断：

> **Agent 让实现更便宜，却不会使这些问题消失。**

一个好的想法可以迅速生成许多页面、文档和功能，也可能逐步「slop 化」：看起来越来越像成品，**重复、冗余和未经验证的假设却越来越多**。讲义给出了一个因果倒置的描述，非常精准：**局部测试不断通过，真实用户仍然可能不愿意用；代码越写越多，原先需要检验的关键假设反而被埋住了。**

因此，开始做原型与及时重构并不矛盾。三者的分工很清晰：**原型让我们碰到现实，反馈让我们知道哪里需要改变，重构则把这种认识落实为新的结构。**最后一句是对全讲的收束：

> **如果失败没有改变我们的判断，下一次循环可能只会更快地重复上一次。**

## 十、实践机会，会变成判断力的差距

讲义把风险从「项目」提升到「社会」，起点是一个朴素的观察：**不做很多次、不见过很多个真实系统，就很难做好。**

**工程判断来自比较**——讲义给出了三个只有亲身经历过才会真正明白的对比式问题：

- 相似需求为什么有人做得简洁，有人越做越乱？
- 同一个检查为什么在这里有用，在那里只制造噪声？
- 什么时候应该继续局部修补，什么时候必须改变架构？

结论：**只有亲手遇到这些问题，经验才不只是几个名词。**

然后讲义引入了 **Token 作为实践资源门槛**的论断。Token 是模型处理和生成内容所消耗的基本计量单位，**也代表了一部分实际试错成本**。没有足够的 Token 预算，就很难获得同等数量、同等规模的自主开发尝试。

讲义对「没有 Token，就没有做很多次尝试的机会」这句话做了很克制的解读：**强调的是这种实践资源的门槛；它不是说花钱越多就一定学得得好。**

更关键的是，讲义指出**资源必须和学习动机、学习能力结合**：愿不愿意追问一次失败？能不能读懂别人的设计？是否会把观察变成下一轮可验证的改进？——**这些都影响着尝试最终产生什么。**

一个正反对照：

> 只是让 Agent 不停输出，并不会自动积累工程能力。相反，**能理解反馈的人，会把一次尝试留下的经验组织起来，使后面的尝试更有价值。**

讲义最后触及了教育的过渡期问题。「这不就斩杀了吗……」背后，是对教育过渡期的担忧：新的软件生产方式已经出现，让更多人获得高质量实践机会的教育组织却未必及时跟上。**实践机会的差距可能积累成判断力的差距。**讲义明确标注：**这是本讲提出的风险判断，不是已经注定的未来。**

收尾一句直接说明了课程的任务定位：除了讲方法，还要让学生有机会**运行系统、观察失败、理解好的设计，并真正完成几轮有反馈的修改**。**我们想培养的，是知道怎样让下一次尝试比上一次更有价值的人。**

## 十一、它不解决什么

- **Harness 不能弥补模型能力的不足。**讲义自己标注了：造芯片、证明黎曼猜想是对能力想象的夸张表达。环境设计得再好，模型判断错了照样产出错误的代码——环境能提供更快的失败信号，提供不了正确性。
- **Ralph Loop 的产出质量不由循环本身决定。**循环不识别「已完成」也不识别「无法改进」，进展判据必须从外面提供。**没有停止条件的 `while true` 只会更快地重复上一次失败。**
- **CI 门禁不判断需求本身对不对。**它能验证「实现满足规格」，但规格是否表达了真正的需求，是第一层失败，门禁管不到。让 it fail 的三层分解里，门禁只覆盖了第一层。
- **行为替身造不出真实系统的全部行为。**讲义明确警告：**替身与真实系统之间的差异也必须验证**，否则造出来的只是一个特别容易过关的考场。
- **「少 Agent」不是普适结论。**Anthropic 那个案例讲的是**任务可分性不足**时增加 Agent 只会撞车。任务划分与失败边界都清晰时，增加 Agent 确实是有效的并行手段。
- **判断力差距没法靠工具补。**讲义把「实践机会」列为门槛，而门槛只决定机会的数量，不决定机会是否被认真使用。

## 十二、一句话总结

好 Harness 不是让 Agent 跑更多轮，而是让它**每一轮失败后留下的证据更可读**。「失败记录位于某份日志」与「功能已完成」之间的差别，就是两者之间的全部差距。

**CI 阻止，Agent 修正，再由同一套标准验证**——闭环的前提是验证器可信，而验证器可信的前提是**修改规则的成本不落在被约束者身上**。
