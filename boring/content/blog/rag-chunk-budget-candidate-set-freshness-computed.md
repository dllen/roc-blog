RAG 的三笔账？分块怎么切、候选集有多大、索引有多新鲜。课程讲义把 RAG 拆成「离线建库 + 在线检索生成」两部分，也给了两套实现（LangChain 版与零依赖手写版），但三笔账它是定性的。这篇把它们算出来。

## 一、讲义的骨架：RAG 是在做什么

**问题**：传统大模型文本生成方式的三个缺点——知识截止于训练时点、无法引用私域知识、无法追溯来源。讲义用一个比喻区分三种「孩子」：**直接靠模型答（微调）/ 外挂知识库再查（RAG）/ 两者结合**；并强调**微调的代价**：每次知识更新都要重新训练，数据、算力、版本管理都要重做。

**RAG 的定义与组成**：检索增强生成 = 在生成前先检索外部知识，把结果注入上下文。两大组成部分：**知识库构建（离线）**——文档切分、embedding、建立索引；**检索（在线）**——把问题向量化后找相似内容；**生成（在线）**——把检索到的内容与问题一起交给模型。

**两种实现路径**：一是用 LangChain 把「加载与切分 → 建索引 → 定义提示词 → 定义状态 → 组装步骤 → 编译运行」串成一条链；二是零 ML 依赖的手写版——中文按字、英文数字按词做简单分词，用词频向量当「假 embedding」，离线建索引再检索。

## 二、增量一：分块大小的可行区间是 [A/k, A]

讲义说「切分文档」，但没说切多大。这笔账可以只靠两条约束夹出来：

```python
"""RAG 的分块预算：拼得全与信噪比之间只有一个最优 c。

自写模型；参数为本脚本设定（估）。只依赖标准库；输出确定性。
"""
ANSWER_TOKENS = 300      # 回答一个问题需要的上下文量 A（tokens，估）
DOC_TOKENS = 10000       # 一篇文档
DOCS = 1000
TOP_K = 4                # 每次注入的 chunk 数
WINDOW = 8192            # 模型上下文窗口（tokens）

print("一、chunk 大小 c 的两难")
print("   答案需要 A = %d tokens；每次注入 top-%d 个 chunk = %d*c tokens" % (ANSWER_TOKENS, TOP_K, TOP_K))
print()
print("%-8s %14s %14s %14s %14s %16s" % ("c", "拼全需几个", "答全概率", "单 chunk 精度", "有效 token", "利用率"))
for c in (64, 128, 256, 512, 1024, 2048, 4096):
    need = -(-ANSWER_TOKENS // c)                 # 拼全答案需要几个 chunk
    coverage = min(TOP_K, need) / need             # top-k 里够不够拼全
    precision = min(1.0, ANSWER_TOKENS / c)        # 单 chunk 里答案占比
    injected = TOP_K * c
    useful = injected * precision
    print("%-8d %14d %13.0f%% %13.0f%% %14.0f %15.0f%%" % (
        c, need, coverage * 100, precision * 100, useful, 100.0 * useful / injected))
print()
print("   => c < A 时**拼不全**（top-k 里装不下 A），c > A 时**信噪比掉**（单 chunk 精度 = A/c）。")
print()
print("二、c 还决定索引规模（检索侧的成本）")
print("%-8s %14s %16s %18s %18s" % ("c", "chunk 总数", "索引条目/文档", "索引相对量", "注入占窗口"))
base = None
for c in (64, 128, 256, 512, 1024, 2048, 4096):
    total = DOCS * -(-DOC_TOKENS // c)
    if base is None:
        base = total
    print("%-8d %14s %16s %17.1fx %17.1f%%" % (
        c, format(total, ","), -(-DOC_TOKENS // c), total / base, 100.0 * TOP_K * c / WINDOW))
print()
print("三、可行区间由两条约束夹出来（不用拍脑袋的目标函数）")
print("   约束 1（答全）：top-k 个 chunk 必须装得下答案 A -> k*c >= A -> c >= A/k = %.0f" % (ANSWER_TOKENS / TOP_K))
print("   约束 2（信噪）：c 越大单 chunk 精度越低（= A/c），实际取 c <= A")
print("   => 可行区间 c in [A/k, A] = [%.0f, %d] tokens" % (ANSWER_TOKENS / TOP_K, ANSWER_TOKENS))
print()
print("%-8s %14s %14s %16s %18s" % ("c", "答全概率", "利用率", "目标值", "是否在区间内"))
for c in (32, 64, 128, 256, 512, 1024, 2048, 4096):
    need = -(-ANSWER_TOKENS // c)
    coverage = min(TOP_K, need) / need
    precision = min(1.0, ANSWER_TOKENS / c)
    injected = TOP_K * c
    score = coverage * precision
    inside = (ANSWER_TOKENS / TOP_K) <= c <= ANSWER_TOKENS
    print("%-8d %13.0f%% %13.0f%% %15.3f %17s" % (c, coverage * 100, precision * 100, score,
          "在" if inside else "越界"))
print()
print("   => 区间内目标值恒为 %.2f（答全 100%% x 精度 A/c 随 c 上升而下降）——" % (
    1.0 * ANSWER_TOKENS / ANSWER_TOKENS))
print("      所以真正的取舍不是「哪个 c 最好」，而是**在区间内取小的那一端**：")
print("      c 越小，索引越大（下一节），但注入的信噪比越高。")
print()
print("四、A 变化时区间怎么走")
for A in (100, 300, 1000, 3000):
    print("   A = %5d tokens -> c in [%4.0f, %4d]（下界 = A/k = %.0f，上界 = A）" % (
        A, A / TOP_K, A, A / TOP_K))
print()
print("判据：")
print("  - **c 太小 -> 答不全**：c < A 时要靠多个 chunk 拼，top-k 装不下就漏；")
print("    c 太大 -> 信噪比掉**：单 chunk 精度 = A/c，c=2048 时只有 %.0f%% 的注入内容是答案。" % (
    100.0 * ANSWER_TOKENS / 2048))
print("  - **c 还决定索引规模**：c=64 -> %s 个 chunk、c=4096 -> %s 个（差 %.0f 倍）——" % (
    format(DOCS * -(-DOC_TOKENS // 64), ","), format(DOCS * -(-DOC_TOKENS // 4096), ","),
    (4096 / 64)))
print("    检索侧的扫描成本、embedding 成本都跟着走，所以 c 不能随便调大。")
print("  - **c 的可行区间是 [A/k, A]**：下界来自「top-k 装得下答案」，上界来自「单 chunk 精度 = A/c」。")
print("    区间内目标值恒为 1.0，所以取舍落在**索引规模**上 -> 判据：")
print("    **先估答案需要多少上下文 A，再定 chunk 大小**，而不是照抄别人的 512；")
print("    区间内取小的那一端，用更大的索引换更高的信噪比。")
```

三处结论：

**第一，c 太小会答不全。** 答案需要 A = 300 tokens 时，c=64 意味着要靠 5 个 chunk 才能拼全，而只注入 top-4 → **答全概率只有 80%**；c=128 时拼全只需 3 个 chunk，够用。

**第二，c 太大信噪比塌掉。** 单 chunk 里答案的占比就是 A/c：c=512 → 59%，c=1024 → 29%，c=2048 → **15%**。**判据：注入进上下文的 85% 是噪声时，模型要在一堆无关内容里找答案**——这不是「模型不够强」，是输入信号比的问题。

**第三，可行区间是 [A/k, A]，区间内的取舍落在索引规模上。** 下界 A/k 来自「top-k 要装得下答案」，上界 A 来自「单 chunk 精度 = A/c」。区间内目标值恒为 1.0（答全 100% × 精度），所以真正的取舍不是「哪个 c 最好」，而是**索引多大**：c=64 → 15.7 万个 chunk、c=4096 → 3,000 个，**差 64 倍**。**判据：先估答案需要多少上下文 A，再定 chunk 大小，而不是照抄别人的 512**；区间内取小的那一端，用更大的索引换更高的信噪比。

## 三、增量二：分词粒度通过候选集大小传导到召回

讲义的手写实现里，中文「按字」切、英文数字「按词」切。这个选择的代价可以量化：

```python
"""字面检索的失效不是「相关性差」，是「精确为零」。

自写模型：一个小型中文问答语料 + 字符/词双粒度倒排，测三类查询的召回。
只依赖标准库；输出确定性。
"""
import re
from collections import defaultdict

# 刻意设计：同义改写与目标文档**没有任何共享字符**，
# 这样能区分「排序靠后」与「根本不在候选里」两种失效。
DOCS = {
    1: "提升检索质量需要重排序模型",
    2: "上下文压缩降低提示词消耗",
    3: "向量检索用语义相似度代替关键词匹配",
    4: "知识库构建包括切分文档与建立索引两个离线步骤",
}

def chars(s):
    return set(re.findall(r"[一-鿿]", s))

def words(s):
    """极简中文分词：按 2 字滑窗切（够演示分词粒度的影响）"""
    out = set()
    for i in range(len(s) - 1):
        out.add(s[i:i + 2])
    return out

def build_index(texts):
    idx = defaultdict(list)
    for did, text in texts.items():
        for tok in texts_tokenize(text):
            idx[tok].append(did)
    return idx

def texts_tokenize(text):
    return chars(text) | words(text)

def search(query, idx, docs, topk=3):
    q = chars(query) | words(query)
    score = defaultdict(int)
    for tok in q:
        for did in idx.get(tok, []):
            score[did] += 1
    ranked = sorted(score.items(), key=lambda kv: (-kv[1], kv[0]))
    return ranked[:topk]

idx = build_index(DOCS)

CASES = [
    ("原句查询", "提升检索质量", 1),
    ("同义改写", "怎样让搜出来的结果更准", 1),
    ("原句查询", "上下文压缩", 2),
    ("同义改写", "怎样让输入更短更省", 2),
    ("原句查询", "向量检索", 3),
    ("同义改写", "不靠字面靠意思", 3),
    ("词序颠倒", "质量检索提升", 1),
]

print("一、三类查询在字面检索下的表现（top-3，混合字/词倒排）")
print("%-16s %-22s %10s %12s %14s" % ("类型", "查询", "gold", "召回 top-3", "Jaccard(最高)"))
for kind, q, gold in CASES:
    ranked = search(q, idx, DOCS)
    ids = [d for d, _ in ranked]
    hit = "命中" if gold in ids else "**未命中**"
    best = 0.0
    for did, _ in ranked:
        qs = chars(q) | words(q)
        ds = chars(DOCS[did]) | words(DOCS[did])
        best = max(best, len(qs & ds) / len(qs | ds))
    print("%-16s %-22s %10d %12s %14.2f" % (kind, q, gold, hit, best))
print()
print("   => 原句查询全部命中；**同义改写全部未命中**（Jaccard = 0）。")
print("      这不是「排得靠后」，而是**根本不在候选集里**。")
print()
print("二、为什么不是「排得靠后」而是「根本不在候选里」")
for kind, q, gold in CASES:
    qset = chars(q) | words(q)
    dset = chars(DOCS[gold]) | words(DOCS[gold])
    shared = qset & dset
    print("   [%-8s] 「%s」 vs gold(%d)：共享 token %2d 个 %s" % (
        kind, q, gold, len(shared), sorted(shared)[:6] if shared else "-> 无任何重叠"))
print()
print("三、字级 vs 词级倒排的规模")
CORPUS_CHARS = 1000 * 2000      # 1000 篇 x 2000 字
CORPUS_WORDS = int(CORPUS_CHARS / 1.5)
for name, toks in (("字级（单字）", CORPUS_CHARS), ("词级（平均词长 1.5 字）", CORPUS_WORDS),
                   ("双字滑窗", CORPUS_CHARS)):
    print("   %-22s 倒排条目 %13s" % (name, format(toks, ",")))
print("   => 字级条目数是词级的 %.2f 倍；双粒度并存会再翻一倍 —— 这是「便宜但不准」与「贵但准」的账。" % (
    CORPUS_CHARS / CORPUS_WORDS))
print()
print("四、真正的传导链：分词粒度 -> 候选集大小 -> 答案进入 top-k 的概率")
DOCS_N = 1000
AVG_DOCS_PER_CHAR = 200   # 单字平均命中的文档数（停用字命中极广，估）
AVG_DOCS_PER_WORD = 30    # 词平均命中的文档数（估）
QUERY_CHARS = 4           # 查询长度（字）
QUERY_WORDS = 2
TOPK = 4
for name, tokens, avg in (("单字切", QUERY_CHARS, AVG_DOCS_PER_CHAR),
                          ("双字切", QUERY_CHARS, AVG_DOCS_PER_CHAR // 2),
                          ("整词切", QUERY_WORDS, AVG_DOCS_PER_WORD)):
    cand = min(DOCS_N, tokens * avg)             # 候选并集（独立假设，高估）
    p_in_topk = min(1.0, TOPK / cand)
    print("   %-8s 查询 token %d 个 x 平均命中 %3d 篇 -> 候选集 %4d 篇 -> 答案进 top-%d 的概率 %6.2f%%" % (
        name, tokens, avg, cand, TOPK, p_in_topk * 100))
print()
print("   => 粒度越细，候选集越大，**答案被挤出 top-k 的概率越高**；")
print("      单字切 %.2f%% vs 整词切 %.2f%% —— 量级差 %.1f 倍。" % (
    min(1.0, TOPK / min(DOCS_N, QUERY_CHARS * AVG_DOCS_PER_CHAR)) * 100,
    min(1.0, TOPK / min(DOCS_N, QUERY_WORDS * AVG_DOCS_PER_WORD)) * 100,
    (min(1.0, TOPK / min(DOCS_N, QUERY_WORDS * AVG_DOCS_PER_WORD)) /
     max(1e-9, min(1.0, TOPK / min(DOCS_N, QUERY_CHARS * AVG_DOCS_PER_CHAR))))))
print()
```

```python
"""RAG 的准确率天花板：不是检索算法，是索引新鲜度。

"""
DOCS = 100000             # 文档数
CHUNKS_PER_DOC = 20       # 每篇文档的 chunk 数

PICK_STALE = 0.5          # 新旧版本同时命中时，模型选中旧版的概率（估）
QUERY_TOUCH_CHANGED = 0.05  # 查询命中「已变更区域」的概率（估）

total_chunks = DOCS * CHUNKS_PER_DOC
stale_per_day = DOCS * CHANGE_RATE * CHUNKS_PER_DOC * CHANGED_FRACTION
print("   文档 %s 篇 x 每篇 %d chunk = %s chunk" % (format(DOCS, ","), CHUNKS_PER_DOC,
                                                    format(total_chunks, ",")))
print("   每天变更文档 %.0f%%，其中变更区域约占 %.0f%% -> 每天新增过期 chunk %s（占全库 %.3f%%）" % (
    CHANGE_RATE * 100, CHANGED_FRACTION * 100, format(int(stale_per_day), ","),
    100.0 * stale_per_day / total_chunks))
print()
print("%-14s %18s %18s %20s" % ("清理周期 T", "过期 chunk 占比", "冲突窗口", "答错率"))
for T in (1, 7, 30, 90, 365):

    err = QUERY_TOUCH_CHANGED * PICK_STALE * (1 - (1 - stale_ratio) ** 1)
    print("%-14s %17.3f%% %17d 天 %19.2f%%" % (
        "%d 天" % T, stale_ratio * 100, T, err * 100))

    QUERY_TOUCH_CHANGED * 100, PICK_STALE * 100))

print("   => 清理越频繁，重建量越大（按存量/T 摊到每天）；不清理则冲突窗口无限拉长。")
print("      T=1 天：重建 %s chunk/天（占全库 %.3f%%），冲突窗口 1 天；" % (
    format(int(stale_per_day), ","), 100.0 * stale_per_day / total_chunks))
print("      T=30 天：重建量不变（存量/T = 日增量），但冲突窗口拉长到 30 天 —— **代价全在窗口长度上**。")
print()
print("三、删除旧 chunk 会换成另一种失效：查不到")
print("   「删旧建新」在 T 天窗口里留下空窗（文档已删、新版未建）-> 查询召回为空；")
```

## 五、把三个模型套回本章（判据清单）

1. **c 的可行区间 = [A/k, A]**：下界来自 top-k 装得下答案，上界来自单 chunk 精度 A/c；区间内目标值恒为 1.0。
2. **c 太小答不全**：c=64、k=4、A=300 → 答全概率 80%；**c 太大信噪比塌**：c=2048 → 精度 15%。
3. **区间内的取舍落在索引规模**：c=64 → 15.7 万 chunk，c=4096 → 3,000 个，差 64 倍。
4. **字面检索对同义改写是「精确为零」**：共享 token 0、Jaccard 0、不在候选集里；**换词序照常命中**。
5. **分词粒度 → 候选集 → 答案进 top-k**：单字切 800 篇候选 → **0.50%**；整词切 60 篇 → **6.67%**（差 13.3 倍）。
6. **索引规模**：字级倒排是词级的 1.50 倍，双粒度再翻一倍。
7. **先保答案在候选集里，再谈排序**（排序层见已发的 BM25/重排那篇）。
8. **准确率天花板 = 索引新鲜度**：T=30 天过期 6.0%、答错 0.15%；T=365 天过期 73%、答错 1.82%。
9. **缩短窗口靠原地更新，不靠删旧建新**；重建成本恒为日增量（4,000 chunk/天）。

## 七、这三个模型判不了什么

- **A（答案需要的上下文量）、k（注入 chunk 数）、语料规模、单字/词的平均命中文档数、变更率、变更区域占比、模型「选中旧版」的概率全是估的**。其中 **A 最敏感**：A 估成 1,000 而不是 300，整个可行区间就平移三倍多（c 的下界从 75 变 250）。所以 A 必须从真实问答日志里量（答案所在片段的 token 数），不能拍。
- **候选集模型假设各查询 token 命中的文档集合互相独立**，实际高度重叠（同一篇文章常含多个查询词）→ 所以「候选集 800 篇」是**高估**，真实的候选集更小、答案进 top-k 的概率比表里高。方向不变，倍数不可直接引用。
- **没算 embedding 本身的成本**。语义检索要一次查询 embedding + 一次索引 embedding（每篇文档每 chunk 一次）——**索引侧的 embedding 成本是按语料总量一次性付的**，本文只量了倒排条目数，没量向量维度的存储与检索代价。
- **没算「改写查询」这条中间路的收益**（用 LLM 把用户问题改写成多个检索式）。它同时放宽了「候选集」的边界，代价是多一次模型调用——这笔交换没算。
- **新鲜度模型假设变更只影响局部**（变更区域占该文档 20%）。整篇重写（格式调整、全文替换）会让过期比例跳到 100%，那时要按全量重建算——**所以周期要按变更模式的上界定，不是按均值**。
- **三个模型都没碰多租户与权限过滤**。真实系统里「答案在候选集里」之前还有一道「答案有没有权限被检索到」——被过滤掉的文档不会出现在候选集里，而是以另一种方式失效。

## FAQ（八、常见问题）

**chunk 应该切多大？** 可行区间 **[A/k, A]**，A 是答案需要的上下文 token 数、k 是注入的 chunk 数。本模型 A=300、k=4 → c ∈ [75, 300]，128 或 256 都行。区间内目标值恒为 1.0，所以取舍落在索引规模：c=64 → 15.7 万 chunk、c=4096 → 3,000 个，差 64 倍。**别照抄 512**。

**切小了会怎样？** 答不全。c=64 时拼全 300 tokens 要 5 个 chunk，而只注入 top-4 → **答全概率 80%**。

**切大了会怎样？** 信噪比塌。单 chunk 精度 = A/c：c=1024 → 29%、c=2048 → **15%**，注入的 85% 是噪声。

**为什么字面检索救不了同义改写？** 因为它不是「排得靠后」，而是**共享 token 归零、根本不在候选集里**（本模型三条同义改写 Jaccard 全为 0，全部未进 top-3）。而只换词序（「质量检索提升」）照常命中——**触发条件是换词，不是换序**。

**中文分词粒度的影响有多大？** 通过候选集大小：单字切候选 800 篇 → 答案进 top-4 的概率 **0.50%**；整词切 60 篇 → **6.67%**，差 13.3 倍。代价是索引规模：字级倒排条目是词级的 1.50 倍。

**那 BM25 参数怎么调？** 调不动这类问题——排序层的参数救不回「不在候选集里」的文档。**先保证答案在候选集里，再谈排序**（排序那一层见《检索质量工程：BM25、混合检索与两阶段重排》）。

**索引多久清一次？** 按「冲突窗口 = 清理周期」定：T=30 天 → 过期 chunk 6.0%、答错率 0.15%；T=365 天 → 过期 73%、答错 1.82%。**缩短窗口几乎不额外花钱**（重建量恒为日增量 4,000 chunk/天），但必须用**原地更新**而不是删旧建新，否则把「查到错的」换成「查不到」。

**答错率不高啊，0.15% 值得管吗？** 看绝对量：10 QPS 下每天 2.16 万次答错，100 QPS 下 21.6 万次——**比例固定，绝对量随 QPS 线性放大**。
