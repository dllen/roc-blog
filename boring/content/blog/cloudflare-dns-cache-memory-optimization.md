1.1.1.1 是全球最大的公共 DNS 解析器之一。它背后的缓存里存着超过 **2500 亿条**记录——在这个量级下，「每条记录浪费 1 个字节」就意味着全集群白白多烧 **250GB 内存**。

2026 年 8 月 27 日，Cloudflare 官方博客发文详细复盘了他们如何通过 5 个 Rust 层面的内存优化，把每条缓存记录的净占用从 **953 字节压到 420 字节（-56%）**，全集群省下约 **100TB 内存**——而且插入吞吐和查询延迟不但没变差，反而分别提升了 43% 和 19%。

> 本文基于 Cloudflare 官方博客文章 [*How we saved 100 terabytes of memory by optimizing 1.1.1.1's DNS cache*](https://blog.cloudflare.com/dns-cache-memory-optimization-1111/) 整理，数据与代码引自原文，部分示意图为本文重绘，评论与引申为笔者补充。

这篇文章值得细读的地方在于：它不是「换个更省的容器」这种单点技巧，而是一条完整的优化链——**每一步都在解决上一步留下的副作用**。下面我们逐一拆解。

## 1. 背景：2500 亿条记录的缓存长什么样

1.1.1.1 背后的平台在 Cloudflare 内部代号 **Big Pineapple**，同时支撑 Gateway DNS、DNS Firewall、AS112 等多项 DNS 服务。它的核心是一个巨大的 DNS 缓存：key 标识一次查询，value 存响应内容和元数据。

缓存的 key 和 value 结构大致如下（引自原文）：

```rust
pub struct CacheKey {
    qname: Name,          // 查询域名
    qtype: Rtype,         // 查询类型（A / AAAA / TXT ...）
    authenticated: bool,  // 是否经过 DNSSEC 验证
    tag: Vec<u8>,         // 业务标签
}

pub struct CacheEntry {
    timestamp: UnixTimeStamp,
    pub inception: Instant,
    pub ttl: Ttl,
    pub hits: u32,                 // 命中计数，用于淘汰决策
    pub answers: Vec<Record>,      // Answer 区
    pub authority: Vec<Record>,    // Authority 区
    pub additional: Vec<Record>,   // Additional 区
    pub errors: Vec<ExtendedError>,
    // ...
}
```

淘汰策略很常规：缓存条目数达到上限后，淘汰更老或更不热门的记录（`hits` 计数器派上用场）；每条记录自带 TTL 和创建时间。

问题出在这些「看起来人畜无害」的类型上：

- `Vec<T>` 和 `String` 是**可变**容器，天生携带容量（capacity）字段和堆预留——但缓存一旦写入就再也不改，这些「为增长预留的空间」纯属浪费；
- `Record` 内部的 `RecordData` 是个枚举，Rust 枚举的大小由**最大的变体**决定，一条只有 4 字节的 A 记录要和 136 字节的 NAPTR 记录住一样大的房子。

于是有了那个著名的乘法：**单条浪费 × 2500 亿条 = 天文数字**。下面 5 个优化，就是围绕这条乘法展开的。

## 2. 优化一：用「箱切片」替换 Vec 和 String

先看 `Vec` 在 64 位平台上的真实长相——它由栈上 3 个字段（24 字节）加堆上数据组成：

```
栈上（24 字节）                       堆上
┌──────┬─────┬──────┐          ┌───┬───┬───┬───┬───┬───┐
│ ptr  │ len │ cap  │ ───────► │ 0 │ 1 │ 2 │ 3 │   │   │
└──────┴─────┴──────┘          └───┴───┴───┴───┴───┴───┘
  8B     8B    8B                len=4, cap=6 → 2 个槽位白白预留
```

`capacity` 存在的唯一意义是支持 `push` 时的摊还 O(1) 扩容。但原文说得很直白：

> Once we store a DNS response in the cache, we never modify it again. The capacity field serves no purpose, but still costs 8 bytes per Vec.
>
> （DNS 响应存进缓存后就再也不会被修改。capacity 字段毫无用处，却每个 Vec 都要花 8 字节。）

解法是换成**箱切片** `Box<[T]>`（字符串则用 `Box<str>`）——它是「胖指针」，只有指针和长度两个字段：

```
栈上（16 字节）                       堆上
┌──────┬─────┐                  ┌───┬───┬───┬───┐
│ ptr  │ len │ ───────────────► │ 0 │ 1 │ 2 │ 3 │
└──────┴─────┘                  └───┴───┴───┴───┘
  8B     8B                      精确分配，没有任何预留
```

两层收益：

1. **栈侧**：每个字段省 8 字节（capacity），`CacheEntry` 里 8 个 `Vec`/`String` 字段，合计 **省 64 字节/条**；
2. **堆侧**：`Vec` 扩容策略通常会预留多余容量，`Box<[T]>` 按实际长度精确分配，这部分隐性浪费也一并消失。

这一步背后的通用原则是：**「一次写入、多次读取」的数据不需要为增长预留空间**。这也是为什么很多高性能系统的只读数据结构（列存文件、快照、缓存）都会选择不可变的紧凑表示。

## 3. 优化二：三段合一，用 u16 偏移标记分区

一条 DNS 响应的记录分布在三个区：Answer、Authority、Additional。优化一之后它们各自是一个 `Box<[Record]>`（16 字节胖指针），三个区就是 48 字节。

但仔细想想：三个区存的是**同一种元素**，完全可以合并成一个连续的 `Box<[Record]>`，再用两个 `u16` 偏移标记分区边界：

```
优化前：三个独立列表（3 × 16 = 48 字节指针开销）
  answers:    [ptr, len] ──► [r0, r1]
  authority:  [ptr, len] ──► [r2]
  additional: [ptr, len] ──► [r3, r4]

优化后：一个列表 + 两个 u16 偏移（16 + 4 = 20 字节）
  records: [ptr, len] ──► [r0, r1 │ r2 │ r3, r4]
  answer_end: u16 ──────────────▲
  authority_end: u16 ─────────────────▲
```

2 个 `u16`（4 字节）替换掉 2 组「指针+长度」（32 字节），**每条记录再省 28 字节**。顺带地，结构体里零散的布尔字段被打包进 bitflags，减少了结构体对齐产生的填充（padding）。

这个手法——「多个同构列表合并为一段连续内存 + 轻量偏移索引」——在列式存储、FlatBuffers、游戏引擎的资源打包里都能见到。它的收益不只是省指针，更重要的是数据变连续了，这一点对后面优化五的意义会回来。

## 4. 优化三：属主名字可选化——能从上下文推导的就不存

DNS 记录有个 `owner` 字段（记录归属的域名）。观察真实流量会发现：**绝大多数记录的 owner 就等于查询域名**（qname）——你查 `example.com` 的 A 记录，响应里大部分记录的 owner 自然也是 `example.com`。

既然如此，不如不存。owner 被改成：

```rust
pub struct Record {
    owner: Option<Box<Name>>,   // None = 与查询域名相同
    class: Class,
    ttl: Ttl,
    rtype: Rtype,
    data: RecordData,
}
```

约定很简单：`None` 表示 owner 与缓存 key 里的 qname 相同，**读取时从 key 推导**；只有 owner 确实不同的记录（比如 CNAME 指向的其他域名）才真正分配一个 `Box<Name>`。

两个值得注意的细节：

- 为什么套一层 `Box`？因为 `Option<Box<T>>` 能吃到 Rust 的 **niche 优化**：`Box` 保证非空，编译器可以用空指针表示 `None`，整个 `Option` 仍然只有 8 字节，不为「可选」多付一分钱；
- 为什么平时存**完整域名**而不是顺着压缩指针走？DNS wire format 里的名字压缩（name compression）用指针复用已出现的域名，但沿指针跳转解析很慢。缓存是「空间换时间」的生意——完整存储名字，读的时候就不用追指针了。

这一步的原则是：**能从上下文推导出来的信息就不要冗余存储**。列式存储里重复值用字典编码、HTTP/2 头部压缩（HPACK）用索引表，本质上都是同一件事。

## 5. 优化四：给枚举的大变体「装箱」

`Record` 里最肥的部分是 `RecordData` 枚举。Rust 枚举有个铁律：**整个枚举的大小 = 最大变体 + 判别值 + 对齐填充**。优化前的样子：

```rust
pub enum RecordData {
    A(Ipv4Addr),      // 4 字节
    Aaaa(Ipv6Addr),   // 16 字节
    Txt(Txt),         // 较大
    Naptr(Naptr),     // 136 字节 ← 最大变体
    Svcb(Svcb),
    // ...
}
```

NAPTR 是个相对冷门的记录类型，它的 136 字节把整个枚举撑到了 **144 字节**。这意味着流量里占比最高的 A 记录——真实数据只有 4 字节——每条也要占 144 字节，**超过 120 字节是纯填充**：

```
每条 A 记录的 RecordData（144 字节）：
┌──────┬────────────────────────────────────────────┐
│ 4B   │  140B 填充（为 NAPTR 预留，永远用不上）       │
└──────┴────────────────────────────────────────────┘
```

解法是把**大而冷门的变体放进堆**，只让常见的小变体内联：

```rust
pub enum RecordData {
    // 小而常见的变体内联存储
    A(Ipv4Addr),
    Aaaa(Ipv6Addr),
    // 大变体装箱，枚举本体只留一个指针
    Txt(Box<Txt>),
    Naptr(Box<Naptr>),
    Svcb(Box<Svcb>),
    // ...
}
```

效果立竿见影：每条 A/AAAA 记录**省下约 120 字节**。但原文很诚实地指出，装箱有两笔代价：

1. **分配器开销**：每条被装箱的记录都是一次独立的堆分配，分配器自身要为每次分配记录元数据；
2. **内存局部性差**：记录数据散落在堆的各个角落，遍历和构造响应时指针追逐、cache miss 增多。

也就是说，优化四虽然省了内存，却引入了新的性能隐患——这就引出了最后一个优化。

## 6. 优化五：返璞归真，直接存 wire format

既然结构化枚举带来这么多麻烦，不如换个思路：**缓存里的数据是只读的，为什么要存「对象」，而不直接存「字节」？**

DNS 协议本身就定义了记录的二进制线上格式（wire format）。优化五把每条缓存的所有记录数据以原始字节的形式存进**一个** `Box<[u8]>`，每条记录前加 2 字节长度前缀：

```
一条缓存条目 = 一次堆分配：
┌────────┬──────────┬────────┬──────────┬───
│ len=16 │ record 0 │ len=28 │ record 1 │ ...
└────────┴──────────┴────────┴──────────┴───
        ▲ answer_end        ▲ authority_end
（u16 偏移标记三个分区，见优化二）
```

一次改动同时消灭了优化四的两个副作用：

- **消灭零碎分配**：不再有「每条记录一次分配」，整条缓存只有 `Box<[u8]>` 一次分配，分配器元数据开销几乎归零；
- **找回内存局部性**：所有记录字节连续存放，顺序扫描对 CPU 缓存极其友好。

连响应构造都变快了：缓存命中时，大部分记录类型可以**直接 memcpy 进响应报文**，跳过了从结构体序列化的步骤。唯一的例外是**包含域名的记录**——DNS 名字压缩的指针依赖「当前名字在报文中的偏移」，预存好的字节没法直接复用，这类记录需要在拷贝时临时解析、按需压缩。

插入侧还有一个小窍门：先在**可复用的暂存缓冲（scratch buffer）**里组装好 wire format 字节，再一次性分配、拷贝进缓存。用「一次分配」替换「每条记录一次装箱分配」，这也是后面插入吞吐不降反升的原因之一。

这一步的原则最有普适性：**对只读数据而言，序列化格式往往就是最好的存储格式**。对象图（object graph）为「可变、可随机访问」付出了指针和元数据的代价；一旦数据不再变化，存紧凑字节 + 轻量索引几乎总是更优——这也是 FlatBuffers、Cap'n Proto 这类「零拷贝」格式的核心思想。

## 7. 结果：内存和速度全都要

五步走完，原文给出的基准数据：

| 指标 | 优化前 | 优化后 | 变化 |
|------|--------|--------|------|
| 单条记录净占用 | 953 字节 | 420 字节 | **-56%** |
| 单条记录实际分配 | 1.1 KB | 461 字节 | **-58%** |
| 缓存插入吞吐 | 62.5 万条/秒 | 89.3 万条/秒 | **+43%** |
| 缓存查询延迟 | 828 ns | 670 ns | **-19%** |

生产环境里，单实例的 p99 常驻内存从 **9.3GB 降到 5.3GB**；2026 年 5 月到 7 月分批灰度上线，p90/p98/p99 内存曲线呈阶梯式下降。按全集群规模折算，总共省下约 **100TB 内存**。

最值得一提的是：**这不是一次「用速度换空间」的优化**。分配次数减少、内存更连续，让吞吐和延迟跟着一起变好。内存优化和性能优化在这里殊途同归——因为它们对抗的是同一个敌人：冗余。

## 8. 对我们自己系统的启发

抛开 DNS 和 Rust 的具体语境，这套组合拳里能带走的东西不少：

**① 先做乘法，再谈优化。** 单条 533 字节的节省平平无奇，乘以 2500 亿条就是 100TB。动手前先算一笔账：你的系统里「单位开销 × 规模」是多少？规模不够大时，很多内存优化根本不值得做；规模足够大时，1 个字节都值得抠。

**② 不可变性是紧凑结构的前提。** 这 5 个优化几乎全部依赖「缓存写入后不再修改」这个前提：不需要 capacity、可以合并列表、可以直接存字节。如果你的缓存需要原地更新，大部分招数都会失效。反过来说，**设计缓存时主动选择「不可变值」，等于提前为内存优化买好了票**。

**③ 警惕语言内置类型的「隐性税」。** Rust 里的 `Vec` 容量字段、枚举按最大变体对齐、结构体填充；对应到 Java 是对象头、装箱、`HashMap` 节点开销，对应到 Go 是 slice 容量、interface 装箱。写高频数据结构时，值得花十分钟画出它的真实内存布局——很多浪费不画不知道。

**④ 每个优化都有副作用，优化是一条链。** 装箱省了枚举填充，却带来分配器开销和局部性恶化；wire format 又把这些副作用一并解决。单看任何一步都不完美，连起来才是完整方案。做优化时别指望一招制胜，要预留「解决上一步副作用」的余地。

**⑤ 用数据闭环：基准测试 + 生产曲线。** 原文既有微基准（纳秒级延迟、每秒插入数），也有生产 p99 内存的灰度曲线。内存优化最容易「本地看着挺好、上线没有变化」，两级验证缺一不可。

**⑥ 更大的工具箱。** 本文涉及的思路之外，大规模缓存常用的手段还有：字符串驻留（string interning）、arena 分配、零拷贝格式（FlatBuffers / Cap'n Proto）、冷热分层（热数据内存 + 冷数据压缩存储）、透明大页减少 TLB miss 等。它们和这 5 个优化一样，都服务于同一个目标——让每一个字节都为数据本身服务，而不是为容器的「管理成本」服务。
