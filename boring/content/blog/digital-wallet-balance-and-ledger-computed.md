数字钱包的三笔账：跨分片转账占多少、协调者状态表写多少、事件重放花多少。讲义把数字钱包的设计要素讲全了（转账语义、分布式事务、事件溯源、Raft 复制、CQRS 读侧），但这三笔「各是多少」它都留成了定性判断。这篇把它们算出来。

这篇不复述译文，也不搬运中文译本的任何段落。它复述这一章的骨架（需求数字、API、估算表、机制演进），然后补三个自写模型：**分片数如何决定跨分片转账比例**、**协调者阶段状态表的写放大**、**事件溯源读侧放大与重放追溯成本**。

## 一、本章骨架：需求数字、一个端点、一张估算表、一条演进线

**需求（讲义用问答敲定）**：只支持两个账户之间的余额转账；**100 万 TPS**；**可用性 99.99%**；支持事务；支持可重现性（能从头重放重建历史，而不只是做对账）；不考虑外汇。

**一个端点**：`POST /v1/wallet/balance_transfer`，把余额从一个钱包转到另一个钱包。请求参数：`from_account`、`to_account`、`amount`（用 string 传以免丢精度）、`currency`、`transaction_id`（幂等键）。响应带 `status` 与 `transaction_id`。

**估算表**：云上关系型数据库约 1000 TPS/节点；要撑 100 万 TPS 需 1000 个节点；但每笔转账两条腿，实际要撑 200 万 TPS。讲义的目标是提高单节点 TPS、减少节点数，给的对应关系是——单节点 100 TPS 要 20000 个节点、1000 TPS 要 2000 个、10000 TPS 要 200 个。

**机制演进线（讲义的推进顺序）**：内存分片（Redis 存 `map<user_id, balance>`，`hash % partitionNumber` 定分片，ZooKeeper 存分区配置，无状态钱包服务）→ 但不能原子转账；→ 分布式事务（2PC 有锁争用与协调者单点；TC/C 用补偿事务；Saga 分编排与集中编排，钱包系统通常选集中编排）→ 为审计引入事件溯源（command / event / state / state machine，FIFO 队列，可重放，CQRS 出只读状态机）→ 为性能把命令与事件落本地磁盘（mmap 缓存、RocksDB 用 LSM 优化写、快照存 HDFS）→ 为可靠用 Raft 复制事件列表（只保证事件列表不丢、顺序一致）→ 为扩展把系统分片成多个 Raft 组，上面再用 TC/C 或 Saga 编排跨组分片事务。

这五个层级讲义都讲了「是什么、怎么走」，但每一个的量——跨分片占多少、状态表写多少、重放花多少——它都留给了读者。下面补这三笔账。

## 二、增量一：分片数与跨分片转账比例

讲义的目标是「提高单节点 TPS、减少节点数」，但它没说破一件事：节点数同时就是分片数，而分片数决定了一笔转账有多大概率跨分片——跨分片就必须走分布式事务。把这条链算出来：

```python
"""模型一：分片数与跨分片转账比例。

讲义把「提高单节点 TPS 从而减少数据库节点数」当成设计目标，但节点数同时就是
分片数，分片数又决定了一笔转账有多大概率落在两个分片上——也就是有多大概率
必须走分布式事务（TC/C 或 Saga）。本脚本把这条链算出来。

只依赖标准库；输出确定性：分区映射用固定 md5 哈希，账户对按固定公式生成，
不用随机数，不依赖 dict / set 的遍历顺序。
"""
import hashlib

# ---- 需求侧数字（讲义给出）----
TARGET_TPS = 1_000_000          # 目标转账吞吐（次/秒）
LEGS_PER_TRANSFER = 2           # 每笔转账两条腿 -> 讲义估算里的 2M TPS

# ---- 讲义给的估算表：单节点 TPS -> 节点数 ----
NODE_TABLE = ((100, 20_000), (1_000, 2_000), (10_000, 200))

# ---- 示例参数 ----
ACCOUNTS = 100_000              # 参与分配的账户数
SAMPLE = 50_000                 # 实测同分片比例用的样本笔数

def partition_of(account, partitions):
    """账户 -> 分片号。用 md5 模拟真实实现的哈希，避免字符串哈希随机化。"""
    digest = hashlib.md5(account.encode("utf-8")).hexdigest()
    return int(digest, 16) % partitions

def transfer_pairs(n):
    """确定性生成 n 笔转账的 (付款方, 收款方) 账户对，不用随机数。"""
    pairs = []
    for i in range(n):
        payer = "acct-%d" % (i % ACCOUNTS)
        payee = "acct-%d" % ((i * 7919 + 13) % ACCOUNTS)
        pairs.append((payer, payee))
    return pairs

PAIRS = transfer_pairs(SAMPLE)
PARTITION_SETS = sorted(set(p for _, p in NODE_TABLE) | {8, 64})

print("目标 %d 次转账/秒，每笔两条腿 -> 事件流 %d 条/秒"
      % (TARGET_TPS, TARGET_TPS * LEGS_PER_TRANSFER))
print("账户数 %d，样本 %d 笔（确定性生成，无随机数）" % (ACCOUNTS, SAMPLE))
print()
print("讲义估算表：一个节点一个分片时，分片数 P = 节点数")
for node_tps, nodes in NODE_TABLE:
    print("  单节点 %6d TPS -> %6d 个节点（= %6d 个分片）"
          % (node_tps, nodes, nodes))
print()
print("实测同分片比例（可做本地单事务的快路径）与理论 1/P：")
print("%8s %13s %12s %14s" % ("分片数P", "实测同分片", "理论1/P", "跨分片比例"))
rows = []
for p in PARTITION_SETS:
    same = 0
    for payer, payee in PAIRS:
        if partition_of(payer, p) == partition_of(payee, p):
            same += 1
    measured = 100.0 * same / SAMPLE
    rows.append((p, measured, 100.0 - measured))
    print("%8d %12.3f%% %11.3f%% %13.3f%%"
          % (p, measured, 100.0 / p, 100.0 - measured))
print()
print("每个分片承担的转账速率，以及必须走分布式事务（TC/C 或 Saga）的速率：")
print("%8s %17s %20s %12s" % ("分片数P", "每分片转账/秒", "跨分片转账/秒", "协调者占比"))
for p, measured, cross in rows:
    print("%8d %17.0f %20.0f %11.2f%%"
          % (p, TARGET_TPS / p, TARGET_TPS * cross / 100.0, cross))
print()
print("读法：")
row200 = [r for r in rows if r[0] == 200][0]
row20000 = [r for r in rows if r[0] == 20000][0]
row8 = [r for r in rows if r[0] == 8][0]
print("  - 分片数 P 越大，同分片（本地单事务快路径）比例越低：P=8 时快路径 %.3f%%，"
      % row8[1])
print("    P=200 时只剩 %.3f%%，P=20000 时只剩 %.3f%%。" % (row200[1], row20000[1]))
print("  - 跨分片比例随之抬到 %.3f%% 与 %.3f%%，也就是 %d 次/秒与 %d 次/秒。"
      % (row200[2], row20000[2],
         TARGET_TPS * row200[2] / 100.0, TARGET_TPS * row20000[2] / 100.0))
print("  - 所以分布式事务路径处理的是全部流量的绝大部分，不是长尾；")
print("    协调者与阶段状态表要按百万次/秒设计，而不是按「少量跨分片」设计。")
print("  - 讲义「提高单节点 TPS、少加节点」与「多加分片提并行度」方向相反：")
print("    少加分片同时降低每分片负载与跨分片比例，是两边都受益的方向。")
```

输出：

```text
目标 1000000 次转账/秒，每笔两条腿 -> 事件流 2000000 条/秒
账户数 100000，样本 50000 笔（确定性生成，无随机数）

讲义估算表：一个节点一个分片时，分片数 P = 节点数
  单节点    100 TPS ->  20000 个节点（=  20000 个分片）
  单节点   1000 TPS ->   2000 个节点（=   2000 个分片）
  单节点  10000 TPS ->    200 个节点（=    200 个分片）

实测同分片比例（可做本地单事务的快路径）与理论 1/P：
    分片数P         实测同分片        理论1/P          跨分片比例
       8       12.654%      12.500%        87.346%
      64        1.578%       1.562%        98.422%
     200        0.540%       0.500%        99.460%
    2000        0.050%       0.050%        99.950%
   20000        0.004%       0.005%        99.996%

每个分片承担的转账速率，以及必须走分布式事务（TC/C 或 Saga）的速率：
    分片数P           每分片转账/秒              跨分片转账/秒        协调者占比
       8            125000               873460       87.35%
      64             15625               984220       98.42%
     200              5000               994600       99.46%
    2000               500               999500       99.95%
   20000                50               999960      100.00%

读法：
  - 分片数 P 越大，同分片（本地单事务快路径）比例越低：P=8 时快路径 12.654%，
    P=200 时只剩 0.540%，P=20000 时只剩 0.004%。
  - 跨分片比例随之抬到 99.460% 与 99.996%，也就是 994600 次/秒与 999960 次/秒。
  - 所以分布式事务路径处理的是全部流量的绝大部分，不是长尾；
    协调者与阶段状态表要按百万次/秒设计，而不是按「少量跨分片」设计。
  - 讲义「提高单节点 TPS、少加节点」与「多加分片提并行度」方向相反：
    少加分片同时降低每分片负载与跨分片比例，是两边都受益的方向。
```

三处结论：

**第一，跨分片比例 ≈ 1 - 1/P，它跟着分片数走，不是跟着流量走。** 同分片（能做本地单事务）的比例实测约等于理论值 1/P——分片 8 个时快路径还有 12.65%，分片 200 个（讲义 10000 TPS/节点 那档）就只剩 **0.54%**，分片 20000 个只剩 0.004%。

**第二，分布式事务路径承载的是流量的绝大部分，不是长尾。** P=200 时跨分片转账 **99.46%**、约 **994,600 次/秒** 都要走 TC/C 或 Saga。这意味着协调者与阶段状态表必须按百万次/秒来设计，而不是按「少量跨分片」的余量来设计。

**第三，讲义的两个优化方向彼此打架。** 「提高单节点 TPS、少加节点」与「多加分片提并行度」方向相反——前者把分片数往下压，顺带把跨分片比例也往下压；后者把分片数往上抬，跨分片比例跟着抬。少加分片是两边都受益的方向：它同时降低每分片负载与跨分片比例。

## 三、增量二：协调者阶段状态表的写放大

讲义给了阶段状态表的字段（事务 ID、try 阶段状态、第二阶段名与状态、乱序标志），并说它要在数据库分片内原子更新、供协调者宕机后恢复——但没算这张表要写多少。把它算出来：

```python
"""模型二：协调者阶段状态表的存储与写放大账。

讲义说 TC/C 与 Saga 协调者要维护一张「阶段状态表」（事务 ID、try 阶段状态、
第二阶段名与状态、乱序标志），在数据库分片内原子更新，供协调者宕机后恢复。
本脚本算这张表的写入放大与规模账——讲义给了表字段，但没算这张表的写成本。

只依赖标准库；输出确定性。
"""

# ---- 需求侧数字（讲义给出）----
TARGET_TPS = 1_000_000      # 转账吞吐（次/秒）

# ---- 示例参数 ----
ROW_BYTES = 200             # 阶段状态表一行的大小（事务 ID + 状态机状态，估）
TRANSITIONS = 4             # 每笔分布式事务对状态表的状态转移次数：
                            #   1. 创建行并标记 try 已发送
                            #   2. 标记 try 已收到响应
                            #   3. 标记第二阶段名（confirm 或 cancel）
                            #   4. 标记第二阶段完成
RETAIN_SECONDS = 86400 * 7  # 状态表行保留时长（7 天，估）
CANCEL_SHARE = 0.02         # 需要回滚（走 cancel 分支）的比例（估）

cross_share = 0.9946        # 跨分片比例（模型一 P=200 时实测 99.46%）

print("目标转账吞吐 %d 次/秒" % TARGET_TPS)
print("跨分片比例 %.3f（模型一实测）-> 分布式事务 %d 次/秒"
      % (cross_share, TARGET_TPS * cross_share))
print()
dist_tps = TARGET_TPS * cross_share
print("阶段状态表写放大账：")
print("  每笔分布式事务 %d 次状态转移 -> 状态表写入 %d 次/秒"
      % (TRANSITIONS, dist_tps * TRANSITIONS))
print("  相当于转账写入（每条腿一次 = %d 次/秒）的 %.1f 倍"
      % (dist_tps * 2, (dist_tps * TRANSITIONS) / (dist_tps * 2.0)))
print()
print("阶段状态表规模账（保留 %d 天）：" % (RETAIN_SECONDS // 86400))
rows_per_s = dist_tps
total_rows = rows_per_s * RETAIN_SECONDS
total_bytes = total_rows * ROW_BYTES
print("  每行 %d 字节 -> 每天新增 %.2f GB"
      % (ROW_BYTES, rows_per_s * 86400 * ROW_BYTES / 1e9))
print("  保留 %d 天 -> %.0f 亿行，%.2f TB"
      % (RETAIN_SECONDS // 86400, total_rows / 1e8, total_bytes / 1e12))
print()
cancel_tps = dist_tps * CANCEL_SHARE
print("回滚账：")
print("  cancel 分支比例 %.1f%% -> %d 笔/秒要走「补偿」路径"
      % (CANCEL_SHARE * 100, cancel_tps))
print("  每笔 cancel 要比 confirm 多写一次补偿记录（+1 次转移）")
print("  -> 每天 cancel 类转移 = %d 次/秒 x 86400 秒 x %d 次 = %.1f 亿次"
      % (cancel_tps, TRANSITIONS + 1,
         cancel_tps * 86400 * (TRANSITIONS + 1) / 1e8))
print()
print("读法：")
print("  - 状态表写入 = 分布式事务次数 x %d，比转账本身的写多 %.0f 倍；"
      % (TRANSITIONS, TRANSITIONS / 2.0))
print("    协调者的真正成本不是「协调决策」，而是这张要持久化的状态表。")
print("  - 状态表必须分片存储（与业务数据同分片，才能原子更新），")
print("    所以它不是一张全局表，而是与转账分片一一对应的 N 张表。")
print("  - cancel 与乱序处理都只发生在状态表上：")
print("    加一个「乱序标志」列，就能在不引入锁的情况下挡住 cancel 先于 try。")
```

输出：

```text
目标转账吞吐 1000000 次/秒
跨分片比例 0.995（模型一实测）-> 分布式事务 994600 次/秒

阶段状态表写放大账：
  每笔分布式事务 4 次状态转移 -> 状态表写入 3978400 次/秒
  相当于转账写入（每条腿一次 = 1989200 次/秒）的 2.0 倍

阶段状态表规模账（保留 7 天）：
  每行 200 字节 -> 每天新增 17186.69 GB
  保留 7 天 -> 6015 亿行，120.31 TB

回滚账：
  cancel 分支比例 2.0% -> 19892 笔/秒要走「补偿」路径
  每笔 cancel 要比 confirm 多写一次补偿记录（+1 次转移）
  -> 每天 cancel 类转移 = 19892 次/秒 x 86400 秒 x 5 次 = 85.9 亿次

读法：
  - 状态表写入 = 分布式事务次数 x 4，比转账本身的写多 2 倍；
    协调者的真正成本不是「协调决策」，而是这张要持久化的状态表。
  - 状态表必须分片存储（与业务数据同分片，才能原子更新），
    所以它不是一张全局表，而是与转账分片一一对应的 N 张表。
  - cancel 与乱序处理都只发生在状态表上：
    加一个「乱序标志」列，就能在不引入锁的情况下挡住 cancel 先于 try。
```

三处结论：

**第一，协调者的成本不在「协调决策」，在状态表。** 每笔分布式事务要对阶段状态表做 **4 次**状态转移（建行、标 try 已发送、标 try 已响应、标第二阶段名与完成），在约 **994,600 次/秒** 的分布式事务下就是 **约 397 万次/秒** 的状态表写入——是转账写入本身（每条腿一次，约 199 万次/秒）的 **2 倍**。写放大的来源是恢复需求，不是业务逻辑。

**第二，状态表不是一张全局表，而是 N 张分片表。** 讲义要求它「在数据库分片内原子更新」，所以它必须与业务数据同分片——有多少个转账分片，就有多少张状态表分片。这也解释了为什么讲义把乱序标志放进状态表而不是加锁：加一个「乱序标志」列，就能在不引入锁的情况下挡住 cancel 先于 try 的乱序。

**第三，规模账由「保留时长」决定。** 每行 200 字节、保留 7 天，约 994,600 次/秒的状态表会积累到 **6015 亿行、120 TB**；若 cancel 分支占 2%，每天还要多写 85.9 亿次补偿类转移。这是审计与恢复的存储下限——不是可选项。

## 四、增量三：事件溯源读侧放大与重放追溯成本

讲义把事件溯源当成审计与可重现性的答案：「能从头重放重建历史」「用不同版本代码重放验证逻辑」。但重放与 CQRS 读侧都有量，讲义没算。把它算出来：

```python
"""模型三：事件溯源的读路径放大账——CQRS 读侧查询成本与重放追溯成本。

讲义说事件溯源支持「从头重放重建历史」与「用不同版本代码重放验证逻辑」，CQRS
靠多个只读状态机回答客户端查询。本脚本算：重放与只读状态机的「读放大」。

只依赖标准库；输出确定性。
"""

# ---- 需求侧数字（讲义给出）----
TARGET_TPS = 1_000_000      # 转账吞吐（次/秒）
LEGS_PER_TRANSFER = 2       # 每笔两条腿 -> 每条腿一条事件 -> 2 条事件/笔

EVENT_TPS = TARGET_TPS * LEGS_PER_TRANSFER

# ---- 示例参数 ----
EVENT_BYTES = 128           # 一条事件的体积（序列化后，估）
REPLAY_RATE = 200_000       # 单核重放吞吐（条/秒，估）
READ_MODELS = 3             # 只读状态机副本数（CQRS 读侧，估）
LOOKBACK_SECONDS = 86400 * 30  # 重放追溯窗口：30 天（估）

print("目标 %d 次转账/秒 -> 事件流 %d 条/秒" % (TARGET_TPS, EVENT_TPS))
print("每事件 %d 字节 -> 事件写入 %.0f MB/秒 = %.2f TB/天"
      % (EVENT_BYTES, EVENT_TPS * EVENT_BYTES / 1e6,
         EVENT_TPS * EVENT_BYTES * 86400 / 1e12))
print()

# CQRS 读侧放大
print("CQRS 读侧放大账：")
print("  %d 个只读状态机副本，每个都要消费全部 %d 条/秒事件"
      % (READ_MODELS, EVENT_TPS))
print("  -> 读侧消费总量 = %d x %d = %d 条/秒"
      % (READ_MODELS, EVENT_TPS, READ_MODELS * EVENT_TPS))
print("  每个只读状态机要具备至少 %d 条/秒的处理能力才能跟上"
      % (EVENT_TPS,))
print()

# 重放追溯成本
window_events = EVENT_TPS * LOOKBACK_SECONDS
replay_hours_single = window_events / REPLAY_RATE / 3600
replay_hours_100 = replay_hours_single / 100
print("重放追溯账（重放 %d 天窗口 = %.1f 万亿条事件）："
      % (LOOKBACK_SECONDS // 86400, window_events / 1e12))
print("  单核重放吞吐 %d 条/秒 -> 需要 %.1f 小时"
      % (REPLAY_RATE, replay_hours_single))
print("  横向 100 核并行 -> %.1f 小时" % replay_hours_100)
print("  每天新增 %.2f TB，重放窗口每天变大 -> 窗口越大越付不起"
      % (EVENT_TPS * EVENT_BYTES * 86400 / 1e12))
print()

print("读法：")
print("  - 「重放重建历史」不是免费审计：重放 %d 天窗口 = %.1f 万亿条事件，"
      % (LOOKBACK_SECONDS // 86400, window_events / 1e12))
print("    单核要 %.0f 小时，这决定了「出事后多久能给出对账结论」的下限。"
      % replay_hours_single)
print("  - 快照是重放的前置条件：没有快照，重放窗口 = 全量历史；")
print("    快照让重放窗口收缩到「最近一次快照之后」。")
print("  - 「用不同版本代码重放验证逻辑」在 %d 条/秒流量下，" % EVENT_TPS)
print("    等于再付一份读侧成本——这就是为什么它常做成离线任务。")
```

输出：

```text
目标 1000000 次转账/秒 -> 事件流 2000000 条/秒
每事件 128 字节 -> 事件写入 256 MB/秒 = 22.12 TB/天

CQRS 读侧放大账：
  3 个只读状态机副本，每个都要消费全部 2000000 条/秒事件
  -> 读侧消费总量 = 3 x 2000000 = 6000000 条/秒
  每个只读状态机要具备至少 2000000 条/秒的处理能力才能跟上

重放追溯账（重放 30 天窗口 = 5.2 万亿条事件）：
  单核重放吞吐 200000 条/秒 -> 需要 7200.0 小时
  横向 100 核并行 -> 72.0 小时
  每天新增 22.12 TB，重放窗口每天变大 -> 窗口越大越付不起

读法：
  - 「重放重建历史」不是免费审计：重放 30 天窗口 = 5.2 万亿条事件，
    单核要 7200 小时，这决定了「出事后多久能给出对账结论」的下限。
  - 快照是重放的前置条件：没有快照，重放窗口 = 全量历史；
    快照让重放窗口收缩到「最近一次快照之后」。
  - 「用不同版本代码重放验证逻辑」在 2000000 条/秒流量下，
    等于再付一份读侧成本——这就是为什么它常做成离线任务。
```

三处结论：

**第一，「重放重建历史」不是免费审计，它有下限。** 100 万 TPS、每笔两条腿 ⇒ 事件流 **200 万条/秒**、每天 **22 TB**。要重放 30 天窗口就是 **5.2 万亿条**事件，单核按 20 万条/秒要 **7200 小时**（100 核并行也要 72 小时）。这个下限决定了「出事后多久能给出对账结论」——它不是秒级。

**第二，快照是重放的前置条件，不是可选项。** 没有快照，重放窗口等于全量历史，每天都更长；有了快照，重放窗口才收缩到「最近一次快照之后」。讲义把快照放在「优化可重现性」一节，但从这笔账看，它是让重放**可行**的前提。

**第三，CQRS 读侧是放大器。** 每个只读状态机都要消费全部 200 万条/秒事件，3 个副本就是 **600 万条/秒** 的读侧消费。「用不同版本代码重放验证逻辑」等于再付一份读侧成本——这就是为什么它通常被做成离线任务，而不是在线校验。

## 五、把三个模型套回本章（判据清单）

1. **分片数一次定对**：它同时决定单分片负载与跨分片比例。P=200 时跨分片转账 99.46%、约 99.5 万次/秒——分布式事务路径承载的是流量的绝大部分，协调者要按百万次/秒设计。
2. **跨分片比例 ≈ 1 - 1/P**：分片数越大，本地单事务快路径越薄。要在「每分片负载」与「跨分片比例」之间取平衡，少加分片是两边都受益的方向。
3. **协调者的成本在状态表**：每笔分布式事务 4 次状态转移，写入量是转账本身的 2 倍；状态表必须与业务数据同分片，且要按保留时长预算存储（7 天约 120 TB）。
4. **重放有下限**：事件流 200 万条/秒、每天 22 TB，重放 30 天窗口单核要 7200 小时——对账结论给多快，由这个下限决定。
5. **快照是重放的前置条件**：它把重放窗口从「全量历史」收缩到「最近一次快照之后」，否则重放不可行。
6. **CQRS 读侧是放大器**：每个只读状态机都消费全量事件，副本数与「不同版本代码重放验证」都要计入读侧成本。

## 七、这三个模型判不了什么

- **单节点 TPS、事件字节数、重放吞吐、行大小都是估的**。真实值随硬件、序列化格式、批大小变化；跨分片比例、写放大倍数、重放耗时的量级随参数线性变化，结论的形状不变。
- **账户对分布用固定公式生成**，真实业务的转账有明显热点（少数大账户、商户账户）；热点会让某几个分片的实际负载远高于均值，模型没算分片倾斜。
- **没算 Raft 复制与选举的代价**：事件列表要跨多数派复制，leader 选举期间的写不可用窗口会直接影响 99.99% 这个可用性目标，本文的模型没体现。
- **没算状态机实现本身的复杂度**：确定性状态机、快照与恢复的工程成本（版本兼容、快照格式演进）都不在这三笔账里。

## 八、常见问题（FAQ）

**跨分片转账比例是多少？** 约等于 1 - 1/P（P 为分片数）。讲义 10000 TPS/节点那档对应 200 个分片，实测同分片只剩 0.54%，跨分片 99.46%——约 99.5 万次/秒要走分布式事务，本地单事务快路径只是零头。

**协调者的阶段状态表要写多少？** 每笔分布式事务 4 次状态转移（建行、标 try 已发送、标 try 已响应、标第二阶段名与完成）。在约 99.5 万次/秒的分布式事务下，状态表写入约 397 万次/秒，是转账写入本身的 2 倍；保留 7 天约 6015 亿行、120 TB。

**重放重建历史要多久？** 事件流 200 万条/秒、每天 22 TB。重放 30 天窗口（5.2 万亿条）单核要 7200 小时，100 核并行也要 72 小时。这个下限决定了出事后多久能给出对账结论，也决定了快照为什么是重放的前置条件。

**为什么少加分片反而好？** 因为分片数同时决定单分片负载与跨分片比例。少加分片会同时降低每分片负载和跨分片比例（1 - 1/P 变小），是「提高单节点 TPS」与「提高并行度」之外、两边都受益的方向。
