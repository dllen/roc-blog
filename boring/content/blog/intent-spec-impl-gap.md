写代码的边际成本正在塌陷，但「这份代码实现了我的意图吗」这个问题一点没变便宜。这篇整理自南京大学《生成式软件工程》2026 秋第 1 讲「欢迎来到未来」（主讲：jyy），[原始讲义](https://jyywiki.cn/GSE/2026/lect1.md)。讲义用二维码 Excel 这个小而完整的失败案例，把意图、规格与实现之间的缺口摆到了台面上。

文中所有代码都在本地实跑过，正文印的输出是真实结果。

## 一、一份满分的作业，证明了谁的能力

课程开篇没有讲技术，而是先问了一个问题：如果把一份编程作业直接交给 AI，它读题、写代码、运行测试，最后交出一个像模像样的结果，那么这份作业的满分，究竟证明了谁的什么能力？

过去人们习惯把作品当成能力留下的痕迹——能做出一个程序，大概就掌握了相应知识。今天同一份作品背后，可能是深入理解系统的人，也可能是只复制粘贴了一句话的人。**作品还在，作品与能力之间的对应关系却变了。**

讲义接着列出三种很真实的焦虑：AI 帮我上完了大学，最后我什么都没学会怎么办；老老实实学了四年，毕业时发现原来训练的技能不值钱了怎么办；为了刷出一份完美简历，把生活变成一场漫长的资格赛，最后又得到了什么。

这三问很难再靠「把下一门课考好」来回答。既然课程式的知识传递正在被绕过，就得亲自试一试：当实现软件的成本发生剧变，什么能力还值得训练？

## 二、四个技术史节点，和一句「怎么让工程不失败」

讲义用四个节点回看技术史：**1975 年的 Altair 8800、1993 年的 Mosaic、2007 年的 iPhone、2022 年的 ChatGPT**。放在一起看，它们是同一种变化的四例——原先只有少数人能使用的能力，逐渐进入普通人的日常生活。今天「把一个想法变成能运行的软件」也在经历同样的变化。

因此这门课被定位成**实验性的课程**，要讨论的是 AI 时代还有用的「软件工程智慧」，其内核是一句加粗的反问：**怎么让工程不失败？** 让一个演示跑起来只是开始；一个系统还要承受需求变化、真实用户、错误输入，以及人与人之间的协作。AI 可以加速实现，这些问题不会随着代码自动生成而自动消失。

关于「大学还能教什么」，课堂给了三个有点扎人的说法：**信息差**（知道计算机世界里有什么、知道哪里能找到答案）、**能坐牢**（做了决定以后有人要承担后果）、**能驾驭**（能把人、工具和反馈组织起来做成一件事）。课程最关心的是最后一项。

还有一句被反复引用的狠话：**「没有 token 的 CS 学生应该立即退学」**。讲义立刻降温——当然不会真的让大家退学，强调的是应当亲自使用工具、形成判断，而不是永远停留在听别人评价的阶段。课程要求 token 自费，但**不鼓励 tokenmaxxing**（以消耗更多 token 为目标的攀比）。

## 三、从填词游戏到能行动的 Agent

讲义给了一个刻意朴素的起点：从使用者角度，自回归语言模型可以先理解为一个条件概率分布——给定已有上下文，预测下一个 token。

```text
Pr[token | context]
```

Token 是模型处理文本的基本单位，不必恰好对应一个汉字或一个单词。这个接口简单得让人怀疑它能做多少事，但关键在于区分两件事：**「预测下一个 token」描述的是计算怎样展开，不能直接拿来判定能力上限。**

因为模型输出的文字会**进入后续上下文**：先写下一个中间结果，再基于它继续计算；发现矛盾，再尝试修正。于是一个看似静态的概率分布，由此展开成很长的计算过程——这是理解思维链与 Agent 的枢纽。

推理型模型让「先尝试、再检查、再修正」更有效：Chain-of-thought 把中间步骤留在上下文中，test-time scaling 则是在使用时投入更多计算换取更深入的尝试。多花计算是否值得，要看这些尝试**能不能得到有效反馈**。

Agent 又向前走了一步：它可以调用工具——读文件、执行命令、查询网页，观察操作结果，再决定下一步。语言模型与运行它的程序、工具和环境共同形成一个**反馈循环**，承载这个循环的外围系统常被称为 **harness**。讲义用了一个对照：**一次对话可以告诉你怎样安装系统，一个 Agent 则可能真的开始安装**，遇到报错后继续排查，直到拿到可以验收的结果。

所以理解 Agent 不能只看模型答题有多聪明，还要看它能观察什么、操作什么，以及操作以后能否知道自己做对了没有。

## 四、二维码 Excel：一个完整但很小的失败案例

讲义给了一个非常具体的需求：只用 Excel 2019 及以前兼容的公式，把一个可能长达数千字符的字符串先做 Base64 编码，再分成二维码帧；刷新显示时循环播放这些帧，扫描得到的数据拼接后应当还原为完整的 Base64 字符串；还要用接近真实运行环境的办法验证公式确实算对了。

看起来已经很具体，但里面仍藏着大量选择：字符串用什么编码？一帧装多少内容？输入变化时，公式和工作表是否要重建？「按 F9 刷新」和「一秒一帧」究竟怎样配合？工作簿能打开，是完成；还是每帧都能被真实解码器读取、拼接后能还原原文，才算完成？**完成的标准本身就是一道未决的规格问题。**

课堂记录里的实验数据最有说服力：

- 一次 **GLM-5.3** 尝试的第一轮思考就持续了 **25 分钟**，随后撞上输出长度限制，最终花了 **6 小时**才完成；
- 一次 **DeepSeek V4 Pro** 尝试给出了**硬编码版本**，被指出问题后承认需要重新设计；
- 得到的 Excel 文件约有 **2 MB**，而且难以维护。

转折出现在后来：通过少量提示调整开发方向，**GLM-5.3 在 200K 上下文内完成了一个正确且更可维护的版本**——公式能够复用，工作表结构不随着文本长度不断膨胀。讲义由此得出关键结论：**真正改变局面的，是对计算结构的设计。**

这里最值得单独拎出来的是「硬编码」这个问题。用户需要的是一个对不同输入都成立的**计算过程**，模型却可能交出一个只让当前输入看起来正确的结果。**演示成功和需求实现之间，隔着一个很大的差别。**

下面这段代码把这个差别做成了可运行的判据。参数化版本把算法写成一份模板；硬编码版本只留一份当初调通过的现成结果；验证用的解码器独立于被测实现，靠回环还原来判断真假：

```python
import base64


def split_parametric(text, frame_size=64):
    """把文本 Base64 编码后切成固定长度的帧——算法模板只有一份。"""
    b64 = base64.b64encode(text.encode("utf-8")).decode("ascii")
    return [b64[i:i + frame_size] for i in range(0, len(b64), frame_size)]


def decode_frames(frames):
    """独立解码器：不属于被测实现，负责把帧还原成原文。"""
    return base64.b64decode("".join(frames)).decode("utf-8")


def roundtrip_ok(text, frames):
    try:
        return decode_frames(frames) == text
    except Exception:
        return False


# 硬编码实现：只认识当初调通的那一条输入
BAKED = {}


def split_hardcoded(text, frame_size=64):
    # 别的输入一律照抄一份旧的
    return BAKED.get(text, BAKED.get(sorted(BAKED)[0], []))


A = "我来到逸夫馆我来到教室我来到食堂"
B = "今天北京多云转晴，气温 8 到 15 摄氏度"

BAKED[A] = split_parametric(A, 64)

for label, t in (("输入 A（当初调通的那条）", A), ("输入 B（同结构，换内容）", B)):
    p = split_parametric(t, 64)
    h = split_hardcoded(t, 64)
    print(f"{label}")
    print(f"  参数化：{len(p)} 帧，独立解码器回环还原 = {roundtrip_ok(t, p)}")
    print(f"  硬编码：{len(h)} 帧，独立解码器回环还原 = {roundtrip_ok(t, h)}")
```

实跑输出：

```text
输入 A（当初调通的那条）
  参数化：1 帧，独立解码器回环还原 = True
  硬编码：1 帧，独立解码器回环还原 = True
输入 B（同结构，换内容）
  参数化：2 帧，独立解码器回环还原 = True
  硬编码：1 帧，独立解码器回环还原 = False
```

关键在于两条实现**在输入 A 上表现完全一样**——演示都能成功，文件都能打开。差别只有在换一个输入时才暴露，而区分二者的判据不是「看起来对不对」，而是**独立解码器能不能还原出原文**。

这正是讲义那句「需要用接近真实运行环境的办法验证公式确实算对了」的可操作版本：验证器必须是**另一个**实现，否则它会跟被测对象共享同一个错误。讲义里考试统分的例子是同一个道理——反序复核并读出算式，把错位、漏项、误识别暴露出来，形成一条可以回查的链。

## 五、局部性：AI slop 真正的判据

讲义对 **AI slop** 重新做了定义：不能只看文件有多大、代码有多丑，更关键的是**修改有没有局部性**——改一个地方，会不会迫使整个系统重来？

「局部性」可以量化。同一件事做两遍：把帧长从 64 改成 48，看各自要重做多少东西。

```python
import base64


def split_parametric(text, frame_size=64):
    b64 = base64.b64encode(text.encode("utf-8")).decode("ascii")
    return [b64[i:i + frame_size] for i in range(0, len(b64), frame_size)]


A = "我来到逸夫馆我来到教室我来到食堂"
B = "今天北京多云转晴，气温 8 到 15 摄氏度"

# 硬编码表：每个输入留一份现成的帧
BAKED = {A: split_parametric(A, 64), B: split_parametric(B, 64)}

print("需求变更：帧长从 64 改成 48")
print("  参数化：要重做的输入样本 = 0 个（算法模板没变，只改一个常量）")

stale = [k for k, v in BAKED.items() if any(len(f) != 48 for f in v)]
print(f"  硬编码：要重做的输入样本 = {len(stale)} 个（每份存下的帧长都变了）")
for k in stale:
    print(f"    - {k[:12]}… 原帧长 64 → 需按 48 重新生成")
```

实跑输出：

```text
需求变更：帧长从 64 改成 48
  参数化：要重做的输入样本 = 0 个（算法模板没变，只改一个常量）
  硬编码：要重做的输入样本 = 2 个（每份存下的帧长都变了）
    - 我来到逸夫馆我来到教室我… 原帧长 64 → 需按 48 重新生成
    - 今天北京多云转晴，气温 … 原帧长 64 → 需按 48 重新生成
```

参数化版本改的是一个常量，模板没变；硬编码版本每条输入各存了一份现成结果，帧长一改全部作废。**输入变长，数据量、帧数和计算量当然可以增加；但表达算法的模板，不应当因此被一份份复制。**

讲义把这接到了软件工程经典上：**如果每次变化都要重新解释全部隐含关系，项目就已经接近《人月神话》里的焦油坑了。越挣扎，越消耗；加入更多生成能力，也可能只是更快地把自己埋进去。**

## 六、Intent、Spec 与 Impl 之间的缺口

二维码案例引出了整门课的一条主线。

- **Intent** 是你真正想达成的目标。它往往**连提出者自己也没有完全想清楚**：「帮我做一个好用的工具」「做一个国民级应用」，都包含大量尚未表达的期待。
- **Spec** 是把意图具体化以后，能够描述行为与约束的规格。
- **Impl** 则是程序实际执行的计算。讲义强调：**计算机必须在每一个执行分支上做出确定的动作，不能留一句「到时候看着办」。**

两段转换的判断类型不同：**从 Intent 到 Spec，需要做产品判断；从 Spec 到 Impl，需要做设计与实现判断。** 同一个意图允许许多规格，同一个规格又允许许多实现。每一步看似合理，最终仍然可能离用户想要的东西很远。

讲义给出一个重要的逻辑警告：**即使程序通过了现有测试，也只能说明它满足了这些检查，不能自动推出规格忠实表达了真实意图。**

模型怎样填补这些空白？很大程度上**靠猜**。并且有一条边界规则：总不能每选一种颜色、每命名一个变量都询问用户；**但在架构、数据表示和验收标准上猜错，代价就大得多**。这正是本课要研究的问题——哪些决定可以先做再验证，哪些决定值得先讨论或做一个小实验。

这也解释了为什么「立即遵循指令」有时会把事情做坏：模型迅速进入实现，许多重要选择还没有被看见，就已经固化在代码里。之后每一步都在维护早期决定，终于走进一个很难掉头的方向。好的协作需要**让重大假设及时显露**，也需要**给推翻假设留出空间**。

## 七、让大工程获得及时的反馈

讲义给软件工程下了一个更完整的定义：**软件工程讨论的是，怎样在人与工具的共同协作下，把一件大事做成。它包含技术，也包含组织、沟通、责任和动机。** 在 LLM 时代，**失败的定义没有根本改变**：软件没有满足真实意图与约束，就是失败。

它对比了两种反馈速度：学校里的题目通常在几分钟或几个小时内有答案，交卷就结束；真实工程的反馈可能很晚才来——用户开始使用才发现流程不对，需求改变才发现结构无法维护。长程任务难就难在：**还没有明确分数的时候，也要持续判断方向。**

解法没有变：**拆解、验证和迭代因此仍然有用。**

- **拆解**让一个大问题变成能看清因果的小问题；
- **测试与持续集成**让已发现的错误不再轻易回流；
- **小步修改**让新的失败尽早出现，便于定位和回退。

三者共同的作用被讲义精确表述为：**缩短了「做了一个决定」与「知道决定是否正确」之间的距离。**

讲义用二维码 Excel 做了一个「如果重新安排开发」的复盘，顺序值得照抄：先拿一个**短字符串**完成**单帧二维码**，并让**独立解码器真实读回原文**——这一步验证最核心的计算；随后扩展到不同输入、Base64 编码和分片，再验证多帧的顺序与拼接；最后处理刷新、兼容性和性能。**每一步都留下可执行的检查；每一步都在消除一种具体的不确定性**，而不是等整个文件写完才看它能不能用。

## 八、当生产变便宜，什么成为瓶颈

讲义用一个**夸张的算式**说明新的成本结构：假设生成能力提高一千倍，即使只有百分之一的垃圾，垃圾的绝对量也达到旧时代全部产量的十倍。讲义承认这是一个假设计算，却提醒我们：**错误率很小和维护负担很小，并不是一回事。**

由此推出一条新的工程结论：**生成可以越来越快，逐行阅读却难以同样加速。** 新的工程工作因此更依赖**好的规格、独立检查器、测试、可观测性和清晰接口**——目标是**让判断也能够跟上生产，让人的注意力花在最值得判断的地方**。

关于「古法编程死了」，讲义把它解读为一个正在发生的机会：对于边界清楚、能得到有效反馈的任务，手工实现的稀缺性正在下降。但立刻加上限定：**软件工程暂时还没有死。** 一个人有机会**调动过去需要一个团队才拥有的实现能力**，去解决以前连开始都不敢想的问题。

至于 AI 将来是否连设计、品味和工程判断都能胜任，讲义诚实地指出**课堂没有给人类留下一块永远安全的领地**。它把这个问题说得更直接：**「为什么我要招你，而不是买一个 200 美元的 Claude Max？」**——除了你可以坐牢，你还提供了什么？

这个问题问的是「能力」而不是「产出」，正好回到开篇那份满分作业。当产出变得极其便宜，区分度就必然从产出转移到别处。

## 九、它不解决什么

- 这门课讲的是**判断的缺口**，不是工具的用法。读完知道该问什么，不代表知道某个框架怎么配置。
- 讲义里的实验记录来自**课堂特定几次尝试**，GLM-5.3 的 6 小时与 2 MB 是那几次的度量，不是该模型的稳定性能特征，换个版本或换个提示未必复现。
- 二维码 Excel 是**一个失败案例**，不是通用结论。参数化优于硬编码在这里成立，是因为需求已经明确成了「对任意输入成立的计算过程」；需求本身含糊时，参数化只是把猜测藏得更深。
- 「能坐牢」的说法预设了责任归属清晰的环境。企业里「模型出了错算谁的」往往没有课程里那么干净。

## FAQ（六、常见问题）

**问：既然测试通过了，为什么还不能说规格忠实表达了意图？**

因为测试断言的是**实现的行为**，而意图是**用户的目标**，两者之间隔着一次人工判断。测试能证明「程序做了它被要求做的事」，不能证明「被要求做的事就是用户想要的事」。规格漂移正是发生在这层——规格本身写对了，但它写的东西已经偏离了真实意图。测试再多也只是把第一层的证据做得更密。

**问：独立检查器到底独立到什么程度？**

至少要独立于**被验证对象自己的假设**。用同一个函数写实现和验证，两边会共享同一个理解错误。讲义的反序复核、读出算式都是这个思路的实例。更强的一层是验证器跑在**接近真实运行环境**里——二维码用真实解码器读回，而不是用生成二维码的那个公式去读。

**问：局部性能不能靠工具自动检查？**

不能自动判定，但可以被**度量**。上面第二个例子里的「要重做的输入样本数」就是一种量化方式：改一个常量后，有多少已存下的产物需要重新生成。这个数字比「代码丑不丑」客观得多，也更容易在 code review 里讨论。

**问：这和已经发过的[错误如何传播与暴露](/blog/fault-error-failure-testing/)那篇什么关系？**

那篇讲的是**已发生的错误怎么被看见**——Fault → Error → Failure 的传播链，以及测试、断言、差分测试各自作用在哪一段。这篇讲的是更靠前的一层：**在错误产生之前，「完成」的标准本身没有定清楚**。两篇是同一条链的前后两段：先要写清什么叫完成（Intent/Spec 缺口），错误才有暴露的判据（传播链）。
