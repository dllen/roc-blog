[南京大学《生成式软件工程》2026 秋第 7 讲「需求和架构 (2)」](https://jyywiki.cn/GSE/2026/lect7.md)有一句很克制的话：**「这套结构提供了可检查的约束，但算得平不等于记得对。」** 这句话值得单独展开——它讲的是一个很容易被忽略的层次差别：可检查的约束只是必要条件，把约束满足了当成业务做对了，会漏掉整整一类错误。

本文做三件事：把讲义给的约束写成能跑的检查器；用课程自己的记账规则表逐条核对讲义举的两个数字；再把讲义里另外三处容易被读串的判断（UNIX 的组合规则、关系数据库的逻辑与物理分离、RFC 1958 的城市比喻）分开摆清——它们各自讲的是不同的东西。

## 一、约束是能检查的，正确性不是

讲义描述的课堂工具用的是「Event Sourcing 与 LLM as a Compiler」的思路：把原始凭证交给语言模型理解，翻译成受约束的记账动作，再由程序按规则执行状态变化。**语言模型是编译器前端**，负责把人的材料翻译成系统能检查的表示；**账本代码是后端**，负责这些动作的确定含义和约束。

后端能给的最基本的约束是复式记账的那条：**借方金额合计等于贷方金额合计**。这条能机械检查，但检查通过说明的东西比直觉里以为的少。我把三种账各写了一遍，跑同一套检查：

```python
from decimal import Decimal

def money(value):
    return str(Decimal(value).quantize(Decimal("0.01")))

def entries():
    """讲义 pay_payroll 的三步：确认费用 / 形成应付 / 实际支付"""
    return [
        ("确认费用", "费用:个人劳务", Decimal("75.00"), "借"),
        ("确认费用", "应付:个人劳务", Decimal("75.00"), "贷"),
        ("支付",     "应付:个人劳务", Decimal("75.00"), "借"),
        ("支付",     "资产:备付金", Decimal("75.00"), "贷"),
    ]

def trial_balance(ps):
    debit = sum((p[2] for p in ps if p[3] == "借"), Decimal("0"))
    credit = sum((p[2] for p in ps if p[3] == "贷"), Decimal("0"))
    return debit, credit, debit == credit

def expense_total(ps):
    return sum((p[2] for p in ps if p[1] == "费用:个人劳务"), Decimal("0"))

base = entries()
for label, ps in [
    ("正确记账", base),
    ("归错科目", [(a, "费用:差旅费" if s == "费用:个人劳务" else s, amt, side)
                  for (a, s, amt, side) in base]),
    ("重复录入", base + base),
]:
    d, c, ok = trial_balance(ps)
    print("%s  试算平衡=%s  借=%s 贷=%s  费用:个人劳务合计=%s"
          % (label, "平" if ok else "不平", money(d), money(c), money(expense_total(ps))))
```

```text
正确记账  试算平衡=平  借=150.00 贷=150.00  费用:个人劳务合计=75.00
归错科目  试算平衡=平  借=150.00 贷=150.00  费用:个人劳务合计=0.00
重复录入  试算平衡=平  借=300.00 贷=300.00  费用:个人劳务合计=150.00
```

三行都是「平」。但只有第一行是对的：第二行把这笔个人劳务记成了差旅费（费用科目错了，借贷仍然抵消）；第三行把整笔录了两遍（金额翻倍，借贷仍然抵消）。

**试算平衡检查的是「分录自身是否自洽」，不是「这笔业务是否记对了」。** 讲义那句「算得平不等于记得对」说的正是这个：把业务归错类、重复录入一笔金额相同的借贷记录，都可能仍然平衡。原始凭证、业务含义和记账动作之间的对应关系，仍然需要核对——这是模型和规则表都替不了的一环。

## 二、规则表能算出讲义的每个数字

讲义给了两个具体数字：银行收支记录包含两笔动作——**财务费用支出 75 元**，**投资收益中的利息收入 22.07 元**；执行后货币资金的净变化是 22.07 − 75 = **−52.93 元**，净利润同样减少 52.93 元。

这两个数字的来源是课程页面上的[记账规则表](https://jyywiki.cn/GSE/2026/p7/rules.html)，它按「每 1 元的增减」列出了各类记账动作对三张报表的影响。表里与这两笔相关的行是这样的（摘录）：

| 记账动作 | 资产负债表 | 利润表 | 现金流量表 |
|---|---|---|---|
| 支出财务费用 | 货币资金 −1.00，未分配利润 −1.00 | 财务费用 +1.00，营业利润 −1.00，利润总额 −1.00，净利润 −1.00 | 支付其他与经营活动有关的现金 +1.00，经营活动产生的现金流量净额 −1.00，现金净增加额 −1.00 |
| 收入投资收益利息 | 货币资金 +1.00，未分配利润 +1.00 | 投资收益 +1.00，营业利润 +1.00，利润总额 +1.00，净利润 +1.00 | 取得投资收益收到的现金 +1.00，投资活动产生的现金流量净额 +1.00，现金净增加额 +1.00 |

表头写得很明确：**「每 1 元的增减；合计与明细不重复相加」**。也就是说这是一套线性的按金额比例规则——把每行的 ±1.00 乘以金额就是这笔动作的效果。我照着这两行算了一遍：

```python
from decimal import Decimal

# 记账规则表（每 1 元的增减）
EXPENSE = {"货币资金": Decimal("-1.00"), "未分配利润": Decimal("-1.00"),
           "财务费用": Decimal("1.00"), "营业利润": Decimal("-1.00"),
           "净利润": Decimal("-1.00"), "现金净增加额": Decimal("-1.00")}
INTEREST = {"货币资金": Decimal("1.00"), "未分配利润": Decimal("1.00"),
            "投资收益": Decimal("1.00"), "营业利润": Decimal("1.00"),
            "净利润": Decimal("1.00"), "现金净增加额": Decimal("1.00")}

def money(value):
    return str(Decimal(value).quantize(Decimal("0.01")))

def apply(rules, amount):
    return dict((k, money(v * amount)) for k, v in rules.items())

e = apply(EXPENSE, Decimal("75"))
i = apply(INTEREST, Decimal("22.07"))
print("支出财务费用 75 元：货币资金=%s 财务费用=%s 净利润=%s"
      % (e["货币资金"], e["财务费用"], e["净利润"]))
print("收入投资收益利息 22.07 元：货币资金=%s 投资收益=%s 净利润=%s"
      % (i["货币资金"], i["投资收益"], i["净利润"]))
print("两笔合并：货币资金净变化=%s  净利润=%s"
      % (money(Decimal(e["货币资金"]) + Decimal(i["货币资金"])),
         money(Decimal(e["净利润"]) + Decimal(i["净利润"]))))
```

```text
支出财务费用 75 元：货币资金=-75.00 财务费用=75.00 净利润=-75.00
收入投资收益利息 22.07 元：货币资金=22.07 投资收益=22.07 净利润=22.07
两笔合并：货币资金净变化=-52.93  净利润=-52.93
```

和讲义印的 −52.93 对上了，两张报表都一致。这也解释了讲义那句「报表上的许多数字共同变化，但我们不希望让模型逐格填写这些数字，而希望它们来自同一组动作及其计算规则」——**模型只该提交动作，数字由规则算出来。** 如果让模型直接填 22 张报表的格子，它填的是自己的猜测；让它提交两笔动作，数字是规则算的，而且可以重算。

## 三、三处容易被读串的判断

讲义里另外三个例子常被混为一谈，其实是三件不同的事。

**UNIX 讲的是组合规则，不是「文本流好」。** UNIX 哲学常被概括成三句——每个程序做好一件事、让程序能够协作、让程序处理文本流——但讲义指出前两句容易赞同，**真正让它们落地的是第三句**：没有共同接口，各自做好一件事的工具仍是一堆连不起来的孤岛。文本流让人和程序、程序和程序有机会用同一种接口，流水线出问题还能在中间截断结果看前一步产出了什么。

不过「都是文本」本身并不足以保证协作，命令行参数怎么区分选项与操作数、数据从哪来、诊断信息去哪、成功失败怎么报告，都需要共同约定。[POSIX 的工具语法约定](https://pubs.opengroup.org/onlinepubs/9699919799.orig/basedefs/V1_chap12.html)区分短选项、选项参数和操作数，并规定用 `--` 结束选项解析——于是 `-weird-name` 这种长得像选项的东西，可以作为普通操作数传进去。

讲义在同一节里补了一句更实际的：**分隔符也是接口的一部分——文件名能包含换行时，就不能假设「按行切开」总能无歧义地还原文件列表。** 这条可以当场验证：造两个文件，其中一个的文件名里带换行符，再按行切开文件名列表：

```python
import os, tempfile

d = tempfile.mkdtemp()
open(os.path.join(d, "报告\n最终版.txt"), "w").close()
open(os.path.join(d, "普通.txt"), "w").close()

names = sorted(os.listdir(d))
print("真实文件数:", len(names))

stream = "\n".join(names)
print("按行切开得到的条目数:", len(stream.splitlines()))
for i, line in enumerate(stream.splitlines(), 1):
    print("  条目", i, ":", repr(line))
```

```text
真实文件数: 2
按行切开得到的条目数: 3
  条目 1 : '报告'
  条目 2 : '最终版.txt'
  条目 3 : '普通.txt'
```

两个文件，按行切开却得到三条——那个文件名里的换行符被当成了分隔符。**「一行一条」这个约定本身是有代价的**，讲义把这一点列进「接口纪律」，是对的。

**关系数据库和 Internet 讲的是同一件事的两面：把逻辑与物理分开。** Codd 1970 年的论文想要保护用户，使他们不必因为数据表示方式、数据规模和访问需求变化，就跟着重写使用数据的方式——**关键是把「数据在逻辑上意味着什么」和「数据在机器里怎样组织」分开**。以图书馆为例，「某位读者借走某册书」可以用读者、馆藏和借阅关系表达，而底层用哪种索引、记录放在哪个数据页、先扫哪张表，属于另一个层次。

[RFC 1958](https://www.rfc-editor.org/rfc/rfc1958.html)开篇讲的也是这件事，只是换了比喻：信息技术一直在变化，因此不能把架构理解为一张永远不变的施工图；文中用城市作比——**街道与建筑不断改建，城市仍然继续运转**。请求经过多个网络到达数据中心，应用不必知道途中每一段链路使用什么硬件。

**UNIX、数据库、Internet 各自具体在讲什么，差别很大：UNIX 讲工具之间怎么协作，数据库讲同一份数据的两层表达，Internet 讲分层协议怎么让局部替换与整体延续同时发生。** 但它们共享同一个形状——**都把「什么必须固定下来」和「什么留给后来者」分开处理。** 讲义把这层意思推到本讲的核心观点上：好的架构不是只选出一个解，而是设计开放需求空间所对应的解空间。

## 四、账本代码管约束，模型管翻译

讲义对模型与代码的分工说得很清楚：**语言模型负责提出符合材料的动作，账本代码负责这些动作的确定含义和约束；编译出来的动作是否符合真实业务，仍然是需要审查的环节。**

三者的责任边界因此是清楚的：

- **模型**：把「原始凭证 + 业务描述」翻译成受约束的记账动作（`报表_支出_财务费用(CNY(75))` 这样的表示）。
- **规则表 + 账本代码**：给出每个动作对三张报表的影响，并保证借贷相等、结算不重复确认费用（讲义规则表的说明里明确写着「结算不重复确认费用，减免或退款冲回原费用」）。
- **人**：核对动作与凭证、业务含义是否对应。

这里有个容易越界的地方值得点出来：**检查器能查什么、不能查什么，是有明确边界的。** 试算平衡能查分录是否自洽；规则表能算准每张报表的每个格子；**两者都查不出「这笔费用到底该不该发生」**。第一节能把「归错科目」标成平，正是这个边界的直接演示——所以不能把「过了检查」写成「做对了」，这正是讲义说「编译出来的动作是否符合真实业务，仍然是需要审查的环节」的原因。

## 五、它不解决什么

- 本文只覆盖讲义的记账案例与三处经典基础设施的判断，**没有复述讲义全篇**。本讲其他内容——需求与架构、Structured Programming、Steele 与「解空间」、MVC 与 MVVM、教务系统的毕业审核依赖链——见本站已有的[让结论可解释：事件溯源、CQRS 与需求变化的位置](/blog/event-sourcing-and-explainable-conclusions/)与[「需求改一处要跟几处」](/blog/requirements-change-impact-measured/)。
- 第一节的三本账是**按讲义 `pay_payroll` 片段重写的最小实现**，讲义原文的片段依赖项目内的金额类型、分类表和账本操作，不能脱离这些定义单独运行；本文补齐了这些上下文，并只保留与本节论证相关的部分。
- 第二节的两个数字按课程规则表的「每 1 元」口径计算，与讲义一致；但规则表本身是课程课堂工具的实现，**不是通用会计准则**，不同准则下同样的业务动作可能落在不同科目。
- 「归错科目」「重复录入」两种错误由我构造，用来演示约束的边界；讲义原文只列举了这两类错误的可能性，没有给出这三个具体样本。
- 第三节的「按行切开得到三条」是**我用 Python 造的两个文件**（其中一个文件名含换行符）跑出来的，不是课程材料里的数字；讲义原话是「文件名能包含换行时，就不能假设『按行切开』总能无歧义地还原文件列表」。

## FAQ（六、常见问题）

**试算平衡通过了，能说明账做对了吗？**
不能。它只说明分录自身自洽。归错科目、重复录入都仍然平衡，区别在于费用科目上的数字对不对。

**那到底什么能判定对错？**
三样一起：模型把凭证翻译出的动作是否与业务含义对应（要人审查）、规则表算出的报表数字、以及来源事实本身。规则表保证「算得对」，不保证「该算的账被算了」。

**为什么不让模型直接填报表格子？**
因为报表有二十多行，模型逐格填的是它的猜测；让它提交记账动作，数字由规则表统一算出，可重算、可审计。讲义的要求是「不希望让模型逐格填写这些数字，而希望它们来自同一组动作及其计算规则」。

**22.07 这个数字是怎么来的？**
它是讲义例子里的利息收入金额，不是推算出来的。规则表按「每 1 元」给影响，我把它乘以 22.07，再与 75 元的支出相加，得 −52.93，与讲义一致。
