> 本文是 **Agent Skills 系列教程**第 4 篇。前三篇把地基和规则都铺好了：第 1 篇说 Agent 是「没有记忆的新人」，codebase 结构决定它的产出质量；第 2 篇说结构该怎么改——深模块把接口做窄、灰盒模块把「人定接口、AI 管实现、测试锁行为」的分工固定下来；第 3 篇给了写 skill 的三条规则——分层架构、命名约定、「skill 不必长」的克制。这一篇是实操上篇：**拿这套规则，从零写一个完整、能用的 skill。** 选的题目是后端和运维天天要面对的一件事——线上故障排查。

---

## 为什么选「线上故障排查」

写第一个 skill 时，最怕的不是「写不出来」，而是「选了一个要么太宽、要么太窄的题目」。太宽，比如「帮我写代码」，你会发现无从下口——它没有可定义的边界，也就没有可固化的路径；太窄，比如「帮我格式化这一行注释」，又撑不起一个 skill 该承载的纪律。**「线上故障排查」恰好落在中间，而且有三个理由让它成为绝佳的入门题。**

**第一个理由：后端和运维天天遇到，是刚需中的刚需。** 生产环境 error 率飙了、某个接口超时了、凌晨三点被 oncall 电话叫起来——这类事不是「偶尔发生」，而是每个后端和 SRE 的日常。正因为高频，它才值得被固化成一个 skill：你会反复用到它，一次写好、长期复用，投入产出比最高。

**第二个理由：它通用，不绑任何技术栈。** 排查一个 Java 服务的 GC 异常、一个 Kafka 消费积压、还是一个 Redis 热 key，背后的过程结构是同一套——确认现象、缩小范围、建立假设、取证、修复、回归。这套过程不依赖你是用 Spring 还是用 Flink，不依赖日志是 ELK 还是 Loki，也不依赖语言是 Go 还是 Python。**正因为通用，它天然是一个「灰盒模块」的理想载体——你定接口（排查循环的骨架），AI 管实现（每一步具体怎么看日志、怎么写命令），测试锁行为（它到底有没有按六步走）。**

**第三个理由：它正好能演示第 2 篇和第 3 篇的两条核心原则。** 第 2 篇讲「灰盒」——人定循环骨架，AI 按步执行，而不是让 AI 在故障现场自由发挥、到处乱猜；第 3 篇讲「description 触发 + 克制」——先定义「什么时候用」，再把正文写到最少的必要字数。一个「线上故障排查」skill，这两条原则都能落进去：**循环骨架就是灰盒里「人定的接口」，description 的触发条件就是克制的第一刀。**

换句话说，选这个题不是因为它「简单」，而是因为它「结构清晰」。结构清晰，你才能把第 3 篇学到的规则一一用上；结构清晰，你写出来的 skill 才经得起下一次真实故障的检验。

## 先写 description（触发条件）

第 3 篇反复强调过一句话：**description 比正文重要。** 因为会话开始时，Agent 只读所有 skill 的 name 和 description，靠它们判断「这个任务该不该加载这个 skill」。description 写砸了，正文写得再精彩也没机会被读到。所以写这个 skill 的第一步，不是写正文，而是先把触发条件定下来。

这本身就是灰盒思维。灰盒模块的第一要素是「人定接口」——先划定边界，再谈实现。对 skill 来说，description 就是它的边界：**你先把「这个 skill 管什么、不管什么」写清楚，后面正文里的每一句才有个不越界的参照。** 很多人写 skill 反过来——先把正文写满，最后补一句 description 应付了事。结果正文写得又长又泛，description 却触发不了，等于白写。

那「线上故障排查」的触发条件该怎么写？回到第 3 篇给的口诀：**「什么时候用 + 关键词」，两个要素缺一不可。** 先想「什么时候用」：当用户报告生产故障、服务不可用、告警、错误率飙升、性能骤降的时候。再想「关键词」：用户可能会说「排查」「定位」「救火」「oncall」。把这两样拼起来，就是这条 description：

```yaml
description: 线上故障/事故排查的纪律化循环。当用户报告生产故障、服务不可用、告警、错误率飙升、性能骤降，或说"排查/定位/救火/oncall"时使用。
```

拆开看：前半句「线上故障/事故排查的纪律化循环」点明这是干什么的；后半句「当用户报告……或说……时使用」列出触发场景和命中关键词。有了这后半句，下次你在对话里说「`生产环境 error 率突然飙到 20%，帮我排查`」，Agent 就能把「排查」这个关键词对上号，自动加载这个 skill。**这就是 description 的力量——它不是给正文写的一个「标题」，而是一个真正的触发开关。**

````markdown
# 线上故障排查

线上故障排查是"控制影响面 → 定位根因 → 修复 → 复盘"的纪律化循环。目标是先止血再追根，用可复现的证据而不是猜测驱动每一步。

## 原则：先止血，再追根

- **第一优先级永远是恢复服务**，不是找到根因。能回滚就回滚，能摘流量就摘流量。
- 动手前先确认影响面：哪个服务、哪个环境、影响多少流量、是否用户可感知。
- 每条结论都要能追溯到日志/指标/告警证据，禁止"感觉是这个问题"。

## 循环（一次只做一步）

1. **确认与分级（Confirm）**：复现或确认故障现象，记录现象、影响面、开始时间。问：这个现象真的存在吗？影响有多大？
2. **缩小范围（Minimise）**：用二分法缩小到最小可疑范围——哪个服务、哪个版本、哪次发布、哪个时间段。问：最近改了什么？（发布/配置/流量/依赖）
3. **建立假设（Hypothesise）**：针对最小范围列出可证伪的假设，按概率排序。每个假设要能回答"如果它对，我能观察到什么"。
4. **取证（Instrument）**：用日志、指标、trace、dump 验证排第一的假设。先看数据，再动系统。
5. **修复（Fix）**：最小改动修复，验证故障消失。
6. **回归与复盘（Regression & Review）**：补回归验证 + 写复盘（根因、时间线、避免再犯的 action）。

## 铁律

- 禁止跳过"确认"直接改代码——你以为的问题往往不是真正的问题。
- 禁止同时改多个变量，否则无法归因。
- 修复后必须回归：故障消失 ≠ 根因修复。
````

这个文件就三段内容——一段原则、一段循环、一段铁律。下面逐段拆解它为什么这样写、每一行在防什么。

### 原则段：先止血，再追根

第一段只有三行，但它定下了整份 skill 的**价值观**，比后面六步都重要。它的核心就一句：**第一优先级永远是恢复服务，不是找到根因。**

这句话是反直觉的，尤其对工程师。工程师的本能是「找到根因」——有问题就有根因，找到根因才算「解决了」。但在生产故障现场，这个本能是危险的：凌晨三点，error 率飙到 20%，用户在刷不出页面。如果你此刻的第一反应是钻进代码里找 bug，你就把「用户的损失」排到了「你的求知欲」后面。**正确顺序是先止血——能回滚就回滚，能摘流量就摘流量，让服务先恢复，再慢慢追根。** 这一行写进 skill，是为了把「正确的顺序」从你的临场反应，变成 Agent 每次都会先走的一步。

后两行是这条价值观的两条配套约束。「动手前先确认影响面」——哪个服务、哪个环境、影响多少流量、是否用户可感知——是为了防止 Agent 在错误的对象上动手：如果它连「是哪个服务挂了」都没确认清楚就开始查，那它查的可能是另一个健康的服务。「每条结论都要能追溯到证据，禁止『感觉是这个问题』」——这是把「证据驱动」钉成硬要求：**故障排查最怕的就是「我觉得」，而 Agent 恰恰是最容易「觉得」的——它没有历史经验，一旦失去证据约束，就会用自信的语气输出一堆猜测。**

### 循环段：六步，一次只做一步

第二段是整个 skill 的主干，也是灰盒模块里「人定的接口」最具体的体现。**你把排查过程拆成了六个有先后顺序的步骤，Agent 每次都必须按这个顺序走，一次只做一步，不跳步、不并行。** 这就是「人定接口」——骨架是你设计的，AI 只是每一步里「怎么执行」的执行者。

六步分别是：**确认与分级（Confirm）→ 缩小范围（Minimise）→ 建立假设（Hypothesise）→ 取证（Instrument）→ 修复（Fix）→ 回归与复盘（Regression & Review）。** 这个顺序不能乱，因为它编码了一条从「现象」到「根因」到「修复」再到「防再犯」的完整因果链。

前两步——**确认**和**缩小范围**——做的是「把问题变成可回答的形式」。确认这一步问「这个现象真的存在吗？影响有多大」，它的价值在标题里的「一次只做一步」：很多人（包括 Agent）一上来就跳到「是不是上次那个 bug」，但那个 bug 和这次的现象可能毫无关系。**先确认现象存在、量化影响面，才能避免在假问题上浪费整个排查。** 缩小范围这一步用的是二分法——哪个服务、哪个版本、哪次发布、哪个时间段，核心问题是「最近改了什么」。生产故障十有八九和「最近的一次变更」有关：一次发布、一次配置改动、一次流量高峰、一次依赖升级。把这个范围缩到最小，后面的假设才不会漫天撒网。

中间两步——**建立假设**和**取证**——是「证据驱动」最密集的地方。建立假设要求「每个假设要能回答：如果它对，我能观察到什么」——**这一步的意义在于把假设变成可证伪的。** 一个不能证伪的假设（「大概是网络问题」）没有价值，因为它没法被验证；一个可证伪的假设（「如果是新版本引入的，那么回滚后 error 率应该下降」）才有资格进入下一步。取证则是用日志、指标、trace、dump 去验证排第一的假设，而且特别强调「**先看数据，再动系统**」——不要为了「验证」而重启服务、清缓存、改配置，那会让证据消失，也让故障现场被破坏。

最后两步——**修复**和**回归与复盘**——收尾。修复要求「最小改动」，呼应第 1 篇「别让 Agent 在错误的地方打补丁」：最小改动才能被归因，改动越大，你越不知道是哪一下修好的。回归与复盘则把「故障消失」和「根因修复」区分开——**故障消失可能是因为流量降了、缓存重建了、临时重启了，而不是根因被修好了。** 不补回归验证，同一个坑下次还会踩；不写复盘，这次踩的坑就不会变成团队下一次的免疫力。

### 铁律段：三条，钉死最容易犯的三个错

第三段只有三行，但每一条都是对「Agent 会在哪个环节翻车」的精准预防。

**「禁止跳过『确认』直接改代码」**——这是最容易犯的错，也是最贵的错。Agent 看到一段报错堆栈，第一冲动就是「我看出问题了，改这一行」。但「你以为的问题往往不是真正的问题」：报错堆栈指出的是症状，不是根因。这条铁律把「先确认」从「建议」升级成了「禁止」。

**「禁止同时改多个变量」**——这是归因的纪律。如果你一次改了三个地方，故障消失了，你无法知道是哪一个改对了；如果故障没消失，你更不知道是哪一个没改对。一次只改一个变量，才能让「修复有效」成为一个可以被验证的结论。

**「修复后必须回归：故障消失 ≠ 根因修复」**——这是对「表面修复」的最后一刀。它和第 3 篇「测试锁行为」一脉相承：**你验证的是「行为恢复了」，而不是「我改了代码」。** 改了代码只是动作，行为恢复才是结果，而结果必须被回归测试确认。

这三条铁律，加上原则段和循环段，合起来就是这个 skill 的全部。它没有一句多余的话，但每一句都在防一个真实会发生的翻车点——这就是第 3 篇说的「在对的时机说对的话」。

## 落地：放进 .agents/，让它真的能被触发

写完文件，接下来是让它「跑起来」。skill 的物理形态极其简单，落地就三步：

**第一步，建目录。** 在项目根目录下创建 `.agents/skills/incident-diagnosis/` 这个文件夹（如果 `.agents/skills/` 还不存在，先创建它）。

**第二步，放文件。** 把上面的完整内容原样存成 `SKILL.md`，放到 `.agents/skills/incident-diagnosis/SKILL.md`。注意文件名是 `SKILL.md`，全大写，不能改名。

**第三步，触发验证。** 重新开一个 Agent 会话，直接说：

```
生产环境 error 率突然飙到 20%，帮我排查
```

如果一切正常，Agent 会先读出这条 description、命中「排查」这个关键词，然后加载 skill，按照六步循环开始走——而不是直接丢给你一段「可能是 XX 问题」的猜测。

这里值得停下来想清楚一件事：**为什么这一步能「自动」发生？** 因为 skill 的加载不是靠你手写「请用 incident-diagnosis skill」，而是靠 description 的触发匹配。会话开始时，Agent 读到了所有 skill 的 name 和 description，你的这句话里「排查」两个字的语义，恰好命中了 description 里的「或说『排查/定位/救火/oncall』时使用」。**开关是自动合上的——你不需要记得有这个 skill，Agent 会在该用的时候自己想起它。** 这正是第 1 篇「Agent 没有记忆」问题的一个漂亮解法：你无法指望 Agent 记得「排查该按什么流程」，但你可以让流程在「排查」两个字出现时，被 description 自动递到它面前。

这也解释了为什么 description 里要把「排查、定位、救火、oncall」这些关键词都写进去——**多写一个关键词，就多一条能被命中的路径。** 你说「帮我定位一下」「这个 oncall 帮我看看」，都能触发同一个 skill。关键词覆盖得越贴近真实说法的多样性，skill 就越不容易「该用的时候没被用到」。

## 验证它真的有用：好响应 vs 坏响应

写好 skill，不是终点。**你得验证它「真的改变了 Agent 的行为」——这也是第 2 篇「测试锁行为」的思想：不要相信 skill 存在，要相信 skill 被触发后，Agent 的行为真的变了。** 怎么验证？给它一个真实故障描述，观察它有没有按六步走，而不是直接猜代码。

假设故障场景是这样的：

> 昨晚 10 点部署了 `order-service` 的 v2.3.1 版本，今天早上开始，下单接口的 P99 延迟从 200ms 涨到 3s，error 率从 0.1% 涨到 8%，用户投诉「下单很慢、偶尔失败」。

**没有 skill 时，一个典型的坏响应长这样：**

> 「这很可能是 v2.3.1 里的 N+1 查询问题，我帮你在 `OrderMapper` 里加一个批量查询，顺便把连接池调大一点。」

这个响应错在哪？**它跳过了确认、跳过了缩小范围、跳过了取证，直接跳到「改代码」。** 它甚至没有先去看一眼延迟涨在哪个环节——是 DB 查询慢、还是下游调用慢、还是 GC 频繁？它凭「最近发了版」这一个信号，就锁定了「N+1 查询」这个猜测，还附带一个「调大连接池」的无关改动（一次改两个变量，违反铁律）。这种响应看着「很能干」，实际上是在瞎猜——它可能蒙对，也可能让故障更糟。

**有了 skill 之后，一个好响应长这样：**

> 我先按排查循环来，一次一步。
>
> 1. **确认**：下单接口 P99 3s、error 率 8% 是真实现象吗？我查一下监控，确认影响的是 `order-service`，影响所有走下单的用户，从今早 7 点开始。
> 2. **缩小范围**：最近一次变更是昨晚 10 点部署 v2.3.1。我先确认延迟是新增的还是偶发的——对比部署前后的 P99 曲线，并定位延迟具体在哪个环节（DB / 下游 / 内部计算）。
> 3. **建立假设**：按概率排序，假设一是 v2.3.1 引入的慢查询；假设二是新版本改动的下游调用超时重试变多。假设一可观察到「DB 慢日志出现对应 SQL」；假设二可观察到「下游调用耗时上升」。
> 4. **取证**：先看数据再动系统。我拉一下 DB 慢查询日志和 trace，看看延迟落在哪一段。

这个响应没有一行改代码，但它每一步都在收敛问题、都在用证据说话。**这就是 skill 的价值：它把「正确的过程」变成了 Agent 的默认行为，而不是每次都要你在 prompt 里苦口婆心地叮嘱「先别改代码，先看数据」。**

怎么把这种验证做成可复用的习惯？很简单：**在 skill 落地后，拿一两个你团队里真实发生过的故障（脱敏后的），喂给 Agent，看它走不走六步。** 走六步，说明 description 触发成功、正文纪律生效；不走六步，回头检查 description 的关键词有没有覆盖到你的真实说法，或者正文是不是哪里写得太含糊。这一步验证不花多少时间，却是「skill 真的有用」和「skill 只是写了个文件」之间的分水岭。

---

## 小结：你已能用最佳实践写 skill

这一篇，你从零写出了一个完整、能跑的 skill。回顾一下你实际做了什么：

**你用了第 3 篇的规则。** 先写 description（触发条件），把「什么时候用 + 关键词」定清楚；正文保持克制，三段、不到 40 行，没有一句废话。

**你用了第 2 篇的灰盒思维。** 人定接口——六步排查循环的骨架是你设计的；AI 管实现——每一步怎么查日志、怎么下命令交给它；测试锁行为——通过「好响应 vs 坏响应」的对比，你验证了 Agent 确实被这条路径牵引着走。

**你用了第 1 篇的结论。** 你无法指望 Agent 记得「排查该按什么流程」，于是你把流程写成了 skill，让它在「排查」两个字出现时被 description 自动递到 Agent 面前——用结构，弥补它「没有记忆」的先天缺陷。

到这里，你已经具备了「用最佳实践写一个 skill」的完整能力。但这只是一个 skill。下一篇——本系列的收官之作——会回答一个更上层的问题：**当你的 skill 不止一个、开始形成一套系统时，怎么给单个 skill 加上 sidecar、再把「主线」这条脊椎搭起来，让一个个 skill 在「idea → ship」的完整链路里各归其位、互相配合。** 单个 skill 让你在「一件事」上可靠，skill 系统让你在「一整条链路」上可靠。第 5 篇，讲的就是这条链路的组合方式。
