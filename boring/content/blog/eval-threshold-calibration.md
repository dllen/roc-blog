RAG 系统跑了三个月，它变好了还是变差了？这个问题之所以难答，是因为 LLM 输出没有单一数字能抓住质量。2026 年主流的三个评估框架各自给出了不同的切入点：

| 维度 | RAGAS | DeepEval | G-Eval |
|---|---|---|---|
| 专注域 | RAG 系统 | 任意 LLM 输出 | 任意 LLM 输出 |
| 是否需要金标准 | 不需要 | 可选 | 可选 |
| 集成方式 | Python API | pytest 插件 | Python API |
| 成本 | 中（LLM 判断） | 中 | 高（多次 LLM 调用） |
| 主要用例 | RAG 质量监控 | CI 回归测试 | 开放式生成质量 |

常见用法是三者互补：RAGAS 做持续监控，DeepEval 做 CI 回归门，G-Eval 做人工审核校准。这张表和这套分工在本站已经写透，不再重复——[DeepEval v4 深度解析](/blog/deepeval-v4-evaluation-framework/)、[三层 AI 评估指标](/blog/three-layer-ai-evaluation-metrics/)、[Eval 设计与自动爬坡](/blog/eval-design-and-hillclimbing/) 分别覆盖了框架内部、指标分层与实验闭环。

剩下一个没人愿意细说、却直接决定门禁是否可信的问题：**`threshold=0.7` 这个 0.7 是谁定的？**

## 一、框架分是相对的，阈值是绝对的

三个框架有一个共同点：分数是**相对**的。同一份答案，换一个判官模型、换一版 prompt、换一批检索块，分数就会动。而 CI 里的门禁是**绝对**的——`assert_test` 只认「≥ 0.7 通过」。

把相对的分数当绝对阈值用，会产生两种事故，而且两种都不会报错：

- **阈值太低**：坏答案通过。门禁常年全绿，团队以为质量没问题，其实只是门没关上。
- **阈值太高**：好答案被拦。研发开始怀疑评估本身，最后把门禁用 `--no-verify` 绕过去——评估体系从此形同虚设。

所以「选框架」只是第一步，真正落到生产的是**校准（calibration）**：拿一批人工标注样本，量出「框架分」和「人类判断」在哪个阈值上最吻合。源笔记把这条写成了选型指南里的第 5 条要求，并且明确拒绝两件事：**拒绝无校准的阈值**、**拒绝在无采样策略的生产流量上做全量评估**。

## 二、把校准写成一次可跑的扫描

校准本身不神秘：给它一批样本，每条带框架分和人工判定，扫一遍阈值，看哪个点的 F1 最高。下面是一份最小实现，20 条玩具样本（人工判定「这条答案可以发」8 条）：

```python
SAMPLES = [
    # (框架分, 人工判定)
    (0.93, True), (0.88, True), (0.84, True), (0.79, True), (0.76, True),
    (0.65, True), (0.62, True), (0.55, True),
    (0.81, False), (0.74, False), (0.71, False), (0.68, False), (0.59, False),
    (0.52, False), (0.47, False), (0.41, False), (0.33, False), (0.28, False),
    (0.22, False), (0.15, False),
]


def scores_at(threshold):
    tp = fp = fn = 0
    for score, label in SAMPLES:
        passed = score >= threshold
        if passed and label:
            tp += 1
        elif passed and not label:
            fp += 1
        elif not passed and label:
            fn += 1
    precision = tp / (tp + fp) if tp + fp else 1.0
    recall = tp / (tp + fn) if tp + fn else 1.0
    f1 = 0.0 if precision + recall == 0 else 2 * precision * recall / (precision + recall)
    return precision, recall, f1


def main():
    print("样本数 {}（人工判为可发 {} 条）".format(
        len(SAMPLES), sum(1 for _, label in SAMPLES if label)))
    print()
    print("阈值  精确率  召回率  F1")
    best = None
    t = 0.50
    while t <= 0.95001:
        p, r, f1 = scores_at(round(t, 2))
        print("{:.2f}   {:.2f}    {:.2f}    {:.3f}".format(round(t, 2), p, r, f1))
        if best is None or f1 > best[1]:
            best = (round(t, 2), f1)
        t += 0.05
    print()
    p70, r70, f70 = scores_at(0.70)
    print("默认拍 0.70：F1 = {:.3f}".format(f70))
    print("校准后最优 {:.2f}：F1 = {:.3f}".format(best[0], best[1]))
    print("差值 = {:+.3f}（这就是「阈值没拍对」的代价）".format(best[1] - f70))


if __name__ == "__main__":
    main()
```

```text
0.55   0.62    1.00    0.762

```

这份输出有三处值得停下来看：

1. **拍出来的 0.70 不是最优**。最优在 0.55，F1 差 0.137。也就是说，一条「随便定 0.7」的门禁，在这批样本上会同时漏掉好答案、放过坏答案——而两边都不报错。
2. **阈值越高越不准，但精确率并不单调**。0.50 → 0.55 → 0.60 的精确率是 0.57 → 0.62 → 0.64 → 0.60，中间回落了一次，因为 0.60 这个点刚好把一个 0.59 的坏样本拦在外面、把 0.62 的好样本也拦了。**这正是「靠直觉调阈值」失效的原因**：precision 与 recall 随阈值的变化是分段跳变的，你不扫一遍就不知道自己站在哪一段。
3. **F1 最优不等于业务最优**。如果漏掉一条好答案的代价远高于放过一条坏答案（例如客服草稿要人工复核），你就该往高阈值挪，接受更低的 F1；反过来（例如内部检索辅助，把坏答案给人看一眼无所谓）就该往低阈值挪。**校准给的是曲线，不是答案。**

## 三、采样：全量评估是最常见的成本事故

第二个被明确拒绝的做法是「在生产流量上做无采样的全量评估」。三个框架的评估都要调 LLM（RAGAS 的忠实度靠 NLI 或 LLM 判官、G-Eval 是多次调用），成本随流量线性增长，而质量结论并不随样本量线性变准。

工程上通常这么配：

| 场景 | 采样口径 | 目的 |
|---|---|---|
| 持续监控（RAGAS） | 按日固定比例的流量，或按异常特征加权（低分、长答案、命中空检索） | 发现趋势与回退，不求精确绝对值 |
| CI 回归（DeepEval） | 固定的测试集（几十到几百条），每次全跑 | 结论可比，成本可控 |
| 人工校准（G-Eval + 人审） | 50-100 条分层抽样 | 定阈值、定期复核 |

注意第二行的关键：**CI 用固定测试集，是为了让两次运行可比**。如果每次从生产流量里随机抽一批，分数变化里就混进了抽样噪声，你分不清是模型退化了还是抽到了更难的样本——这和「用 mtime 判断文件有没有变」是同一类错误：**拿会动的量当基准**。

## 四、校准的边界（这份脚本判不了什么）

- **玩具数据不是校准**。上面的 20 条是为了演示机制；真实校准要 50-100 条以上人工标注，且要覆盖不同难度层（简单事实题、多跳推理、拒答）。样本里只有 8 条正例，F1 对单条样本的进出非常敏感。
- **阈值不能跨任务搬**。RAG 的忠实度和创意写作的连贯性不是一个量纲，0.55 在 A 场景最优不代表在 B 场景可用。每次换判官模型、换 prompt、换指标实现，都要重新扫一遍。
- **F1 不是唯一目标**。上面第三点已经写了：业务代价不对称时，最优阈值不在 F1 最高点。
- **它不判断答案对不对**。校准只对齐「框架分」与「人类判断」的一致性；如果人工标注本身错了，校准会忠实地把这个错误固化进阈值。所以标注质量是这套流程真正的上限。

## 五、落成一条可执行的要求

把上面几节压成一句可检查的话：**每个上线的阈值，都要能指出它是从哪批人工标注、哪次扫描里出来的。**

这句话可以当作 review 检查项：CI 里出现 `threshold=0.7` 时，问三个问题——这批标注有多少条、覆盖哪些难度层、最近一次校准是什么时候。答不上来的阈值，按未校准处理。
