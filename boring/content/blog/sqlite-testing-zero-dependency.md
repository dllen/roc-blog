「SQLite的活法」是一个被反复问起的问题：一个诞生在军舰项目里的 side project，今天跑在浏览器、手机、汽车和客机里，存着你的 iMessage 和 WhatsApp 消息，按一些统计口径是全世界部署最广的软件模块——它为什么没有像 OpenSSL 那样在成为基础设施的瞬间被维护压力压垮？CoRecursive 播客第 066 期对作者 Richard Hipp 的访谈给了第一手答案。本文是对这篇访谈字稿的译写整理（未获转载授权，引用只摘短句），增量有三处：把 Hipp 的口述数字与 sqlite.org 官方文档的口径做成对照表，校正 DO-178B 的时效信息，以及把访谈里的故事提炼成三条可迁移的机制——治理上的「出钱换荣誉不换控制权」、测试上的资产与发布速度关系、依赖上的「零依赖 + 保留接管能力」。

## 一、军舰上诞生的数据库

SQLite 的起点是一个尴尬的弹窗。2000 年前后，Hipp 作为 Bath Iron Works 的承包商给驱逐舰 DDG-79 Oscar Austin 写损管阀门控制系统——管道破裂时，该关哪些阀、该开哪些阀恢复下游系统，是个通用有向图上 NP 完全的问题，得用启发式近似求解。算法是他的团队写的，数据库是船上装好的 Informix，服务器时好时坏。每次 Informix 宕机，屏幕上弹出「Can't connect to database server」——对话框是他们画的，锅就是他们的。战损场景下，这种弹窗不可接受。

Hipp 的反思很直接：我们只是把数据读进内存做计算，不做事务，为什么要一个服务器？当时没有直读磁盘的 SQL 引擎，同事随口一句「那你自己写一个」，加上据他回忆（口述自带 "if I recall correctly" 的对冲）2000 年前后一场「Newt Gingrich 和比尔·克林顿的某种斗争」导致联邦合同经费中断，让他闲了几个月，SQLite 就诞生了。编者注：公开记录里 Gingrich–Clinton 预算之争引发的联邦政府停摆发生在 1995-96 年，2000 年并没有联邦停摆——口述与公开记录对不上，本文两说并记，不裁定真伪。架构带着他编译器背景的直接印记：把每条 SQL 语句当程序，编译成字节码执行。事后看，这条独立发明的路线与 Postgres 的火山模型（volcano model）在优化手段上殊途同归——两条互不知情的路线收敛到同一组答案，Hipp 把它当作对理论的验证。

项目恢复后客户坚持用 Informix，SQLite 只当内部开发测试用，但 Hipp 把它放上了互联网。传播靠的是 netnews 上一个帖子：「我在 Palm Pilot 上跑起了 SQL 数据库。」嵌入式场景的需求一直在那里，只是没人做过。

## 二、8 万美元，和一条治理规则

商业化的第一单来自 Motorola（2001/2002 年），对方要把 SQLite 放进新手机操作系统，问报价。Hipp 当时的反应是慌：「开源软件能赚钱？怎么定价？」他把答复拖到第二天，仓促之间编了个报价，约 8 万美元——「当时我以为那是全世界的钱」。这笔钱雇了三个人，成了起点。随后是 AOL（安装 CD 里要一个数据库）和 Symbian：Nokia 手机操作系统的团队跑了一场 bake-off，10 个数据库引擎（2 个开源、7 个闭源、加上 SQLite），给了其他九家调优机会，SQLite 照样赢了。为了这个结果，Hipp 感恩节当天飞去了伦敦。

真正值得抄下来的是接下来的治理设计。Symbian 提出 SQLite 的 bus factor 太低（Hipp 被公共汽车撞了项目就停），要求建立 SQLite Consortium 保证长期可用。Hipp 最初的方案是成员投票制，Mozilla 基金会的 Mitchell Baker 听说后直接打电话过来：「你把这事做错了。」她定的规则是——开发者控制一切，开发者的决定是最终决定；公司成员只有出钱的荣誉，没有投票权。「不用担心没人加入，他们会来的。这样做的话，Mozilla 就是创始成员。」最终创始成员是 Mozilla、Symbian、Adobe。

这条规则可以概括为**出钱换荣誉，不换控制权**。对比常见的基金会模式（白金会员换董事席位），它放弃了用治理权换取更多资金的可能性，换来的是技术决策永远不被出资方绑架。对任何要接受商业赞助的开源项目，这是防「公司捕获」的最小可行结构。

## 三、Android 的预言，和「没有 bug」的破产

2005 年前后，iPhone 还没发布，Hipp 在 Mountain View 和 Android 团队调试 SQLite。那天他见到了一幕后来他认为预示了格局的场面：工程师手里是一台跑在公网蜂窝网络上的原型机，插着 GDB 在工作站上调试，中途还接了个老婆的电话。而同期 Motorola、Nokia、Symbian 的软硬件迭代周期是 30 天，工程师手上只有连不上无线电的大面包板。「一天刷好几次固件，对着真机在公网上调试——那一刻我知道 Android 会巨大。」但 NDA 让他不能回去提醒任何人，「那大概是它们衰落的原因之一」。

Android 带来的不只是市场，还有现实的毒打。百万级设备出货后，crash 报告涌来，Hipp 此前「SQLite 没有严重 bug」的公开说法被当场证伪：「你以为你能写出没有 bug 的软件，直到它被装进几百万台设备。」

转机来自一份航空标准。Hipp 同期为航电厂商 Rockwell Collins 干活，接触到 DO-178B——航空安全关键软件的质量标准，他特意强调这是少有的「真的读得懂」的标准：几百美元能买到，不厚，下功夫能理解。它对最高软件等级（Level A）的关键要求之一是 100% MC/DC（modified condition/decision coverage，修正条件判定覆盖）：机器码级别，每个分支操作都要被「取过」和「落过」至少一次，且每个布尔子条件都要独立影响过判定结果——比通常说的分支覆盖再严一档。需要说明时效：DO-178B 已在 2011 年被 DO-178C 取代（访谈录制较早），今天做航电认证对应的是后者，但 MC/DC 的要求一脉相承。

Hipp 决定把 SQLite 做到 100% MC/DC。代价是一年、每周 60 小时、每天 12 小时。他的总结带着那著名的边际曲线：前 95% 的覆盖率用前 95% 的预算就能拿到，最后 5% 要再花一个 95%。回报是：达标之后，来自 Android 的 bug 报告停止了，用他的话说「之后八九年基本没有 bug」（口述，主观口径）。关于错误如何从代码里被暴露出来，我在[软件质量保障：错误如何传播与暴露](/blog/fault-error-failure-testing/)里整理过 Fault→Error→Failure 的传播链——MC/DC 的意义就是把「测试推动 Fault 显形为 Error」这条箭头拉满到机器码的每个判定点。

## 四、测试体系全貌：口述数字与官方现值对照

访谈里 Hipp 报了一组数字，sqlite.org 的官方测试文档（2026-11-26 抓取）给出了另一组。两套口径相隔几年，都值得记录：

| 维度 | Hipp 口述（访谈录制时） | sqlite.org 官方文档（基于 3.42.0 版本口径，2023-05-16；2026-11-26 抓取） |
|---|---|---|
| 测试规模 | 约 10 万个独立测试用例，参数化后单次发布跑「数十亿次测试」 | 核心库约 155.8 KSLOC，测试代码与脚本 92,053.1 KSLOC——**590 倍** |
| TH3（100% MC/DC 套件） | 专有，本想卖给航电厂商，「一份都没卖出去」 | 证实专有、100% 分支覆盖 + 100% MC/DC；全覆盖运行约 240 万个测试实例；发布前 soak 测试约 2.485 亿次 |
| 模糊测试 | 「自定义 fuzzer 持续跑」 | dbsqlfuzz 同时变异 SQL 与数据库文件，16 核常驻，单实例 400 用例/秒 ≈ 每天 5 亿次；文档另一节写约 10 亿次变异/天（两处口径不一，均照录） |
| 发布前测试 | 「至少连跑 3 天」 | 未在文档中找到对应数字 |

标题里的 590 倍就是这张表的第一行：产品代码 15.6 万行，测试代码和脚本 9200 万行（官方口径基于 3.42.0 版本，2023-05-16）。这个比例解释了 TH3 的商业失败为什么不重要——它一份没卖出去，但让 SQLite 的新功能和修复可以极快发布，因为每次改动的回归风险被测试资产兜住了（Hipp 把极快发布归因于 TH3 本身，官方口径其本体约 1055.4 KSLOC、约核心的 6.8 倍；把功劳扩展到全部测试资产是本文的推断）。测试在 SQLite 这里不是成本中心，是发布速度的前提。

测试体系里有两件工具值得单独说。一是 **SQL Logic Test（SLT）**：Shane Harrelson 做的巨型 SQL 语料库，拿同一批语句跑遍所有能拿到的数据库引擎，比对结果是否等价。据 Hipp 口述，战绩彪悍：它让每一个引擎都 segfault 过——包括 SQLite 自己、商业版 Oracle、DB2——唯独 Postgres 从不崩且答案正确（「Postgres 的人说是我们不够努力」）。SLT 本质是差分测试的极限形态：不假设自己对，只要求和大家一致；这和用 NEMU 对拍 x86、用香山 DiffTest 对拍 RTL 仿真是同一个思想。二是**多平台执念**：Hipp 办公室里留着 PowerPC iBook 专门跑大端序测试，32 位、ARM、Intel、Windows、Linux、Mac、OpenBSD 一个不落。

对照 [从测试到证明](/blog/formal-verification-testing-to-proof/) 里讨论过的边界：100% MC/DC 是测试这一侧能做到的天花板，它仍然不是证明——Hipp 自己承认 Android 之前「没有 bug」的信念破过产。SQLite 的选择是把测试做到航空级、把模糊测试做到每天亿级，而不是走向形式化；对一个被全世界解析不可信输入的库来说，这个取舍本身就是一份论证。

## 五、第一性原理：书架上的 Knuth 与大西洋上空的覆盖索引

Hipp 写 SQLite 时找不到任何「如何写一个 SQL 数据库引擎」的参考资料——数据库理论集中在 MIT、Harvard、Berkeley，圈外的人不知道这套理论存在。他只好全部自己发明，工具是书架上的《The Art of Computer Programming》：B 树照 Knuth 的搜索章节写。有个细节很 Knuth：书里给了查找和插入的算法，**删除是章末习题**——写自己的 B 树之前，得先把习题做了。多年以后（录制访谈前一两年）他需要伪随机数生成器，第一反应还是翻这本书。

覆盖索引（covering index）的来历更戏剧：他在德国一场 PHP 大会上听 MySQL 创始成员 David Axmark 演讲，才知道「多列索引的查询若答案就在索引剩余列里，可以只查索引不回表」这个概念，回程的 Delta 航班上整排没人，他摊开笔记本在大西洋上空把整个特性实现了。Bloomberg 的工程师也以同样方式贡献过优化点子——「你怎么没做 X？」「没想到过。」「能做吗？」「看看。」

这些故事的共同点是：SQLite 的很多关键能力不是规划出来的，是**保持第一性原理的工作方式，然后接住每一个撞进来的想法**。没有参考资料意味着没有路径依赖，独立实现意味着每个决定都能讲出理由。

## 六、零依赖哲学：freedom 是背包客的自由

SQLite 几乎没有 Hipp 没亲手写的依赖——除了 C 编译器和少量 libc。解析器生成器是自己写的（Lemon，不用 Yacc/Bison，因为需要新语言特性时「生成器是我自己的，我就能改」）；版本控制是自己写的（Fossil）；连 bug tracker 都是自己的。

为什么不直接用 Git？Hipp 的回答是工具与项目的适配问题：Git 是为 Linux 内核社区完美设计的，对内核开发它无可挑剔；但换到 SQLite 的工作流上「完全糟糕」，而 Fossil 对 SQLite 完美，因为就是为它写的。他还给过一个反事实：如果 SQLite v2 当年选了 Berkeley DB 做存储引擎，后来 Berkeley DB 被卖给 Oracle 变成双许可专有，SQLite 就被别人的商业决策绑架了。

这套选择的底层逻辑，Hipp 用背包客作比：「freedom means taking care of yourself」——自由就是自己背起所有东西，不依赖第三方。访谈录制时他正被 Gmail 退信困扰，反应是「我要自己写一个邮件服务器」，尽管他承认这比写数据库引擎还难。但注意他没有把话说绝：他雇人割草，可车库里还留着自己的割草机——外包可以，**保留随时接管的能力**。这是零依赖哲学里最可操作的一条：现代工程没人能事事自建，但每个关键依赖都该问一句「它消失了，我能不能自己顶上」。对 npm 一个包消失全站瘫痪这类供应链故事，这是另一个极端的参照系。

至于给开源作者的建议，Hipp 只有一条：「别太听专家的。」无服务器、直读磁盘、不强制数据类型的数据库引擎，当年问任何专家都会得到「不可能、永远不会work、愚蠢的想法」——「幸运的是我不认识任何专家，所以就做了。」

## 七、能带走的三件事

把整个故事压缩成三条可迁移的机制：

1. **治理**：接受商业赞助时，用「出钱换荣誉、不换控制权」保住技术决策的独立性——Consortium 的成员名单给的是资金，不是对技术方向的背书，也不用担心赞助方反过来绑架方向。
2. **测试**：590 倍的测试资产不是洁癖，是发布速度的前提；覆盖率曲线的最后 5% 最贵，但用 Hipp 的话说，补完那最后 5% 之后，来自 Android 的 bug 报告停止了。评估自己的项目时，先问「发布前敢不敢连跑三天测试」。
3. **依赖**：每个外包决策都保留割草机——接管能力可以不常练，但不能没有；判断标准不是「现在方便吗」，而是「它消失了我怎么办」。
