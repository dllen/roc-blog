基础篇讲的是「该优化什么、怎么衡量」。这篇是它的执行版：一份 Agent Token 优化十层检查清单，可以在架构评审会上逐条勾。清单里的分层思路与 [Anthropic 的上下文工程指南](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) 一致：先管住进入上下文的东西，再谈压缩它。

清单的价值在于它把「你觉得已经很省了」变成「这五十来条你签个字确认」。下面每一层都给出三个东西：**要问的问题、常见反模式、可验证的判据**。

## 一、先分清四类动作

Agent 消耗 Token 的路径可以归成四类，评审时先判断某个动作属于哪类，再决定该不该调：

| 类别 | 含义 | 典型动作 |
|---|---|---|
| **少喂** | 减少上下文输入 | 精选信息、滑动窗口、分层记忆、工具结果结构化后回传 |
| **少想** | 压缩提示词 | 结构化格式替代长自然语言、模块化提示、精简 few-shot、基础提示保持最小 |
| **少说** | 控制输出长度 | 默认短回答、格式与长度约束、对废话与自动复述设边界 |
| **少循环** | 降低调用频率 | 事件驱动优先于定时驱动、去重冷却、延迟批处理 |

这四类是排查顺序，不是优化目标。「少喂」优先，因为它通常不动模型、不改逻辑，改一个查询就能见效。

## 二、十层检查清单

### 上下文层

- [ ] 是否采用「最近窗口 + 历史摘要 + 长期记忆」三层结构，而不是全量拼接上下文
- [ ] 是否对旧消息做增量摘要，而不是每次重写整段历史
- [ ] 是否在上下文接近阈值时主动压缩，而不是等满了再截断
- [ ] 是否把工具输出在进入上下文前先过滤、去噪、截断
- [ ] 是否只保留决策、状态、未完成项，而不是保留所有原始过程文本
- [ ] 是否对不同内容设定不同压缩比（工具输出压得更狠，最近对话尽量保留原文）

**反模式**：把整个 `git log`、整个 API 响应、整个文件塞进上下文，指望模型自己挑。

**判据**：随机抽一轮请求，问「删掉上下文里 30% 的内容，任务成功率会掉吗」。不掉，说明那 30% 是纯浪费。

### 提示词层

- [ ] System prompt 是否短且稳定，避免把业务说明、操作手册、示例都塞进去
- [ ] 是否把长提示拆成基础规则、场景模板、任务附加说明三部分动态组合
- [ ] 是否避免重复描述同一约束（安全规则、输出格式、角色定义尤其容易重复）
- [ ] few-shot 是否只保留少量高价值样本，而不是堆很多近似例子
- [ ] 是否把自由文本指令改成结构化 schema，让模型少读废话

**反模式**：提示词随功能增长而膨胀，没人敢删，因为不知道哪句还在用。

**判据**：把提示词里每条约束标上「这条在最近 100 次调用里生效过吗」，长期没被触发的直接删。

### 工具层

- [ ] 是否只向模型暴露当前任务真正需要的工具
- [ ] 工具描述、参数名、返回字段是否尽量短
- [ ] 工具返回是否做字段裁剪，只回传下一步需要的信息
- [ ] 是否避免「查一次、再总结一次、再校验一次」这种重复往返
- [ ] 能并行的工具是否并行执行，而不是串行多轮
- [ ] 是否对相同输入结果做缓存，避免重复调用同一工具

**反模式**：先拉全量数据，再让模型「挑出相关的 10 条」。筛选本该发生在工具里。

**判据**：量一次工具返回的原始字节数与实际送进上下文的字节数。比值接近 1 的工具通常有裁剪空间。

### 任务编排层

- [ ] 是否把大任务拆成多个短任务，减少单轮上下文膨胀
- [ ] 是否区分「检索、抽取、分类、总结、决策」五类动作，并对每类使用不同流程
- [ ] 是否优先让确定性代码处理规则逻辑、字段拆分、计算，再交给模型处理语义部分
- [ ] 是否减少 agent 自我反思、自我校验、自我复述的轮次
- [ ] 是否设置最大循环轮数和失败重试上限，防止空转

**反模式**：一个 Agent 拿着完整任务描述一路做到底，中间失败就从头再来。

**判据**：看最长的那条调用链有多长。超过 5 步基本就该拆了。

### 模型路由层

- [ ] 是否为不同任务设置不同模型档位，简单任务不占用大模型
- [ ] 是否先用小模型做分类、路由、意图识别，再决定是否升级
- [ ] 是否把摘要、标签、结构化抽取这些工作交给更便宜的模型
- [ ] 是否对高频任务启用缓存或模板回复，减少重复生成
- [ ] 是否对长上下文场景单独设计「压缩后再推理」的路径

**反模式**：所有请求走同一个最强模型，因为「省心」。

**判据**：按任务类型统计调用分布。如果高档位模型的调用里超过一半是分类和格式化，路由就是摆设。

### 输出层

- [ ] 是否默认短输出，只在用户明确需要时才展开
- [ ] 是否限制最终回答的格式，例如「结论 + 3 条依据」
- [ ] 是否避免模型重复输出已经确认过的信息
- [ ] 是否对表格、JSON、要点列表等结构化输出做长度约束
- [ ] 是否让模型只输出下一步所需动作，不输出过程复述

**反模式**：默认输出长篇分析，读者只要一句话。

**判据**：统计输出 Token / 输入 Token 比值。持续高于 1 的场景，说明模型在写没人要的东西。

### 循环层

- [ ] 是否用事件驱动触发，而不是定时轮询
- [ ] 是否对重复事件做去重与冷却时间控制
- [ ] 是否将长任务拆成状态机，让每一步只看必要状态

**反模式**：定时扫描 + 无冷却，同一件事被反复处理。

**判据**：看触发日志里同一目标被触发的次数分布，长尾的那部分基本都是浪费。

### 可观测层

- [ ] 是否按请求记录 input token、output token、tool token 三类成本
- [ ] 是否统计每个节点、每个工具、每个模型的平均 token 消耗
- [ ] 能否定位最贵的 Top 10 场景
- [ ] 是否有上下文长度告警阈值（比如达到 70% 就触发压缩）
- [ ] 是否记录「重复读取、重复总结、重复调用」的漂移信号
- [ ] 是否把 token 数据接入仪表盘，支持按任务、用户、会话、版本拆分

**反模式**：只看总账单。总额告诉你「贵」，不告诉你「哪里贵」。

**判据**：能不能在十分钟内回答「上次那批任务里最贵的三个场景是什么」。不能，就还没建起可观测层。

### 缓存与复用

- [ ] 是否缓存系统提示词的固定部分
- [ ] 是否缓存常见检索结果、工具结果和中间摘要
- [ ] 是否对重复 query 做语义去重
- [ ] 是否考虑 prefix caching 或网关层缓存策略
- [ ] 是否避免同一会话中重复生成相同中间产物

**反模式**：每轮把系统提示词重新拼一遍，顺序还差一点。缓存就这么没了。

**判据**：看缓存命中率。稳定前缀的 Agent 场景，命中率低到个位数说明前缀在漂移。

### 失败修复

- [ ] 是否在失败案例中记录「为何浪费 token」
- [ ] 是否对失败样本做提示词和摘要策略回归优化
- [ ] 是否对异常长输出、异常长循环设置自动熔断
- [ ] 是否为不同业务场景建立专属压缩策略，而不是一套通用规则通吃
- [ ] 是否定期回收过期记忆、废弃工具和无效模板

**反模式**：失败就是重试，重试就是再烧一遍同样的 Token。

**判据**：算一次失败重试的代价。如果失败路径的成本接近成功路径，问题在设计而不在运气。

## 三、六问审查

评审会上如果只来得及问六句，问这些：

1. **这段信息真的需要进上下文吗？**
2. **这次任务需要大模型吗？**
3. **工具返回能不能只保留 20% 的关键字段？**
4. **这轮输出能不能再短一半？**
5. **这个循环有没有可能只跑一次？**
6. **这一步能不能不用模型？**

前四问针对上下文与输出，第五问针对调用次数，第六问针对成本结构。前三问通常能砍掉一半以上的开销；第六问威力最大但最难推动，因为会碰到架构。

## 四、记忆分层的最小实现

清单里的「分层记忆」和「滑动窗口」可以落成一个很小的结构。核心只有两条：**按层级分配预算、按重要性淘汰**。

```python
class HierarchicalMemory:
    """分层记忆系统"""

    MEMORY_TIERS = {
        "working":  {"retention": "current_task",     "max_tokens": 2000},
        "task":     {"retention": "current_session",  "max_tokens": 5000},
        "episodic": {"retention": "summarized",      "max_tokens": 2000},
        "longterm": {"retention": "external_rag",    "max_tokens": None},
    }

    def __init__(self):
        self.tiers = {k: [] for k in self.MEMORY_TIERS}

    def store(self, content: str, tier: str = "working", importance: float = 1.0):
        """按层级存储记忆"""
        max_tokens = self.MEMORY_TIERS[tier]["max_tokens"]
        self.tiers[tier].append({"content": content, "importance": importance})
        self.tiers[tier].sort(key=lambda x: x["importance"], reverse=True)
        if max_tokens:
            self._prune(tier, max_tokens)

    def _prune(self, tier: str, max_tokens: int):
        """淘汰低优先级记忆"""
        while self._estimate_tokens(tier) > max_tokens and len(self.tiers[tier]) > 1:
            self.tiers[tier].pop()

    def get_context(self, max_tokens: int = 4000) -> str:
        """按优先级组装上下文"""
        result, remaining = [], max_tokens
        for tier in ["working", "task", "episodic"]:
            for item in self.tiers[tier]:
                if remaining <= 0:
                    return "\n".join(result)
                tokens = self._estimate_content_tokens(item["content"])
                if tokens <= remaining:
                    result.append(item["content"])
                    remaining -= tokens
        return "\n".join(result)

    def _estimate_content_tokens(self, content: str) -> int:
        """粗略估算：中英混合按每 3 个字符约 1 token 折算"""
        return max(1, len(content) // 3)

    def _estimate_tokens(self, tier: str) -> int:
        """估算某一层当前占用的 token 总量"""
        return sum(
            self._estimate_content_tokens(item["content"])
            for item in self.tiers[tier]
        )
```

三个设计点值得单独说：

**层级对应不同的检索时机。** `working` 永远在上下文里，`longterm` 永远不在——它住在外部检索系统，需要时再拉回来。把长期知识常驻上下文，是最容易被忽略的一种浪费。

**淘汰按重要性，不按时间。** 纯按时间淘汰会先删掉最关键的信息（往往是最早写入的任务目标）。所以 `store` 时按 importance 排序，裁剪时从尾部丢。

**预算分层而非统一。** 不同层给不同预算，是因为它们的衰减速度不一样：任务状态几轮就过期，长期经验则可以只留索引。

## 五、落地顺序与一个警告

| 步骤 | 行动 | 为什么排这个位置 |
|---|---|---|
| 1 | 先做监控 | 把 token 花在哪看清楚，否则后面全是盲改 |
| 2 | 再做上下文压缩 | 尤其是工具回传和历史对话 |
| 3 | 然后做工具裁剪和缓存 | 减少无效调用 |
| 4 | 接着做模型路由 | 小任务别上大模型 |
| 5 | 最后做编排重构 | 把长链路拆成短状态机，牵涉面最大 |

顺序的理由：前三步都不改 Agent 的行为逻辑，可以在不动架构的前提下改完；第四步开始要区分任务类型；最后一步是重构，风险最高，所以放在监控和低风险改动都做完之后。

**一个警告**：这份清单里没有任何一项能承诺具体的节省比例。收益完全取决于你的任务分布——工具返回有多脏、提示词有多长、失败率多高。所以别信任何「照做能省 X%」的说法，包括这份清单自己。正确做法是把清单变成判据，用你自己的任务集测：改前改后各跑一遍固定任务集，看**每个成功任务的总成本**降没降、质量有没有掉。

这一点是 [按成功任务算 Token 成本](/blog/agent-token-cost-per-task/) 那篇的核心，也是整套方法与「省 Token 技巧清单」的根本区别。
