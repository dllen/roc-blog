全局顺序的三笔账？每次提交多等多久、跨区要等多久、时钟不准怎么办。分布式数据库要给出全局顺序，主流是四条路：物理时钟（TrueTime）、逻辑时钟（Lamport、向量时钟）、混合时钟（HLC）、中心化时间戳（TSO）。这条笔记把它们各自的原理与权衡写清楚了，但**三笔「各是多少」它也留成了定性判断**。这篇把它们算出来。

## 一、笔记的骨架：四条路线与它们各自买到了什么

**问题背景**：三个节点各自写入 `x=100 / x=50 / x=200`，节点必须对「x 的最终值」达成一致。笔记列出全局顺序的三条用途：**外部一致性**（事务按真实发生顺序提交）、**线性一致性**（操作瞬间生效、全局有序）、**冲突解决**（并发写入时谁真正在先）。

**路线一 · 物理时钟**：纯物理时钟的问题是**不可信**——NTP 同步有误差、时钟可能回退，一旦回退，时间戳就不再单调。TrueTime 的做法是**把不确定性显式建模**：用 GPS + 原子钟 + 定期同步，让 API 返回一个区间 `TT.now() = [t − ε, t + ε]`，而不是一个点。笔记给的口径是 **ε < 10ms**。

**commit wait 的流程**：读 `TT.now()` 取区间，**提交时间戳取区间最晚端 `s = t + ε`**，然后**等到本地时钟超过 s** 才提交——等待区间宽度就是 **2ε**。笔记的原话是「等待时间 ≈ 2ε ≈ 几毫秒」，以及每次提交额外等待 ~10ms。它把 commit wait 称作一个「悖论」：**看似增加延迟，实则降低整体延迟**——因为它用「确定的等待（固定 2ε）」换掉了「锁竞争 + 串行化 + 高延迟」的不确定延迟，在高并发场景下反而更低。

**路线二 · 逻辑时钟**：Lamport 时钟给出**因果顺序**（A 看到 B 之后，A 的时间戳必然更大），但**不区分并发**：两个互不相关的节点上 Lamport 戳的大小关系是任意的。向量时钟为每个节点维护一个向量，能**精确检测并发**（「两个向量互不包含 ⇒ 并发」），代价是元数据随节点数线性增长。

**路线三 · 混合时钟 HLC**：`(物理时间 l, 逻辑计数 c)`。物理部分保证时间戳**贴近真实时间**，逻辑部分保证**单调不减**——即使物理时钟回退，HLC 也不会回退。

**路线四 · 中心化时间戳 TSO**（TiDB）：由一个中心发号器（PD）分配时间戳与事务 ID，天然全局有序、无漂移问题。笔记记的延迟是 **同 AZ ~0.1ms、跨 Region ~1–3ms**，代价是单点与跨区延迟。

**Spanner 的落地**：地理分布 + 就近读；跨大西洋 RTT ~80–100ms，总写入延迟 ~90–110ms，本地读 ~5–20ms。关键点是 **TrueTime 保证所有副本对「时间顺序」有共识，于是每个副本可以独立判断「能否安全返回数据」**。

**PACELC 视角**：笔记把各方案映射到 PACELC 定位——要全局顺序的方案落在 P/EL 一侧，不要全局顺序的（Cassandra、DynamoDB）落在 PA/EL。

## 二、增量一：commit wait 是固定成本，不是并发成本

笔记说 commit wait「看似增加延迟，实则降低整体延迟」。这句话需要一个量化的对照：

```python
"""commit wait 的 2ε：固定代价换可预测延迟。

用笔记里的数字：ε < 10ms（GPS + 原子钟 + 定期同步）、提交时间戳取 t+ε、等待约 2ε。
只依赖标准库；输出确定性。
"""
EPS_MS = 5.0               # 真钟不确定度 ε（笔记：ε < 10ms；示例 1ms + 10ms = 11ms -> ε=5ms）
TXN_BASE_MS = 1.0           # 事务本身处理时间（估）

print("TrueTime 提交路径：读 TT.now() -> 取 s = t + ε -> 等到本地时钟超过 s -> 提交")
print("  等待区间宽度 = 2ε = %.0f ms（笔记：ε < 10ms，commit wait ~10ms）" % (2 * EPS_MS))
print()
print("%-14s %22s %26s" % ("并发事务数", "commit wait 方案", "全局锁/单点串行方案"))
for c in (1, 10, 100, 1000):
    wait_latency = TXN_BASE_MS + 2 * EPS_MS
    lock_latency = c * TXN_BASE_MS + (c - 1) * 2 * EPS_MS
    print("%-14d %14.0f ms %21.0f ms" % (c, wait_latency, lock_latency))
print()
print("  => commit wait 的延迟**与并发数无关**：永远是 2ε 的固定代价；")
print("     而串行化方案的延迟随并发线性涨（每个后来的事务要等前面全部走完 + 各自的等待）。")
print()
print("代价换到了什么：")
print("  - 固定 2ε 的等待，换来「无锁竞争、无重试、延迟可预测」（笔记原话）")
print("  - 吞吐上限 = 并发数 / 单事务耗时 = %d / %.0f ms = %s TPS" % (1000, TXN_BASE_MS + 2 * EPS_MS, format(int(1000 / (TXN_BASE_MS + 2 * EPS_MS)), ",")))
print()
print("如果 ε 变大（同步更差，或把跨区 RTT 算进 ε）：")
for eps in (1, 5, 10, 50, 100):
    lat = TXN_BASE_MS + 2 * eps
    print("  ε = %5.0f ms -> 单事务 %6.1f ms；100 并发的吞吐上限 %8s TPS"
          % (eps, lat, format(int(1000 / lat), ",")))
print()
print("判据：")
print("  - **commit wait 是固定成本，不是并发成本**：所以 TrueTime 类方案适合高并发短事务；")
print("  - 但 ε 是物理约束：笔记说 ε < 10ms 靠 GPS + 原子钟 + 定期同步，换来的是每次提交固定等 2ε。")
print("  - ε 一旦涨到 50ms 以上，2ε 就吃掉整个延迟预算（100 ms），并发吞吐上限掉到 %s TPS ——" % format(int(1000 / (TXN_BASE_MS + 100)), ","))
print("    此时方案就不再是「固定代价换可预测性」，而是「固定代价把所有事都拖慢」。")
```

三处结论：

**第一，commit wait 的延迟与并发数无关。** ε = 5ms 时单事务恒为 **11ms**（笔记自己的示例就是「1ms + 10ms = 11ms」），并发 1000 个事务时单笔仍是 11ms；而串行化（全局锁/单点）方案的延迟随并发线性涨：并发 1000 时是 **10,990ms**。**这就是「用确定的等待换不确定的等待」的准确含义**——把延迟从「取决于排队」变成「一个常数」。

**第二，代价买到的是可预测性，不是吞吐。** 并发 1000、单事务 11ms → 吞吐上限约 **90 TPS**；而 ε=1ms 时是 333 TPS、ε=10ms 时 47 TPS、ε=50ms 时只剩 **9 TPS**。判据：**ε 是这个方案的吞吐天花板**，它不是实现细节，而是物理约束（GPS + 原子钟 + 定期同步的代价）。

**第三，ε 涨过某个点，方案性质会变。** ε ≤ 10ms 时是「固定代价换可预测性」；ε ≥ 50ms 时 2ε = 100ms 已经吃掉整个延迟预算，吞吐掉到 9 TPS——**这时它不再是「固定代价」，而是「所有事都变慢」**。所以 ε 必须在设计阶段被当成一个待采购/待约束的量来谈，而不是「先上线再说」。

## 三、增量二：跨区写的延迟下界是复制 RTT，不是 commit wait

笔记说跨大西洋 RTT 80–100ms、总写入延迟 ~90–110ms。这两个数字之间是什么关系？把它拆开：

```python
"""地理距离的账：写延迟 = 复制 RTT + 本地 commit wait。

用笔记里的数字：跨大西洋 RTT 80-100ms、总写入延迟 ~90-110ms、就近读取 5-20ms。
只依赖标准库；输出确定性。
"""
REGIONS = (
    ("同机房（同 AZ）", 0.5),
    ("同城跨 AZ", 2.0),
    ("跨 Region（同大陆）", 20.0),
    ("跨大西洋", 90.0),
)
EPS_MS = 1.0        # 单区域内 ε（笔记：单区内可做到 1ms 量级）
REPLICAS = 5

print("关键前提：ε 是**区域级**的 —— 每个区域自己用 GPS + 原子钟同步，跨区不共享同一个 ε。")
print("否则跨区 RTT 90ms 会让 ε = 45ms，commit wait = 90ms，本地提交就不可接受了。")
print()
print("%-22s %10s %18s %22s %16s" % ("场景", "RTT", "写延迟(=RTT+2ε)", "就近读延迟", "跨区一致性靠"))
for name, rtt in REGIONS:
    write = rtt + 2 * EPS_MS
    read = rtt * 0.1 + 2 * EPS_MS      # 就近读：读副本在本区（估 10% 的 RTT）
    print("%-22s %8.1f ms %16.1f ms %20.1f ms %16s" % (name, rtt, write, read, "Paxos/多数派"))
print()
print("副本的代价：%d 副本跨 N 个区域，每写一次要等多数派确认" % REPLICAS)
print("  多数派确认在 leader 已就绪时约等于一次跨区 RTT/2，所以写延迟 ≈ 1.5 x RTT + 2ε：")
for rtt in (2.0, 90.0):
    print("    RTT %5.0f ms -> 写延迟 ≈ %6.1f ms" % (rtt, 1.5 * rtt + 2 * EPS_MS))
print()
print("与笔记的一致性：跨大西洋总写入延迟 ~90-110ms，本模型算出 %.0f ms（= RTT 90 + 2ε + 余量）——同量级。" % (90 + 2 * EPS_MS))
print()
print("判据：")
print("  - **跨区写入的延迟下界是复制 RTT，不是 commit wait**（2ε 只有 2ms）；")
print("    所以「就近写」优化的是用户感知，不是事务提交时间。")
print("  - ε 必须区域级：跨区共享 ε 会让本地提交等 90ms，方案直接不可用。")
print("  - 就近读延迟 ≈ 本区 RTT + 2ε（读也要过 commit wait 才能保证「读到的是已提交且不早于某时间戳」）；")
print("    跨区读到的是滞后副本，笔记给的 ~5-20ms 正是这个代价。")
```

三处结论：

**第一，跨区写的延迟几乎全是网络，不是时间戳机制。** 跨大西洋 RTT 90ms → 写延迟 **92ms**（= RTT + 2ε），与笔记的 90–110ms 同量级；**而 commit wait 只占其中 2ms**。判据：**跨区写的延迟下界是复制 RTT（外加多数派确认），不是 commit wait**。所以「就近写」优化的是用户感知和链路成本，不会让事务本身提交得更快。

**第二，ε 必须区域级，不能跨区共享。** 如果把跨区 RTT 计入同一个 ε，跨大西洋场景下 ε = 45ms → commit wait = 90ms，**本地提交要等 90ms**，方案直接不可用。Spanner 的做法是每个区域自己驯服时钟、各自的 ε 独立，跨区一致性交给 Paxos 复制与外部一致性协议，而不是靠一个全局共享的 ε。

**第三，就近读的代价是「读到的是滞后副本」。** 就近读延迟 ≈ 本区 RTT/10 + 2ε（跨大西洋约 11ms，与笔记的 ~5–20ms 同量级），但读到的副本可能落后于 leader；笔记说 TrueTime 的价值正在于**每个副本能独立判断「这个副本的数据是否已经安全」**，从而在不联系 leader 的前提下回答读请求。

## 四、增量三：漂移下 HLC 买到的到底是什么

笔记说 HLC 同时保证「贴近真实时间」和「单调不减」。这两件事在漂移下会分开——算一笔：

```python
"""时钟漂移的账：HLC 保证单调，但物理部分会偏离真实时间。

只依赖标准库；输出确定性。
"""
PPM = 500.0            # 时钟漂移率（估：普通晶振 ±20~100 ppm，校准后更好，这里取 500 ppm 保守）
PPM_GOOD = 20.0        # 校准良好（GPS/原子钟驯服后）

print("漂移率 %d ppm = %.3f%%/秒" % (PPM, PPM / 1e4))
print()
print("%-12s %20s %20s %18s" % ("时长", "漂移 %d ppm" % PPM, "漂移 %d ppm" % PPM_GOOD, "纯物理时钟"))
for label, seconds in (("1 分钟", 60), ("1 小时", 3600), ("1 天", 86400), ("1 年", 365 * 86400)):
    d_bad = seconds * PPM / 1e6 * 1000
    d_good = seconds * PPM_GOOD / 1e6 * 1000
    print("%-12s %18.0f ms %18.0f ms %18s" % (label, d_bad, d_good, "同样会漂移"))
print()
print("HLC 的保证结构：HLC = (物理时间 l, 逻辑计数 c)")
print("  - 单调性：无论物理时钟怎么跳，HLC 自身单调不减 —— 这是纯物理时钟方案没有的")
print("  - 真实性：物理部分 l 不超过真实时间太多（偏差有上界，随漂移率线性增长）")
print("  - 偏差上界：%.0f ms/小时（%d ppm）" % (3600 * PPM / 1e6 * 1000, PPM))
print()
print("三种方案在「漂移 + 中心化故障」下的取舍：")
print("%-28s %22s %22s %18s" % ("方案", "漂移下的问题", "单调性", "单点故障"))
rows = (
    ("纯物理时钟（NTP）", "时间可能回退", "无保证", "无"),
    ("HLC", "物理部分漂移，但单调", "保证", "无"),
    ("TSO（中心化发号）", "无漂移问题", "保证", "有（PD/发号器）"),
)
for r in rows:
    print("%-28s %22s %22s %18s" % r)
print()
print("判据：")
print("  - **HLC 买的是「单调」，不是「准确」**：校准良好时偏差 %d ppm -> %.0f ms/小时；" % (PPM_GOOD, 3600 * PPM_GOOD / 1e6 * 1000))
print("    漂移差时 %.0f ms/小时 —— 这个偏差只影响「按时间排序/按时间做业务判断」，不影响顺序正确性。" % (3600 * PPM / 1e6 * 1000))
```

三处结论：

**第一，HLC 买的是「单调」，不是「准确」。** 漂移 500 ppm 时物理钟 1 小时偏 **1,800ms**、1 天偏 43 秒、1 年偏 4.4 小时；校准良好（20 ppm）时是 72ms/小时、1.7 秒/天。**HLC 的逻辑计数 c 保证的是「无论物理时钟怎么跳，HLC 自身单调不减」**——这是纯物理时钟方案完全没有的性质（NTP 同步下时间可能回退，时间戳就不再单调）。

**第二，所以选型看的是「要什么保证」。** 要严格单调顺序（冲突解决、事务排序）→ HLC 或 TSO；**要时间戳贴近真实时间（TTL 过期、计费窗口、审计时间）→ 不要依赖漂移的物理钟**，因为偏差会直接变成业务误差（72ms 也许无所谓，4.4 小时就荒谬了）。

## 五、把三个模型套回本章（判据清单）

1. **commit wait 是固定成本**：ε=5ms → 单事务恒 11ms，与并发无关；串行化方案并发 1000 时是 10,990ms。延迟可预测性是它买到的东西。
2. **ε 是吞吐天花板**：ε=1/5/10/50ms → 333/90/47/9 TPS。ε ≥ 50ms 时方案性质从「固定代价」变成「全面变慢」。
3. **ε 必须区域级**：跨区共享 ε 会让 commit wait = 跨区 RTT（90ms），本地提交不可用。
4. **跨区写延迟 ≈ RTT + 2ε + 多数派确认**：跨大西洋 ~92ms，其中 commit wait 只占 2ms。
5. **就近读 ≈ 本区 RTT/10 + 2ε**：快，代价是副本可能滞后——靠「副本能否安全返回」的时间戳共识来兜。
6. **HLC 的偏差要按漂移率估**：500 ppm → 1.8 秒/小时；20 ppm → 72ms/小时。**单调性由逻辑计数保证，准确性由时钟驯服保证**，两者要分开看。
7. **TTL、计费窗口、审计时间这类业务不要用漂移的物理钟**：1 天 43 秒的偏差已经是业务事故。
8. **TSO 用单点换掉漂移问题**：延迟同 AZ ~0.1ms / 跨 Region ~1–3ms，代价是中心化依赖。

## 七、这三个模型判不了什么

- **ε=5ms、漂移 500/20 ppm、各档 RTT、单事务处理 1ms 都是估的**。笔记说 ε < 10ms 靠 GPS + 原子钟 + 定期同步保证，但**这是「平均」还是「最大」没说清**——commit wait 等待的是「最坏情况下的区间右端」，所以该用最大 ε 建模，用平均 ε 会低估延迟。
- **没算 GPS/原子钟的成本与运维**。笔记把 ε < 10ms 当成既有事实，但维持它意味着机房级的硬件与运维投入——**这才是 TrueTime 方案真正的隐藏成本**，也是很多系统最终不选它的原因。
- **没算客户端时钟回拨与 commit wait 的交互**：客户端时间戳用于「读到的数据不早于某时刻」这类判断，回拨会破坏它。
- **没算跨区写冲突的代价**。跨大西洋两个用户同时改同一行，92ms 的写延迟意味着冲突窗口是 92ms 量级——**这个数字决定了「单区域写 + 异步复制」的可行性边界**，比延迟本身更影响产品设计。
- **三个模型都没碰向量时钟**：笔记说它能精确检测并发、代价是元数据随节点数线性增长；**「线性增长」在几千节点时是几十 MB 的元数据与每次写都要带上的开销**，这个量级本文没算。

## FAQ（八、常见问题）

**commit wait 到底是变慢还是变快？** 对单笔事务是变慢（多等 2ε），对**整体延迟分布**是变快：ε=5ms 时单事务恒为 11ms（并发 1000 仍是 11ms），而串行化方案并发 1000 时是 10,990ms。**它把「取决于排队的延迟」换成「一个固定常数」**，高并发下反而更低且可预测。

**ε 怎么影响吞吐？** 它是天花板：ε=1/5/10/50ms 对应并发 1000 下的吞吐上限 333/90/47/**9 TPS**。ε ≥ 50ms 时 2ε = 100ms 吃掉整个延迟预算，方案从「固定代价换可预测性」退化成「全面变慢」。

**跨区写要等多久？** ≈ 复制 RTT + 2ε + 多数派确认：跨大西洋 RTT 90ms → **~92ms**（笔记记的 90–110ms 同量级），其中 commit wait 只占 2ms。**跨区写的延迟下界是网络，不是时间戳机制。**

**能不能跨区共享一个 ε？** 不能。跨大西洋 RTT 90ms 若计入共享 ε，则 ε=45ms、commit wait=90ms，本地提交要等 90ms，方案不可用。**ε 必须区域级**：各区域各自驯服时钟，跨区一致性交给复制协议。

**HLC 能保证时间戳准吗？** 不能，HLC 保证的是**单调**。漂移 500ppm 时物理部分 1 小时偏 1,800ms、1 天偏 43 秒；校准良好（20ppm）是 72ms/小时。**TTL、计费窗口、审计时间这类业务不能用漂移的物理钟**——顺序正确性没问题，但时间值本身会错。

**TSO 是不是更好的选择？** 它把漂移问题彻底消掉（发号器单一顺序），代价是中心化依赖与延迟（同 AZ ~0.1ms、跨 Region ~1–3ms）。**要多一个可用性风险换掉「时钟准不准」这个持续问题**——取决于你的系统是否更怕单点。
