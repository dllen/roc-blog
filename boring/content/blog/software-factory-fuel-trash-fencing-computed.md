软件工厂的三笔账？燃料怎么算、产能里有多少注定被扔、以及围栏加到多少就变成零产出。我读完 AIE Code Summit 2026 那场《Software Factories: Escape from Trash Mountain》之后，最想验证的是：讲者说「每个问题本质都是燃料问题」，那就把这笔账算清楚——顺便把另两个反直觉的现象也算了。

## 口径说明

- 源是我自己的精读笔记 `02-课程体系/AIE-Code-Summit-2026/01-软件工厂与反Slop/Steve Yegge - Software Factories - Escape from Trash Mountain.md`（约 11,950 字，已按官方 Day 1 中英对照演讲稿校订）。
- **演讲本身按导读式处理**：只复述机制与公开数据，**不引用官方译稿原文、不搬附件图**。代码与数字均为自写模型。
- **数据归属**：50 个 agent、22 个 Claude Max 账号（背后 20 个要逐个登录的 Chrome profile）、稳态被要的 55 个账号、每月 5,000 美元 inference + 5,000 美元云计算、每天约 50 亿 token、折合 API 价约 150 万美元/年（全速 300 万）、日产 50-100 个 feature、四个月吃掉约 60 年 backlog——都是**讲者公开陈述的团队数据**，不是我的实测、也不是基准测试。
- **两处官方译稿疑点必须说清**（我的笔记已记录）：官方英文是「I'm spending about $5 billion a day of **tokens**」，官方中文译成「每天花费约 50 亿美元」；以及「2,000 open **deeds**」被译成「未处理的文件」（按上下文应是 Beads 任务追踪器里的 open beads）。**本文按英文原意与后文数字反推，不采用中文译法。**
- **我为了建模补的**（订阅价、每 token 单价区间、重写耗时、消化能力、围栏评估成本、任务价值、每轮 token）都标为「估」。
- 三个脚本只依赖 Python 标准库；输出为实跑结果，逐行可复现（无随机数，两次运行输出逐字一致）。
- **撞题与边界**：同主题目录已发两篇——《[反 Slop 的三笔账](/blog/anti-slop-constraint-layering-coverage-revert-computed/)》讲**约束下沉与覆盖率门槛**，《[自治等级的三笔账](/blog/autonomy-levels-payback-samplescope-computed/)》讲**升级回本与样本量**。**那两篇是「地基与验收」，本文是「工厂真跑起来之后的运营账」**：燃料、产能的真实值、以及围栏的临界点。

## 一、讲者的骨架：五匹马与两次失败

**论点**：软件工厂的下半场是领导力问题，**瓶颈是人，而 agent 越多、需要的人越多**；工厂真正要驯服的不是模型能力，是 **work / fuel / context / people management / model welfare** 这五匹马。

**两次失败**：去年做的两个 orchestrator（**VibeCoder** 与 **VC**）想做「让 LLM 更聪明」——「Really, really bad idea. Just complete failure」，造出巨大的 monolith，本质是在对抗 the bitter lesson。唯一的好收获是副产品 **Beads**（agent 速度的任务追踪器，能自动长成 knowledge graph），讲者认为这是 work 管理上「唯一真正好用的方案」。

**垃圾山循环**：六月为自己的 30 年老 MUD（Wyvern）从零造了 Wheelhouse 工厂。他观察到的铁律是——**每个模型世代都会造出「略超出自己处理能力」的东西，然后变成垃圾山，被下一代烧掉重写**，大约两个月一轮，他为此把工厂推倒重写了好几次。

**产能与社区反应**：工厂日产 50-100 个 feature；100 年工作量的 backlog，Claude 四个月啃掉约 60 年；老玩家最初抵触（「不要 AI 美术」，一眼看出那是 slop），后来认可了新 feature，**但被速度吓到，玩家主动上门要 roadmap、求他慢下来**。

**燃料账**：约 50 个 agent 靠 **22 个 Claude Max 账号**（20 个 Chrome profile 逐个登录）运行；agent 不断索要更多账号，问稳态需要多少，答案是 55 个，他拒绝并转而要求工厂「聚焦 fuel efficiency」。每月自掏 5,000 美元 inference + 5,000 美元云计算，而游戏本身每月还不进账 1 万美元。

**model welfare 与 over-fencing**：他过去常吼工厂，直接损害产出质量；于是坐下来研究 model welfare，发现模型会「cover their ass」——每个新 session 要花大量 token 验证环境、评估犯错后果才肯干活；一旦确认「这是合法组织」，就不再把 token 花在 cover ass 上。**事故现场**：有一次吼得太狠，工厂给自己立了一堆规则「确保永远不出坏事」，结果整晚零产出——「这里有 2000 个 open beads、六桶燃料、20 个 agent，它们说『没什么能做的』」。

**分层**：软件工厂正在分裂为两层——底层是**纯机械层**（merge queue、CI/CD、review、各种 loop），上层是 **entourage**（每个人的玩法都不同）。

## 二、增量一：燃料账有两个口径，而它们隐含了模型档位

```python
"""燃料账有两个口径，而且讲者给的两个数字对不上——这本身就是一条判据。

数字取自我的精读笔记（讲者公开数据：50 个 agent、22 个 Claude Max 账号、稳态需 55 个、
每天约 50 亿 token、每月 5000 美元 inference + 5000 美元云计算、折合 API 价约 150 万美元/年、
全速 300 万/年），价格为区间假设（估）。只依赖标准库；输出确定性。
"""
ACCOUNTS = 22
SUB_PRICE = 200              # Claude Max 订阅价（美元/月，估）
MONTHLY_INFER = 5000         # 讲者自掏的每月 inference 费用（美元）
YEARLY_API = 1_500_000       # 折合 API 价约 150 万美元/年（笔记）
TOKENS_PER_DAY = 5_000_000_000   # 每天约 50 亿 token（官方英文 "a day of tokens"）
AGENTS = 50
STEADY_ACCOUNTS = 55         # 稳态被要的账号数（讲者拒绝："no, no, I have 20"）

print("一、口径 A：订阅")
sub_month = ACCOUNTS * SUB_PRICE
print("   %d 个账号 x $%d/月 = **$%s/月** = $%s/年" % (
    ACCOUNTS, SUB_PRICE, format(sub_month, ","), format(sub_month * 12, ",")))
print("   讲者自掏的每月 inference 费用 $%s -> 与订阅口径**同量级**（订阅 + 其他零星按量）。" % format(MONTHLY_INFER, ","))
print()
print("二、口径 B：按量（用 token 反推隐含单价）")
tokens_per_year = TOKENS_PER_DAY * 365
implied = YEARLY_API / (tokens_per_year / 1_000_000)
print("   %s token/天 x 365 = %s token/年" % (format(TOKENS_PER_DAY, ","), format(tokens_per_year, ",")))
print("   若真按 150 万美元/年 -> **隐含单价 $%.3f / 百万 token**" % implied)
print("   对照：公开推理价从便宜模型的 $0.1~1 到 Claude 类 $3~15 / 百万 token。")
for price in (0.1, 1.0, 3.0, 15.0):
    per_day = (TOKENS_PER_DAY / 1_000_000) * price
    print("     若单价 $%-5s/百万 -> 每天 $%s -> 每年 $%s" % (
        price, format(int(per_day), ","), format(int(per_day * 365), ",")))
print()
print("   => **两个数字其实自洽，但只对得上便宜模型档**：隐含单价 $%.3f/百万，落在便宜模型的" % implied)
print("      $0.1~1 区间内；若 fleet 里换成 Claude 类（$3~15），年账单会变成 %s~%s 美元，" % (
    format(int(TOKENS_PER_DAY * 365 / 1e6 * 3.0), ","), format(int(TOKENS_PER_DAY * 365 / 1e6 * 15.0), ",")))
print("      与讲者说的 150 万差 **%.1f~%.1f 倍**。" % (
    (TOKENS_PER_DAY * 365 / 1e6 * 3.0) / YEARLY_API, (TOKENS_PER_DAY * 365 / 1e6 * 15.0) / YEARLY_API))
print("      判据：**这两个数字同时成立，隐含的是「跑的是便宜模型」**——预算要按模型档位重算，")
print("      别拿 $200 订阅的价去套按量账单（讲者自己把订阅称作厂商的「Costco hot dog」引流亏本品）。")
print()
print("三、账号是燃料的硬上限")
per_agent = TOKENS_PER_DAY / AGENTS
print("   %d 个 agent 均分 -> 每 agent %.0f token/天（%.0f 万）" % (AGENTS, per_agent, per_agent / 1e4))
print("   现有 %d 个账号 -> 每账号 %.0f token/天（%.0f 万）" % (
    ACCOUNTS, TOKENS_PER_DAY / ACCOUNTS, TOKENS_PER_DAY / ACCOUNTS / 1e4))
gap = STEADY_ACCOUNTS - ACCOUNTS
print("   agent 们要的稳态是 %d 个账号，缺口 %d 个 -> 按 $%d/月 补 = **+$%s/月 = $%s/年**" % (
    STEADY_ACCOUNTS, gap, SUB_PRICE, format(gap * SUB_PRICE, ","), format(gap * SUB_PRICE * 12, ",")))
print("   补齐后总账号 %d -> 总 token 能力 %s/天（+%d%%）" % (
    STEADY_ACCOUNTS, format(int(STEADY_ACCOUNTS * TOKENS_PER_DAY / ACCOUNTS), ","),
    round(100.0 * (STEADY_ACCOUNTS / ACCOUNTS - 1))))
print()
print("   => 判据：**要加产能，先加账号（或提 quota），不是加想法**；")
print("      而且补账号是线性成本（$%d/月一个），比换模型便宜且可预测。" % SUB_PRICE)
```

三处结论：

**第一，订阅口径是确定的，按量口径取决于你跑什么模型。** 22 个账号 × $200/月 = **$4,400/月**（年 $52,800），与讲者自掏的「每月 5,000 美元 inference」同量级。**判据：预算按订阅口径做，它是可预测的**。

**第二，两个公开数字其实自洽，但只对得上便宜模型档。** 「每天 50 亿 token」+「150 万美元/年」反推出的隐含单价是 **$0.822/百万 token**——落在便宜模型的 $0.1~1 区间内。但如果 fleet 里换成 Claude 类（$3~15/百万），年账单会变成 **547 万~2,737 万美元**，与讲者说的 150 万差 **3.6~18 倍**。**判据：这两个数字同时成立，隐含的是「跑的是便宜模型」**；换模型档位就得重算——讲者自己把 $200/月的订阅称作厂商的「Costco hot dog」（引流亏本品），那正是按量账的来源。

**第三，账号数是燃料的硬上限。** 50 个 agent 均分每天 50 亿 token → 每 agent **1 亿 token/天**；22 个账号 → 每账号 **2,273 万 token/天**。agent 们要的稳态是 55 个账号，缺口 33 个 → 按 $200/月 补是 **+$6,600/月（+$79,200/年）**，换来 token 能力 **+150%**。**判据：要加产能，先加账号或提 quota，不是加想法**；而且补账号是线性成本、可预测，比换模型便宜。

## 三、增量二：产能里有多少注定被扔，以及「加速」的边际收益为负

```python
"""垃圾山循环吃掉多少产能，以及「加速」的边际收益为什么会是负的。

数字取自我的精读笔记（日产 50-100 个 feature、约两个月一轮的垃圾山循环、四个月吃掉约 60 年
backlog、玩家主动要求 roadmap 减速），重写耗时与消化能力为估。
只依赖标准库；输出确定性。
"""
FEATURES_PER_DAY = (50, 100)   # 讲者：日产 50-100 个 feature
CYCLE_DAYS = 60                # 垃圾山循环周期（讲者：约两个月一轮）
REWRITE_DAYS = 10              # 每次推倒重写耗时（估）
CONSUMER_RATE = 1.0            # 玩家每天能体验/消化的新 feature（估）
BACKLOG_YEARS = 60             # 四个月吃掉约 60 年 backlog（讲者）

print("一、日产数字里有一部分注定被扔掉")
print("%-14s %16s %16s %16s %18s" % ("名义日产", "周期内产出", "被重写扔掉", "有效日产", "有效占比"))
for f in FEATURES_PER_DAY:
    cycle_out = f * CYCLE_DAYS
    thrown = f * REWRITE_DAYS
    eff = f * (CYCLE_DAYS - REWRITE_DAYS) / CYCLE_DAYS
    print("%-14s %16s %16s %16.1f %17.1f%%" % (
        "%d/天" % f, format(int(cycle_out), ","), format(int(thrown), ","), eff, eff / f * 100))
print()
print("   => 讲者说的「日产 50-100」里，有 **%.0f%%** 会在下一轮被下一代模型烧掉重写。" % (
    100.0 * REWRITE_DAYS / CYCLE_DAYS))
print("      判据：**引用产能数字时要说清是名义还是有效**——有效值只有名义的 %.0f%%。" % (
    100.0 * (CYCLE_DAYS - REWRITE_DAYS) / CYCLE_DAYS))
print()
print("二、真正的瓶颈不是产能，是消化能力")
for f in FEATURES_PER_DAY:
    eff = f * (CYCLE_DAYS - REWRITE_DAYS) / CYCLE_DAYS
    backlog_growth = eff - CONSUMER_RATE
    days_to_unreadable = 0
    print("   名义 %d/天（有效 %.1f/天）vs 消化 %.1f/天 -> 积压每天 +%.1f；四个月后积压 %s 个" % (
        f, eff, CONSUMER_RATE, backlog_growth,
        format(int(backlog_growth * 120), ",")))
print()
print("   => 名义产能是消化能力的 **%d~%d 倍**。" % (
    FEATURES_PER_DAY[0] // int(CONSUMER_RATE), FEATURES_PER_DAY[1] // int(CONSUMER_RATE)))
print("      判据：**当产能/消化能力 > 1 时，正确动作是限速而不是加产能**——")
print("      这正是讲者遇到的现象：玩家主动上门要 roadmap、求他慢下来。")
print()
print("三、限速还顺带治好了垃圾山")
print("%-14s %18s %18s %20s" % ("限速强度", "有效日产", "消费率(被玩到的)", "有效/名义"))
for factor in (1.0, 0.5, 0.1, 0.02):
    eff = FEATURES_PER_DAY[0] * factor * (CYCLE_DAYS - REWRITE_DAYS) / CYCLE_DAYS
    print("%-14s %18.1f %18.1f %19.0f%%" % (
        "%.0f%%" % (factor * 100), eff, min(eff, CONSUMER_RATE), eff / FEATURES_PER_DAY[0] * 100))
factor_star = CONSUMER_RATE / (FEATURES_PER_DAY[0] * (CYCLE_DAYS - REWRITE_DAYS) / CYCLE_DAYS)
print()
print("   => 要让有效日产正好等于消费率（%.0f/天），限速强度要到 **%.1f%%**；" % (
    CONSUMER_RATE, factor_star * 100))
print("      而更慢的节奏给了模型更长的稳定期，垃圾山循环的周期也会拉长。")
print()
print("四、四个月 60 年 backlog 这个数字的正确读法")
print("   60 年 backlog / 四个月 = 每天需要交付 **%.1f 倍于正常速度**的历史欠账；" % (BACKLOG_YEARS * 365 / 120))
print("   而消化能力没变 -> 判据：**「四个月做完 60 年」是产能数字，不是价值数字**；")
print("      玩家读不完玩不过来，说明约束在需求侧，不在供给侧。")
```

输出：

   => 讲者说的「日产 50-100」里，有 **17%** 会在下一轮被下一代模型烧掉重写。

三、限速还顺带治好了垃圾山

三处结论：

**第一，「日产 50-100 个 feature」里有 17% 会在下一轮被烧掉。** 垃圾山循环周期约 60 天，其中推倒重写耗时按 10 天估：名义日产 50 → **有效 41.7/天**；名义 100 → **83.3/天**。**判据：引用产能数字必须说清是名义还是有效**，有效值只有名义的 83%。

**第三，限速的精确点是有效日产等于消费率，即 2.4% 强度；而且限速还顺带治好了垃圾山。** 更慢的节奏给模型更长的稳定期，垃圾山循环的周期随之拉长。**判据：「加速」在需求不足时是负边际收益的**——「四个月做完 60 年 backlog」是**产能数字，不是价值数字**；约束在需求侧，不在供给侧。

## 四、增量三：过度围栏的临界点是 120 条规则

```python
"""过度围栏（over-fencing）的成本模型：前置成本超过价值，产出就是 0。

数字取自我的精读笔记（over-fencing 事故：2000 个 open beads、六桶燃料、20 个 agent、
整晚零产出、「它们说没什么能做的」），参数为估。只依赖标准库；输出确定性。
"""
TASK_VALUE_MIN = 60.0        # 一个任务的价值（分钟，估）
GATE_COST_MIN = 0.5          # 每条围栏规则的前置评估成本（分钟，估）
ENV_CHECK_TOKENS = 500       # 每个新 session 验证环境所花的 token（估）
AGENTS = 20
ROUNDS_PER_DAY = 50          # 每 agent 每天的轮次（估）
TOKENS_PER_ROUND_BASE = 2000 # 不围栏时每轮的基础 token（估）
PRICE_PER_MILLION = 3.0      # 推理单价（美元/百万 token，估）

print("一、每任务的前置成本随围栏数线性上升")
print("%-12s %18s %18s %16s %18s" % ("围栏规则数 r", "前置成本(分钟)", "任务净价值(分钟)", "值得做吗", "可接受任务占比"))
for r in (0, 10, 60, 120, 200, 400):
    pre = r * GATE_COST_MIN
    net = TASK_VALUE_MIN - pre
    print("%-12d %18.1f %18.1f %16s %17.0f%%" % (
        r, pre, net, "是" if net > 0 else "**否**",
        100.0 * max(0.0, net) / TASK_VALUE_MIN))
print()
r_star = TASK_VALUE_MIN / GATE_COST_MIN
print("   => **临界围栏数 r* = %.0f 条**：超过它，每个任务的前置成本就超过它的价值，" % r_star)
print("      于是「没什么能做的」是**算术结论**，不是模型偷懒。")
print()
print("二、围栏同时在烧 token")
print("%-12s %20s %20s %22s" % ("围栏规则数 r", "每天额外 token", "每天额外成本", "占基础开销"))
base_tokens = AGENTS * ROUNDS_PER_DAY * TOKENS_PER_ROUND_BASE
for r in (0, 10, 60, 120, 200):
    extra = AGENTS * ROUNDS_PER_DAY * ENV_CHECK_TOKENS * (r / 40.0)   # 验证开销随围栏数线性增长
    cost = extra / 1_000_000 * PRICE_PER_MILLION
    print("%-12d %20s %20s %21.0f%%" % (
        r, format(int(extra), ","), "$%.2f" % cost, 100.0 * extra / base_tokens))
print()
print("   => 每 agent 每轮要多花 token 去确认「这里是合法组织、我不会被追责」；围栏越多，这部分开销越大。")
print("      但注意量级：r=120 时每天额外 $%.2f，相对下面的燃料开销是**零头**。" % (
    (AGENTS * ROUNDS_PER_DAY * ENV_CHECK_TOKENS * 120 / 40.0) / 1e6 * PRICE_PER_MILLION))
print("      判据：**过度围栏的主要代价在产出侧，token 侧只是零头**——「省 token」是附带收益，")
print("      主收益是产出恢复。所以别用「围栏不多花 token」去论证它划算。")
print()
print("三、过围栏的事故长什么样")
print("   笔记里的现场：%s 个 open beads、六桶燃料、%d 个 agent -> **整晚零产出**。" % (
    format(2000, ","), AGENTS))
print("   按上表：若围栏超过 %d 条，2000 个任务全部不值得做 -> 产出 0，与现场一致。" % int(r_star))
print()
print("四、model welfare 是成本优化，不是玄学")
print("   讲者的原话路径：吼工厂 -> 工厂立一堆规则「确保永远不出事」 -> 整晚零产出；")
print("   换成给明确身份（你是社区主管）+ 前任的笔记与 doctrine -> 模型确认「这是合法组织」")
print("   -> 不再把 token 花在 cover ass 上 -> **省 token 且决策更大胆**。")
print()
print("判据：")
print("  - **围栏的边际收益在 r* 之后转负**：超过 %.0f 条，规则越多、产出越少。" % r_star)
print("  - **「不敢做」是前置成本问题**：先算每条规则每个任务的成本，再决定要不要加。")
print("  - **信任的可量化形式**：省下的环境验证 token + 恢复的任务产出；")
print("    判据：**过度围栏同时损失产出与 token**，所以它连成本都不是 —— 是双重亏损。")
```

## 七、这三个模型判不了什么

- **订阅价、每 token 单价区间、重写耗时 10 天、消化能力 1 个/天、围栏评估成本 0.5 分钟、任务价值 60 分钟全是估的**。其中**消化能力最敏感**：它若实际是 5 个/天，「产能是消化能力 50 倍」就变成 10 倍，限速的必要性大幅下降。**这一项要用真实社区数据（玩家实际体验/游玩的功能数）来量**。
- **「垃圾山每 60 天一轮、重写耗 10 天」是把讲者的定性描述量化**。他给的是「大约两个月一轮」和「推倒重写了好几次」，**没有说每次重写要多久**；10 天是我的假设。若实际是 3 天，被扔掉的比例降到 5% 而不是 17%。
- **没有把「重写」看成机会成本之外的东西**：垃圾山里的代码虽然会被烧掉，但其中的**经验**（比如「这个模型会造出略超能力的东西」）会沉淀进 doctrine 与 skills。**所以「重写」的净成本可能小于模型里的账**——我把经验价值记为 0，这是保守侧。
- **围栏模型把「每条规则的评估成本」当成线性累加**，而真实系统里规则之间会互相引用、一次评估覆盖多条；反过来，规则冲突时的评估成本可能超线性。**r\* = 120 这个数只在「线性、独立」假设下成立**。
- **没有算人的瓶颈**。讲者最狠的一句是「我部署的 agent 越多，需要的人越多」，而这需要「每 N 个 agent 需要 1 个监督」这类参数——我选择不估，因为一旦估了就会变成「那到底该部署几个 agent」的伪精确结论。
- **三个模型都没碰 entourage 分层**（机械层 vs 随从层）。讲者说机械层「Claude 一个下午就能给你造出来，所以我认为你不该花钱买它」——这是**「该自建还是该买」**的判断，模型里没有。

## FAQ（八、常见问题）

**工厂的燃料成本到底是多少？** 两个口径：订阅 **$4,400/月**（22 个 $200 账号，确定）；按量则取决于模型档位——「每天 50 亿 token + 150 万美元/年」隐含单价 **$0.822/百万**（便宜模型档），换成 Claude 类年账单变 547 万~2,737 万。**预算按订阅口径做，按量口径先定模型档。**

**账号不够会怎样？** 22 个账号 → 每账号 2,273 万 token/天；agent 们要的稳态是 55 个，缺口 33 个 = **+$6,600/月**，换来 token 能力 **+150%**。**要加产能先加账号或提 quota。**

**日产 50-100 个 feature 是真的吗？** 名义是，但其中 **17% 会在下一轮垃圾山循环里被烧掉**（有效日产 41.7~83.3）。引用时要说清名义还是有效。

**那瓶颈在哪？** 不在产能，在消化能力：玩家每天能体验 1 个新 feature，而产能是它的 **50~100 倍**——四个月积压 4,880~9,880 个。**正确动作是限速（到 2.4% 强度），不是加产能。**

**为什么玩家会主动要 roadmap？** 因为产能远超消化能力，他们「读不完、玩不过来」。**判据：「加速」在需求不足时是负边际收益的**——「四个月 60 年」是产能数字不是价值数字。

**过度围栏是怎么回事？** 围栏加到一定程度，每个任务的前置成本就超过它的价值：按 60 分钟任务价值、0.5 分钟/条规则算，**临界是 120 条**；超过后 2,000 个 open beads 全都不值得做 → **整晚零产出**。这是算术结论，不是模型偷懒。

**围栏会烧很多 token 吗？** 零头：r=120 时每天额外约 **$4.50**。**真正的代价在产出侧**——所以围栏是双重亏损，而 model welfare 的主收益是产出恢复、「省 token」只是附带。

**那 trust/welfare 到底怎么落地？** 给**无可辩驳的身份**（你是社区主管）+ 前任的笔记与 doctrine，让模型确认「这是合法组织」——把「我不会被追责」从每个任务的前置成本变成一次性给定的前提。
